Antes de escrever HTML, vale entender por que a Web existe e por que ela se tornou
uma das plataformas mais importantes da computação. A Web não é apenas um lugar para
publicar páginas: ela é uma arquitetura para identificar, acessar, conectar e
apresentar recursos distribuídos pela Internet.

## Objetivo

Entender a origem da Web, diferenciar Web de Internet, reconhecer o papel de URL,
HTTP e HTML e explicar como clientes, servidores, links, cache, estado e padrões
abertos sustentam a navegação e a escala da Web.

## Por Que a Web Importa?

A Web tornou possível publicar informações e sistemas que podem ser acessados de
máquinas diferentes, em lugares diferentes, usando navegadores diferentes. Essa
capacidade é importante porque reduz barreiras:

- quem publica não precisa controlar o computador de quem acessa;
- quem acessa não precisa instalar uma aplicação específica para cada site;
- links permitem conectar conteúdos criados por pessoas e organizações diferentes;
- padrões abertos permitem que navegadores, servidores e ferramentas evoluam juntos.

<Aside type="note" title="Web não é sinônimo de Internet">
  A Internet é a infraestrutura de redes conectadas. A Web é um dos serviços que
  rodam sobre essa infraestrutura. E-mail, chamadas de vídeo, jogos online e
  mensageria também usam a Internet, mas não são necessariamente Web.
</Aside>

## Origem no CERN

A Web nasceu no CERN, laboratório europeu de pesquisa em física. O problema inicial
era prático: pesquisadores, documentos e sistemas estavam espalhados em computadores
diferentes, usando formatos e ferramentas diferentes. Encontrar e conectar essas
informações era difícil.

Antes da Web, compartilhar informação entre grupos diferentes exigia combinar várias
coisas ao mesmo tempo: qual arquivo seria criado, como ele seria enviado e qual
programa conseguiria abri-lo. Uma equipe poderia escrever um relatório em um formato
de editor específico, enviar por e-mail, FTP ou rede interna, e a outra pessoa ainda
precisaria ter o programa certo para ler aquele arquivo. Mesmo quando o arquivo
chegava, ele ficava separado dos outros documentos: não havia um padrão simples para
apontar de um documento para outro, navegar por links e acessar tudo por uma mesma
ferramenta.

Por exemplo: alguém criava um arquivo `relatorio.doc`, enviava por e-mail, e quem
recebia precisava de um editor compatível. Outro grupo publicava dados em um servidor
FTP, mas era necessário saber o endereço, a pasta correta e o nome do arquivo. Em
outro caso, uma documentação ficava presa a um sistema interno que só funcionava em
determinados computadores. A informação existia, mas estava fragmentada.

Em 1989, Tim Berners-Lee propôs um sistema de hipertexto distribuído para melhorar o
compartilhamento de informação entre cientistas. Em 1990, com a colaboração de
Robert Cailliau, a proposta ganhou forma como o projeto WorldWideWeb. A primeira
implementação reuniu navegador, servidor, protocolo HTTP, endereços para localizar
recursos e HTML para estruturar documentos.

O primeiro site ficou hospedado em [info.cern.ch](https://info.cern.ch/) e
explicava o próprio projeto: o que era a World Wide Web, como usar um navegador e
como criar um servidor Web.

Essa evolução aparece em documentos importantes da época. A proposta
[“Information Management: A Proposal”](https://cds.cern.ch/record/369245/files/dd-89-001.pdf),
de 1989, apresenta o problema de gerenciamento de informações no CERN. A proposta
[“WorldWideWeb: Proposal for a HyperText Project”](https://www.w3.org/Proposal.html),
de 1990, descreve um projeto de hipertexto para conectar diferentes fontes de
informação por uma interface comum. Em 1992, o artigo
[“World-Wide Web: The Information Universe”](https://www.emerald.com/intr/article-abstract/2/1/52/184536/World-Wide-Web-The-Information-Universe)
apresenta a Web como uma iniciativa prática para criar um universo global de
informação usando tecnologias disponíveis.

Em 1994, a visão aparece novamente sistematizada no artigo
[“The World-Wide Web”](https://cacm.acm.org/research/the-world-wide-web-2/),
publicado na *Communications of the ACM* por Tim Berners-Lee, Robert Cailliau, Ari
Luotonen, Henrik Frystyk Nielsen e Arthur Secret. O texto apresenta a Web como um
sistema de hipertexto distribuído, baseado em documentos, links, clientes,
servidores e protocolos abertos.

<Aside type="tip" title="A Web cresceu porque era conectável">
  A ideia central não era criar um único repositório central, mas permitir que
  qualquer documento pudesse apontar para outro por meio de links. Essa decisão
  tornou a Web descentralizada e escalável.
</Aside>

## O Tripé da Web

Para uma página aparecer no navegador, três peças trabalham juntas. Elas não fazem a
mesma coisa, mas se completam.

<div class="not-content" style="display: grid; gap: 1rem;">
  <Card title="URL" icon="link">
    Identifica onde está um recurso, como uma página, imagem, arquivo ou endpoint de
    API. Exemplo: `https://example.com/produtos/`.
  </Card>

  <Card title="HTTP" icon="server">
    Define como cliente e servidor conversam. O navegador faz uma requisição e o
    servidor responde com o recurso solicitado, um erro ou um redirecionamento.
  </Card>

  <Card title="HTML" icon="seti:html">
    Estrutura o conteúdo principal da página. Ele informa ao navegador quais partes
    são títulos, parágrafos, links, listas, imagens, formulários e regiões da página.
  </Card>
</div>

Em termos simples:

| Peça | Pergunta que responde | Exemplo |
| ---- | --------------------- | ------- |
| URL | Onde está o recurso? | `https://www.w3.org/standards/` |
| HTTP | Como pedir e receber esse recurso? | `GET /standards/` |
| HTML | Como o conteúdo recebido é estruturado? | `<h1>Web Standards</h1>` |

A tabela separa as responsabilidades de cada peça. No acesso real, elas aparecem
juntas no fluxo descrito a seguir.

## O Caminho de Uma Página

Quando alguém acessa uma página, muita coisa acontece rapidamente:

<figure>
  <img
    src="../../../../dw/imgs/html/http-client-server-flow.svg"
    alt="Fluxo HTTP: navegador cliente envia uma requisição HTTP para o servidor Web, que devolve uma resposta HTTP com HTML para o navegador renderizar a página."
  />
  <figcaption>
    O navegador usa a URL para descobrir o recurso, envia uma requisição HTTP ao
    servidor e recebe uma resposta que pode conter HTML, imagens, CSS, JavaScript ou
    outros arquivos.
  </figcaption>
</figure>

<Steps>

1. A pessoa digita uma URL ou clica em um link.

2. O navegador descobre qual servidor deve responder por aquele endereço.

3. O navegador envia uma requisição HTTP pedindo o recurso.

4. O servidor devolve uma resposta, geralmente com um documento HTML.

5. O navegador lê o HTML, monta a estrutura da página e busca recursos relacionados,
   como CSS, JavaScript, imagens e fontes.

6. A página é renderizada para a pessoa interagir.

</Steps>

Esse fluxo explica por que HTML, CSS e JavaScript aparecem juntos no desenvolvimento
Web. HTML estrutura o conteúdo, CSS define a apresentação visual e JavaScript
acrescenta comportamento.

<Aside type="note" title="O navegador não carrega apenas HTML">
  A função inicial do navegador era abrir documentos de hipertexto, mas os
  navegadores atuais entendem muitos outros recursos: CSS, JavaScript, imagens,
  fontes, áudio, vídeo, PDF, JSON e arquivos usados por APIs. Quando o navegador
  recebe um formato que ele não sabe exibir, executar ou incorporar, ele pode
  acionar o download do arquivo ou delegar a abertura para um aplicativo compatível,
  dependendo do tipo do arquivo, dos cabeçalhos HTTP e da configuração do usuário.
</Aside>

<Aside type="tip" title="Cliente e servidor são papéis">
  O mesmo computador pode executar um cliente e um servidor ao mesmo tempo. Durante
  o desenvolvimento, é comum abrir o navegador como cliente e rodar um servidor local
  em `localhost`, por exemplo em `http://localhost:8080`.
</Aside>

## HTTP, Estado e Escala

HTTP é um protocolo **stateless**: cada requisição deve trazer as informações
necessárias para o servidor entendê-la, sem depender automaticamente da requisição
anterior. Isso não significa que aplicações Web não tenham login, carrinho de compras
ou preferências; esses estados costumam ser construídos por cima do HTTP com cookies,
tokens, sessões no servidor ou armazenamento no navegador.

Essa característica ajuda a escalar o acesso. Como uma requisição HTTP pode ser
tratada de forma relativamente independente, várias máquinas podem responder pelo
mesmo site atrás de um balanceador de carga. Também fica mais fácil usar caches,
CDNs e proxies para reaproveitar respostas quando o conteúdo não muda a cada acesso.

<Aside type="tip" title="Cache reduz trabalho repetido">
  Se uma imagem, um arquivo CSS ou uma página não mudou, o navegador ou um cache
  intermediário pode reaproveitar uma resposta anterior. Isso reduz latência,
  economiza banda e diminui a carga sobre o servidor de origem.
</Aside>

## Hipertexto e Links

O diferencial da Web está no hipertexto: documentos que apontam para outros
documentos. Um link transforma um texto em porta de entrada para outro recurso.

Isso muda a forma de publicar conhecimento. Uma página não precisa conter tudo; ela
pode referenciar documentação, imagens, artigos, sistemas, arquivos e APIs. Para
quem desenvolve, entender links é entender uma das ideias mais importantes da Web:
recursos independentes podem formar uma rede navegável.

Essa navegação também pode atravessar servidores diferentes sem que a pessoa precise
pensar nisso. Um link em `ifpb.edu.br` pode apontar para `w3.org`, `developer.mozilla.org`
ou `info.cern.ch`; ao clicar, o navegador resolve o novo endereço, conversa com outro
servidor e apresenta a próxima página dentro da mesma experiência de navegação.

## Padrões Abertos

A Web funciona porque suas peças principais são especificadas publicamente. Um
navegador não precisa ser feito pela mesma empresa que criou o servidor, e uma
página não precisa ser escrita para um único dispositivo.

Em 1994, Tim Berners-Lee fundou o
[World Wide Web Consortium (W3C)](https://www.w3.org/) no MIT para coordenar a
evolução desses padrões. O W3C publica especificações e recomendações que ajudam
navegadores, servidores, ferramentas de autoria e tecnologias assistivas a
interpretarem a Web de forma compatível.

Esse compromisso com padrões abertos sustenta características importantes:

- interoperabilidade entre navegadores, servidores e sistemas;
- acessibilidade para diferentes pessoas e dispositivos;
- preservação de links e documentos ao longo do tempo;
- possibilidade de aprender, inspecionar e criar usando ferramentas comuns.

## Perguntas de revisão

**1. Qual problema motivou a criação da Web no CERN?**

<details>
  <summary>Possível resposta</summary>

  A dificuldade de compartilhar, encontrar e conectar informações entre cientistas,
  documentos e sistemas distribuídos em computadores diferentes.
</details>

**2. Por que Web e Internet não são a mesma coisa?**

<details>
  <summary>Possível resposta</summary>

  A Internet é a infraestrutura de redes conectadas. A Web é um serviço construído
  sobre essa infraestrutura, usando tecnologias como URL, HTTP e HTML.
</details>

**3. Qual é o papel de uma URL?**

<details>
  <summary>Possível resposta</summary>

  Identificar um recurso na Web para que o navegador saiba qual endereço acessar.
</details>

**4. Qual é o papel do HTTP?**

<details>
  <summary>Possível resposta</summary>

  Definir a comunicação entre cliente e servidor: o cliente faz uma requisição e o
  servidor responde com um recurso, erro ou redirecionamento.
</details>

**5. Qual é o papel do HTML no tripé da Web?**

<details>
  <summary>Possível resposta</summary>

  Estruturar o conteúdo recebido pelo navegador, indicando títulos, parágrafos,
  links, imagens, listas, formulários e outras partes da página.
</details>

**6. Dê exemplos de clientes HTTP além do navegador.**

<details>
  <summary>Possível resposta</summary>

  Ferramentas de linha de comando como `curl` e `wget`, extensões como REST Client
  no VS Code, ferramentas gráficas como Postman e Insomnia e ferramentas de segurança
  como Burp Suite também podem enviar requisições HTTP.
</details>

**7. Qual é a diferença entre um servidor HTTP de produção e um servidor local de desenvolvimento?**

<details>
  <summary>Possível resposta</summary>

  Um servidor de produção precisa ficar disponível continuamente, normalmente 24/7,
  e lidar com segurança, desempenho e múltiplos acessos. Um servidor local de
  desenvolvimento costuma ser temporário, usado para testar arquivos, páginas ou
  APIs durante a criação do projeto.
</details>

**8. Como links permitem navegar entre servidores diferentes?**

<details>
  <summary>Possível resposta</summary>

  Um link pode apontar para qualquer URL. Ao clicar, o navegador resolve o novo
  endereço, conversa com o servidor correspondente e mostra a próxima página, mesmo
  que ela esteja em outro domínio.
</details>

**9. Por que padrões abertos são importantes para a Web?**

<details>
  <summary>Possível resposta</summary>

  Porque permitem que diferentes navegadores, servidores, ferramentas e dispositivos
  interpretem a Web de modo compatível, sem depender de um único fabricante.
</details>

**10. Por que os documentos iniciais da Web são referências importantes?**

<details>
  <summary>Possível resposta</summary>

  Porque registram a passagem de um problema prático de compartilhamento de
  informação para uma solução técnica integrada, combinando hipertexto, documentos,
  links, navegadores, servidores, endereços e protocolos abertos.
</details>

**11. Por que o fato de HTTP ser stateless ajuda na escala da Web?**

<details>
  <summary>Possível resposta</summary>

  Porque cada requisição pode ser tratada de modo mais independente. Isso facilita o
  uso de vários servidores, balanceamento de carga, caches, CDNs e proxies para
  atender muitas pessoas sem depender de uma única máquina mantendo todo o histórico
  de navegação.
</details>

**12. Como o cache ajuda no acesso a páginas Web?**

<details>
  <summary>Possível resposta</summary>

  O cache permite reaproveitar respostas anteriores quando o conteúdo não mudou,
  como imagens, CSS e JavaScript. Isso reduz tempo de carregamento, economiza banda
  e diminui a carga no servidor de origem.
</details>
