Nível **Iniciante → Avançado** · HTML · Tailwind CSS · Vite · Node.js · Express.js · TypeScript · Prisma · Testes

O **MonitorApp** é o projeto irmão do [InvestApp](../investapp/): a mesma trilha incremental, o
mesmo rigor de camadas, mas outro domínio e outra arquitetura de front. Aqui a aplicação
cadastra hosts de rede, executa `ping` periodicamente e guarda o histórico de latência de cada
um — e o front-end tem **build próprio**, servido em outra origem.

## Análise de requisitos

### Público-alvo

O **MonitorApp** foi projetado para atender a dois perfis principais de usuários:
- **Estudantes e Desenvolvedores Web**: alunos que já percorreram o InvestApp e querem exercitar as mesmas camadas em um domínio com relação muitos-para-muitos, chamada de sistema operacional e atualização em tempo real.
- **Times de infraestrutura e professores de laboratório**: pessoas que precisam de um painel simples e privado para acompanhar se um conjunto de máquinas, serviços ou sites está no ar e com que latência responde.

### Objetivo do sistema

O **MonitorApp** visa fornecer um painel web para acompanhar a disponibilidade e a latência de
hosts de rede. O sistema permite cadastrar endereços (IPv4 ou nome de domínio), organizá-los por
tags, disparar medições sob demanda ou em intervalos automáticos, e visualizar o histórico de
cada host em uma linha do tempo, com o painel se atualizando sozinho conforme as medições
acontecem.

### Requisitos Funcionais (RF)

| Código | Requisito | Descrição |
| ------ | --------- | --------- |
| **RF01** | Gestão de Hosts (CRUD) | O sistema deve permitir criar, listar, consultar por id, atualizar e remover hosts com nome e endereço (IPv4 ou nome de domínio). |
| **RF02** | Classificação por Tags | O sistema deve permitir rotular cada host com várias tags, e cada tag deve poder rotular vários hosts, com filtro da lista por tag. |
| **RF03** | Histórico de Medições | O sistema deve registrar cada medição de um host com o resultado (sucesso ou falha), a latência em milissegundos e o instante da coleta. |
| **RF04** | Coleta Automática e Sob Demanda | O sistema deve executar `ping` real contra os hosts em intervalos configuráveis e permitir antecipar uma medição pela interface. |
| **RF05** | Cadastro de Usuários | O sistema deve permitir o auto-cadastro de novos usuários informando nome, e-mail único e senha. |
| **RF06** | Autenticação & Sessão | O sistema deve autenticar usuários via e-mail e senha, retornando um token de acesso JWT para manter a sessão ativa. |
| **RF07** | Isolamento por Dono | O sistema deve garantir que o usuário autenticado acesse e manipule estritamente os seus próprios hosts e o histórico deles. |
| **RF08** | Painel em Tempo Real | O sistema deve atualizar o estado dos hosts na tela assim que uma medição é registrada, sem que o usuário recarregue a página. |

### Requisitos Não-Funcionais (RNF)

| Código | Requisito | Descrição |
| ------ | --------- | --------- |
| **RNF01** | Validação Estrita de Dados | Todas as entradas de dados via HTTP (`body`, `query`, `params`) devem ser validadas no servidor com schemas Zod antes do processamento. |
| **RNF02** | Criptografia & Segurança | Senhas nunca devem ser gravadas em texto limpo; o armazenamento deve utilizar hash Argon2id com salt por registro, e a sessão deve usar JWT HS256. |
| **RNF03** | Persistência Relacional | Os dados devem ser armazenados em banco relacional (SQLite) com Prisma ORM, incluindo uma relação muitos-para-muitos entre hosts e tags. |
| **RNF04** | Segurança na Chamada de Sistema | A execução do comando `ping` deve receber o endereço como argumento isolado, sem passar por shell, impedindo injeção de comando. |
| **RNF05** | Origens Separadas | O front-end deve ter build próprio e ser publicado independentemente da API, com CORS no servidor e proxy no ambiente de desenvolvimento. |
| **RNF06** | Manutenibilidade & Tipagem | O código do servidor deve ser tipado estaticamente e organizado em camadas (rotas, controllers, models), com tratamento de erros centralizado. |
| **RNF07** | Documentação da API | O contrato da API deve ser publicado em OpenAPI 3, gerado a partir dos mesmos schemas que validam as requisições, e navegável por interface web. |
| **RNF08** | Qualidade & Testabilidade | A aplicação deve possuir testes de unidade, de rotas (`supertest`), de front (Vitest) e fluxo completo E2E em navegador (Playwright). |
| **RNF09** | Portabilidade & Conteinerização | A aplicação inteira — API Node.js, banco SQLite e front compilado — deve ser empacotável em imagens Docker e orquestrada por Docker Compose. |

## Stack tecnológica da aplicação

O projeto evolui adicionando bibliotecas e ferramentas de mercado conforme a necessidade do sistema:

| Camada | Tecnologias e bibliotecas |
| ------ | ------------------------- |
| **Front-end** | HTML5 semântico, Tailwind CSS (classes utilitárias), JavaScript vanilla (`fetch`, DOM API) e build com Vite |
| **Back-end & Runtime** | Node.js 24, Express 5 e TypeScript (da etapa 3 em diante) |
| **Validação & Erros** | Schemas declarativos com Zod e middleware de erros customizado (`HttpError`) |
| **Persistência** | SQLite nativo (`node:sqlite`) e, depois, Prisma ORM (schema declarativo, migrations e relação N-N) |
| **Coleta** | `node:child_process` executando o `ping` do sistema, com agendador em `setInterval` |
| **Segurança & Auth** | Hash Argon2id e JWT HS256, ambos com `node:crypto`, e middleware de autorização |
| **Tempo real** | Server-Sent Events sobre HTTP, consumidos com `fetch` e `ReadableStream` |
| **Qualidade & Testes** | `node:test` com `supertest` (rotas), Vitest com jsdom (front) e Playwright (E2E) |
| **Infraestrutura** | Docker (API em Node, front compilado em Nginx), Docker Compose e volume de dados |

## Arquitetura do sistema

O MonitorApp separa front-end e API em **duas origens** desde a primeira etapa. O front é um
projeto Vite com build próprio; a API é um servidor Express em TypeScript. Em desenvolvimento, o
proxy do Vite faz o navegador enxergar uma origem só; em produção, o Nginx da imagem do front
assume esse papel e o middleware `cors` do Express autoriza a chamada.

### Dicionário de dados do domínio

O dicionário formaliza a estrutura, os tipos, as regras de integridade e o propósito de cada
campo mantido pela aplicação.

#### 1. Entidade `User` (Conta)

Representa a pessoa cadastrada na plataforma, dona de um conjunto de hosts monitorados e
responsável pela autenticação no sistema.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único universal da conta, gerado no cadastro. |
| `name` | `String` | Obrigatório | Nome completo do usuário (mínimo de 3 caracteres). |
| `email` | `String` | Obrigatório, **Unique** | E-mail usado para login; duplicidade responde `409`. |
| `password` | `String` | Hash | Hash da senha gerado com **Argon2id** no formato PHC, com salt por registro (mínimo de 8 caracteres na entrada). |
| `createdAt` | `DateTime` | Default `now()` | Data e hora de criação do registro. |

#### 2. Entidade `Host` (Endereço monitorado)

Representa um endereço de rede acompanhado pela aplicação: um IP, uma máquina interna ou um site
público.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único do host. |
| `name` | `String` | Obrigatório | Nome de exibição do host (mínimo de 3 caracteres, ex.: "Google DNS"). |
| `address` | `String` | Obrigatório | Endereço IPv4 ou nome de domínio. URLs completas são recusadas com `400`. |
| `createdAt` | `DateTime` | Default `now()` | Data e hora do cadastro. |
| `userId` | `String` | **FK** (`User.id`), `onDelete: Cascade` | Dono do host; preenchido a partir do token, nunca do corpo da requisição. |

#### 3. Entidade `Ping` (Medição)

Registra o resultado de uma verificação individual. É a entidade que dá ao sistema uma dimensão
temporal: um host não tem “um estado”, tem uma série de medições.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único da medição. |
| `latency` | `Int?` | Opcional | Latência em milissegundos. **Nulo** quando o host não respondeu — a medição existe, a latência não. |
| `success` | `Boolean` | Default `true` | Indica se houve resposta dentro do tempo limite. |
| `createdAt` | `DateTime` | Default `now()` | Instante da coleta; é por ele que a série é ordenada. |
| `hostId` | `String` | **FK** (`Host.id`), `onDelete: Cascade` | Host medido. Remover o host apaga o histórico junto. |

#### 4. Entidade `Tag` (Rótulo)

Classificação livre e compartilhada entre hosts. É o lado muitos-para-muitos do modelo: uma tag
rotula vários hosts, e um host carrega várias tags.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único da tag. |
| `name` | `String` | Obrigatório, **Unique** | Nome do rótulo (ex.: "infra", "dns", "produção"). É por ele que o host conecta a tag. |
| `color` | `String` | Obrigatório | Cor hexadecimal `#rrggbb` usada no badge do front. Tags criadas junto com um host nascem com a cor neutra `#64748b`. |

<Aside type="note" title="Por que a junção não vira uma entidade do dicionário">
  A tabela `_HostTags`, que materializa a relação muitos-para-muitos, é criada e mantida pelo
  próprio Prisma. Ela não aparece no dicionário porque não tem campos de negócio: existe apenas
  para ligar dois identificadores. A [etapa 7](prisma/) mostra o SQL que o Prisma gera para ela.
</Aside>

## Trilha incremental de desenvolvimento

<Steps>

1. **Front estático**: Quatro telas em HTML semântico e Tailwind CSS, já no projeto Vite, sem JavaScript.
2. **API em memória**: Rotas REST Express sobre um array, com o front consumindo a API pelo proxy do Vite.
3. **TypeScript em camadas**: Migração da API para TypeScript com divisão em rotas, controllers, models e manipuladores de erro.
4. **Validação**: Validação estrita de entradas HTTP (`body`, `query`, `params`) com schemas Zod, incluindo a regra de endereço.
5. **Documentação da API**: Documento OpenAPI gerado dos próprios schemas Zod e servido com Swagger UI.
6. **SQLite nativo**: Substituição do array por banco relacional com `node:sqlite`, migration e seeders, sem ORM.
7. **Prisma e relações**: Modelagem declarativa, migrations versionadas e as relações `Ping` (1-N) e `Tag` (N-N).
8. **Ping real**: Execução do comando do sistema com `node:child_process` e agendador de coleta periódica.
9. **Cadastro de usuário**: Criação da entidade `User`, formulário de auto-cadastro e hash de senhas com Argon2id.
10. **Autenticação**: Login com credenciais, emissão de tokens JWT e isolamento dos hosts por dono.
11. **Tempo real**: Painel que se atualiza sozinho via Server-Sent Events conforme as medições chegam.
12. **Testes de software**: Suíte de unidade, de rotas (`supertest`), de front (Vitest) e E2E (Playwright).
13. **Docker**: Duas imagens (API em Node e front em Nginx), Docker Compose e volume de dados.

</Steps>

## Evolução incremental do projeto

<Aside type="tip" title="O trilho é cumulativo por construção">
  Cada pasta de etapa nasce como cópia da anterior mais o delta daquela etapa. Nada que foi
  introduzido desaparece depois: o TypeScript da etapa 3 vale até a 13, a validação da etapa 4
  continua nas rotas de todas as seguintes, e o isolamento por dono da etapa 10 acompanha o
  resto. As duas únicas remoções do trilho são substituições explicadas na própria página — o
  array em memória sai na etapa 6, quando o banco entra, e os scripts de migration manual saem
  na etapa 7, quando o Prisma assume.
</Aside>

Cada etapa resolve exatamente um problema novo e mantém tudo que veio antes. O código de todo
o projeto reside 100% no próprio repositório, dentro de `examples/express/projects/`. Não é
necessário clonar repositórios externos (`git clone`).

Comparar duas pastas locais com `git diff --no-index` mostra, de forma isolada, exatamente o que
aquela etapa alterou no código — e é a melhor forma de ver o efeito direto de uma decisão de
arquitetura.

<Aside type="tip" title="Compare duas etapas com um comando">
  Você pode comparar quaisquer duas pastas de etapas locais dentro do repositório DevLab com o comando:

  ```bash title="Terminal"
  git diff --no-index -- \
    examples/express/projects/monitor-app-static \
    examples/express/projects/monitor-app-api || true
  ```

  Ou comparar a transição da persistência nativa em SQLite para o Prisma ORM:

  ```bash title="Terminal"
  git diff --no-index -- \
    examples/express/projects/monitor-app-db-simple \
    examples/express/projects/monitor-app-prisma || true
  ```

  O parâmetro `--no-index` instrui o Git a comparar diretamente duas pastas locais sem depender de
  histórico ou repositório remoto. O `|| true` evita que o terminal trate diferenças de arquivos
  como erro de comando.
</Aside>

### Execução dos projetos locais

Cada página de etapa aponta para uma pasta em `examples/express/projects/`. Como front e API são
projetos separados, cada um tem o seu `npm install` e o seu terminal:

```bash title="Terminal 1 — a API"
cd examples/express/projects/monitor-app-prisma/back
npm install
cp .env.example .env
npm run db:migrate
npm run db:seed
npm run dev
```

```bash title="Terminal 2 — o front"
cd examples/express/projects/monitor-app-prisma/front
npm install
npm run dev
```

<Aside type="caution" title="As dependências mudam entre as pastas">
  A etapa 7 em diante instala o Prisma; a etapa 3 acrescenta `typescript` e `@types/*`; a etapa 12
  acrescenta `supertest`, `vitest` e o Playwright. Rode `npm install` de novo sempre que trocar de
  pasta — o `package.json` é diferente.
</Aside>
