Etapa **4 de 13** · Nível **Intermediário** · Zod · Validação de entrada

Até aqui o controller confiava no cliente. O `req.body as HostInput` da etapa 3 era uma promessa
ao compilador, não uma verificação: em tempo de execução, qualquer JSON passava. Esta etapa
substitui essa promessa por um schema que roda antes do handler.

E o MonitorApp tem uma regra própria para validar, que nenhum tipo do TypeScript consegue
expressar: **o que é um endereço de host válido**.

### US04 — Saber exatamente o que corrigir · RNF01

> **Como** pessoa que integra com a API,
> **quero** que a resposta de erro diga qual campo está errado e por quê,
> **para** corrigir a requisição sem adivinhar.

```gherkin
Cenário: CA04.1 - A resposta de erro descreve o problema
  Quando envio POST /api/hosts com o nome vazio
  Então recebo o status 400
  E o corpo traz a lista issues com a mensagem do campo

Cenário: CA04.2 - Cada issue aponta a origem do dado
  Quando envio uma requisição inválida
  Então cada issue tem um path começando por body, params ou query

Cenário: CA04.3 - O endereço aceita IP e domínio
  Quando envio address igual a "8.8.8.8"
  Então recebo o status 201
  E quando envio address igual a "www.exemplo.com"
  Então também recebo o status 201

Cenário: CA04.4 - O endereço recusa URL completa
  Quando envio address igual a "https://exemplo.com/status"
  Então recebo o status 400
  E a mensagem diz que o endereço deve ser um IPv4 ou um nome de domínio

Cenário: CA04.5 - O id precisa ser um UUID
  Quando envio GET /api/hosts/abc
  Então recebo o status 400
  E não 404

Cenário: CA04.6 - Filtro vazio é erro
  Quando envio GET /api/hosts?name=
  Então recebo o status 400

Cenário: CA04.7 - Os controllers deixaram de conferir campos
  Dado o arquivo hosts.controller.ts
  Então não existe nenhum if de campo obrigatório
```

## O que muda nesta etapa

| Etapa 3 (`monitor-app-typescript`) | Etapa 4 (`monitor-app-validation`) |
| ---------------------------------- | ---------------------------------- |
| `req.body as HostInput` sem verificação | `validate(createHostSchema)` antes do handler |
| `if (!name \|\| !address)` no model | a obrigatoriedade declarada no schema |
| erro genérico `"Unable to create host"` | `"Validation error"` com a lista `issues` |
| id inexistente e id inválido, ambos `404` | id malformado responde `400`; id válido e ausente, `404` |
| qualquer texto aceito em `address` | IPv4 ou nome de domínio, e nada mais |

## Descrição das tarefas

### TK04.1 · Criar `src/middlewares/validate.ts` (O middleware genérico)

```bash title="Terminal: dentro de back/"
npm install zod
```

Um middleware só, para todas as rotas. A função das linhas 11 a 23 recebe um schema e devolve o
middleware — é o padrão de fábrica que permite escrever `validate(createHostSchema)` na rota.

A decisão de projeto está nas linhas 12 a 16: o schema não valida apenas o corpo, valida as
**três fontes de uma vez**, montando um objeto com `body`, `query` e `params`. É isso que faz o
`path` de cada issue começar pela origem do dado, e é isso que permite a uma rota como o `PUT`
validar o parâmetro da URL e o corpo no mesmo passo.

A linha 18 usa `safeParse`, e não `parse`: em vez de o Zod lançar a sua própria exceção, o
resultado é inspecionado e convertido em `HttpError` — o mesmo tipo de erro que o resto da
aplicação já sabe tratar. A biblioteca não vaza para fora deste arquivo.

### TK04.2 · Criar `src/schemas/host.schema.ts` (As regras do recurso)

O arquivo tem duas metades. A primeira declara as três fontes possíveis; a segunda compõe, a
partir delas, um schema por rota.

O trecho destacado nas linhas 8 a 14 é o coração desta etapa: a regra que define o que é um
endereço. Um host de rede é identificado por um IPv4 ou por um nome de domínio — nunca por uma
URL completa, porque o `ping` opera sobre host, não sobre caminho HTTP.

O `.refine()` da linha 11 aceita as duas formas: `z.ipv4()` cobre o endereço numérico, e a
expressão regular da linha 12 cobre o nome de domínio, exigindo pelo menos um ponto e um sufixo
de duas letras ou mais. Aceitar `https://exemplo.com` aqui adiaria o erro para o momento da
medição, na etapa 8, quando ele seria muito mais difícil de explicar a quem cadastrou o host.

As linhas 22 a 28 declaram as outras duas fontes. O `params` exige um UUID — é o que faz
`GET /api/hosts/abc` responder `400`, e não `404`. E o `query` marca `name` como `.optional()`,
mas com `.min(1)`: o filtro pode não vir, mas não pode vir vazio, porque `?name=` é quase sempre
um bug do cliente que uma lista completa esconderia.

As cinco exportações das linhas 30 a 38 mostram por que valeu a pena separar as fontes: cada rota
declara exatamente o que usa. O `updateHostSchema` da linha 36 é o único que combina duas.

<Aside type="note" title="`400` e `404` param de se confundir">
  Na etapa 3, `GET /api/hosts/abc` respondia `404`: o model procurava `abc` no array, não achava,
  e o controller traduzia isso em "não encontrado". Estava errado — `abc` nunca poderia ser um id
  deste sistema. Agora a requisição sequer chega ao controller, e a resposta diz a verdade: o
  pedido está malformado.
</Aside>

## Conceitos abordados

- Middleware de fábrica: uma função que recebe schema e devolve middleware
- Validar `body`, `query` e `params` na mesma passada
- `safeParse` em vez de `parse`, para não deixar a biblioteca vazar
- `.refine()` para regras que nenhum tipo primitivo expressa
- Campo opcional que não pode ser vazio
- `400` para pedido malformado, `404` para recurso ausente
