Etapa **7 de 13** · Nível **Avançado** · Prisma ORM · Relações 1-N e N-N

Esta é a etapa em que o MonitorApp deixa de ser um CRUD e passa a ter um domínio. Duas entidades
novas entram, e cada uma traz um tipo diferente de relação:

- **`Ping`** — o histórico de medições de um host. Um host tem muitas medições, e cada medição
  pertence a exatamente um host: uma relação **um-para-muitos**.
- **`Tag`** — o rótulo compartilhado. Um host tem várias tags, e uma tag rotula vários hosts:
  uma relação **muitos-para-muitos**, que exige uma tabela de junção.

Escrever isso em SQL puro, como na etapa 6, significaria montar `JOIN`s à mão e manter a tabela
de junção manualmente. É exatamente o trabalho que o Prisma assume.

### US07 — Organizar e comparar os hosts · RF02, RF03, RNF03

> **Como** responsável pela rede,
> **quero** rotular os hosts por finalidade e consultar o histórico de cada um,
> **para** enxergar o comportamento de um grupo de máquinas ao longo do tempo.

```gherkin
Cenário: CA07.1 - As tabelas nascem da migration
  Quando executo npm run db:migrate
  Então são criadas as tabelas Host, Ping, Tag e a junção _HostTags

Cenário: CA07.2 - A listagem já vem resolvida
  Quando envio GET /api/hosts
  Então cada host traz o array tags preenchido
  E o array pings com as medições mais recentes

Cenário: CA07.3 - Tag nova é criada na hora
  Quando cadastro um host com a tag "backup", que não existe
  Então o host é criado com a tag conectada
  E a tag passa a existir para os próximos hosts

Cenário: CA07.4 - Filtrar por tag
  Quando envio GET /api/hosts?tag=infra
  Então recebo apenas os hosts rotulados com infra

Cenário: CA07.5 - Remover host apaga o histórico

  Quando envio DELETE /api/hosts/{id}
```

## O que muda nesta etapa

Esta é a segunda e última **remoção** do trilho: os scripts de migration manual da etapa 6 saem,
porque o Prisma assume o versionamento do esquema.

| Etapa 6 (`monitor-app-db-simple`) | Etapa 7 (`monitor-app-prisma`) |
| --------------------------------- | ------------------------------ |
| `migration.ts` com `CREATE TABLE IF NOT EXISTS` | `prisma/migrations/` versionadas |
| `seeders.ts` + `load.ts` | `src/database/seed.ts`, chamado por `prisma db seed` |
| `SELECT id, name, address FROM hosts` | `prisma.host.findMany({ include })` |
| uma entidade | três entidades e uma tabela de junção |
| um recurso na API | três: `hosts`, `tags` e `pings` |
| `host.html` com dados escritos à mão | `host.js` desenhando a série a partir da API |

## Descrição das tarefas

### TK07.1 · Escrever `prisma/schema.prisma` (O modelo declarativo)

```bash title="Terminal: dentro de back/"
npm install prisma @prisma/client @prisma/adapter-better-sqlite3
cp .env.example .env
```

O schema descreve o domínio inteiro em 37 linhas. Vale lê-lo por relação.

**Um-para-muitos** — o `pings Ping[]` da linha 17 no `Host` e o par `host` / `hostId` das linhas
28 e 29 no `Ping` são os dois lados da mesma relação. A chave estrangeira mora no lado "muitos",
como em qualquer modelo relacional. O `onDelete: Cascade` da linha 28 é uma decisão de domínio:
uma medição não faz sentido sem o host que a originou, então apagar o host apaga o histórico.

**Muitos-para-muitos** — o `tags Tag[] @relation("HostTags")` da linha 19 e o
`hosts Host[] @relation("HostTags")` da linha 36 são o outro par. Repare no que **não** está
escrito: não existe um `model HostTag` com duas chaves estrangeiras. O Prisma cria e mantém essa
tabela sozinho a partir do nome da relação.

A linha 25 merece uma leitura em separado: `latency Int?`, com interrogação. Uma medição que
falhou existe — foi tentada, tem instante — mas não tem latência. Modelar isso como `0` seria
mentira estatística: a média das latências passaria a incluir quedas como se fossem respostas
instantâneas. O nulo é o valor honesto.

<Aside type="tip" title="Migration versionada versus `CREATE TABLE IF NOT EXISTS`">
  A diferença aparece na segunda alteração, não na primeira. Quando a etapa 9 acrescentar a
  tabela `User` e uma coluna `userId` em `Host`, o Prisma vai gerar uma **nova** pasta de
  migration com o `ALTER`/`REDEFINE` necessário. O banco de quem já rodava a etapa 7 evolui sem
  ser apagado — algo que o `IF NOT EXISTS` da etapa 6 nunca conseguiria fazer.
</Aside>

### TK07.3 · Reescrever os models

O `Host.ts` é o arquivo mais interessante da etapa. Duas constantes no topo carregam quase toda a
decisão.

O `include` das linhas 8 a 11 substitui o `JOIN` que seria escrito à mão: ele pede ao Prisma que
traga as tags e as **dez medições mais recentes** na mesma ida ao banco. O `take: 10` é
deliberado — o cartão do painel mostra a última latência e nada mais; carregar o histórico
inteiro de todos os hosts para desenhar uma barra seria desperdício.

O `connectTags` das linhas 14 a 21 resolve o cadastro por nome. O `connectOrCreate` da linha 16 é
a operação que faz `tags: ["infra", "backup"]` funcionar mesmo quando `backup` ainda não existe:
existe, conecta; não existe, cria com a cor neutra. Sem ele, o front teria que consultar as tags,
criar as que faltam e só então cadastrar o host — três requisições no lugar de uma.

O filtro por tag da linha 38 é a outra ponta da mesma relação. O `tags: { some: { name } }`
atravessa a tabela de junção sem uma linha de SQL escrita por nós.

E o `update` da linha 64 traz o detalhe mais fácil de errar: `set: []` antes do
`connectOrCreate`. Sem ele, uma tag omitida na atualização continuaria vinculada, e a lista
enviada seria interpretada como acréscimo em vez de substituição.

### TK07.4 · Criar as rotas de tags e de pings

O histórico é um recurso **aninhado**: `GET /api/hosts/:id/pings`. A escolha do caminho é
semântica — uma medição não existe fora de um host, e o URL diz isso.

O controller confere a existência do host antes de ler o histórico. Sem essa checagem, um id
inexistente devolveria `[]` com status `200`, o que é indistinguível de um host sem medições.

O recurso de tags é mais simples, com duas rotas. O `POST /api/tags` existe para criar uma tag

| GET | `/api/hosts/:id` | — | `200` | `400`, `404` |
| PUT | `/api/hosts/:id` | `{ name, address, tags? }` | `200` | `400`, `404` |
| DELETE | `/api/hosts/:id` | — | `204` | `400`, `404` |

| GET | `/api/tags?name=` | — | `200` | `400` |
| POST | `/api/tags` | `{ name, color }` | `201` | `400`, `409` |

## Conceitos abordados

- Schema declarativo e migrations versionadas
- Relação um-para-muitos com `onDelete: Cascade`
- Relação muitos-para-muitos e a tabela de junção implícita
- `include` no lugar de `JOIN` escrito à mão
- `connectOrCreate` e `set: []` na atualização de vínculos
- Campo opcional (`Int?`) como modelagem honesta da ausência
- Recurso aninhado no URL (`/hosts/:id/pings`)
