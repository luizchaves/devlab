Etapa **5 de 13** · Nível **Intermediário** · OpenAPI 3 · Swagger UI

A etapa 4 escreveu as regras da API em schemas Zod. Essas mesmas regras já são, na prática, a
documentação do contrato — só estão em um formato que só o servidor lê. Esta etapa as publica.

A escolha central aqui não é qual biblioteca usar: é **não escrever o contrato duas vezes**. Um
documento OpenAPI mantido à mão desatualiza no primeiro dia corrido.

  - **Contrato**: veja [Construção de API](../../../api/construction/)
</Aside>

### US05 — Integrar sem ler o código · RNF07

> **Como** pessoa que consome a API,
> **quero** um documento navegável com todos os endpoints e formatos,
> **para** integrar sem abrir o repositório do servidor.

```gherkin
Cenário: CA05.1 - A interface navegável
  Quando abro http://localhost:3000/api/docs
  Então vejo os endpoints do recurso hosts com os corpos e status codes

Cenário: CA05.2 - O documento cru
  Quando envio GET /api/openapi.json
  Então recebo um documento OpenAPI 3 válido

Cenário: CA05.3 - Documentação e validação concordam
  Dado que o schema exige nome com no mínimo 3 caracteres
  Então o documento OpenAPI declara minLength 3 para o mesmo campo

Cenário: CA05.4 - Mudar o schema muda a documentação
  Quando altero uma regra em host.schema.ts
  E reinicio o servidor
  Então a alteração aparece no Swagger UI sem que eu edite outro arquivo

Cenário: CA05.5 - Nenhuma regra escrita duas vezes
  Dado o arquivo docs/openapi.ts
  Então ele não repete nenhuma restrição já declarada no schema
```

### Tasks da etapa

<Steps>

1. **TK05.1 · Criar `src/docs/openapi.ts`**: converter os schemas Zod em JSON Schema e montar o documento.

## Estrutura da aplicação

Esta é a etapa com o menor delta do trilho: duas pastas novas, `docs/` e mais um arquivo em
`routes/`, e **nenhuma linha alterada** em `schemas/`, `models/`, `controllers/` ou
`routes/hosts.routes.ts`. O tamanho da mudança é o próprio argumento da etapa — documentar não
deveria custar reescrever o contrato.

  │       │   └── hosts.routes.ts

  │       └── index.ts                   registra o novo roteador
  └── front/                    inalterado nesta etapa
`}

O desenho abaixo é o que justifica essa economia. O `host.schema.ts` da etapa 4 continua sendo o
único lugar onde as regras existem, e agora alimenta **dois** consumidores: o middleware que
recusa requisição inválida em tempo de execução, e o gerador que descreve o contrato para quem
está de fora.

<Mermaid title="Uma fonte, dois destinos">
{`
flowchart LR
  S["host.schema.ts<br/>schemas Zod"] --> V["validate()<br/>recusa requisição inválida"]
  S --> J["z.toJSONSchema()<br/>openapi.ts"]
  J --> D["GET /api/docs<br/>Swagger UI"]
  J --> R["GET /api/openapi.json<br/>ferramentas"]
`}
</Mermaid>

Repare que as duas pontas da direita nunca voltam para o schema: nada do que é publicado pode
divergir do que valida, porque não existe caminho de escrita nessa direção.

## O que muda nesta etapa

| Etapa 4 (`monitor-app-validation`) | Etapa 5 (`monitor-app-swagger`) |
| ---------------------------------- | ------------------------------- |
| o contrato existe só no código | o contrato é publicado em `/api/docs` |
| o `requests.http` como única referência externa | o `requests.http` **e** o documento OpenAPI |
| dois roteadores registrados no app | três: `docsRoutes` entra antes de `hostRoutes` |
| — | `swagger-ui-express` nas dependências |

Nada em `schemas/`, `models/`, `controllers/` ou `routes/hosts.routes.ts` foi tocado. É o
indicador de que a documentação foi derivada, e não duplicada.

## Descrição das tarefas

### TK05.1 · Criar `src/docs/openapi.ts` (O documento derivado)

```bash title="Terminal: dentro de back/"
npm install swagger-ui-express
npm install -D @types/swagger-ui-express
```

O arquivo tem três partes. A primeira, nas linhas 9 a 18, são as duas funções que fazem a
conversão. A `toSchema` da linha 9 usa `z.toJSONSchema()` — desde o Zod 4 essa conversão é
nativa, sem biblioteca auxiliar. O parâmetro `target: 'openapi-3.0'` importa: o OpenAPI 3.0 usa
um dialeto próprio de JSON Schema, e sem ele campos como `nullable` sairiam no formato errado.

A `shapeOf` da linha 14 resolve um detalhe da nossa modelagem: como cada schema de rota envelopa
as fontes (`{ body }`, `{ params }`, `{ query }`), é preciso descer um nível para chegar ao
formato que interessa à documentação.

A segunda parte, nas linhas 20 a 58, monta os blocos reutilizáveis. O `host` da linha 24 é o
recurso como ele **sai** da API: o `id` gerado pelo servidor mais as propriedades declaradas no
schema de entrada, espalhadas na linha 28. O `idParameter` da linha 32 reaproveita a regra de
UUID já escrita no `params`, e o `validationError` da linha 45 descreve o corpo de erro que o
`errorHandler` da etapa 4 produz.

A terceira parte, da linha 60 em diante, é o documento em si: metadados, servidores e o objeto
`paths`. Ela é longa e repetitiva — cada rota descreve parâmetros, corpo e respostas — e por isso
aparece recolhida. O que vale ler é a ausência: em nenhum lugar dessa seção há um `minLength`, um
`format` ou um `required` escrito à mão. Todos vieram do schema.

<Aside type="tip" title="Como conferir que a derivação funciona">
  Abra `GET /api/openapi.json` e procure por `address`. O `pattern` e o `minLength` que aparecem
  ali não foram escritos no `openapi.ts` — vieram de `host.schema.ts`. Mude o mínimo do `name` de
  3 para 5, reinicie e recarregue: o documento acompanha.
</Aside>

### TK05.2 · Criar `src/routes/docs.routes.ts` (As duas portas de entrada)

O roteador é curto e serve dois públicos diferentes. A linha 9 devolve o documento cru em
`GET /api/openapi.json` — é o que ferramentas consomem: Insomnia e Postman importam esse arquivo,
e geradores de client produzem código a partir dele. A linha 12 monta a interface navegável em
`GET /api/docs`, que é o que uma pessoa abre.

## Executando

<Steps>

1. Instale a dependência nova e suba a API:

   ```bash title="Terminal 1"
   cd examples/courses/express/projects/monitor-app-swagger/back
   npm install
   npm run dev
   ```

2. Abra a documentação navegável em <code>http://localhost:3000/api/docs</code>.

3. Baixe o documento cru:

   ```bash title="Terminal"
   curl http://localhost:3000/api/openapi.json | head -40
   ```

</Steps>

<Aside type="caution" title="A documentação não substitui a especificação">
  O documento OpenAPI descreve **formatos**: tipos, obrigatoriedade, status codes. Ele não
  descreve **decisões** — por que um host de outra conta responde `404` e não `403`, ou por que
  uma medição com falha responde `201`. Essas ficam na
  [Especificação da API](../api-spec/), que é a leitura humana do mesmo contrato.
</Aside>

## Conceitos abordados

- `z.toJSONSchema()` com alvo OpenAPI 3.0
- Uma fonte da verdade para validar e para documentar
- Documento cru para ferramentas, interface navegável para pessoas
- Blocos reutilizáveis (`idParameter`, `jsonBody`, `validationError`) dentro do documento
- Documentação que acompanha a mudança de schema sem edição manual
