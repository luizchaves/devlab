Etapa **1 de 13** · Nível **Iniciante** · HTML · Tailwind CSS · Sem JavaScript

O InvestApp começa pela experiência visual completa. Nesta etapa existem telas, navegação,
formulários e estados estáticos, mas nenhum `fetch`, nenhum manipulador de evento e nenhum
arquivo JavaScript. A ideia é congelar a UX antes de ligar comportamento.

### US01 — Conhecer o sistema antes de usá-lo · RF01, RF02, RF03, RF06

> **Como** visitante,
> **quero** navegar pelas telas de carteira, cadastro, login e perfil,
> **para** entender o que a aplicação faz antes de confiar meus dados a ela.

```gherkin
Cenário: CA01.1 - As telas abrem sem servidor
  Dado que o projeto foi apenas baixado, sem instalação
  Quando abro o arquivo index.html no navegador
  Então a página da carteira é exibida com os cartões de exemplo

Cenário: CA01.2 - A navegação liga as quatro telas
  Dado que estou na página index.html
  Quando clico nos links do cabeçalho
  Então chego a signin.html, signup.html e profile.html
  E nenhuma navegação depende de JavaScript

Cenário: CA01.3 - Os campos já declaram o contrato futuro
  Dado que abro o formulário de novo investimento
  Então os campos têm os atributos name "name", "value" e "interest"
  E é por esses nomes que a etapa 2 vai ler os dados

Cenário: CA01.4 - A etapa não tem comportamento
  Quando procuro arquivos JavaScript no projeto
  Então não existe nenhum arquivo .js
  E nenhuma página contém a tag script
```

## O que esta etapa entrega

O front nasce como um protótipo navegável em HTML. O arquivo `css/tailwind.css` concentra as
classes utilitárias usadas pelas páginas, simulando o resultado de um CSS compilado e mantendo
a regra da etapa: **sem JavaScript**.

## O que entra e o que fica de fora

Esta é a primeira etapa, então não existe um diff contra a etapa anterior — tudo é novo. O que
vale registrar é a fronteira que a etapa impõe: quatro páginas e uma folha de estilo entram, e
todo o comportamento fica para a etapa 2.

| Entra nesta etapa | Fica para as próximas |
| ----------------- | --------------------- |
| `index.html`, `signup.html`, `signin.html` e `profile.html` | a pasta `public/js/` e qualquer tag `<script>` |
| `css/tailwind.css` com utilitários e classes de componente | `fetch`, manipuladores de evento e estado de tela |
| `public/imgs/profile/avatar.png` como avatar padrão | o upload real da imagem, que chega na etapa 11 |

### 1. Criar `index.html` (Dashboard de Investimentos)

<HtmlPreview path="examples/express/projects/invest-app-static/index.html" height="24rem" serveFromPublic />

O dashboard é montado com três blocos. O cabeçalho de navegação ocupa as linhas 10 a 22; o resumo da carteira aparece no cartão `<div class="card metric p-6">` das linhas 35 a 39; e a grade de ativos repete a mesma estrutura em cada `<article class="card investment-card p-6">`, cuja primeira ocorrência está nas linhas 43 a 53. Os dois cartões seguintes (linhas 55 a 77) são cópias com outros textos e por isso aparecem recolhidos — a estrutura que importa é a do cartão visível.

O trecho destacado nas linhas 80 a 108 é o único elemento interativo da página: o formulário de novo investimento vive dentro de um `<details class="mt-8 card p-6 group">`, e é o `<summary>` da linha 81 que abre e fecha o bloco, sem uma única linha de JavaScript. Dentro do `<form>` estão os três campos que a API da etapa 2 vai ler pelos atributos `name`: `name="name"` na linha 96, `name="value"` na linha 100 e `name="interest"` na linha 104.

Repare também que o botão da linha 106 usa `type="button"`, e não `type="submit"`. Essa escolha congela a estrutura visual sem disparar recarregamento de página: os nomes dos campos já são o contrato que o JavaScript vanilla vai consumir nas etapas seguintes.

### 2. Criar `css/tailwind.css` (Folha de estilos utilitária)

A folha de estilo tem três camadas bem separadas. As linhas 1 a 44 fazem o reset e declaram os tokens de cor e de raio em `:root`; as linhas 45 a 260 são os utilitários no estilo Tailwind (`.mx-auto`, `.gap-4`, `.text-slate-500`), repetitivos e por isso recolhidos; e o `@media (min-width: 768px)` da linha 360 devolve as variantes `md-*` que as telas usam para o layout em colunas.

O bloco destacado nas linhas 261 a 359 é o que interessa nesta etapa. Ali moram as classes de componente que formam o vocabulário visual do InvestApp: `.card` (linha 261), `.btn` e suas variantes `.btn-primary`, `.btn-dark` e `.btn-soft` (linhas 268 a 296), `.field` e `.input` (linhas 297 a 315), além de `.badge`, `.metric`, `.investment-card`, `.status-dot`, `.avatar` e `.file-drop`.

São essas classes, e não os utilitários, que as quatro páginas reutilizam. Elas garantem espaçamentos e cores padronizados sem depender de build step nem de pré-processador durante a prototipagem.

### 3. Criar `signup.html` (Tela de criação de conta)

<HtmlPreview path="examples/express/projects/invest-app-static/signup.html" height="24rem" serveFromPublic />

O cartão centralizado das linhas 10 a 21 repete a moldura que o `signin.html` também usa, e por isso está recolhido: é a mesma combinação de `.card p-6` com logo e título.

O `<form class="mt-6 grid gap-4">` destacado nas linhas 22 a 45 é a novidade da tela. Ele declara os quatro campos do cadastro pelos atributos `name`: `name="name"` na linha 25, `name="email"` na linha 29, `name="password"` na linha 33 e `name="confirmationPassword"` na linha 40. Esses nomes são exatamente o corpo que a etapa 8 vai enviar em `POST /api/users`.

O botão da linha 44 também usa `type="button"`: a tela define a experiência de onboarding, mas o envio real — com o hash da senha no servidor — só entra quando existir uma API para receber o formulário.

### 4. Criar `signin.html` (Tela de autenticação)

<HtmlPreview path="examples/express/projects/invest-app-static/signin.html" height="24rem" serveFromPublic />

O login é a tela mais enxuta do projeto e reaproveita a mesma moldura do cadastro nas linhas 10 a 21, recolhidas por serem idênticas às do `signup.html`.

O formulário destacado nas linhas 22 a 32 reduz a entrada a dois campos: `name="email"` na linha 25 e `name="password"` na linha 29. O botão da linha 31 usa a variante `.btn-dark`, diferente do `.btn-primary` do cadastro, para diferenciar visualmente a ação de entrar da ação de criar conta.

Esses dois campos são a interface que, na etapa 9, vai receber o token JWT devolvido por `POST /api/signin` e guardá-lo no `localStorage`.

### 5. Criar `profile.html` e `public/imgs/profile/avatar.png` (Tela de perfil)

<HtmlPreview path="examples/express/projects/invest-app-static/profile.html" height="24rem" serveFromPublic />

A tela de perfil divide a área principal em dois cartões lado a lado. O primeiro trecho destacado, nas linhas 27 a 33, mostra a identidade do usuário: a tag `<img class="avatar" src="public/imgs/profile/avatar.png" />` da linha 28 carrega a imagem padrão que acompanha o projeto, ao lado do nome e do e-mail.

Logo abaixo, o formulário das linhas 35 a 45 repete o padrão `.field` mais `.input` já visto nas outras telas, agora com `value` preenchido em vez de `placeholder` — é a diferença entre um formulário de criação e um de edição.

O segundo trecho destacado, nas linhas 55 a 59, é o `<div class="mt-6 file-drop">`: uma área de soltar arquivo puramente visual, com o texto do limite de 2 MB e um botão `.btn-soft`. Ela deixa o painel pronto para a etapa 11, quando o mesmo bloco passa a disparar um `FormData` para o endpoint de upload com Multer.

## Executando

<Steps>

1. Entre no exemplo estático:

   ```bash title="Terminal"
   cd examples/express/projects/invest-app-static
   ```

2. Abra o HTML diretamente no navegador ou suba um servidor simples:

   ```bash title="Terminal"
   npm install
   npm run preview
   ```

3. Navegue entre `index.html`, `signup.html`, `signin.html` e `profile.html`.

</Steps>

<Aside type="tip" title="Por que começar sem JavaScript">
  Separar primeiro a experiência visual evita misturar três problemas ao mesmo tempo:
  layout, contrato HTTP e estado de tela. A próxima etapa mantém esse front e conecta o
  formulário à API usando JavaScript vanilla.
</Aside>

## Conceitos abordados

- Estrutura de páginas HTML sem build
- CSS utilitário no arquivo `tailwind.css`
- Formulários preparados para etapas futuras
- Avatar e navegação de perfil já previstos
- Evolução incremental sem framework de front-end
