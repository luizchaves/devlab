Nível **Iniciante → Avançado** · HTML · Tailwind CSS · Node.js · Express.js · TypeScript · Prisma · Testes

O **InvestApp** é a aplicação que atravessa o guia inteiro: um controle de investimentos com
front-end web e API própria. Ele não é um projeto pronto — é a **mesma** aplicação em treze
estados, com cada etapa isolando uma decisão técnica.

## Análise de requisitos

### Público-alvo

O **InvestApp** foi projetado para atender a dois perfis principais de usuários:

- **Estudantes e Desenvolvedores Web**: Alunos de cursos de tecnologia e engenheiros de software que buscam aprender, de forma prática e incremental, a construir uma aplicação Full-stack profissional com Node.js, Express, TypeScript, Zod, Prisma, Vitest e Docker.
- **Investidores Pessoais**: Pessoas físicas que necessitam de uma ferramenta direta e privada para organizar e acompanhar o patrimônio investido (Renda Fixa, Pós-fixado, Internacional, Ações) com leitura visual clara e controle centralizado.

### Objetivo do sistema

O **InvestApp** visa fornecer uma plataforma web intuitiva e segura para a gestão e acompanhamento de carteiras de investimentos pessoais. O sistema permite centralizar a visualização de ativos financeiros (renda fixa, ações, fundos, títulos públicos), facilitando o controle de valores investidos, rentabilidade contratada, corretoras de custódia e categorias de ativos em uma interface otimizada para tomada de decisão rápida.

## Backlog do produto

Os requisitos acima dizem **o que** o sistema deve fazer. O backlog decompõe isso em unidades
de trabalho: quem precisa de cada coisa, em que ordem ela é construída e como saber que ficou
pronta.

São quatro níveis, do mais abrangente ao mais verificável, e cada um responde a uma pergunta
diferente:

| Nível | Responde | Formato |
| ----- | -------- | ------- |
| **Épico** (`EP`) | que grande bloco de valor é este? | uma frase |
| **Feature** (`FT`) | que capacidade concreta entrega esse valor? | um recorte por etapa |
| **User Story** (`US`) | quem precisa disso, e para quê? | Como… quero… para… |
| **Critério de Aceitação** (`CA`) | como sabemos que está pronto? | Gherkin, executável a olho |

As **tasks** (`TK`) ficam em cada página de etapa: são o *como fazer*, e correspondem
exatamente aos passos da implementação.

### Requisitos Funcionais (RF)

| Código | Requisito | Descrição |
| ------ | --------- | --------- |
| **RF01** | Gestão de Investimentos (CRUD) | O sistema deve permitir criar, listar, consultar por id, atualizar e remover investimentos com nome, valor, taxa/indexador, corretora e categoria. |
| **RF02** | Cadastro de Usuários | O sistema deve permitir o auto-cadastro de novos investidores informando nome, e-mail único e senha. |
| **RF03** | Autenticação & Sessão | O sistema deve autenticar usuários via e-mail e senha, retornando um token de acesso JWT para manter a sessão ativa. |
| **RF04** | Isolamento por Dono | O sistema deve garantir que o investidor autenticado acesse e manipule estritamente a sua própria carteira de ativos. |
| **RF05** | Notificação de Boas-Vindas | O sistema deve enviar automaticamente um e-mail transacional de confirmação ao concluir o cadastro de um novo usuário. |
| **RF06** | Gestão de Perfil & Upload de Avatar | O sistema deve permitir a atualização dos dados cadastrais e o envio de foto de perfil (imagem no formato PNG/JPG). |

### Requisitos Não-Funcionais (RNF)

| Código | Requisito | Descrição |
| ------ | --------- | --------- |
| **RNF01** | Validação Estrita de Dados | Todas as entradas de dados via HTTP (`body`, `query`, `params`) devem ser validadas no servidor com schemas Zod antes do processamento. |
| **RNF02** | Criptografia & Segurança | Senhas de usuários nunca devem ser gravadas em texto limpo; o armazenamento deve utilizar hash Argon2id com salt por registro. |
| **RNF03** | Persistência Relacional | Os dados da aplicação devem ser armazenados em banco de dados relacional (SQLite) utilizando o Prisma ORM para migrations versionadas e garantia de integridade referencial. |
| **RNF04** | Qualidade & Testabilidade | A aplicação deve possuir suítes de testes automatizados cobrindo lógica unitária, integração de rotas API (`supertest`) e fluxo completo E2E em navegador (`Playwright`). |
| **RNF05** | Portabilidade & Conteinerização | A aplicação inteira (Node.js API + banco SQLite + assets) deve ser empacotável em imagem Docker multi-estágio e executável via Docker Compose. |
| **RNF06** | Manutenibilidade & Tipagem | O código do servidor deve ser tipado estaticamente e organizado em camadas (rotas, controllers, models), com tratamento de erros centralizado. |
| **RNF07** | Documentação da API | O contrato da API deve ser publicado em OpenAPI 3, gerado a partir dos mesmos schemas que validam as requisições, e navegável por interface web. |

## Stack tecnológica da aplicação

O projeto evolui adicionando bibliotecas e ferramentas de mercado conforme a necessidade do sistema:

| Camada | Tecnologias e bibliotecas |
| ------ | ------------------------- |
| **Front-end** | HTML5 semântico, Tailwind CSS (classes utilitárias), JavaScript vanilla (`fetch`, DOM API) |
| **Back-end & Runtime** | Node.js 24, Express 5 e TypeScript (da etapa 3 em diante) |
| **Validação & Erros** | Schemas declarativos com Zod e middleware de erros customizado (`HttpError`) |
| **Persistência** | SQLite nativo (`node:sqlite`) e, depois, Prisma ORM (schema declarativo e migrations) |
| **Segurança & Auth** | Hash Argon2id e JWT HS256, ambos com `node:crypto`, e middleware de autorização |
| **Serviços & Upload** | Envio de e-mail transacional (Nodemailer) e upload multipart/form-data (Multer) |
| **Qualidade & Testes** | Vitest (unidade e rotas com `supertest`) e Playwright (testes E2E) |
| **Infraestrutura** | Docker (Dockerfile otimizado), Docker Compose e volumes de dados |

### Dicionário de dados do domínio

O dicionário de dados formaliza a estrutura, tipos, regras de integridade e propósitos de cada campo mantido pela aplicação:

#### 1. Entidade `User` (Investidor / Conta)

Representa o investidor cadastrado na plataforma, dono da carteira de investimentos e responsável pela autenticação no sistema.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único universal do investidor gerado no cadastro. |
| `name` | `String` | Obrigatório | Nome completo do usuário (mínimo de 3 caracteres). |
| `email` | `String` | Obrigatório, **Unique** | E-mail do investidor usado para login e recebimento de notificações transacionais. |
| `password` | `String` | Hash | Hash da senha gerado com **Argon2id** no formato PHC, com salt por registro (mínimo de 8 caracteres na entrada). |
| `image` | `String?` | Opcional | Nome ou caminho relativo da foto de avatar enviada pelo usuário (ex: `avatar-123.jpg`). |
| `createdAt` | `DateTime` | Default `now()` | Data e hora de criação do registro no banco de dados. |

#### 2. Entidade `Investment` (Investimento / Ativo Financeiro)

Representa um ativo financeiro ou título custodiado pertencente à carteira de um usuário.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único do ativo no banco de dados. |
| `name` | `String` | Obrigatório | Nome comercial ou código do ativo (ex: "Tesouro Selic 2029", "CDB Liquidez", "IVVB11"). |
| `amount` | `Int` | Obrigatório | Valor monetário aplicado em reais (deve ser um valor positivo). |
| `interest` | `String` | Obrigatório | Taxa de rentabilidade ou indexador associado (ex: "100% Selic", "110% CDI", "IPCA + 6%"). |
| `dueDate` | `DateTime?` | Opcional | Data de vencimento ou resgate estipulada para o título financeiro. |
| `userId` | `String` | **FK** (`User.id`) | Identificador do usuário proprietário deste investimento (garante isolamento por dono). |
| `categoryId` | `String?` | **FK** (`Category.id`) | Categoria de classificação do investimento (ex: Renda Fixa, Pós-fixado). |
| `brokerId` | `String?` | **FK** (`Broker.id`) | Instituição financeira ou corretora de custódia do título. |

#### 3. Entidade `Category` (Categoria de Ativos)

Classificação temática dos ativos para agrupar e filtrar os investimentos no dashboard.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único da categoria. |
| `name` | `String` | Obrigatório | Nome da categoria (ex: "Renda fixa", "Pós-fixado", "Internacional"). |
| `color` | `String` | Obrigatório | Código de cor CSS/hexadecimal para estilização do badge visual no front. |

#### 4. Entidade `Broker` (Corretora / Instituição Financeira)

Instituição ou plataforma onde os títulos e valores estão custodiados.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `String` (UUID v4) | **PK** | Identificador único da corretora. |
| `name` | `String` | Obrigatório | Nome da instituição financeira ou corretora (ex: "Banco Inter", "XP Investimentos", "Avenue"). |

## Trilha incremental de desenvolvimento

<Steps>

1. **Front estático**: Telas HTML semânticas e estilização em Tailwind CSS, definindo a UX do sistema sem JavaScript.
2. **API em memória**: Rotas REST Express alimentando o front-end via JavaScript vanilla (`fetch`).
3. **TypeScript em camadas**: Migração da API para TypeScript com divisão em rotas, controllers e manipuladores de erro.
4. **Validação**: Validação estrita de entradas HTTP (`body`, `query`, `params`) com schemas Zod.
5. **Documentação da API**: Documento OpenAPI gerado dos próprios schemas Zod e servido com Swagger UI.
6. **SQLite nativo**: Substituição do array em memória por banco relacional SQLite com `node:sqlite`, sem ORM.
7. **Prisma ORM**: Modelagem declarativa com Prisma Client, migrations versionadas e relacionamentos.
8. **Cadastro de usuário**: Criação da entidade `User`, formulário de auto-cadastro e hash de senhas com Argon2id.
9. **Autenticação**: Login com credenciais, emissão de tokens JWT e autorização de investimentos por dono.
10. **E-mail**: Notificações transacionais de boas-vindas enviadas via Nodemailer.
11. **Upload de avatar**: Envio multipart (`FormData`) e upload de imagens de perfil via Multer.
12. **Testes de software**: Suíte de testes de unidade, de rotas (`supertest`), de front (Vitest) e E2E (`Playwright`).
13. **Docker**: Empacotamento em imagem Docker multi-estágio, orquestração via Docker Compose e volumes.

</Steps>

## Evolução incremental do projeto

<Aside type="tip" title="O trilho é cumulativo por construção">
  Cada pasta de etapa nasce como cópia da anterior mais o delta daquela etapa. Nada que foi
  introduzido desaparece depois: o TypeScript da etapa 3 vale até a 12, a validação da etapa 4
  continua nas rotas de todas as seguintes, e o isolamento por dono da etapa 9 acompanha o
  resto. As duas únicas remoções do trilho são substituições explicadas na própria página — o
  array em memória sai na etapa 6, quando o banco entra, e os scripts de migration manual saem
  na etapa 7, quando o Prisma assume.
</Aside>


Cada etapa resolve exatamente um problema novo e mantém tudo que veio antes. O código de todo
o projeto reside 100% no próprio repositório, dentro de `examples/express/projects/`. Não é necessário
clonar repositórios externos (`git clone`).

Comparar duas pastas locais com `git diff --no-index` mostra, de forma isolada, exatamente o que aquela
etapa alterou no código — e é a melhor forma de ver o efeito direto de uma decisão de arquitetura.

A regra da trilha é cumulativa: o código da etapa `n+1` parte do código da etapa `n`. O front
começa estático com HTML e `tailwind.css`; depois a API conecta esse front com JavaScript
vanilla; então o back-end migra para TypeScript e continua em TypeScript nas etapas seguintes.
A comparação mostra apenas as linhas que saíram, entraram ou mudaram.

<Aside type="tip" title="Compare duas etapas com um comando">
  Você pode comparar quaisquer duas pastas de etapas locais dentro do repositório DevLab com o comando:

  ```bash title="Terminal"
  git diff --no-index -- \
    examples/express/projects/invest-app-static \
    examples/express/projects/invest-app-api || true
  ```

  Ou comparar a transição da persistência nativa em SQLite para o Prisma ORM:

  ```bash title="Terminal"
  git diff --no-index -- \
    examples/express/projects/invest-app-db-simple \
    examples/express/projects/invest-app-prismajs-relation || true
  ```

  O parâmetro `--no-index` instrui o Git a comparar diretamente duas pastas locais sem depender de histórico ou repositório remoto. O `|| true` evita que o terminal trate diferenças de arquivos como erro de comando.
</Aside>

### Execução dos projetos locais

Cada página de etapa aponta para uma pasta em `examples/express/projects/`. Localmente:

```bash title="Terminal"
cd examples/express/projects/invest-app-db-simple
npm install
npm run dev
```

<Aside type="caution" title="As dependências mudam entre as pastas">
  A etapa 7 em diante instala o Prisma; a etapa 3 acrescenta `typescript` e `@types/*`.
  Rode `npm install` de novo sempre que trocar de pasta — o `package.json` é diferente.
</Aside>
