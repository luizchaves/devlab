### US07 — Enxergar como a carteira está distribuída · RF01, RNF03

> **Como** investidor,
> **quero** classificar cada ativo por categoria e corretora,
> **para** enxergar como o meu patrimônio está distribuído.

```gherkin
Cenário: CA07.1 - Reconstruir o banco via migrations
  Quando rodo npx prisma migrate deploy
  Então a estrutura inteira é recriada no SQLite a partir das migrations

Cenário: CA07.2 - A listagem já traz as relações
  Quando busco os investimentos
  Então cada registro inclui a sua categoria e a sua corretora

Cenário: CA07.3 - Corretora é criada se não existir
  Quando crio um investimento informando uma corretora que ainda não existe
  Então recebo o status 201
  E a corretora passa a existir para os próximos investimentos

Cenário: CA07.4 - Categoria precisa existir
  Quando crio um investimento com um categoryId inexistente
  Então recebo o status 400

Cenário: CA07.5 - O que se versiona é a migration
  Quando inspeciono o repositório
  Então a pasta prisma/migrations está versionada
  Mas o arquivo prisma/dev.db está no gitignore
```

## O que muda nesta etapa

Comparando com a etapa anterior, o SQL manual é substituído pelo Prisma ORM. A pasta `prisma/` assume a responsabilidade do esquema declarativo e migrations versionadas. Além disso, a aplicação ganha os modelos `Category` e `Broker`, relacionando investimentos a categorias e corretoras de custódia com integridade referencial.

## Descrição das tarefas

Abaixo estão detalhadas as tarefas de implementação desta etapa, com orientações e trechos de código.

### TK07.1 · Instalar Prisma e criar `prisma/schema.prisma` (Schema declarativo)

```bash title="Terminal: instalação do Prisma ORM e do driver adapter"
npm install prisma @prisma/client @prisma/adapter-better-sqlite3
npx prisma init --datasource-provider sqlite
```

O arquivo abre com dois blocos de configuração: o `generator client` das linhas 4 a 6, que define o que será gerado a partir do schema, e o `datasource db` das linhas 8 a 11, que aponta para o SQLite e lê a string de conexão de `env("DATABASE_URL")` — por isso o `.env` é obrigatório.

O `model Investment` das linhas 13 a 23 é o mesmo investimento das etapas anteriores, agora descrito em vez de criado por SQL. A linha 14 substitui o `AUTOINCREMENT` da etapa 6 por `@id @default(uuid())`, e o `@default(now())` da linha 18 transfere ao banco a responsabilidade pelo `createdAt`.

O trecho destacado nas linhas 19 a 22 é a novidade da etapa. Cada relação aparece em **duas** linhas: o campo escalar `categoryId` (linha 20), que vira a coluna de chave estrangeira no banco, e o campo de relação `category` (linha 19), que só existe no código e é o que permite escrever `investment.category.name`. O `@relation(fields: [categoryId], references: [id])` é o que amarra os dois.

Do outro lado, `Category` e `Broker` (linhas 25 a 36) declaram `investments Investment[]` — a ponta "muitos" da relação. Repare também nos `@unique` das linhas 27, 28 e 34: é essa restrição que torna possível o `connectOrCreate` por nome que aparece no model.

### TK07.2 · Substituir `src/database/database.ts` (Client com driver adapter)

O arquivo que na etapa 6 abria o SQLite à mão e envolvia a API síncrona em promessas encolheu para catorze linhas.

A novidade do Prisma 7 está na linha 9: o client recebe um **driver adapter**. Até a versão 6, o Prisma embarcava um binário próprio para falar com o banco; agora quem conversa com o SQLite é um driver Node comum, e o Prisma se apoia nele. Na prática isso significa instalação mais leve e o mesmo driver que o resto do ecossistema usa.

A linha 12 cria **uma** instância de `PrismaClient` e a linha 14 a exporta; todos os models importam essa mesma instância. A instância única não é detalhe de estilo: cada `new PrismaClient()` abre seu próprio pool de conexões.

### TK07.3 · Modificar `src/models/Investment.ts` (De SQL para ORM)

As cinco funções continuam com os mesmos nomes e as mesmas assinaturas tipadas, exportadas na linha 92. Nenhuma linha de controller precisou mudar. O que desapareceu foram as strings de SQL e o `mapRow`.

O `include` das linhas 8 a 11 é o que substitui o `JOIN` escrito à mão: declarado uma vez, no topo, e reutilizado em todas as consultas — é isso que garante que a entidade saia com o mesmo formato em todas as rotas.

O trecho destacado nas linhas 13 a 37 é o `create` e mostra as duas formas de ligar um registro a outro. Em `category` (linha 31), o `connect` exige que a categoria **já exista** e recebe o id. Em `broker` (linha 33), o `connectOrCreate` procura a corretora pelo nome e, se não achar, cria — só funciona porque `Broker.name` é `@unique` no schema.

O `read` da linha 39 merece uma segunda olhada: a linha 40 reescreve o filtro de nome como `{ contains: ... }`, que é a tradução Prisma do `LIKE '%...%'` que a etapa 6 escrevia à mão. O `update` e o `remove`, nas linhas 55 a 90, repetem o desenho do `create` e estão recolhidos.

### TK07.4 · Substituir os scripts de banco pelo `prisma db seed`

Os dois scripts que criavam a tabela e carregavam os dados na etapa 6 saem do projeto. O `CREATE TABLE` agora é gerado pelo `prisma migrate` a partir do schema, e a carga inicial passa a ser o `src/database/seed.ts`, registrado no `package.json` sob a chave `prisma.seed`.

O seeder ficou mais curto e mais seguro: o `upsert` das linhas 14 a 18 grava a categoria se ela não existir e não faz nada se já existir — rodar o seed duas vezes deixa de ser um erro. O `$disconnect` das linhas 23 e 26 é obrigatório em um script avulso: sem ele, o processo não termina.

<Aside type="caution" title="O `.env` é obrigatório">
  O `prisma.config.ts` lê a conexão de `process.env.DATABASE_URL`. Sem um `.env` na raiz do
  projeto, qualquer comando do Prisma falha antes de tocar no banco — por isso o passo de
  execução começa com `cp .env.example .env`.
</Aside>

<Aside type="tip" title="O caminho do banco mudou de referência">
  Com o driver adapter, `file:./prisma/dev.db` é resolvido a partir de **onde o processo roda**,
  e não mais da pasta do schema. É por isso que o `.env` desta etapa escreve o caminho completo
  a partir da raiz do projeto.
</Aside>

## Migrations

```bash title="Terminal"
npx prisma migrate dev --name init
npx prisma generate
npx prisma studio
```

| Comando                 | Quando usar                                   |
| ----------------------- | --------------------------------------------- |
| `migrate dev`           | ao alterar o schema, em desenvolvimento        |
| `migrate deploy`        | em produção — aplica sem gerar nem resetar     |
| `migrate reset`         | recomeçar do zero (**apaga tudo**)             |
| `db seed`               | popular com os dados iniciais                  |
| `studio`                | inspecionar visualmente                        |

## Executando

<Steps>

1. Entre na pasta desta etapa e instale:

   ```bash title="Terminal"
   cd examples/express/projects/invest-app-prismajs-relation
   npm install
   cp .env.example .env
   ```

2. Crie o banco a partir do schema e popule as categorias:

   ```bash title="Terminal"
   npx prisma migrate dev
   npx prisma db seed
   ```

3. Suba o servidor:

   ```bash title="Terminal"
   npm run dev
   ```

4. Inspecione os dados no navegador:

   ```bash title="Terminal"
   npx prisma studio
   ```

</Steps>

## O diff que importa

```bash title="Terminal"
git diff --no-index -- \
  examples/express/projects/invest-app-db-simple/src/models \
  examples/express/projects/invest-app-prismajs-relation/src/models || true

git diff --no-index -- \
  examples/express/projects/invest-app-db-simple/src/routes.js \
  examples/express/projects/invest-app-prismajs-relation/src/routes.js || true
```

O primeiro diff é grande: os models foram reescritos de ponta a ponta. O segundo é curto — as
rotas continuam chamando `Investment.create`, `Investment.read` e `Investment.readById` com os
mesmos argumentos. É a segunda vez no projeto que a camada de dados é trocada inteira sem que
as camadas acima percebam, e é exatamente isso que a separação em camadas promete.

<Aside type="caution" title="`prisma/dev.db` não vai para o Git">
  O arquivo do banco é binário e muda a cada requisição. O que se versiona é a pasta
  `prisma/migrations/`: ela reconstrói o banco inteiro em qualquer máquina com
  `npx prisma migrate dev`.
</Aside>
