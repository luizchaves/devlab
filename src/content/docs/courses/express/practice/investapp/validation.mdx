## O que muda nesta etapa

A etapa anterior organizou o código. Esta etapa aproveita essa organização para encaixar um
middleware de validação entre a rota e o handler:

```diff title="Etapa 3 → 4: a verificação sai do handler e vira contrato" showLineNumbers
 // src/routes/investments.routes.ts
+import { validate } from '@/middlewares/validate.ts';
+import { createInvestmentSchema } from '@/schemas/investment.schema.ts';

-router.post('/investments', requireJson, InvestmentController.create);
+router.post(
+  '/investments',
+  requireJson,
+  validate(createInvestmentSchema),
+  InvestmentController.create,
+);
```

O ponto importante é que a rota passa a declarar o contrato que aceita. Dado inválido não
fica espalhado em `if` dentro do controller.

### TK04.1 · Instalar Zod e criar `src/middlewares/validate.ts` (Middleware genérico de validação)

```bash title="Terminal: instalação do Zod"
npm install zod
```

A função `validate` da linha 11 não é um middleware: ela **devolve** um. Esse padrão é o que permite escrever `validate(createInvestmentSchema)` na declaração da rota e ainda assim entregar ao Express a assinatura `(req, res, next)` que ele espera.

O `safeParse` das linhas 13 a 17 é o coração do arquivo. Repare que ele não valida `req.body` sozinho: monta um objeto com as **três** fontes de dados de uma requisição — `body`, `query` e `params` — e valida o conjunto. É por isso que todo schema desta etapa começa com uma dessas três chaves.

O restante é a bifurcação. Dados inválidos viram um `HttpError` com as issues do Zod anexadas (linha 20), e quem transforma isso em resposta é o `errorHandler` que a etapa 3 já tinha — nenhum middleware novo monta resposta de erro. Dados válidos seguem para o handler com o `next()` da linha 23.

## As três camadas de validação

O schema desta etapa protege a API, mas ele não é a única barreira de um sistema — nem deveria
ser. Validação aparece em três lugares, com propósitos diferentes, e confundi-los é a origem de
duas falhas clássicas: achar que o front protege, e achar que o servidor basta.

| Camada | Onde roda | Serve para | Um atacante contorna? |
| ------ | --------- | ---------- | --------------------- |
| Front-end | navegador | dar retorno imediato a quem digita | sim, trivialmente |
| API (esta etapa) | servidor | recusar dado inválido antes da regra de negócio | não |
| Banco de dados | SGBD | impedir estado inválido, venha de onde vier | não |

As três se sobrepõem de propósito. A repetição não é desperdício: cada uma falha de um jeito
diferente, e a de baixo é a última que resta quando as outras falham.

### No front-end: retorno imediato, nunca proteção

O HTML já valida sem uma linha de JavaScript. Os campos do formulário da etapa 1 podem declarar
as mesmas regras do schema:

```html title="public/index.html — validação nativa do navegador"
<input class="input" type="text" name="name" required minlength="3" />
<input class="input" type="number" name="value" required min="1" step="1" />
```

O navegador bloqueia o envio e exibe a mensagem sozinho. Para mensagens próprias, a API de
validação de formulário do DOM dá o estado de cada campo:

```js title="public/js/index.js — mensagens próprias"
form.onsubmit = (event) => {
  const campo = form.querySelector('[name="name"]');

  if (!campo.checkValidity()) {
    event.preventDefault();
    // `validity` diz *qual* regra quebrou: tooShort, valueMissing, rangeUnderflow…
    campo.setCustomValidity(
      campo.validity.tooShort ? 'O nome deve ter no mínimo 3 caracteres' : ''
    );
    campo.reportValidity();
  }
};
```

O ganho é de experiência: o usuário descobre o erro enquanto digita, sem esperar a ida ao
servidor. O ganho de segurança é **zero** — o `minlength` é um atributo do HTML na máquina de
quem acessa, e some com um clique no DevTools ou com um `curl` que ignora o formulário.

<Aside type="danger" title="Validação de front nunca protege a API">
  Qualquer cliente pode chamar `POST /api/investments` sem passar pelo formulário. É por isso
  que a etapa 4 existe: as regras do front são uma cópia por conveniência, e a cópia que vale é
  a do servidor.
</Aside>

### No banco: a última linha de defesa

O schema do Zod protege quem entra **pela API**. O banco continua exposto a tudo o mais: um
seeder, um script de migração de dados, um `INSERT` no terminal, ou um segundo serviço que
compartilhe a base no futuro.

Por isso as mesmas regras aparecem uma terceira vez, agora como restrições da tabela. Na etapa
6, quando o SQLite entrar, o `CREATE TABLE` já traz as primeiras:

```sql title="Restrições que vivem na tabela"
CREATE TABLE investments (
  id    TEXT PRIMARY KEY,                    -- unicidade garantida pelo banco
  name  TEXT NOT NULL,                       -- obrigatoriedade
  value INTEGER NOT NULL CHECK (value > 0)   -- a mesma regra do z.number().positive()
);
```

Cada uma tem um equivalente do lado da aplicação:

| Regra | No Zod | No banco |
| ----- | ------ | -------- |
| campo obrigatório | ausência de `.optional()` | `NOT NULL` |
| valor positivo | `z.number().positive()` | `CHECK (value > 0)` |
| e-mail único | consulta prévia, sujeita a corrida | `UNIQUE` |
| dono existente | nenhuma | `FOREIGN KEY` |

A linha do e-mail merece atenção, porque é onde a diferença entre as camadas fica visível.
Verificar na aplicação se o e-mail já existe **não** garante unicidade: entre a consulta e a
inserção, outra requisição pode gravar o mesmo endereço. Só o `UNIQUE` do banco fecha essa
janela, porque a checagem acontece dentro da transação. É por isso que a etapa 8 declara
`email String @unique` no schema do Prisma e trata a violação como `409`, em vez de confiar
em um `if`.

<Aside type="tip" title="A regra de bolso">
  Valide **cedo** para a experiência e **fundo** para a integridade. O front avisa, a API
  recusa, o banco impede. Quando as três discordam, quem manda é a de baixo — e é por isso que
  a mensagem amigável tem que estar em cima.
</Aside>

## Testando

As três fontes são verificadas antes de o handler rodar — nada chega ao model. Comece pelo
corpo, com nome curto demais e valor negativo:

<ApiRequest method="POST" path="/api/investments" baseUrl="http://localhost:3000" description="Corpo inválido em dois campos">
{`
  {
    "name": "TS",
    "value": -100
  }
`}
</ApiRequest>

<ApiResponse status={400}>
{`
  {
    "error": "Validation error",
    "issues": [
      { "code": "too_small", "message": "O nome deve ter no minimo 3 caracteres", "path": ["body", "name"] },
      { "code": "too_small", "message": "O valor deve ser positivo", "path": ["body", "value"] }
    ]
  }
`}
</ApiResponse>

Agora o parâmetro de rota. Um `:id` que não é UUID nem chega a ser procurado no banco:

<ApiRequest method="GET" path="/api/investments/abc" baseUrl="http://localhost:3000" description="Parâmetro de rota inválido" />

<ApiResponse status={400}>
{`
  {
    "error": "Validation error",
    "issues": [
      { "validation": "uuid", "message": "O id deve ser um UUID valido", "path": ["params", "id"] }
    ]
  }
`}
</ApiResponse>

E a query string. O filtro `name` é opcional, mas se vier não pode ser vazio:

<ApiRequest method="GET" path="/api/investments?name=" baseUrl="http://localhost:3000" description="Filtro presente e vazio" />

<ApiResponse status={400}>
{`
  {
    "error": "Validation error",
    "issues": [
      { "code": "too_small", "message": "O filtro name nao pode ser vazio", "path": ["query", "name"] }
    ]
  }
`}
</ApiResponse>

Repare no `path` de cada issue: ele começa em `"body"`, `"params"` ou `"query"` justamente
porque o middleware valida o objeto `{ body, query, params }` inteiro. É esse caminho que
permite ao front destacar o campo exato que falhou, sem adivinhação.

Note também a diferença entre `400` e `404` nas duas leituras por id. `GET /api/investments/abc`
é `400`: o formato do id está errado. Já um UUID bem formado que não existe no banco é `404` —
o pedido faz sentido, o recurso é que não está lá.

## Conceitos abordados

- Validação de `body`, `query` e `params` com um único middleware
- Schemas com Zod, compostos por fonte de dados
- Erro `400` antes de a requisição chegar ao model
- Contrato da API declarado na própria rota
- As três camadas: front para a experiência, API para o contrato, banco para a integridade
- Por que verificar unicidade na aplicação não substitui o `UNIQUE` do banco
