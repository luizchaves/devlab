Este documento é o **contrato** da API do InvestApp no seu estado final, ao fim da etapa 13. Ele
descreve o que o servidor aceita e o que devolve, independentemente de como está implementado por
dentro. A [visão geral](../) trata do produto; o [backlog](../backlog/) trata do trabalho; esta
página trata da interface entre o front-end e o servidor.

<Aside type="tip" title="Esta página e o documento OpenAPI">
  Da [etapa 5](../swagger/) em diante o mesmo contrato é publicado em OpenAPI 3, gerado a partir
  dos schemas Zod que validam as requisições: `GET /api/openapi.json` devolve o documento, e
  `GET /api/docs` o serve navegável. Esta página é a leitura humana desse contrato, com as
  regras de negócio que o JSON Schema não expressa.
</Aside>

## Convenções gerais

| Aspecto | Regra |
| ------- | ----- |
| **Base** | `http://localhost:3000/api` — o front é servido pelo **mesmo** processo, por `express.static`, então API e páginas compartilham a origem |
| **Formato** | JSON em requisição e resposta, exceto o upload de avatar, que é `multipart/form-data` |
| **Content-Type** | Toda requisição com corpo JSON deve enviar `application/json`; o servidor responde `400` caso contrário |
| **Identificadores** | UUID v4 gerados pelo servidor; enviar `id` no corpo não tem efeito |
| **Datas** | ISO 8601 em UTC, no formato `2026-03-01T12:00:00.000Z` |
| **Valores monetários** | Inteiros em **centavos**. `value: 1000000` são R$ 10.000,00 |
| **Autenticação** | `Authorization: Bearer <token>` em todas as rotas, exceto `POST /api/users` e `POST /api/signin` |
| **Paginação** | Não há. A carteira de um usuário é devolvida inteira |

<Aside type="caution" title="Por que o valor viaja em centavos">
  Ponto flutuante não representa `0,1` exatamente, e somar centenas de aportes em `Float` acumula
  erro de arredondamento. Guardar centavos em `Int` elimina a classe inteira de bugs: a conversão
  acontece só na borda — o front multiplica por 100 ao enviar e divide por 100 ao exibir.
</Aside>

### Formato de erro

Toda falha responde com um objeto que tem sempre a chave `error`. Quando a falha veio da
validação, vem junto a lista `issues`, no formato do Zod:

<Tabs>
  <TabItem label="Erro simples">
    ```json title="404 Not Found"
    {
      "error": "Investment not found"
    }
    ```
  </TabItem>

  <TabItem label="Erro de validação">
    ```json title="400 Bad Request"
    {
      "error": "Validation error",
      "issues": [
        {
          "code": "too_small",
          "path": ["body", "value"],
          "message": "O valor deve ser positivo"
        }
      ]
    }
    ```

    O `path` começa pela **fonte** da requisição (`body`, `params` ou `query`), o que permite ao
    cliente destacar o campo certo do formulário sem inferir nada.
  </TabItem>
</Tabs>

### Status codes usados

| Código | Quando |
| ------ | ------ |
| `200` | Leitura bem-sucedida, ou atualização que devolve o recurso |
| `201` | Recurso criado — investimento, usuário ou avatar |
| `204` | Remoção concluída, sem corpo na resposta |
| `400` | Corpo, query ou parâmetro que não passou no schema; `Content-Type` ausente; arquivo inválido |
| `401` | Token ausente, malformado, adulterado ou expirado; credenciais inválidas |
| `404` | Recurso inexistente **ou pertencente a outra conta** |
| `409` | Conflito de unicidade: e-mail já cadastrado |
| `500` | Falha não prevista; o corpo nunca expõe detalhes internos |

<Aside type="caution" title="Por que `404` e não `403` para o recurso de outra conta">
  Responder `403` confirmaria que o recurso existe. Como a existência de um investimento também é
  informação do dono, a API trata "não é seu" e "não existe" como a mesma resposta. Isso é uma
  decisão de contrato, e está coberta pelos critérios `CA10.2` e `CA10.3` do
  [backlog](../backlog/).
</Aside>

## Autenticação

O ciclo é o mesmo em todas as rotas privadas: o cliente troca credenciais por um token e o
reapresenta a cada requisição.

<Mermaid title="Do login à requisição autenticada">
{`
sequenceDiagram
  participant F as Front
  participant A as API
  participant D as SQLite

  F->>A: POST /api/signin { email, password }
  A->>D: busca o usuário pelo e-mail
  D-->>A: registro com o hash Argon2id
  A->>A: verifyPassword em tempo constante
  A-->>F: 200 { auth: true, token }
  Note over F: guarda o token no localStorage
  F->>A: GET /api/investments (Authorization: Bearer …)
  A->>A: verifyJwt → req.userId
  A->>D: SELECT ... WHERE userId = ?
  D-->>A: apenas os investimentos do dono
  A-->>F: 200 [ … ]
`}
</Mermaid>

O token é um JWT HS256 com o seguinte payload. Ele **não é criptografado**: qualquer pessoa
consegue lê-lo, e o que a assinatura garante é apenas que ele não foi alterado.

```json title="Payload do token"
{
  "sub": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "name": "Luiz Chaves",
  "email": "luiz@exemplo.com",
  "iat": 1772409600,
  "exp": 1772413200
}
```

| Campo | Significado |
| ----- | ----------- |
| `sub` | O dono do token. É este valor que vira `req.userId` e entra em toda consulta |
| `iat` | Instante de emissão, em segundos desde a época |
| `exp` | Instante de expiração; passado esse ponto, a rota responde `401` |

## Recurso `users`

Cadastro de conta. É uma das duas rotas públicas do sistema — quem se cadastra ainda não tem
token.

### `POST /api/users`

| Campo | Tipo | Regra |
| ----- | ---- | ----- |
| `name` | `string` | obrigatório, mínimo de 3 caracteres |
| `email` | `string` | obrigatório, formato de e-mail, único no sistema |
| `password` | `string` | obrigatório, mínimo de 8 caracteres |
| `confirmationPassword` | `string` | opcional; quando presente, deve ser igual a `password` |

<ApiRequest method="POST" path="/api/users" baseUrl="http://localhost:3000">
{`
  {
    "name": "Luiz Chaves",
    "email": "luiz@exemplo.com",
    "password": "senha-secreta",
    "confirmationPassword": "senha-secreta"
  }
`}
</ApiRequest>

<ApiResponse status={201}>
{`
  {
    "id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
    "name": "Luiz Chaves",
    "email": "luiz@exemplo.com"
  }
`}
</ApiResponse>

A senha **nunca** aparece na resposta, nem como hash. O `confirmationPassword` é conferido pelo
schema e descartado antes de chegar ao model.

<Aside type="note" title="O e-mail de boas-vindas não faz parte do contrato">
  Concluído o cadastro, a [etapa 10](../email/) dispara uma notificação transacional. O envio é
  **efeito colateral**: um SMTP fora do ar é registrado no log e o cadastro segue respondendo
  `201`. Nenhum cliente deve inferir, pela resposta, que a mensagem chegou.
</Aside>

### `POST /api/signin`

<ApiRequest method="POST" path="/api/signin" baseUrl="http://localhost:3000">
{`

    "email": "luiz@exemplo.com",
    "password": "senha-secreta"
  }
`}
</ApiRequest>

<ApiResponse status={200}>
{`
  {
    "auth": true,
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI5YjFkZWI0ZCJ9.Xr2..."
  }
`}
</ApiResponse>

<ApiResponse status={401}>
{`
  {
    "error": "Invalid credentials"
  }
`}
</ApiResponse>

E-mail inexistente e senha errada devolvem exatamente esta resposta. Diferenciar as duas
entregaria a um atacante a lista de e-mails cadastrados.

## Recurso `investments`

O recurso central. Todas as rotas exigem token, e todas são resolvidas dentro do escopo do dono.

### Representação

```json title="Investment"
{
  "id": "0d4d0b8e-1f4a-4c62-9a54-6c2f1f2a9d31",
  "name": "Tesouro Selic 2029",
  "value": 1000000,
  "interest": "100% Selic",
  "createdAt": "2026-03-01T12:00:00.000Z",
  "userId": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "categoryId": "c1a2b3c4-…",
  "brokerId": "b1a2b3c4-…",
  "category": { "id": "c1a2b3c4-…", "name": "Pós", "color": "#6366f1" },
  "broker": { "id": "b1a2b3c4-…", "name": "Banco Inter" }
}
```

`category` e `broker` vêm **resolvidos** na mesma resposta, pelo `include` do Prisma: o cliente
não precisa de uma segunda requisição para exibir o nome da categoria ou da corretora.

### Corpo aceito em `POST` e `PUT`

| Campo | Tipo | Regra |
| ----- | ---- | ----- |
| `name` | `string` | obrigatório, mínimo de 3 caracteres |
| `value` | `number` | obrigatório, positivo, **em centavos** |
| `interest` | `string` | obrigatório; taxa ou indexador livre (ex.: `"110% CDI"`, `"IPCA + 6%"`) |
| `categoryId` | `string` | obrigatório, UUID de uma categoria existente |
| `broker` | `string` | obrigatório; a corretora é ligada pelo **nome**, não pelo id |
| `createdAt` | `string` | opcional; quando ausente, o servidor usa o instante atual |

<Aside type="note" title="Categoria por id, corretora por nome">
  A assimetria é intencional. As categorias são um conjunto fechado, semeado pela aplicação — o
  front as lista em um `<select>` e envia o id. As corretoras são abertas: o usuário digita o
  nome, e o servidor conecta a existente ou cria uma nova (`connectOrCreate`). Uma corretora
  nunca precisa ser cadastrada antes de ser usada.
</Aside>

### `GET /api/investments`

Aceita o filtro opcional `?name=`, que devolve os investimentos cujo nome contém o texto
informado.

<ApiRequest method="GET" path="/api/investments?name=Tesouro" baseUrl="http://localhost:3000" description="Requer o cabeçalho Authorization" />

<ApiResponse status={200}>
{`
  [
    {
      "id": "0d4d0b8e-…",
      "name": "Tesouro Selic 2029",
      "value": 1000000,
      "interest": "100% Selic",
      "category": { "name": "Pós", "color": "#6366f1" },
      "broker": { "name": "Banco Inter" }
    }
  ]
`}
</ApiResponse>

Um filtro vazio (`?name=`) responde `400`: é quase sempre um bug do cliente, e devolver a lista
inteira esconderia o problema.

### `POST /api/investments`

<ApiRequest method="POST" path="/api/investments" baseUrl="http://localhost:3000">
{`
  {
    "name": "Tesouro Selic 2029",
    "value": 1000000,
    "interest": "100% Selic",
    "categoryId": "c1a2b3c4-1234-4321-abcd-1234567890ab",
    "broker": "Banco Inter"
  }
`}
</ApiRequest>

<ApiResponse status={201}>
{`
  {
    "id": "0d4d0b8e-…",
    "name": "Tesouro Selic 2029",
    "value": 1000000,
    "interest": "100% Selic",
    "createdAt": "2026-03-01T12:00:00.000Z",
    "userId": "9b1deb4d-…",
    "category": { "id": "c1a2b3c4-…", "name": "Pós", "color": "#6366f1" },
    "broker": { "id": "b1a2b3c4-…", "name": "Banco Inter" }
  }
`}
</ApiResponse>

O `userId` da resposta vem do token. Enviá-lo no corpo não muda o dono — o campo é simplesmente
ignorado pelo schema.

Um `categoryId` que não corresponde a nenhuma categoria responde `400`: o schema aceita o formato
UUID, mas a chave estrangeira é recusada pelo banco.

### `PUT /api/investments/:id`

Substitui o recurso inteiro, e exige os mesmos campos obrigatórios do `POST`. Um id de outro dono
responde `404`.

### `DELETE /api/investments/:id`

Responde `204`, sem corpo.

## Recursos `categories` e `brokers`

Os dois são **somente leitura** pela API: as categorias são semeadas pela aplicação, e as
corretoras nascem sozinhas quando um investimento cita um nome novo. Ambos exigem token e aceitam
o filtro opcional `?name=`.

<ApiRequest method="GET" path="/api/categories" baseUrl="http://localhost:3000" />

<ApiResponse status={200}>
{`
  [
    { "id": "c1a2b3c4-…", "name": "Pós", "color": "#6366f1" },
    { "id": "c2a2b3c4-…", "name": "Pré", "color": "#d946ef" },
    { "id": "c3a2b3c4-…", "name": "IPCA", "color": "#f43f5e" },
    { "id": "c4a2b3c4-…", "name": "Renda Variável", "color": "#eab308" }
  ]
`}
</ApiResponse>

O `color` acompanha a categoria porque é o front quem desenha o badge: a cor é dado, e não
estilo escrito na tela.

<Aside type="caution" title="Categorias e corretoras são globais">
  Nenhum dos dois pertence a uma conta — são vocabulário compartilhado. O que é isolado por dono é
  o **investimento**, que é quem tem `userId`. Em um produto real essa é uma decisão a revisar, e
  é o tipo de pergunta que uma especificação escrita ajuda a fazer cedo.
</Aside>

## Upload de avatar

As duas únicas rotas que não falam JSON. O corpo é `multipart/form-data` com um campo de arquivo
chamado `image`.

| Regra | Valor |
| ----- | ----- |
| Nome do campo | `image` |
| Tipos aceitos | `image/jpeg`, `image/png`, `image/gif` |
| Tamanho máximo | 2 MB |
| Nome no disco | prefixo aleatório de 16 bytes + nome original |
| Local | `public/imgs/profile/`, servido por `express.static` |

<ApiRequest method="POST" path="/api/users/image" baseUrl="http://localhost:3000" lang="http" description="multipart/form-data com o campo image">
{`
  Content-Type: multipart/form-data; boundary=----Boundary
  Authorization: Bearer <token>

  ------Boundary
  Content-Disposition: form-data; name="image"; filename="avatar.png"
  Content-Type: image/png

  <bytes do arquivo>
  ------Boundary--
`}
</ApiRequest>

<ApiResponse status={201}>
{`
  {
    "id": "e5f6a7b8-…",
    "path": "/imgs/profile/2c140192a308afe95752c7de669f6424-avatar.png",
    "userId": "9b1deb4d-…"
  }
`}
</ApiResponse>

A resposta traz o **caminho público**, não o binário: o banco guarda a referência, e a imagem é
servida como arquivo estático. Um arquivo de tipo não permitido ou acima de 2 MB responde `400`.

`POST` cria o primeiro avatar; `PUT` substitui o que já existe e responde `200`. A distinção é
possível porque `userId` é `@unique` na tabela `Image`: cada conta tem no máximo um avatar.

<Aside type="note" title="Um endpoint que o front chama e a API ainda não expõe">
  As telas `home.html` e `profile.html` chamam `GET /api/users/me` para exibir nome, e-mail e
  avatar, e o `requests.http` também exercita esse caminho — mas a rota **não está registrada** em
  `src/routes/users.routes.ts`. Hoje a chamada cai no `notFoundHandler` e responde `404`, e a tela
  de perfil recorre ao avatar padrão. Expor esse endpoint é o menor incremento pendente do
  projeto, e um bom primeiro exercício depois da etapa 13.
</Aside>

## Contrato executável

O arquivo `requests.http` de cada etapa é a versão executável desta especificação: cada bloco
separado por `###` vira um botão *Send Request* na extensão
[REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client) do VS Code,
e o token capturado no login é reutilizado nas requisições seguintes.

```http title="requests.http (trecho)"
@host = http://localhost:3000/api
@token = {{signin.response.body.$.token}}

### Signin Ok

# @name signin
POST {{host}}/signin
Content-Type: application/json

{
  "email": "luiz@email.com",
  "password": "12345678"
}

### Read Investments

GET {{host}}/investments
Authorization: Bearer {{token}}
```

Rodar o arquivo de cima a baixo exercita o contrato inteiro, incluindo os caminhos de erro —
token ausente, credenciais inválidas e id em formato inválido.
