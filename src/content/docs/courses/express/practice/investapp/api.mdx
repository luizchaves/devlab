### US02 — Manter a carteira pela aplicação · RF01

> **Como** investidor,
> **quero** cadastrar, consultar, editar e remover os meus investimentos,
> **para** manter a carteira atualizada sem depender de planilha.

```gherkin
Cenário: CA02.1 - Listar os investimentos
  Quando envio GET /api/investments
  Então recebo o status 200
  E o corpo é uma lista de investimentos

Cenário: CA02.2 - Filtrar pelo nome
  Dado que existe um investimento chamado "Tesouro Selic 2029"
  Quando envio GET /api/investments?name=Tesouro
  Então recebo o status 200
  E a lista traz apenas os investimentos cujo nome contém "Tesouro"

Cenário: CA02.3 - Criar um investimento
  Quando envio POST /api/investments com nome e valor válidos
  Então recebo o status 201
  E o corpo traz o investimento criado, com um id gerado pelo servidor

Cenário: CA02.4 - Recusar corpo incompleto
  Quando envio POST /api/investments sem o campo "value"
  Então recebo o status 400
  E nada é acrescentado à lista

Cenário: CA02.5 - Investimento inexistente
  Quando envio GET, PUT ou DELETE em /api/investments/{id} com um id que não existe
  Então recebo o status 404

Cenário: CA02.6 - Remover um investimento
  Dado um investimento existente
  Quando envio DELETE /api/investments/{id}
  Então recebo o status 204
  E a resposta não tem corpo

Cenário: CA02.7 - O front consome a API
  Quando abro http://localhost:3000
  Então os cartões exibidos vêm de uma chamada fetch
  E não estão escritos no HTML

Cenário: CA02.8 - O limite conhecido desta etapa
  Dado investimentos cadastrados
  Quando reinicio o servidor
  Então a lista volta ao estado inicial
```

## Estrutura da aplicação

O front-end desta etapa vive dentro de `public/` e é servido pelo próprio Express através do middleware `express.static('public')`. Ao mesmo tempo, as rotas sob `/api/investments` expõem os dados dinâmicos a partir de um array em memória. Como front e API compartilham a mesma origem, o navegador não precisa de CORS para conversar com o servidor — o middleware `cors` continua registrado apenas para permitir chamadas de fora, como as do `requests.http`.

## O que muda nesta etapa

A etapa 1 desenhou as telas com dados escritos à mão no HTML. Esta etapa mantém a mesma
interface — cabeçalho, cartões de ativo e formulário — e troca esses dados fixos por respostas
da API.

| Etapa 1 (`invest-app-static`) | Etapa 2 (`invest-app-api`) |
| ----------------------------- | -------------------------- |
| páginas HTML abertas direto do disco | páginas em `public/`, servidas por `express.static` |
| três cartões escritos no HTML | cartões gerados em JavaScript a partir de `GET /api/investments` |
| formulário com `type="button"`, sem envio | `form.onsubmit` disparando `POST /api/investments` |
| nenhum arquivo `.js` | `public/js/index.js`, `services/api.js` e `lib/format.js` |
| nenhum servidor | `src/index.js`, `src/routes.js` e `src/data/investments.js` |

<Aside type="note" title="Express 5 dispensa o `express-async-errors`">
  No Express 4 era preciso instalar o pacote `express-async-errors`: um `throw` dentro de um
  handler `async` vira uma promessa rejeitada, e o `try`/`catch` interno do framework não a
  enxergava — o processo caía com `unhandledRejection` em vez de responder um erro HTTP.

  O Express 5 encaminha promessas rejeitadas sozinho. Como todo o InvestApp está na versão 5,
  o pacote não aparece em nenhuma etapa: o `throw` das rotas síncronas desta etapa e o das
  rotas `async` da etapa 6 em diante chegam ao mesmo manipulador de erros sem ajuda externa.
  Veja [Tratamento de Erros](../../../api/error-handling/).
</Aside>

<Aside type="caution" title="`req.body` pode ser `undefined` no Express 5">
  No Express 4, o `express.json()` deixava `req.body` como `{}` quando não havia corpo. No
  Express 5 ele fica **`undefined`**, e desestruturar `undefined` lança `TypeError`. Por isso a
  linha 15 do `routes.js` escreve `const { name, value } = req.body ?? {}`: sem o `?? {}`, um
  `POST` sem corpo devolveria `500` em vez do `400` previsto no contrato.
</Aside>

### TK02.2 · Criar `src/data/investments.js` (Armazenamento em memória)

O arquivo inteiro é um `export const investments` com dois registros de exemplo. Cada objeto já tem a forma que a API vai devolver: `id` como UUID (linhas 3 e 8), `name` e `value`.

Repare que o `id` é uma string, e não um número sequencial. Essa escolha antecipa o comportamento do banco de dados das etapas 6 e 6 e evita que o front-end passe a depender de um contador que só existiria em memória.

Como é um array exportado por um módulo ES, todas as rotas manipulam a **mesma** referência: o `push` de uma rota é visível na leitura da outra. É o suficiente para exercitar o ciclo completo de leitura e escrita sem banco de dados.

### TK02.3 · Criar `src/routes.js` (Endpoints do recurso `/api/investments`)

Este é o arquivo mais longo da etapa, e vale lê-lo em quatro partes.

A classe `HttpError` das linhas 5 a 10 estende `Error` e acrescenta o campo `code`. É ela que permite escrever `throw new HttpError('Investment not found', 404)` no meio de uma rota e ainda assim responder com o status certo.

O bloco destacado nas linhas 14 a 28 é o `POST /investments` e serve de modelo para as demais rotas: lê `name` e `value` de `req.body` (linha 15), rejeita entrada incompleta com `400` (linhas 17 a 19), gera o identificador com `uuidv4()` (linha 21), empurra o objeto para o array (linha 25) e responde `201` com o recurso criado (linha 27).

As leituras vêm em seguida: o `GET /investments` das linhas 30 a 40 aceita o filtro opcional `req.query.name` (linha 31) e devolve o array inteiro quando ele não vem; o `GET /investments/:id` das linhas 42 a 52 usa `findIndex` e responde `404` quando o índice não existe. O `PUT` (linhas 54 a 74) e o `DELETE` (linhas 76 a 88) repetem exatamente esse par de verificações e por isso aparecem recolhidos.

Fecham o arquivo os dois middlewares finais: o das linhas 91 a 93 responde `404` para qualquer caminho não declarado, e o das linhas 96 a 104 é o manipulador de erros — ele converte um `HttpError` no status guardado em `err.code` e transforma qualquer outra exceção em `500`. É esse par que sustenta o contrato de status codes da tabela a seguir.

### TK02.4 · Criar `public/js/services/api.js` e `public/js/index.js` (Integração Vanilla JS)

O front é dividido em duas responsabilidades, e essa separação é o ponto didático da etapa: **um único arquivo conhece `fetch`**, e a tela conversa apenas com ele.

O `services/api.js` é essa camada fina. As quatro funções — `create`, `read`, `update` e `remove` — montam a URL a partir da constante `domain = '/api'` da linha 1 e diferem apenas no método e no corpo. O `read` da linha 20 é o caso mais simples, sem objeto `config`; o `create` da linha 3 mostra o trio que sempre acompanha um envio de JSON: `method: 'POST'`, `body: JSON.stringify(data)` e o cabeçalho `Content-Type` da linha 11. Já o `remove` da linha 45 não chama `res.json()`, porque a rota responde `204 No Content`, sem corpo.

### TK02.5 · Criar `requests.http` (Especificação executável da API)

O arquivo é uma documentação executável: cada bloco separado por `###` vira um botão *Send Request* na extensão REST Client do VS Code.

O trecho destacado nas linhas 1 a 13 mostra o mecanismo que torna o arquivo encadeável. A linha 1 define a variável `@host` com a base da API; a linha 6 nomeia a requisição com `# @name createdInvestment`; e a linha 2 captura o `id` da resposta dessa requisição em `@createdInvestmentId`. É por isso que, mais adiante, a linha 34 consegue escrever `GET {{host}}/investments/{{createdInvestmentId}}` sem que você precise copiar um UUID à mão.

O restante do arquivo, recolhido, exercita justamente os caminhos de erro do contrato: criação sem `value` para provocar `400`, leitura por um id inválido para provocar `404` e assim por diante. Rodar o arquivo de cima a baixo valida a API inteira sem abrir o navegador.

## O front-end

A interface continua vanilla: módulos pequenos, sem React, Vue ou framework de componentes. A
regra que sustenta o front desta etapa é a separação em três arquivos, cada um com uma
responsabilidade só.

| Arquivo | Responsabilidade | Conhece `fetch`? |
| ------- | ---------------- | ---------------- |
| `public/js/services/api.js` | montar URL, método, cabeçalhos e corpo das requisições | sim, e é o único |
| `public/js/index.js` | ler o DOM, tratar eventos e desenhar os cartões | não |
| `public/js/lib/format.js` | formatar valores em Real com `toLocaleString('pt-br')` | não |

Essa divisão é o que permite trocar a origem da API, acrescentar um cabeçalho `Authorization`
ou mudar o tratamento de erro em um único arquivo. Na etapa 9, quando o token JWT entrar, a
alteração acontece só dentro de `services/api.js`.
