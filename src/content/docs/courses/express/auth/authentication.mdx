Com o usuário cadastrado, falta responder à pergunta que toda requisição seguinte carrega:
**quem está chamando?** Esta aula constrói essa resposta com JSON Web Tokens assinados por
`node:crypto`.

## Objetivo

Ao final você saberá diferenciar autenticação de autorização, explicar o que um JWT é e o
que ele não é, assinar e verificar tokens sem bibliotecas, proteger rotas com um middleware
e reconhecer as armadilhas clássicas de sessões sem estado.

## Autenticação não é autorização

São duas perguntas distintas, respondidas por middlewares distintos e com status HTTP
distintos:

| Pergunta                    | Nome           | Status quando falha | Middleware        |
| --------------------------- | -------------- | ------------------- | ----------------- |
| Quem é você?                | Autenticação   | `401 Unauthorized`  | `authenticate`    |
| O que você pode fazer?      | Autorização    | `403 Forbidden`     | `authorize`       |

<Aside type="note" title="O nome `401 Unauthorized` é enganoso">
  Apesar do nome, `401` significa **não autenticado** — "identifique-se". Quem está
  identificado mas não tem permissão recebe `403`. A confusão vem da própria especificação
  do HTTP, não do Express.
</Aside>

## Sessão com estado ou token sem estado

Há duas formas de o servidor lembrar quem está do outro lado, e a escolha define a
arquitetura:

<Mermaid title="Sessão com estado no servidor versus token sem estado">
{`
flowchart TD
  subgraph S["Sessão com estado"]
    S1["Login válido"] --> S2["Servidor cria a sessão<br/>e guarda em memória ou Redis"]
    S2 --> S3["Cliente recebe um cookie<br/>com o id da sessão"]
    S3 --> S4["Cada requisição:<br/>servidor consulta o armazenamento"]
  end
  subgraph T["Token sem estado"]
    T1["Login válido"] --> T2["Servidor assina um token<br/>com os dados dentro"]
    T2 --> T3["Cliente guarda o token"]
    T3 --> T4["Cada requisição:<br/>servidor só confere a assinatura"]
  end
`}
</Mermaid>

| Critério                     | Sessão com estado          | Token (JWT)                     |
| ---------------------------- | -------------------------- | ------------------------------- |
| Onde o estado mora           | servidor (memória, Redis)  | no próprio token, com o cliente |
| Consulta por requisição      | sim                        | não                             |
| Escalar para várias instâncias | exige armazenamento compartilhado | trivial                |
| Revogar imediatamente        | apagar a sessão            | **difícil** — o token é válido até expirar |
| Tamanho por requisição       | um id curto                | o token inteiro                 |
| Uso típico                   | aplicação web com servidor de páginas | API consumida por SPA e mobile |

<Aside type="tip" title="JWT não é sempre a resposta">
  Para uma aplicação web com um único servidor, uma sessão em cookie é mais simples e
  permite logout de verdade. O JWT brilha quando há várias instâncias, clientes móveis ou
  serviços diferentes validando o mesmo token.
</Aside>

## Anatomia de um JWT

Um JWT é apenas **texto**: três partes em Base64URL separadas por ponto.

```txt title="Um JWT decomposto"
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwiaWF0IjoxNzY0NDAwMDAwLCJleHAiOjE3NjQ0MDM2MDB9.qk3Xr6…
└──────────── header ────────────┘ └──────────── payload ────────────┘ └── signature ──┘

header  (base64url) => {"alg":"HS256","typ":"JWT"}
payload (base64url) => {"sub":"1","iat":1764400000,"exp":1764403600}
signature           => HMAC-SHA256("header.payload", segredo)
```

<Aside type="danger" title="O payload NÃO é criptografado">
  Base64 é codificação, não cifra: qualquer pessoa cola o token em
  [jwt.io](https://jwt.io/) e lê o conteúdo. **Nunca** coloque senha, CPF ou qualquer dado
  sensível no payload. O que a assinatura garante é integridade — que ninguém alterou os
  dados —, não sigilo.
</Aside>

As chaves curtas do payload são padronizadas pela [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html):

| Chave  | Nome        | Significado                                     |
| ------ | ----------- | ----------------------------------------------- |
| `sub`  | subject     | quem é o dono do token — o id do usuário         |
| `iat`  | issued at   | quando foi emitido (segundos desde 1970)         |
| `exp`  | expiration  | quando deixa de valer                            |
| `iss`  | issuer      | quem emitiu                                      |
| `aud`  | audience    | para qual serviço o token vale                   |

Três checagens, três ataques evitados:

| Checagem                          | Ataque que ela impede                                    |
| --------------------------------- | -------------------------------------------------------- |
| `timingSafeEqual` na assinatura   | ataque de temporização e token forjado                    |
| `alg !== 'HS256'` recusado        | token com `"alg":"none"`, que dispensa assinatura         |
| `exp < agora` recusado            | reuso indefinido de um token antigo                       |

<Aside type="danger" title="O ataque `alg: none`">
  Bibliotecas antigas confiavam no campo `alg` do **próprio token** para escolher como
  verificar. Um atacante trocava `"alg":"none"`, removia a assinatura e era aceito. A regra
  é fixar o algoritmo no servidor e recusar qualquer outro — nunca perguntar ao token.
</Aside>

## Onde o cliente guarda o token

Não existe opção sem risco — existe a escolha do risco que se prefere:

<Tabs syncKey="token-storage">
  <TabItem label="localStorage">
    ```js title="public/js/lib/session.js" showLineNumbers
    export function setToken(token) {
      localStorage.setItem('@app:token', token);
    }

    export function getAuthHeaders() {
      const token = localStorage.getItem('@app:token');

      return token ? { Authorization: `Bearer ${token}` } : {};
    }
    ```

    Simples e funciona com API em outro domínio. Vulnerável a XSS: qualquer script injetado
    na página lê o token.
  </TabItem>

  <TabItem label="Cookie httpOnly">
    ```ts title="src/controllers/auth-controller.ts" showLineNumbers {2-5}
    res.cookie('token', token, {
      httpOnly: true,   // JavaScript da página não lê
      secure: true,     // só trafega em HTTPS
      sameSite: 'lax',  // mitiga CSRF
      maxAge: 3600_000,
    });
    ```

    Inacessível ao JavaScript, logo imune a XSS na leitura. Em troca, exige cuidado com
    CSRF e configuração adicional quando a API está em outro domínio.
  </TabItem>
</Tabs>

| Risco                        | `localStorage` | Cookie `httpOnly`         |
| ---------------------------- | -------------- | ------------------------- |
| XSS lê o token               | sim            | não                       |
| CSRF                         | não            | sim — mitigado por `SameSite` |
| API em outro domínio         | simples        | exige `credentials` e CORS |
| Enviado automaticamente      | não            | sim                       |

<Aside type="caution" title="Nem `localStorage` nem cookie salvam de XSS">
  Com XSS ativo, o atacante não precisa ler o cookie: ele faz as requisições a partir da
  própria página, e o navegador anexa o cookie sozinho. A defesa real é não ter XSS —
  assunto de [Endurecimento](../../security/hardening/).
</Aside>

## Expiração, renovação e logout

Um token sem estado não pode ser cancelado: enquanto a assinatura for válida e `exp` não
tiver passado, ele funciona. Isso tem três consequências práticas.

**Expiração curta.** Quanto menor o `exp`, menor a janela de um token roubado. Uma hora é um
ponto de partida razoável para um token de acesso.

**Renovação.** Para não obrigar o usuário a fazer login a cada hora, usa-se um par: um
*access token* curto e um *refresh token* longo, guardado com mais cuidado e **este sim** com
estado no servidor, para poder ser revogado.

**Logout.** No cliente, logout é apagar o token. No servidor, o token continua válido até
expirar:

```js title="public/js/lib/session.js" showLineNumbers
export function signOut() {
  // Do lado do servidor, o token continua válido até o `exp`.
  localStorage.removeItem('@app:token');
  window.location.href = 'signin.html';
}
```

| Necessidade                     | Solução                                              |
| ------------------------------- | ---------------------------------------------------- |
| Reduzir a janela de risco       | `exp` curto (15 min a 1 h)                            |
| Não pedir login o tempo todo    | refresh token com estado no servidor                  |
| Revogar um token específico     | lista de revogação (`jti`) consultada a cada requisição|
| Revogar todos de um usuário     | campo `tokenVersion` no usuário, comparado no payload  |

<Aside type="note" title="Revogação devolve o estado que o JWT tirou">
  Qualquer mecanismo de revogação exige consultar algo a cada requisição — exatamente o que
  o token sem estado evitava. É um custo consciente, não uma falha de projeto.
</Aside>

## Exercício

No projeto `express-auth`:

1. Faça login e cole o token em [jwt.io](https://jwt.io/) — leia o payload sem o segredo.
2. Altere um caractere do payload, reenvie e confirme que a API responde `401`.
3. Gere um token com `signJwt({ sub: '1' }, -1)` e confirme a recusa por expiração.
4. Acrescente `iss: 'investment-api'` ao payload e valide-o em `verifyJwt`.
5. Proteja `GET /users` com `authenticate` aplicado ao router inteiro e verifique que
   nenhuma rota ficou de fora.

<details>
  <summary>Possível resposta</summary>

  ```ts title="src/utils/jwt.ts" showLineNumbers {6-8}
  const ISSUER = 'investment-api';

  export function verifyJwt(token: string): JwtPayload {
    // … verificação da assinatura …

    if (payload.iss !== ISSUER) {
      throw new Error('Emissor inválido');
    }

    return payload;
  }
  ```

  Alterar o payload invalida o token porque a assinatura foi calculada sobre
  `header.payload`: qualquer byte diferente produz um HMAC diferente, e o
  `timingSafeEqual` recusa.
</details>

## Desafio

Implemente a revogação por `tokenVersion`: acrescente o campo ao usuário, inclua-o no payload
do token e faça o `authenticate` recusar quando o valor do token for menor que o do banco.
Use isso para implementar "sair de todos os dispositivos". Meça o custo: quantas consultas a
mais por requisição?

## Perguntas de revisão

### Conceitos

1. **Qual a diferença entre autenticação e autorização?**

   <details>
     <summary>Possível resposta</summary>

     Autenticação responde "quem é você" e falha com `401`. Autorização responde "o que você
     pode fazer" e falha com `403`. São middlewares distintos, e o segundo pressupõe o
     primeiro.
   </details>

2. **Por que um JWT não deve conter dados sensíveis?**

   <details>
     <summary>Possível resposta</summary>

     Porque o payload é apenas Base64: qualquer pessoa com o token lê o conteúdo. A
     assinatura garante que ninguém **alterou** os dados, não que ninguém os leia.
   </details>

3. **O que a assinatura garante, então?**

   <details>
     <summary>Possível resposta</summary>

     Integridade e origem: o token foi emitido por quem tem o segredo e não foi modificado
     desde então. Sem o segredo, não é possível produzir uma assinatura válida para um
     payload alterado.
   </details>

### Operação

4. **Por que logout não invalida um JWT no servidor?**

   <details>
     <summary>Possível resposta</summary>

     Porque o servidor não guarda nada sobre o token: ele apenas confere a assinatura e a
     expiração. Apagar o token no cliente impede o uso por aquele navegador, mas uma cópia
     roubada continua funcionando até `exp`.
   </details>

5. **Qual o problema de um `exp` muito longo?**

   <details>
     <summary>Possível resposta</summary>

     A janela de exploração de um token roubado é a validade dele. Com um mês de `exp`, um
     token vazado dá acesso por um mês — e não há como cancelá-lo sem reintroduzir estado no
     servidor.
   </details>
