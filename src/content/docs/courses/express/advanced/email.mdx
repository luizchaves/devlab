Confirmar um cadastro, redefinir uma senha, avisar sobre um vencimento: três funcionalidades
comuns que dependem de a API conseguir enviar e-mail. Esta aula trata do como — e dos
cuidados que a redefinição de senha exige.

## Objetivo

Ao final você saberá enviar e-mail a partir do Express, testar sem entregar mensagem a
ninguém, implementar confirmação de cadastro e redefinição de senha com token de uso único, e
manter o envio fora do caminho crítico da requisição.

## SMTP e serviços transacionais

O protocolo de envio é o SMTP, e há duas formas de falar com ele:

| Opção                         | Como funciona                                  | Quando usar                     |
| ----------------------------- | ---------------------------------------------- | ------------------------------- |
| SMTP direto (Gmail, provedor) | a aplicação conecta a um servidor SMTP          | projeto pequeno, sala de aula   |
| Serviço transacional (API)    | requisição HTTP para Resend, SendGrid, SES      | produção                        |
| Caixa de teste (Ethereal, Mailpit) | intercepta e mostra sem entregar          | desenvolvimento e testes        |

<Aside type="caution" title="Entregabilidade é o problema real">
  Enviar é fácil; **chegar na caixa de entrada** é difícil. Sem SPF, DKIM e DMARC
  configurados no domínio, a mensagem vai para spam. Serviços transacionais existem
  basicamente para resolver isso.
</Aside>

## Enviando com `nodemailer`

O [`nodemailer`](https://nodemailer.com/) é o cliente SMTP padrão em Node. A configuração
vive no ambiente, nunca no código:

<PackageManagerTabs package="nodemailer" />

```ini title=".env.example"
MAIL_HOST="smtp.ethereal.email"
MAIL_PORT=587
MAIL_USER=""
MAIL_PASSWORD=""
MAIL_FROM="InvestApp <nao-responda@investapp.dev>"
```

```ts title="src/config/mail.ts" showLineNumbers {3-9}
import nodemailer from 'nodemailer';

export const transporter = nodemailer.createTransport({
  host: process.env.MAIL_HOST,
  port: Number(process.env.MAIL_PORT ?? 587),
  // 587 usa STARTTLS; `secure: true` só para a porta 465.
  secure: Number(process.env.MAIL_PORT) === 465,
  auth: { user: process.env.MAIL_USER, pass: process.env.MAIL_PASSWORD },
});
```

```ts title="src/services/mail-service.ts" showLineNumbers {8-9}
import { transporter } from '#config/mail.ts';

export async function sendMail({ to, subject, html }: MailInput) {
  return transporter.sendMail({
    from: process.env.MAIL_FROM,
    to,
    subject,
    html,
    // Alternativa em texto puro: clientes antigos e filtros de spam agradecem.
    text: html.replace(/<[^>]+>/g, ''),
  });
}
```

<Aside type="danger" title="Credencial de e-mail é credencial">
  `MAIL_PASSWORD` no repositório permite a qualquer pessoa enviar mensagens em nome do seu
  domínio — o que é usado para phishing, não para curiosidade. Vale a mesma regra de
  [Configuração](../../architecture/config/): apenas no `.env`, nunca versionado.
</Aside>

## Confirmação de cadastro

O e-mail de confirmação prova que o endereço existe e pertence a quem se cadastrou. O fluxo
usa um token de uso único:

<Mermaid title="Fluxo de confirmação de cadastro por e-mail">
{`
flowchart TD
  A["POST /users<br/>cria com emailVerified = false"] --> B["Gera token aleatório<br/>randomBytes(32)"]
  B --> C["Guarda o hash do token<br/>com validade de 24 h"]
  C --> D["Envia link<br/>/confirm?token=…"]
  D --> E["GET /confirm?token=…"]
  E --> F{"Token existe,<br/>não expirou<br/>e não foi usado?"}
  F -->|não| G["400 Token inválido"]
  F -->|sim| H["emailVerified = true<br/>token apagado"]
`}
</Mermaid>

```ts title="src/services/verification-service.ts" showLineNumbers {2,5,8}
export async function criarTokenDeConfirmacao(userId: string) {
  const token = randomBytes(32).toString('base64url');

  await prisma.emailToken.create({
    // Guarda o hash: um vazamento do banco não entrega tokens utilizáveis.
    data: {
      userId,
      tokenHash: createHash('sha256').update(token).digest('hex'),
      expiresAt: new Date(Date.now() + 24 * 60 * 60 * 1000),
    },
  });

  return token;   // só o e-mail recebe o valor original
}
```

<Aside type="tip" title="Token de e-mail também é credencial">
  Quem tem o token entra na conta. Guarde apenas o hash, dê validade curta e invalide após o
  uso — as mesmas três regras de qualquer segredo.
</Aside>

## Redefinição de senha

É o fluxo mais delicado da aplicação, porque é uma porta de entrada legítima que não exige
saber a senha atual.

```ts title="src/controllers/password-controller.ts" showLineNumbers {6,9,12}
export async function solicitarRedefinicao(req: Request, res: Response) {
  const { email } = req.body as { email?: string };
  const user = email ? await User.findByEmail(email) : null;

  if (user) {
    const token = await criarTokenDeRedefinicao(user.id);

    await sendMail({
      to: user.email,
      subject: 'Redefinição de senha',
      html: `<p>Use o link para redefinir: <a href="${config.appUrl}/reset?token=${token}">redefinir senha</a></p>`,
    });
  }

  // Sempre 202, exista ou não a conta.
  res.status(202).json({ message: 'Se o e-mail estiver cadastrado, enviaremos as instruções.' });
}
```

<ApiRequest method="POST" path="/auth/password/forgot" baseUrl="http://localhost:3000">
{`
  {
    "email": "qualquer@example.com"
  }
`}
</ApiRequest>

<ApiResponse status={202} description="A mesma resposta para e-mail existente e inexistente">
{`
  {
    "message": "Se o e-mail estiver cadastrado, enviaremos as instruções."
  }
`}
</ApiResponse>

As regras que tornam esse fluxo seguro:

| Regra                                   | O que ela impede                                    |
| --------------------------------------- | --------------------------------------------------- |
| Resposta idêntica para e-mail inexistente| enumeração de contas                                |
| Token aleatório de 32 bytes             | adivinhação                                         |
| Guardar apenas o hash do token          | uso de tokens vazados do banco                      |
| Validade curta (15 a 60 minutos)        | reuso de um link antigo encontrado no e-mail        |
| Invalidar após o uso                    | reutilização do mesmo link                          |
| Limite de requisições na rota           | uso da API como ferramenta de spam                  |
| Invalidar sessões após a troca          | permanência de um invasor já logado                 |

<Aside type="danger" title="Nunca envie a senha por e-mail">
  Nem a antiga (não existe — só o hash), nem uma nova gerada pelo servidor. E-mail não é
  canal seguro: fica em texto no servidor do provedor, em backups e em qualquer dispositivo
  logado. O que se envia é um link de troca com validade.
</Aside>

## Envio fora do caminho da requisição

Um SMTP lento transforma um cadastro de 50 ms em um cadastro de 3 s — e uma falha no
provedor transforma em `500` uma operação que já deu certo:

```ts title="Cadastro que não depende do e-mail" showLineNumbers {5,7-9}
export async function store(req: Request, res: Response) {
  const user = await User.create(req.body);

  // A resposta não espera o SMTP.
  res.status(201).json(user);

  sendMail({ to: user.email, subject: 'Bem-vindo', html: boasVindas(user) }).catch((error) =>
    console.error({ level: 'error', evento: 'falha-envio-email', userId: user.id, error }),
  );
}
```

<Aside type="caution" title="Isto é uma fila improvisada">
  Se o processo cair entre a resposta e o envio, o e-mail se perde sem registro. Em produção,
  o envio vira um **job** em uma fila com retentativa (BullMQ, pg-boss). O padrão acima é o
  suficiente para aprender — e o suficiente para e-mails não críticos.
</Aside>

## Exercício

No projeto `express-auth`:

1. Configure o `nodemailer` com Ethereal e envie um e-mail de boas-vindas no cadastro.
2. Imprima a URL de prévia com `getTestMessageUrl` e abra a mensagem no navegador.
3. Implemente `POST /auth/password/forgot` respondendo sempre `202`.
4. Implemente `POST /auth/password/reset` que valide o token, troque a senha e invalide o
   token.
5. Aplique `rateLimit({ max: 3, windowMs: 15 * 60_000 })` na rota de solicitação.

<details>
  <summary>Possível resposta</summary>

  ```ts title="src/controllers/password-controller.ts" showLineNumbers {6,12}
  export async function redefinir(req: Request, res: Response) {
    const { token, password } = req.body as { token?: string; password?: string };

    if (!token || !password || password.length < 8) {
      throw new HttpError(422, 'Token e senha (mínimo 8 caracteres) são obrigatórios');
    }

    const hash = createHash('sha256').update(token).digest('hex');
    const registro = await prisma.passwordToken.findUnique({ where: { tokenHash: hash } });

    if (!registro || registro.expiresAt < new Date()) {
      throw new HttpError(400, 'Token inválido ou expirado');
    }

    await User.update({ id: registro.userId, password });
    await prisma.passwordToken.delete({ where: { id: registro.id } });

    res.sendStatus(204);
  }
  ```

  Apagar o token depois do uso é o que impede o mesmo link de funcionar duas vezes.
</details>

## Desafio

Implemente a invalidação de sessões após a troca de senha usando o campo `tokenVersion`
sugerido na aula de [Autenticação](../../auth/authentication/): incremente-o na redefinição
e faça o `authenticate` recusar tokens com versão antiga. Teste que a sessão aberta em outro
navegador é derrubada.

## Perguntas de revisão

### Envio

1. **Por que testes não devem enviar e-mail de verdade?**

   <details>
     <summary>Possível resposta</summary>

     Porque a suíte passa a depender de rede e de um provedor externo, fica lenta e pode
     entregar mensagens a endereços reais. Caixas de teste ou um transporte falso resolvem.
   </details>

2. **Por que o envio não deve bloquear a resposta do cadastro?**

   <details>
     <summary>Possível resposta</summary>

     Porque o SMTP é lento e pode falhar: o usuário esperaria segundos, e uma falha no
     provedor devolveria `500` para uma operação que já foi concluída com sucesso.
   </details>

### Redefinição de senha

3. **Por que responder `202` mesmo para e-mail inexistente?**

   <details>
     <summary>Possível resposta</summary>

     Porque uma resposta diferente revelaria quais e-mails têm conta no sistema. A mensagem
     condicional ("se estiver cadastrado") mantém a experiência aceitável sem vazar nada.
   </details>

4. **Por que guardar o hash do token e não o token?**

   <details>
     <summary>Possível resposta</summary>

     Porque quem tem o token entra na conta. Com apenas o hash no banco, um vazamento não
     entrega tokens utilizáveis — mesma lógica das senhas.
   </details>

5. **Por que nunca enviar uma senha por e-mail?**

   <details>
     <summary>Possível resposta</summary>

     Porque o e-mail permanece em texto no provedor, em backups e em dispositivos logados. E
     a senha antiga sequer existe no servidor — só o hash. O que se envia é um link de troca
     com validade.
   </details>
