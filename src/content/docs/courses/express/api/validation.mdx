Todo dado que chega pela rede é hostil até prova em contrário: pode faltar, vir com o tipo
errado, com o tamanho errado ou com conteúdo malicioso. Esta aula trata de barrar isso antes
que chegue ao controller.

## Objetivo

Ao final você saberá em quais camadas a validação precisa existir, escrever um middleware de
validação sem dependências, descrever regras com um schema e responder erros de validação em
um formato que o front-end consiga usar.

## Validação em camadas

Validar em um lugar só é insuficiente — cada camada protege de uma coisa diferente:

<Mermaid title="Camadas de validação de uma requisição, do navegador ao banco">
{`
flowchart TD
  A["Formulário HTML<br/>required, type, pattern"] -->|"experiência"| B["Middleware de validação<br/>formato, tipo, tamanho"]
  B -->|"contrato da API"| C["Regra de negócio<br/>no controller ou serviço"]
  C -->|"consistência"| D["Banco de dados<br/>NOT NULL, UNIQUE, CHECK"]
  D --> E[("Dado íntegro")]
`}
</Mermaid>

| Camada        | Protege de                                  | Pode ser burlada?                    |
| ------------- | ------------------------------------------- | ------------------------------------ |
| Formulário    | erro de digitação, ida desnecessária ao servidor | sim — basta usar `curl`          |
| Middleware    | formato, tipo, tamanho, campo ausente        | não, se registrado antes da rota     |
| Regra de negócio | estado inválido no domínio                | não                                  |
| Banco         | dado inconsistente vindo de qualquer origem  | não — vale até para seed e migração  |

<Aside type="danger" title="Validação no front-end não é validação">
  O HTML `required` melhora a experiência e nada mais: qualquer pessoa envia a requisição
  direto para a API. Toda regra que importa precisa existir também no servidor.
</Aside>

## Middleware de validação nativo

O padrão de fábrica da aula de [Middleware](../../basics/middleware/) resolve o caso mais
comum — campos obrigatórios — sem nenhuma dependência:

```ts title="src/middlewares/validate.ts" showLineNumbers {1,4,10}
export function requireFields(...campos: string[]) {
  return (req: Request, _res: Response, next: NextFunction) => {
    const body = (req.body ?? {}) as Record<string, unknown>;

    const faltando = campos.filter((campo) => body[campo] === undefined || body[campo] === '');

    if (faltando.length > 0) {
      throw new HttpError(422, `Campos obrigatórios: ${faltando.join(', ')}`);
    }

    next();
  };
}
```

```ts title="src/routes/user-router.ts" showLineNumbers {1}
router.post('/', requireJson, requireFields('name', 'email', 'password'), userController.store);
```

Regras de formato também cabem em funções pequenas e testáveis:

```ts title="src/validators/user.ts" showLineNumbers {5,9}
const EMAIL = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

export function validateUser(body: UserInput): string[] {
  const erros: string[] = [];

  if (!body.name || body.name.trim().length < 2) {
    erros.push('name: informe ao menos 2 caracteres');
  }

  if (!body.email || !EMAIL.test(body.email)) {
    erros.push('email: formato inválido');
  }

  if (!body.password || body.password.length < 8) {
    erros.push('password: mínimo de 8 caracteres');
  }

  return erros;
}
```

<Aside type="caution" title="Nem tudo cabe em regex">
  Validar e-mail por expressão regular só filtra erros grosseiros — a gramática real de um
  endereço válido é longa demais. Para o que importa (o endereço existe e é do usuário?), a
  única prova é enviar um e-mail de confirmação, assunto da aula de
  [Envio de E-mail](../../advanced/email/).
</Aside>

## Schemas com Zod

Quando as regras crescem, descrevê-las declarativamente evita dezenas de `if`. O
[Zod](https://zod.dev/) define o formato uma vez e ainda **infere o tipo TypeScript** a
partir dele.

Antes de chegar ao schema, porém, falta uma peça: um erro capaz de carregar o mapa de campos,
já que o `HttpError` leva apenas uma mensagem.

```ts title="src/errors/ValidationError.ts" showLineNumbers {2,5}
import { HttpError } from '#errors/HttpError.ts';

export class ValidationError extends HttpError {
  issues: Record<string, string>;

  constructor(issues: Record<string, string>) {
    super(422, 'Dados inválidos');
    this.name = 'ValidationError';
    this.issues = issues;
  }
}
```

O `errorHandler` passa a incluir `issues` quando ele existir:

```ts title="src/middlewares/error-handler.ts" ins={4}
res.status(status).json({
  error: {
    status,
    ...(error instanceof ValidationError ? { issues: error.issues } : {}),
    message: status >= 500 ? 'Erro interno do servidor' : error.message,
  },
});
```

Com isso resolvido, o schema descreve as regras e o middleware apenas o executa:

<Tabs syncKey="validation">
  <TabItem label="Schema">
    ```ts title="src/schemas/user.ts" showLineNumbers {12}
    import { z } from 'zod';

    export const createUserSchema = z.object({
      name: z.string().trim().min(2, 'informe ao menos 2 caracteres'),
      email: z.email('formato inválido'),
      password: z.string().min(8, 'mínimo de 8 caracteres'),
      role: z.enum(['user', 'admin']).default('user'),
    });

    // O tipo sai do schema: uma fonte de verdade, não duas.
    export type CreateUserInput = z.infer<typeof createUserSchema>;
    ```
  </TabItem>

  <TabItem label="Middleware">
    ```ts title="src/middlewares/validate.ts" showLineNumbers {5,8,14}
    import type { ZodType } from 'zod';

    export function validate(schema: ZodType) {
      return (req: Request, _res: Response, next: NextFunction) => {
        const resultado = schema.safeParse(req.body);

        if (!resultado.success) {
          throw new ValidationError(formatIssues(resultado.error));
        }

        // O corpo validado substitui o original: tipos garantidos daqui em diante.
        req.body = resultado.data;

        next();
      };
    }
    ```
  </TabItem>

  <TabItem label="Uso">
    ```ts title="src/routes/user-router.ts" showLineNumbers {1}
    router.post('/', requireJson, validate(createUserSchema), userController.store);
    ```
  </TabItem>
</Tabs>

| Critério                     | Validação manual        | Zod                                |
| ---------------------------- | ----------------------- | ---------------------------------- |
| Dependência                  | nenhuma                 | uma dependência de produção        |
| Regras simples               | curto e claro           | curto e claro                      |
| Objetos aninhados e arrays   | verboso e repetitivo    | declarativo                        |
| Tipo TypeScript              | escrito à mão, separado | inferido do schema                 |
| Conversão (`"3"` → `3`)      | manual                  | `z.coerce.number()`                |
| Mensagem por campo           | montada à mão           | vem pronta em `error.issues`       |

<Aside type="tip" title="`safeParse` em vez de `parse`">
  `parse` lança uma exceção do Zod que o `errorHandler` não conhece e trataria como `500`.
  `safeParse` devolve `{ success, data | error }` e deixa a decisão do status com a
  aplicação.
</Aside>

## O formato do erro de validação

Um erro de validação precisa dizer **qual campo** falhou — senão o front-end não consegue
destacar o input. Uma mensagem única em texto obriga a adivinhação:

<ApiRequest method="POST" path="/users" baseUrl="http://localhost:3000">
{`
  {
    "name": "A",
    "email": "nao-e-email",
    "password": "123"
  }
`}
</ApiRequest>

<ApiResponse status={422}>
{`
  {
    "error": {
      "status": 422,
      "message": "Dados inválidos",
      "issues": {
        "name": "informe ao menos 2 caracteres",
        "email": "formato inválido",
        "password": "mínimo de 8 caracteres"
      }
    }
  }
`}
</ApiResponse>

A conversão das *issues* do Zod para esse mapa cabe em uma função:

```ts title="src/middlewares/validate.ts" showLineNumbers {4}
function formatIssues(error: ZodError): Record<string, string> {
  return Object.fromEntries(
    error.issues.map((issue) => [issue.path.join('.'), issue.message]),
  );
}
```

<Aside type="note" title="`400` ou `422`?">
  `400 Bad Request` cobre a requisição malformada — JSON quebrado, `Content-Type` ausente.
  `422 Unprocessable Content` cobre a requisição bem formada com conteúdo semanticamente
  inválido — que é o caso da validação. Muita API usa `400` para os dois; o importante é ser
  consistente e documentar.
</Aside>

## Restrições no banco

A última camada é a única que vale para **toda** origem — inclusive um seed, uma migração ou
uma consulta manual. É por isso que ela não é opcional:

| Restrição SQL            | Garante                                | Equivalente no Prisma            |
| ------------------------ | -------------------------------------- | -------------------------------- |
| `NOT NULL`               | a coluna sempre tem valor              | campo sem `?`                    |
| `UNIQUE`                 | não há duplicata                       | `@unique`                        |
| `DEFAULT`                | valor quando o campo é omitido         | `@default(...)`                  |
| `CHECK`                  | condição sobre o valor                 | não há — use uma migração manual |
| `FOREIGN KEY`            | a referência existe                    | `@relation(...)`                 |

```sql title="Restrições na criação da tabela" showLineNumbers {3,5,7}
CREATE TABLE "User" (
  "id"        TEXT     NOT NULL PRIMARY KEY,
  "name"      TEXT     NOT NULL,
  "email"     TEXT     NOT NULL,
  "password"  TEXT     NOT NULL CHECK (LENGTH(password) >= 8),
  "createdAt" DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
```

A violação chega ao Express como erro da biblioteca e precisa de tradução — `UNIQUE` vira
`409`, como visto em [Tratamento de Erros](../error-handling/).

<Aside type="caution" title="A checagem prévia não substitui a restrição">
  `if (await User.existsByEmail(email))` antes do `INSERT` deixa uma janela entre a consulta
  e a escrita: dois cadastros simultâneos passam pelos dois `if` e gravam o mesmo e-mail.
  Só o índice `UNIQUE` impede de verdade — a checagem prévia serve para a mensagem bonita.
</Aside>

## Exercício

No projeto `express-typescript`:

1. Escreva `requireFields` conforme a aula e aplique-o em `POST /users`.
2. Acrescente `validateUser` com as regras de nome, e-mail e senha.
3. Faça a resposta de erro trazer o mapa `issues` com um campo por chave.
4. Responda `422`, e não `400`, para a falha de validação.
5. Confirme com `curl` que enviar `{}` lista os três campos de uma vez, e não apenas o
   primeiro.

<details>
  <summary>Possível resposta</summary>

  ```ts title="src/middlewares/validate.ts" showLineNumbers
  import type { NextFunction, Request, Response } from 'express';

  import { ValidationError } from '#errors/ValidationError.ts';
  import { validateUser } from '#validators/user.ts';

  export function validateUserBody(req: Request, _res: Response, next: NextFunction) {
    const erros = validateUser((req.body ?? {}) as UserInput);

    if (erros.length > 0) {
      const issues = Object.fromEntries(
        erros.map((erro) => erro.split(': ') as [string, string]),
      );

      throw new ValidationError(issues);
    }

    next();
  }
  ```

  Reunir **todos** os erros antes de responder é o ponto: validar campo a campo e responder
  no primeiro obriga o usuário a descobrir os problemas um por vez.
</details>

## Desafio

Adapte o middleware `validate(schema)` para validar também `req.params` e `req.query`,
recebendo um objeto `{ body?, params?, query? }` de schemas. Trate o caso de `?page=2`:
a query chega como string e precisa virar número — compare fazer isso à mão com usar
`z.coerce.number()`.

## Perguntas de revisão

### Camadas

1. **Por que validar no front-end não dispensa validar no servidor?**

   <details>
     <summary>Possível resposta</summary>

     Porque o cliente é controlado por quem chama: qualquer pessoa envia a requisição direto
     com `curl`. A validação do formulário melhora a experiência; a do servidor é a que
     protege os dados.
   </details>

2. **Por que manter restrições no banco se o middleware já validou?**

   <details>
     <summary>Possível resposta</summary>

     Porque o banco é a única camada que vale para toda origem — seed, migração, script,
     consulta manual — e a única que resolve corridas entre requisições simultâneas.
   </details>

### Implementação

3. **Por que `safeParse` e não `parse`?**

   <details>
     <summary>Possível resposta</summary>

     `parse` lança uma exceção que o `errorHandler` não reconhece e trataria como `500`.
     `safeParse` devolve um resultado e deixa a aplicação escolher o status e o formato do
     erro.
   </details>

4. **Qual a vantagem de substituir `req.body` pelo dado validado?**

   <details>
     <summary>Possível resposta</summary>

     O controller passa a trabalhar com o dado já convertido e com valores padrão aplicados,
     e o tipo inferido do schema corresponde ao que está lá de fato — não a uma promessa.
   </details>

5. **Por que reunir todos os erros antes de responder?**

   <details>
     <summary>Possível resposta</summary>

     Porque responder no primeiro erro obriga o usuário a submeter o formulário várias vezes
     para descobrir todos os problemas. Um mapa `campo → mensagem` permite ao front-end
     destacar tudo de uma vez.
   </details>
