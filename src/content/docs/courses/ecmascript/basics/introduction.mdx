Antes de manipular páginas, consumir APIs ou construir servidores com Node.js, vale
entender o que é JavaScript e por que o termo **ECMAScript** aparece quando falamos
da linguagem. JavaScript não é apenas "a linguagem do navegador": hoje ela roda em
navegadores, servidores, ferramentas de build, aplicações desktop, automações e
ambientes de teste.

Nesta disciplina, JavaScript será usado nos dois lados da aplicação Web: no
navegador, para adicionar comportamento à interface, e no servidor, para construir
APIs HTTP com Node.js e Express.

## Objetivo

Entender a origem do JavaScript, diferenciar JavaScript de ECMAScript, reconhecer o
papel das Web APIs, identificar onde o código pode ser executado e preparar o
ambiente básico para escrever e testar scripts durante a disciplina.

## Por Que JavaScript Importa?

JavaScript se tornou uma das linguagens centrais da Web porque é suportada pelos
navegadores. Quando uma página precisa reagir a cliques, validar um formulário,
alterar elementos, buscar dados de uma API ou atualizar a tela sem recarregar tudo,
normalmente existe JavaScript envolvido.

Com Node.js, a linguagem também passou a ser usada fora do navegador. Isso permitiu
usar JavaScript para escrever servidores, ferramentas de linha de comando, scripts
de automação, testes, processos de build e aplicações completas.

<Aside type="note" title="JavaScript não substitui HTML nem CSS">
  HTML estrutura o conteúdo, CSS define a apresentação visual e JavaScript adiciona
  comportamento. Uma página Web bem construída combina essas três camadas, em vez
  de tentar resolver tudo com uma única tecnologia.
</Aside>

## Origem e a História dos Nomes

JavaScript foi criado em maio de 1995 por **Brendan Eich** enquanto trabalhava na **Netscape**. A linguagem foi desenvolvida em apenas 10 dias com o objetivo de adicionar comportamento dinâmico e interatividade às páginas do navegador Netscape Navigator.

### A Evolução dos Nomes da Linguagem

A linguagem passou por rápidas transições de nome em seu primeiro ano de vida. Criada inicialmente sob o codinome **Mocha**, foi rebatizada comercialmente como **LiveScript** no lançamento beta do Netscape Navigator 2.0. Pouco depois, em uma parceria de marketing entre a Netscape e a Sun Microsystems, o nome foi alterado para **JavaScript**, aproveitando o enorme interesse e a popularidade da linguagem Java no mercado na época.

Com o surgimento de implementações concorrentes, como o *JScript* da Microsoft no Internet Explorer, a Netscape decidiu submeter a linguagem à **Ecma International** para criar um padrão aberto e neutro. Como os direitos da marca "Java" pertenciam à Sun (e atualmente à Oracle), a especificação técnica oficial foi batizada como **ECMAScript** (definida pelo padrão **ECMA-262**).

A tabela a seguir resume essa cronologia de transição e o contexto histórico de cada nomenclatura:

| Nome | Ano | Contexto e Motivação |
| :--- | :--- | :--- |
| **Mocha** | Maio / 1995 | Nome interno do projeto durante o desenvolvimento do protótipo por Brendan Eich. |
| **LiveScript** | Setembro / 1995 | Primeiro nome comercial utilizado no lançamento beta do Netscape Navigator 2.0. |
| **JavaScript** | Dezembro / 1995 | Parceria de marketing com a Sun Microsystems (marca hoje pertencente à Oracle). |
| **ECMAScript** | 1996 - Presente | Especificação técnica oficial e padronizada pela Ecma International (ECMA-262). |

<Aside type="note" title="JavaScript vs Java">
  Apesar da semelhança no nome, **Java e JavaScript são linguagens completamente diferentes** em paradigma, regras de sintaxe, tipos e motores de execução. Uma analogia técnica popular diz que *"Java está para JavaScript assim como Carro está para Carpinteiro"*.
</Aside>

### Padronização ECMA-262 e o TC39

Em termos conceituais, **ECMAScript** é a especificação teórica e padronizada da linguagem, mantida pelo comitê **TC39** (*Technical Committee 39*) da Ecma International. Ela define as regras formais de gramática, tipos, semântica e recursos que toda implementação deve seguir. Já **JavaScript** é a implementação concreta desse padrão executada pelos ambientes do usuário.

A execução do código é realizada por motores especializados (*engines*), como o **V8** (usado no Google Chrome e no Node.js), o **SpiderMonkey** (usado no Mozilla Firefox) e o **JavaScriptCore** (usado no Safari da Apple).

Para atingir alta performance, motores modernos como o V8 combinam interpretação rápida com compilação *Just-In-Time* (JIT). O fluxo arquitetural desse processo é apresentado no diagrama a seguir:

<Mermaid title="Fluxo de Compilação e Execução do Motor V8 (JIT Compiler)">
{`
flowchart TD
  Code["1. Código Fonte JavaScript (.js)"]
  --> Parser["2. Scanner & Parser (Árvore Sintática Abstrata - AST)"]
  --> Ignition["3. Interpretador Ignition (Geração e execução de Bytecode)"]
  --> TurboFan["4. Compilador JIT TurboFan (Gera Código de Máquina Otimizado)"]
  --> CPU["5. Execução de Alta Performance na CPU"]

  Ignition -. "Profiling: detecta funções quentes (Hot Code)" .-> TurboFan
  TurboFan -. "Deopt: desotimiza se o tipo de dado mudar" .-> Ignition
`}
</Mermaid>

O pipeline de execução do motor V8 é composto pelas seguintes etapas principais:

1. **Código-fonte (`.js`)**: O arquivo de script em texto puro é carregado como entrada no motor.
2. **Scanner e Parser (AST)**: O *Scanner* divide o texto em unidades léxicas (*tokens*), e o *Parser* valida a sintaxe para construir a **Árvore Sintática Abstrata** (*Abstract Syntax Tree* ou AST), que representa a estrutura hierárquica das instruções.
3. **Interpretador Ignition (*Bytecode*)**: O *Ignition* converte a AST em um formato intermediário eficiente (*bytecode*) e inicia a execução imediatamente, garantindo que o programa comece a rodar sem atrasos de compilação prévia. Durante a execução, o interpretador realiza *profiling*, monitorando quais funções são executadas repetidamente (*hot code*) e registrando os tipos de dados que trafegam por elas.
4. **Compilador JIT TurboFan (Otimização)**: As funções frequentes (*hot code*) são repassadas ao *TurboFan*, que compila o *bytecode* diretamente para código de máquina nativo e otimizado para a CPU, assumindo que os tipos de dados permanecerão estáveis.
5. **Desotimização (*Deopt*)**: Se uma premissa de tipagem for violada em tempo de execução (por exemplo, uma função otimizada para receber inteiros recebe subitamente uma string), o TurboFan descarta a versão otimizada e devolve o fluxo de controle para o interpretador Ignition de forma transparente (*bailout / deoptimization*).

A cada ciclo anual, o comitê TC39 consolida os recursos que amadureceram em uma nova publicação oficial do padrão **ECMA-262** (como a **17ª edição, ECMAScript 2026**), enquanto o rascunho vivo (*draft*) mantido pelo comitê continua evoluindo para as edições seguintes da especificação.

<Aside type="tip" title="Especificação não é tutorial">
  A especificação ECMAScript é escrita principalmente para quem implementa motores da linguagem, como V8 (Chrome/Node.js), SpiderMonkey (Firefox) ou JavaScriptCore (Safari). Para aprender a programar, a documentação da MDN costuma ser mais adequada.
</Aside>

## JavaScript, ECMAScript e Web APIs

No uso diário, é comum dizer apenas "JavaScript". Tecnicamente, porém, uma aplicação combina o núcleo da linguagem ECMAScript com APIs e ferramentas fornecidas pelo ambiente de execução (navegador ou servidor). A tabela a seguir diferencia o papel de cada uma dessas partes:

| Termo | Papel | Exemplos |
| ----- | ----- | -------- |
| ECMAScript | Define a linguagem base | variáveis, funções, objetos, arrays, classes, módulos, promises |
| JavaScript | Nome comum da linguagem usada pelos desenvolvedores | código escrito em arquivos `.js` ou dentro de `<script>` |
| Web APIs | Recursos oferecidos pelo navegador | DOM, eventos, `fetch`, `localStorage`, timers, console |
| Node.js APIs | Recursos oferecidos pelo Node.js | sistema de arquivos, processos, servidor HTTP, módulos nativos |
| npm | Ecossistema de pacotes | Express, Vite, Prisma, Chart.js, bibliotecas de teste |

Por isso, `Array`, `Object`, `Promise` e `Map` pertencem à linguagem base. Recursos como `document.querySelector`, `addEventListener` e `localStorage` pertencem ao ambiente do navegador (Web APIs). Já APIs como `process`, `Buffer` e módulos nativos como `node:fs` e `node:http` pertencem exclusivamente ao ambiente do Node.js.

<Aside type="note" title="O ambiente importa">
  Um código pode ser JavaScript válido e ainda assim não funcionar em todos os
  lugares. `document` existe no navegador, mas não existe em um script Node comum.
  Por outro lado, módulos como `node:fs` existem no Node.js, mas não no navegador.
</Aside>

ECMAScript define a base da linguagem que será usada nos próximos tópicos. A tabela

## Características Importantes

JavaScript é uma linguagem de alto nível, dinâmica e multiparadigma. Essas características resumem decisões fundamentais de arquitetura que definem como a linguagem opera e como devemos escrever e depurar programas:

| Característica | Ideia principal | Exemplo prático |
| -------------- | --------------- | --------------- |
| Alto nível | Esconde detalhes de memória e gerenciamento de hardware | Objetos e arrays criados sem gerenciar ponteiros manualmente |
| Execução JIT | Combina interpretação com compilação dinâmica em tempo de execução | Execução direta com `node arquivo.js` sem build binário prévio |
| Linguagem de script | Automatiza comportamentos em um ambiente hospedeiro | Scripts manipulando elementos no navegador ou tarefas no servidor |
| Tipagem dinâmica | O tipo de dado é associado ao valor em memória, não à variável | Uma mesma variável pode receber número e posteriormente string |
| Tipagem fraca | Realiza conversões implícitas automáticas entre tipos | Expressões como `'5' * 2` resultam no número `10` |
| Multiparadigma | Permite combinar estilos imperativos, funcionais e orientados a eventos | Callbacks para eventos no navegador, classes e composição |
| Protótipos | Objetos herdam comportamentos diretamente de outros objetos | Métodos de arrays herdados da cadeia `Array.prototype` |
| ASI | Inserção automática de ponto e vírgula pelo motor | Omissão de `;` interpretada pelas regras gramaticais da engine |

Por ser uma linguagem de **alto nível**, o JavaScript gerencia a memória automaticamente por meio de um coletor de lixo (*Garbage Collector*), liberando o desenvolvedor da alocação manual de ponteiros e descarte de recursos de hardware. Ao mesmo tempo, sua natureza **multiparadigma** trata funções como cidadãs de primeira classe (*first-class citizens*), permitindo armazená-las em variáveis, repassá-las como parâmetros (*callbacks*) e compor fluxos funcionais ou orientados a objetos. Essa capacidade viabiliza diretamente a **programação orientada a eventos** no navegador, na qual funções de callback são registradas para escutar e responder assincronamente a ações do usuário, como cliques em botões, digitação em formulários e respostas de requisições de rede.

No modelo de **herança baseada em protótipos**, os objetos conectam-se diretamente a outros objetos por meio de uma cadeia (*prototype chain*), da qual herdam métodos e propriedades nativas. Mesmo quando utilizamos a palavra-chave `class` no JavaScript moderno, a linguagem continua utilizando protótipos internamente como mecanismo de extensão.

Já o recurso de **ASI** (*Automatic Semicolon Insertion*) faz com que o analisador sintático insira pontos e vírgulas automaticamente em determinadas quebras de linha quando a instrução pode ser validada gramaticalmente. Embora viabilize estilos de código sem ponto e vírgula explícito, o ASI pode provocar retornos vazios acidentais em quebras de linha após a instrução `return`, tornando o uso de ferramentas de linting e formatação muito recomendado.

<Aside type="note" title="Ponto e vírgula: usar ou omitir?">
  A comunidade JavaScript divide-se entre dois estilos principais de escrita:
  - **Com ponto e vírgula explícito**: Adotado por padrões como Google, Airbnb e pela maioria dos projetos com TypeScript. Torna os limites de cada declaração evidentes e elimina ambiguidades em quebras de linha.
  - **Sem ponto e vírgula (StandardJS / No-Semi)**: Focado em código mais enxuto e visualmente limpo, confiando no ASI e em regras estritas de linters para evitar casos especiais (como linhas que começam com parênteses, colchetes ou crases).
  
  Ambos os estilos são amplamente utilizados. A melhor prática é garantir a **consistência em toda a base de código**, configurando formatadores automáticos como Biome ou Prettier.
</Aside>

A **tipagem dinâmica** é outra decisão central: as variáveis não possuem tipos estáticos fixos no momento da declaração, e o tipo é inferido e vinculado ao dado em tempo de execução:

```js title="Tipagem dinâmica"
let value = 10;
console.log(typeof value); // "number"

value = "10";
console.log(typeof value); // "string"
```

No exemplo acima:
- A variável `value` inicia guardando o número `10`, fazendo com que o operador `typeof` retorne `"number"`.
- Em seguida, a mesma variável recebe o texto `"10"`, e o `typeof` passa a retornar `"string"`.
- O motor de execução aceita essa transição sem lançar erros, demonstrando que o tipo pertence ao valor em memória e não à variável em si.

Em conjunto com a tipagem dinâmica, o JavaScript adota **tipagem fraca**, realizando conversões automáticas entre tipos distintos (*coerção implícita*) durante certas operações, em vez de interromper o programa com uma exceção:

```js title="Conversão automática"
console.log("5" * 2); // 10
console.log("5" + 2); // "52"
```

A diferença de resultado entre as duas operações decorre das regras específicas de cada operador:
- **Na multiplicação (`*`)**: O operador aritmético `*` opera exclusivamente sobre números. O motor converte a string `"5"` para o número `5` e executa a conta matemática `5 * 2`, resultando em `10`.
- **Na adição (`+`)**: O operador `+` possui sobrecarga na linguagem, atuando tanto para adição aritmética quanto para concatenação de strings. Quando um dos lados é texto, o JavaScript prioriza a concatenação, convertendo o número `2` para o texto `"2"` e gerando a string `"52"`.

Esses comportamentos fazem parte das decisões originais de design da linguagem. Para prevenir surpresas e comportamentos indesejados, é recomendada a prática de conversões explícitas e o uso de comparações estritas com `===`.

## Comentários em JavaScript

Comentários são anotações inseridas no código que o motor de execução ignora totalmente. Eles servem para documentar intenções, explicar regras de negócio ou desativar temporariamente instruções durante o desenvolvimento. A linguagem oferece três formatos para diferentes necessidades de documentação.

O **comentário de linha única** inicia com duas barras (`//`) e estende-se até o fim da linha, sendo ideal para notas curtas e diretas:

```js title="Comentário de linha única"
// Define a taxa de desconto para clientes VIP
const VIP_DISCOUNT = 0.15;

const total = 100; // Valor base da compra
```

O **comentário de múltiplas linhas** (ou comentário de bloco) inicia com `/*` e encerra em `*/`. É utilizado para explicações mais detalhadas ou para desativar blocos inteiros de código:

```js title="Comentário de bloco"
/*
  Cálculo de tributação para produtos importados.
  Considera a alíquota estadual (ICMS) e federal.
  Atualizado conforme a legislação vigente.
*/
function calculateTax(amount) {
  return amount * 0.20;
}
```

Os **comentários de documentação JSDoc** iniciam com `/**` e encerram com `*/`. O **JSDoc** é o padrão oficial de documentação da comunidade JavaScript. Ele permite descrever parâmetros (`@param`), tipos e valores de retorno (`@returns`), fornecendo autocompletar e auxílio visual inteligente no editor de código:

```js title="Documentação com JSDoc"
/**
 * Calcula o preço final aplicando desconto.
 *
 * @param {number} price Preço original do produto.
 * @param {number} discount Taxa de desconto de 0 a 1 (ex: 0.10 para 10%).
 * @returns {number} Valor final com o desconto aplicado.
 */
function applyDiscount(price, discount) {
  return price * (1 - discount);
}
```

<Aside type="tip" title="Boas Práticas de Comentários">
  - **Explique o PORQUÊ, não o O QUÊ**: Evite comentar o que o código já deixa óbvio (`let x = 10; // declara x como 10`). Explique o motivo ou o contexto por trás da decisão.
  - **Priorize Código Autoexplicativo**: Nomes claros para variáveis e funções reduzem drasticamente a necessidade de comentários informativos.
  - **Evite Código Morto**: Remova códigos velhos comentados antes de enviar o projeto para produção ou controle de versão (Git).
</Aside>

## Evolução da Linguagem

JavaScript continua evoluindo. O comitê TC39 organiza propostas de novas funcionalidades em estágios. Uma ideia começa imatura e precisa amadurecer até entrar oficialmente na especificação.

<Aside type="tip" title="Guia Completo de Versões do ECMAScript">
  Para uma visão aprofundada da evolução do JavaScript ano a ano, com exemplos práticos de código de todas as versões (do **ES6 / ES2015** até **ES2024 / ES2025**), consulte o nosso [Guia Completo de Versões do ECMAScript](../../evolution/tc39/).
</Aside>

O comitê TC39 estrutura o ciclo de vida e a maturação de cada proposta nos cinco estágios a seguir:

| Estágio | Ideia geral |
| ------- | ----------- |
| Stage 0 | Ideia inicial, ainda muito experimental |
| Stage 1 | Proposta com problema e direção discutidos |
| Stage 2 | Rascunho mais concreto da solução |
| Stage 3 | Candidato próximo de finalização |
| Stage 4 | Recurso finalizado, pronto para entrar na especificação |

Para acompanhar a evolução da linguagem, os links mais úteis são:

- [TC39 Proposals](https://github.com/tc39/proposals), com propostas ativas;
- [Finished Proposals](https://github.com/tc39/proposals/blob/main/finished-proposals.md),
  com recursos que chegaram ao Stage 4;
- [ECMA-262](https://ecma-international.org/publications-and-standards/standards/ecma-262/),
  com a edição anual oficial da especificação;
- [ECMAScript draft](https://tc39.es/ecma262/), com o rascunho vivo da próxima
  edição.

Na tabela abaixo, "liberado" significa que o recurso entrou em uma edição anual do
ECMAScript. A disponibilidade em navegadores, Node.js, Deno ou Bun pode variar de
acordo com a versão do ambiente.

| Edição | Exemplos importantes | Por que marcou a linguagem |
| ------ | -------------------- | -------------------------- |
| ES2015 | `let`, `const`, arrow functions, classes, modules, promises | Modernizou a sintaxe e consolidou a base do JavaScript usado hoje |
| ES2017 | `async`/`await` | Tornou código assíncrono mais parecido com código sequencial |
| ES2020 | optional chaining (`?.`), nullish coalescing (`??`), `BigInt` | Reduziu verificações repetitivas de `null`/`undefined` e adicionou inteiros grandes |
| ES2021 | logical assignment (`&&=`, `\|\|=`, `??=`), `String.prototype.replaceAll()` | Melhorou atribuições condicionais e manipulação de strings |
| ES2022 | class fields, private fields (`#name`), top-level `await` | Fortaleceu a sintaxe de classes e simplificou módulos assíncronos |
| ES2023 | `Array.prototype.findLast()`, `findLastIndex()`, `toSorted()`, `toReversed()` | Adicionou métodos úteis para arrays, incluindo operações que não alteram o array original |
| ES2024 | `Object.groupBy()`, `Map.groupBy()`, `Promise.withResolvers()` | Trouxe APIs para agrupamento de dados e criação mais direta de promises |

<Aside type="caution" title="Nem toda novidade deve ser usada imediatamente">
  Uma feature pode aparecer em artigos, navegadores ou ferramentas antes de estar
  amplamente disponível. Em projetos reais, confira suporte no ambiente alvo,
  documentação e necessidade de transpilação antes de depender de recursos recentes.
</Aside>

    4. **Modo Interativo (Node.js REPL)**

       Você também pode testar trechos de código em tempo real abrindo o ambiente interativo (REPL) ao digitar `node` sem argumentos. No REPL, o caractere `>` indica o prompt interativo:

       ```js title="Node.js REPL"
       $ node
       Welcome to Node.js v24.19.0.
       Type ".help" for more information.
       > const name = "DevLab";
       undefined
       > `Olá, ${name}!`;
       'Olá, DevLab!'
       > 5 + 3 * 2;
       11
       > .exit
       ```

    </Steps>

    <Aside type="note" title="Node.js, npm, npx e nvm">
      Para a maioria dos projetos de aula e produção, prefira a versão LTS indicada
      no site oficial do Node.js. Versões Current trazem novidades antes, mas podem
      ser menos adequadas para projetos que precisam de estabilidade.

      O `npm` e o `npx` costumam acompanhar a instalação do Node.js e serão usados
      para instalar dependências e executar ferramentas do projeto.

      Para gerenciar e alternar facilmente entre múltiplas versões do Node.js no mesmo sistema (por exemplo, alternar entre a versão 20 e 24), utiliza-se o [nvm](https://github.com/nvm-sh/nvm) (*Node Version Manager*). Com comandos como `nvm install 24`, `nvm use 24` e `nvm ls`, é possível alterar a versão ativa do Node.js no terminal sem desinstalar versões anteriores.
    </Aside>

  </TabItem>

  <TabItem label="Deno">

    [Deno](https://deno.com/) é um runtime moderno para JavaScript, TypeScript e
    WebAssembly. Ele tem TypeScript integrado, permissões de segurança por padrão e
    compatibilidade crescente com projetos do ecossistema Node.js.

    <Steps>

    1. **Verifique a versão instalada**

       ```bash title="Terminal"
       deno --version
       ```

       ```text title="Saída"
       deno 2.9.5
       v8 ...
       typescript ...
       ```

    2. **Crie um arquivo JavaScript**

       ```js title="main.js"
       console.log("Olá, Deno");
       ```

    3. **Execute o arquivo pelo terminal**

       ```bash title="Terminal"
       deno run main.js
       ```

       ```text title="Saída"
       Olá, Deno
       ```

    4. **Teste TypeScript quando fizer sentido**

       O comando `deno run` também aceita arquivos TypeScript diretamente:

       ```bash title="Terminal"
       deno run main.ts
       ```

    </Steps>

  </TabItem>

  <TabItem label="Bun">

    [Bun](https://bun.com/) é um runtime e toolkit para JavaScript e TypeScript. Ele
    inclui runtime, gerenciador de pacotes, test runner e bundler em uma única
    ferramenta.

    <Steps>

    1. **Verifique a versão instalada**

       ```bash title="Terminal"

       ```

       ```text title="Saída"
       1.4.0
       ```

    2. **Crie um arquivo JavaScript**


    3. **Execute o arquivo pelo terminal**

       ```bash title="Terminal"
       bun run main.js
       ```

       ```text title="Saída"
       Olá, Bun
       ```

    4. **Use o atalho quando preferir**

       Também é possível executar sem a palavra `run`:

       ```bash title="Terminal"
       bun main.js
       ```

    </Steps>

  </TabItem>
</Tabs>

### Arquivo carregado pelo navegador

Nesse cenário, o JavaScript é carregado por uma página HTML. O output de
`console.log()` não aparece no corpo da página; ele aparece no Console do DevTools.

<Steps>

1. **Crie a página HTML**

   Use a tag `script` para carregar o arquivo JavaScript.

   ```html title="index.html"
   <script src="main.js"></script>
   ```

2. **Crie o arquivo JavaScript**

   ```js title="main.js"
   console.log("Olá, página");
   ```

3. **Abra a página no navegador**

   Abra o arquivo `index.html` no navegador ou sirva a pasta com um servidor local.
   O navegador carregará `main.js` junto com a página.

4. **Veja o output**

   Abra o DevTools, entre na aba Console e observe a saída:

   ```text title="Console"
   Olá, página
   ```

</Steps>

## Navegador, Node.js e npm

Quando usamos JavaScript no navegador, o arquivo normalmente faz parte de uma página
Web. Quando usamos JavaScript no Node.js, o arquivo é executado como programa no
sistema operacional.

| Ambiente | Como executar | Uso comum |
| -------- | ------------- | --------- |
| Navegador | `<script>`, Console, DevTools | interagir com HTML, CSS, eventos, DOM e APIs Web |
| Node.js | `node arquivo.js` | criar scripts, servidores, APIs e automações |
| npm | `npm install`, `npm run`, `npx` | instalar pacotes e executar tarefas do projeto |

O `npm` será importante porque muitos projetos Web dependem de pacotes. Vite,
Bootstrap, Tailwind, Express, Prisma e várias ferramentas de teste ou build entram
no projeto por meio do ecossistema npm.

Mas o ecossistema JavaScript não depende apenas do `npm`. Existem outros gerenciadores
de pacotes, runtimes e registros de pacotes que podem aparecer em projetos modernos.
Eles não têm exatamente o mesmo papel, então vale separar o que cada um resolve.

| Ferramenta | Tipo | Uso comum |
| ---------- | ---- | --------- |
| [pnpm](https://pnpm.io/) | Gerenciador de pacotes | Alternativa ao npm com foco em velocidade, economia de disco e monorepos |
| [Yarn](https://yarnpkg.com/) | Gerenciador de pacotes | Alternativa ao npm com foco em projetos reproduzíveis e organização de dependências |
| [Bun](https://bun.com/) | Runtime e toolkit | Executar JavaScript/TypeScript, instalar pacotes, rodar testes e empacotar projetos |
| [Deno](https://deno.com/) | Runtime e toolkit | Executar JavaScript/TypeScript com permissões de segurança, ferramentas integradas e suporte moderno a módulos |
| [JSR](https://jsr.io/) | Registro de pacotes | Registro moderno para JavaScript e TypeScript, com foco em ESM e TypeScript |

## Exercício

Execute os três testes abaixo e observe onde cada um funciona:

1. No console do navegador:

   ```js
   console.log(document.title);
   ```

2. Em um arquivo `main.js` executado com Node.js:

   ```js
   console.log(process.version);
   ```

3. Nos dois ambientes:

   ```js
   const message = "JavaScript";
   console.log(message.toUpperCase());
   ```

Depois, responda: quais comandos pertencem à linguagem e quais dependem do ambiente
de execução?

## Perguntas de revisão

**1. Qual é a diferença entre JavaScript e ECMAScript?**

<details>
  <summary>Possível resposta</summary>

  ECMAScript é a especificação padronizada da linguagem. JavaScript é o nome comum
  da linguagem usada pelos desenvolvedores e implementada em navegadores, Node.js e
  outros ambientes.
</details>

**2. Por que JavaScript se tornou tão importante na Web?**

<details>
  <summary>Possível resposta</summary>

  Porque os navegadores passaram a executar JavaScript para adicionar comportamento
  às páginas, como responder a eventos, manipular o DOM, validar formulários e
  consumir APIs.
</details>

**3. O que são Web APIs?**

<details>
  <summary>Possível resposta</summary>

  São recursos fornecidos pelo navegador, como DOM, eventos, `fetch`, `localStorage`
  e timers. Elas são usadas por JavaScript, mas não fazem parte do núcleo da
  linguagem ECMAScript.
</details>

**4. Por que `document` funciona no navegador e não em um script Node comum?**

<details>
  <summary>Possível resposta</summary>

  Porque `document` é uma API do navegador para representar a página carregada. Em
  um script Node comum não existe uma página HTML sendo renderizada.
</details>

**5. Para que serve Node.js?**

<details>
  <summary>Possível resposta</summary>

  Node.js permite executar JavaScript fora do navegador, por exemplo para criar
  scripts, servidores HTTP, APIs, ferramentas de build e automações.
</details>

**6. Qual é o papel do npm?**

<details>
  <summary>Possível resposta</summary>

  npm é o ecossistema usado para instalar pacotes, gerenciar dependências e executar
  scripts do projeto, como comandos de desenvolvimento, build e testes.
</details>

**7. O que significa dizer que JavaScript tem tipagem dinâmica?**

<details>
  <summary>Possível resposta</summary>

  Significa que o tipo está associado ao valor em tempo de execução. Uma mesma
  variável pode receber valores de tipos diferentes ao longo do programa.
</details>

**8. Por que comparações estritas, como `===`, são preferíveis em muitos casos?**

<details>
  <summary>Possível resposta</summary>

  Porque evitam conversões automáticas inesperadas durante a comparação, tornando o
  comportamento do código mais previsível.
</details>

**9. O que o TC39 faz?**

<details>
  <summary>Possível resposta</summary>

  TC39 é o comitê responsável por evoluir a especificação ECMAScript, discutindo,
  avaliando e amadurecendo propostas de novas funcionalidades da linguagem.
</details>

**10. Por que a especificação ECMAScript não costuma ser o melhor material inicial para aprender a programar?**

<details>
  <summary>Possível resposta</summary>

  Porque ela é escrita para definir regras precisas de implementação da linguagem.
  Para aprender a escrever scripts, materiais como guias e referências da MDN são
  mais didáticos.
</details>
