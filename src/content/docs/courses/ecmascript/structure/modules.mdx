Este tópico apresenta os **Módulos** em JavaScript: como dividir uma aplicação em arquivos isolados, tornar públicos apenas os valores desejados e consumir tanto código do próprio projeto quanto pacotes instalados pelo npm.

Materiais: [slides do tópico](../../../../slides/courses/ecmascript/structure/modules/) e
[mapa mental](../../../../mindmaps/courses/ecmascript/structure/modules/)

## Objetivo

Dominar a modularização de aplicações JavaScript, do arquivo isolado até o consumo de pacotes da comunidade. Ao final do tópico, o leitor deve ser capaz de:

- Explicar por que cada arquivo tem escopo privado e o que um sistema de módulos resolve.
- Diferenciar o sistema legado **CommonJS** (`require`/`module.exports`) do padrão **ES Modules** (`import`/`export`).
- Escolher entre exportação nomeada e *default*, aplicando *aliases* com `as`.
- Usar *namespace imports* (`import * as`) e *dynamic imports* (`await import()`) quando o cenário pedir.
- Reconhecer a avaliação única dos módulos e o comportamento dos vínculos vivos (*live bindings*).
- Configurar o Node.js para ESM, distinguir especificadores relativos de pacotes npm e interpretar as versões do **SemVer**.

## O que acontece sem módulos?

Enquanto todo o código cabe em um arquivo só, nada disso é necessário. O projeto inteiro é um arquivo:

<FileTree>
{`
  function-sum/
  └── index.js    declara e usa a função sum
`}
</FileTree>

Dentro desse arquivo, a função declarada no topo está visível para todo o restante do código:

<SourceCode path="examples/courses/ecmascript/modules/function-sum/index.js" title="function-sum/index.js" />

O problema aparece quando o projeto cresce e esse mesmo código é dividido em dois arquivos, cada um com sua responsabilidade:

<FileTree>
{`
  no-module/
  ├── lib.js     declara a função sum
  └── main.js    tenta chamar a função sum
`}
</FileTree>

A biblioteca passa a declarar apenas a função:

<SourceCode path="examples/courses/ecmascript/modules/no-module/lib.js" title="no-module/lib.js" />

O arquivo principal a utiliza como se ela ainda estivesse no mesmo arquivo:

<SourceCode path="examples/courses/ecmascript/modules/no-module/main.js" title="no-module/main.js" />

Ao executar o arquivo principal com o Node.js, o código falha com um erro de referência:

```bash title="Terminal"
node main.js
```

```txt title="Output"
ReferenceError: sum is not defined
    at Object.<anonymous> (main.js:1:13)
```

Como cada arquivo possui um escopo privado e isolado, a função `sum` declarada em `lib.js` **não é visível** no arquivo `main.js`. Um sistema de módulos é justamente o mecanismo que constrói a ponte entre os dois escopos, de forma explícita.

O diagrama a seguir contrasta as duas situações, o arquivo isolado e o arquivo conectado por `export`/`import`:

<Mermaid title="Escopos isolados antes e depois de um sistema de módulos">
{`
flowchart TD
  subgraph Isolado["Sem módulos"]
    A["lib.js<br/>function sum(a, b)"]
    B["main.js<br/>sum(2, 1)"]
    A -. "sum não é visível" .-> B
  end

  Isolado -- "declarar export e import" --> Modular

  subgraph Modular["Com ES Modules"]
    C["lib.js<br/>export function sum(a, b)"]
    D["main.js<br/>import { sum }<br/>from './lib.js'"]
    C -- "vínculo explícito" --> D
  end
`}
</Mermaid>

## Sistemas de módulos em JavaScript

Historicamente, JavaScript não possuía um sistema oficial de módulos. Para resolver isso no
desenvolvimento de aplicações no servidor com Node.js, surgiram padrões como o **CommonJS**.
A partir do ES6 (ES2015), o ecossistema padronizou o **ES Modules (ESM)**.

Os dois sistemas convivem até hoje no Node.js, e a tabela a seguir resume as diferenças que
mais aparecem no dia a dia:

| Característica | CommonJS (CJS) | ES Modules (ESM) |
| :--- | :--- | :--- |
| **Origem** | Convenção criada pelo Node.js | Padrão oficial do ECMAScript (ES6) |
| **Exportação** | `module.exports = valor` | `export` e `export default` |
| **Importação** | `require('./lib.js')` | `import ... from './lib.js'` |
| **Carregamento** | Síncrono, em tempo de execução | Estático, analisado antes da execução |
| **Onde roda** | Node.js | Node.js e navegadores |
| **Configuração** | Padrão do Node.js sem `"type"` | Exige `"type": "module"` no `package.json` |

## CommonJS (CJS)

No estilo CommonJS, a exportação é feita atribuindo valores ao objeto `module.exports`,
e a importação é realizada através da função `require()`.

O primeiro exemplo tem os dois arquivos de código e o `package.json` que mantém a pasta no modo
CommonJS:

<FileTree>
{`
  cjs-default/
  ├── lib.js          exporta uma única função
  ├── main.js         consome a função exportada
  └── package.json    marca a pasta como CommonJS
`}
</FileTree>

Para exportar um único valor principal (o equivalente ao *default export*), basta atribuir a
própria função ao `module.exports`:

Como `require()` devolve exatamente o valor que foi atribuído, o nome local no arquivo que
importa é livre:

<SourceCode path="examples/courses/ecmascript/modules/cjs-default/main.js" title="cjs-default/main.js" />

O segundo exemplo repete essa estrutura, agora com uma biblioteca que expõe quatro operações:

<FileTree>
{`
  cjs-named/
  ├── lib.js          exporta quatro funções dentro de um objeto
  ├── main.js         importa com desestruturação
  └── package.json    marca a pasta como CommonJS
`}
</FileTree>

Para expor vários valores de uma vez, atribui-se um objeto ao `module.exports`. Repare que a
forma de declarar cada função (declaração, expressão ou *arrow*) não interfere na exportação:

<SourceCode path="examples/courses/ecmascript/modules/cjs-named/lib.js" title="cjs-named/lib.js" />

Do outro lado, a desestruturação do objeto devolvido por `require()` extrai apenas os membros
que interessam:

<SourceCode path="examples/courses/ecmascript/modules/cjs-named/main.js" title="cjs-named/main.js" />

<Aside type="note" title="CommonJS é o padrão legado do Node.js">
  O CommonJS era o padrão exclusivo do Node.js em suas primeiras versões. Embora ainda
  seja amplamente encontrado em projetos antigos e em bibliotecas legadas, a especificação
  oficial recomendada para projetos modernos no navegador e no Node.js é o **ES Modules (ESM)**.
</Aside>

## Exports e imports nomeados

Com o **ES Modules (ESM)**, um módulo pode conter quantas exportações nomeadas (*named exports*)
forem necessárias. Cada exportação deve possuir um nome único dentro do arquivo.

A pasta do exemplo é a mesma do caso anterior em CommonJS, trocando apenas o modo declarado no
`package.json`:

<FileTree>
{`
  esm-named/
  ├── lib.js          exporta quatro funções nomeadas
  ├── main.js         importa entre chaves e cria um alias
  └── package.json    marca a pasta como ES Modules
`}
</FileTree>

A palavra-chave `export` funciona como um prefixo aplicado à declaração, seja ela uma função,
uma expressão de função ou uma *arrow function*:

<SourceCode path="examples/courses/ecmascript/modules/esm-named/lib.js" title="esm-named/lib.js" />

Na importação, os membros desejados são extraídos entre chaves `{ ... }` e os nomes precisam
coincidir com os exportados. Quando é preciso evitar conflitos ou deixar a intenção mais clara,
a palavra-chave `as` cria um *alias* local:

<SourceCode path="examples/courses/ecmascript/modules/esm-named/main.js" title="esm-named/main.js" />

Por serem analisadas antes da execução, as importações nomeadas permitem que a linguagem
detecte nomes duplicados ou inexistentes já na leitura do arquivo:

```js title="Erros em exportações e importações nomeadas"
// SyntaxError: Identifier 'sum' has already been declared.
// export function sum(a, b) { return a + b; }
// export function sum(a, b) { return a + b; }

// SyntaxError: The requested module './lib.js' does not provide an export named 'add'.
// import { add } from './lib.js';
```

## Export e import default

O *export default* é usado para definir o valor principal de um módulo (por exemplo, a
instância de uma aplicação Express ou uma classe principal). Cada módulo pode ter no máximo
**um** `export default`.

O exemplo desta seção mantém a estrutura de dois arquivos:

<FileTree>
{`
  esm-default/
  ├── lib.js          exporta uma função como valor principal
  ├── main.js         importa o default com dois nomes diferentes
  └── package.json    marca a pasta como ES Modules
`}
</FileTree>

O módulo abaixo declara a função normalmente e a elege como valor principal na última linha:

<SourceCode path="examples/courses/ecmascript/modules/esm-default/lib.js" title="esm-default/lib.js" />

Ao importar um *export default*, **não** são utilizadas chaves `{}` e o nome da variável
local é livre, como mostram as duas importações do mesmo arquivo:

<SourceCode path="examples/courses/ecmascript/modules/esm-default/main.js" title="esm-default/main.js" />

As duas formas de exportação convivem no mesmo arquivo, como mostra a próxima pasta de exemplo:

<FileTree>
{`
  esm-default-named/
  ├── lib.js          combina exportações nomeadas e um export default
  ├── main.js         importa o default e um nomeado na mesma instrução
  └── package.json    marca a pasta como ES Modules
`}
</FileTree>

É comum expor funções nomeadas e, ao mesmo tempo, um objeto principal que agrupa todas elas:

<SourceCode path="examples/courses/ecmascript/modules/esm-default-named/lib.js" title="esm-default-named/lib.js" />

Nesse caso, uma única instrução de importação traz o *default* e os membros nomeados, com o
valor principal sempre antes das chaves:

<SourceCode path="examples/courses/ecmascript/modules/esm-default-named/main.js" title="esm-default-named/main.js" />

A tabela a seguir resume as diferenças entre as duas formas de exportar em ESM:

| Característica | Named export | Default export |
| :--- | :--- | :--- |
| **Quantidade por arquivo** | Vários, com nomes únicos | No máximo um |
| **Sintaxe de exportação** | `export const sum = ...` | `export default sum` |
| **Sintaxe de importação** | `import { sum } from './lib.js'` | `import qualquerNome from './lib.js'` |
| **Nome local** | Igual ao exportado, ou com `as` | Livre |
| **Uso típico** | Utilitários e coleções de funções | Valor principal do módulo |

<Aside type="caution" title="Erros comuns no export default">
  Tentar definir dois `export default` no mesmo arquivo resulta em erro de sintaxe.
  Além disso, tentar importar um *export default* usando chaves `{ sum }` fará o JavaScript
  procurar por uma exportação nomeada chamada `sum`, falhando caso ela não exista.
</Aside>

O trecho comentado a seguir registra as mensagens produzidas em cada um desses dois casos:

```js title="Erros em export default"
// SyntaxError: Identifier '.default' has already been declared.
// export default function sum(a, b) { return a + b; }
// export default function subtract(a, b) { return a - b; }

// SyntaxError: The requested module './lib.js' does not provide an export named 'sum'.
// import { sum } from './lib.js'; (quando lib.js só possui export default)
```

## Import de namespace (`import * as`)

Quando um módulo expõe diversas exportações nomeadas (e opcionalmente um *export default*),
podemos importar todo o módulo como um único objeto de *namespace* utilizando `import * as Alias`.

A pasta de exemplo segue o mesmo formato das anteriores:

<FileTree>
{`
  esm-namespace/
  ├── lib.js          exporta uma constante, uma função e um default
  ├── main.js         importa o módulo inteiro com import * as
  └── package.json    marca a pasta como ES Modules
`}
</FileTree>

O módulo combina uma constante, uma função nomeada e um valor principal:

<SourceCode path="examples/courses/ecmascript/modules/esm-namespace/lib.js" title="esm-namespace/lib.js" />

No arquivo que importa, todas as exportações passam a ser propriedades de um mesmo objeto, e o
*export default* fica acessível pela chave `default`:

<SourceCode path="examples/courses/ecmascript/modules/esm-namespace/main.js" title="esm-namespace/main.js" />

<Aside type="caution" title="Objetos de namespace são somente leitura">
  O objeto retornado por `import * as` é **imutável (read-only)**. Qualquer tentativa
  de reatribuir ou alterar uma propriedade do objeto de namespace lançará um `TypeError`.
</Aside>

O trecho comentado a seguir mostra a mensagem devolvida ao tentar sobrescrever uma dessas
propriedades:

```js title="Mutação de namespace é bloqueada"
// TypeError: Cannot assign to read only property 'PI' of object '[object Module]'.
// Lib.PI = 3;
```

## Imports dinâmicos (`import()`)

Instruções `import` estáticas devem ser colocadas no nível superior (*top-level*) do arquivo,
porque são analisadas antes da execução do código. Quando o módulo só precisa ser carregado sob
demanda, condicionalmente ou dentro de uma função, entra em cena a função de **import dinâmico**
`import()`, que devolve uma `Promise`.

A diferença deste exemplo não está na estrutura de arquivos, que continua a mesma, e sim no
momento em que um deles é carregado:

<FileTree>
{`
  esm-dynamic/
  ├── lib.js          módulo carregado apenas quando necessário
  ├── main.js         chama await import() dentro de um if
  └── package.json    marca a pasta como ES Modules
`}
</FileTree>

O módulo carregado sob demanda não tem nada de especial, é um ESM comum:

<SourceCode path="examples/courses/ecmascript/modules/esm-dynamic/lib.js" title="esm-dynamic/lib.js" />

A diferença está em quem importa: a chamada acontece dentro do `if`, momento em que a condição
já foi avaliada:

<SourceCode path="examples/courses/ecmascript/modules/esm-dynamic/main.js" title="esm-dynamic/main.js" />

<Aside type="tip" title="Desestruturando import() dinâmico">
  A chamada `await import('./lib.js')` resolve para um objeto de namespace. Para desestruturar
  o *export default*, renomeie a chave `default` (por exemplo: `{ default: MathLib }`), já que
  `default` é uma palavra reservada da linguagem.
</Aside>

Escrever a mesma condição com um `import` estático não é possível, como registra o trecho
comentado a seguir:

```js title="Import estático dentro de um bloco"
// SyntaxError: import declarations may only appear at top level of a module.
// if (needsCalculation) {
//   import { sum } from './lib.js';
// }
```

## Avaliação única e vínculos vivos (Live Bindings)

Dois comportamentos fundamentais caracterizam a execução dos ES Modules e explicam por que um
módulo pode guardar estado compartilhado por toda a aplicação.

### Avaliação única (*Singleton Evaluation*)

Um módulo é executado **apenas uma única vez**, na primeira oportunidade em que é importado. Se
vários arquivos da aplicação importarem o mesmo módulo, o código do topo roda somente na
primeira vez e o resultado fica em cache para todas as importações seguintes.

O exemplo desta seção usa dois arquivos, o módulo que guarda o estado e o arquivo que o consome:

<FileTree>
{`
  esm-live-bindings/
  ├── counter.js      exporta a variável count e a função increment
  ├── main.js         importa o módulo duas vezes
  └── package.json    marca a pasta como ES Modules
`}
</FileTree>

O módulo a seguir imprime uma mensagem no topo justamente para tornar esse momento visível:

<SourceCode path="examples/courses/ecmascript/modules/esm-live-bindings/counter.js" title="esm-live-bindings/counter.js" />

Como a variável `count` vive no escopo do módulo e não é recriada a cada importação, ela se
comporta como um estado único compartilhado por todos os arquivos que a importam.

### Vínculos vivos (*Live Bindings*)

As exportações em ESM não são cópias dos valores, mas **vínculos vivos (live bindings)**. Quando
o módulo de origem altera o valor de uma variável exportada através de uma função interna, todos
os módulos que a importaram observam o novo valor imediatamente.

O arquivo abaixo importa `count` duas vezes, chama `increment()` e lê novamente as duas
referências:

<SourceCode path="examples/courses/ecmascript/modules/esm-live-bindings/main.js" title="esm-live-bindings/main.js" />

A execução confirma tanto a avaliação única (a mensagem do módulo aparece uma só vez, apesar das
duas importações) quanto o vínculo vivo:

```bash title="Terminal"
node main.js
```

```txt title="Output"
Modulo counter.js executado
0
1
1
```

O caminho inverso, porém, é bloqueado: o arquivo que importa o valor **não pode reatribuí-lo**,
já que variáveis importadas se comportam como constantes (*read-only bindings*).

```js title="Reatribuir uma importação é bloqueado"
// TypeError: Assignment to constant variable.
// count = 10;
```

## Resolução de módulos e regras no Node.js

Para utilizar o ES Modules com sucesso no Node.js, é fundamental configurar o projeto e entender as regras de resolução de arquivos locais e pacotes da comunidade npm.

### Configuração do package.json

Para avisar ao Node.js que os arquivos `.js` do seu projeto devem ser interpretados como
**ES Modules** (e não como o CommonJS legado), inclua `"type": "module"` no `package.json` do projeto:

```json title="package.json" {4}
{
  "name": "meu-projeto",
  "private": true,
  "type": "module"
}
```

### Obrigatoriedade da extensão em ESM

Ao contrário do CommonJS clássico, a especificação do ES Modules no Node.js exige que a
**extensão do arquivo (ex: `.js`)** seja fornecida explicitamente em especificadores relativos:

```js title="Omitir extensão em ESM causa erro"
// Error [ERR_MODULE_NOT_FOUND]: Cannot find module './lib'.
// import MathLib from './lib';

import MathLib from './lib.js'; // Correto
```

### Especificadores relativos vs. pacotes npm

Ao importar um módulo no Node.js, o formato do caminho especificado indica a estratégia de resolução que será utilizada:

- **Especificador relativo**: Começa obrigatoriamente com `./` ou `../` e indica o caminho para um arquivo local do projeto.
- **Especificador de pacote**: Não possui `./` ou `../`. O Node.js busca a biblioteca dentro da pasta `node_modules`.

O diagrama a seguir mostra a decisão que o Node.js toma a partir do texto do especificador:

<Mermaid title="Resolução de um especificador de import no Node.js">
{`

  B -- "sim" --> C["Especificador relativo:<br/>arquivo do próprio projeto"]
  C --> D["Extensão obrigatória<br/>./lib.js"]
  B -- "não" --> E["Especificador de pacote:<br/>biblioteca instalada"]
  E --> F["Procura em node_modules,<br/>subindo os diretórios"]
`}
</Mermaid>

  ├── lib.js          biblioteca local do projeto

</FileTree>

O arquivo principal combina os dois casos, importando a biblioteca local e o pacote `mathjs`:

Para utilizar pacotes da comunidade como `mathjs`, é necessário instalá-los através de um gerenciador de pacotes. O **npm** é o gerenciador padrão que acompanha o Node.js, mas também é muito comum utilizar alternativas como o **pnpm** (que otimiza o uso de espaço em disco e o tempo de instalação através de *hard links*) ou o **Yarn**.

```json title="package.json (antes da instalação)"

  "type": "module"

```


### Versionamento semântico (SemVer)

Ao instalar um pacote, o npm especifica sua versão no `package.json` utilizando o padrão **Semantic Versioning (SemVer)**. Uma versão no formato `MAJOR.MINOR.PATCH` (ex: `11.7.0`) é dividida em três números:

- **MAJOR (`11`)**: Mudanças incompatíveis que podem quebrar o código existente (*breaking changes*).
- **MINOR (`7`)**: Adição de novas funcionalidades mantendo a compatibilidade retroativa.
- **PATCH (`0`)**: Correção de *bugs* mantendo a compatibilidade retroativa.

Os prefixos antes da versão indicam as regras de atualização automática aceitas pelo projeto:

| Prefixo | Exemplo | Descrição de atualização |
| :--- | :--- | :--- |
| `^` (caret) | `"^11.7.0"` | Permite atualizações **MINOR** e **PATCH** (ex: `< 12.0.0`). É o padrão do npm. |
| `~` (tilde) | `"~11.7.0"` | Permite apenas atualizações de **PATCH** (ex: `< 11.8.0`). |
| Nenhum | `"11.7.0"` | Trava a dependência na versão **exata** especificada. |

Além de modificar o `package.json`, a instalação realiza outras duas ações essenciais:

1. **Arquivo de trava (`package-lock.json`, `pnpm-lock.yaml` ou `yarn.lock`)**: Registra as versões exatas de toda a árvore de dependências para garantir instalações idênticas em diferentes ambientes.
2. **`node_modules/`**: Cria a pasta onde o Node.js armazena o código-fonte do pacote baixado e de suas subdependências.

Comparada com a árvore mostrada antes da instalação, a mesma pasta ganha duas entradas, ambas destacadas abaixo:

<FileTree>
{`
  esm-npm/
  ├── .gitignore              mantém node_modules fora do Git
  ├── **node_modules/**       código do mathjs e de suas subdependências
  ├── lib.js
  ├── main.js
  ├── **package-lock.json**   versões exatas de toda a árvore
  └── package.json            agora com a seção dependencies
`}
</FileTree>

<Aside type="caution" title="Adicione node_modules no .gitignore">
  A pasta `node_modules/` pode ter um tamanho considerável e **nunca** deve ser enviada para o controle de versão (Git). Inclua `node_modules/` no seu arquivo `.gitignore`:

  ```txt title=".gitignore"
  node_modules/
  ```

  Para regenerar a pasta `node_modules/` em um repositório clonado ou em um servidor de produção, basta executar o comando de instalação (`npm install`, `pnpm install` ou `yarn install`) no terminal. O gerenciador utilizará o `package.json` e o arquivo de trava para baixar novamente todas as dependências do projeto.
</Aside>

## Resumo e Boas Práticas

Esta seção consolida as decisões práticas do tópico. Use-a como referência rápida para escolher o sistema de módulos, a forma de exportação e a configuração do projeto.

### Escolha do sistema de módulos

Projetos novos nascem em ESM; o CommonJS aparece quando é preciso manter código legado.

- Adote **ES Modules** em qualquer projeto novo, no servidor ou no navegador, declarando `"type": "module"` no `package.json`.
- Reserve **CommonJS** para manutenção de projetos antigos e para bibliotecas que ainda não publicaram uma versão ESM.
- Não misture os dois sistemas no mesmo arquivo: `require()` não existe dentro de um módulo ES.

A tabela a seguir resume, lado a lado, a sintaxe equivalente nos dois sistemas:

| Cenário | CommonJS | ES Modules |
| :--- | :--- | :--- |
| **Uma função** | `module.exports = sum` / `const sum = require('./lib.js')` | `export default sum` / `import sum from './lib.js'` |
| **Várias funções** | `module.exports = { sum, subtract }` / `const { sum } = require('./lib.js')` | `export { sum, subtract }` / `import { sum } from './lib.js'` |
| **Módulo inteiro** | `const Lib = require('./lib.js')` | `import * as Lib from './lib.js'` |

### Exportações e importações

Deixe explícito o que é público e mantenha o restante do arquivo privado.

- Prefira *named exports* para conjuntos de utilitários: eles permitem verificação estática de nomes e importações seletivas.
- Reserve o *export default* para o valor principal do módulo, e nunca declare mais de um por arquivo.
- Use `as` para resolver conflitos de nomes em vez de renomear a exportação de origem.
- Recorra a `await import()` apenas quando o carregamento precisar ser condicional ou adiado; o `import` estático continua sendo o padrão.

### Configuração e dependências

Trate o `package.json` e o arquivo de trava como parte do código do projeto.

- Sempre informe a extensão do arquivo (`./lib.js`) em especificadores relativos no Node.js.
- Versione o `package.json` e o arquivo de trava, e mantenha `node_modules/` no `.gitignore`.
- Entenda o prefixo da versão antes de atualizar dependências: `^` libera MINOR e PATCH, `~` libera apenas PATCH e a versão sem prefixo trava a dependência.

## Exercício

Crie uma estrutura modular para gerenciar um catálogo de produtos:

1. Crie um arquivo `product-service.js` contendo um array privado de produtos e exporte:
   - Uma função nomeada `findAll()` que retorne todos os produtos;
   - Uma função nomeada `findById(id)` que busque um produto pelo ID;
   - Um *export default* contendo um objeto com as duas funções;
2. Crie um arquivo `index.js` que importe o serviço e exiba a lista completa e uma busca por ID;
3. Teste a execução com `node index.js`.

<details>
  <summary>Possível resposta</summary>

  ```js title="product-service.js"
  const products = [
    { id: 1, name: "Teclado", price: 150 },
    { id: 2, name: "Mouse", price: 80 },
  ];

  export function findAll() {
    return products;
  }

  export function findById(id) {
    return products.find((product) => product.id === id);
  }

  export default {
    findAll,
    findById,
  };
  ```

  ```js title="index.js"
  import productService, { findById } from './product-service.js';

  console.log(productService.findAll());
  console.log(findById(2));
  ```
</details>

## Desafio

Crie uma aplicação com carregamento condicional e dinâmico de módulos:

1. Crie o módulo `advanced-math.js` exportando funções para `power(base, exp)` e `squareRoot(val)`;
2. No arquivo `main.js`, declare uma constante `enableAdvancedMath = true`;
3. Se a constante for verdadeira, utilize `await import('./advanced-math.js')` para carregar o módulo sob demanda e calcular `power(2, 8)`;
4. Demonstre a desestruturação do import dinâmico obtendo a função `power`.

<details>
  <summary>Possível resposta</summary>

  ```js title="advanced-math.js"
  export function power(base, exp) {
    return base ** exp;
  }

  export function squareRoot(val) {
    return Math.sqrt(val);
  }

  export default {
    power,
    squareRoot,
  };
  ```

  ```js title="main.js"
  const enableAdvancedMath = true;

  if (enableAdvancedMath) {
    const { power, squareRoot } = await import('./advanced-math.js');

    console.log(power(2, 8)); // 256
    console.log(squareRoot(16)); // 4
  }
  ```
</details>

## Perguntas de revisão

### CommonJS vs ES Modules

**1. Qual é a principal diferença de sintaxe e carregamento entre CommonJS e ES Modules?**

<details>
  <summary>Possível resposta</summary>

  CommonJS utiliza `require()` e `module.exports` com carregamento síncrono em tempo de execução. ES Modules utiliza `import` e `export` com carregamento estático e assíncrono padronizado pela linguagem.
</details>

**2. O que acontece ao omitir a extensão `.js` ao importar um arquivo relativo em ESM no Node.js?**

<details>
  <summary>Possível resposta</summary>

  O Node.js lança um erro `ERR_MODULE_NOT_FOUND`, pois em ESM especificadores relativos exigem a extensão completa do arquivo.
</details>

### Named e Default Exports

**3. Quantos *named exports* e *default exports* um mesmo módulo pode conter?**

<details>
  <summary>Possível resposta</summary>

  Um módulo pode conter múltiplos *named exports* (desde que cada nome seja único), mas no máximo **um** `export default`.
</details>

**4. Como a importação de um *default export* difere da importação de um *named export*?**

<details>
  <summary>Possível resposta</summary>

  *Named exports* exigem o uso de chaves `{}` e os nomes devem corresponder aos exportados (ou usar `as`). O *default export* é importado sem chaves e pode receber qualquer nome local desejado.
</details>

**5. Como alterar o nome local de um *named export* durante a importação?**

<details>
  <summary>Possível resposta</summary>

  Utiliza-se a palavra-chave `as` dentro das chaves da instrução de importação, por exemplo: `import { sum as add } from './lib.js'`.
</details>

### Namespace e Dynamic Imports

**6. Para que serve a sintaxe `import * as Namespace` e qual é a propriedade especial de um objeto de namespace?**

<details>
  <summary>Possível resposta</summary>

  Serve para agrupar todas as exportações de um módulo em um único objeto prefixado. O objeto de namespace é **imutável (read-only)** e qualquer tentativa de mutação causa erro.
</details>

**7. Por que não podemos colocar uma instrução `import` estática dentro de um bloco `if`?**

<details>
  <summary>Possível resposta</summary>

  Porque declarações `import` estáticas são analisadas antes da execução do código e só podem aparecer no nível superior (*top-level*) do arquivo.
</details>

**8. Como realizar o carregamento condicional de um módulo em tempo de execução?**

<details>
  <summary>Possível resposta</summary>

  Utiliza-se a função de import dinâmico `import('caminho.js')`, que retorna uma `Promise` que resolve para o objeto de namespace do módulo (podendo ser consumida com `await import()`).
</details>

### Execução e vínculos vivos

**9. Quantas vezes o código do topo de um módulo é executado quando ele é importado por vários arquivos?**

<details>
  <summary>Possível resposta</summary>

  Apenas uma vez. O módulo é avaliado na primeira importação e o resultado fica em cache para todas as importações seguintes, o que faz suas variáveis funcionarem como estado compartilhado.
</details>

**10. O que é um vínculo vivo (*live binding*) e por que não é possível reatribuir uma variável importada?**

<details>
  <summary>Possível resposta</summary>

  A importação aponta para a variável do módulo de origem, e não para uma cópia do valor: alterações feitas lá dentro passam a ser visíveis imediatamente. A reatribuição no arquivo que importa é bloqueada com `TypeError` porque as importações se comportam como constantes (*read-only bindings*).
</details>

### Resolução e Configuração

**11. O que diferencia um especificador de arquivo relativo de um especificador de pacote npm?**

<details>
  <summary>Possível resposta</summary>

  Especificadores relativos começam obrigatoriamente com `./` ou `../` para indicar arquivos locais. Especificadores de pacote não contêm `./` e são buscados pelo Node.js dentro do diretório `node_modules`.
</details>

**12. Qual configuração é necessária no `package.json` para habilitar ES Modules em um projeto Node.js?**

<details>
  <summary>Possível resposta</summary>

  Incluir a propriedade `"type": "module"` no arquivo `package.json`.
</details>

**13. O que significam os três números e o símbolo `^` na versão `"^11.7.0"` de um pacote no `package.json` (SemVer)?**

<details>
  <summary>Possível resposta</summary>

  No SemVer (`MAJOR.MINOR.PATCH`), `11` é a versão MAJOR (mudanças que quebram código), `7` é a MINOR (novas funcionalidades retrocompatíveis) e `0` é a PATCH (correções de bugs). O símbolo `^` (caret) permite atualizar automaticamente para versões MINOR e PATCH mais recentes, bloqueando alterações na versão MAJOR.
</details>
