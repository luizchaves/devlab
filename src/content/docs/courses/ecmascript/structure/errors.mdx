Este tópico apresenta os mecanismos para tratamento de erros e tolerância a falhas em tempo de execução em JavaScript, detalhando o funcionamento da estrutura `try...catch...finally`, o disparo de exceções com `throw`, a taxonomia de erros nativos (`TypeError`, `ReferenceError`, `SyntaxError`, `RangeError`), o encadeamento de causa raiz com `cause` (ES2022), a criação de classes de erros customizadas e a gestão de erros em fluxos assíncronos.

## Objetivo

Dominar a gestão de exceções e a recuperação de falhas em tempo de execução em JavaScript, do isolamento de blocos de risco à modelagem de classes de erro de domínio e tratamento assíncrono. Ao final do tópico, o leitor deve ser capaz de:

- Interceptar exceções de forma graciosa com `try...catch`, garantindo a execução de rotinas de limpeza com `finally`.
- Lançar erros estruturados com a instrução `throw`, inspecionando propriedades nativas como `.message`, `.name`, `.stack` e a causa raiz em `.cause`.
- Identificar e diferenciar as principais classes de erro nativas (`TypeError`, `ReferenceError`, `SyntaxError`, `RangeError`, `URIError` e `AggregateError`).
- Criar e estender classes de erros personalizadas (*custom errors*), filtrando o tratamento de falhas com o operador `instanceof`.
- Tratar falhas em fluxos assíncronos tanto em cadeias de Promises (`.catch()`) quanto em funções `async/await` com `try...catch`.

Antes de decidir como tratar uma falha, observe o diagnóstico que o ambiente já
fornece. A mensagem de erro é parte do material de investigação, não apenas um texto
para ocultar ou substituir.

<Aside type="tip" title="Leia a mensagem de erro antes de corrigir">
  Uma mensagem de erro geralmente indica o tipo da falha, como `SyntaxError`,
  `ReferenceError` ou `TypeError`, e pode apontar arquivo, linha, coluna e pilha de
  chamadas. Esse conjunto costuma revelar onde a investigação deve começar.

  Se o programa não terminar, ficar lento ou produzir uma saída inesperada, torne a
  execução visível com o console: use `console.log()` para conferir valores,
  `console.table()` para comparar coleções e `console.time()` com
  `console.timeEnd()` para medir trechos suspeitos.
</Aside>

## O Bloco `try...catch...finally`

Quando ocorre um erro em tempo de execução (*runtime error*), o JavaScript interrompe imediatamente a execução do script e lança uma exceção. Para interceptar essas exceções e tratar a falha de forma graciosa sem encerrar o programa, utiliza-se a estrutura **`try...catch...finally`**.

### Fluxo de Controle

O bloco a seguir mostra a estrutura completa e a ordem em que cada parte é executada:

```js title="Estrutura de try/catch/finally"
try {
  // Código protegido que pode lançar uma exceção
} catch (error) {
  // Bloco executado SOMENTE se ocorrer um erro no bloco try
} finally {
  // Bloco executado SEMPRE, independentemente de ter ocorrido erro ou não
}
```

- **`try`**: Contém o bloco de código sujeito a falhas (ex: operações de I/O, parsing de JSON, requisições de rede).
- **`catch`**: Intercepta o objeto de erro lançado e permite tomar medidas corretivas (ex: registrar logs, exibir mensagens amigáveis ao usuário).
- **`finally`**: Executado **incondicionalmente** ao término da operação. É ideal para tarefas de limpeza (*cleanup*), como fechar conexões de banco de dados, fechar arquivos ou desativar indicadores de carregamento (*spinners*).

O diagrama a seguir ilustra a bifurcação de execução entre o caminho feliz (sem erros) e o tratamento de falhas, convergindo incondicionalmente no bloco de finalização:

<Mermaid title="Ciclo de Vida de Execução: try...catch...finally">
{`
flowchart TD
  Start(["Início da operação"]) --> Try["Executa bloco try"]
  Try --> Check{"Ocorreu exceção?"}
  Check -->|Não| NormalPath["Conclui o código<br>do try"]
  Check -->|Sim| Catch["Executa catch(error)<br>captura e trata a falha"]
  NormalPath --> Finally["Executa finally<br>limpeza obrigatória"]
  Catch --> Finally
  Finally --> EndNode(["Continua a execução<br>do programa"])
`}
</Mermaid>

O exemplo prático a seguir demonstra esse ciclo de vida ao realizar o *parsing* de dados no formato JSON:

```js title="Exemplo: try...catch...finally"
function parseUserData(jsonString) {
  console.log("Iniciando processamento...");

  try {
    const user = JSON.parse(jsonString);
    console.log(`Usuário carregado: ${user.name}`);
    return user;
  } catch (error) {
    console.error(`Falha ao ler JSON: ${error.message}`);
    return null;
  } finally {
    console.log("Finalizando operação (limpeza de recursos).\n");
  }
}

// 1. Caso de Sucesso:
parseUserData('{"name": "Ana"}');

// 2. Caso de Erro de Sintaxe no JSON:
parseUserData('JSON_INVÁLIDO');
```

<Aside type="note" title="Garantia de Execução do Bloco Finally">
  O bloco `finally` é executado **mesmo se houver uma instrução `return`** dentro dos blocos `try` ou `catch`. O retorno da função é temporariamente suspenso até que as instruções do `finally` terminem de rodar.
</Aside>

### Opcional: Catch sem Parâmetro (ES2019)

A partir do ES2019, caso você não precise inspecionar os detalhes do objeto de erro, é possível omitir os parênteses do `catch` (*Optional Catch Binding*):

```js title="Optional Catch Binding (ES2019)"
try {
  performRiskyAction();
} catch {
  console.log("Ação falhou, mas não precisamos dos detalhes do erro.");
}
```

## Lançamento de Exceções (`throw`)

A instrução **`throw`** permite interromper o fluxo normal do programa e lançar uma exceção intencionalmente. Em JavaScript, é possível lançar qualquer tipo de dado (strings, números, booleanos ou objetos), mas a **boa prática padrão é lançar instâncias da classe nativa `Error`** (ou de suas subclasses).

### O Objeto `Error` Nativo

Ao instanciar `new Error("mensagem")`, o JavaScript captura automaticamente o contexto de execução e disponibiliza três propriedades fundamentais:

- **`.message`**: A mensagem descritiva do erro.
- **`.name`**: O nome do tipo de erro (por padrão, `"Error"`).
- **`.stack`**: A pilha de chamadas (*stack trace*) que mostra em qual linha e arquivo a exceção foi gerada.
- **`.cause`** *(ES2022)*: Propriedade para encadear a causa raiz original do erro.

```js title="Lançando erros com throw new Error()"
function divide(a, b) {
  if (typeof a !== "number" || typeof b !== "number") {
    throw new TypeError("Ambos os argumentos devem ser números.");
  }

  if (b === 0) {
    throw new RangeError("Divisão por zero não é permitida.");
  }

  return a / b;
}

try {
  console.log(divide(10, 2)); // 5
  divide(10, 0);             // Lança RangeError
} catch (error) {
  console.log(`[${error.name}]: ${error.message}`);
}
```

Quando uma exceção é lançada com `throw` e a função corrente não possui um bloco `try...catch`, o erro é propagado para a função chamadora na pilha de execução (*call stack unwinding*):

<Mermaid title="Propagação de Exceções na Pilha de Chamadas (Call Stack Unwinding)">
{`
flowchart TD
  C["funcaoC()<br>throw new RangeError(...)"] -->|Propaga| B["funcaoB()<br>sem try/catch"]
  B -->|Propaga| A["funcaoA()<br>try { funcaoB() } catch(err)"]
  A --> Handled(["Exceção tratada"])
`}
</Mermaid>

### Encadeamento de Erro com `cause` (ES2022)

Introduzida no ES2022, a opção **`cause`** permite encapsular um erro de baixo nível em um erro de alto nível com mais contexto, preservando o diagnóstico original:

```js title="Encadeamento de causa com cause (ES2022)"
function readConfigFile() {
  try {
    JSON.parse("JSON_CORRUPTO");
  } catch (originalError) {
    // Encapsula o erro original na propriedade 'cause'
    throw new Error("Falha ao carregar as configurações do sistema.", {
      cause: originalError,
    });
  }
}

try {
  readConfigFile();
} catch (error) {
  console.error(error.message); // "Falha ao carregar as configurações do sistema."
  console.error("Causa raiz:", error.cause.message); // "Unexpected token 'J'..."
}
```

## Tipos de Erros Nativos em JavaScript

O JavaScript possui um conjunto de subclasses nativas da classe base `Error`, cada uma representando uma categoria específica de falha:

| Tipo de Erro | Causa Comum | Exemplo de Código |
| :--- | :--- | :--- |
| **`TypeError`** | Operação executada em tipo incompatível ou acesso a `null`/`undefined`. | `"texto".push(1)` ou `null.prop` |
| **`ReferenceError`** | Acesso a uma variável que não foi declarada no escopo ou acessada na TDZ. | `console.log(naoDeclarado)` |
| **`SyntaxError`** | Código ferindo a gramática da linguagem ou JSON malformatado. | `JSON.parse("{ bad }")` |
| **`RangeError`** | Número ou argumento fora do intervalo numérico aceitável. | `new Array(-1)` ou estouro de pilha |
| **`URIError`** | Uso de caracteres inválidos nas funções `decodeURI()` ou `encodeURI()`. | `decodeURIComponent("%")` |
| **`AggregateError`** | Agrupa múltiplos erros em uma única exceção (ex: `Promise.any()`). | `Promise.any([p1_falsas])` |

```js title="Exemplos de erros nativos"
// 1. TypeError
try {
  const num = 42;
  num.toUpperCase(); // Método de String chamado em Number
} catch (err) {
  console.log(err instanceof TypeError); // true
}

// 2. ReferenceError
try {
  console.log(nonExistentVar);
} catch (err) {
  console.log(err instanceof ReferenceError); // true
}
```

## Erros Personalizados (*Custom Errors*)

Em aplicações de grande porte, é recomendável criar **classes de erros customizadas** herdando de `Error`. Isso permite categorizar falhas de negócio (como erros de validação de formulário, autenticação ou banco de dados) e capturá-las especificamente usando o operador **`instanceof`**.

O diagrama a seguir exibe a hierarquia de herança a partir da classe base `Error`, englobando tanto as subclasses nativas da especificação quanto as classes customizadas da aplicação:

<Mermaid title="Hierarquia de Classes: Error Nativo e Subclasses Customizadas">
{`
flowchart LR
  Base["Error<br>classe base"] --> Native["Erros nativos<br>da engine"]
  Base --> Custom["Erros de domínio<br>(custom)"]
  Native --> T1["TypeError"]
  Native --> T2["RangeError"]
  Native --> T3["SyntaxError"]
  Native --> T4["ReferenceError"]
  Custom --> C1["ValidationError"]
  Custom --> C2["NotFoundError"]
`}
</Mermaid>

O exemplo a seguir demonstra a criação e a identificação seletiva dessas classes com o operador `instanceof`:

```js title="Criando e identificando Erros Personalizados"
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

class NotFoundError extends Error {
  constructor(message) {
    super(message);
    this.name = "NotFoundError";
  }
}

function registerUser(userData) {
  if (!userData.email) {
    throw new ValidationError("O campo e-mail é obrigatório.", "email");
  }

  if (userData.id !== 1) {
    throw new NotFoundError("Usuário não encontrado na base de dados.");
  }
}

try {
  registerUser({ id: 2, email: "user@devlab.com" });
} catch (error) {
  // Filtrando o tipo de erro com o operador instanceof
  if (error instanceof ValidationError) {
    console.error(`[Validação] Erro no campo '${error.field}': ${error.message}`);
  } else if (error instanceof NotFoundError) {
    console.error(`[Não Encontrado]: ${error.message}`);
  } else {
    console.error(`[Erro Inesperado]: ${error.message}`);
  }
}
```

## Tratamento de Erros em Código Assíncrono

O tratamento de erros em operações assíncronas varia de acordo com o padrão utilizado (**Promises** ou **`async/await`**).

### 1. Tratamento com Promises (`.catch()`)

Nas Promises, exceções lançadas ou rejeições ocorridas dentro da cadeia assíncrona são capturadas pelo método **`.catch()`**:

```js title="Tratamento de erro em Promises"
function fetchUser(id) {
  return new Promise((resolve, reject) => {
    if (id <= 0) {
      reject(new Error("ID de usuário inválido."));
    } else {
      resolve({ id, name: "Lucas" });
    }
  });
}

fetchUser(-1)
  .then((user) => console.log(user))
  .catch((error) => console.error(`[Promise Error]: ${error.message}`))
  .finally(() => console.log("Operação de busca encerrada."));
```

### 2. Tratamento com `async/await` (`try...catch`)

Funções declaradas com `async` permitem utilizar a sintaxe tradicional **`try...catch`** para capturar exceções de Promises de forma síncrona e limpa:

```js title="Tratamento de erro com async/await"
async function loadData() {
  try {
    const user = await fetchUser(-1);
    console.log(user);
  } catch (error) {
    console.error(`[Async/Await Error]: ${error.message}`);
  } finally {
    console.log("Finalizado.");
  }
}

loadData();
```

O diagrama a seguir demonstra como o operador `await` intercepta a rejeição de uma Promise e a converte internamente em uma exceção síncrona dentro do bloco `try...catch`:

<Mermaid title="Fluxo de Tratamento de Exceções com async/await">
{`
flowchart TD
  Call["await operacaoAssincrona()"] --> State{"Promise resolvida<br>ou rejeitada?"}
  State -->|"Resolvida"| Ret["Recebe o valor<br>e segue no try"]
  State -->|"Rejeitada"| ThrowErr["Lança exceção<br>e desvia para o catch"]
  ThrowErr --> Catch["Executa catch(error)"]
  Ret --> Finally["Executa finally"]
  Catch --> Finally
  Finally --> EndNode(["Continua execução"])
`}
</Mermaid>

## Tratamento de Erros na Era da Inteligência Artificial

Pedir "adicione tratamento de erros" a um assistente de código quase sempre devolve a mesma coisa: um `try...catch` envolvendo o bloco inteiro, um `console.error()` dentro do `catch` e a execução seguindo em frente. O código passa a parecer robusto, e o efeito prático é o oposto, porque a falha deixa de interromper o fluxo e passa a se manifestar mais tarde, longe da causa.

Esta é a área do JavaScript em que a sugestão plausível é mais perigosa: um erro tratado errado não aparece em teste feliz, não aparece em revisão apressada e só aparece no relato de quem usou o sistema.

### O catch que engole a exceção

O trecho abaixo é a resposta mais comum ao pedido de "tornar a função segura". Ela captura tudo, registra no console e devolve um valor de aparência inofensiva:

```js title="account.js (primeira versão gerada)"
export function parseBalance(payload) {
  try {
    return JSON.parse(payload).balance;
  } catch (error) {
    console.error("Erro ao processar saldo:", error);
    return 0; // valor padrão para não quebrar a aplicação
  }
}
```

O comentário do próprio modelo entrega o problema: "para não quebrar a aplicação". Um saldo ausente virou o número `0`, que é um saldo válido, e a diferença entre "não sei" e "zero" desapareceu antes de chegar a quem chamou a função.

O teste abaixo formaliza a distinção que o `catch` apagou:

```js title="account.test.js"
import { test } from "node:test";
import assert from "node:assert/strict";
import { parseBalance } from "./account.js";

test("lê o saldo de um payload válido", () => {
  assert.equal(parseBalance('{"balance":1500.5}'), 1500.5);
});

test("sinaliza payload inválido em vez de devolver saldo zero", () => {
  assert.throws(() => parseBalance("{quebrado"), SyntaxError);
});
```

A execução mostra que a função nunca falha, nem quando deveria:

```bash title="Terminal"
node --test account.test.js
```

```txt title="Output" frame="terminal"
✔ lê o saldo de um payload válido (0.8834ms)
✖ sinaliza payload inválido em vez de devolver saldo zero (1.3221ms)
ℹ tests 2
ℹ suites 0
ℹ pass 1
ℹ fail 1

✖ failing tests:

test at account.test.js:9:1
✖ sinaliza payload inválido em vez de devolver saldo zero (1.3221ms)
  AssertionError [ERR_ASSERTION]: Missing expected exception.
```

A correção não é remover o `try...catch`, é decidir o que o `catch` acrescenta. Aqui ele acrescenta contexto e propaga a falha com a causa original preservada em `cause`:

```js title="account.js (versão corrigida)"
export function parseBalance(payload) {
  try {
    return JSON.parse(payload).balance;
  } catch (error) {
    // Acrescenta contexto e mantém o rastro original em error.cause
    throw new SyntaxError("Payload de saldo inválido", { cause: error });
  }
}
```

<Aside type="caution" title="Dica de IA: Todo catch precisa justificar sua existência">
  Ao revisar um `try...catch` sugerido por IA, exija uma resposta para uma pergunta: o que este bloco faz além de esconder a falha? Se a resposta for "registra no console e segue", o bloco está piorando o sistema. `catch` válido é o que **traduz**, **acrescenta contexto**, **tenta novamente** ou **decide um caminho alternativo consciente**.

  **Prompt:** *"Para cada `try...catch` deste arquivo, responda: o bloco traduz o erro, acrescenta contexto, tenta novamente ou decide um caminho alternativo? Remova ou reescreva os que apenas registram no console e seguem em frente."*
</Aside>

### Do catch genérico ao erro tipado

O segundo padrão recorrente é o `catch` único que trata todas as falhas como iguais. O trecho herdado abaixo mistura três causas diferentes em uma resposta só:

```js title="Tratamento herdado, genérico demais"
try {
  const user = await findUser(id);
  return user.profile.name;
} catch (error) {
  return "Usuário desconhecido";
}
```

A decomposição separa o que aquele único `catch` está capturando de fato:

| Falha capturada | Origem real | Resposta adequada |
| :--- | :--- | :--- |
| `TypeError` em `user.profile` | O usuário existe, mas não tem perfil. | Devolver o nome padrão é aceitável. |
| Erro de rede ou de banco | A consulta não chegou ao destino. | Propagar e responder com falha temporária. |
| `ReferenceError` de digitação | Defeito no próprio código. | Nunca capturar: precisa quebrar em desenvolvimento. |

Com erros tipados, cada causa recebe o tratamento que merece, e o defeito de programação continua subindo:

```js title="user-service.js"
export class UserNotFoundError extends Error {
  constructor(id) {
    super(`Usuário ${id} não encontrado`);
    this.name = "UserNotFoundError";
    this.status = 404;
  }
}

export async function getUserName(id) {
  try {
    const user = await findUser(id);
    return user.profile?.name ?? "Sem nome cadastrado";
  } catch (error) {
    if (error instanceof UserNotFoundError) return "Usuário desconhecido";

    throw error; // rede, banco e defeitos de código continuam subindo
  }
}
```

### A mensagem de erro que vaza detalhes

Assistentes otimizam para depuração, e a sugestão padrão de resposta de erro em uma API devolve ao cliente exatamente o que ajuda quem está desenvolvendo, incluindo o que não deveria sair do servidor:

```js title="Resposta de erro sugerida e resposta segura"
// Sugestão comum: repassar a mensagem e a pilha para o cliente
app.use((error, req, res, next) => {
  res.status(500).json({ error: error.message, stack: error.stack });
});

// Versão que registra tudo no servidor e devolve o essencial ao cliente
app.use((error, req, res, next) => {
  console.error(error); // mensagem, pilha e causa ficam no log

  const status = error.status ?? 500;
  const message = status < 500 ? error.message : "Erro interno do servidor";

  res.status(status).json({ error: message });
});
```

A diferença entre os dois blocos não é de estilo. A pilha de chamadas expõe caminhos de arquivos, versões de dependências e, com frequência, trechos de consulta ao banco de dados com nomes reais de tabelas e colunas.

### Perguntas que revelam um tratamento mal posicionado

Antes de aprovar um bloco de tratamento de erros gerado por IA, três perguntas costumam resolver a revisão sem discussão de estilo:

1. **Quem consome esta função consegue distinguir sucesso de falha?** Um retorno `0`, `null` ou `[]` no `catch` apaga essa distinção;
2. **Este `catch` está no nível certo?** Tratamento em toda função transforma qualquer chamada em um ponto de decisão; o lugar natural é a borda do sistema, como o *middleware* de erro ou o `main`;
3. **O erro original sobreviveu?** Um `throw new Error("falhou")` sem `cause` descarta a pilha da falha real e deixa o próximo incidente sem rastro.

<Aside type="tip" title="Dica de IA: Rastrear, reproduzir e corrigir é onde a IA mais ajuda">
  Vale reconhecer a assimetria: assistentes de código são medianos ao adivinhar a arquitetura de um projeto e são **muito bons** diante de um erro concreto. Uma mensagem de exceção, uma pilha de chamadas e o trecho apontado por ela formam exatamente o tipo de evidência que um modelo correlaciona bem, e a depuração assistida costuma encurtar horas de investigação. O ganho, porém, depende do que é colado e da ordem dos pedidos.

  Três estratégias mudam o resultado:

  1. **Cole a evidência inteira, não o resumo.** Mensagem, pilha completa, versão do Node.js e o trecho da primeira linha do rastro que pertence ao seu código. Descrever o erro com as próprias palavras joga fora a informação mais útil que você tem.
  2. **Peça reprodução antes da correção.** *"Escreva o menor teste com `node:test` que reproduz esta falha, sem corrigir o código."* Um teste que falha prova o diagnóstico, e depois vira proteção contra a regressão.
  3. **Termine perguntando pelo resto do sistema.** *"Que outras chamadas deste módulo teriam o mesmo defeito?"* O mesmo padrão de erro costuma aparecer em três lugares, e só um deles apareceu no relatório.

  Quando o erro não se reproduz, inverta o pedido: em vez da causa, peça as condições que produziriam aquele estado, como campo ausente, condição de corrida, fuso horário ou cache antigo.

  **Prompt:** *"Este é o erro, esta é a pilha completa e este é o trecho apontado por ela. Liste três causas possíveis em ordem de probabilidade e, para cada uma, o comando ou o `console.log` que confirma ou descarta a hipótese. Não corrija ainda."*
</Aside>

### Armadilhas frequentes em tratamento de erros gerado por IA

O conjunto de falhas abaixo se repete com frequência suficiente para virar item de revisão:

| Armadilha | Como se manifesta | Como mitigar |
| :--- | :--- | :--- |
| **`catch` vazio ou só com log** | A falha vira uma linha no console e o fluxo continua com dado inválido. | Exigir tradução, contexto, nova tentativa ou repropagação em todo `catch`. |
| **Valor padrão no lugar do erro** | `return 0`, `return null` ou `return []` escondendo a causa. | Testar o caminho de falha com `assert.throws()`. |
| **Perda da causa original** | `throw new Error("erro ao salvar")` sem `{ cause: error }`. | Sempre repassar a causa, disponível desde o ES2022. |
| **`try...catch` em torno de `Promise` sem `await`** | O bloco não captura nada, pois a rejeição acontece depois. | Conferir se há `await` dentro do `try` ou usar `.catch()`. |
| **Captura de defeitos de programação** | `TypeError` e `ReferenceError` engolidos junto com falhas esperadas. | Filtrar por tipo com `instanceof` e repropagar o restante. |
| **Detalhe interno na resposta HTTP** | `error.stack` e mensagens de banco devolvidas ao cliente. | Registrar no servidor e responder com mensagem genérica em erros 5xx. |

A quarta armadilha **falha em silêncio**, porque o código tem a forma correta e não protege nada:

```js title="try...catch que não captura a rejeição"
// Sugestão comum: try...catch em volta de uma chamada assíncrona sem await
try {
  fetchData(); // devolve uma Promise rejeitada, fora do fluxo síncrono
} catch (error) {
  console.error("nunca chega aqui:", error);
}

// Com await, a rejeição vira exceção dentro do bloco
try {
  await fetchData();
} catch (error) {
  console.error("agora sim:", error.message);
}
```

A inteligência artificial reduziu o custo de escrever um `try...catch`, mas não alterou em nada o custo de descobrir tarde demais que a aplicação vinha ignorando falhas em produção.

## Boas práticas

A tabela a seguir consolida as diretrizes essenciais para estruturar o tratamento de exceções de forma limpa, robusta e diagnóstica:

| Prática | Motivo |
| ------- | ------ |
| Sempre lance instâncias de `Error` | Preserva a pilha de chamadas (*stack trace*) e padroniza o formato do objeto |
| Utilize `finally` para liberar recursos | Executa incondicionalmente, mesmo após `return` antecipado ou exceções no `catch` |
| Filtre tipos de erro com `instanceof` | Permite aplicar ações corretivas distintas conforme a natureza da falha |
| Encapsule diagnósticos com `error.cause` | Preserva a causa raiz de baixo nível ao emitir mensagens contextuais amigáveis |
| Nunca crie blocos `catch` vazios | Engolir erros sem log ou tratamento mascara falhas críticas em produção |
| Capture rejeições assíncronas com `try...catch` | Evita interrupções por promessas rejeitadas não tratadas (*unhandled rejections*) |

O exemplo a seguir demonstra a combinação dessas práticas em uma rotina de serviço completa:

```js title="Resumo prático"
class DatabaseError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = "DatabaseError";
  }
}

async function safeFetchUserData(userId) {
  let connection = null;

  try {
    connection = { open: true };

    if (!userId || userId <= 0) {
      throw new TypeError("ID de usuário inválido.");
    }

    try {
      throw new Error("Timeout ao conectar ao cluster.");
    } catch (dbErr) {
      throw new DatabaseError("Falha ao consultar registro do usuário.", { cause: dbErr });
    }
  } catch (error) {
    if (error instanceof TypeError) {
      console.warn(`[Aviso de Tipo]: ${error.message}`);
    } else if (error instanceof DatabaseError) {
      console.error(`[Erro de Banco]: ${error.message} (Causa: ${error.cause.message})`);
    } else {
      console.error("[Erro Crítico]:", error);
    }
    return null;
  } finally {
    if (connection?.open) {
      connection.open = false;
      console.log("Conexão fechada com sucesso no finally.");
    }
  }
}

await safeFetchUserData(0);
await safeFetchUserData(10);
```

## Exercício

Crie uma função `parseJSONSafe(jsonString, fallback = {})` para leitura segura de dados em formato JSON:

1. Utilize o bloco `try` para tentar converter a string com `JSON.parse()`;
2. Em caso de falha (`catch`), capture a mensagem do erro e retorne o objeto `fallback`;
3. Adicione uma cláusula `finally` registrando no console `"Tentativa de parsing concluída."`;
4. Teste a função passando uma string válida (`'{"status":"ok"}'`) e uma string com erro (`'{ bad }'`).

A solução a seguir encapsula a operação em um bloco protegido com valor de fallback e finalização garantida:

<details>
  <summary>Possível resposta</summary>

  ```js title="json-safe.js"
  function parseJSONSafe(jsonString, fallback = {}) {
    try {
      return JSON.parse(jsonString);
    } catch (error) {
      console.error(`[Erro no JSON]: ${error.message}`);
      return fallback;
    } finally {
      console.log("Tentativa de parsing concluída.");
    }
  }

  console.log(parseJSONSafe('{"status":"ok"}')); // { status: "ok" }
  console.log(parseJSONSafe('{ bad }', { status: "fallback" })); // { status: "fallback" }
  ```
</details>

## Desafio

Crie um sistema de saque bancário com erros customizados e tratamento granular:

1. Crie a classe `InsufficientFundsError` herdando de `Error`, armazenando as propriedades `balance` e `amount`;
2. Crie uma classe `BankAccount` com método `withdraw(amount)`. Se `amount <= 0`, lance um `TypeError` com a mensagem `"Valor de saque inválido"`. Se `amount > this.balance`, lance `InsufficientFundsError`;
3. Instancie uma conta com R$ 200,00 e envolva chamadas de saque em um bloco `try/catch/finally`, usando `instanceof` para exibir mensagens específicas para cada tipo de falha.

A solução a seguir modela o erro customizado e implementa o controle de saldo com validação granular via `instanceof`:

<details>
  <summary>Possível resposta</summary>

  ```js title="bank-error.js"
  class InsufficientFundsError extends Error {
    constructor(balance, amount) {
      super(`Saldo insuficiente: disponível R$ ${balance}, solicitado R$ ${amount}`);
      this.name = "InsufficientFundsError";
      this.balance = balance;
      this.amount = amount;
    }
  }

  class BankAccount {
    constructor(balance) {
      this.balance = balance;
    }

    withdraw(amount) {
      if (typeof amount !== "number" || amount <= 0) {
        throw new TypeError("Valor de saque inválido.");
      }
      if (amount > this.balance) {
        throw new InsufficientFundsError(this.balance, amount);
      }
      this.balance -= amount;
      return this.balance;
    }
  }

  const account = new BankAccount(200);

  try {
    account.withdraw(300);
  } catch (error) {
    if (error instanceof InsufficientFundsError) {
      console.error(`[Transação Recusada]: ${error.message}`);
    } else if (error instanceof TypeError) {
      console.error(`[Tipo Inválido]: ${error.message}`);
    } else {
      console.error(`[Erro Desconhecido]: ${error.message}`);
    }
  } finally {
    console.log(`Saldo final: R$ ${account.balance}`); // 200
  }
  ```
</details>

## Perguntas de revisão

### Bloco try...catch...finally

**1. O que acontece se uma exceção for lançada dentro do bloco `try` e não houver um bloco `catch` correspondente?**

<details>
  <summary>Possível resposta</summary>

  O erro não será tratado no escopo atual e continuará propagando (*bubbling*) para os blocos externos da pilha de chamadas. Se não for capturado em nenhum nível, a aplicação será interrompida abruptamente lançando uma exceção não capturada (*unhandled exception*).
</details>

**2. O bloco `finally` é executado se houver uma instrução `return` dentro do bloco `try`?**

<details>
  <summary>Possível resposta</summary>

  Sim. O bloco `finally` sempre é executado antes que o controle de execução seja devolvido ao chamador da função, mesmo que o bloco `try` ou `catch` tenha executado uma instrução `return`.
</details>

### Tipos de Erro e Exceções Customizadas

**3. Qual é a diferença essencial entre `TypeError` e `ReferenceError`?**

<details>
  <summary>Possível resposta</summary>

  O `ReferenceError` ocorre ao tentar utilizar uma variável ou identificador que não existe no escopo atual. O `TypeError` ocorre quando um valor existe, mas tentamos realizar uma operação incompatível com o seu tipo de dado (ex: invocar uma string como se fosse função ou acessar propriedades de `null`/`undefined`).
</details>

**4. Para que serve a propriedade `cause` ao instanciar `new Error(message, { cause })` no ES2022?**

<details>
  <summary>Possível resposta</summary>

  A propriedade `cause` serve para armazenar o erro original de baixo nível que provocou a falha atual, permitindo encadear diagnósticos e rastrear a causa raiz sem perder o contexto do erro de alto nível.
</details>

**5. Como podemos identificar e tratar diferentes tipos de erros em um único bloco `catch`?**

<details>
  <summary>Possível resposta</summary>

  Utilizando o operador `instanceof` dentro do bloco `catch` para checar se o objeto de erro capturado é uma instância de uma classe específica (ex: `if (error instanceof ValidationError) { ... }`).
</details>
