## O que é Async/Await? (Açúcar Sintático sobre Promises)

Introduzidas no ES2017 (ES8), as palavras-chave `async` e `await` não substituem as Promises: elas operam **juntas com as Promises**, oferecendo uma sintaxe mais limpa, sequencial e intuitiva para gerenciar o assincronismo.

O diagrama a seguir demonstra como o motor do JavaScript suspende temporariamente a função `async` no ponto do `await` e devolve o controle à thread principal enquanto a resolução ocorre na fila de microtarefas:

<Mermaid title="Fluxo de Execução com Async/Await e Liberação da Thread Principal">
{`
flowchart TD
  A["Início da Função async"] --> B["Executa código síncrono"]
  B --> C["Encontra instrução: await promise"]
  C --> D["Pausa a execução desta função<br/>Libera a thread principal (Event Loop)"]
  D --> E["Promise é resolvida na Microtask Queue"]
  E --> F["Retoma a execução da função async<br/>Retorna o valor do await"]
`}
</Mermaid>

A relação entre as duas palavras-chave resume-se aos seguintes papéis:

| Recurso | Descrição | Comportamento |
| ------- | --------- | ------------- |
| **`async`** | Modificador colocado antes da declaração de uma função | Faz a função **retornar obrigatoriamente uma Promise** |
| **`await`** | Operador utilizado dentro de uma função `async` | **Pausa a execução** da função até que a Promise seja liquidada |

O exemplo a seguir contrasta o consumo de endpoints com encadeamento `.then()` versus a clareza linear obtida com `async/await`:

```js title="Comparação de Sintaxe: Promises .then() vs Async/Await"
// 1. Consumo com Promises e encadeamento .then()
function fetchUserThen(id) {
  return fetch(`https://api.devlab.org/users/${id}`)
    .then((response) => response.json())
    .then((user) => console.log(user))
    .catch((error) => console.error(error.message));
}

// 2. Consumo idêntico usando Async/Await
async function fetchUserAsync(id) {
  try {
    const response = await fetch(`https://api.devlab.org/users/${id}`);
    const user = await response.json();
    console.log(user);
  } catch (error) {
    console.error(error.message);
  }
}
```

<Aside type="tip" title="async/await não substitui Promises!">
  Por baixo dos panos, o operador `await` extrai o valor de resolução de uma **Promise**. Além disso, o valor retornado por qualquer função marcada com `async` é automaticamente encapsulado em uma Promise resolvida.
</Aside>

## Declaração e Comportamento de Funções Async

A palavra-chave `async` modifica a assinatura e a semântica de retorno de uma função, permitindo o uso do operador `await` em seu escopo interno.

### Formas de Declaração de Funções Async

A palavra-chave `async` pode ser empregada em todas as formas válidas de declaração de funções em JavaScript:

```js title="Formas de declaração de funções async"
// 1. Declaração de Função Tradicional
async function getData() {
  return "Dados carregados";
}

// 2. Arrow Function Assíncrona
const getCategories = async () => {
  return ["Tecnologia", "Redes", "Web"];
};

// 3. Método Assíncrono em Objeto Literal ou Classe
const apiService = {
  async fetchStatus() {
    return { status: "OK", uptime: 99.9 };
  },
};
```

### Coerção de Retorno e Exceções

O motor JavaScript impõe duas regras de coerção automáticas dentro do corpo de uma função `async`:
- Qualquer valor retornado por `return valor` é automaticamente envelopado em `Promise.resolve(valor)`.
- Qualquer erro disparado com `throw erro` é automaticamente convertido em `Promise.reject(erro)`.

O trecho a seguir demonstra como uma função `async` é consumida exatamente como uma Promise convencional:

```js title="Coerção de retornos em funções async"
async function checkNumber(num) {
  if (num < 0) {
    throw new Error("Número negativo não permitido"); // Vira Promise.reject
  }
  return num * 2; // Vira Promise.resolve
}

// Consumindo o retorno da função async como uma Promise normal
checkNumber(5)
  .then((res) => console.log("Resultado:", res)) // "Resultado: 10"
  .catch((err) => console.error(err.message));

checkNumber(-1)
  .catch((err) => console.error("Erro capturado:", err.message)); // "Erro capturado: Número..."
```

## Tratamento de Erros com try...catch...finally

A integração de `async/await` com blocos `try...catch...finally` unifica o tratamento de exceções síncronas e rejeições assíncronas em uma estrutura de controle única e familiar.

### Estrutura try...catch...finally e Validação HTTP

Enquanto o encadeamento tradicional de Promises utiliza `.catch()`, a sintaxe com `async/await` resgata a estrutura tradicional de blocos **`try...catch...finally`**, permitindo capturar tanto exceções síncronas de programação quanto rejeições assíncronas no mesmo local:

```js title="Estrutura completa de tratamento de erros"
async function loadUserProfile(userId) {
  try {
    console.log("Buscando usuário...");
    const response = await fetch(`https://jsonplaceholder.typicode.com/users/${userId}`);

    // Validação indispensável de status HTTP
    if (!response.ok) {
      throw new Error(`Erro na requisição: Status ${response.status}`);
    }

    const user = await response.json();
    return user;

  } catch (error) {
    if (error instanceof Error) {
      console.error("Falha no carregamento:", error.message);
    } else {
      console.error("Erro inesperado:", error);
    }
    return null; // Fallback seguro

  } finally {
    console.log("Operação de busca finalizada.");
  }
}
```

<Aside type="caution" title="O HTTP fetch não rejeita em status 404 ou 500!">
  A função `fetch()` só rejeita a Promise em caso de falha de conexão de rede. Para códigos de erro retornados pelo servidor HTTP (como 404 Not Found ou 500 Server Error), a Promise resolve com sucesso com `response.ok = false`. Sempre verifique `if (!response.ok)` para lançar um erro explícito.
</Aside>

### A Armadilha de `return promise` versus `return await promise`

Uma das armadilhas mais sutis do JavaScript ocorre ao retornar uma Promise de dentro de um bloco `try/catch`. 

Se você escrever `return promise` sem `await`, a função `async` retorna a Promise ainda pendente e **sai imediatamente do bloco `try`**. Caso a Promise venha a ser rejeitada posteriormente, a exceção não será capturada pelo bloco `catch` local, escapando para quem chamou a função!

```js title="A diferença crítica entre return e return await dentro de try/catch"
async function fetchData() {
  return Promise.reject(new Error("Falha na API externa"));
}

// ARMADILHA: a rejeição escapa do catch local!
async function riskyHandler() {
  try {
    return fetchData(); // Retorna a Promise pendente e encerra o try!
  } catch (err) {
    console.error("Catch local:", err.message); // NUNCA É EXECUTADO!
    return null;
  }
}

// FORMA CORRETA: aguarda a resolução dentro do escopo protegido
async function safeHandler() {
  try {
    return await fetchData(); // Aguarda aqui: se rejeitar, pula para o catch!
  } catch (err) {
    console.error("Catch local capturou:", err.message); // Executado com sucesso!
    return null;
  }
}
```

## Execução Sequencial vs. Execução Paralela

Uma falha comum de desempenho com `async/await` é criar **gargalos sequenciais desnecessários** colocando `await` em chamadas assíncronas que poderiam ocorrer simultaneamente.

### O Gargalo da Execução Sequencial

Quando colocamos `await` na frente de cada chamada de forma isolada, a segunda requisição só é despachada após a primeira ter sido concluída por completo:

```js title="Execução Sequencial (Lenta: 2s + 2s = 4s total)"
function delay(ms, value) {
  return new Promise((resolve) => setTimeout(() => resolve(value), ms));
}

async function loadDataSequentially() {
  console.time("Tempo Sequencial");

  // A segunda chamada fica bloqueada aguardando a primeira terminar!
  const users = await delay(2000, ["Ana", "Bruno"]);
  const posts = await delay(2000, ["Post A", "Post B"]);

  console.timeEnd("Tempo Sequencial"); // ~4000ms
  return { users, posts };
}
```

### A Solução Concorrente com `Promise.all()` e `await`

Quando as operações forem mutuamente independentes, devemos disparar ambas as requisições simultaneamente e aguardar a liquidação conjunta com `await Promise.all()`:

```js title="Execução Paralela com Promise.all (Rápida: Max(2s, 2s) = 2s total)"
async function loadDataInParallel() {
  console.time("Tempo Paralelo");

  // Dispara ambas as requisições em paralelo (sem await no disparo inicial)
  const usersPromise = delay(2000, ["Ana", "Bruno"]);
  const postsPromise = delay(2000, ["Post A", "Post B"]);

  // Aguarda a resolução conjunta das duas Promises
  const [users, posts] = await Promise.all([usersPromise, postsPromise]);

  console.timeEnd("Tempo Paralelo"); // ~2000ms
  return { users, posts };
}
```

A comparação entre os dois paradigmas resume-se a:

| Abordagem | Funcionamento | Tempo de Execução Total | Quando Utilizar? |
| --------- | ------------- | ----------------------- | ---------------- |
| **Sequencial** | Um `await` após o outro | Soma de todos os tempos ($\sum t$) | Quando a 2ª chamada depende dos dados da 1ª |
| **Paralela** | Dispara todas e faz `await Promise.all()` | Tempo da operação mais demorada ($\max t$) | Quando as chamadas são independentes |

<Aside type="caution" title="Evite await dentro de laços forEach!">
  O método `.forEach()` de arrays **não aguarda o retorno de Promises**. Inserir `await` dentro do callback de um `.forEach()` fará o laço avançar e o código seguinte executar antes das requisições terminarem.
  
  Para disparar requisições em paralelo a partir de um array, utilize `.map()` combinado com `Promise.all()`:
  
  ```js
  const userDetails = await Promise.all(userIds.map((id) => fetchUser(id)));
  ```
</Aside>

## Iteração Assíncrona com `for await...of`

Quando lidamos com fluxos contínuos de dados assíncronos (como *streams* de arquivos, sockets ou iteradores assíncronos), o JavaScript disponibiliza o laço **`for await...of`**:

```js title="Iteração sequencial sobre fontes assíncronas com for await...of"
async function* generateNumbers() {
  for (let i = 1; i <= 3; i++) {
    await delay(300);
    yield i;
  }
}

async function processStream() {
  // Cada iteração aguarda a resolução do próximo chunk
  for await (const num of generateNumbers()) {
    console.log("Número gerado:", num);
  }
}
```

## Top-Level Await e Aplicações no Node.js / Express

Tradicionalmente, a palavra-chave `await` era restrita ao interior de funções marcadas com `async`. Com a evolução do padrão ECMAScript e a consolidação dos módulos ES (ESM), tornou-se possível utilizar `await` diretamente no escopo raiz dos arquivos, simplificando rotinas de inicialização, conexões com bancos de dados e carregamento de configurações.

### Top-Level Await em Módulos ES

Em Módulos ECMAScript (arquivos `.mjs` ou com `"type": "module"` no `package.json`), é permitido utilizar `await` no escopo raiz do arquivo, **sem a necessidade de envolvê-lo em uma função `async`**:

```js title="Exemplo de Top-Level Await em módulo ES"
// database.js (Módulo ES)
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

// Aguarda a conexão antes de exportar a instância
await prisma.$connect();
console.log("Conexão com o banco de dados estabelecida.");

export default prisma;
```

### Controllers Assíncronos no Express 5

No ecossistema Node.js, funções de rotas e controladores que interagem com bancos de dados são declaradas como funções `async`.

A partir do **Express 5**, qualquer rejeição de Promise ou exceção disparada em uma rota `async` é automaticamente encaminhada para o *middleware* global de erros do servidor, eliminando a necessidade de blocos `try/catch` repetitivos em cada rota:

```js title="src/controllers/user-controller.js"
import prisma from "../database.js";

// Controller assíncrono de listagem de usuários
export async function index(req, res) {
  // O await suspende a rota sem bloquear a thread principal do Node.js
  const users = await prisma.user.findMany();
  res.json(users);
}

// Controller assíncrono de busca por ID
export async function show(req, res) {
  const { id } = req.params;
  const user = await prisma.user.findUnique({ where: { id: Number(id) } });

  if (!user) {
    return res.status(404).json({ error: "Usuário não encontrado" });
  }

  res.json(user);
}
```

## Resumo e Boas Práticas

A adoção disciplinada de `async/await` garante código legível, resiliente e de alto desempenho.

| Prática Recomendada | Motivo Técnico |
| ------------------- | -------------- |
| **Usar `await Promise.all()` para tarefas independentes** | Evita gargalos sequenciais desnecessários, reduzindo a latência para o tempo da chamada mais longa. |
| **Escrever `return await` dentro de blocos `try/catch`** | Garante que a Promise seja resolvida dentro do escopo local, permitindo ao `catch` interceptar falhas. |
| **Validar `response.ok` no consumo de `fetch`** | Códigos de erro HTTP (404/500) não disparam exceções na Promise nativa. |
| **Substituir `.forEach()` assíncrono por `.map()` com `Promise.all()`** | O laço `.forEach()` ignora os retornos de Promises de seus callbacks. |
| **Aproveitar o tratamento de erros do Express 5** | Rejeições assíncronas em rotas são repassadas automaticamente ao middleware de erro global. |
| **Limitar o Top-Level Await à inicialização crítica** | Bloqueia o carregamento de módulos dependentes durante o tempo de espera. |

O bloco a seguir reúne essas práticas em um serviço de agregação de dados com tratamento defensivo e execução concorrente:

```js title="Resumo prático de async/await"
async function fetchUserDashboard(userId) {
  try {
    // 1. Disparo de tarefas independentes em paralelo
    const userPromise = fetch(`https://api.devlab.org/users/${userId}`).then((r) => {
      if (!r.ok) throw new Error("Usuário não encontrado");
      return r.json();
    });

    const settingsPromise = fetch("https://api.devlab.org/settings").then((r) => r.json());

    // 2. Aguarda ambas as tarefas simultaneamente
    const [user, settings] = await Promise.all([userPromise, settingsPromise]);

    return { user, settings, loadedAt: new Date() };

  } catch (error) {
    console.error("Falha ao montar o dashboard:", error.message);
    throw error; // Repassa erro devidamente tipado

  } finally {
    console.log("Tentativa de montagem de dashboard concluída.");
  }
}
```

## Perguntas de revisão
 
Revise os principais conceitos aprendidos sobre a sintaxe `async/await`, ciclo de vida das Promises, fluxo de controle e tratamento de exceções com as questões a seguir:

### Declaração e Funcionamento

**1. O que são as palavras-chave `async` e `await` e qual é a relação delas com Promises?**

<details>
  <summary>Possível resposta</summary>

  `async` e `await` são uma camada de sintaxe simplificada (*syntactic sugar*) construída sobre Promises. A palavra `async` faz a função retornar obrigatoriamente uma Promise, enquanto `await` suspende a função até que a Promise seja resolvida, liberando a thread principal.
</details>

**2. O que acontece quando uma função `async` retorna um valor comum ou dispara um `throw`?**

<details>
  <summary>Possível resposta</summary>

  O valor retornado é automaticamente empacotado em uma Promise resolvida (`Promise.resolve(valor)`). Um erro disparado com `throw` é convertido em uma Promise rejeitada (`Promise.reject(erro)`).
</details>

**3. O que é *Top-Level Await* e onde ele pode ser utilizado legitimamente?**

<details>
  <summary>Possível resposta</summary>

  É o recurso que permite utilizar o operador `await` no escopo raiz de um arquivo, fora de funções `async`. Ele só é permitido em Módulos ES (arquivos `.mjs` ou projetos com `"type": "module"`), sendo ideal para tarefas de inicialização de conexões e configurações.
</details>

**4. O operador `await` pode ser utilizado antes de valores que não são Promises?**

<details>
  <summary>Possível resposta</summary>

  Sim. Se um valor não for uma Promise, o JavaScript o encapsula automaticamente em `Promise.resolve(valor)` e o retorna de forma síncrona na microtarefa imediata.
</details>

### Tratamento de Erros e Armadilhas

**5. Por que a expressão `return promise` dentro de um bloco `try/catch` assíncrono pode gerar bugs graves?**

<details>
  <summary>Possível resposta</summary>

  Porque sem o `await`, a função retorna a Promise pendente e encerra o bloco `try`. Se a Promise rejeitar posteriormente, a exceção não é interceptada pelo `catch` local, escapando para o chamador da função. A forma correta é `return await promise`.
</details>

**6. Por que a função nativa `fetch()` não cai no bloco `catch` em respostas HTTP com código 404 ou 500?**

<details>
  <summary>Possível resposta</summary>

  Porque o método `fetch()` só rejeita a Promise em caso de falha física de conexão de rede. Respostas HTTP legítimas do servidor (mesmo indicando erro) resolvem com sucesso, exigindo a verificação de `response.ok`.
</details>

**7. Para que serve o bloco `finally` em uma estrutura assíncrona `try...catch...finally`?**

<details>
  <summary>Possível resposta</summary>

  Serve para executar instruções obrigatórias de finalização e limpeza (como desativar *spinners* visuais ou fechar descritores de arquivo), independentemente de o bloco ter resolvido com sucesso ou entrado no `catch`.
</details>

**8. Por que nunca devemos colocar `await` dentro do callback de um laço `array.forEach()`?**

<details>
  <summary>Possível resposta</summary>

  Porque o método `.forEach()` não é projetado para esperar retornos de Promises de seus callbacks, fazendo o laço terminar imediatamente enquanto as operações ainda estão rodando em segundo plano.
</details>

### Desempenho e Aplicações no Backend

**9. O que é o gargalo da execução sequencial e como mitigá-lo em chamadas assíncronas independentes?**

<details>
  <summary>Possível resposta</summary>

  O gargalo ocorre ao usar `await` antes de cada chamada independente, somando os tempos de espera. Para mitigá-lo, disparamos todas as Promises em paralelo e aguardamos o resultado consolidado com `await Promise.all([p1, p2])`.
</details>

**10. Como disparar requisições em paralelo a partir de um array dinâmico de IDs?**

<details>
  <summary>Possível resposta</summary>

  Utilizando `array.map(id => fetchUser(id))` para gerar um array de Promises e aguardando a conclusão coletiva com `await Promise.all(promises)`.
</details>

**11. Qual é a vantagem de utilizar controllers `async` no Express 5?**

<details>
  <summary>Possível resposta</summary>

  No Express 5, qualquer rejeição de Promise ou erro disparado dentro de uma rota `async` é automaticamente interceptado e repassado para o middleware global de tratamento de erros, dispensando blocos `try/catch` manuais repetitivos.
</details>

**12. O que é o laço `for await...of` e qual é a sua utilidade prática?**

<details>
  <summary>Possível resposta</summary>

  É uma estrutura de controle projetada para iterar sobre fontes de dados assíncronas (*AsyncIterables*, como *streams* de dados ou geradores assíncronos), aguardando a resolução de cada elemento de forma sequencial.
</details>
