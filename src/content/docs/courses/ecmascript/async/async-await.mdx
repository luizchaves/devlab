Este tópico apresenta as palavras-chave **`async`** e **`await`** em JavaScript: como escrever código assíncrono com a mesma legibilidade e estrutura do código síncrono, como tratar erros com blocos `try/catch`, e como otimizar o desempenho alternando entre execução sequencial e paralela com `Promise.all()`.

## Objetivo

Compreender o papel de `async` e `await` como camada de sintaxe (*syntactic sugar*) sobre **Promises**, declarar e consumir funções assíncronas, tratar erros e exceções utilizando estruturas `try...catch...finally`, diferenciar execução sequencial de execução paralela, utilizar *Top-Level Await* e integrar funções assíncronas em controladores do **Express 5** e ORMs no Node.js.

## O que é Async/Await? (Açúcar Sintático sobre Promises)

Introduzidas no ES2017 (ES8), as palavras-chave `async` e `await` não substituem as Promises — elas trabalham **juntas com as Promises**, oferecendo uma sintaxe mais limpa, sequencial e intuitiva para gerenciar o assincronismo.

O diagrama a seguir demonstra como o motor do JavaScript pausa temporariamente a função `async` no ponto do `await` e libera a linha de execução principal enquanto aguarda a resolução na fila de microtarefas:

<Mermaid title="Fluxo de Execução com Async/Await e Liberação da Thread Principal">
{`
flowchart TD
  A["Início da Função async"] --> B["Executa código síncrono"]
  B --> C["Encontra instrução: await promise"]
  C --> D["Pausa a execução desta função<br/>Libera a thread principal (Event Loop)"]
  D --> E["Promise é resolvida na Microtask Queue"]
  E --> F["Retoma a execução da função async<br/>Retorna o valor do await"]
`}
</Mermaid>

| Recurso | Descrição | Comportamento |
| ------- | --------- | ------------- |
| **`async`** | Modificador colocado antes da declaração de uma função | Faz a função **retornar obrigatoriamente uma Promise** |
| **`await`** | Operador utilizado dentro de uma função `async` | **Pausa a execução** da função até que a Promise seja liquidada |

```js title="Comparação de Sintaxe: Promises .then() vs Async/Await"
// 1. Consumo com Promises e encadeamento .then()
function fetchUserThen(id) {
  return fetch(`https://api.devlab.org/users/${id}`)
    .then((response) => response.json())
    .then((user) => console.log(user))
    .catch((error) => console.error(error));
}

// 2. Consumo idêntico usando Async/Await
async function fetchUserAsync(id) {
  try {
    const response = await fetch(`https://api.devlab.org/users/${id}`);
    const user = await response.json();
    console.log(user);
  } catch (error) {
    console.error(error);
  }
}
```

<Aside type="tip" title="async/await NÃO substitui Promises!">
  Por baixo dos panos, a instrução `await` só funciona quando colocada antes de um valor ou função que retorne uma **Promise**. Além disso, o retorno de toda função marcada com `async` é automaticamente envolvido em uma Promise.
</Aside>

Referência: [async function | MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function).

## Declaração e Comportamento de Funções Async

Você pode utilizar a palavra-chave `async` em qualquer tipo de declaração de função em JavaScript.

```js title="Formas de declaração de funções async"
// 1. Declaração de Função Tradicional
async function getData() {
  return "Dados carregados";
}

// 2. Arrow Function Assíncrona
const getCategories = async () => {
  return ["Tecnologia", "Redes", "Web"];
};

// 3. Método Assíncrono em Objeto ou Classe
const apiService = {
  async fetchStatus() {
    return { status: "OK", uptime: 99.9 };
  },
};
```

## Coerção de Retorno e Exceções

Dentro de uma função `async`:
- Retornar um valor comum (ex: `return "sucesso"`) equivale a retornar `Promise.resolve("sucesso")`.
- Lançar um erro com `throw` (ex: `throw new Error("falha")`) equivale a retornar `Promise.reject(erro)`.

```js title="Coerção de retornos em funções async"
async function checkNumber(num) {
  if (num < 0) {
    throw new Error("Número negativo não permitido"); // Vira Promise.reject
  }
  return num * 2; // Vira Promise.resolve
}

// Consumindo o retorno da função async como uma Promise normal
checkNumber(5)
  .then((res) => console.log("Resultado:", res)) // "Resultado: 10"
  .catch((err) => console.error(err.message));

checkNumber(-1)
  .catch((err) => console.error("Erro capturado:", err.message)); // "Erro capturado: Número..."
```

## Tratamento de Erros com `try...catch...finally`

Em código assíncrono baseado em `.then()`, os erros são capturados com `.catch()`. Com `async/await`, o tratamento de erros utiliza a estrutura tradicional **`try...catch...finally`** do JavaScript.

```js title="Estrutura completa de tratamento de erros"
async function loadUserProfile(userId) {
  try {
    console.log("Buscando usuário...");
    const response = await fetch(`https://jsonplaceholder.typicode.com/users/${userId}`);

    // Verificação de erros de status HTTP (ex: 404 Not Found ou 500 Server Error)
    if (!response.ok) {
      throw new Error(`Erro na requisição: Status ${response.status}`);
    }

    const user = await response.json();
    return user;

  } catch (error) {
    // Trata erros de rede, falha de parse JSON ou erros lançados com throw
    if (error instanceof Error) {
      console.error("Falha no carregamento:", error.message);
    } else {
      console.error("Erro desconhecido:", error);
    }
    return null; // Retorno de fallback seguro

  } finally {
    console.log("Operação de busca encerrada.");
  }
}
```

<Aside type="caution" title="O HTTP fetch não lança erro no status 404 ou 500!">
  A função nativa `fetch()` só rejeita a Promise em caso de falha de conexão de rede. Para códigos de erro HTTP (como 404 Not Found ou 500 Server Error), a Promise resolve normalmente com `response.ok = false`. Sempre verifique `if (!response.ok)` para lançar um erro intencional!
</Aside>

Referência: [await | MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/await).

## Execução Sequencial vs. Execução Paralela

Uma das armadilhas mais comuns ao utilizar `async/await` é criar **gargalos de desempenho** executando operações independentes de forma sequencial.

### O Gargalo da Execução Sequencial

Quando colocamos `await` na frente de cada chamada de forma isolada, a segunda requisição só começará a ser executada **após** a primeira ter sido totalmente concluída.

```js title="Execução Sequencial (Lenta: 2s + 2s = 4s total)"
function delay(ms, value) {
  return new Promise((resolve) => setTimeout(() => resolve(value), ms));
}

async function loadDataSequentially() {
  console.time("Tempo Sequencial");

  // A segunda busca aguarda a primeira terminar!
  const users = await delay(2000, ["Ana", "Bruno"]);
  const posts = await delay(2000, ["Post A", "Post B"]);

  console.timeEnd("Tempo Sequencial"); // ~4000ms
  return { users, posts };
}
```

### A Solução em Paralelo com `Promise.all()` e `await`

Se as operações forem independentes, devemos disparar ambas as Promises simultaneamente e aguardar o resultado combinado com `await Promise.all()`.

```js title="Execução Paralela com Promise.all (Rápida: Max(2s, 2s) = 2s total)"
async function loadDataInParallel() {
  console.time("Tempo Paralelo");

  // Dispara ambas as requisições em paralelo (sem await inicial)
  const usersPromise = delay(2000, ["Ana", "Bruno"]);
  const postsPromise = delay(2000, ["Post A", "Post B"]);

  // Aguarda a resolução simultânea das duas Promises
  const [users, posts] = await Promise.all([usersPromise, postsPromise]);

  console.timeEnd("Tempo Paralelo"); // ~2000ms
  return { users, posts };
}
```

| Abordagem | Funcionamento | Tempo de Execução Total | Quando Utilizar? |
| --------- | ------------- | ----------------------- | ---------------- |
| **Sequencial** | Um `await` após o outro | Soma de todos os tempos ($\sum t$) | Quando a 2ª chamada depende dos dados da 1ª |
| **Paralela** | Dispara todas e faz `await Promise.all()` | Tempo da operação mais longa ($\max t$) | Quando as chamadas são independentes |

<Aside type="caution" title="Evite o uso de await em laços forEach!">
  O método `.forEach()` de arrays **não aguarda Promises**. Colocar `await` dentro do callback de um `.forEach()` fará o laço continuar executando sem esperar pelas requisições!
  
  Para executar requisições em paralelo a partir de um array de itens, utilize `.map()` com `Promise.all()`:
  
  ```js
  const users = await Promise.all(userIds.map((id) => fetchUser(id)));
  ```
</Aside>

## Top-Level Await e Aplicações no Node.js / Express

### Top-Level Await

Em Módulos ES (ESM com `"type": "module"` no `package.json`), você pode utilizar a palavra-chave `await` no nível superior do arquivo, **fora de qualquer função `async`**.

```js title="Exemplo de Top-Level Await em arquivo ES Module"
// database.js (Módulo ES)
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

// Top-Level Await: aguarda a conexão com o banco antes de exportar
await prisma.$connect();
console.log("Conexão com o banco de dados estabelecida com sucesso!");

export default prisma;
```

### Controllers Assíncronos no Express 5

No ecossistema Node.js (especialmente com **Express** e ORMs como **Prisma** ou **Sequelize**), as funções de controller que acessam o banco de dados são declaradas como funções `async`.

A partir do **Express 5**, qualquer rejeição de Promise ou erro lançado em um controller `async` é repassado automaticamente para o *middleware* de erro global do servidor!

```js title="src/controllers/user-controller.js"
import prisma from "../database.js";

// Controller de listagem de usuários
export async function index(req, res) {
  // O await aguarda a consulta ao banco de dados sem travar o servidor Node.js
  const users = await prisma.user.findMany();
  res.json(users);
}

// Controller de busca por ID
export async function show(req, res) {
  const { id } = req.params;
  const user = await prisma.user.findUnique({ where: { id: Number(id) } });

  if (!user) {
    return res.status(404).json({ error: "Usuário não encontrado" });
  }

  res.json(user);
}
```

## Resumo e Boas Práticas

<CardGrid>
  <Card title="Sintaxe e Erros" icon="pencil">
    - Toda função declarada com `async` retorna uma **Promise**.
    - Utilize blocos `try...catch...finally` em volta dos comandos `await` para gerenciar exceções.
    - Lembre-se de verificar `response.ok` ao usar a Fetch API nativa.
  </Card>

  <Card title="Desempenho e Paralelismo" icon="star">
    - Não encadeie `await` sequenciais para chamadas independentes; utilize `await Promise.all()` para disparar requisições em paralelo.
    - Substitua laços `.forEach()` com `await` por `array.map()` combinado a `Promise.all()`.
  </Card>
</CardGrid>

- Utilize *Top-Level Await* apenas no nível raiz de módulos para tarefas de inicialização pesada (como conexões de banco de dados).
- No Express 5, aproveite o repasse automático de erros em rotas `async` para manter seus controllers limpos e centralizar o tratamento no middleware de erro.

<details>
  <summary>Possível resposta</summary>

  ```js title="api-aggregator.js"
  const fetchServerHealth = () =>
    new Promise((res) => setTimeout(() => res({ status: "Healthy", uptime: "99.9%" }), 300));

  const fetchStorageMetrics = () =>
    new Promise((res) => setTimeout(() => res({ usedGb: 450, totalGb: 1000 }), 400));

  const fetchBackupLogs = () =>
    new Promise((_, rej) => setTimeout(() => rej("Falha ao conectar ao serviço de backup"), 200));

    console.log("Carregando painel de monitoramento...");

    // Disparando em paralelo
    const results = await Promise.allSettled([
      fetchServerHealth(),
      fetchStorageMetrics(),
      fetchBackupLogs(),
    ]);

    const [health, storage, backup] = results;

    console.log("\n--- STATUS DO PAINEL ---");

    if (health.status === "fulfilled") {
      console.log("Servidor:", health.value.status, `(Uptime: ${health.value.uptime})`);
    }

    if (storage.status === "fulfilled") {
      console.log("Armazenamento:", `${storage.value.usedGb}GB de ${storage.value.totalGb}GB`);
    }

    if (backup.status === "rejected") {
      console.warn("Módulo de Backup:", `[AVISO] ${backup.reason}`);
    }
  }

  loadDashboardData();
  ```
</details>

## Perguntas de revisão

### Declaração e Funcionamento

**1. O que são as palavras-chave `async` e `await` e qual é a sua relação com Promises?**

<details>
  <summary>Possível resposta</summary>

  `async` e `await` são uma camada de sintaxe mais limpa (*syntactic sugar*) construída diretamente sobre Promises. A palavra-chave `async` faz uma função retornar obrigatoriamente uma Promise, enquanto `await` pausa a execução da função até que uma Promise seja resolvida ou rejeitada.
</details>

**2. O que acontece com o valor retornado por uma função declarada como `async`?**

<details>
  <summary>Possível resposta</summary>

  O valor retornado é automaticamente encapsulado em uma Promise resolvida (`Promise.resolve(valor)`). Se a função lançar uma exceção com `throw`, ela retornará uma Promise rejeitada (`Promise.reject(erro)`).
</details>

**3. É possível utilizar o operador `await` fora de uma função marcada como `async`?**

<details>
  <summary>Possível resposta</summary>

  Em funções tradicionais, não (resultará em erro de sintaxe). A única exceção é o *Top-Level Await*, que permite usar `await` no nível raiz de arquivos configurados como Módulos ES (ESM).
</details>

### Tratamento de Erros e Fetch API

**4. Como é feito o tratamento de erros ao utilizar a sintaxe `async/await`?**

<details>
  <summary>Possível resposta</summary>

  O tratamento de erros é feito utilizando a estrutura tradicional `try...catch...finally`. Qualquer rejeição de Promise aguardada com `await` é capturada como uma exceção dentro do bloco `catch`.
</details>

**5. Por que a função nativa `fetch()` não entra no bloco `catch` em respostas com status HTTP 404 ou 500?**

<details>
  <summary>Possível resposta</summary>

  Porque a função `fetch()` só rejeita a Promise em caso de falha de conexão física de rede. Respostas do servidor com códigos de erro HTTP (como 404 ou 500) resolvem normalmente com a propriedade `response.ok = false`.
</details>

**6. Para que serve o bloco `finally` em uma estrutura `try...catch...finally` assíncrona?**

<details>
  <summary>Possível resposta</summary>

  O bloco `finally` é executado obrigatoriamente ao término da operação assíncrona, independente de ter havido sucesso ou erro, sendo ideal para desligar indicadores de carregamento (*spinners*) ou fechar conexões.
</details>

### Desempenho e Aplicações

**7. O que é o gargalo da execução sequencial com `await` e como evitá-lo em chamadas independentes?**

<details>
  <summary>Possível resposta</summary>

  O gargalo ocorre quando colocamos `await` seguidos antes de disparar cada requisição, fazendo uma esperar o término da outra. Para evitá-lo em requisições independentes, devemos disparar todas em paralelo e aguardar os resultados combinados com `await Promise.all([p1, p2])`.
</details>

**8. Por que não devemos usar `await` dentro de um laço `.forEach()` ao iterar sobre arrays?**

<details>
  <summary>Possível resposta</summary>

  Porque a função de callback do `.forEach()` não aguarda o retorno de Promises, fazendo o laço continuar executando sem esperar pela conclusão das operações. Para requisições em arrays, deve-se usar `.map()` com `await Promise.all()`.
</details>

**9. Por que os controllers que acessam banco de dados no Node.js/Express são declarados como funções `async`?**

<details>
  <summary>Possível resposta</summary>

  Porque operações de banco de dados (como consultas do Prisma ou Sequelize) são assíncronas. O uso de `async/await` permite aguardar os dados sem bloquear o servidor Node.js, e no Express 5 os erros assíncronos são automaticamente encaminhados para o middleware de erro.
</details>

**10. Qual é a vantagem de utilizar `Promise.allSettled()` junto com `await` em vez de `Promise.all()`?**

<details>
  <summary>Possível resposta</summary>

  `Promise.all()` falha imediatamente ao primeiro erro encontrado. `Promise.allSettled()` aguarda todas as Promises terminarem (com sucesso ou falha) e permite tratar cada resultado individualmente sem interromper as demais operações.
</details>
