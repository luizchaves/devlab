Este tópico apresenta as **Promises** em JavaScript: o padrão fundamental para gerenciar operações assíncronas (como requisições HTTP, leitura de arquivos e consultas a bancos de dados), seus três estados, encadeamento com `.then()`, tratamento de erros com `.catch()`, combinadores e os recursos do ES2024.

## Objetivo

Compreender o modelo assíncrono e *single-threaded* do JavaScript, dominando o ciclo de vida e a manipulação de Promises desde a criação básica até combinadores concorrentes e os novos recursos da especificação. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o papel do Event Loop, Call Stack e Microtask Queue na resolução de código assíncrono.
- Instanciar Promises tanto com a função executora tradicional quanto pelo método moderno `Promise.withResolvers()`.
- Diferenciar os estados `Pending`, `Fulfilled` e `Rejected`, compreendendo a imutabilidade do valor liquidado.
- Construir fluxos de transformação lineares com `.then()`, `.catch()` e `.finally()`, eliminando o aninhamento de *callbacks*.
- Empregar os combinadores estáticos (`Promise.all`, `Promise.allSettled`, `Promise.race`, `Promise.any`) segundo os requisitos de tolerância a falhas.
- Tratar exceções de rede com segurança, validando `response.ok` na Fetch API e gerenciando rejeições não tratadas (*unhandled rejections*).

## O que é Assincronismo em JavaScript?

O JavaScript executa código em um ambiente de linha de execução única (*single-threaded*) guiado por um **Event Loop**. Operações de entrada e saída (I/O) (como buscar dados em uma API, ler um arquivo do disco ou aguardar um temporizador) demoram um tempo imprevisível para responder.

Se o JavaScript congelasse a execução até essas operações terminarem, toda a aplicação ou interface do usuário travaria. Para evitar esse bloqueio, as operações de I/O são delegadas ao ambiente hospedeiro e processadas de forma **assíncrona**.

A evolução dos padrões assíncronos no JavaScript reflete a busca por legibilidade e controle de fluxo:

| Modelo | Funcionamento | Problema / Desafio |
| ------ | ------------- | ------------------ |
| **Síncrono** | Cada instrução é executada em sequência, bloqueando a próxima até terminar | Bloqueia a aplicação durante operações lentas |
| **Callbacks** | Funções passadas como argumento para serem executadas após a conclusão | Gera aninhamento excessivo e difícil manutenção (*Callback Hell*) |
| **Promises** | Objetos que representam o resultado futuro de uma operação assíncrona | Permite código assíncrono estruturado, encadeável e legível |

O exemplo a seguir ilustra a transição entre o aninhamento piramidal de callbacks e o fluxo plano e legível oferecido pelo encadeamento de Promises:

```js title="Do Callback Hell às Promises"
// 1. Abordagem antiga com Callbacks (Callback Hell / Pyramids of Doom)
buscarUsuario(1, (usuario) => {
  buscarPedidos(usuario.id, (pedidos) => {
    buscarDetalhesPedido(pedidos[0].id, (detalhes) => {
      console.log(detalhes);
    });
  });
});

// 2. Abordagem moderna com Promises encadeadas
buscarUsuario(1)
  .then((usuario) => buscarPedidos(usuario.id))
  .then((pedidos) => buscarDetalhesPedido(pedidos[0].id))
  .then((detalhes) => console.log(detalhes))
  .catch((erro) => console.error("Erro na cadeia:", erro));
```

## O Conceito e Estados de uma Promise

Uma **Promise** é um objeto JavaScript que atua como um contrato para um valor que pode estar disponível no presente, no futuro ou nunca.

O diagrama a seguir ilustra as transições possíveis entre os três estados de uma Promise e os manipuladores acionados ao final do ciclo:

<Mermaid title="Ciclo de Vida e Transição de Estados de uma Promise">
{`
flowchart TD
  A["new Promise(executor)"] --> B["Pending (Pendente)"]
  B -->|"resolve(valor)"| C["Fulfilled (Realizada)"]
  B -->|"reject(motivo)"| D["Rejected (Rejeitada)"]
  C --> E[".then(onFulfilled)"]
  D --> F[".catch(onRejected)"]
  E --> G[".finally(onFinally)"]
  F --> G
`}
</Mermaid>

Uma Promise opera sob **três estados mutuamente exclusivos**:

| Estado | Nome | Descrição |
| ------ | ---- | --------- |
| **Pending** | Pendente | Estado inicial. A operação assíncrona ainda está em processamento |
| **Fulfilled** | Realizada / Resolvida | A operação foi concluída com êxito e retornou um **valor** |
| **Rejected** | Rejeitada | A operação falhou e retornou uma **razão de erro** (*reason*) |

<Aside type="caution" title="Imutabilidade do Estado de uma Promise">
  Uma Promise transita do estado `Pending` para `Fulfilled` (sucesso) ou `Rejected` (erro) uma **única vez**. Após ser liquidada (*settled*), seu estado e seu valor tornam-se completamente **imutáveis**.
</Aside>

Ao imprimir uma Promise no console, o ambiente revela seu estado interno e o valor retido caso a liquidação já tenha ocorrido:

```js title="Estados de uma Promise"
// Promise em estado PENDING (Pendente)
const pendingPromise = new Promise(() => {});
console.log(pendingPromise); // Promise { <pending> }

// Promise resolvida (FULFILLED)
const fulfilledPromise = Promise.resolve("Sucesso!");
console.log(fulfilledPromise); // Promise { 'Sucesso!' }

// Promise rejeitada (REJECTED)
const rejectedPromise = Promise.reject(new Error("Falha ao carregar dados"));
console.log(rejectedPromise); // Promise { <rejected> Error: Falha ao carregar dados }
```

## Criando e Consumindo Promises

O trabalho com Promises divide-se em duas etapas essenciais: a **produção** (a criação e controle da promessa por quem realiza a tarefa assíncrona) e o **consumo** (o registro de callbacks e tratamento dos resultados por quem dispara a operação). A linguagem disponibiliza tanto o construtor clássico quanto métodos estáticos e utilitários modernos para gerenciar esses fluxos.

### Criando uma Promise com o Construtor Tradicional

Para criar uma Promise, invoca-se o construtor `new Promise` fornecendo uma função executora (*executor*). Essa função recebe dois parâmetros callback fornecidos pelo motor JavaScript: `resolve` e `reject`:

```js title="Criando uma Promise personalizada"
function checkServerStatus(isOnline) {
  return new Promise((resolve, reject) => {
    // Simula uma operação assíncrona de 1 segundo
    setTimeout(() => {
      if (isOnline) {
        resolve("Servidor operacional (Status 200 OK)");
      } else {
        reject(new Error("Falha na conexão: Servidor indisponível"));
      }
    }, 1000);
  });
}
```

O método estático `Promise.resolve(valor)` cria diretamente uma Promise já resolvida, enquanto `Promise.reject(motivo)` cria uma já rejeitada:

```js title="Criação direta com métodos estáticos"
const immediateSuccess = Promise.resolve({ userId: 1, role: "admin" });
const immediateError = Promise.reject(new TypeError("Parâmetro inválido"));
```

### O Recurso Moderno: Promise.withResolvers() (ES2024)

Historicamente, quando precisávamos resolver uma Promise a partir de um evento externo (como um clique, resposta de socket ou stream), éramos obrigados a extrair as funções `resolve` e `reject` para variáveis externas ao executor.

A especificação ECMAScript 2024 padronizou o método **`Promise.withResolvers()`**, que retorna diretamente o objeto da Promise juntamente com suas funções de resolução e rejeição desestruturadas:

```js title="Uso do Promise.withResolvers() (ES2024)"
// Cria a Promise e seus controladores diretamente
const { promise, resolve, reject } = Promise.withResolvers();

// A Promise pode ser retornada ou consumida em qualquer lugar:
promise
  .then((data) => console.log("Recebido:", data))
  .catch((err) => console.error("Erro:", err.message));

// E pode ser resolvida externamente sem aninhar código:
setTimeout(() => {
  resolve("Operação externa concluída com sucesso!");
}, 500);
```

### Execução Síncrona do Executor

Um aspecto arquitetural essencial é que a função executora passada para `new Promise((resolve, reject) => { ... })` é executada **imediatamente e de forma síncrona** no momento da instanciação:

```js title="Execução síncrona do executor"
console.log("1. Antes de criar a Promise");

const promise = new Promise((resolve, reject) => {
  console.log("2. Dentro do executor (execução síncrona imediata)");
  resolve("Dados prontos");
});

console.log("3. Depois de criar a Promise");

promise.then((data) => {
  console.log("4. Dentro do .then() (execução assíncrona via microtask)");
});

console.log("5. Fim do script principal");

// Ordem observada:
// 1. Antes de criar a Promise
// 2. Dentro do executor (execução síncrona imediata)
// 3. Depois de criar a Promise
// 5. Fim do script principal
// 4. Dentro do .then() (execução assíncrona via microtask)
```

### Consumindo com `.then()`, `.catch()` e `.finally()`

A API de consumo das Promises é composta por três métodos encadeáveis:

| Método | Quando é Executado? | Função Principal |
| ------ | ------------------- | ---------------- |
| `.then(onFulfilled)` | Quando a Promise transita para `Fulfilled` | Recebe o valor resolvido e projeta o próximo passo |
| `.catch(onRejected)` | Quando a Promise transita para `Rejected` ou lança um erro | Intercepta falhas ocorridas na cadeia |
| `.finally(onFinally)` | Quando a Promise é liquidada (independente do desfecho) | Executa rotinas de limpeza ou finalização |

O código a seguir exemplifica o consumo completo de uma Promise simulando o ciclo de vida de uma operação:

```js title="Consumindo a Promise com then, catch e finally"
console.log("Iniciando verificação...");

checkServerStatus(true)
  .then((message) => {
    console.log("Sucesso:", message);
  })
  .catch((error) => {
    console.error("Erro:", error.message);
  })
  .finally(() => {
    console.log("Verificação concluída.");
  });
```

<Aside type="note" title="Comportamento do método .finally()">
  O callback fornecido a `.finally()` não recebe argumentos, pois sua finalidade é executar rotinas agnósticas ao resultado (como fechar conexões ou ocultar *spinners*). O valor de retorno de `.finally()` é ignorado, repassando o resultado ou erro original para o restante do fluxo.
</Aside>

## Encadeamento de Promises (Promise Chaining)

O encadeamento linear (*chaining*) evita o *Callback Hell*. Quando a função dentro de um `.then()` retorna um valor primitivo ou objeto comum, o JavaScript o encapsula automaticamente em uma nova Promise resolvida. Se ela retornar outra Promise, a cadeia aguardará a resolução dessa nova Promise antes de passar para o próximo `.then()`:

```js title="Encadeamento de Promises com transformações sucessivas"
function fetchUser(userId) {
  return new Promise((resolve) => {
    setTimeout(() => resolve({ id: userId, name: "Alice", points: 100 }), 300);
  });
}

function calculateBonus(user) {
  return new Promise((resolve) => {
    setTimeout(() => resolve(user.points * 1.5), 300);
  });
}

fetchUser(42)
  .then((user) => {
    console.log(`Usuário encontrado: ${user.name}`);
    return calculateBonus(user); // Retorna nova Promise
  })
  .then((bonusPoints) => {
    console.log(`Pontuação com bônus: ${bonusPoints}`); // 150
    return bonusPoints > 100; // Retorna um booleano simples
  })
  .then((isEligible) => {
    console.log(`Elegível para prêmio? ${isEligible}`); // true
  })
  .catch((error) => {
    console.error("Erro em alguma etapa do processo:", error.message);
  });
```

<Aside type="caution" title="Tratamento Centralizado de Erros">
  Um único bloco `.catch()` posicionado ao final da cadeia intercepta qualquer erro ou rejeição lançada em **qualquer uma das etapas anteriores**.
</Aside>

## Combinadores de Promises

Para coordenar múltiplas operações assíncronas concorrentes, o JavaScript disponibiliza quatro métodos estáticos combinadores:

| Método Estático | Condição de Sucesso | Condição de Falha | Cenário Típico |
| --------------- | ------------------- | ----------------- | -------------- |
| `Promise.all([p1, p2])` | Todas resolvem (retorna array de valores) | Rejeita no **primeiro erro** (*Fail-Fast*) | Carregamento essencial dependente |
| `Promise.allSettled([p1, p2])` | Todas terminam (sucesso ou erro) | **Nunca rejeita**; retorna status de cada uma | Painéis e relatórios parciais |
| `Promise.race([p1, p2])` | A primeira a liquidar (seja sucesso ou erro) | Acompanha a primeira a responder | *Timeouts* e corridas de rede |
| `Promise.any([p1, p2])` | A **primeira com sucesso** | Rejeita só se **todas falharem** (`AggregateError`) | Réplicas e servidores espelho |

O exemplo a seguir ilustra a diferença prática entre o rigor do `Promise.all` e a resiliência do `Promise.allSettled`:

```js title="Comparativo entre Promise.all e Promise.allSettled"
const fetchPosts = new Promise((res) => setTimeout(() => res(["Post 1", "Post 2"]), 300));
const fetchComments = new Promise((res) => setTimeout(() => res(["Comentário 1"]), 500));
const fetchFail = new Promise((_, rej) => setTimeout(() => rej(new Error("Falha no servidor D")), 200));

// 1. Promise.all() falha imediatamente se qualquer chamada rejeitar
Promise.all([fetchPosts, fetchComments])
  .then(([posts, comments]) => {
    console.log("Resultados combinados:", posts, comments);
  })
  .catch((err) => console.error("Erro no Promise.all:", err.message));

// 2. Promise.allSettled() aguarda todas as chamadas independentemente de falhas
Promise.allSettled([fetchPosts, fetchFail])
  .then((results) => {
    console.log("Status individual de cada operação:", results);
  });
```

## Ordem de Execução: Event Loop e Microtask Queue

Para dominar o comportamento assíncrono, é fundamental compreender a arquitetura e a hierarquia de prioridades do **Event Loop** no motor JavaScript.

O diagrama a seguir ilustra a coordenação entre a Call Stack, as APIs do ambiente e a precedência estrita entre a fila de microtarefas e a fila de macrotarefas:

<EventLoopDiagram />

Para compreender o ciclo de execução representado no diagrama, acompanhe a sequência dos fluxos numerados:

1. **Disparo de Operação Assíncrona (Passo 1: Call Stack → APIs do Ambiente):** O motor JavaScript executa o código síncrono frame a frame na Call Stack de forma linear (*single-threaded*). Ao encontrar funções assíncronas (como `fetch()`, `setTimeout()` ou leitura de arquivos), o JavaScript não interrompe o fluxo principal: ele delega o processamento concorrente para as APIs do ambiente (Web APIs no navegador ou threads C++ da biblioteca `libuv` no Node.js) e segue imediatamente para a próxima instrução síncrona da pilha.
2. **Encaminhamento para as Filas Específicas (Passos 2a e 2b: APIs do Ambiente → Filas):** Quando a operação externa conclui seu processamento em segundo plano, o callback associado é direcionado para uma das duas filas assíncronas:
   - **Passo 2a (Microtask Queue):** Se o callback pertencer a uma Promise resolvida ou rejeitada (`.then`, `.catch`, `.finally`), a uma continuação de função após um `await` ou a uma tarefa criada com `queueMicrotask()`, ele entra na **Microtask Queue**, que possui prioridade máxima de execução.
   - **Passo 2b (Macrotask Queue):** Se a tarefa for disparada pelo término de um temporizador (`setTimeout`, `setInterval`), por um evento de interface de usuário ou por I/O de disco/rede, ela entra na **Macrotask Queue** (também chamada de *Task Queue*).
3. **Monitoramento Contínuo da Pilha (Passo 3: Call Stack → Event Loop):** O Event Loop opera em um laço ininterrupto observando a Call Stack. Enquanto houver qualquer função síncrona em execução na pilha principal, o motor permanece dedicado a ela; nenhuma tarefa assíncrona é transferida até que a Call Stack fique completamente vazia. Repare que o Event Loop nunca executa código: ele apenas decide **o que entra na pilha e em que ordem**.
4. **Drenagem Completa da Microtask Queue (Passo 4: Microtask Queue → Event Loop):** Assim que a pilha esvazia, o Event Loop concede prioridade imediata à Microtask Queue e retira dela **todas as microtarefas enfileiradas até zerar a fila**, incluindo as novas microtasks geradas durante a execução desse mesmo lote.
5. **Processamento Unitário de Macrotasks (Passo 5: Macrotask Queue → Event Loop):** Somente após a Microtask Queue estar 100% vazia (e após renderizações visuais de tela, no caso do navegador), o Event Loop retira **uma única macrotarefa** da Macrotask Queue.
6. **Entrega para Execução (Passo 6: Event Loop → Call Stack):** Cada callback retirado nos passos 4 e 5 é empurrado pelo Event Loop para a Call Stack, que o executa como qualquer código síncrono. Concluída a tarefa, o ciclo retorna obrigatoriamente ao Passo 3, e novas microtarefas são conferidas antes de qualquer outra macrotarefa.

7. **Renderização (Passo 7: Event Loop → Renderização):** No navegador, e apenas nele, o mesmo laço ainda dispara a etapa de pintura da tela, no máximo uma vez por quadro (cerca de 16 ms a 60 quadros por segundo). Ela roda **depois** da drenagem das microtarefas e é composta, nesta ordem, pelos *callbacks* de `requestAnimationFrame`, pelo cálculo de estilo, pelo layout (*reflow*), pelo *paint* e pela composição das camadas. No Node.js essa etapa simplesmente não existe, porque não há tela.

É por passar sempre pelo Event Loop que as duas filas nunca competem entre si: as setas 4 e 5 chegam ao mesmo orquestrador, e é ele quem impõe a ordem, drenando a fila de microtarefas por inteiro antes de aceitar a próxima macrotarefa. A renderização segue a mesma regra, e daí vem uma consequência prática: uma microtarefa que nunca termina, ou um lote muito grande delas, **adia a pintura da tela** e trava a interface, mesmo sem nenhum código síncrono pesado em execução.

O trecho a seguir comprova experimentalmente essa ordem de execução, demonstrando como as microtarefas de Promises ultrapassam temporizadores mesmo configurados com zero milissegundos:

```js title="Prioridade de Microtasks no Event Loop"
console.log("1. Síncrono - Início");

setTimeout(() => {
  console.log("2. Macrotask (setTimeout 0ms)");
}, 0);

Promise.resolve()
  .then(() => {
    console.log("3. Microtask 1 (Promise)");
  })
  .then(() => {
    console.log("4. Microtask 2 (Promise encadeada)");
  });

console.log("5. Síncrono - Fim");

// Ordem impressa no terminal:
// 1. Síncrono - Início
// 5. Síncrono - Fim
// 3. Microtask 1 (Promise)
// 4. Microtask 2 (Promise encadeada)
// 2. Macrotask (setTimeout 0ms)
```

## Boas Práticas no Tratamento de Falhas e Rejeições

O tratamento de falhas em Promises exige atenção tanto no nível de chamadas individuais de rede quanto na prevenção de exceções assíncronas que possam derrubar a aplicação.

### Consumo da Fetch API e Validação de `response.ok`

Na comunicação com serviços HTTP via `fetch()`, a função retorna uma Promise resolvida com o objeto `Response`.

<Aside type="caution" title="Armadilha crítica da Fetch API">
  A Promise gerada por `fetch()` **não é rejeitada em respostas com status de erro HTTP (como 404 Not Found ou 500 Internal Server Error)**. Ela só é rejeitada se houver uma falha estrutural de rede. Portanto, é indispensável validar `response.ok` antes de invocar `.json()`:
</Aside>

O código a seguir apresenta a verificação recomendada para evitar processamento indevido de respostas de erro:

```js title="Consumo correto da Fetch API com validação"
fetch("https://api.github.com/users/octocat")
  .then((response) => {
    if (!response.ok) {
      throw new Error(`Falha HTTP: Status ${response.status} (${response.statusText})`);
    }
    return response.json();
  })
  .then((user) => {
    console.log("Nome do usuário:", user.name);
  })
  .catch((error) => {
    console.error("Erro capturado:", error.message);
  });
```

### Rejeições Não Tratadas (Unhandled Rejections)

Quando uma Promise é rejeitada e nenhum manipulador `.catch()` é encadeado, o motor emite um evento global de **Unhandled Rejection**. No Node.js moderno, rejeições não tratadas encerram o processo com código de erro diferente de zero por padrão:

```js title="Captura global de rejeições no Node.js e no Navegador"
// No ambiente Node.js:
process.on("unhandledRejection", (reason, promise) => {
  console.error("Aviso: Rejeição não tratada detectada:", reason);
});

// No ambiente do Navegador:
window.addEventListener("unhandledrejection", (event) => {
  console.error("Erro assíncrono não tratado:", event.reason);
});
```

## Conexão com Async/Await

A sintaxe `async/await` introduzida no ES2017 é uma camada de conveniência (*syntactic sugar*) construída sobre Promises, permitindo escrever lógica assíncrona com estrutura sequencial:

```js title="Comparativo: Promises com then versus Async/Await"
// Abordagem 1: Encadeamento com .then()
function loadUserThen(id) {
  return fetchUser(id)
    .then((user) => calculateBonus(user))
    .then((bonus) => console.log("Bônus:", bonus))
    .catch((err) => console.error(err.message));
}

// Abordagem 2: Sintaxe com Async/Await (mesmo comportamento subjacente)
async function loadUserAsync(id) {
  try {
    const user = await fetchUser(id);
    const bonus = await calculateBonus(user);
    console.log("Bônus:", bonus);
  } catch (err) {
    console.error(err.message);
  }
}
```

## Promises na Era da Inteligência Artificial

Promises acumulam mais de uma década de estilos sobrepostos: *callbacks* com `error` no primeiro parâmetro, `.then()` encadeado, `new Promise()` em toda função e, por fim, `async/await`. Assistentes de código aprenderam com esse material inteiro, e a resposta que produzem costuma ser uma mistura das quatro épocas na mesma função.

O código gerado funciona. O problema é que ele carrega, quase sempre, um dos dois defeitos clássicos que a comunidade já catalogou: o embrulho desnecessário de algo que já era uma promessa e o tratamento de falhas colocado no elo errado da cadeia.

### O antipadrão do construtor explícito

Ao pedir "uma função que busque o usuário e devolva uma Promise", a resposta mais frequente envolve uma promessa já existente dentro de outra:

```js title="Antipadrão: new Promise em volta de uma promessa"
function getUser(id) {
  return new Promise((resolve, reject) => {
    fetch(`/api/users/${id}`)
      .then((response) => response.json())
      .then((data) => resolve(data))
      .catch((error) => reject(error));
  });
}
```

O `new Promise()` aqui não acrescenta nada: `fetch()` já devolve uma promessa, e o embrulho apenas cria um lugar novo para o erro se perder. Se `response.json()` lançar depois de `resolve()` ter sido chamado, a falha desaparece sem rastro.

A versão equivalente devolve a cadeia diretamente, com o mesmo comportamento e sem o intermediário:

```js title="A mesma função sem o embrulho"
function getUser(id) {
  return fetch(`/api/users/${id}`).then((response) => response.json());
}
```

O construtor `new Promise()` continua tendo um uso legítimo, e é exatamente aquele que o modelo raramente sugere: **converter uma API baseada em *callback* que ainda não devolve promessa**, como `setTimeout` ou uma biblioteca antiga.

```js title="Uso legítimo: adaptar uma API de callback"
const delay = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

await delay(500);
```

A regra de revisão cabe em uma frase: se dentro do `new Promise()` existe um `.then()` ou um `await`, o construtor está sobrando.

### O combinador escolhido sem perguntar

O segundo padrão recorrente aparece quando o pedido envolve várias operações. `Promise.all()` é a resposta automática, mesmo quando o requisito real era outro:

| O que o pedido dizia | Combinador sugerido | Combinador adequado |
| :--- | :--- | :--- |
| "busque os três dados de uma vez" | `Promise.all()` | `Promise.all()`, correto quando todos são obrigatórios. |
| "carregue as notificações de cada serviço" | `Promise.all()` | `Promise.allSettled()`, para não perder tudo se um serviço cair. |
| "use o primeiro que responder" | `Promise.all()` ou `race()` | `Promise.any()`, que ignora as rejeições e espera o primeiro sucesso. |
| "cancele se demorar mais que 2 segundos" | `Promise.all()` com contador | `Promise.race()` entre a operação e um `delay` que rejeita. |

A diferença entre `all` e `allSettled` fica visível quando um dos serviços falha. No primeiro caso, os resultados que já haviam chegado são descartados junto com a rejeição:

```js title="all descarta o parcial, allSettled preserva"
const tasks = [
  Promise.resolve("perfil carregado"),
  Promise.reject(new Error("serviço de pedidos indisponível")),
  Promise.resolve("mensagens carregadas"),
];

try {
  await Promise.all(tasks);
} catch (error) {
  console.log("all:", error.message); // os dois sucessos foram perdidos
}

const results = await Promise.allSettled(tasks);

console.log(results.map((r) => r.status)); // [ 'fulfilled', 'rejected', 'fulfilled' ]
console.log(results.filter((r) => r.status === "fulfilled").length); // 2
```

```bash title="Terminal"
node combinators.js
```

```txt title="Output"
all: serviço de pedidos indisponível
[ 'fulfilled', 'rejected', 'fulfilled' ]
2
```

<Aside type="tip" title="Dica de IA: Descreva o comportamento na falha, não a quantidade de chamadas">
  O elemento que falta no *prompt* quase nunca é técnico: é a regra de negócio da falha. Pedir "busque os três dados em paralelo" leva sempre a `Promise.all()`; descrever o que deve acontecer quando um deles cair leva ao combinador certo.

  **Prompt:** *"Busque perfil, pedidos e mensagens em paralelo. Se um dos três serviços falhar, quero exibir os outros dois e um aviso, em vez de perder a tela inteira. Escolha o combinador de Promise adequado a esse comportamento e explique a escolha."*
</Aside>

### O catch colocado no elo errado

Em uma cadeia longa, a posição do `.catch()` decide quais erros ele enxerga. Assistentes tendem a colocá-lo no meio, logo depois da chamada que parece mais arriscada, e o restante da cadeia fica descoberto.

O trecho abaixo compara as duas posições sobre a mesma cadeia:

```js title="Posição do catch em uma cadeia"
// catch no meio: erros de parseUser e de render passam direto
fetch("/api/users/1")
  .then((response) => response.json())
  .catch((error) => console.error("falha na rede:", error))
  .then((data) => parseUser(data))
  .then((user) => render(user));

// catch no fim: cobre a cadeia inteira, inclusive parseUser e render
fetch("/api/users/1")
  .then((response) => response.json())
  .then((data) => parseUser(data))
  .then((user) => render(user))
  .catch((error) => console.error("falha ao carregar usuário:", error));
```

Há um detalhe adicional que o `catch` no meio esconde: depois de tratar o erro, a cadeia **continua**, e o `.then()` seguinte recebe `undefined` como se tudo tivesse dado certo. É a mesma classe de defeito do `catch` que devolve valor padrão, agora distribuída ao longo de vários elos.

### Armadilhas frequentes em código de Promise gerado por IA

O conjunto de falhas abaixo se repete com frequência suficiente para virar item de revisão:

| Armadilha | Como se manifesta | Como mitigar |
| :--- | :--- | :--- |
| **Construtor explícito desnecessário** | `new Promise()` em volta de `fetch()` ou de outra promessa. | Devolver a cadeia diretamente; o construtor só adapta *callbacks*. |
| **Mistura de `.then()` e `await`** | A mesma função encadeia `.then()` e usa `await` no meio. | Escolher um estilo por função e pedir a reescrita completa. |
| **`.catch()` no meio da cadeia** | Elos posteriores ficam sem tratamento e recebem `undefined`. | Concentrar o tratamento no fim ou usar `try...catch` com `await`. |
| **`Promise.all()` por padrão** | Falha de um item descarta todos os resultados obtidos. | Perguntar o que deve acontecer na falha parcial antes de escolher. |
| **Promessa criada e não aguardada** | A chamada dispara, a função retorna e a rejeição fica órfã. | Guardar a referência e aguardar, ou tratar com `.catch()` explícito. |
| **Rejeição com valor que não é `Error`** | `reject("deu erro")` produz rastro de pilha inútil. | Rejeitar sempre com uma instância de `Error`. |

A promessa órfã **falha em silêncio** até o processo encerrar, e no Node.js atual esse silêncio termina com a aplicação derrubada:

```js title="Rejeição não tratada"
// Sugestão comum quando o pedido é "dispare o envio do e-mail e siga"
sendEmail(user); // promessa rejeitada sem tratamento

// Intenção explícita: seguir adiante, mas registrar a falha
sendEmail(user).catch((error) => console.error("envio falhou:", error.message));
```

### Checklist de revisão antes do merge

Antes de aprovar qualquer código baseado em Promises gerado com auxílio de IA, percorra as verificações abaixo:

1. **Existe `new Promise()` com `.then()` ou `await` dentro?** O construtor está sobrando;
2. **A função mistura `.then()` e `async/await`?** Peça a reescrita inteira em um único estilo;
3. **Onde está o `.catch()`?** Um tratamento no meio da cadeia deixa os elos seguintes descobertos;
4. **O combinador corresponde à regra de falha?** `all`, `allSettled`, `any` e `race` respondem a perguntas diferentes;
5. **Toda promessa criada é aguardada ou tratada?** Chamadas disparadas e esquecidas derrubam o processo quando rejeitam;
6. **As rejeições carregam uma instância de `Error`?** Texto solto em `reject()` chega ao log sem pilha.

A inteligência artificial reduziu o custo de escrever uma cadeia de promessas, mas não alterou em nada o custo de perder uma rejeição no meio dela em produção.

## Resumo e Boas Práticas

A gestão profissional de Promises previne congelamento de threads e falhas silenciosas de rede.

| Prática Recomendada | Motivo Técnico |
| ------------------- | -------------- |
| **Sempre anexar um `.catch()` final** | Evita rejeições não tratadas (*unhandled rejections*) que derrubam processos Node.js. |
| **Retornar Promises em funções** | Garante que quem consome a função consiga utilizar `.then()` ou `await` para compor o fluxo. |
| **Validar `response.ok` em requisições fetch** | O método nativo `fetch()` resolve com sucesso mesmo diante de erros HTTP 404 ou 500. |
| **Evitar o aninhamento de `.then()`** | Retorne a Promise interna para manter a cadeia plana (*flat chain*), melhorando a legibilidade. |
| **Usar `Promise.allSettled()` para tolerância a falhas** | Impede que a falha de um serviço secundário cancele todas as respostas de operações bem-sucedidas. |
| **Preferir `Promise.withResolvers()` no ES2024** | Evita a extração imperativa das funções de resolução para variáveis de escopo externo ao executor. |

O bloco a seguir reúne essas práticas em uma rotina de sincronização de dados com controle de falha e finalização:

```js title="Resumo prático de Promises"
function syncDeviceData(deviceId) {
  return checkServerStatus(true)
    .then((status) => {
      console.log("Status:", status);
      return Promise.allSettled([
        fetchUser(deviceId),
        Promise.resolve({ syncTime: Date.now() }),
      ]);
    })
    .then((results) => {
      const [userResult, syncResult] = results;
      return {
        user: userResult.status === "fulfilled" ? userResult.value : null,
        sync: syncResult.status === "fulfilled" ? syncResult.value : null,
      };
    })
    .catch((error) => {
      console.error("Falha irrecuperável na sincronização:", error.message);
      throw error;
    })
    .finally(() => {
      console.log("Ciclo de sincronização finalizado.");
    });
}
```

## Perguntas de revisão

Pratique e consolide os conceitos fundamentais sobre assincronismo, ciclo de vida de Promises e combinadores respondendo às questões a seguir:

### Conceitos e Estados

**1. O que é o modelo assíncrono em JavaScript e por que ele é indispensável?**

<details>
  <summary>Possível resposta</summary>

  Como o JavaScript executa em uma única thread principal, o modelo assíncrono permite disparar operações demoradas de entrada e saída (como rede e disco) em segundo plano, mantendo a aplicação responsiva sem travar o Event Loop.
</details>

**2. Quais são os 3 estados possíveis de uma Promise e como ocorrem as transições?**

<details>
  <summary>Possível resposta</summary>

  Os estados são `Pending` (pendente/inicial), `Fulfilled` (resolvida/sucesso) e `Rejected` (rejeitada/falha). A Promise transita de `Pending` para um dos estados finais uma única vez, tornando-se imutável em seguida.
</details>

**3. O que é o executor de uma Promise e qual é a sua característica temporal de execução?**

<details>
  <summary>Possível resposta</summary>

  O executor é a função `(resolve, reject) => { ... }` passada para o construtor `new Promise`. Ele é executado de forma síncrona e imediata no momento da criação da instância da Promise.
</details>

**4. Para que serve o método moderno `Promise.withResolvers()` introduzido no ES2024?**

<details>
  <summary>Possível resposta</summary>

  Serve para criar uma Promise retornando diretamente a promessa e as funções `resolve` e `reject` desestruturadas em um objeto, evitando a necessidade de extrair variáveis manualmente de dentro do executor.
</details>

### Encadeamento e Ciclo de Vida

**5. Como funciona o encadeamento (*chaining*) com o método `.then()`?**

<details>
  <summary>Possível resposta</summary>

  Cada chamada a `.then()` retorna uma nova Promise. Se a função executada retornar um valor simples ou outra Promise, o próximo `.then()` da cadeia aguardará e receberá o resultado dessa resolução.
</details>

**6. Qual é a principal vantagem de usar um único `.catch()` ao final da cadeia de Promises?**

<details>
  <summary>Possível resposta</summary>

  O `.catch()` final centraliza o tratamento de falhas, interceptando erros ou rejeições lançadas em qualquer um dos elos anteriores da cadeia de processamento.
</details>

**7. O que acontece com o retorno do método `.finally()` em uma cadeia de Promises?**

<details>
  <summary>Possível resposta</summary>

  O método `.finally()` não recebe argumentos e seu valor retornado é ignorado, repassando o resultado ou erro original da Promise adiante na cadeia, sendo utilizado estritamente para rotinas de limpeza.
</details>

**8. O que é uma rejeição não tratada (*Unhandled Rejection*) e qual o seu risco em Node.js?**

<details>
  <summary>Possível resposta</summary>

  Ocorre quando uma Promise é rejeitada sem nenhum manipulador `.catch()` associado. No Node.js moderno, isso dispara o evento `unhandledRejection` e encerra a aplicação com código de erro fatal por padrão.
</details>

### Combinadores e Event Loop

**9. Qual é a diferença de comportamento entre `Promise.all()` e `Promise.allSettled()`?**

<details>
  <summary>Possível resposta</summary>

  `Promise.all()` falha imediatamente ao encontrar a primeira rejeição na lista (*fail-fast*). Já `Promise.allSettled()` aguarda todas as Promises serem liquidadas, retornando um array de objetos com o status e o valor/razão de cada uma.
</details>

**10. Em que cenários é recomendado utilizar o combinador `Promise.any()`?**

<details>
  <summary>Possível resposta</summary>

  Quando temos múltiplas fontes alternativas para o mesmo dado (como servidores espelho ou réplicas de cache) e desejamos prosseguir assim que a primeira fonte responder com sucesso, falhando apenas se todas rejeitarem.
</details>

**11. Qual é a prioridade da Fila de Microtarefas (*Microtask Queue*) em relação aos temporizadores de Macrotarefas?**

<details>
  <summary>Possível resposta</summary>

  A fila de microtarefas (onde rodam os callbacks de Promises) tem prioridade absoluta sobre a fila de macrotarefas (`setTimeout`), sendo esvaziada por completo antes que qualquer temporizador seja executado.
</details>

**12. Por que requisições HTTP feitas com `fetch()` não caem no bloco `.catch()` em status 404 ou 500?**

<details>
  <summary>Possível resposta</summary>

  Porque o método `fetch()` só rejeita a Promise em caso de falha física de rede. Respostas HTTP válidas recebidas do servidor resolvem com sucesso, exigindo que a aplicação verifique `response.ok`.
</details>
