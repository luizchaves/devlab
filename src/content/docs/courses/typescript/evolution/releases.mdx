O **TypeScript** não é padronizado por um comitê internacional como o JavaScript. Ele é um produto mantido pela Microsoft, publicado em ciclo próprio, e as decisões de linguagem seguem um conjunto de objetivos de projeto declarados publicamente. Conhecer esse histórico ajuda a entender por que certos recursos existem, por que outros foram recusados e a partir de qual versão cada sintaxe deste guia está disponível.

Materiais: [slides do tópico](../../../../slides/courses/typescript/evolution/releases/) e [mapa mental](../../../../mindmaps/courses/typescript/evolution/releases/)

## Objetivo

Compreender como o TypeScript evolui, quais recursos cada linha de versão trouxe desde o lançamento em 2012 e o que muda na transição do 5.x para o 6.0 e para o compilador nativo do 7.0.

## Como o TypeScript Evolui?

O ciclo de lançamentos é aproximadamente trimestral. Cada versão passa por uma fase *beta*, uma *release candidate* e a publicação estável no npm, sempre com notas de versão detalhadas. A numeração segue `major.minor`, mas não é SemVer estrito: uma versão *minor* pode introduzir erros de tipo novos em código que antes compilava, porque uma verificação mais precisa é considerada correção, não quebra.

As decisões de linguagem seguem os objetivos de projeto publicados no repositório, dos quais três explicam a maior parte das recusas de proposta:

- **Alinhamento com o ECMAScript**: sintaxe nova de execução vem do TC39, não do TypeScript. Recursos como *optional chaining* e campos privados só entraram depois de avançarem no comitê do JavaScript.
- **Apagamento completo dos tipos**: o sistema de tipos não pode influenciar o comportamento em tempo de execução. É por isso que não existe verificação de tipo em runtime nem sobrecarga de método baseada em tipos.
- **Solidez pragmática, não formal**: o compilador aceita conscientemente algumas construções inseguras, como a bivariância de parâmetros de método, quando exigir a forma correta atrapalharia mais do que ajudaria.

<Aside type="note" title="TypeScript não define sintaxe de execução">
  A única exceção histórica relevante são os `enum` e os `namespace`, criados antes de o ECMAScript ter módulos e uniões literais. Hoje eles são considerados legado pela própria equipe, e o guia usa união literal e `as const` no lugar deles.
</Aside>

## Visão Geral da Linha do Tempo

A tabela reúne as versões que mudaram de forma perceptível a maneira de escrever TypeScript. Versões intermediárias, focadas em desempenho e correções, ficaram de fora:

| Versão | Ano | Principais destaques |
| :--- | :--- | :--- |
| **1.0** | 2014 | Anotações de tipo, `interface`, generics, `enum`, `namespace`, arquivos `.d.ts`. |
| **2.0** | 2016 | `strictNullChecks`, uniões discriminadas, `never`, `readonly`, tipos literais. |
| **2.8** | 2018 | Tipos condicionais, `infer`, `Exclude`, `Extract`, `ReturnType`. |
| **3.0** | 2018 | Tuplas em parâmetros rest, `unknown`, referências de projeto. |
| **3.7** | 2019 | *Optional chaining* (`?.`), *nullish coalescing* (`??`), funções de asserção. |
| **4.0** | 2020 | Tuplas variádicas, elementos de tupla nomeados, `catch` com `unknown`. |
| **4.1** | 2020 | *Template literal types*, remapeamento de chaves com `as`. |
| **4.3** | 2021 | `override`, acessadores com tipos distintos para leitura e escrita. |
| **5.0** | 2023 | Decorators do padrão ECMAScript, `const` em parâmetro de tipo, `satisfies`, `verbatimModuleSyntax`. |
| **5.2** | 2023 | `using` e `await using` para descarte determinístico de recursos. |
| **5.4** | 2024 | Estreitamento preservado dentro de closures, `NoInfer`. |
| **5.5** | 2024 | Predicados de tipo inferidos, verificação de grupos em expressões regulares. |
| **5.8** | 2025 | `erasableSyntaxOnly`, alinhamento com a remoção de tipos do Node.js. |
| **5.9** | 2025 | `import defer`, `module: node20`. |
| **6.0** | — | Versão de transição: `strict` por padrão, remoção do alvo ES5, depreciações preparatórias. |
| **7.0** | — | Compilador nativo portado para Go, com ganho expressivo de desempenho. |

## TypeScript 1.x — A Fundação

A primeira linha estável definiu o vocabulário que o guia inteiro usa. As anotações de tipo com dois-pontos, o `interface` para descrever a forma de um objeto, os generics com `<T>` e os arquivos de declaração `.d.ts` nasceram aqui e continuam praticamente iguais.

O exemplo abaixo já compilaria no TypeScript 1.0, e continua válido hoje:

```ts title="Sintaxe da primeira linha estável"
interface User {
  id: number;
  name: string;
}

function first<T>(list: T[]): T {
  return list[0];
}

const user: User = { id: 1, name: "Ana" };
console.log(first([user]).name); // Ana
```

Dessa mesma época vêm o `enum` e o `namespace`, discutidos em [Tipos Básicos](../../basics/types/) e em [Módulos e Declarações](../../tooling/modules/). Os dois resolviam problemas que o JavaScript ainda não resolvia, e hoje têm substitutos melhores na própria linguagem.

## TypeScript 2.x — O Rigor Entra em Cena

A versão 2.0 é o divisor de águas do sistema de tipos, porque introduziu o `strictNullChecks`. Antes dele, `null` e `undefined` pertenciam a todos os tipos, e o compilador aceitava silenciosamente o erro mais comum de JavaScript.

A diferença entre os dois modos aparece na mesma função:

```ts title="Efeito do strictNullChecks"
function upper(text: string): string {
  return text.toUpperCase();
}

// Sem strictNullChecks: compila e quebra em runtime.
// Com strictNullChecks: erro de compilação.
upper(null);
```

A mesma linha trouxe as **uniões discriminadas**, o tipo `never`, o modificador `readonly` e os tipos literais de string, que juntos formam a base do estreitamento estudado em [Narrowing](../../basics/narrowing/).

A versão 2.8 fechou o ciclo com os **tipos condicionais** e a palavra-chave `infer`, o mecanismo que permitiu escrever a biblioteca de utilitários da linguagem:

```ts title="Tipos condicionais e infer, introduzidos no 2.8"
type ElementOf<T> = T extends (infer U)[] ? U : never;

type Names = ElementOf<string[]>; // string
```

Sem esse recurso, os utilitários vistos em [Utility Types](../../advanced/utility-types/) não existiriam.

## TypeScript 3.x — `unknown` e Projetos Compostos

A linha 3.x concentrou-se em tuplas e em organização de código. As tuplas passaram a poder ser espalhadas em parâmetros rest, o que tornou possível tipar funções variádicas com precisão.

O recurso mais importante para o dia a dia foi o tipo `unknown`, a alternativa segura ao `any`:

```ts title="unknown, introduzido no 3.0"
const data: unknown = JSON.parse('{"name":"Ana"}');

// data.name;  // erro: é preciso estreitar antes

if (typeof data === "object" && data !== null && "name" in data) {
  console.log(data.name);
}
```

A versão 3.7 alinhou a linguagem com o ECMAScript 2020, adotando *optional chaining* e *nullish coalescing* assim que as propostas amadureceram no TC39, e acrescentou as funções de asserção com `asserts`.

## TypeScript 4.x — Tipos como Linguagem

Se a linha 2.x deu rigor ao sistema de tipos, a 4.x o transformou em uma linguagem de manipulação de dados por si só. As **tuplas variádicas** do 4.0 permitiram compor assinaturas a partir de outras assinaturas.

O salto mais visível veio no 4.1, com os *template literal types*:

```ts title="Template literal types, introduzidos no 4.1"
type Event = "click" | "focus";
type Handler = `on${Capitalize<Event>}`;
// "onClick" | "onFocus"
```

Na mesma versão entrou o remapeamento de chaves com `as` dentro de tipos mapeados, combinação explorada em [Manipulação de Tipos](../../advanced/type-manipulation/). O 4.3 acrescentou o modificador `override`, que faz o compilador reclamar quando um método deixa de sobrescrever algo na classe base.

<Aside type="tip" title="A partir daqui os tipos viram programação">
  Tipos condicionais, `infer`, tipos mapeados e template literals formam um pequeno sistema de computação em tempo de compilação. É poderoso e vicia: a página [Manipulação de Tipos](../../advanced/type-manipulation/) tem uma seção inteira sobre quando parar.
</Aside>

## TypeScript 5.0 — Decorators, `const` e `satisfies`

A versão 5.0 marcou a adoção dos **decorators do padrão ECMAScript**, substituindo a implementação experimental que dependia da flag `experimentalDecorators` desde 2015. As duas sintaxes convivem, mas a nova é a que segue a proposta do TC39.

Para o guia, o recurso mais usado do 5.0 é o operador `satisfies`, que verifica a compatibilidade sem alargar o tipo inferido:

```ts title="satisfies, introduzido no 5.0"
const palette = {
  primary: "#42a5f5",
  danger: "#e53935",
} satisfies Record<string, string>;

palette.primary.toUpperCase(); // continua sendo string literal, não string
```

Também entraram os parâmetros de tipo `const`, que preservam literais na inferência, e o `verbatimModuleSyntax`, que tornou previsível o que o compilador emite em relação a `import type`.

A versão 5.2 acrescentou o descarte determinístico de recursos com `using` e `await using`, acompanhando a proposta de *explicit resource management* do TC39.

## TypeScript 5.4 a 5.9 — Inferência Mais Fina e ESM

A segunda metade da linha 5.x concentrou-se em fazer o compilador entender melhor o código que já era escrito. O 5.4 passou a preservar o estreitamento dentro de closures criadas depois da verificação, eliminando uma queixa antiga.

O 5.5 trouxe os **predicados de tipo inferidos**, que dispensam a anotação explícita em funções de filtro:

```ts title="Predicado inferido, introduzido no 5.5"
const values = [1, undefined, 3];

// Antes do 5.5, era preciso escrever: (v): v is number => v !== undefined
const numbers = values.filter((v) => v !== undefined);
// number[], sem anotação
```

As versões 5.8 e 5.9 olharam para fora da linguagem. O `erasableSyntaxOnly` proíbe a sintaxe que não é apagável, como `enum` e `namespace`, para que os arquivos funcionem com a remoção de tipos nativa do Node.js, assunto de [Execução e Build](../../tooling/runtime/). O 5.9 acompanhou o `import defer` do ECMAScript e acrescentou o alvo de módulos `node20`.

## TypeScript 6.0 — A Versão de Transição

O 6.0 é declaradamente uma ponte para o 7.0. Ele mantém compatibilidade de API com o 5.9 e não muda o que você sabe sobre a linguagem, mas ajusta padrões e retira opções que não sobreviverão à próxima linha.

As mudanças de padrão são as que mais afetam projetos existentes:

| Opção | Padrão até o 5.9 | Padrão no 6.0 |
| :--- | :--- | :--- |
| `strict` | `false` | `true` |
| `module` | `commonjs` | `esnext` |
| `target` | `es5` | versão ES do ano corrente |
| `noUncheckedSideEffectImports` | `false` | `true` |
| `libReplacement` | `true` | `false` |

Junto delas vem um conjunto de depreciações que reconhece o desaparecimento dos ambientes legados:

- **`target: es5`**: com a aposentadoria do Internet Explorer, o alvo mínimo passa a ser `es2015`. Quem ainda precisa de saída ES5 deve usar um compilador externo.
- **`downlevelIteration`**: só tinha efeito na emissão ES5, e perde a razão de existir junto dela.
- **`moduleResolution: node` (`node10`)**: representa o Node.js de uma década atrás. A migração é para `nodenext`, ao mirar o Node.js diretamente, ou `bundler`, ao usar empacotador ou Bun.
- **`module` com `amd`, `umd`, `systemjs` e `none`**: formatos anteriores aos módulos nativos, hoje substituídos por ESM, *import maps* e empacotadores.

Durante a transição, `"ignoreDeprecations": "6.0"` silencia esses avisos. É um prazo, não uma solução: o 7.0 remove as opções de vez.

<Aside type="caution" title="Este guia usa a linha 5.x">
  Os exemplos e as configurações deste guia assumem TypeScript 5.x, onde `strict` precisa ser ativado explicitamente no `tsconfig.json`. Sob o 6.0, `strict` já vem ligado e várias opções descritas em [tsconfig.json](../../tooling/tsconfig/) mudam de padrão. Confirme a sua versão com `npx tsc --version` antes de copiar uma configuração.
</Aside>

## TypeScript 7.0 — O Compilador Nativo em Go

O 7.0 é a reescrita do compilador em **Go**, distribuída sob o nome `tsgo` durante o desenvolvimento. O objetivo declarado é desempenho: verificação de tipos e inicialização do servidor de linguagem várias vezes mais rápidas em bases grandes, sem mudar a linguagem que você escreve.

Três consequências práticas importam para quem planeja a migração:

- **A linguagem não muda.** Os tipos, a sintaxe e a semântica de verificação continuam os mesmos. O que muda é o programa que faz a verificação.
- **As opções depreciadas no 6.0 somem.** Não há `ignoreDeprecations` no 7.0, então o caminho recomendado é atualizar para o 6.0, corrigir os avisos e só então avançar.
- **A API de compilador é reescrita.** Ferramentas que dependem da API do TypeScript, como transformadores personalizados e alguns plugins, precisam de adaptação.

## Adoção e Suporte nos Runtimes Modernos

O TypeScript não é executado diretamente por navegador nenhum, mas o cenário de execução mudou bastante desde 2023. O Node.js passou a remover tipos nativamente, o Deno e o Bun executam `.ts` desde sempre, e os empacotadores modernos apagam os tipos sem verificar.

A tabela resume onde cada ambiente está hoje:

| Ambiente | Executa `.ts` diretamente? | Verifica os tipos? |
| :--- | :--- | :--- |
| Navegador | Não | Não |
| Node.js 22+ | Sim, removendo tipos | Não |
| Deno | Sim | Sim, por padrão |
| Bun | Sim | Não |
| `tsx` e empacotadores | Sim | Não |
| `tsc --noEmit` | Não executa | Sim |

O padrão que atravessa a tabela é sempre o mesmo: **executar é rápido porque ninguém verifica**. A verificação continua sendo um passo separado, discutido em [Execução e Build](../../tooling/runtime/), e é ela que precisa rodar na integração contínua.

<Aside type="caution" title="Dica de IA: confirme a versão antes de aceitar a sugestão">
  Assistentes de código respondem a partir de um corpo de texto com data de corte e costumam errar em duas direções opostas: sugerem `satisfies`, `using` ou predicados inferidos em um projeto preso a uma versão antiga, ou insistem em anotar manualmente o que o compilador já infere desde o 5.5.

  **Prompt:** *"A partir de qual versão do TypeScript este recurso existe? Se a minha versão for anterior, mostre a alternativa equivalente que compila nela."*
</Aside>
