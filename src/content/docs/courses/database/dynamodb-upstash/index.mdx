Este tópico apresenta o panorama de bancos de dados chave-valor gerenciados na nuvem (*Managed Key-Value DBaaS*), com ênfase no **Amazon DynamoDB** (banco NoSQL de hiperescala e latência de dígito único de milissegundo), no **Upstash Redis** (Redis serverless otimizado para ambientes Edge/Serverless via HTTP/REST) e no **AWS ElastiCache** (clusters gerenciados de cache in-memory em redes privadas).

---

## Objetivo

Compreender a arquitetura, o modelo de modelagem baseada em chaves de partição e as estratégias de escalabilidade de bancos chave-valor na nuvem. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o funcionamento da chave de partição (*Partition Key - PK*) e chave de ordenação (*Sort Key - SK*) no particionamento do DynamoDB.
- Diferenciar os modos de capacidade provisionada (*Provisioned Throughput*) e sob demanda (*On-Demand Serverless*).
- Descrever o ecossistema de índices secundários globais (*GSI*) e locais (*LSI*) no DynamoDB.
- Compreender a integração do Upstash Redis em arquiteturas *Edge Computing* (Cloudflare Workers, Vercel Edge Functions) via API REST HTTP.
- Avaliar quando empregar um banco de cache em memória (ElastiCache/Upstash) versus um armazenamento persistente de chave-valor (DynamoDB).

## O Paradigma Chave-Valor em Hiperescala

Bancos chave-valor em nuvem resolvem o gargalo de concorrência massiva desacoplando leituras e escritas por nós de armazenamento independentes calculados via funções de *hash*:

<Mermaid title="Particionamento de dados baseado em Hash Key no Amazon DynamoDB">
{`
flowchart LR
    Client["Aplicação / API"] -->|"PUT / GET (PK = user#123)"| Router["Request Router (DynamoDB Engine)"]

    subgraph StorageNodes ["Partições Físicas Independentes (SSD NVMe)"]
        Router -->|"Hash(PK) = 0x0A"| P1[("Partição 1 (IDs 0x00 - 0x3F)")]
        Router -->|"Hash(PK) = 0x8F"| P2[("Partição 2 (IDs 0x40 - 0x7F)")]
        Router -->|"Hash(PK) = 0xC2"| P3[("Partição 3 (IDs 0x80 - 0xFF)")]
    end
`}
</Mermaid>

A previsibilidade de latência (geralmente entre 1ms e 9ms) decorre do fato de que o motor nunca realiza varreduras completas em disco para buscas por chave primária.

## Amazon DynamoDB: Persistência e Single-Table Design

O **Amazon DynamoDB** é um serviço NoSQL totalmente gerenciado da AWS projetado para cargas de trabalho de qualquer escala com tolerância a falhas multi-AZ automática:

<Mermaid title="Arquitetura de recursos do Amazon DynamoDB">
{`
flowchart TD
    App["Microsserviços AWS Lambda / ECS"] --> DDB[("Tabela DynamoDB (PK + SK)")]

    DDB --> GSI["Global Secondary Index (GSI)"]
    DDB --> Streams["DynamoDB Streams (Change Data Capture)"]
    DDB --> TTL["Time-to-Live (Expiração Automática Gratuita)"]

    Streams --> Lambda["Função Lambda (Processamento em Tempo Real)"]
`}
</Mermaid>

Os principais mecanismos do DynamoDB incluem:

1. **Chave Primária Composta (PK + SK)**: Permite relacionamentos de 1:N dentro de uma mesma partição física, viabilizando o padrão *Single-Table Design* onde múltiplas entidades coabitam a mesma tabela.
2. **DynamoDB Streams**: Captura sequencial de todas as alterações (inserções, atualizações e exclusões) em um fluxo de eventos em tempo real, acionando reações orientadas a eventos via AWS Lambda.
3. **Time-to-Live (TTL)**: Remove itens expirados de forma assíncrona sem consumir unidades de leitura ou escrita (*RCU/WCU*), ideal para carrinhos de compras e sessões de usuários temporárias.
4. **Capacidade On-Demand vs. Provisionada**: Permite pagar exatamente pelo número de requisições de leitura e escrita efetuadas, ou contratar capacidade fixa com auto-scaling para cargas previsíveis.

## Upstash Redis: Redis Serverless para a Borda

Em arquiteturas serverless modernas (Next.js no Vercel, Cloudflare Workers), manter pools de conexões TCP persistentes com o Redis tradicional é inviável devido ao ciclo de vida efémero das funções. O **Upstash Redis** resolve essa limitação expondo o protocolo Redis nativo e uma **API REST HTTP**:

<Mermaid title="Comunicação HTTP vs TCP com Upstash Redis em Edge Functions">
{`
flowchart LR
    subgraph Edge ["Edge Functions / Lambdas"]
        F1["Edge Worker 1"]
        F2["Edge Worker 2"]
        F3["Edge Worker 3"]
    end

    subgraph Upstash ["Upstash Redis Serverless"]
        Gateway["HTTP REST API Gateway (Sem TCP Pool)"]
        Engine[("Motor Redis em Memória Multi-Zona")]
        Gateway --> Engine
    end

    F1 -->|"fetch('https://.../set/key')"| Gateway
    F2 -->|"fetch('https://.../get/key')"| Gateway
    F3 -->|"fetch('https://.../incr/limit')"| Gateway
`}
</Mermaid>

Os diferenciais do Upstash abrangem:

- **Conexões sem estado (*Stateless HTTP*)**: As funções realizam requisições HTTP normais (`fetch`), eliminando o esgotamento de conexões (*Connection Exhaustion*).
- **Scale-to-Zero Real**: Cobrança baseada no número de comandos executados (ex: \$0,20 por 100.000 comandos), sem custo fixo de instâncias ociosas.
- **Ratelimiting e Filas na Borda**: SDKs prontos para limitar requisições de APIs (*Rate Limiting*) e gerenciar filas de mensagens (*Upstash QStash*).

## Aceleração e Cache: DynamoDB, DAX e Amazon ElastiCache

Ao desenhar arquiteturas de altíssima vazão em nuvem, surge frequentemente a dúvida sobre como acelerar leituras: usar o banco diretamente, adicionar **DAX** ou acoplar **Amazon ElastiCache**?

<Mermaid title="Padrões arquiteturais: DAX (Inline Cache) vs ElastiCache (Look-Aside Cache)">
{`
flowchart TD
    subgraph PatternDAX ["1. DAX: Cache em Linha (Inline / Write-Through)"]
        direction LR
        App1["Aplicação (SDK DynamoDB)"] -->|"1. GetItem / Query (Microssegundos)"| DAX["DAX Cluster (In-Memory)"]
        DAX -->|"2. Cache Miss / Write-Through"| DDB1[("Amazon DynamoDB (SSD)")]
    end

    subgraph PatternElastiCache ["2. ElastiCache: Cache Desacoplado (Look-Aside / Cache-Aside)"]
        direction TB
        App2["Aplicação"] -->|"1. Verifica Chave"| EC["ElastiCache (Redis / Valkey)"]
        App2 -->|"2. Se Cache Miss, busca no Banco"| DDB2[("DynamoDB / PostgreSQL")]
        App2 -->|"3. Atualiza Cache com TTL"| EC
    end
`}
</Mermaid>

A escolha entre DAX e ElastiCache baseia-se no modelo de integração e na complexidade das estruturas de dados:

### 1. Amazon DynamoDB (Banco Persistente)
É a camada primária de persistência e fonte da verdade (*Source of Truth*). Oferece durabilidade garantida em 3 zonas de disponibilidade (Multi-AZ) e latência consistente de 1 dígito de milissegundo (entre 4ms e 9ms) para qualquer volume de dados.

### 2. DAX - DynamoDB Accelerator (Cache Inline Especializado)
O **DAX** é um cache em memória totalmente gerenciado projetado especificamente para o DynamoDB:

- **Transparência de Código (*Drop-in Replacement*)**: A aplicação utiliza o mesmo SDK do DynamoDB, alterando apenas o endpoint de conexão para o cluster DAX. Nenhuma lógica de *cache-aside* precisa ser escrita pelo desenvolvedor.
- **Latência em Microssegundos**: Reduz o tempo de resposta de milissegundos para sub-milissegundos (~100µs a 200µs) para leituras repetitivas (*Read-Heavy*) e picos de tráfego em chaves populares (*Hot Keys*).
- **Gerenciamento Automático**: O DAX atualiza seu cache interno automaticamente durante operações de escrita (*Write-Through*).

### 3. Amazon ElastiCache (Cache Look-Aside Genérico)
O **ElastiCache** (Redis, Valkey ou Memcached) atua como um armazenamento em memória desacoplado e de propósito geral:

- **Estruturas de Dados Avançadas**: Permite usar recursos nativos do Redis como *Sorted Sets* (para placares em tempo real e rankings), *Hashes*, *Bitmaps* e *Pub/Sub*, que não existem no DAX.
- **Agregação Multi-Banco**: Pode cachear resultados agregados que combinam dados do DynamoDB, PostgreSQL, MySQL e APIs externas de terceiros na mesma chave.
- **Padrão Cache-Aside**: A aplicação é responsável por gerenciar manualmente a verificação de cache, a busca no banco primário em caso de falha (*cache miss*) e a expiração com TTL.

## Comparativo: DynamoDB vs. DAX vs. ElastiCache vs. Upstash

A tabela abaixo sintetiza os papéis dos principais motores chave-valor e cache em nuvem:

| Característica | Amazon DynamoDB | DynamoDB Accelerator (DAX) | AWS ElastiCache (Redis) | Upstash Redis |
| :--- | :--- | :--- | :--- | :--- |
| **Papel Arquitetural** | Banco NoSQL persistente primário | Cache *Inline* dedicado ao DynamoDB | Cache *Look-Aside* genérico em VPC | Cache *Serverless* para Edge/HTTP |
| **Latência Típica** | 4ms a 9ms (Milissegundos) | 100µs a 200µs (Microssegundos) | 200µs a 800µs (Microssegundos) | 10ms a 30ms (HTTP Edge) / 1ms (TCP) |
| **Integração na Aplicação** | SDK padrão AWS DynamoDB | Mesmo SDK DynamoDB (troca de endpoint) | SDK Redis nativo com lógica Cache-Aside | SDK REST HTTP (`fetch`) ou Redis |
| **Estruturas Suportadas** | Documentos JSON, Chaves PK/SK | Apenas operações de Item/Query DynamoDB | Sorted Sets, Hashes, Lists, Pub/Sub | Estruturas Redis completas |
| **Fonte de Dados** | Próprio armazenamento SSD | Exclusivo para tabelas DynamoDB | Qualquer banco (SQL, NoSQL, APIs) | Qualquer aplicação Web / Serverless |

## Quando usar, e quando não usar?

A seleção da tecnologia chave-valor deve considerar persistência, tempo de resposta e topologia de rede:

| Cenário | Escolha | Por quê |
| :--- | :--- | :--- |
| Banco de dados primário serverless com milhões de acessos simultâneos por chave | **Amazon DynamoDB** | Alta disponibilidade multi-AZ, latência constante independente do volume de dados. |
| Controle de taxa (*Rate Limiting*) e sessões em rotas serverless / Edge | **Upstash Redis** | Acesso via HTTP `fetch` sem manter conexões TCP ativas, precificação serverless. |
| Cache de segundo nível de alta frequência para acelerar consultas PostgreSQL/MySQL | **[Redis Nativo](../redis/) / AWS ElastiCache** | Latência de microssegundos em memória dentro da mesma rede virtual (VPC). |
| Consultas com relacionamentos dinâmicos (*JOINs*), agregações analíticas e ordenações variáveis | **[PostgreSQL](../postgresql/) ou [Aurora](../rds-aurora/)** | Flexibilidade relacional, chaves estrangeiras e índices B-Tree compostos. |

## Perguntas de revisão

<details>
<summary>1. O que é o fenômeno de "Hot Partition" no DynamoDB e como preveni-lo?</summary>
Uma *Hot Partition* ocorre quando uma chave de partição específica recebe uma concentração desproporcional de tráfego de leitura ou escrita, excedendo os limites físicos da partição (1.000 WCU ou 3.000 RCU). Para preveni-la, deve-se projetar chaves com alta cardinalidade (como UUIDs ou combinações de ID + data) ou aplicar técnicas de *write sharding* (adicionando um sufixo aleatório à chave).
</details>

<details>
<summary>2. Como o DynamoDB garante transações atômicas entre múltiplos itens?</summary>
O DynamoDB oferece a operação `TransactWriteItems`, que permite executar até 100 ações de gravação/atualização de forma atômica em itens de partições diferentes com garantia *All-or-Nothing*, consumindo o dobro de unidades de capacidade de escrita.
</details>
