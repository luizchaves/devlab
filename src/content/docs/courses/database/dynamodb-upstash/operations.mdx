A modelagem e operação de bancos chave-valor em nuvem exige padrões arquiteturais especializados. Enquanto bancos relacionais normalizam dados em dezenas de tabelas com `JOINs`, o **Amazon DynamoDB** atinge escala extrema através do **Single-Table Design** e do **DynamoDB Streams**. No ecossistema de borda, o **Upstash** viabiliza controle de taxa (*Rate Limiting*) instantâneo com algoritmos de janela deslizante.

---

## Objetivo

Dominar as técnicas avançadas de modelagem em tabela única, criação de índices secundários, processamento reativo de eventos e limitação de requisições na borda. Ao final do tópico, o leitor deve ser capaz de:

- Modelar entidades heterogêneas (Usuários, Pedidos e Itens) na mesma tabela através do padrão *Single-Table Design*.
- Criar e consultar Índices Secundários Globais (*GSIs*) para habilitar novos padrões de acesso.
- Processar alterações em tempo real via *DynamoDB Streams* conectado a funções AWS Lambda.
- Habilitar o recurso de *Time-to-Live (TTL)* para expiração automática de dados sem custos de capacidade.
- Implementar limitação de requisições (*Rate Limiting*) com o pacote `@upstash/ratelimit`.

## Single-Table Design no DynamoDB

No DynamoDB, criar múltiplas tabelas e fazer consultas em cascata gera sobrecarga de rede e custos elevados. O padrão **Single-Table Design** consolida todas as entidades do sistema em uma única tabela utilizando chaves genéricas (`PK` e `SK`):

<Mermaid title="Exemplo de Single-Table Design com entidades heterogêneas">
{`
flowchart TD
    subgraph SingleTable ["Tabela Única do DynamoDB"]
        Row1["PK: 'USER#ana' | SK: 'METADATA' | Nome: 'Ana Silva', Email: 'ana@dev.io'"]
        Row2["PK: 'USER#ana' | SK: 'ORDER#2026-001' | Total: 450.00, Status: 'PAGO'"]
        Row3["PK: 'USER#ana' | SK: 'ORDER#2026-002' | Total: 120.00, Status: 'PENDENTE'"]
        Row4["PK: 'ORDER#2026-001' | SK: 'ITEM#LIVRO_JS' | Quantidade: 1, Preco: 80.00"]
    end
`}
</Mermaid>

Com essa estrutura:
- Para buscar o usuário e todos os seus pedidos de uma só vez: `Query(PK = 'USER#ana', SK begins_with 'ORDER#')` — resolvido em **uma única requisição HTTP**.
- Para buscar apenas o perfil do usuário: `GetItem(PK = 'USER#ana', SK = 'METADATA')`.

## Global Secondary Indexes (GSI)

Quando você precisa consultar dados por um atributo que não faz parte da chave primária original (ex: buscar um pedido pelo seu código `ORDER#2026-001` sem saber qual usuário o comprou), cria-se um **Global Secondary Index (GSI)**:

<Mermaid title="Inversão de chaves com Global Secondary Index (GSI)">
{`
flowchart LR
    subgraph BaseTable ["Tabela Base"]
        B1["PK: USER#ana | SK: ORDER#2026-001 | Status: PAGO"]
    end

    subgraph GSI1 ["GSI-1 (Chaves Invertidas)"]
        G1["GSI1_PK: ORDER#2026-001 | GSI1_SK: USER#ana | Total: 450.00"]
    end

    B1 -.->|"Replicação Assíncrona Automática"| G1
`}
</Mermaid>

O GSI mantém uma partição separada atualizada de forma eventualmente consistente sem impactar as gravações da tabela principal.

## Arquitetura Orientada a Eventos com DynamoDB Streams

O **DynamoDB Streams** captura todas as operações de escrita (inserções, atualizações e exclusões) em um log estritamente ordenado e aciona funções AWS Lambda instantaneamente:

<Mermaid title="Pipeline de processamento com DynamoDB Streams e AWS Lambda">
{`
flowchart TD
    App["API"] -->|"1. Salva Pedido"| DDB[("Tabela DynamoDB")]
    DDB -->|"2. Emite Evento de CDC"| Stream["DynamoDB Stream"]
    Stream -->|"3. Aciona em Lote"| Lambda["AWS Lambda (Processador)"]
    Lambda -->|"4. Envia Email / Atualiza Cache"| Services["Notificações / Upstash"]
`}
</Mermaid>

## Aceleração com DAX vs Caching Estruturado com ElastiCache

Ao operar tabelas DynamoDB com picos massivos de leitura, a equipe pode escolher entre duas abordagens práticas de aceleração:

### 1. Aceleração Transparente com DAX (Inline Cache)
O **DAX** elimina a necessidade de gerenciar chaves e expirações manualmente. A aplicação utiliza o SDK do DynamoDB acoplado ao cliente DAX:

```typescript title="dax-example.ts: Leitura acelerada com DAX Client em Node.js"
import AmazonDaxClient from 'amazon-dax-client';
import AWS from 'aws-sdk';

// Cria o cliente apontando para o cluster DAX dentro da VPC
const dax = new AmazonDaxClient({
  endpoints: ['dax-cluster.m7q.dax-clusters.us-east-1.amazonaws.com:8111'],
  region: 'us-east-1',
});

const ddbDocClient = new AWS.DynamoDB.DocumentClient({ service: dax });

// A consulta executa em microssegundos se o item estiver em cache (Cache Hit)
async function getProduct(productId: string) {
  const result = await ddbDocClient.get({
    TableName: 'Catalog',
    Key: { PK: `PRODUCT#${productId}`, SK: 'METADATA' },
  }).promise();

  return result.Item;
}
```

### 2. Padrão Cache-Aside com ElastiCache (Redis)
Quando o sistema necessita de estruturas de dados ricas (como ranqueamentos com `ZREVRANGE` ou contadores em tempo real), adota-se o padrão *Cache-Aside* com o ElastiCache:

```typescript title="cache-aside.ts: Padrão Cache-Aside combinando Redis e DynamoDB"
import { DynamoDBClient, GetItemCommand } from '@aws-sdk/client-dynamodb';
import Redis from 'ioredis';

const redis = new Redis(process.env.ELASTICACHE_PRIMARY_ENDPOINT);
const ddb = new DynamoDBClient({ region: 'us-east-1' });

async function getUserProfile(userId: string) {
  const cacheKey = `user:profile:${userId}`;

  // 1. Tenta recuperar do ElastiCache (Redis)
  const cachedData = await redis.get(cacheKey);
  if (cachedData) {
    return JSON.parse(cachedData); // Cache Hit (Microssegundos)
  }

  // 2. Cache Miss: Busca no DynamoDB
  const response = await ddb.send(new GetItemCommand({
    TableName: 'AppSingleTable',
    Key: { PK: { S: `USER#${userId}` }, SK: { S: 'PROFILE' } },
  }));

  if (response.Item) {
    // 3. Popula o cache com TTL de 1 hora (3600 segundos)
    await redis.setex(cacheKey, 3600, JSON.stringify(response.Item));
  }

  return response.Item;
}
```

## Controle de Taxa na Borda (Upstash Rate Limiting)

Para proteger APIs públicas contra abusos e ataques de negação de serviço (*DDoS*), utiliza-se o **Upstash Rate Limit** com o algoritmo *Sliding Window*:

```typescript
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(20, '10 s'), // Permite 20 requisições a cada 10 segundos
  analytics: true,
});

export async function handleRequest(ip: string) {
  const { success, limit, remaining, reset } = await ratelimit.limit(ip);

  if (!success) {
    return {
      status: 429,
      body: 'Limite de requisições excedido. Tente novamente em alguns segundos.',
    };
  }

  return { status: 200, remaining };
}
```

## Perguntas de revisão

<details>
<summary>1. O que acontece se uma partição do DynamoDB sofrer sobrecarga (Hot Key)?</summary>
Se uma chave de partição específica receber mais de 1.000 gravações por segundo ou 3.000 leituras por segundo, o DynamoDB pode emitir o erro `ProvisionedThroughputExceededException`. A solução arquitetural é aplicar técnicas de *Write Sharding* (adicionando um sufixo randômico à PK, como `EVENT#2026-09-11_N`).
</details>

<details>
<summary>2. Como o Upstash QStash complementa o Redis em tarefas assíncronas serverless?</summary>
O *Upstash QStash* é uma fila de mensagens e agendador de tarefas cron 100% serverless. Ele envia requisições HTTP para endpoints e garante entregas do tipo *At-Least-Once* com retentativas automáticas (*backoff exponencial*), dispensando servidores de workers permanentes.
</details>
