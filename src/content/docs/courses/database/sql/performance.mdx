Este tópico ensina a fazer ao banco a pergunta que resolve a maioria dos problemas de lentidão: **como você vai executar isto?** O `EXPLAIN` responde com o plano de execução, e o arquivo `performance.sql` do projeto `invest-db` mostra o plano mudando conforme o índice existe, a consulta o permite e a paginação o aproveita.

## Objetivo

Compreender a criação de índices e o plano de execução como ferramentas essenciais de diagnóstico e otimização de desempenho, capacitando o desenvolvedor a estruturar índices adequados e eliminar gargalos em aplicações web. Ao final do tópico, o leitor deve ser capaz de:

- Criar, configurar e remover índices simples, compostos e únicos (`CREATE INDEX`, `CREATE UNIQUE INDEX`, `DROP INDEX`).
- Reconhecer os tipos de índice e suas peculiaridades nos principais motores de banco de dados (PostgreSQL, MySQL e SQLite).
- Ler um plano de execução com `EXPLAIN` e distinguir varredura sequencial (*Scan*) de busca por índice (*Index Search*).
- Identificar as expressões no `WHERE` que impedem o planejador de usar um índice existente.
- Reconhecer o problema N+1 no código da aplicação e substituí-lo por uma junção.
- Explicar o custo da paginação por `OFFSET` e implementar a paginação por cursor.
- Decidir quando o problema é a consulta, o índice, o modelo ou o servidor.

## Criação e Gestão de Índices (INDEX)

Um **índice** é uma estrutura de dados auxiliar gerenciada pelo SGBD para acelerar drasticamente a localização de registros em tabelas relacionais. De forma análoga ao índice remissivo ao final de um livro, o índice armazena chaves ordenadas apontando diretamente para a localização física das linhas em disco (*ROWID* ou ponteiro de tupla), transformando varreduras sequenciais completas (*Table Scans*) em buscas balanceadas de tempo logarítmico $O(\log n)$.

### 1. Definição e Sintaxe SQL Fundamental

A linguagem SQL DDL padroniza a criação e remoção de índices por meio das seguintes instruções:

```sql
-- 1. Índice Simples: acelera filtros WHERE, junções JOIN e cláusulas ORDER BY
CREATE INDEX idx_post_views ON Post (views);

-- 2. Índice Composto (Multi-coluna): ordenação combinada onde a ordem das colunas importa
CREATE INDEX idx_post_author_created ON Post (authorId, createdAt DESC);

-- 3. Índice Único: garante unicidade de valores e otimiza a recuperação exata
CREATE UNIQUE INDEX idx_user_email_unique ON User (email);

-- 4. Índice Parcial (Condicional): indexa apenas linhas que atendem a um predicado
CREATE INDEX idx_post_published ON Post (createdAt) WHERE published = 1;

-- 5. Remoção de Índices (DROP INDEX)
-- Padrão PostgreSQL e SQLite:
DROP INDEX IF EXISTS idx_post_views;

-- Padrão MySQL (exige especificar o nome da tabela com a cláusula ON):
DROP INDEX idx_post_views ON Post;
```

A criação de um índice traz ganhos expressivos em operações de leitura, mas impõe um custo de escrita: a cada `INSERT`, `UPDATE` ou `DELETE`, o motor do banco precisa atualizar não apenas a tabela principal, mas também cada uma das árvores de índice associadas.

### 2. Tipos de Índices e Comportamento nos Motores

Embora a estrutura de **Árvore B-Tree** (ou B+Tree) seja o padrão universal para comparações de igualdade e intervalos (`=`, `<`, `>`, `BETWEEN`), os principais SGBDs fornecem famílias especializadas de índices para diferentes cargas de trabalho:

| Motor SGBD | Tipos de Índice Suportados | Características Notáveis |
| :--- | :--- | :--- |
| **PostgreSQL** | B-Tree (padrão), Hash, GIN, GiST, BRIN, SP-GiST | Suporta índices parciais com `WHERE`, índices em expressões calculadas (`LOWER(col)`), tipos GIN para busca em documentos `JSONB` e vetores, e criação concorrente sem travar escritas com `CREATE INDEX CONCURRENTLY`. |
| **MySQL (InnoDB)** | B-Tree (Clustered e Secondary), Full-Text, Spatial (R-Tree) | A chave primária forma o *Clustered Index* (as linhas da tabela ficam fisicamente ordenadas dentro da árvore da PK). Os índices secundários armazenam o valor da chave primária como ponteiro. |
| **SQLite** | B-Tree | Índices leves embutidos no próprio arquivo de banco, com suporte a índices parciais e índices sobre expressões, além de índices automáticos criados para `PRIMARY KEY` e restrições `UNIQUE`. |

Compreender o comportamento do índice em cada motor permite escolher a melhor estratégia de indexação para cada volume de dados e padrão de acesso da aplicação.

### 3. Índices para Busca Textual no PostgreSQL (GIN e Text Search)

Enquanto os índices B-Tree tradicionais são eficientes para valores exatos e ordenação, buscas textuais em corpos de artigos ou buscas parciais (`LIKE '%termo%'`) provocam varreduras completas (*Table Scans*). O PostgreSQL oferece soluções nativas de alta performance baseadas em índices **GIN** (*Generalized Inverted Index*):

1. **Full-Text Search com `tsvector` e `tsquery`**:
   Indexa documentos decompondo o texto em lexemas normalizados (com remoção de palavras vazias e redução a radicais no idioma configurado):

   ```sql
   -- Criação do índice GIN sobre o vetor de busca em português
   CREATE INDEX idx_post_content_fts ON Post USING GIN (to_tsvector('portuguese', content));

   -- Consulta ultra-rápida utilizando o operador @@ de casamento textual
   SELECT id, title
   FROM Post
   WHERE to_tsvector('portuguese', content) @@ to_tsquery('portuguese', 'banco & dados');
   ```

2. **Busca por Trigramas com `pg_trgm` (Acelera `LIKE '%termo%'`)**:
   A extensão nativa `pg_trgm` divide as palavras em sequências de três caracteres consecutivos (trigramas), permitindo que consultas com curinga inicial (`LIKE '%termo%'`) utilizem o índice GIN em vez de varrer a tabela:

   ```sql
   -- Habilita a extensão de trigramas e cria o índice GIN
   CREATE EXTENSION IF NOT EXISTS pg_trgm;
   CREATE INDEX idx_post_title_trgm ON Post USING GIN (title gin_trgm_ops);

   -- Esta consulta com '%SQL%' agora utiliza o índice GIN diretamente
   SELECT id, title FROM Post WHERE title LIKE '%SQL%';
   ```

## O Plano de Execução

Antes de executar uma consulta, o motor decide **como**: em que ordem ler as tabelas, se usa índice, como junta. Essa decisão é o plano, e o `EXPLAIN` a mostra sem executar. No SQLite o comando é `EXPLAIN QUERY PLAN`; no PostgreSQL, `EXPLAIN` (e `EXPLAIN ANALYZE` para executar e medir); no MySQL, `EXPLAIN`.

A consulta abaixo filtra posts por audiência. Sem índice em `views`, o plano é uma varredura:

<SourceCode path="examples/courses/database/invest-db/performance.sql" region="plan-scan" />

```txt title="Output"
-- plano: SCAN Post
```

`SCAN Post` significa ler todas as linhas e testar cada uma. Com seis posts é instantâneo; com seis milhões, é o motivo de a página demorar. A linha 7 cria o índice, e a linha 10 repete a pergunta:

<SourceCode path="examples/courses/database/invest-db/performance.sql" region="plan-index" mark={[7, 10, 13]} />

```txt title="Output"
-- ok
-- plano: SEARCH Post USING INDEX idx_post_views (views>?)
-- plano: SCAN Post
```

A segunda linha mostra o índice em uso: `SEARCH ... (views>?)` lê só o intervalo. A terceira é a armadilha desta página: a consulta da linha 13 filtra a mesma coluna, tem o mesmo índice disponível, e voltou a `SCAN Post`. O motivo é a expressão `views * 2 > 200`: o índice ordena `views`, não `views * 2`, e o planejador não reescreve a álgebra. A tabela abaixo lista as formas que costumam derrubar um índice:

| Expressão no `WHERE` | Usa o índice em `col`? | Alternativa |
| --- | --- | --- |
| `col = ?`, `col > ?`, `col BETWEEN ? AND ?` | Sim | |
| `col * 2 > 200` | Não | `col > 100` |
| `LOWER(col) = 'ana'` | Não | Índice sobre a expressão, ou coluna já normalizada |
| `col LIKE 'Ana%'` | Sim, em muitos motores | |
| `col LIKE '%Ana'` | Não no B-Tree | Índice GIN com `pg_trgm` ou Full-Text Search |
| `CAST(col AS TEXT) = '1'` | Não | Comparar com o tipo certo |
| `col IS NULL` | Depende do motor | |

<Aside type="caution" title="Dica de IA: Peça o plano, não a garantia">
  Assistentes afirmam que "a consulta usa o índice" com base na presença do índice, sem consultar o planejador. As formas da tabela acima aparecem com frequência em código gerado, especialmente `LOWER(email)` para comparar sem diferenciar maiúsculas.

  **Prompt:** *"Para cada consulta deste módulo, escreva o `EXPLAIN` correspondente, execute contra o banco com os índices atuais e cole o plano; para cada `SCAN` em tabela com índice disponível, reescreva a condição para que o índice seja usado."*
</Aside>

## O Problema N+1

O N+1 não aparece no SQL: aparece no código que o chama. A aplicação busca a lista de autores (uma consulta) e, para cada autor, busca os posts dele (N consultas). Com quatro autores são cinco idas ao banco; com mil, são mil e uma, cada uma com a latência de rede de uma requisição.

O arquivo mostra as duas formas. As linhas 18 a 20 são o N+1 escrito à mão; a linha 23 é a junção que devolve tudo de uma vez:

<SourceCode path="examples/courses/database/invest-db/performance.sql" region="n-plus-one" mark={[18, 19, 20, 23]} />

```txt title="Output"
id | name
---+------------
1  | Ana Silva
2  | Bruno Costa
3  | Carla Souza
4  | Diego Lima
title
----------------------
Introdução ao SQL
Junções explicadas
Rascunho sobre índices
title
-----------------
Receita de pão
Viagem ao litoral
name        | title
------------+------------------------
Ana Silva   | Introdução ao SQL
Ana Silva   | Junções explicadas
Ana Silva   | Rascunho sobre índices
Bruno Costa | Receita de pão
Bruno Costa | Viagem ao litoral
Carla Souza | Normalização na prática
Diego Lima  | NULL
```

A junção devolve o mesmo conteúdo em uma consulta, com o autor repetido em cada linha, o que é o custo aceitável. O N+1 é o problema de desempenho mais comum em aplicações com ORM, porque o código `for (const user of users) user.posts` parece inocente e gera exatamente as N consultas. Os ORMs oferecem carregamento antecipado (`include` no Prisma) para transformá-lo em uma junção ou em duas consultas com `IN`.

## Paginação

A paginação com `LIMIT` e `OFFSET`, vista em [SQL DQL (Consulta)](../dql/), tem um custo escondido: para devolver a página 500 de 20 itens, o banco lê e descarta 9.980 linhas. A linha 31 pede a terceira página de dois, e o plano é uma varredura:

<SourceCode path="examples/courses/database/invest-db/performance.sql" region="pagination" mark={[31, 34]} />

```txt title="Output"
-- plano: SCAN Post
-- plano: SEARCH Post USING INTEGER PRIMARY KEY (rowid>?)
```

A linha 34 é a **paginação por cursor**: em vez de "pule N linhas", a consulta diz "continue a partir do último `id` que eu vi", e o plano vira uma busca pela chave primária. O custo passa a ser o mesmo em qualquer página, e é a forma que APIs com muitos dados adotam (o cliente recebe o último `id` como cursor e o devolve na próxima requisição).

| Forma | Consulta | Custo da página N | Limite |
| --- | --- | --- | --- |
| **OFFSET** | `ORDER BY id LIMIT 20 OFFSET 20 * N` | Cresce com N | Simples; "ir para a página 37" funciona |
| **Cursor** | `WHERE id > :ultimo ORDER BY id LIMIT 20` | Constante | Só avança; exige ordenação por coluna única e indexada |

## A Ordem de Investigação

Diante de uma consulta lenta, a ordem de investigação abaixo resolve quase tudo antes de qualquer mudança de infraestrutura:

<Steps>
1. **Meça.** O `EXPLAIN` mostra o plano; no PostgreSQL, `EXPLAIN ANALYZE` mostra o tempo real de cada etapa. Uma consulta que parece lenta na aplicação e é rápida no banco é problema de rede ou de N+1.
2. **Procure o `SCAN` em tabela grande.** É o sinal de índice ausente ou de expressão que o derruba.
3. **Conte as consultas por requisição.** Um registro de consultas (o `log` do ORM) revela o N+1 imediatamente.
4. **Revise o modelo.** Uma consulta que precisa de cinco junções para uma tela frequente pode estar pedindo uma [desnormalização medida](../../modeling/normalization/) ou uma visão materializada.
5. **Só então o servidor.** Mais memória e CPU escondem um `SCAN` por um tempo, e ele volta com o dobro dos dados.
</Steps>

## Quando usar, e quando não usar?

As ferramentas desta página têm momentos certos, e usá-las cedo demais é um custo tão real quanto usá-las tarde.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Consulta frequente com `WHERE` em coluna sem índice | **Criar o índice** | O `SCAN` cresce com a tabela; o índice não. |
| Tabela pequena, ou coluna com dois ou três valores | **Deixar sem índice** | O planejador varre de qualquer forma; o índice só custa nas escritas. |
| Lista com itens relacionados carregados em laço | **Junção ou carregamento antecipado** | N+1 é latência multiplicada por N. |
| Paginação de tela com poucas páginas | **`OFFSET`** | Simples, e o custo é irrelevante em páginas baixas. |
| Rolagem infinita ou API sobre milhões de linhas | **Cursor** | Custo constante por página. |
| Consulta lenta sem `SCAN` e sem N+1 | **Revisar o modelo** | Junções demais para a tela mais usada pedem outra forma dos dados. |

## Exercício

Responda com base nos planos do arquivo:

1. Por que `views * 2 > 200` não usa o índice que `views > 100` usa, se as duas condições são equivalentes?
2. Onde o N+1 aparece: no SQL ou no código da aplicação? Como ele se manifesta?
3. Por que a paginação por cursor tem custo constante e a por `OFFSET` não?

<details>
  <summary>Possível resposta</summary>

  1. Porque o índice ordena os valores de `views`, e o planejador procura no índice pelo valor da coluna. Ele não reescreve `views * 2 > 200` como `views > 100`; a expressão sobre a coluna o impede de usar a ordenação.

  2. No código: um laço que executa uma consulta por item de uma lista obtida por outra consulta. Manifesta-se como N+1 idas ao banco por requisição, cada uma com a latência da rede.

  3. Porque o cursor vira uma busca pela chave (`WHERE id > :ultimo`), que encontra o ponto de partida direto no índice. O `OFFSET` obriga o banco a ler e descartar todas as linhas anteriores à página.
</details>

## Desafio

O blog do projeto tem seis posts, e nenhum plano mostra diferença de tempo. Escreva um script `seed-big.mjs` que insira cem mil posts com `node:sqlite` em uma transação, e meça com `console.time` as três consultas da página (`views > 100` sem e com índice, e a página 4.000 por `OFFSET` contra a mesma página por cursor).

Registre os tempos e responda: em qual das três a diferença é maior, e o que aconteceria com cada uma se a tabela tivesse dez vezes mais linhas?

<details>
  <summary>Possível resposta</summary>

  Com cem mil linhas em memória, a consulta por `views` cai de alguns milissegundos (varredura) para centésimos de milissegundo (busca), cerca de quarenta vezes, e a diferença cresce linearmente com a tabela: dez vezes mais linhas, dez vezes mais tempo na varredura, quase o mesmo tempo na busca. A paginação por `OFFSET` na página 4.000 lê e descarta 80 mil linhas e leva dezenas de vezes mais do que a mesma página por cursor, que leva o mesmo que a página 1; dez vezes mais linhas não mudam o cursor.

  A maior diferença costuma estar na paginação profunda, porque o `OFFSET` multiplica o custo pela posição da página, e nenhum índice o resolve. É o caso em que a mudança não é um índice novo, e sim outra forma de consultar, o que a aplicação precisa suportar (devolvendo e recebendo o cursor).
</details>

## Perguntas de revisão

### Índices e Plano de Execução

1. **Qual é a diferença entre `CREATE INDEX` e `CREATE UNIQUE INDEX`?**
   <details><summary>Possível resposta</summary>Ambos criam uma estrutura de busca B-Tree acelerada, mas o `CREATE UNIQUE INDEX` impõe adicionalmente a restrição de integridade que impede a inserção de valores duplicados na(s) coluna(s).</details>

2. **O que `SCAN` e `SEARCH ... USING INDEX` significam no plano de execução do SQLite?**
   <details><summary>Possível resposta</summary>`SCAN` representa uma varredura sequencial completa por todas as linhas da tabela; `SEARCH ... USING INDEX` é a busca direta e eficiente na árvore de índice, lendo apenas o intervalo de linhas necessário.</details>

3. **Cite três expressões no `WHERE` que impedem o otimizador de utilizar um índice existente.**
   <details><summary>Possível resposta</summary>Aritmética sobre a coluna (ex: `col * 2 > 100`), funções que envolvem o campo (ex: `LOWER(email) = '...'`) e buscas textuais com curinga no início (ex: `LIKE '%termo'`).</details>

### Padrões e Diagnóstico de Desempenho

4. **Como um ORM evita o problema N+1?**
   <details><summary>Possível resposta</summary>Através de carregamento antecipado (*eager loading* ou `include`), que converte o laço de requisições repetidas em uma única junção (`JOIN`) ou em uma consulta secundária em lote utilizando o operador `IN (...)`.</details>

5. **Qual é a vantagem da paginação por cursor sobre a paginação por `LIMIT / OFFSET`?**
   <details><summary>Possível resposta</summary>A paginação por cursor mantém tempo de resposta constante $O(\log n)$ mesmo em páginas profundas (`WHERE id > :ultimo`), enquanto o `OFFSET` degrada o desempenho ao forçar o banco a ler e descartar todas as linhas anteriores.</details>

6. **Por que adicionar mais hardware (CPU/RAM) deve ser a última opção em caso de lentidão?**
   <details><summary>Possível resposta</summary>Porque o hardware adicional apenas mascara temporariamente um `SCAN` ineficiente ou um gargalo N+1. Conforme a base de dados cresce, o problema ressurge com custos exponenciais. A otimização de consultas, criação de índices corretos e revisão de modelagem resolvem a causa raiz.</details>
