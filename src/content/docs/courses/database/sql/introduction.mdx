A linguagem **SQL** (*Structured Query Language*) é a linguagem padrão universal para definição, manipulação e consulta de dados em sistemas de gerenciamento de bancos de dados relacionais (SGBDs). Desenvolvida na década de 1970 a partir do modelo relacional proposto por Edgar F. Codd, a SQL tornou-se a espinha dorsal do armazenamento e recuperação estruturada de informações em toda a indústria de tecnologia.

---

## Objetivo

Compreender a fundamentação teórica, a evolução histórica, o propósito arquitetural e a taxonomia da linguagem SQL, preparando a base conceitual para o domínio dos seus subconjuntos práticos. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o que é a SQL e como sua evolução histórica moldou os padrões internacionais ANSI/ISO.
- Diferenciar o paradigma declarativo da SQL do paradigma procedural das linguagens de programação convencionais.
- Identificar e classificar instruções SQL dentro dos cinco subconjuntos formais (DDL, DML, DQL, DCL e TCL).
- Compreender o pipeline interno de processamento de uma consulta SQL no motor do banco de dados (Parser, Otimizador e Motor de Execução).
- Reconhecer as diferenças entre o padrão ANSI/ISO e as extensões proprietárias dos principais dialetos do mercado.

## O que é a Linguagem SQL

A SQL é uma linguagem de domínio específico (*Domain-Specific Language - DSL*) projetada para interagir com bancos de dados relacionais. Ao contrário de linguagens de programação de propósito geral (como Python, JavaScript, Java ou C#), a SQL não foi criada para construir aplicações inteiras, mas sim para expressar operações sobre dados organizados em tabelas (relações), linhas (tuplas) e colunas (atributos).

<Mermaid title="Papel central da SQL na arquitetura de aplicações">
{`
flowchart LR
    App["Aplicação Backend<br/>(Node.js / Python / Go)"] -->|"Comandos SQL<br/>(Texto via TCP / Driver)"| DBMS["SGBD Relacional<br/>(PostgreSQL / MySQL / SQLite)"]
    DBMS -->|"Conjunto de Resultados<br/>(Tabelas / Registros / Status)"| App
`}
</Mermaid>

A principal característica distintiva da SQL é a sua natureza **declarativa**: ao escrever uma consulta, o desenvolvedor especifica **o que** deseja obter como resultado, e não **como** o computador deve percorrer os discos, carregar blocos de memória ou ordenar os registros para produzir essa resposta. O motor interno do SGBD é o responsável por determinar o algoritmo de busca mais eficiente.

## Breve História e Evolução

A história da SQL está diretamente ligada à criação da teoria dos bancos de dados relacionais:

1. **1970 (O Modelo Relacional)**: O matemático britânico Edgar Frank Codd publicou no laboratório da IBM o artigo seminal *"A Relational Model of Data for Large Shared Data Banks"*, propondo que os dados deveriam ser armazenados em tabelas matemáticas independentes da estrutura física de armazenamento em disco.
2. **1974 (SEQUEL na IBM)**: Donald Chamberlin e Raymond Boyce criaram a linguagem *SEQUEL* (*Structured English Query Language*) no projeto *System R* da IBM para permitir consultas legíveis baseadas na álgebra relacional. O nome foi posteriormente encurtado para **SQL** por questões de marca registrada.
3. **1979 (Oracle e Comercialização)**: A *Relational Software* (que mais tarde se tornaria a Oracle Corporation) lançou o primeiro SGBD relacional comercial baseado em SQL.
4. **1986 em diante (Padronização ANSI/ISO)**: O *American National Standards Institute* (ANSI) e a *International Organization for Standardization* (ISO) formalizaram o padrão **SQL-86**. Atualizações marcantes se seguiram, incluindo:
   - **SQL-92 (SQL2)**: Introduziu a sintaxe explícita de `JOIN`, tipos de dados expandidos e restrições de integridade complexas.
   - **SQL:1999 (SQL3)**: Adicionou expressões de tabela comuns (CTEs com `WITH`), recursos procedurais e tipos orientados a objetos.
   - **SQL:2003 e SQL:2016**: Introduziram funções de janela (*Window Functions*), suporte nativo a dados em formato `JSON` e tabelas temporais.
   - **SQL:2023**: Incorporou tipos de dados de grafos (*Property Graph Queries - SQL/PGQ*), aprimoramentos em manipulação de vetores e JSON.

## O Paradigma Declarativo: O "O Quê" vs o "Como"

Para compreender a elegância da SQL, compare a recuperação de dados em um paradigma procedural/imperativo convencional com a abordagem declarativa da SQL.

Considere a necessidade de encontrar o nome de clientes ativos que gastaram mais de R\$ 1.000,00, ordenados pelo valor total:

<Mermaid title="Comparação de paradigmas: Imperativo vs Declarativo">
{`
flowchart TD
    subgraph Imperativo ["Paradigma Imperativo (Algoritmo Explícito)"]
        direction TB
        I1["1. Abrir arquivo / array de clientes"] --> I2["2. Loop for each cliente"]
        I2 --> I3{"3. if cliente.ativo == true?"}
        I3 -- Sim --> I4{"4. if cliente.total > 1000?"}
        I4 -- Sim --> I5["5. Adicionar a lista temporária"]
        I5 --> I6["6. Aplicar algoritmo Quicksort por total"]
        I6 --> I7["7. Retornar os 10 primeiros"]
    end

    subgraph Declarativo ["Paradigma Declarativo SQL (Especificação do Resultado)"]
        direction TB
        D1["SELECT name, total<br/>FROM Customer<br/>WHERE active = 1 AND total > 1000<br/>ORDER BY total DESC<br/>LIMIT 10;"]
    end
`}
</Mermaid>

No modelo declarativo, o desenvolvedor não precisa gerenciar ponteiros de memória, implementar laços de repetição nem escolher se usará uma busca binária ou varredura sequencial. O otimizador de consultas (*Query Optimizer*) do SGBD analisa os índices disponíveis, o volume estatístico de linhas na tabela e o custo de I/O em disco para traçar o plano de execução mais veloz.

## Taxonomia dos Subconjuntos da Linguagem SQL

Embora a SQL seja tratada como uma linguagem única, ela é composta formalmente por cinco subconjuntos especializados, cada um responsável por um domínio de responsabilidade operacional:

<Mermaid title="Taxonomia dos subconjuntos da linguagem SQL">
{`
flowchart TD
    SQL["Linguagem SQL"]
    SQL --> DDL["1. DDL<br/>Data Definition"]
    SQL --> DML["2. DML<br/>Data Manipulation"]
    SQL --> DQL["3. DQL<br/>Data Query"]
    SQL --> TCL["4. TCL<br/>Transaction Control"]
    SQL --> DCL["5. DCL<br/>Data Control"]

    DDL --- DDL_C["CREATE<br/>ALTER<br/>DROP<br/>TRUNCATE"]
    DML --- DML_C["INSERT<br/>UPDATE<br/>DELETE<br/>MERGE"]
    DQL --- DQL_C["SELECT<br/>WHERE<br/>GROUP BY<br/>ORDER BY"]
    TCL --- TCL_C["COMMIT<br/>ROLLBACK<br/>SAVEPOINT"]
    DCL --- DCL_C["GRANT<br/>REVOKE<br/>DENY"]
`}
</Mermaid>

A tabela abaixo descreve o papel, o impacto e os comandos característicos de cada subconjunto:

| Subconjunto | Nome Completo | Propósito Principal | Comandos Fundamentais |
| :--- | :--- | :--- | :--- |
| **DDL** | *Data Definition Language* | Define, altera e remove a estrutura física e lógica dos esquemas, tabelas, índices e restrições. | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| **DML** | *Data Manipulation Language* | Insere, modifica e remove os registros de dados armazenados dentro das tabelas existentes. | `INSERT`, `UPDATE`, `DELETE`, `MERGE` |
| **DQL** | *Data Query Language* | Consulta, filtra, projeta, agrupa e extrai informações a partir das tabelas relacionais. | `SELECT` |
| **TCL** | *Transaction Control Language* | Gerencia a atomicidade, confirmação ou cancelamento de blocos de operações transacionais (ACID). | `COMMIT`, `ROLLBACK`, `SAVEPOINT` |
| **DCL** | *Data Control Language* | Controla níveis de permissão, privilégios de acesso e segurança de usuários e papéis (*roles*). | `GRANT`, `REVOKE`, `DENY` |

<Aside type="note" title="DQL vs DML na Literatura">
  Muitas referências bibliográficas clássicas agrupam o comando `SELECT` dentro do subconjunto DML (considerando-o uma operação de leitura de dados). No entanto, a separação moderna destaca o `DQL` para evidenciar que comandos de consulta pura não geram efeitos colaterais de mutação nos dados gravados.
</Aside>

## Anatomia de uma Instrução SQL

Uma instrução SQL é composta por cláusulas, palavras-chave reservadas, identificadores de entidades (tabelas e colunas), literais e predicados lógicos.

Observe os componentes fundamentais que compõem uma consulta padrão:

```sql
SELECT
  u.name AS author_name,
  COUNT(p.id) AS total_posts
FROM User AS u
LEFT JOIN Post AS p ON p.authorId = u.id
WHERE u.createdAt >= '2026-01-01'
GROUP BY u.id, u.name
HAVING COUNT(p.id) > 5
ORDER BY total_posts DESC
LIMIT 10;
```

A estrutura segue uma ordem gramatical estrita:

1. **`SELECT`**: Define as colunas projetadas e expressões agregadas.
2. **`FROM` & `JOIN`**: Especifica as tabelas de origem e as condições lógicas de relacionamento entre elas.
3. **`WHERE`**: Filtra linhas individuais antes de qualquer agrupamento.
4. **`GROUP BY`**: Agrupa registros com base em valores idênticos nas colunas especificadas.
5. **`HAVING`**: Filtra os grupos agregados após o processamento das funções de grupo (`COUNT`, `SUM`).
6. **`ORDER BY`**: Ordena o conjunto final de dados (ascendente ou descendente).
7. **`LIMIT` / `OFFSET`**: Restringe a quantidade de linhas devolvidas ao cliente.

## Dicas Essenciais e Boas Práticas

Para escrever código SQL limpo, seguro e portável no dia a dia, observe as regras práticas fundamentais:

- **Padrão Formal**: A linguagem é padronizada internacionalmente como **Structured Query Language (SQL:2023 ou ISO/IEC 9075:2023)**. Conhecer a norma ajuda a distinguir o que é padrão do que é extensão exclusiva de um motor.
- **Palavras-chave não são Case Sensitive**: Comandos como `SELECT`, `select` ou `Select` produzem o mesmo efeito. No entanto, a boa prática universal da comunidade recomenda escrever todas as palavras-chave e cláusulas reservadas em **MAIÚSCULAS** para destacar a estrutura da consulta.
- **Nomes de Tabelas e Colunas podem ser Case Sensitive**: O comportamento varia por SGBD e sistema operacional. No Linux, o MySQL diferencia `Tabela` de `tabela` por criar arquivos no disco com o nome da entidade. No PostgreSQL, todos os identificadores sem aspas são convertidos para minúsculas por padrão; para preservar maiúsculas, o nome deve ser envolvido em aspas duplas (`"MinhaTabela"`). Como boa prática, adote `snake_case` em minúsculas para todos os nomes de tabelas e colunas.
- **Não esqueça do Ponto e Vírgula (`;`)**: O `;` é o delimitador formal de término de instrução. Em scripts multi-linha, clientes CLI e migrações contendo múltiplos comandos em sequência, o `;` é obrigatório para que o parser do banco separe as instruções sem erros.
- **Interprete as Mensagens de Erro**: Quando uma consulta falhar, leia atentamente o retorno do SGBD. A mensagem geralmente aponta a linha exata, o caractere ou token inesperado (ex: vírgula a mais antes do `FROM`), ou o nome da restrição violada (ex: `duplicate key value violates unique constraint`).

## Operadores da Linguagem SQL

Os operadores permitem realizar comparações lógicas, cálculos matemáticos, manipulação de bits e testes de pertinência de conjuntos dentro de instruções SQL:

| Categoria | Operadores | Descrição Didática |
| :--- | :--- | :--- |
| **Comparação** | `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=` | Avaliam igualdade, desigualdade e relações de grandeza entre valores escalares. |
| **Lógicos e Conjunto** | `AND`, `OR`, `NOT`, `ALL`, `ANY`, `SOME`, `BETWEEN`, `IN`, `LIKE`, `EXISTS`, `REGEXP`, `IS NULL`, `CASE` | Combinam condições booleanas, testam intervalos, listas e padrões de texto. |
| **Aritméticos** | `+`, `-`, `*`, `/`, `%` | Realizam soma, subtração, multiplicação, divisão e resto da divisão inteira (módulo). |
| **Bit a Bit (Bitwise)** | `&`, `\|`, `^` | Executam operações binárias (AND, OR e XOR) diretamente sobre inteiros. |
| **Compostos** | `+=`, `-=`, `*=`, `/=`, `%=` | Operadores de atribuição abreviada suportados em linguagens procedurais (T-SQL, PL/pgSQL). |

## Funções Nativas Fundamentais

Todos os SGBDs relacionais fornecem uma biblioteca rica de funções embutidas para transformar dados em consultas e expressões:

### 1. Funções de Agregação
Resumem múltiplos registros em um único valor escalar:
- `COUNT()`: Conta o número de linhas ou valores não nulos.
- `SUM()`: Calcula o somatório total de uma coluna numérica.
- `AVG()`: Calcula a média aritmética dos valores.
- `MIN()` e `MAX()`: Retornam o menor e o maior valor de um conjunto.

### 2. Funções Numéricas e Matemáticas
Processam e ajustam valores numéricos:
- `ROUND(x, d)`: Arredonda o valor para $d$ casas decimais.
- `CEIL(x)` / `CEILING(x)`: Arredonda para cima (menor inteiro maior ou igual a $x$).
- `FLOOR(x)`: Arredonda para baixo (maior inteiro menor ou igual a $x$).
- `ABS(x)`: Retorna o valor absoluto positivo de um número.
- `RAND()` / `RANDOM()`: Gera um número pseudoaleatório entre $0.0$ e $1.0$.

### 3. Funções de Manipulação de Texto (*String*)
Formatam, extraem e transformam cadeias de caracteres:
- `LENGTH(str)`: Retorna a contagem de caracteres da string.
- `UPPER(str)` e `LOWER(str)`: Converte o texto para maiúsculas ou minúsculas.
- `TRIM(str)`, `LTRIM(str)`, `RTRIM(str)`: Remove espaços em branco nas pontas, no início ou no fim.
- `LEFT(str, n)` e `RIGHT(str, n)`: Extrai os $n$ primeiros ou últimos caracteres.
- `SUBSTRING(str, pos, len)`: Extrai uma fatia de texto a partir de uma posição.
- `LOCATE(sub, str)` / `INSTR(str, sub)`: Localiza a posição inicial de um termo no texto.
- `REPLACE(str, de, para)`: Substitui todas as ocorrências de um termo por outro.
- `CONCAT(a, b, ...)` ou `a || b`: Concatena múltiplos textos em uma única cadeia.

### 4. Funções de Data e Hora
Manipulam carimbos de tempo, calendário e durações:
- `NOW()` / `CURRENT_TIMESTAMP`: Retorna a data e hora atual do sistema.
- `CURDATE()` e `CURTIME()`: Retornam a data corrente ou hora corrente isoladamente.
- `YEAR()`, `MONTH()`, `DAY()`, `HOUR()`, `MINUTE()`, `SECOND()`: Extraem partes específicas da data/hora.
- `DAYNAME()`, `MONTHNAME()`: Retornam o nome do dia da semana ou do mês por extenso.
- `EXTRACT(campo FROM data)`: Extração padronizada ANSI de componentes temporais.
- `DATE_FORMAT()`, `TIME_FORMAT()`: Formatam datas em padrões textuais específicos.
- `DATE_ADD()`, `DATE_SUB()`, `DATEDIFF()`: Somam, subtraem e calculam a diferença de dias entre datas.
- `TIME_TO_SEC()`: Converte um intervalo de tempo em total de segundos.

### 5. Tratamento de Nulos e Controle Condicional
Gerenciam valores nulos e bifurcações lógicas:
- `COALESCE(v1, v2, ...)`: Retorna o primeiro valor não nulo da lista de argumentos (padrão ANSI universal).
- `IFNULL(val, fallback)`: Retorna o valor reserva caso o primeiro argumento seja nulo (MySQL/SQLite).
- `NULLIF(a, b)`: Retorna `NULL` se os dois argumentos forem iguais (útil para evitar divisão por zero).
- `IF(cond, verdadeiro, falso)`: Expressão condicional ternária rápida em MySQL.
- `CASE WHEN ... THEN ... ELSE ... END`: Estrutura condicional completa e padronizada ANSI.

## Pipeline Interno de Processamento no SGBD

Quando a aplicação envia uma sequência de caracteres contendo uma instrução SQL para o banco via conexão TCP ou chamada de driver local, o SGBD executa um pipeline rigoroso de processamento em etapas:

<Mermaid title="Pipeline de execução de uma instrução SQL no motor relacional">
{`
flowchart TD
    SQLInput["Instrução SQL (String de Texto)"] --> Parser["1. Parser Sintático & Léxico<br/>Valida gramática e monta Árvore AST"]
    Parser --> Catalog["2. Validação Semântica & Catálogo<br/>Verifica se tabelas, colunas e tipos existem"]
    Catalog --> Optimizer["3. Otimizador de Consultas (Planner)<br/>Avalia índices, estatísticas e gera Plano de Execução"]
    Optimizer --> Executor["4. Motor de Execução (Execution Engine)<br/>Executa o plano ótimo de passos"]
    Executor --> Storage["5. Storage Engine & Buffer Pool<br/>Lê páginas de dados em disco / memória RAM"]
    Storage --> ResultSet["Resultado Retornado à Aplicação"]
`}
</Mermaid>

1. **Parser Sintático e Léxico**: Faz a análise léxica do texto, identifica palavras-chave reservadas e verifica erros de sintaxe (como parênteses não fechados ou vírgulas extras), gerando uma Árvore de Sintaxe Abstrata (*Abstract Syntax Tree - AST*).
2. **Validação Semântica e Catálogo**: Consulta o dicionário de dados interno do SGBD (*schema metadata*) para confirmar se as tabelas e colunas citadas realmente existem e se o usuário autenticado possui privilégios de acesso.
3. **Otimizador de Consultas (*Query Planner/Optimizer*)**: A etapa mais complexa do motor. O otimizador simula dezenas ou centenas de planos possíveis para executar a mesma instrução (por exemplo: se deve usar um *Index Scan* ou um *Sequential Scan*, ou qual tabela deve entrar primeiro no algoritmo de *Hash Join*), escolhendo aquele com o menor custo estimado de CPU e disco.
4. **Motor de Execução (*Execution Engine*)**: Interpreta o plano de execução escolhido, orquestrando as chamadas de baixo nível para o subsistema de armazenamento.
5. **Buffer Pool e Storage Engine**: Recupera as páginas de dados da memória cache (*Buffer Pool*) ou realiza leitura/escrita física no arquivo de dados em disco.

## Padrão ANSI/ISO versus Dialetos de Mercado

Embora exista a norma formal ANSI/ISO SQL, nenhum SGBD comercial ou open-source implementa 100% da norma de forma idêntica. Cada fabricante adiciona recursos proprietários, otimizações específicas e variações de sintaxe conhecidas como **dialetos**.

A tabela abaixo compara o comportamento de alguns recursos comuns entre os principais motores:

| Recurso / Sintaxe | Padrão ANSI SQL | PostgreSQL | MySQL | SQLite | Oracle Database |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Autoincremento de ID** | `GENERATED ALWAYS AS IDENTITY` | `IDENTITY` ou `SERIAL` | `AUTO_INCREMENT` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `IDENTITY` ou `SEQUENCE` |
| **Concatenação de Texto** | `CONCAT(a, b)` ou `a \|\| b` | `a \|\| b` ou `concat(a, b)` | `CONCAT(a, b)` | `a \|\| b` | `a \|\| b` ou `CONCAT(a, b)` |
| **Limitação de Linhas** | `FETCH FIRST n ROWS ONLY` | `LIMIT n` ou `FETCH FIRST` | `LIMIT n` | `LIMIT n` | `FETCH FIRST n ROWS ONLY` (12c+) |
| **Tratamento de Nulos na Ordenação** | `NULLS FIRST / LAST` | `NULLS FIRST / LAST` | Emula com `IS NULL` | `NULLS FIRST / LAST` | `NULLS FIRST / LAST` |
| **Lógica Procedural** | SQL/PSM | PL/pgSQL | Sintaxe `BEGIN ... END` | Não possui (apenas triggers) | PL/SQL |

<Aside type="tip" title="Escrevendo SQL Portável">
  Para garantir que seus esquemas e consultas possam migrar de um banco para outro com o menor retrabalho possível, priorize sempre a sintaxe padrão ANSI SQL e evite depender de funções ou atalhos exclusivos de um único fabricante, a não ser quando estritamente justificado por ganho de performance.
</Aside>

## Exercício

Com base nos conceitos fundamentais da linguagem SQL apresentados:

1. Qual é a diferença essencial entre uma linguagem imperativa (como JavaScript/Python) e a linguagem declarativa SQL?
2. Em qual dos cinco subconjuntos da SQL se enquadram, respectivamente, as instruções `CREATE TABLE`, `INSERT INTO`, `SELECT`, `COMMIT` e `GRANT`?
3. O que faz o Otimizador de Consultas (*Query Optimizer*) dentro do pipeline de processamento do SGBD?
4. Por que existem pequenas diferenças de sintaxe (como `AUTO_INCREMENT` vs `SERIAL`) entre o PostgreSQL, MySQL e SQLite, se todos suportam SQL?

<details>
  <summary>Possível resposta</summary>

  1. A linguagem imperativa exige que o desenvolvedor descreva passo a passo o algoritmo e as estruturas de repetição para encontrar os dados. A linguagem declarativa SQL permite que o usuário apenas descreva as características do resultado desejado, deixando a escolha do algoritmo de busca a cargo do motor interno do banco.
  2. `CREATE TABLE` pertence ao **DDL**; `INSERT INTO` pertence ao **DML**; `SELECT` pertence ao **DQL**; `COMMIT` pertence ao **TCL**; `GRANT` pertence ao **DCL**.
  3. O otimizador analisa a consulta parseada, avalia as estatísticas de volume de dados das tabelas, os índices disponíveis e o custo de I/O em disco, gerando e selecionando o plano de execução mais eficiente.
  4. Porque cada motor implementou seu próprio dialeto antes ou em paralelo à publicação das normas ANSI/ISO, criando extensões de mercado e otimizações arquiteturais próprias.
</details>

## Desafio

Uma equipe de engenharia está desenhando um novo sistema financeiro e discute onde manter as validações de integridade e regras de negócio:

1. Quais regras devem ser delegadas diretamente à camada de definição de dados (**DDL**) do banco de dados relacional?
2. Quais operações devem ser encapsuladas em transações controladas por **TCL** e por quê?

<details>
  <summary>Possível resposta</summary>

  1. Regras de integridade estrutural e unicidade (como obrigatoriedade de campos com `NOT NULL`, garantia de e-mails únicos com `UNIQUE`, valores mínimos ou faixas numéricas válidas com `CHECK`, e relacionamentos com integridade referencial via `FOREIGN KEY`) devem residir no DDL do banco para garantir consistência mesmo se diferentes aplicações ou scripts acessarem os dados diretamente.
  2. Todas as transferências de saldo ou liquidações compostas por múltiplos débitos e créditos devem ser delimitadas por comandos TCL (`BEGIN`, `COMMIT`, `ROLLBACK`), garantindo que ou todas as alterações sejam gravadas com sucesso ou nenhuma persista em caso de erro (propriedade de atomicidade do ACID).
</details>
