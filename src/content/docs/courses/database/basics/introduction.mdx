Esta aula apresenta os conceitos fundamentais de Banco de Dados. Você entenderá por que sistemas modernos abandonaram o armazenamento simples em arquivos de texto ou JSON em favor de Sistemas Gerenciadores de Banco de Dados (SGBD), além de conhecer as propriedades ACID, o modelo relacional e NoSQL.

## Objetivo

Compreender o papel de um Banco de Dados e de um SGBD na arquitetura de software, dominando os conceitos de abstração de dados, integridade, transações ACID e as diferenças fundamentais entre bancos relacionais e Não-Relacionais (NoSQL).

## De Arquivos para Banco de Dados

Nos primórdios da computação, os dados de uma aplicação eram salvos diretamente em arquivos no sistema operacional (como arquivos de texto, CSV ou JSON). Embora simples, essa abordagem impõe limitações severas em sistemas reais:

- **Redundância e Inconsistência**: Os mesmos dados acabam duplicados em arquivos diferentes com informações divergentes.
- **Dificuldade de Acesso**: Qualquer consulta exige escrever código customizado para percorrer e filtrar arquivos.
- **Concorrência Insegura**: Dois processos tentando alterar o mesmo arquivo simultaneamente resultam em corrupção de dados.
- **Ausência de Integridade**: Não há garantia de que um campo de idade conterá apenas números válidos ou que um e-mail seja único.

Um **Banco de Dados** é uma coleção organizada de dados inter-relacionados. O **SGBD** (Sistema Gerenciador de Banco de Dados) é o software responsável por gerenciar esses dados de forma segura, eficiente e transparente.

---

## O que é um SGBD?

O SGBD atua como uma camada intermediária entre as aplicações e os arquivos físicos no disco rígido. Ele abstrai a complexidade do armazenamento e oferece uma interface unificada para consulta e manipulação de dados.

O diagrama a seguir ilustra a arquitetura típica de interação entre a aplicação, o SGBD e o armazenamento em disco:

    B -->|Mecanismo de Busca & Cache| C[Memória RAM]

### Níveis de Abstração de Dados

Para isolar o usuário final da complexidade interna do hardware, o SGBD divide a visão dos dados em três níveis de abstração:

1. **Nível de Visão (Externo)**: A forma como os usuários ou partes da aplicação enxergam os dados (telas, visões específicas, relatórios).
2. **Nível Lógico (Conceitual)**: Define quais dados estão armazenados e quais são seus relacionamentos (tabelas, colunas, tipos e restrições).
3. **Nível Físico (Interno)**: Descreve como os dados são realmente gravados nos blocos do disco (índices, estruturas B-Tree, alocação de arquivos).

## Propriedades ACID e Transações

Uma **transação** é uma sequência de uma ou mais operações executadas como um bloco único e indivisível de trabalho. Um caso clássico é a transferência bancária: tirar dinheiro de uma conta e colocar em outra.

Para garantir a confiabilidade das transações, os bancos relacionais implementam o acrônimo **ACID**:

| Propriedade | Significado | Descrição Didática |
| :--- | :--- | :--- |
| **Atomicidade** | Tudo ou Nada (*All or Nothing*) | Se uma das etapas da transação falhar, toda a transação é cancelada (*rollback*) e o banco volta ao estado anterior. |
| **Consistência** | Respeito às Regras | O banco passa de um estado válido para outro estado válido, respeitando todas as chaves e restrições configuradas. |
| **Isolamento** | Operações Simultâneas | Transações concorrentes são executadas de forma isolada, impedindo que uma interfira nos dados intermediários da outra. |
| **Durabilidade** | Persistência Permanente | Uma vez que a transação é confirmada (*commit*), os dados ficam gravados de forma permanente, mesmo se houver queda de energia. |

<Aside type="caution" title="Atomicidade na Prática">
  Sem transações ACID, se o servidor desligar no meio de uma transferência PIX entre o débito na conta A e o crédito na conta B, o dinheiro sumiria do sistema sem rastro.
</Aside>

## Modelo Relacional vs NoSQL

Existem dois grandes paradigmas para gerenciamento de dados na computação moderna:

### Banco de Dados Relacional (RDBMS)

Criado por Edgar F. Codd na década de 1970, organiza os dados em **tabelas** (relações) compostas por **linhas** (tuplas) e **colunas** (atributos). Utiliza a linguagem SQL como padrão de consulta.

- **Esquema Rígido (*Schema-first*)**: A estrutura das tabelas precisa ser definida antes da inserção dos dados.
- **Foco**: Integridade relacional, consistência forte e suporte nativo a ACID.
- **Exemplos**: PostgreSQL, MySQL, SQLite, Oracle, SQL Server.

### Banco de Dados Não-Relacional (NoSQL)

Surgiu para atender demandas de escalabilidade horizontal, grande volume de dados não estruturados e esquema flexível.

- **Esquema Dinâmico (*Schema-less*)**: Documentos ou registros podem ter estruturas diferentes na mesma coleção.
- **Foco**: Alta velocidade de escrita, escalabilidade em cluster e flexibilidade de modelo.
- **Tipos principais**:
  - **Documentos**: JSON/BSON (ex: MongoDB).
  - **Chave-Valor**: Armazenamento ultra-rápido em memória (ex: Redis).
  - **Colunas Largas**: Consultas de grande escala (ex: Cassandra).
  - **Grafos**: Redes de relacionamentos complexos (ex: Neo4j).

## Executando

Para visualizar a diferença entre uma persistência simples em arquivo e o uso de um banco relacional, veja o script em Node.js a seguir:

```js title="exemplo-persistencia.js"
// Em arquivos de texto simples (sem SGBD):
const fs = require('fs');

// Escrita manual sem garantia de concorrência ou integridade
const usuario = { id: 1, nome: "Ana", email: "ana@email.com" };
fs.writeFileSync('usuarios.json', JSON.stringify(usuario));

console.log("Dado gravado em arquivo direto no SO!");
```

Execute o arquivo no terminal para confirmar a geração:

```bash title="Terminal"
node exemplo-persistencia.js
```

```txt title="Output"
Dado gravado em arquivo direto no SO!
```

## Exercício

Imagine um e-commerce com clientes, pedidos e produtos.

1. Identifique duas falhas que poderiam ocorrer se os pedidos fossem gravados em um arquivo `.txt` compartilhado.
2. Explique como a propriedade de **Atomicidade** garante a segurança no fechamento de um carrinho de compras com 3 itens.

<details>
  <summary>Possível resposta</summary>

  1. **Falhas no arquivo .txt**: 
     - Duas compras simultâneas poderiam sobrescrever o arquivo ao mesmo tempo, corrompendo os pedidos (*race condition*).
     - Não haveria validação se o `cliente_id` informado realmente existe no sistema.

  2. **Atomicidade no carrinho**:
     - O fechamento do carrinho exige: debitar o estoque dos 3 itens, gerar a cobrança e registrar o pedido. Se o estoque de um dos itens falhar, a atomicidade garante um *rollback* completo, sem cobrar o cliente nem deixar o pedido incompleto.
</details>

## Perguntas de revisão

1. **O que é um Sistema Gerenciador de Banco de Dados (SGBD)?**
   <details><summary>Possível resposta</summary>É o software responsável por criar, manipular, consultar e administrar bancos de dados, oferecendo segurança, concorrência e abstração de hardware.</details>

2. **Quais são os 3 níveis de abstração de dados em um SGBD?**
   <details><summary>Possível resposta</summary>Nível de Visão (Externo), Nível Lógico (Conceitual) e Nível Físico (Interno).</details>

3. **O que significa a sigla ACID?**
   <details><summary>Possível resposta</summary>Atomicidade, Consistência, Isolamento e Durabilidade.</details>

4. **Qual a diferença entre um esquema rígido (*schema-first*) e um esquema flexível (*schema-less*)?**
   <details><summary>Possível resposta</summary>No esquema rígido (relacional), a estrutura de tabelas e colunas deve ser criada antes dos dados. No esquema flexível (NoSQL), os documentos podem ter atributos variados sem pré-definição fixa.</details>

5. **O que é o fenômeno de *rollback* em uma transação?**
   <details><summary>Possível resposta</summary>É o ato de desfazer todas as alterações de uma transação quando ocorre um erro em qualquer uma das suas etapas, restaurando o banco ao estado inicial.</details>

6. **Dê dois exemplos de bancos de dados relacionais e dois de bancos NoSQL.**
   <details><summary>Possível resposta</summary>Relacionais: PostgreSQL, MySQL. NoSQL: MongoDB, Redis.</details>

7. **Por que arquivos JSON em disco não são recomendados para sistemas concorrentes?**
   <details><summary>Possível resposta</summary>Porque não possuem controle de acesso concorrente (trava de linha/tabela) nem suporte nativo a transações e integridade relacional.</details>

8. **O que garante a propriedade de Durabilidade em um SGBD?**
   <details><summary>Possível resposta</summary>Garante que, uma vez confirmado o *commit*, as alterações são salvas permanentemente em meio não-volátil (disco), resistindo a falhas de energia.</details>
