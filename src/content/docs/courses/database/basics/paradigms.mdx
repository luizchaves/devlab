Este tópico responde à pergunta que vem antes de escolher um motor: **que forma os dados vão ter?** Tabelas com junções, documentos aninhados, pares de chave e valor, colunas por família, nós e arestas em grafos, fluxos temporais ou vetores matemáticos são respostas diferentes, e cada uma torna algumas consultas instantâneas e outras impraticáveis. "NoSQL" nomeou as primeiras alternativas ao modelo relacional, mas o ecossistema atual vai além.

## Objetivo

Compreender os paradigmas fundamentais e especializados de banco de dados como modelos estruturais distintos, com garantias, formas de indexação e consultas próprias, para escolher a família arquitetural adequada antes do motor e reconhecer quando um projeto está usando o modelo errado. Ao final do tópico, o leitor deve ser capaz de:

- Classificar dados em estruturados, semiestruturados e não estruturados, identificando os repositórios adequados para cada formato.
- Compreender o papel do armazenamento de objetos (*Object Storage* como Amazon S3, Google Cloud Storage, Azure Blob Storage, Cloudflare R2 e MinIO) na persistência de dados não estruturados e sua integração com bancos de dados.
- Descrever o modelo de dados de cada paradigma e a unidade elementar que ele armazena.
- Identificar as consultas que cada modelo faz com eficiência nativa e as que ele não atende.
- Explicar o que a sigla "NoSQL" agrupa historicamente e como os motores modernos se tornaram multiparadigma.
- Diferenciar os modelos clássicos dos paradigmas especializados (séries temporais, vetores, busca textual e geoespacial).
- Aplicar o teorema CAP como critério para sistemas distribuídos, sem exagerar o seu alcance.
- Escolher o paradigma de um projeto a partir da forma dos dados, dos requisitos de consulta e da escala.

## Tipos de Estrutura de Dados: Estruturados, Semiestruturados e Não Estruturados

Antes de decidir entre uma tabela relacional, uma coleção de documentos NoSQL ou um balde de armazenamento em nuvem, é essencial categorizar os dados de acordo com o seu grau de formatação e previsibilidade:

{`

    end
`}
</Mermaid>

A compreensão dessa classificação evita o erro clássico de tentar forçar arquivos binários pesados dentro de bancos relacionais ou de dispensar esquemas onde a integridade é mandatória.

### Dados Estruturados (Structured Data)

Os **dados estruturados** seguem um esquema fixo e estrito definido previamente antes de qualquer gravação (*Schema-on-Write*). Todas as linhas de uma mesma tabela compartilham exatamente as mesmas colunas e tipos de dados (inteiros, datas, strings com tamanho delimitado):

- **Características**: Alta consistência, facilidade de indexação com árvores B-Tree, suporte completo à álgebra relacional e consultas declarativas com SQL.
- **Exemplos típicos**: Registros financeiros, transações bancárias, cadastros de clientes com CPF/CNPJ, tabelas contábeis e itens de pedidos.
- **Motores representativos**: PostgreSQL, MySQL, SQLite, MariaDB, SQL Server e Oracle Database.

### Dados Semiestruturados (Semi-Structured Data)

Os **dados semiestruturados** não possuem uma tabela rígida bidimensional, mas contêm marcadores, rótulos, tags ou estruturas de pares chave-valor que separam os elementos internamente (*Self-Describing Data*):

- **Características**: Esquema flexível ou dinâmico (*Schema-on-Read*), suporte a listas aninhadas, objetos embutidos e coexistência de registros com campos diferentes na mesma coleção.
- **Formatos universais**: JSON (*JavaScript Object Notation*), BSON (*Binary JSON*), XML, YAML e colunas `JSONB` em bancos relacionais.
- **Exemplos típicos**: Catálogos de comércio eletrônico (onde uma camiseta tem "tamanho" e "cor", enquanto um celular tem "processador" e "bateria"), feeds de redes sociais, mensagens de eventos em Kafka e configurações de sistemas.
- **Motores representativos**: MongoDB, Google Cloud Firestore, Amazon DynamoDB, Couchbase e Elasticsearch.

### Dados Não Estruturados e Armazenamento de Objetos (Object Storage)

Os **dados não estruturados** não possuem uma estrutura interna previsível ou delimitadores conceituais que um motor de banco de dados possa indexar diretamente através de campos de texto ou números:

- **Características**: São armazenados em blocos binários opacos (*Binary Large Objects - BLOBs*), consumindo de alguns megabytes a vários gigabytes por unidade.
- **Exemplos típicos**: Fotografias digitais (JPEG, PNG), transmissões de vídeo (MP4, HLS), gravações de áudio, documentos digitalizados em PDF, modelos de machine learning e arquivos de backup de infraestrutura.
- **Repositórios adequados (Object Storage / Blob Storage)**: **Amazon S3 (Simple Storage Service)**, **Azure Blob Storage**, **Google Cloud Storage (GCS)**, **Cloudflare R2** e **MinIO** (solução de código aberto compatível com a API do S3 para ambientes locais e Kubernetes).

<Aside type="caution" title="Por que NÃO salvar BLOBs (imagens e PDFs) dentro do Banco de Dados?">
  Embora bancos relacionais possuam o tipo `BLOB` / `BYTEA`, gravar arquivos pesados diretamente na tabela causa degradação crítica:
  1. **Poluição de Memória RAM**: Cada varredura de tabela ou leitura carrega dezenas de megabytes inúteis no pool de buffers do SGBD.
  2. **Backups Lentos e Gigantescos**: O dump lógico (`pg_dump`, `mysqldump`) e as réplicas de streaming sofrem gargalos desnecessários de I/O de rede e disco.
  3. **Custo Financeiro Desproporcional**: O gigabyte em SSD provisionado para banco de dados (ex: EBS gp3/io2) custa de 5 a 10 vezes mais do que o gigabyte em *Object Storage* (como Amazon S3 ou Cloudflare R2 com zero custo de saída).

  **A boa prática universal**: Salve o arquivo no **Amazon S3 / Blob Storage** e guarde no banco de dados relacional apenas o endereço URL (`https://...`), tamanho em bytes, MIME type e identificador do objeto.
</Aside>

### Matriz Comparativa de Estruturas de Dados

A tabela abaixo resume as propriedades fundamentais dos três tipos de estrutura:

| Dimensão | Dados Estruturados | Dados Semiestruturados | Dados Não Estruturados |
| :--- | :--- | :--- | :--- |
| **Esquema (*Schema*)** | Rígido e pré-definido (*Schema-on-Write*) | Flexível e auto-descritivo (*Schema-on-Read*) | Inexistente no conteúdo (apenas metadados externos) |
| **Formato Principal** | Linhas e colunas tabulares | JSON, BSON, XML, YAML | Binários puros (JPEG, MP4, PDF, ZIP) |
| **Linguagem / Protocolo** | SQL declarativo | MQL, Query DSL, APIs REST/JSON | Protocolo HTTP REST (S3 API: `PUT`, `GET`, `DELETE`) |
| **Mecanismo de Consulta** | Índices B-Tree, Hash, Junções relacionais | Índices em caminhos de atributos, inversão | Chave de caminho do objeto (*Bucket / Key*) e tags de metadados |
| **Repositório Primário** | PostgreSQL, MySQL, SQLite, Oracle | MongoDB, Firestore, DynamoDB, Redis | Amazon S3, Azure Blob Storage, Cloudflare R2, MinIO |
| **Custo por Gigabyte** | Mais alto (disco transacional de alta velocidade) | Médio (armazenamento NoSQL indexado) | Ultrabaixo (camadas Standard, Glacier e Archive) |

## Famílias de Bancos de Dados e Armazenamento

O ecossistema contemporâneo de persistência de dados divide-se em quatro grandes grupos arquiteturais:

1. **Bancos Relacionais (SQL)**:
   - **Relacional Tradicional (OLTP)**: Baseado em tabelas com esquemas rígidos (*schema-first*), chaves primárias, chaves estrangeiras e integridade transacional estrita (ACID). São a escolha padrão para sistemas de gestão (ERP, CRM), finanças e comércio eletrônico (como PostgreSQL, MySQL e SQLite).
   - **Relacional Distribuído (NewSQL)**: Combina a linguagem SQL padrão e as garantias ACID com escalabilidade horizontal transparente e replicação de consenso global (como CockroachDB, Cloud Spanner e TiDB).

2. **Bancos Não-Relacionais (NoSQL)**:
   - **Documentos**: Armazenam registros semiestruturados em formatos como JSON ou BSON. Cada documento é auto-descritivo e pode conter campos aninhados e esquemas flexíveis, facilitando o desenvolvimento ágil e a correspondência direta com objetos da aplicação (como MongoDB e Firestore).
   - **Chave-Valor (*Key-Value*)**: O modelo mais simples e veloz de persistência, baseado em tabelas hash em memória RAM indexadas por chaves únicas. Oferece latência sub-milissegundo para leitura e escrita, sendo ideal para sessões, filas e cache (como Redis e DynamoDB).
   - **Colunas Largas (*Wide-Column*)**: Agrupam os dados em famílias de colunas dinâmicas distribuídas por chaves de partição. São otimizados para escrita contínua em escala massiva de petabytes sem a necessidade de travas centralizadas (como Apache Cassandra e ScyllaDB).
   - **Grafos (*Graph*)**: Modelam as entidades como nós (vértices) e as relações como conexões explícitas (arestas) com propriedades associadas. Permitem percorrer redes complexas de múltiplos saltos com alto desempenho, sem a sobrecarga de sucessivos `JOIN` relacionais (como Neo4j e Neptune).

3. **Motores Especializados e Analíticos**:
   - **Analítico / OLAP (*Online Analytical Processing*)**: Organizam os dados em blocos orientados a colunas em vez de linhas. Esse formato permite compactação extrema e varredura de bilhões de registros por segundo para cálculos de agregação (`SUM`, `AVG`, `COUNT`), sendo a base de *Data Warehouses* e ferramentas de BI (como ClickHouse e DuckDB).
   - **Séries Temporais (*Time-Series*)**: Otimizados para gravação e consulta de fluxos contínuos de eventos cronológicos indexados por carimbos de data e hora (*timestamps*), oferecendo retenção automática e compressão de métricas de telemetria (como TimescaleDB e InfluxDB).
   - **Busca Textual (*Search Engines*)**: Utilizam índices invertidos e algoritmos de pontuação de relevância (como BM25 e TF-IDF) para viabilizar pesquisas flexíveis em linguagem natural, tolerância a erros de digitação e filtros facetados (como OpenSearch e Meilisearch).
   - **Geoespacial (*Spatial / GIS*)**: Incorporam tipos geométricos (pontos, polígonos, linhas e geometrias esferoidais) e estruturas de indexação multidimensional (R-Tree e GiST), permitindo consultas rápidas de raio, proximidade e sobreposição de rotas (como PostGIS e SpatiaLite).
   - **Vetorial (*Vector / AI*)**: Armazenam representações matemáticas (*embeddings*) geradas por modelos de inteligência artificial. Realizam buscas por vizinhos mais próximos aproximados (*ANN - Approximate Nearest Neighbor*) para suportar busca semântica e sistemas de Recuperação Aumentada por Geração (como pgvector, Qdrant e Milvus).

4. **Armazenamento em Nuvem (*Storage & Data Lakes*)**:
   - **Armazenamento de Objetos (*Object / Blob Storage*)**: Armazenamento elástico para arquivos binários opacos e dados não estruturados de qualquer tamanho (fotos, vídeos, relatórios em PDF, modelos de machine learning e logs brutos) indexados por identificador único (*bucket/key*), acessados via API HTTP REST com durabilidade de 99,999999999% (como Amazon S3, Google Cloud Storage, Azure Blob Storage, Cloudflare R2 e MinIO).
   - **Sistemas de Arquivos Compartilhados (*File Storage / NAS*)**: Armazenamento hierárquico com suporte a protocolos de rede como NFS e SMB para montagem concorrente em múltiplos servidores (como AWS EFS e Azure Files).
   - **Armazenamento em Bloco (*Block Storage*)**: Discos virtuais de baixa latência anexados a máquinas virtuais para sustentar o próprio sistema de arquivos do SGBD (como AWS EBS, Google Persistent Disk e Azure Managed Disks).

## Formas Fundamentais de Guardar Dados

A tabela abaixo apresenta os paradigmas pela unidade que armazenam, pelo seu mecanismo definidor, pelos motores nativos de código aberto e pelos equivalentes em nuvem gerenciada (DBaaS):

| Paradigma | Unidade Armazenada | O que o define | Motores Nativos / Open Source | Bancos de Nuvem / DBaaS |
| :--- | :--- | :--- | :--- | :--- |
| **Relacional (SQL)** | Linha em tabela com esquema rígido | Junções (`JOIN`), restrições de integridade e transações ACID | PostgreSQL, MySQL, SQLite, MariaDB | Supabase, Neon, Turso, AWS RDS/Aurora, Cloud SQL |
| **Documentos** | Documento semiestruturado em coleção | Esquema flexível (JSON/BSON), leitura de agregados e modelagem por telas | MongoDB, CouchDB, Couchbase | MongoDB Atlas, Cloud Firestore, AWS DocumentDB, Cosmos DB |
| **Chave-valor** | Valor opaco indexado por chave | Acesso direto por chave em memória com latência sub-milissegundo | Redis, Valkey, Memcached, RocksDB | Upstash Redis, AWS DynamoDB, AWS ElastiCache, Memorystore |
| **Colunar Amplo (Wide-Column)** | Famílias de colunas distribuídas por partição | Escrita massiva distribuída e tolerância a falhas sem travas centralizadas | Apache Cassandra, ScyllaDB, Apache HBase | DataStax Astra DB, AWS Keyspaces, Cloud Bigtable, Cosmos DB |
| **Grafos** | Nós (vértices) e arestas com propriedades | Travessia de redes e caminhos complexos (*Index-Free Adjacency*) | Neo4j, Memgraph, Apache TinkerPop | Neo4j AuraDB, AWS Neptune, Cloud Spanner Graph |
| **Séries Temporais** | Evento ordenado por *timestamp* | Ingestão contínua de telemetria, janelamento temporal e compressão | InfluxDB, TimescaleDB, Prometheus | InfluxDB Cloud, AWS Timestream, Timescale Cloud |
| **Busca Textual** | Documento indexado em estrutura invertida | Análise léxica, tokenização, busca aproximada e relevância BM25 | Elasticsearch, OpenSearch, Meilisearch | Elastic Cloud, AWS OpenSearch Service, Algolia |
| **Analítico (OLAP)** | Blocos de dados orientados a colunas | Varredura de bilhões de linhas para agregações analíticas (`SUM`, `AVG`) | ClickHouse, DuckDB, Apache Druid | Google BigQuery, Snowflake, AWS Redshift |
| **Vetorial** | Vetores numéricos (*embeddings*) | Busca por similaridade semântica via algoritmos de vizinhos mais próximos (ANN) | pgvector, Qdrant, Milvus, Chroma | Pinecone, Qdrant Cloud, Vertex AI Vector Search |
| **Geoespacial** | Geometrias e geografias (pontos e polígonos) | Indexação espacial multidimensional (R-Tree, GiST) para cálculos de raio | PostGIS, SpatiaLite, MySQL Spatial | AWS Location Service, Azure Maps, BigQuery GIS |
| **Armazenamento de Objetos (Object / Blob)** | Objeto binário (*BLOB*) com metadados | Acesso direto via HTTP REST (`PUT`/`GET`), escala ilimitada e custo por GB ultrabaixo | MinIO, Ceph, SeaweedFS | Amazon S3, Azure Blob Storage, Cloudflare R2, Google Cloud Storage |

## O Que Cada Paradigma Abre Mão e Ganha

O termo "NoSQL" surgiu para nomear bancos que abriam mão do modelo relacional tradicional, mas a especialização de bancos modernos vai além da oposição SQL versus NoSQL. Cada paradigma foi desenhado para maximizar a eficiência de um tipo específico de acesso e estrutura, abrindo mão de garantias generalistas em favor de desempenho extremo:

A tabela abaixo sintetiza os trade-offs arquiteturais de cada família:

| Paradigma | Abre mão de | Ganha |
| --- | --- | --- |
| **Documentos** | Junções nativas eficientes e esquema rígido | Leitura de um bloco, flexibilidade de evolução e partição por documento |
| **Chave-valor** | Consultas ricas por conteúdo interno | Latência mínima em memória e escala linear por chave |
| **Colunar (OLAP / Wide-Column)** | Transações atômicas por linha e escritas pontuais | Escrita massiva contínua, compressão agressiva e agregações em bilhões de registros |
| **Grafos** | Particionamento e escala horizontal trivial | Travessia de redes de relacionamento em múltiplos níveis sem explosão combinatória |
| **Séries Temporais** | Atualizações arbitrárias no passado (*random updates*) | Ingestão sequencial de alta vazão, agregações por janelas e expiração automática |
| **Vetorial** | Correspondência exata e determinística | Busca por similaridade semântica em alta dimensão para IA e RAG |
| **Busca Textual** | Consistência imediata e garantias ACID rígidas | Tolerância a erros fonéticos, lematização, sinônimos e pontuação BM25 |
| **Geoespacial** | Estruturas de índices unidimensionais simples | Cálculos geodésicos exatos, intersecções e consultas de proximidade espacial |
| **Armazenamento de Objetos (Object / Blob)** | Consultas ricas por conteúdo interno e transações ACID | Capacidade elástica ilimitada, custo insignificante por GB, durabilidade de 11 noves e CDN global |
| **Armazenamento de Arquivos em Rede (NAS / File)** | Consultas estruturadas e particionamento em hiperescala | Hierarquia de diretórios padrão POSIX compartilhada entre múltiplos servidores via NFS |

O modelo relacional, por sua vez, abre mão da especialização extrema e da partição horizontal automática, mas entrega a combinação de junções, restrições declarativas e transações ACID completas entre tabelas, funcionando como a fundação mais segura e versátil para a grande maioria das aplicações.

<Aside type="tip" title="O relacional se tornou multiparadigma">
O `JSONB` e o `pgvector` do PostgreSQL, o tipo `JSON` do MySQL e o suporte a dados geoespaciais (PostGIS e SpatiaLite) mostram como os motores relacionais modernos absorveram boa parte dos paradigmas NoSQL e especializados. Um campo de formulário dinâmico, coordenadas GPS ou embeddings de IA cabem em colunas relacionais sem a necessidade de fragmentar a arquitetura em vários bancos separados.
</Aside>

## Quando usar, e quando não usar?

A escolha do paradigma parte de três perguntas: qual é a forma natural dos dados, quais consultas são frequentes, e quanto precisa escalar. A tabela abaixo cruza cenários com a resposta que costuma vencer:

| Cenário | Paradigma Recomendado | Por quê |
| --- | --- | --- |
| Aplicação de negócio com entidades relacionadas, relatórios e transações | **Relacional ([PostgreSQL](../../postgresql/) / [MySQL](../../mysql/) / [SQLite](../../sqlite/))** | Junções, restrições e ACID entre tabelas são o núcleo do problema. |
| Catálogo, conteúdo, eventos com forma variável, lidos em bloco | **Documentos ([MongoDB](../../mongodb/))** | Cada item tem os próprios campos; a tela lê um documento. |
| Aplicativo móvel com sincronização em tempo real e uso offline | **Documentos ([Firestore](../../../cloud/firebase/firestore/))** | O SDK resolve cache local e reconciliação remota. |
| Sessão, cache, contador, fila leve, limite de requisições (*rate limit*) | **Chave-valor ([Redis](../../redis/))** | Acesso por chave em microssegundos; sem consulta por conteúdo. |
| Telemetria, métricas de servidores, sensores IoT e cotações | **Séries Temporais ([InfluxDB](../../influxdb/))** | Ingestão contínua com agregação temporal e descarte de dados velhos. |
| Busca semântica, agentes inteligentes e RAG para LLMs | **Vetorial** (pgvector/Qdrant) | Busca por proximidade de conceitos e similaridade em vetores. |
| Busca em e-commerce com tolerância a erros e filtros facetados | **Busca Textual ([Elasticsearch](../../elasticsearch/))** | Índices invertidos, relevância e autocompletar instantâneo. |
| Rotas de entrega, geofencing e proximidade de motoristas | **Geoespacial** (PostGIS/SpatiaLite) | Tipos geométricos nativos e índices espaciais (R-Tree/GiST). |
| Arquivos de mídia (fotos, vídeos, PDFs, modelos de IA) e backups | **[Object Storage](../../../cloud/resources/file-storage/) (Amazon S3 / Blob Storage / MinIO)** | Custo por GB ultrabaixo, durabilidade de 11 noves, CDN na borda e não sobrecarrega a RAM do banco. |
| Diretórios compartilhados entre múltiplos servidores ou containers (POSIX/NFS) | **[File Storage / NAS](../../../cloud/resources/file-storage/) (AWS EFS / Azure Files)** | Sistema de arquivos hierárquico padrão montado diretamente no sistema operacional. |
| Disco de alta performance para o próprio motor do banco de dados (I/O intensivo) | **Block Storage (AWS EBS / Persistent Disk)** | Latência em microssegundos com IOPS dedicados para sustentar as tabelas do SGBD. |
| *Data Warehouse*, análise histórica de métricas e BI | **Colunar / OLAP** (ClickHouse/DuckDB) | Varreduras e somas sobre bilhões de linhas em frações de segundo. |
| Escrita distribuída em escala massiva de bilhões de eventos | **Colunar Amplo ([Cassandra](../../cassandra/))** | Arquitetura *masterless* de alta vazão sem ponto único de falha. |
| Recomendação, rede social profunda, detecção de fraude por conexões | **Grafos ([Neo4j](../../neo4j/))** | "Amigos de amigos até o quarto nível" é um percurso em grafo. |
| Campo variável dentro de um modelo relacional corporativo | **Relacional com JSONB** | Sem complexidade operacional de manter dois bancos distintos. |
| Projeto novo sem escala definida | **Relacional ([PostgreSQL](../../postgresql/) / [MySQL](../../mysql/) / [SQLite](../../sqlite/))** | Abrange mais casos; a especialização ocorre sob demanda comprovada. |

A última linha é o conselho padrão do guia: começar no relacional não é conservadorismo, é a escolha que mais tarde se revela certa com mais frequência, e a que deixa o caminho aberto para acrescentar um chave-valor para cache ou extensões especializadas sem migrar o modelo inteiro.

<Aside type="caution" title="Dica de IA: Peça a consulta que o paradigma não faz">
  Ao pedir "qual banco para o meu projeto", assistentes respondem com a lista de virtudes do paradigma sugerido e omitem o que ele não faz. Um MongoDB recomendado para um sistema de pedidos vai bem até o primeiro relatório que cruza clientes, produtos e pedidos.

## Exercício

Responda com base na tabela de paradigmas e nas seções de estrutura e NoSQL:

1. Qual a diferença fundamental entre dados estruturados, semiestruturados e não estruturados?
2. Por que é considerado um antipadrão gravar imagens e arquivos PDF pesados diretamente em colunas `BLOB` de um banco relacional?
3. O que o relacional abre mão que os NoSQL ganham, e o que ele garante que eles não garantem?
4. Um projeto roda em um único servidor de banco. O teorema CAP se aplica a ele?

<details>
  <summary>Possível resposta</summary>

  1. Dados estruturados possuem esquema rígido e tipado na escrita (*schema-on-write*, como tabelas SQL). Semiestruturados possuem marcadores e flexibilidade interna (*schema-on-read*, como JSON/BSON). Não estruturados são binários opacos sem estrutura delimitada pelo banco (como vídeos, fotos e PDFs).

  2. Porque degrada a performance do pool de memória RAM do banco, infla os tempos de backup/dump, encarece o custo de armazenamento (SSD transacional vs Object Storage) e sobrecarrega a rede do SGBD. A boa prática é guardar o binário no Object Storage (S3/Blob Storage) e apenas a URL/metadados no banco.

  3. Abre mão da escala horizontal fácil, que exige particionar tabelas entre servidores. Garante junções, restrições entre tabelas e transações entre tabelas, que os outros paradigmas oferecem parcialmente ou não oferecem.

  4. Não. O CAP trata do comportamento durante uma partição de rede entre servidores; com um servidor só, não há partição possível, e as garantias são as ACID do próprio motor.
</details>

## Desafio

Pegue o modelo de rede social do projeto `invest-db` (`modeling/social-feed.sql`) e escreva, para cada um dos cinco paradigmas, como a consulta "sugestões de pessoas para seguir: quem os que eu sigo seguem, e eu não sigo" seria expressa, ou por que não seria.

Depois responda: em qual paradigma ela é natural, em qual é possível e cara, e o que acontece com o relacional quando a profundidade passa a ser "até o quarto nível"?

<details>
  <summary>Possível resposta</summary>

  No relacional, a consulta é uma autojunção dupla em `follow` com `NOT EXISTS` para excluir quem já sigo, e funciona bem em dois níveis. Em documentos, exige guardar a lista de seguidos em cada conta e fazer duas leituras (a minha lista, e a lista de cada seguido), com o `$lookup` como alternativa cara. Em chave-valor, é `SMEMBERS` da lista de cada seguido mais operações de conjunto no Redis, que resolve bem exatamente esse caso, com `SDIFF`. No colunar, não é uma consulta para a qual ele foi feito. Em grafos, é o caso natural: `MATCH (eu)-[:SEGUE]->()-[:SEGUE]->(s) WHERE NOT (eu)-[:SEGUE]->(s)`.

  No relacional, cada nível é mais uma autojunção, e no quarto nível a consulta tem quatro junções sobre a mesma tabela com um produto que cresce exponencialmente; `WITH RECURSIVE` a expressa, mas o custo continua. É a fronteira em que o grafo deixa de ser luxo e vira a ferramenta certa, e é raro uma aplicação chegar a ela.
</details>

## Perguntas de revisão

### Estrutura e Paradigmas

1. **Qual é a unidade de armazenamento de cada paradigma e onde residem os dados não estruturados?**
   <details><summary>Possível resposta</summary>Relacional: linha em tabela. Documentos: documento em coleção. Chave-valor: valor por chave. Colunar: colunas por família. Grafos: nós e arestas. Não estruturados: objetos binários em Object Storage (S3, Azure Blob, GCS, MinIO).</details>

2. **Por que o colunar é rápido para somar uma coluna e lento para ler uma linha inteira?**
   <details><summary>Possível resposta</summary>Porque guarda cada coluna separada: somar uma coluna lê só ela, em sequência; ler uma linha inteira exige reunir o valor de cada coluna, espalhado.</details>

3. **Que consulta define o paradigma de grafos?**
   <details><summary>Possível resposta</summary>O percurso de relações em profundidade arbitrária, como "amigos de amigos de amigos", que no relacional exige uma junção por nível.</details>

### Escolha e Arquitetura

4. **O que o `JSONB` do PostgreSQL absorveu do paradigma de documentos, e o que não absorveu?**
   <details><summary>Possível resposta</summary>Absorveu o documento consultável e indexável dentro da linha. Não absorveu a partição horizontal por documento nem a sincronização com o cliente.</details>

5. **Como um banco de dados relacional e um balde S3 colaboram na gestão de uploads de usuários?**
   <details><summary>Possível resposta</summary>O arquivo binário é enviado ao S3/Blob Storage (frequentemente via URLs pré-assinadas), e a API salva no banco relacional apenas o registro com metadados (ID do usuário, nome original, tamanho, data e a URL/chave do objeto no S3).</details>

6. **O que os sistemas AP fazem durante uma partição, e o que isso custa?**
   <details><summary>Possível resposta</summary>Continuam respondendo em todos os servidores, aceitando que as respostas divirjam até a reconciliação. Custa consistência eventual: uma leitura pode devolver um valor antigo por um tempo.</details>

7. **Por que o guia recomenda começar no relacional?**
   <details><summary>Possível resposta</summary>Porque abrange mais casos, e um chave-valor para cache ou um documento para um campo podem ser acrescentados depois sem migrar o modelo. A troca de paradigma, se vier, terá um motivo medido.</details>
