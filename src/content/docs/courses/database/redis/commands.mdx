O verdadeiro poder do **Redis** reside no seu rico conjunto de tipos de dados. Em vez de tratar todos os registros como strings cegas serializadas, a aplicação manipula diretamente estruturas como listas encadeadas, mapas hash e tabelas de pontuação ordenadas com complexidade computacional ótima ($O(1)$ ou $O(\log N)$).

## Objetivo

Dominar as estruturas de dados nativas do Redis e seus respectivos comandos no contexto de aplicações web, aplicando padrões de cache, filas de processamento e limitação de taxa de requisições (*rate limiting*). Ao final do tópico, o leitor deve ser capaz de:

- Escolher e manipular as 5 estruturas fundamentais: Strings, Hashes, Lists, Sets e Sorted Sets.
- Configurar políticas de expiração automática com `EXPIRE` e `SET ... EX`.
- Utilizar blocos transacionais com `MULTI` e `EXEC`.
- Implementar padrões práticos de cache (*Cache-Aside*) e contadores de taxa de requisições.

## Principais Estruturas e seus Comandos

A tabela abaixo resume os comandos mais utilizados por tipo de dado:

| Estrutura | Comandos Chave | Complexidade | Uso Típico no Desenvolvimento Web |
| :--- | :--- | :--- | :--- |
| **String** | `SET`, `GET`, `INCR`, `SETEX`, `MGET` | $O(1)$ | Cache de respostas JSON, contadores de visualização, tokens de sessão. |
| **Hash** | `HSET`, `HGET`, `HGETALL`, `HINCRBYFLOAT` | $O(1)$ por campo | Objetos estruturados (perfil de usuário, dados de um ativo de investimento). |
| **List** | `LPUSH`, `RPUSH`, `LPOP`, `RPOP`, `LRANGE` | $O(1)$ nas pontas | Histórico de atividades recentes, filas de mensagens do tipo FIFO/LIFO. |
| **Set** | `SADD`, `SMEMBERS`, `SISMEMBER`, `SINTER` | $O(1)$ por item | Tags únicas, categorias sem repetição, controle de permissões. |
| **Sorted Set** | `ZADD`, `ZRANGE`, `ZREVRANGE`, `ZSCORE` | $O(\log N)$ | Placares (*leaderboards*), rankings de rentabilidade, filas de prioridade. |

## Padrões Práticos de Engenharia

### 1. Padrão Cache-Aside (Leitura com Fallback)

No padrão *Cache-Aside*, a aplicação tenta ler o dado do Redis primeiro. Se o dado não existir (*cache miss*), busca no banco relacional (ex: PostgreSQL), salva no Redis com um tempo de expiração e devolve a resposta:

```bash
# 1. Consulta tenta ler a chave de cache
GET cache:asset:VALE3

# 2. Em caso de ausência (nil), a aplicação consulta o PostgreSQL e salva no Redis por 10 minutos
SET cache:asset:VALE3 '{"name":"Vale S.A.","price":65.20}' EX 600
```

### 2. Rate Limiting por Janela Temporal

Para limitar requisições de uma API a 100 chamadas por minuto por usuário:

```bash
# Incrementa a contagem de requisições do usuário no minuto atual
INCR rate_limit:user:123:min:45

# Se for a primeira requisição da chave, define o TTL de 60 segundos
EXPIRE rate_limit:user:123:min:45 60
```

## Transações Atômicas com MULTI / EXEC

Diferente do SQL com isolamentos complexos, uma transação no Redis enfileira comandos sequenciais e os executa de forma estritamente atômica e ininterrupta:

```bash
MULTI
HINCRBYFLOAT investment:1 value -500.00
HINCRBYFLOAT investment:2 value 500.00
EXEC
```

Se a transação for interrompida ou cancelada com `DISCARD`, nenhum comando intermediário é aplicado.

## Exercício

Com base nos comandos apresentados:

1. Como registrar no Redis uma lista com as 3 últimas transações de um usuário de forma que apenas os 10 registros mais recentes sejam mantidos em memória?
2. Qual comando verifica em tempo $O(1)$ se a tag `"Ações"` pertence ao conjunto de categorias ativas do sistema?
3. Qual comando recupera os 3 investidores com maior patrimônio em um Sorted Set `leaderboard:investors`?

<details>
  <summary>Possível resposta</summary>

  1. Utiliza-se `LPUSH` para inserir a nova transação no início da lista e `LTRIM` para podar a lista mantendo apenas os índices de 0 a 9:
     ```text
     LPUSH user:1:transactions "BUY: PETR4 1000.00"
     LTRIM user:1:transactions 0 9
     ```

  2. Utiliza-se o comando `SISMEMBER`:
     ```text
     SISMEMBER categories "Ações"
     ```

  3. Utiliza-se o comando `ZREVRANGE`:
     ```text
     ZREVRANGE leaderboard:investors 0 2 WITHSCORES
     ```
</details>

## Desafio

Um sistema de votação em tempo real precisa registrar o voto de milhares de usuários em diferentes ativos de investimento, garantindo duas regras:
1. Cada usuário só pode votar uma única vez por dia.
2. O sistema deve devolver o ranking instantâneo dos ativos mais votados.

Desenhe os comandos Redis necessários para atender aos dois requisitos simultaneamente.

<details>
  <summary>Possível resposta</summary>

  1. Para garantir que o usuário vote apenas uma vez no dia, usamos um `Set` por dia com expiração de 24 horas:
     ```text
     # SADD retorna 1 se o usuário foi adicionado (primeiro voto) ou 0 se já votou
     SADD daily_votes:2024-03-11 "user:42"
     EXPIRE daily_votes:2024-03-11 86400
     ```

  2. Se `SADD` retornou 1, incrementa a pontuação do ativo no `Sorted Set` do dia:
     ```text
     ZINCRBY asset_votes:2024-03-11 1 "VALE3"
     ```

  3. Para obter os 5 ativos mais votados:
     ```text
     ZREVRANGE asset_votes:2024-03-11 0 4 WITHSCORES
     ```
</details>

## Perguntas de revisão

1. **Qual a diferença entre um Set e um Sorted Set?**
   <details><summary>Possível resposta</summary>Um Set guarda elementos únicos sem ordem garantida. Um Sorted Set associa a cada elemento único um valor numérico (*score*), mantendo a coleção ordenada permanentemente pela pontuação.</details>

2. **O comando `KEYS *` deve ser executado em ambientes de produção?**
   <details><summary>Possível resposta</summary>Não. O `KEYS *` varre toda a base bloqueando o event-loop do Redis até terminar, o que pode paralisar a aplicação. A alternativa segura para varreduras é o comando paginado `SCAN`.</details>

3. **Qual é o comportamento do comando `HINCRBYFLOAT`?**
   <details><summary>Possível resposta</summary>Incrementa o valor numérico de ponto flutuante de um campo específico dentro de um Hash de forma atômica.</details>
