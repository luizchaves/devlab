Este tópico apresenta as principais opções de bancos de dados orientados a famílias de colunas gerenciados na nuvem (*Managed Wide-Column DBaaS*): o **DataStax Astra DB** (banco serverless nativo em nuvem construído sobre o Apache Cassandra com suporte a busca vetorial e APIs JSON) e o **Amazon Keyspaces** (serviço gerenciado e serverless compatível com o Apache Cassandra da AWS).

---

## Objetivo

Compreender a transformação operacional do Apache Cassandra ao ser executado como um serviço gerenciado serverless na nuvem pública. Ao final do tópico, o leitor deve ser capaz de:

- Descrever como o DataStax Astra DB e o Amazon Keyspaces desacoplam a computação do armazenamento distribuído, eliminando a manutenção manual de anéis de nós (*Cassandra Rings*).
- Compreender a compatibilidade com a linguagem de consulta **CQL (Cassandra Query Language)** e drivers oficiais de mercado.
- Identificar as vantagens do modelo de capacidade sob demanda (*Serverless On-Demand*) frente ao provisionamento estático de nós EC2.
- Explicar o suporte a busca vetorial e APIs de documentos no Astra DB (*Vector Search* e *Data API*).
- Escolher a solução colunar adequada para cargas massivas de telemetria, streaming e mensageria de alta vazão.

---

## A Eliminação do Custo Operacional do Cassandra

O Apache Cassandra tradicional é famoso pela sua escalabilidade linear inigualável e arquitetura sem ponto único de falha (*Masterless*), mas sua administração manual exige tarefas complexas de reparo de nós (*Node Repair*), compactação de SSTables e rebalanceamento de anéis de nós:

<Mermaid title="Evolução do Cassandra tradicional para serviços gerenciados serverless">
{`
flowchart TD
    subgraph Traditional ["Cassandra Tradicional (Self-Hosted)"]
        T1["Anel de Nós Físicos (Ring)"] --> T2["Reparos Manuais (nodetool repair)"]
        T2 --> T3["Gerenciamento de GC na JVM e Discos EBS"]
    end

    subgraph ModernCloud ["DBaaS Serverless (Astra DB / Amazon Keyspaces)"]
        C1["Camada de Computação Elástica (Stateless CQL Gateways)"]
        C2["Camada de Armazenamento Replicada em 3 Zonas (NVMe / S3)"]
        C1 --> C2
    end
`}
</Mermaid>

Ao migrar para Astra DB ou Amazon Keyspaces, o desenvolvedor consome a potência do CQL sem a necessidade de configurar parâmetros internos da máquina virtual Java (JVM) ou executar utilitários de linha de comando `nodetool`.

## DataStax Astra DB: Cassandra Serverless e Busca Vetorial

O **DataStax Astra DB** é a plataforma de dados em nuvem da DataStax baseada no Apache Cassandra, disponível na AWS, Google Cloud e Microsoft Azure:

<Mermaid title="Arquitetura do DataStax Astra DB com Vector Search e Data API">
{`
flowchart LR
    App["Aplicações Web / IA / Microserviços"] --> Router["Astra DB Gateway (Serverless)"]

    subgraph AstraCore ["Motor Astra DB Multinuvem"]
        Router --> CQL["Driver CQL Nativo (Porta 9042)"]
        Router --> JSON["Data API (Documentos JSON sem CQL)"]
        Router --> Vector["Vector Search (HNSW Integrado)"]
    end

    AstraCore --> Storage[("Armazenamento Distribuído Autoescalável")]
`}
</Mermaid>

Os principais diferenciais do DataStax Astra DB incluem:

1. **Arquitetura 100% Serverless**: Capacidade de escrita e leitura elástica com *scale-to-zero*, pagando apenas pelas operações realizadas (leituras, escritas e armazenamento consumido).
2. **Astra Vector Search**: Permite indexar e consultar vetores de alta dimensionalidade para aplicações de IA generativa (RAG) combinados com a escalabilidade de bilhões de registros do Cassandra.
3. **Data API (JSON API)**: Permite que desenvolvedores manipulem dados com sintaxe intuitiva de documentos JSON sem precisar escrever declarações CQL formais.
4. **Camada Gratuita Mensal**: Créditos mensais perpétuos para desenvolvimento e testes de novos projetos.

## Amazon Keyspaces: O Cassandra Nativo da AWS

O **Amazon Keyspaces (for Apache Cassandra)** é o serviço compatível com CQL totalmente gerenciado da AWS:

<Mermaid title="Arquitetura de alta disponibilidade do Amazon Keyspaces">
{`
flowchart TD
    App["Aplicações com Drivers Cassandra (Java, Python, Node.js, Go)"] --> KS[("Amazon Keyspaces Endpoint")]

    subgraph AWSInfra ["Infraestrutura Multi-AZ Gerenciada"]
        KS --> AZ1["Armazenamento Replicado na Zona A"]
        KS --> AZ2["Armazenamento Replicado na Zona B"]
        KS --> AZ3["Armazenamento Replicado na Zona C"]
    end

    KS --> PITR["Point-in-Time Recovery (PITR)"]
    KS --> KMS["Criptografia em Repouso AWS KMS"]
`}
</Mermaid>

Os pilares do Amazon Keyspaces abrangem:

1. **Compatibilidade Total com CQL**: Reutilize códigos e drivers existentes do Cassandra 3.11 e 4.x sem alteração nas consultas SQL/CQL da aplicação.
2. **Capacidade Sob Demanda ou Provisionada**: Modos de faturamento flexíveis que atendem desde tráfego imprevisível até picos agendados de milhões de transações por segundo.
3. **Point-In-Time Recovery (PITR)**: Restauração de dados contínua para qualquer segundo dos últimos 35 dias com proteção contra exclusões acidentais.
4. **Integração com o Ecossistema AWS**: Autenticação via SigV4 do AWS IAM, métricas no CloudWatch e trilhas de auditoria no CloudTrail.

## Comparativo: DataStax Astra DB vs. Amazon Keyspaces

A tabela abaixo resume as principais distinções entre as ofertas colunares:

| Característica | DataStax Astra DB | Amazon Keyspaces |
| :--- | :--- | :--- |
| **Provedores de Nuvem** | Multinuvem (AWS, GCP, Azure) | Exclusivo da AWS |
| **Recursos de IA** | Busca vetorial nativa (*Vector Search*) e Data API | Focado no suporte CQL tradicional com integrações AWS |
| **Modo de Operação** | Puramente Serverless (com tier gratuito mensal) | Serverless On-Demand ou Capacidade Provisionada |
| **Protocolos de Acesso** | CQL (gRPC / Porta 9042), REST, GraphQL, JSON API | CQL nativo via TLS (Porta 9142) |
| **Backups e Restauração** | Snapshots e restauração elástica | Point-In-Time Recovery (PITR) nativo de 35 dias |
| **Ideal para** | Aplicações modernas de IA, multinuvem e APIs JSON | Cargas corporativas consolidadas no ecossistema AWS |

## Quando usar, e quando não usar?

A escolha por bancos colunares amplos na nuvem deve ser orientada pelo volume massivo de gravações:

| Cenário | Escolha | Por quê |
| :--- | :--- | :--- |
| Aplicação global de telemetria com milhões de escritas/segundo e consultas por chave primária | **[DataStax Astra DB](../cassandra/) / Amazon Keyspaces** | Escalabilidade horizontal ilimitada, replicação geográfica e zero paradas. |
| Sistemas de Inteligência Artificial que necessitam de RAG sobre bilhões de vetores | **DataStax Astra DB (Vector)** | Une a escala colunar com indexação vetorial de alto desempenho. |
| Aplicações que realizam consultas com filtros ad-hoc em múltiplas colunas arbitrárias | **[Elasticsearch](../elasticsearch/) / [OpenSearch](../elastic-cloud-opensearch/)** | Índices invertidos são feitos para buscas flexíveis; Cassandra exige chave primária estrita. |
| Sistemas transacionais com integridade referencial complexa e transações ACID multi-tabela | **[Amazon Aurora / RDS](../rds-aurora/)** | Chaves estrangeiras, junções relacionais e ACID rigoroso. |

## Desafio

Uma plataforma global de música em streaming precisa registrar o histórico de reproduções (*scrobbles*) de 100 milhões de usuários diários:
- Cada usuário reproduz cerca de 30 faixas por dia (3 bilhões de eventos diários).
- A consulta mais comum na interface é recuperar as últimas 50 músicas tocadas por um usuário específico.
- Modele a tabela CQL (`CREATE TABLE`) com a Partition Key e Clustering Key adequadas e justifique a escolha do Astra DB ou Amazon Keyspaces.

## Perguntas de revisão

<details>
<summary>1. Como o Astra DB viabiliza o modelo scale-to-zero sem desligar o Cassandra?</summary>
O Astra DB desacoplou a camada de roteamento e computação CQL da camada de armazenamento distribuído em disco. Quando não há requisições ativas, os gateways de computação e recursos efêmeros são desalocados, mantendo apenas os dados comprimidos na camada de armazenamento durável, reduzindo os custos de ociosidade a zero.
</details>

<details>
<summary>2. Por que consultas sem a Partition Key (utilizando ALLOW FILTERING) devem ser evitadas em produção?</summary>
No Cassandra e em serviços compatíveis, omitir a *Partition Key* força o banco a enviar a consulta para todos os nós ou partições do cluster sequencialmente (*Full Cluster Scan*), degradando severamente a latência e consumindo recursos desproporcionais de capacidade.
</details>
