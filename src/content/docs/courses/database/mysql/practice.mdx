Esta prática guiada conduz você pela construção incremental e exploração analítica de um banco de dados real de monitoramento de infraestrutura de rede, o **`monitor_db`**. Inspirada no estudo de caso clássico do MonitorApp e nas diretrizes de formação do IFPB, você partirá de um arquivo de telemetria bruto em formato **`.csv`**, estruturará as tabelas normalizadas no MySQL, carregará e distribuirá os dados, resolverá problemas reais de conectividade com consultas analíticas e, ao final, gerará o arquivo de backup completo com `mysqldump`.

## Objetivo

Consolidar na prática os comandos e recursos fundamentais do MySQL e da linguagem SQL, evoluindo um banco de dados desde a importação de arquivos CSV brutos até a modelagem relacional na 3FN com consultas analíticas, visões e procedimentos armazenados. Ao final do tópico, o leitor deve ser capaz de:

- Inspecionar e importar conjuntos de dados externos em formato delimitado (`.csv`) para tabelas intermediárias de *staging*.
- Executar comandos DDL incrementais para criar bancos de dados, tabelas, restrições e índices no MySQL.
- Distribuir e normalizar dados brutos em entidades relacionais (`hosts`, `tags`, `pings`, `stats`) preservando a integridade referencial.
- Responder a perguntas analíticas de latência, disponibilidade e perda de pacotes com junções múltiplas, funções agregadoras e filtros temporais.
- Empregar funções nativas do MySQL para manipulação de strings, cálculos matemáticos, formatação de datas e classificação condicional com `CASE`.
- Criar visões analíticas (*Views*) e procedimentos armazenados (*Stored Procedures*) com parâmetros de entrada e saída.
- Exportar o banco de dados final em um arquivo de backup lógico estruturado através do utilitário `mysqldump`.

## 1. DDL: Criação do Banco e Tabelas Relacionais

Iniciaremos inspecionando o servidor MySQL e criando o banco de dados e as tabelas normalizadas.

### 1.1 Criação do Banco de Dados
Primeiro, verificamos os bancos existentes no servidor e criamos o banco de dados `monitor_db`:

```sql title="Comandos DDL: Criação do Banco de Dados"
-- Lista os bancos gerenciados pelo servidor MySQL
SHOW DATABASES;

-- Cria o banco com suporte completo ao padrão UTF-8
CREATE DATABASE monitor_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

-- Seleciona o banco recém-criado
USE monitor_db;

-- Confirma qual banco está ativo na sessão
SELECT DATABASE();
```

### 1.2 Criação das Tabelas de Cadastros (`hosts`, `users`, `tags`)
Criamos as entidades fundamentais do sistema com chaves primárias e restrições de unicidade:

```sql title="Comandos DDL: Tabelas de Cadastros"
-- 1. Servidores monitorados
CREATE TABLE hosts (
  id INT NOT NULL AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  address VARCHAR(100) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_hosts_name_address (name, address)
) ENGINE = InnoDB;

-- 2. Operadores e agentes do sistema
CREATE TABLE users (
  id INT NOT NULL AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  password VARCHAR(100) NOT NULL,
  email VARCHAR(100) DEFAULT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_email (email)
) ENGINE = InnoDB;

-- 3. Categorias de servidores (ex: 'Portal', 'Educacional', 'DNS')
CREATE TABLE tags (
  id INT NOT NULL AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tags_name (name)
) ENGINE = InnoDB;

-- 4. Associação N:M entre servidores e categorias
CREATE TABLE tag_hosts (
  id INT NOT NULL AUTO_INCREMENT,
  host_id INT NOT NULL,
  tag_id INT NOT NULL,
  PRIMARY KEY (id),
  CONSTRAINT fk_th_host FOREIGN KEY (host_id) REFERENCES hosts (id) ON DELETE CASCADE,
  CONSTRAINT fk_th_tag FOREIGN KEY (tag_id) REFERENCES tags (id) ON DELETE CASCADE
) ENGINE = InnoDB;
```

### 1.3 Criação das Tabelas de Telemetria (`pings`, `stats`, `icmps`)
Modelamos o histórico de testes e as métricas de pacotes com integridade referencial:

```sql title="Comandos DDL: Tabelas de Telemetria"
-- 5. Sessões de ping executadas
CREATE TABLE pings (
  id INT NOT NULL AUTO_INCREMENT,
  host_id INT NOT NULL,
  user_id INT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  CONSTRAINT fk_ping_host FOREIGN KEY (host_id) REFERENCES hosts (id) ON DELETE RESTRICT,
  CONSTRAINT fk_ping_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE RESTRICT
) ENGINE = InnoDB;

-- 6. Métricas consolidadas por teste
CREATE TABLE stats (
  id INT NOT NULL AUTO_INCREMENT,
  ping_id INT NOT NULL,
  transmitted INT NOT NULL,
  received INT NOT NULL,
  time FLOAT NOT NULL,
  PRIMARY KEY (id),
  CONSTRAINT fk_stat_ping FOREIGN KEY (ping_id) REFERENCES pings (id) ON DELETE CASCADE
) ENGINE = InnoDB;

-- 7. Detalhamento dos pacotes ICMP individuais
CREATE TABLE icmps (
  id INT NOT NULL AUTO_INCREMENT,
  ping_id INT NOT NULL,
  seq INT NOT NULL,
  ttl INT NOT NULL,
  time FLOAT NOT NULL,
  PRIMARY KEY (id),
  CONSTRAINT fk_icmp_ping FOREIGN KEY (ping_id) REFERENCES pings (id) ON DELETE CASCADE
) ENGINE = InnoDB;
```

## 2. DML: Carga do Arquivo CSV e Distribuição Relacional

Para popular o banco a partir do arquivo [`dataset.csv`](file:///Users/lucachaves/code/subjects/devlab/examples/courses/database/servers/mysql-server/dataset.csv), utilizamos uma tabela temporária de transição (*staging table*). Essa estratégia é o padrão da indústria para importar arquivos externos e distribuí-los para tabelas normalizadas.

### 2.1 Criação da Tabela de Staging e Importação do CSV
Criamos a tabela de recepção dos dados brutos e realizamos a carga:

```sql title="Criação da Tabela de Staging e Carga do CSV"
-- Tabela transitória para receber o CSV bruto
CREATE TABLE raw_pings (
  name VARCHAR(100),
  address VARCHAR(100),
  transmitted INT,
  received INT,
  time FLOAT,
  created_at DATETIME
) ENGINE = InnoDB;

-- Carga do arquivo CSV no MySQL (executado no console ou cliente)
LOAD DATA LOCAL INFILE 'dataset.csv'
INTO TABLE raw_pings
FIELDS TERMINATED BY ','
LINES TERMINATED BY '\n'
IGNORE 1 ROWS
(name, address, transmitted, received, time, created_at);
```

### 2.2 Distribuição e Normalização dos Dados
Com os dados na tabela transitória, populamos as tabelas normalizadas em sequência lógica:

```sql title="Distribuição dos Dados para o Esquema Relacional"
-- 1. Insere os operadores e categorias padrão
INSERT INTO users (id, name, password, email) VALUES
  (1, 'Agente Telemetria', 'hash_secret', 'telemetria@ifpb.edu.br');

INSERT INTO tags (name) VALUES
  ('Portal'),
  ('Educacional'),
  ('Sistema'),
  ('Infraestrutura');

-- 2. Insere os servidores únicos a partir do CSV
INSERT IGNORE INTO hosts (name, address)
SELECT DISTINCT name, address
FROM raw_pings;

-- 3. Associa categorias aos servidores
INSERT INTO tag_hosts (host_id, tag_id)
SELECT h.id, t.id
FROM hosts h, tags t
WHERE (h.name LIKE '%.edu.br' AND t.name = 'Educacional')
   OR (h.name LIKE 'portal.%' AND t.name = 'Portal')
   OR (h.name LIKE 'suap.%' AND t.name = 'Sistema')
   OR (h.name LIKE '%dns%' AND t.name = 'Infraestrutura');

-- 4. Insere as sessões de ping vinculando com o ID dos hosts
INSERT INTO pings (host_id, user_id, created_at)
SELECT h.id, 1, r.created_at
FROM raw_pings r
INNER JOIN hosts h ON r.name = h.name AND r.address = h.address;

-- 5. Insere as estatísticas vinculando com as sessões de ping criadas
INSERT INTO stats (ping_id, transmitted, received, time)
SELECT p.id, r.transmitted, r.received, r.time
FROM raw_pings r
INNER JOIN hosts h ON r.name = h.name AND r.address = h.address
INNER JOIN pings p ON p.host_id = h.id AND p.created_at = r.created_at;

-- 6. Remove a tabela de staging após a distribuição
DROP TABLE raw_pings;
```

## 3. DQL: Respondendo às Questões com Consultas Analíticas

Com os dados do CSV populados e normalizados, construímos as consultas SQL analíticas para responder a cada pergunta operacional.

### Questão 1: Volume total de pacotes transmitidos, recebidos e perdidos
Utilizamos as funções de agregação `SUM()` e `COUNT()` para consolidar os totais de toda a base:

```sql title="Consulta 1: Volume Total de Pacotes"
SELECT
  SUM(transmitted) AS total_transmitidos,
  SUM(received) AS total_recebidos,
  SUM(transmitted - received) AS total_perdidos,
  COUNT(id) AS total_testes_executados
FROM stats;
```

### Questão 2: Taxa percentual de perda de pacotes por servidor
Realizamos a junção (`INNER JOIN`) entre `hosts`, `pings` e `stats`, calculando a proporção com `ROUND()` e agrupando por servidor:

```sql title="Consulta 2: Perda de Pacotes por Host"
SELECT
  h.name AS host_name,
  h.address AS ip_address,
  SUM(s.transmitted) AS total_enviados,
  SUM(s.received) AS total_recebidos,
  SUM(s.transmitted - s.received) AS pacotes_perdidos,
  ROUND((SUM(s.transmitted - s.received) / SUM(s.transmitted)) * 100, 2) AS taxa_perda_pct
FROM hosts h
INNER JOIN pings p ON h.id = p.host_id
INNER JOIN stats s ON p.id = s.ping_id
GROUP BY h.id, h.name, h.address
ORDER BY taxa_perda_pct DESC;
```

### Questão 3: Tempo médio de resposta (RTT) e extremos de latência
Calculamos a latência média (`AVG`), o valor mínimo (`MIN`) e o pico de lentidão (`MAX`) por host:

```sql title="Consulta 3: Métricas de Latência por Host"
SELECT
  h.name AS host_name,
  ROUND(AVG(s.time), 2) AS latencia_media_ms,
  MIN(s.time) AS menor_tempo_ms,
  MAX(s.time) AS maior_tempo_ms
FROM hosts h
INNER JOIN pings p ON h.id = p.host_id
INNER JOIN stats s ON p.id = s.ping_id
GROUP BY h.id, h.name
ORDER BY latencia_media_ms ASC;
```

### Questão 4: Perda de pacotes do IFPB em horário comercial
Filtramos servidores com domínio `.ifpb.edu.br` usando `LIKE`, limitando o período ao horário comercial (entre 09:00 e 18:00) através das funções `DATE()` e `HOUR()`:

```sql title="Consulta 4: Telemetria Filtrada por Horário Comercial"
SELECT
  h.name AS host_name,
  DATE_FORMAT(p.created_at, '%d/%m/%Y %H:%i') AS data_hora_teste,
  s.transmitted,
  s.received,
  ROUND(((s.transmitted - s.received) / s.transmitted) * 100, 2) AS taxa_perda_pct
FROM hosts h
INNER JOIN pings p ON h.id = p.host_id
INNER JOIN stats s ON p.id = s.ping_id
WHERE h.name LIKE '%.ifpb.edu.br'
  AND HOUR(p.created_at) BETWEEN 9 AND 18
ORDER BY taxa_perda_pct DESC, p.created_at ASC;
```

### Questão 5: Servidores da categoria "Portal" com perda superior a 15%
Combinamos quatro tabelas com junção e aplicamos o filtro pós-agrupamento no `HAVING`:

```sql title="Consulta 5: Filtro por Categoria e HAVING"
SELECT
  h.name AS host_name,
  t.name AS tag_name,
  SUM(s.transmitted) AS total_enviados,
  SUM(s.received) AS total_recebidos,
  ROUND((SUM(s.transmitted - s.received) / SUM(s.transmitted)) * 100, 2) AS perda_pct
FROM hosts h
INNER JOIN tag_hosts th ON h.id = th.host_id
INNER JOIN tags t ON th.tag_id = t.id
INNER JOIN pings p ON h.id = p.host_id
INNER JOIN stats s ON p.id = s.ping_id
WHERE t.name = 'Portal'
GROUP BY h.id, h.name, t.name
HAVING perda_pct > 15.00;
```

## 4. Recursos Nativos e Automação no MySQL

Exploramos funções nativas do MySQL e criamos objetos analíticos reutilizáveis no catálogo do banco.

### 4.1 Funções de Texto, Data e Classificação com `CASE`
Combinamos funções de manipulação de strings com classificação dinâmica:

```sql title="Manipulação de Texto e Classificação com CASE"
SELECT
  h.name,
  -- Extrai o prefixo do subdomínio
  SUBSTRING_INDEX(h.name, '.', 1) AS prefixo_host,
  -- Formata a data no padrão brasileiro
  DATE_FORMAT(p.created_at, '%d/%m/%Y às %H:%i') AS data_brasil,
  s.time AS latencia_ms,
  -- Classificação semântica do estado do link
  CASE
    WHEN s.received = 0 THEN 'FORA DO AR (CRÍTICO)'
    WHEN (s.transmitted - s.received) >= 3 THEN 'INSTÁVEL (ALTA PERDA)'
    WHEN s.time > 80.0 THEN 'LENTO (ALTA LATÊNCIA)'
    ELSE 'ESTÁVEL (NORMAL)'
  END AS status_qualidade
FROM hosts h
INNER JOIN pings p ON h.id = p.host_id
INNER JOIN stats s ON p.id = s.ping_id;
```

### 4.2 Criação de Visão Analítica (*View*)
Criamos a visão `v_host_health_summary` para alimentar painéis e relatórios de observabilidade:

```sql title="Criação da View Analítica de Saúde da Rede"
CREATE OR REPLACE VIEW v_host_health_summary AS
SELECT
  h.id AS host_id,
  h.name AS host_name,
  h.address AS ip_address,
  COUNT(p.id) AS total_amostras,
  ROUND(AVG(s.time), 2) AS latencia_media_ms,
  ROUND((SUM(s.transmitted - s.received) / SUM(s.transmitted)) * 100, 2) AS perda_media_pct,
  MAX(p.created_at) AS ultimo_ping
FROM hosts h
LEFT JOIN pings p ON h.id = p.host_id
LEFT JOIN stats s ON p.id = s.ping_id
GROUP BY h.id, h.name, h.address;
```

Para consultar os nós com perda média superior a zero:

```sql title="Consulta sobre a View"
SELECT * FROM v_host_health_summary WHERE perda_media_pct > 0;
```

### 4.3 Criação de Stored Procedure com Delimitador
Criamos uma rotina procedural para diagnosticar a qualidade de um host com parâmetros `IN` e `OUT`:

```sql title="Stored Procedure para Diagnóstico no MySQL"
DELIMITER //

CREATE PROCEDURE sp_avaliar_host(
  IN p_host_id INT,
  OUT p_diagnostico VARCHAR(50)
)
BEGIN
  DECLARE v_taxa_perda DECIMAL(5, 2);

  -- Calcula a taxa média de perda do host
  SELECT ROUND((SUM(s.transmitted - s.received) / SUM(s.transmitted)) * 100, 2)
    INTO v_taxa_perda
    FROM pings p
   INNER JOIN stats s ON p.id = s.ping_id
   WHERE p.host_id = p_host_id;

  -- Avalia a métrica
  IF v_taxa_perda IS NULL THEN
    SET p_diagnostico = 'SEM DADOS SUFICIENTES';
  ELSEIF v_taxa_perda = 0 THEN
    SET p_diagnostico = 'EXCELENTE (0% PERDA)';
  ELSEIF v_taxa_perda <= 15 THEN
    SET p_diagnostico = 'ACEITÁVEL (INSTABILIDADE LEVE)';
  ELSE
    SET p_diagnostico = 'CRÍTICO (ALTA DEGRADAÇÃO)';
  END IF;
END //

DELIMITER ;
```

Para invocar a procedure e ler a variável de saída:

```sql title="Execução da Procedure"
CALL sp_avaliar_host(1, @resultado);
SELECT @resultado AS diagnostico_servidor;
```

## 5. Exportando o Banco: Backup com `mysqldump`

Após concluir a modelagem, as inserções, as visões e os procedimentos, geramos o backup lógico completo do banco de dados `monitor_db` utilizando o utilitário **`mysqldump`**.

### 5.1 Executando o Comando de Backup
O comando a seguir conecta ao contêiner MySQL, extrai a definição das tabelas, os dados populados e os objetos procedurais, salvando o resultado no arquivo `database.sql`:

```bash title="Terminal"
# Executa o dump completo com transação isolada, rotinas e triggers
docker compose exec mysql mysqldump \
  -uroot \
  -psecret \
  --single-transaction \
  --routines \
  --triggers \
  --databases monitor_db > database.sql
```

Os parâmetros utilizados garantem a completude do backup:
- **`--single-transaction`**: Realiza o dump em tabelas InnoDB dentro de uma transação isolada, garantindo consistência sem bloquear leituras ou escritas.
- **`--routines`**: Inclui todas as *Stored Procedures* e *Functions* do banco no arquivo de saída.
- **`--triggers`**: Exporta todos os gatilhos associados às tabelas.
- **`--databases monitor_db`**: Insere os comandos de criação e seleção do banco (`CREATE DATABASE IF NOT EXISTS monitor_db; USE monitor_db;`).

     ```sql
     SELECT h.name, COUNT(p.id) AS total_testes
     FROM hosts h
     LEFT JOIN pings p ON h.id = p.host_id
     GROUP BY h.id, h.name;
     ```

  2. Consulta com subconsulta escalar no `WHERE`:
     ```sql
     SELECT id, ping_id, seq, time
     FROM icmps
     WHERE time > (SELECT AVG(time) FROM icmps);
     ```

  3. Para permitir que as tabelas sejam recriadas e populadas em qualquer ordem durante a restauração, sem que restrições de chave estrangeira causem falhas por dependências circulares ou tabelas pai ainda não populadas.

## Desafio

Crie uma consulta analítica no MySQL que gere um ranking dos servidores com maior instabilidade nos últimos 7 dias. O relatório deve apresentar o nome do host, o total de testes realizados, a taxa média de perda de pacotes e classificar o servidor como `'CRÍTICO'` se a perda for maior que 20%, ou `'ALERTA'` caso contrário, considerando apenas servidores com pelo menos 3 medições.

<details>
  <summary>Possível resposta</summary>

  ```sql
  SELECT
    h.name AS host_name,
    COUNT(p.id) AS total_medicoes,
    ROUND((SUM(s.transmitted - s.received) / SUM(s.transmitted)) * 100, 2) AS taxa_perda_pct,
    IF(
      ROUND((SUM(s.transmitted - s.received) / SUM(s.transmitted)) * 100, 2) > 20.0,
      'CRÍTICO',
      'ALERTA'
    ) AS nivel_risco
  FROM hosts h
  INNER JOIN pings p ON h.id = p.host_id
  INNER JOIN stats s ON p.id = s.ping_id
  WHERE p.created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
  GROUP BY h.id, h.name
  HAVING total_medicoes >= 3
  ORDER BY taxa_perda_pct DESC;
  ```
</details>

## Perguntas de revisão

### Modelagem e Análise

1. **Por que a tabela `stats` foi isolada da tabela `hosts` em vez de armazenar o contador de pacotes diretamente no registro do host?**
   <details><summary>Possível resposta</summary>Porque as medições variam com o tempo (relação 1:N). Guardar no host limitaria o sistema a uma única medição ou exigiria colunas repetitivas, violando as formas normais.</details>

2. **Qual a diferença funcional entre `WHERE` e `HAVING` ao calcular a perda de pacotes?**
   <details><summary>Possível resposta</summary>`WHERE` filtra linhas individuais antes do agrupamento (ex: data ou domínio). `HAVING` filtra os grupos consolidados após a aplicação das funções agregadoras (ex: `SUM(perda) > 15`).</details>

### Recursos do MySQL e Backup

3. **Qual é a função do comando `DELIMITER //` na criação de uma Stored Procedure?**
   <details><summary>Possível resposta</summary>Ele substitui temporariamente o delimitador padrão de comandos (de `;` para `//`), permitindo que blocos internos `BEGIN ... END` contenham instruções terminadas em ponto e vírgula sem disparar a execução prematura do `CREATE PROCEDURE`.</details>

4. **Por que a opção `--single-transaction` é recomendada no `mysqldump` para tabelas InnoDB?**
   <details><summary>Possível resposta</summary>Porque ela cria um snapshot consistente dos dados dentro de uma transação isolada, permitindo realizar o backup sem bloquear comandos de inserção ou atualização na aplicação.</details>
