Os navegadores modernos evoluíram de simples leitores de documentos HTML para plataformas de execução robustas capazes de acessar hardware, gerenciar armazenamento local, capturar mídia e se comunicar em tempo real. As **Web APIs** são as interfaces nativas fornecidas pelo navegador para que o JavaScript interaja com todos esses recursos do sistema.

## Objetivo

Formar um mapa das interfaces que o navegador expõe ao JavaScript, para escolher a API certa em vez de descobri-la por acaso. Ao final do tópico, o leitor deve ser capaz de:

- Agrupar as Web APIs pelos domínios que elas cobrem (interface, armazenamento, rede, mídia e hardware).
- Explicar o que é contexto seguro (HTTPS) e por que ele condiciona o acesso a boa parte das APIs.
- Diferenciar API que exige permissão explícita de API que exige apenas gesto do usuário.
- Decidir entre APIs concorrentes a partir do problema, e não da novidade da interface.
- Reconhecer o que precisa ser verificado em código de Web API gerado por assistente antes de aceitá-lo.

## Segurança, Permissões e Contexto Seguro

O navegador protege o usuário restringindo o acesso a APIs sensíveis de hardware e sistema operacional. Para utilizar a maioria das Web APIs modernas, três requisitos devem ser atendidos:

1. **Contexto Seguro (*Secure Context*)**: A aplicação deve ser servida estritamente via protocolo HTTPS (ou estar rodando em `localhost` durante o desenvolvimento).
2. **Gesto Explícito do Usuário (*User Activation*)**: APIs como Clipboard, Fullscreen, Web Speech e Vibration exigem uma ação iniciada diretamente pelo usuário (ex: evento de clique em botão).
3. **Solicitação de Permissão (*Permissions API*)**: Recursos como Geolocalização e Notificações exigem autorização prévia e explícita do usuário através de um popup nativo do navegador.

## Web APIs na Era da Inteligência Artificial

Pedir a um assistente "carregue os dados da API e mostre na tela" ou "copie este texto para a área de
transferência" devolve, em segundos, um trecho que compila, executa e faz o que foi pedido. O
problema é que quase toda Web API tem um comportamento de borda que só aparece fora do caminho
feliz, e é justamente esse comportamento que o modelo não pode verificar por você.

O que mudou no trabalho, então, não foi a escrita: foi o ponto onde a atenção precisa estar.

| O que mudou | O que permanece |
| --- | --- |
| Escrever a chamada da API deixou de ser o gargalo | Decidir **qual** API resolve o problema continua sendo humano |
| O modelo conhece a assinatura de quase toda interface | Ele não sabe se o seu servidor envia `Access-Control-Allow-Origin` |
| O código gerado passa no primeiro teste manual | Permissão negada, `null` e status 500 continuam acontecendo em produção |
| A sintaxe raramente vem errada | O caso de erro raramente vem tratado |

As subseções a seguir mostram esse desencontro em um caso concreto, catalogam o que o modelo erra por
API e fecham com o que conferir antes de aprovar um *pull request*.

### Armadilhas por API

O caso do `response.ok` é o mais frequente, mas cada interface deste catálogo tem a sua. A tabela
reúne as que mais aparecem em código gerado, com o sintoma pelo qual você as reconhece na revisão:

| API | O que o modelo costuma gerar | Como se manifesta | Como mitigar |
| --- | --- | --- | --- |
| Fetch | `await response.json()` sem checar o status | Erro em `map()` ou tela em branco | Exigir `if (!response.ok) throw` no *prompt* |
| Web Storage | `JSON.parse(localStorage.getItem(k))` direto | `null` na primeira visita, `SyntaxError` com dado corrompido | Pedir valor padrão e `try/catch` na leitura |
| Notification | `requestPermission()` no carregamento | Bloqueio permanente para o site | Pedir que a chamada nasça de um gesto do usuário |
| Clipboard | `writeText()` sem `try/catch` | Botão que não reage quando a permissão falha | Exigir retorno visível para sucesso e falha |
| Geolocation | Só o callback de sucesso | Tela parada quando o usuário recusa | Exigir o callback de erro e um caminho manual |
| Drag and Drop | `drop` sem `preventDefault()` em `dragover` | O item nunca é aceito pelo destino | Citar os dois `preventDefault()` no pedido |
| CORS | `mode: 'no-cors'` como solução do bloqueio | Resposta opaca, corpo ilegível, erro só depois | Rejeitar e corrigir os cabeçalhos no servidor |
| DOM | `innerHTML` com dado vindo da API | Injeção de script (XSS) sem nenhum aviso | Exigir `textContent` para conteúdo externo |

A linha do CORS merece destaque porque a sugestão é ativamente prejudicial. `mode: 'no-cors'` não
libera nada: ele troca o erro visível no console por uma resposta opaca, cujo corpo o JavaScript não
consegue ler, e adia a descoberta do problema para bem mais tarde.

### Elementos do pedido que mudam o resultado

Um pedido que descreve só o resultado devolve só o caminho feliz. Fixar dialeto, casos de erro e
forma de verificação muda bastante o que chega de volta:

```txt title="Prompt de geração com contrato explícito"
Escreva uma função `loadItems(url)` que busca itens em uma API REST e devolve os nomes.
Requisitos: JavaScript moderno com módulos ECMAScript, sem bibliotecas; lançar erro citando
o status quando `response.ok` for falso; não engolir falha de rede. Depois escreva testes
com `node:test` cobrindo: resposta 200 com dois itens, resposta 500 e falha de rede. Mostre
primeiro os testes e explique o que cada um garante.
```

Três elementos fazem a diferença nesse texto, e valem para qualquer Web API: o **dialeto**
(JavaScript moderno, sem bibliotecas), o **contrato de erro** (o que deve acontecer quando dá errado)
e a **verificação** (os testes, pedidos antes do código).

### Checklist de revisão antes do merge

Antes de aprovar um trecho de Web API gerado por assistente, percorra os pontos abaixo. Eles cobrem
os defeitos que o código gerado tem com mais frequência, e nenhum deles aparece no caminho feliz:

1. Todo `fetch()` confere `response.ok` antes de consumir o corpo?
2. Toda leitura de `localStorage` tem valor padrão e proteção contra JSON inválido?
3. Toda API que pede permissão é chamada a partir de um gesto do usuário, e não no carregamento?
4. Toda Promise de Web API tem tratamento de rejeição com retorno visível na interface?
5. Nenhum dado vindo de fora da página é escrito com `innerHTML`?
6. O código só usa APIs disponíveis nos navegadores que o projeto suporta?
7. Existe um teste, mesmo pequeno, cobrindo o caminho de erro descrito acima?

A responsabilidade continua sendo de quem assina o *commit*. O assistente escreve o caminho feliz em
segundos; o caso de erro, a permissão negada e o dado ausente continuam sendo problema de quem revisa.
