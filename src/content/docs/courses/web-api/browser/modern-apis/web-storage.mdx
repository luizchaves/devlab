A **Web Storage API** oferece dois armazenamentos simples por origem: `localStorage` e
`sessionStorage`. Ambos salvam pares chave-valor em formato de texto.

## Objetivo

Aplicar o Web Storage dentro de uma interface real, do salvamento ao carregamento inicial da tela, tratando o dado ausente como caso normal. Ao final do tópico, o leitor deve ser capaz de:

- Gravar e ler valores com `localStorage.setItem()` e `getItem()`.
- Serializar e desserializar objetos com `JSON.stringify()` e `JSON.parse()`.
- Diferenciar `localStorage` de `sessionStorage` pelo tempo de vida do dado.
- Explicar o escopo por origem e o que isso significa para dados de outro domínio ou porta.
- Tratar `null` no primeiro acesso e proteger o `JSON.parse()` de um valor corrompido.

## Um dicionário de strings por origem

O Web Storage é mais simples do que o nome sugere: é um dicionário de chaves e valores, ambos strings,
guardado pelo navegador e associado a uma origem. Duas restrições saem direto dessa definição e
explicam quase todos os erros do tópico.

A primeira é que **tudo vira string**. Guardar um número devolve um número escrito por extenso, e
guardar um objeto sem serializar devolve o literal `[object Object]`. A segunda é que **a chave pode
não existir**, e nesse caso a leitura devolve `null`, que o `JSON.parse()` aceita sem reclamar e
converte em `null`.

A tabela mostra o que sai da leitura em cada caso:

| O que foi gravado | O que `getItem()` devolve | Cuidado |
| --- | --- | --- |
| `setItem('total', 42)` | `'42'` | Converter com `Number()` antes de calcular |
| `setItem('user', { id: 1 })` | `'[object Object]'` | Serializar com `JSON.stringify()` antes de gravar |
| Nada, chave inexistente | `null` | Definir um valor padrão na leitura |
| Um JSON corrompido por edição manual | A string inválida | `JSON.parse()` lança `SyntaxError` |

O trecho abaixo trata os quatro casos com duas funções curtas, e é o padrão que a interface do exemplo
utiliza:

```js title="Leitura e escrita com valor padrão"
function read(key, fallback = []) {
  try {
    return JSON.parse(localStorage.getItem(key)) ?? fallback;
  } catch {
    return fallback;
  }
}

function write(key, value) {
  localStorage.setItem(key, JSON.stringify(value));
}
```

O `??` da linha 3 resolve a chave inexistente, e o `catch` da linha 4 resolve o valor corrompido. Sem
esses dois cuidados, um único dado inválido no armazenamento deixa a tela em branco para sempre, e o
usuário não tem como se recuperar sem limpar os dados do site.

## Modelo da API

Os dois objetos usam os mesmos métodos. A diferença principal é o tempo de vida dos dados.

| Recurso | Papel |
| --- | --- |
| `localStorage` | Persiste dados mesmo depois de fechar a aba |
| `sessionStorage` | Mantém dados apenas enquanto a aba existir |
| `setItem(chave, valor)` | Grava uma string |
| `getItem(chave)` | Lê uma string ou retorna `null` |
| `removeItem(chave)` | Remove uma chave específica |
| `clear()` | Remove todas as chaves daquele armazenamento |
| `JSON.stringify()` e `JSON.parse()` | Convertem objetos entre JS e texto |

<Aside type="caution" title="Storage não é banco de dados seguro">
Não grave senhas, tokens sensíveis ou dados privados importantes em `localStorage`. O conteúdo fica
acessível ao JavaScript executado na mesma origem.
</Aside>

## Quando usar, e quando não usar?

Este tópico aplica o Web Storage a uma interface, então a decisão relevante é sobre **o que** guardar
na origem, e não sobre a API em si.

A tabela relaciona cada tipo de dado ao lugar adequado:

| Situação | Escolha | Por quê |
| --- | --- | --- |
| Preferência de exibição (tema, ordenação, aba ativa) | `localStorage` | Pequeno, próprio daquele navegador e sem valor para o servidor |
| Rascunho de formulário até o envio | `sessionStorage` | Some ao fechar a aba, sem precisar de limpeza |
| Lista de itens que o usuário quer ver em outro aparelho | Servidor | O armazenamento local não sai daquele navegador |
| Token de sessão | Cookie `HttpOnly` | Em `localStorage`, qualquer script injetado consegue lê-lo |
| Coleção grande, com busca por campo | IndexedDB | O acesso síncrono do Web Storage trava a interface |

A terceira linha é a que costuma decidir o rumo de um projeto de estudo. Enquanto os dados vivem em
`localStorage`, a aplicação funciona em um navegador só: o momento em que o usuário quer ver a mesma
lista no celular é o momento em que ela precisa de uma API.

## Exercício

1. Salve um objeto `{ text, createdAt }` no lugar de uma string simples.
2. Use `JSON.stringify()` na gravação.
3. Use `JSON.parse()` na leitura e trate JSON inválido com `try/catch`.

<details>
  <summary>Possível resposta</summary>

  A gravação pode criar `const item = { text: input.value, createdAt: new Date().toISOString() }` e
  salvar `JSON.stringify(item)`. Na leitura, `JSON.parse()` deve ficar dentro de `try/catch` para
  evitar quebrar a interface se o valor armazenado estiver corrompido.
</details>

## Perguntas de revisão

### Tipos e ausência de dado

1. **Por que `localStorage.setItem('total', 42)` devolve `'42'` na leitura?**

<details>
  <summary>Possível resposta</summary>

  Porque o Web Storage armazena apenas strings, convertendo qualquer valor recebido.
</details>

2. **O que acontece ao gravar um objeto sem serializar?**

<details>
  <summary>Possível resposta</summary>

  Ele é convertido pela regra padrão de string e vira `'[object Object]'`, perdendo todo o conteúdo.
</details>

3. **O que `getItem()` devolve para uma chave inexistente, e por que isso importa?**

<details>
  <summary>Possível resposta</summary>

  Devolve `null`. Como `JSON.parse(null)` também devolve `null`, o código precisa de um valor padrão
  para não quebrar na primeira execução.
</details>

4. **Por que envolver o `JSON.parse()` em um `try/catch`?**

<details>
  <summary>Possível resposta</summary>

  Porque um valor corrompido lança `SyntaxError`, e sem tratamento a tela fica quebrada até que o
  usuário limpe os dados do site.
</details>

### Escopo e escolha

5. **O que significa dizer que o armazenamento é "por origem"?**

<details>
  <summary>Possível resposta</summary>

  Que protocolo, domínio e porta juntos delimitam o espaço. Outra porta ou outro subdomínio enxergam
  um armazenamento diferente.
</details>

6. **Qual a diferença prática entre `localStorage` e `sessionStorage`?**

<details>
  <summary>Possível resposta</summary>

  `localStorage` persiste até ser removido; `sessionStorage` vive apenas enquanto aquela aba estiver
  aberta.
</details>

7. **Por que um token de sessão não deve ficar em `localStorage`?**

<details>
  <summary>Possível resposta</summary>

  Porque qualquer script injetado na página consegue lê-lo. Um cookie `HttpOnly` não é acessível pelo
  JavaScript.
</details>

8. **Quando o Web Storage deixa de ser suficiente para uma aplicação?**

<details>
  <summary>Possível resposta</summary>

  Quando os dados precisam ser vistos em outro aparelho, quando passam de alguns megabytes ou quando
  exigem busca por campo, casos de servidor e de IndexedDB.
</details>
