Os navegadores evoluíram de simples formatadores de hipertexto para ambientes de execução ricos, capazes de acessar hardware, gerenciar persistência local, capturar mídia, desenhar em alta taxa de quadros e comunicar-se em tempo real. As **Web APIs** são as interfaces padronizadas que o ambiente expõe para que o JavaScript interaja com todos esses recursos.

Este tópico organiza o catálogo das interfaces ensinadas ao longo deste guia, explicando seus domínios, regras de segurança e critérios para escolher a API certa para cada necessidade.

## Objetivo

Compreender o mapa geral das interfaces que o navegador expõe ao JavaScript, orientando a escolha da API adequada para cada problema de desenvolvimento front-end. Ao final do tópico, o leitor deve ser capaz de:

- Agrupar as Web APIs pelos domínios que elas cobrem (interface, estrutura DOM, mídia, transferência, dispositivo, armazenamento e rede).
- Explicar o que é contexto seguro (HTTPS) e por que ele condiciona o acesso a boa parte das APIs nativas.
- Diferenciar APIs que exigem permissão explícita do usuário daquelas que exigem apenas gesto prévio (*user activation*).
- Decidir entre APIs concorrentes a partir do problema real, evitando soluções excessivamente complexas.
- Reconhecer armadilhas frequentes em código de Web APIs gerado por assistentes antes de aceitá-lo em produção.

## Segurança, Permissões e Contexto Seguro

O navegador protege o usuário restringindo o acesso a APIs sensíveis de hardware e sistema operacional. Para utilizar a maioria das Web APIs, três níveis de proteção são aplicados:

1. **Contexto Seguro (*Secure Context*)**: A aplicação deve ser servida estritamente via protocolo HTTPS (ou estar rodando em `localhost` durante o desenvolvimento local).
2. **Gesto Explícito do Usuário (*User Activation*)**: APIs como Clipboard, Fullscreen, Web Speech e Vibration exigem uma ação iniciada diretamente pelo usuário (como o clique em um botão).
3. **Solicitação de Permissão (*Permissions API*)**: Recursos como Geolocalização e Notificações exigem autorização prévia e explícita do usuário através de uma caixa de diálogo nativa do navegador.

## Qual API para qual problema?

O catálogo responde "o que existe". Esta seção responde a pergunta prática: dado um problema concreto, qual interface resolve, e qual alternativa costuma ser tentada incorretamente:

| Necessidade | Escolha | Alternativa que perde, e por quê |
| --- | --- | --- |
| Confirmar uma ação com o usuário | [Dialog](../../ui/dialog/) com `showModal()` | `div` com `z-index`: foco, `Esc` e camada superior ficam por sua conta |
| Guardar uma preferência de interface | [Web Storage](../../storage/local-storage/) | Cookie: viaja em toda requisição HTTP, sem necessidade |
| Guardar uma sessão autenticada | [Cookie `HttpOnly`](../../storage/cookies/) | `localStorage`: qualquer script injetado (XSS) lê o token |
| Buscar dados de uma API | [Fetch](../../http/fetch/) | `XMLHttpRequest`: mais verboso, baseado em callbacks legados |
| Avisar o usuário fora da aba | [Notification](../../device/notification/) | Título da aba piscando: só funciona se a barra do navegador estiver visível |
| Avisar sobre algo visível na tela | Aviso na própria página | [Notification](../../device/notification/): interrompe desnecessariamente o usuário |
| Copiar um valor para a área de transferência | [Clipboard](../../input/clipboard/) | Instrução textual para selecionar à mão |
| Receber arquivos arrastados | [Drag and Drop](../../input/drag-and-drop/) | Apenas `<input type="file">`: ignora o gesto natural de arrastar da área de trabalho |
| Localizar o usuário para buscar algo perto | [Geolocation](../../device/geolocation/) | GeoIP no servidor: precisão apenas em nível de cidade/provedor |
| Escolher idioma ou moeda | Cabeçalho `Accept-Language` | [Geolocation](../../device/geolocation/): gasta o diálogo de permissão do navegador à toa |
| Desenhar muitos elementos gráficos por quadro | [Canvas](../../media/canvas/) | SVG: múltiplos nós no DOM não sustentam alta taxa de quadros (60 fps) |
| Desenhar um gráfico acessível e interativo | SVG e HTML | [Canvas](../../media/canvas/): o desenho em pixels não existe para leitores de tela |
| Ler a página em voz alta a pedido | [Web Speech](../../media/web-speech/) | Leitura automática: conflita com o leitor de tela pré-configurado do usuário |
| Confirmar um toque em celular | [Vibration](../../device/vibration/) | Alerta puramente visual: exige que o usuário esteja olhando para a tela |
| Ocupar a tela com vídeo ou apresentação | [Fullscreen](../../ui/fullscreen/) | `position: fixed`: não esconde a barra de endereços do navegador |
| Evitar que cálculos pesados travem a interface | [Web Worker](../workers/) | Otimização prematura em JS: apenas adia o travamento sem isolar a thread |
| Acelerar um algoritmo matemático intensivo | [WebAssembly](../webassembly/) | [Web Worker](../workers/) isolado: destrava a interface, mas não acelera a execução da conta |

<Aside type="note" title="Além das Trilhas Principais">
O ecossistema do navegador também conta com interfaces avançadas para gráficos 3D (WebGL, WebGPU), bancos locais (IndexedDB), Service Workers offline, áudio modular (Web Audio), biometria (WebAuthn/Passkeys) e acesso a periféricos (Web Bluetooth/USB). Para uma visão panorâmica dessas interfaces complementares, consulte a página de referência [Outras Web APIs](../../reference/other-apis/).
</Aside>

## Web APIs na Era da Inteligência Artificial

Pedir a um assistente "carregue os dados da API e mostre na tela" ou "copie este texto para a área de transferência" devolve, em segundos, um trecho que compila e executa. Contudo, quase toda Web API tem comportamentos de borda que só aparecem fora do caminho feliz:

| O que mudou | O que permanece |
| --- | --- |
| Escrever a sintaxe da chamada deixou de ser o gargalo | Decidir **qual** API resolve o problema continua sendo responsabilidade do desenvolvedor |
| O modelo conhece a assinatura de quase toda interface | Ele não prevê se o servidor remoto responderá com cabeçalhos de CORS adequados |
| O código gerado passa no primeiro teste manual | Permissão negada, `null` e status HTTP 500 continuam ocorrendo em produção |
| A sintaxe raramente vem errada | O tratamento de erros e estados intermediários costuma vir incompleto |

As subseções a seguir mostram esse comportamento na prática e detalham o checklist essencial de revisão.

### Armadilhas Recorrentes por API

A tabela resume as omissões mais frequentes em código gerado por IA para Web APIs:

| API | O que o modelo costuma gerar | Como se manifesta | Como mitigar |
| --- | --- | --- | --- |
| Fetch | `await response.json()` sem checar `response.ok` | Erro em `map()` ou tela em branco | Exigir `if (!response.ok) throw` no contrato |
| Web Storage | `JSON.parse(localStorage.getItem(k))` direto | `null` na primeira visita ou `SyntaxError` com dado corrompido | Fornecer valor padrão e envolver a leitura em `try/catch` |
| Notification | `requestPermission()` disparado no carregamento da página | Bloqueio automático e permanente pelo navegador | Disparar a solicitação apenas após ação do usuário |
| Clipboard | `writeText()` sem tratamento de rejeição | Botão inerte quando a permissão da área de transferência é recusada | Tratar a Promise e exibir feedback visual de sucesso ou falha |
| Geolocation | Apenas o callback de sucesso | Aplicação travada sem resposta caso o usuário recuse o compartilhamento | Obrigatoriamente fornecer callback de erro e alternativa manual |
| Drag and Drop | Ouvinte de `drop` sem `preventDefault()` no evento `dragover` | O elemento arrastado nunca é aceito pela zona de soltura | Adicionar `event.preventDefault()` em ambos os eventos |
| CORS | Sugestão de `mode: 'no-cors'` para contornar bloqueios | Resposta opaca com corpo inacessível ao JavaScript | Rejeitar a flag e ajustar os cabeçalhos `Access-Control-*` no servidor |
| DOM | `innerHTML` concatenando dados recebidos da API | Vulnerabilidade a injeção de scripts (XSS) | Utilizar `textContent` ou nós criados via `createElement` |

### Checklist de revisão antes do merge

Antes de aceitar trechos de Web APIs em sua aplicação, valide os seguintes pontos:

1. Toda chamada `fetch()` valida `response.ok` antes de consumir o corpo da resposta?
2. Toda leitura de `localStorage` ou `sessionStorage` trata parsing de JSON e valor padrão?
3. Chamadas a APIs com permissão (Notificações, Câmera, Localização) partem exclusivamente de um gesto do usuário?
4. Toda Promise de Web API possui tratamento adequado de rejeição com retorno claro na interface?
5. Dados dinâmicos de origem externa são renderizados com segurança sem `innerHTML` vulnerável?
6. As interfaces utilizadas possuem suporte garantido nos navegadores definidos pelo projeto?
