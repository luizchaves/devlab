Os navegadores evoluíram de simples formatadores de hipertexto para ambientes de execução ricos, capazes de acessar hardware, gerenciar persistência local, capturar mídia, desenhar em alta taxa de quadros e comunicar-se em tempo real. As **Web APIs** são as interfaces padronizadas que o ambiente expõe para que o JavaScript interaja com todos esses recursos.

Materiais: [slides do tópico](../../../../slides/courses/web-api/browser/catalog/) e [mapa mental](../../../../mindmaps/courses/web-api/browser/catalog/).

Este tópico organiza o catálogo das interfaces ensinadas ao longo deste guia, explicando seus domínios, regras de segurança e critérios para escolher a API certa para cada necessidade.

## Objetivo

Compreender o mapa geral das interfaces que o navegador expõe ao JavaScript, orientando a escolha da API adequada para cada problema de desenvolvimento front-end. Ao final do tópico, o leitor deve ser capaz de:

- Agrupar as Web APIs pelos domínios que elas cobrem (interface, estrutura DOM, mídia, transferência, dispositivo, armazenamento e rede).
- Compreender o modelo de sandbox do navegador e as fronteiras arquiteturais entre o front-end e o back-end.
- Explicar o que é contexto seguro (HTTPS), ativação por gesto e permissões de acesso ao hardware.
- Decidir entre APIs concorrentes a partir do problema real, evitando soluções excessivamente complexas.
- Reconhecer armadilhas frequentes em código de Web APIs gerado por assistentes antes de aceitá-lo em produção.

## Mapa das APIs do Guia

Quando um script JavaScript é executado em um navegador, ele não roda isolado em uma máquina virtual pura. O ambiente hospedeiro (*host environment*) injeta um conjunto extenso de objetos e métodos globais que permitem à aplicação interagir com a janela, ouvir ações do usuário, desenhar elementos gráficos, persistir dados localmente, comunicar-se com servidores remotos e até acessar recursos físicos do dispositivo. Esse ecossistema de interfaces padronizadas por órgãos internacionais (W3C e WHATWG) forma as **Web APIs**.

Dominar as Web APIs significa saber exatamente qual recurso nativo utilizar para solucionar cada necessidade do front-end sem depender de bibliotecas externas redundantes. As interfaces ensinadas neste guia estão estruturadas em sete domínios funcionais:

1. **Ambiente e Interface**: Controle de navegação SPA com a History API, modais acessíveis na camada superior com a Dialog API e imersão visual com a Fullscreen API.
2. **Estrutura DOM e Interatividade**: Manipulação e criação dinâmica de nós HTML, delegação de eventos, validação com Constraint Validation API, rolagem suave e observadores assíncronos de visibilidade e redimensionamento.
3. **Desenho e Mídia**: Renderização 2D direta em bitmap de alta performance com a Canvas API, recursos de síntese e reconhecimento de voz via Web Speech API, captura direta de câmera e microfone com a MediaDevices API e transmissão em tempo real ou adaptativa com WebRTC e Media Source Extensions (MSE).
4. **Entrada e Transferência**: Acesso controlado à área de transferência com a Clipboard API e fluxos visuais de arrastar e soltar arquivos e elementos com a Drag and Drop API.
5. **Dispositivo e Processamento**: Consulta de localização geográfica com Geolocation API, notificações de sistema, retorno tátil por vibração, paralelismo fora da thread principal com Web Workers e execução binária de alta velocidade com WebAssembly.
6. **Armazenamento no Cliente**: Persistência síncrona de chave-valor com `localStorage` e `sessionStorage`, além do gerenciamento de identificadores de sessão com Cookies protegidos.
7. **Rede e Comunicação**: Requisições assíncronas baseadas em Promises via Fetch API, fluxos contínuos de eventos com Server-Sent Events (SSE) e comunicação bidirecional em tempo real full-duplex com WebSockets.

### O Modelo de Sandbox e as Fronteiras com o Back-end

Ao navegar na web, o usuário carrega e executa código JavaScript de sites desconhecidos a cada página acessada. Para proteger a integridade do sistema operacional e a privacidade dos dados locais, o navegador executa todo o código front-end dentro de uma caixa de proteção rígida, denominada **sandbox**.

Por conta desse modelo de segurança, existem limites claros sobre o que uma Web API pode ou não fazer. O desenvolvimento web divide responsabilidades entre o cliente (navegador) e o servidor (back-end). As seguintes operações **não pertencem** ao domínio das Web APIs no front-end e são de responsabilidade exclusiva do back-end:

- **Acesso direto e irrestrito ao sistema de arquivos em disco**: No navegador, scripts não podem ler pastas locais arbitrárias nem gravar arquivos silenciosamente sem o consentimento intencional do usuário (via `<input type="file">` ou diálogo de permissão). No back-end, ambientes como o **Node.js** utilizam os módulos nativos `node:fs` e `node:fs/promises` para ler e escrever arquivos, diretórios e logs no servidor com controle total de permissões do sistema operacional.
- **Armazenamento de segredos e credenciais mestras**: Chaves privadas de APIs externas (como Stripe, OpenAI e AWS), tokens administrativos e senhas de banco de dados nunca devem residir no front-end, onde ficam visíveis a qualquer pessoa pelo DevTools. No back-end, o **Node.js** lê variáveis de ambiente confidenciais de forma segura através de `process.env` e cofres de segredos (*Secret Managers*), sem expô-las ao cliente.
- **Conexões de rede em portas e sockets brutos (*raw TCP/UDP*)**: O front-end é restrito a protocolos de aplicação web (HTTP/HTTPS via `fetch` e WebSockets), não podendo abrir conexões TCP arbitrárias para servidores de e-mail (SMTP) ou portas de bancos de dados (como 5432 do PostgreSQL ou 3306 do MySQL). No back-end, o **Node.js** utiliza `node:net`, drivers nativos de banco de dados (`pg`, `mysql2`) e clientes de e-mail para abrir sockets diretos em qualquer porta autorizada.
- **Processamento em lote e rotinas de segundo plano independentes**: No navegador, o processamento depende da aba estar aberta pelo usuário; se a aba for fechada ou entrar em suspensão pelo sistema operacional, a execução é interrompida. No back-end, serviços em **Node.js** orquestrados por agendadores de tarefas (*cron jobs*), filas de mensageria (Redis, BullMQ) ou contêineres executam rotinas pesadas continuamente 24 horas por dia.
- **Transações corporativas e integridade de banco de dados**: O armazenamento do navegador (`localStorage`, `IndexedDB`) é isolado no aparelho de um único usuário e não atende a concorrência global de múltiplos acessos simultâneos. No back-end, o **Node.js** utiliza ORMs e query builders (como Prisma ou Drizzle) conectados a bancos de dados relacionais e transacionais (PostgreSQL, MySQL) para garantir operações ACID e integridade consistente entre todos os usuários.

<Aside type="note" title="SaaS, BaaS e Acesso a Serviços no Front-end">
Embora o front-end não possa abrir conexões TCP diretas para bancos de dados ou servidores SMTP por conta do sandbox, arquiteturas modernas frequentemente utilizam serviços em nuvem (SaaS e Backend-as-a-Service) que expõem APIs web seguras sobre HTTPS e WebSockets.

Nesses cenários, a aplicação front-end conversa com serviços como **Resend**, **EmailJS** ou **SendGrid** para envio transacional de e-mails, ou conecta-se a plataformas BaaS como **Supabase** e **Firebase**. Provedores como o **Supabase** empacotam uma infraestrutura completa acessível diretamente do navegador:

- **Autenticação (Auth)**: cadastro de usuários, login social (OAuth) e controle de sessões via tokens JWT.
- **Banco de Dados e Realtime**: consultas ao PostgreSQL e sincronização em tempo real de dados via WebSockets.
- **Armazenamento de Arquivos (Storage)**: upload, download e entrega de mídias em buckets na nuvem.
- **Funções Serverless (Edge Functions)**: execução de lógicas de negócio e rotinas sensíveis fora do cliente.

A segurança dessas integrações não depende de sockets abertos na máquina do usuário, mas de chaves públicas de escopo restrito, tokens de sessão e políticas de segurança em nível de linha (*Row Level Security* ou RLS) aplicadas no próprio servidor.
</Aside>

### Segurança, Permissões e Níveis de Acesso

Para os recursos do dispositivo e do sistema que as Web APIs expõem com segurança, o navegador adota quatro camadas progressivas de proteção para evitar abusos por páginas maliciosas:

1. **Isolamento por Origem (*Same-Origin Policy*)**: Dados armazenados no `localStorage`, cookies e caches pertencem estritamente à combinação de protocolo, domínio e porta da aplicação. Um site em `exemplo.com` não consegue ler dados de `outro-site.com`.
2. **Contexto Seguro (*Secure Context*)**: Recursos modernos e sensíveis (como Geolocation, Clipboard assíncrono, Web Workers compartilhados e Web Cryptography) só funcionam quando servidos sob HTTPS criptografado (ou em `localhost` durante o desenvolvimento).
3. **Gesto Explícito do Usuário (*User Activation*)**: Ações intrusivas como tocar áudio audível, entrar em tela cheia (Fullscreen), acionar vibração física ou copiar/ler dados da área de transferência exigem uma interação prévia e intencional do usuário (como o clique em um botão).
4. **Solicitação Explícita de Permissão (*Permissions API*)**: Hardware crítico e sensores privados (localização geográfica por GPS, notificações do sistema operacional e acesso a microfone/câmera) abrem um diálogo nativo do navegador e só executam após autorização expressa do usuário.

## Qual API para qual problema?

O catálogo responde "o que existe". Esta seção responde a pergunta prática: dado um problema concreto, qual interface resolve, e qual alternativa costuma ser tentada incorretamente:

| Necessidade | Escolha | Alternativa que perde, e por quê |
| --- | --- | --- |
| Confirmar uma ação com o usuário | [Dialog](../../ui/dialog/) com `showModal()` | `div` com `z-index`: foco, `Esc` e camada superior ficam por sua conta |
| Guardar uma preferência de interface | [Web Storage](../../storage/local-storage/) | Cookie: viaja em toda requisição HTTP, sem necessidade |
| Guardar uma sessão autenticada | [Cookie `HttpOnly`](../../storage/cookies/) | `localStorage`: qualquer script injetado (XSS) lê o token |
| Buscar dados de uma API | [Fetch](../../http/fetch/) | `XMLHttpRequest`: mais verboso, baseado em callbacks legados |
| Avisar o usuário fora da aba | [Notification](../../device/notification/) | Título da aba piscando: só funciona se a barra do navegador estiver visível |
| Avisar sobre algo visível na tela | Aviso na própria página | [Notification](../../device/notification/): interrompe desnecessariamente o usuário |
| Copiar um valor para a área de transferência | [Clipboard](../../input/clipboard/) | Instrução textual para selecionar à mão |
| Receber arquivos arrastados | [Drag and Drop](../../input/drag-and-drop/) | Apenas `<input type="file">`: ignora o gesto natural de arrastar da área de trabalho |
| Localizar o usuário para buscar algo perto | [Geolocation](../../device/geolocation/) | GeoIP no servidor: precisão apenas em nível de cidade/provedor |
| Escolher idioma ou moeda | Cabeçalho `Accept-Language` | [Geolocation](../../device/geolocation/): gasta o diálogo de permissão do navegador à toa |
| Desenhar muitos elementos gráficos por quadro | [Canvas](../../media/canvas/) | SVG: múltiplos nós no DOM não sustentam alta taxa de quadros (60 fps) |
| Desenhar um gráfico acessível e interativo | SVG e HTML | [Canvas](../../media/canvas/): o desenho em pixels não existe para leitores de tela |
| Renderizar cenas 3D interativas aceleradas por hardware | [WebGL e WebGPU](../../media/webgl-webgpu/) | Canvas 2D: rasterização por CPU sem pipeline de shaders nem malhas 3D complexas |
| Ler a página em voz alta a pedido | [Web Speech](../../media/web-speech/) | Leitura automática: conflita com o leitor de tela pré-configurado do usuário |
| Capturar vídeo da webcam ou áudio do microfone | [MediaDevices](../../media/media-devices/) com `getUserMedia` | Upload manual de arquivo: não permite visualização nem processamento em tempo real |
| Fazer chamada de vídeo em tempo real (< 500 ms) | [Streaming](../../media/streaming/) com WebRTC | Polling HTTP ou WebSockets: sobrecarga e latência excessivas para fluxo contínuo de vídeo |
| Transmitir live ou vídeo longo para grande público | [Streaming](../../media/streaming/) com MediaSource (MSE) | WebRTC puro: custo de tráfego e infraestrutura P2P inviável para milhares de espectadores simultâneos |
| Compartilhar a tela do computador | [Streaming](../../media/streaming/) com `getDisplayMedia` | Gravação manual externa com upload posterior |
| Confirmar um toque em celular | [Vibration](../../device/vibration/) | Alerta puramente visual: exige que o usuário esteja olhando para a tela |
| Ocupar a tela com vídeo ou apresentação | [Fullscreen](../../ui/fullscreen/) | `position: fixed`: não esconde a barra de endereços do navegador |
| Evitar que cálculos pesados travem a interface | [Web Worker](../workers/) | Otimização prematura em JS: apenas adia o travamento sem isolar a thread |
| Acelerar um algoritmo matemático intensivo | [WebAssembly](../webassembly/) | [Web Worker](../workers/) isolado: destrava a interface, mas não acelera a execução da conta |

<Aside type="note" title="Além das Trilhas Principais">
O ecossistema do navegador também conta com interfaces avançadas para bancos locais (IndexedDB), Service Workers offline, áudio modular (Web Audio), biometria (WebAuthn/Passkeys) e acesso a periféricos (Web Bluetooth/USB). Para uma visão panorâmica dessas interfaces complementares, consulte a página de referência [Outras Web APIs](../../reference/other-apis/).
</Aside>

## Web APIs na Era da Inteligência Artificial

Pedir a um assistente "carregue os dados da API e mostre na tela" ou "copie este texto para a área de transferência" devolve, em segundos, um trecho que compila e executa. Contudo, quase toda Web API tem comportamentos de borda que só aparecem fora do caminho feliz:

| O que mudou | O que permanece |
| --- | --- |
| Escrever a sintaxe da chamada deixou de ser o gargalo | Decidir **qual** API resolve o problema continua sendo responsabilidade do desenvolvedor |
| O modelo conhece a assinatura de quase toda interface | Ele não prevê se o servidor remoto responderá com cabeçalhos de CORS adequados |
| O código gerado passa no primeiro teste manual | Permissão negada, `null` e status HTTP 500 continuam ocorrendo em produção |
| A sintaxe raramente vem errada | O tratamento de erros e estados intermediários costuma vir incompleto |

As subseções a seguir mostram esse comportamento na prática e detalham o checklist essencial de revisão.

### Armadilhas Recorrentes por API

A tabela resume as omissões mais frequentes em código gerado por IA para Web APIs:

| API | O que o modelo costuma gerar | Como se manifesta | Como mitigar |
| --- | --- | --- | --- |
| Fetch | `await response.json()` sem checar `response.ok` | Erro em `map()` ou tela em branco | Exigir `if (!response.ok) throw` no contrato |
| Web Storage | `JSON.parse(localStorage.getItem(k))` direto | `null` na primeira visita ou `SyntaxError` com dado corrompido | Fornecer valor padrão e envolver a leitura em `try/catch` |
| Notification | `requestPermission()` disparado no carregamento da página | Bloqueio automático e permanente pelo navegador | Disparar a solicitação apenas após ação do usuário |
| Clipboard | `writeText()` sem tratamento de rejeição | Botão inerte quando a permissão da área de transferência é recusada | Tratar a Promise e exibir feedback visual de sucesso ou falha |
| Geolocation | Apenas o callback de sucesso | Aplicação travada sem resposta caso o usuário recuse o compartilhamento | Obrigatoriamente fornecer callback de erro e alternativa manual |
| Drag and Drop | Ouvinte de `drop` sem `preventDefault()` no evento `dragover` | O elemento arrastado nunca é aceito pela zona de soltura | Adicionar `event.preventDefault()` em ambos os eventos |
| CORS | Sugestão de `mode: 'no-cors'` para contornar bloqueios | Resposta opaca com corpo inacessível ao JavaScript | Rejeitar a flag e ajustar os cabeçalhos `Access-Control-*` no servidor |
| DOM | `innerHTML` concatenando dados recebidos da API | Vulnerabilidade a injeção de scripts (XSS) | Utilizar `textContent` ou nós criados via `createElement` |
| WebGL | Criação de buffers dentro do loop de animação (`render`) | Vazamento de VRAM na GPU e quedas bruscas de FPS | Alocar buffers e shaders uma única vez na inicialização |
| MediaDevices | `video.srcObject = null` sem invocar `track.stop()` | Câmera física permanece ativa consumindo bateria e LED aceso | Executar `stream.getTracks().forEach(t => t.stop())` no desmonte |
| WebRTC | Omissão de servidores STUN/TURN no `iceServers` | Conexão funciona em rede local mas falha entre celulares e NATs | Configurar servidores STUN/TURN públicos ou corporativos na conexão |

### Checklist de revisão antes do merge

Antes de aceitar trechos de Web APIs em sua aplicação, valide os seguintes pontos:

1. Toda chamada `fetch()` valida `response.ok` antes de consumir o corpo da resposta?
2. Toda leitura de `localStorage` ou `sessionStorage` trata parsing de JSON e valor padrão?
3. Chamadas a APIs com permissão (Notificações, Câmera, Localização) partem exclusivamente de um gesto do usuário?
4. Toda Promise de Web API possui tratamento adequado de rejeição com retorno claro na interface?
5. Dados dinâmicos de origem externa são renderizados com segurança sem `innerHTML` vulnerável?
6. As interfaces utilizadas possuem suporte garantido nos navegadores definidos pelo projeto?
