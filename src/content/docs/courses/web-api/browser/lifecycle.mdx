Antes de manipular elementos com JavaScript, é preciso entender **em que momento a página existe**.
O navegador baixa o HTML, interpreta as tags, constrói a árvore DOM, carrega arquivos externos,
executa scripts e dispara eventos em uma ordem específica.

## Objetivo

Compreender o caminho que o navegador percorre do primeiro byte de HTML até a página interativa, para escolher o momento certo e o formato ideal de executar cada script. Ao final do tópico, o leitor deve ser capaz de:

- Descrever as etapas entre a chegada do HTML e a construção completa do DOM.
- Comparar as diferentes formas de integrar JavaScript ao HTML (scripts embutidos, externos, atributos inline e módulos) e suas regras de escopo.
- Escolher entre `defer`, `async` e `type="module"` conforme o script precise ou não do DOM pronto.
- Diferenciar `DOMContentLoaded` de `load` pelo que já está disponível em cada um.
- Consultar `document.readyState` para decidir se o código deve esperar por um evento.
- Reagir a `visibilitychange`, `pagehide` e `beforeunload` para salvar estado antes que a aba seja ocultada ou descartada.

## O Caminho do HTML até a Página Interativa

Quando o navegador requisita um endereço na web, a página não surge instantaneamente pronta. O navegador recebe um fluxo contínuo de bytes pela rede e realiza diversas tarefas em paralelo: analisa as tags HTML (*parsing*), constrói a árvore de elementos do DOM, dispara o download de recursos externos (folhas de estilo CSS, imagens, fontes e scripts JavaScript) e executa o código conforme as regras de bloqueio de cada tag.

O diagrama de sequência abaixo ilustra a ordem temporal em que o servidor, o navegador, o parser HTML e o motor JavaScript interagem durante o carregamento de uma página:

<Mermaid title="Linha do Tempo do Carregamento da Página">
{`
sequenceDiagram
  autonumber
  participant S as Servidor
  participant B as Navegador
  participant P as Parser
  participant D as DOM
  participant JS as JavaScript

  S->>B: Envia HTML
  B->>P: Inicia parsing
  P->>D: Cria nós do DOM
  B->>S: Solicita CSS, imagens e JS
  Note over P,JS: Script síncrono pausa o parser
  P->>D: Conclui leitura do HTML
  D->>JS: Dispara DOMContentLoaded
  S-->>B: Entrega assets externos
  B->>JS: Dispara window load
`}
</Mermaid>

### O Processo de Carregamento Passo a Passo

O fluxo demonstrado na linha do tempo organiza-se em cinco etapas fundamentais:

1. **Recepção do Stream e Parsing Incremental**: O navegador não aguarda o arquivo `.html` completo chegar pela rede para iniciar o processamento. Conforme os primeiros pacotes de bytes chegam, o parser converte o texto em tokens (`<html>`, `<body>`, `<main>`) e insere os nós correspondentes na árvore DOM.
2. **Preload Scanner e Downloads em Paralelo**: Enquanto o parser principal analisa o documento sequencialmente, um processo em segundo plano (*Preload Scanner*) inspeciona o arquivo à procura de tags `<link rel="stylesheet">`, `<img>` e `<script src="...">`, solicitando o download desses recursos pela rede o mais cedo possível.
3. **Ponto Crítico de Bloqueio do Parser**: Ao encontrar uma tag `<script>` tradicional (sem `defer` ou `type="module"`), o parser interrompe a leitura do HTML. O navegador aguarda o download do arquivo JavaScript e o executa imediatamente antes de continuar a processar as tags restantes do corpo da página.
4. **Disparo do Evento `DOMContentLoaded`**: Assim que o parser atinge a tag de fechamento `</html>` e todos os scripts com `defer` ou módulos foram executados, o evento `DOMContentLoaded` é emitido. Neste estágio, a estrutura de elementos está completamente montada na memória.
5. **Disparo do Evento `window.load`**: Após o término do download e decodificação de todas as imagens, fontes tipográficas, folhas de estilo CSS e iframes externos, o navegador emite o evento global `load` na janela (`window`).

### Impacto Prático no Código Front-end

Compreender essa cronologia evita os dois erros mais recorrentes no desenvolvimento front-end com JavaScript vanilla:

- **Seleção de elementos inexistentes (`null`)**: Se um script for executado no `<head>` sem atributos assíncronos, o parser ainda não terá chegado nas tags do `<body>`. Qualquer chamada a `document.querySelector('#botao')` retornará `null`, gerando a clássica exceção `TypeError: Cannot read properties of null`.
- **Medição de dimensões zeradas em imagens**: No momento em que o evento `DOMContentLoaded` dispara, os nós `<img>` já existem no DOM, mas os arquivos de imagem podem ainda estar em trânsito pela rede. Tentar ler propriedades dimensionais como `img.offsetWidth` ou `img.naturalHeight` nesse instante pode retornar `0`. Medições geométricas de mídia só são confiáveis após o evento `load` da própria imagem ou de `window`.

<Aside type="tip" title="Diretriz de inicialização">
Para associar ouvintes de eventos a botões, formulários e elementos visuais, utilize scripts carregados com `type="module"` ou aguarde o evento `DOMContentLoaded`. Deixe para escutar o evento `load` apenas quando sua lógica depender do carregamento completo de imagens ou folhas de estilo externas.
</Aside>

## Formas de Integrar JavaScript ao HTML

No desenvolvimento web, o código JavaScript pode ser conectado ao HTML de múltiplas maneiras. Cada formato define regras próprias de isolamento de escopo, ordem de execução e manutenção da aplicação.

As subseções a seguir analisam cada padrão em detalhe e apresentam cenários didáticos de visibilidade de variáveis.

### 1. Script Embutido (Inline) vs Arquivo Externo

A tag `<script>` pode conter o código diretamente em seu corpo ou apontar para um arquivo externo através do atributo `src`:

```html title="Comparativo: script embutido vs arquivo externo"
<!-- 1. Script Embutido (Inline): o código mora dentro do arquivo HTML -->
<script>
  console.log('Executando script embutido no HTML');
</script>

<!-- 2. Script Externo: o código mora em um arquivo .js separado -->
<script src="/js/app.js"></script>
```

Existe uma **regra inviolável do elemento `<script>`**: a tag ou contém código interno entre `<script>` e `</script>`, ou utiliza o atributo `src`, **mas nunca os dois ao mesmo tempo**. Se você declarar `src` e também escrever código dentro da tag, o navegador fará o download do arquivo externo e **ignorará solenemente todo o código interno**:

```html title="Armadilha comum: código interno ignorado quando src existe"
<!-- ATENÇÃO: o console.log NÃO será executado pelo navegador! -->
<script src="/js/app.js">
  console.log('Este código é 100% ignorado pelo navegador porque o atributo src foi informado!');
</script>
```

<Aside type="caution" title="Regra de ouro">
Para carregar um arquivo externo e executar um script de inicialização, declare sempre **duas tags `<script>` separadas**.
</Aside>

### 2. Código em Atributos HTML (Manipuladores Inline e Pseudo-protocolos)

O HTML permite historicamente executar JavaScript dentro de atributos de tags:

```html title="Exemplos de código embutido em atributos HTML"
<!-- 1. Manipuladores de eventos inline (onevent) -->
<button onclick="alert('Clicado!')">Salvar</button>
<input type="text" oninput="console.log(this.value)" />

<!-- 2. Pseudo-protocolo javascript: em links -->
<a href="javascript:void(0)" onclick="abrirModal()">Ver Detalhes</a>
```

Apesar de funcionarem por compatibilidade com a web antiga, essas práticas são **fortemente desencorajadas em projetos modernos**:

- **Mistura de responsabilidades**: Dificulta a manutenção ao espalhar regras de negócio e lógica de controle dentro da estrutura visual da página.
- **Escopo confuso**: O código dentro de um `onclick` roda em uma cadeia de escopos oculta do navegador, o que gera comportamentos imprevisíveis ao tentar acessar variáveis do script principal.
- **Incompatível com CSP**: Políticas de segurança contra ataques de injeção de script (XSS) bloqueiam manipuladores inline por padrão.
- **Prejuízo à acessibilidade**: O uso de `href="javascript:..."` quebra o comportamento padrão de links para leitores de tela e atalhos de teclado.

A abordagem moderna e recomendada é manter o HTML declarativo e registrar os ouvintes no JavaScript via `addEventListener()`:

```html title="HTML limpo e semântico"
<button id="btn-salvar">Salvar Alterações</button>
```

```js title="app.js"
const botao = document.querySelector('#btn-salvar');
botao.addEventListener('click', () => {
  console.log('Evento tratado de forma limpa e desacoplada');
});
```

### 3. Escopo e Visibilidade entre Contextos de Execução

Quando você possui vários scripts na mesma página, a visibilidade de variáveis depende do tipo da tag `<script>` utilizada:

```html title="Cenário de múltiplos scripts e visibilidade de escopo"
<!-- Script Clássico 1: variáveis no topo entram no escopo global -->
<script>
  var nomeApp = 'DevLab';
  let versao = 1.0;
  function somar(a, b) {
    return a + b;
  }
</script>

<!-- Script Clássico 2: enxerga tudo declarado no Script 1 -->
<script>
  console.log(nomeApp); // 'DevLab' (disponível diretamente)
  console.log(window.nomeApp); // 'DevLab' (var vira propriedade de window)
  console.log(versao); // 1.0 (let global é compartilhado entre scripts clássicos)
  console.log(somar(10, 5)); // 15
</script>

<!-- Script Módulo: possui escopo de módulo totalmente ISOLADO -->
<script type="module">
  const segredoInterno = 'chave-123';
  export const TAXA = 0.05;

  // Para expor intencionalmente algo para scripts externos legados:
  window.executarAcaoGlobal = () => console.log('Ação chamada do módulo');
</script>

<!-- Script Clássico 3: NÃO consegue acessar variáveis internas do Módulo -->
<script>
  console.log(typeof segredoInterno); // 'undefined' (o módulo não vaza variáveis!)
  window.executarAcaoGlobal(); // Funciona porque foi anexada explicitamente a window
</script>
```

As diferenças essenciais entre scripts clássicos e módulos JavaScript são:

- **Scripts Clássicos (`<script>`)**: Compartilham o escopo global. Declarações com `var` e `function` viram propriedades diretas do objeto `window`. Variáveis `let` e `const` no topo não entram em `window`, mas permanecem visíveis para scripts clássicos executados posteriormente.
- **Módulos JavaScript (`<script type="module">`)**: Possuem **escopo fechado por arquivo**. Nenhuma variável declarada vaza para `window` ou para outros scripts, evitando colisões de nomes.
- **Strict Mode Automático**: Módulos rodam em modo estrito (`'use strict'`) por padrão, prevenindo erros sutis de variáveis não declaradas.
- **Execução Adiada (*Deferred*)**: Módulos nunca bloqueiam a montagem do HTML; o navegador baixa os módulos em paralelo e só os executa após o DOM estar pronto.

### 4. Tabela Comparativa de Integração

A tabela resume as opções de integração de código JavaScript no HTML:

| Forma de Integração | Sintaxe Exemplo | Escopo de Variáveis | Ordem de Execução | Recomendação de Uso |
| --- | --- | --- | --- | --- |
| **Módulo JavaScript** | `<script type="module" src="app.js"></script>` | Módulo isolado (fechado) | Adiado (após o DOM pronto) | **Padrão recomendado para aplicações modernas** |
| **Script Externo com `defer`** | `<script defer src="app.js"></script>` | Global compartilhado (`window`) | Adiado (após o DOM pronto) | Padrão seguro para scripts clássicos sem bundler |
| **Script Externo Clássico** | `<script src="app.js"></script>` | Global compartilhado (`window`) | Imediato (bloqueia o parser) | Evitar no `<head>` sem `defer` |
| **Script Embutido (Inline)** | `<script>...</script>` | Global compartilhado | Imediato na posição em que é lido | Apenas para configurações iniciais críticas |
| **Manipulador Inline** | `<button onclick="...">` | Escopo opaco do elemento | Ao disparar o evento | **Evitar** (usar `addEventListener`) |
| **Pseudo-protocolo `href`** | `<a href="javascript:...">` | Escopo global | Ao clicar no link | **Evitar** (usar `<button>` com ouvinte) |

## Modos de Execução: Síncrono, `defer`, `async` e Módulos

Ao utilizar arquivos JavaScript externos com a tag `<script src="...">`, o navegador oferece três atributos fundamentais para controlar **quando o arquivo é baixado** e **quando ele é executado**:

| Forma de carregar | Quando baixa? | Quando executa? | Uso recomendado |
| --- | --- | --- | --- |
| `<script src="app.js"></script>` | Ao encontrar a tag | Imediatamente, bloqueando o parser | Evitar em páginas modernas |
| `<script defer src="app.js"></script>` | Em paralelo ao HTML | Depois do DOM pronto, antes de `DOMContentLoaded` | Padrão seguro para scripts clássicos |
| `<script async src="app.js"></script>` | Em paralelo ao HTML | Assim que baixar, sem ordem garantida | Scripts independentes, como analytics |
| `<script type="module" src="app.js"></script>` | Em paralelo ao HTML | Como `defer`, com suporte a `import/export` | Padrão moderno para aplicações |

```html title="Carregamento recomendado para JavaScript moderno"
<head>
  <script type="module" src="/src/main.js"></script>
</head>
<body>
  <button id="btn-salvar">Salvar</button>
</body>
```

Como módulos são adiados por padrão, o botão já existe quando `main.js` roda:

```js title="main.js"
const botao = document.querySelector('#btn-salvar');

botao.addEventListener('click', () => {
  console.log('Dados salvos');
});
```

<Aside type="tip" title="Regra prática">
Em projetos com Vite, React, Vue ou módulos ES, use `type="module"`. Em HTML simples com JavaScript
clássico, use `defer`. Evite depender de scripts no final do `<body>` como única estratégia de
organização.
</Aside>

## `DOMContentLoaded` vs `load`

Dois eventos aparecem muito no ciclo de carregamento:

- **`DOMContentLoaded`**: dispara quando o HTML foi lido e o DOM está montado.
- **`load`**: dispara depois que imagens, CSS, iframes e outros recursos externos terminaram de carregar.

```js title="Quando usar cada evento"
document.addEventListener('DOMContentLoaded', () => {
  const titulo = document.querySelector('h1');
  console.log('DOM pronto:', titulo.textContent);
});

window.addEventListener('load', () => {
  console.log('Pagina e recursos externos carregados');
});
```

Use `DOMContentLoaded` para inicializar interatividade. Use `load` apenas quando o código depende
das dimensões finais de imagens, iframes ou recursos externos.

## `document.readyState`

A propriedade `document.readyState` informa o estágio atual do documento:

| Valor | Significado |
| --- | --- |
| `loading` | O HTML ainda está sendo processado |
| `interactive` | O DOM já foi construído, mas recursos externos podem estar carregando |
| `complete` | Página e recursos externos terminaram de carregar |

```js title="Inicializacao segura reaproveitavel"
function iniciarPagina() {
  const app = document.querySelector('#app');

  if (!app) {
    console.warn('Elemento #app nao encontrado.');
    return;
  }

  app.textContent = 'Aplicacao iniciada';
}

if (document.readyState === 'loading') {
  document.addEventListener('DOMContentLoaded', iniciarPagina);
} else {
  iniciarPagina();
}
```

Esse padrão é útil para bibliotecas ou arquivos reaproveitáveis que podem ser carregados em momentos
diferentes.

## Página Visível, Oculta ou Descartada

O usuário pode trocar de aba, bloquear o celular, minimizar a janela ou navegar para outra página.
O navegador expõe alguns eventos para reagir a essas mudanças.

### `visibilitychange`

O evento `visibilitychange` indica se a página está visível ou oculta:

```js title="Pausando tarefas quando a aba fica oculta"
document.addEventListener('visibilitychange', () => {
  if (document.hidden) {
    console.log('Aba oculta: pausar atualizacoes pesadas.');
  } else {
    console.log('Aba visivel: retomar atualizacoes.');
  }
});
```

Casos comuns:

- pausar animações ou polling;
- reduzir chamadas HTTP quando a aba está em segundo plano;
- salvar rascunhos antes de uma navegação;
- retomar sincronização quando a aba volta a ficar visível.

### `beforeunload`

O evento `beforeunload` pode avisar sobre perda de dados ao fechar ou recarregar a página. Use com
moderação, apenas quando existe risco real de descarte de trabalho não salvo.

```js title="Aviso ao sair com alteracoes nao salvas"
let formularioAlterado = false;

document.querySelector('form').addEventListener('input', () => {
  formularioAlterado = true;
});

window.addEventListener('beforeunload', (event) => {
  if (!formularioAlterado) return;

  event.preventDefault();
  event.returnValue = '';
});
```

<Aside type="caution" title="Limitação importante">
Navegadores modernos não permitem personalizar livremente a mensagem do `beforeunload`. Eles exibem
um aviso genérico para evitar abuso.
</Aside>

## Quando usar, e quando não usar?

Escolher o momento de execução é uma decisão de uma linha, tomada no atributo da tag ou no nome do
evento, e ela define se o script vê o DOM pronto, se ele atrasa a primeira pintura da página e se ele
ainda roda quando o usuário troca de aba.

A tabela reúne as cinco situações mais frequentes e a alternativa que perde em cada uma:

| Situação | Escolha | Em vez de |
| --- | --- | --- |
| Script que manipula elementos da página | `defer` ou `type="module"` | `<script>` no `<head>` sem atributo, que bloqueia o *parser* |
| Script independente do DOM (métrica, telemetria) | `async` | `defer`, que atrasa o disparo sem necessidade |
| Código que precisa da árvore montada, mas não das imagens | `DOMContentLoaded` | `load`, que espera cada imagem e cada iframe |
| Medição de tempo total de carregamento | `load` | `DOMContentLoaded`, que ignora os recursos externos |
| Salvar rascunho antes de a aba sumir | `visibilitychange` com `hidden` | `beforeunload`, que não dispara de forma confiável no celular |

As duas últimas linhas costumam ser trocadas uma pela outra. `load` só interessa quando o assunto é o
peso dos recursos; para tudo que depende de elementos, `DOMContentLoaded` chega antes e evita que a
interface fique inerte enquanto uma imagem grande termina de baixar.

## Erros Comuns

Três sintomas concentram quase todo problema de sincronização entre script e DOM. A tabela liga cada um à causa provável e à correção, e vale como roteiro de diagnóstico quando o código "não encontra" um elemento que está visivelmente na página:

| Sintoma | Causa provável | Correção |
| --- | --- | --- |
| `querySelector(...)` retorna `null` | Script executou antes do elemento existir | Use `defer`, `type="module"` ou `DOMContentLoaded` |
| Evento de clique não funciona | O elemento foi criado depois do listener | Use delegação de eventos ou registre após renderizar |
| Medida de imagem vem `0` | Imagem ainda não carregou | Use `load` da imagem ou `window.load` |
| Timer continua rodando em aba oculta | Código ignora visibilidade da página | Use `visibilitychange` |
| Usuário perde formulário ao fechar aba | Estado não foi salvo | Use autosave e, se necessário, `beforeunload` |

<details>
  <summary>Possível resposta</summary>

  1. `DOMContentLoaded` dispara quando o DOM está pronto para manipulação. `load` dispara depois que

  2. Scripts do tipo módulo são executados de forma adiada em relação ao parsing do HTML, de modo
  semelhante a `defer`. Assim, o DOM básico já está montado quando o código roda.

  3. Quando a aplicação deve pausar ou retomar tarefas conforme a aba fica visível ou oculta, como
  polling, animações, sincronização e timers.
</details>

Crie uma função `inicializarQuandoPronto(callback)` que execute o `callback` imediatamente se o DOM
