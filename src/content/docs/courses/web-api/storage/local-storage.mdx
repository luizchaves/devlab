Diferente das requisições HTTP tradicionais que armazenam dados no servidor, as **Web Storage APIs** permitem que as aplicações mantenham informações salvas diretamente no navegador do usuário de forma persistente.

## Objetivo

Compreender a Web Storage API como persistência simples no cliente, com suas garantias e seus limites. Ao final do tópico, o leitor deve ser capaz de:

- Comparar `localStorage`, `sessionStorage`, cookies e IndexedDB por tempo de vida, capacidade e finalidade.
- Usar `setItem()`, `getItem()`, `removeItem()` e `clear()`, lembrando que tudo é armazenado como string.
- Serializar e recuperar objetos com `JSON.stringify()` e `JSON.parse()`, tratando o valor ausente.
- Encapsular o acesso em um módulo reutilizável em vez de espalhar chaves pelo código.
- Sincronizar abas abertas na mesma origem com o evento `storage`.

---

## Comparativo de Armazenamento no Navegador

O navegador oferece diferentes opções para salvar dados no cliente, cada uma adequada a um caso de uso específico:

| Tecnologia | Capacidade Média | Expiração | Acesso no Servidor? | Tipo de Dados |
| --- | --- | --- | --- | --- |
| **`localStorage`** | ~5 MB por origem | Permanente (até ser limpo) | Não | Apenas Strings |
| **`sessionStorage`** | ~5 MB por origem | Ao fechar a aba/janela | Não | Apenas Strings |
| **Cookies** | ~4 KB por cookie | Data configurável | Sim (enviado via HTTP) | Strings |
| **IndexedDB** | > 250 MB (banco de dados) | Permanente | Não | Objetos / Chave-Valor |

## A Web Storage API

Os objetos `localStorage` e `sessionStorage` compartilham exatamente a mesma interface de métodos e propriedades. A única diferença é a persistência: enquanto o `sessionStorage` é limpo quando a aba é fechada, o `localStorage` permanece armazenado por tempo indeterminado.

<Mermaid title="Fluxo de Armazenamento no LocalStorage">
{`
flowchart TD
  A["1. Objeto JS original<br />{ id: 42, nome: 'Ana' }"] -->|"JSON.stringify()"| B["2. String JSON serializada"]
  B -->|"localStorage.setItem()"| C["3. Disco do Navegador<br />(Armazenamento Local)"]
  C -->|"localStorage.getItem()"| D["4. String JSON lida"]
  D -->|"JSON.parse()"| E["5. Objeto JS reconstituído"]
`}
</Mermaid>

A interface tem cinco métodos, e todos operam sobre strings. O exemplo percorre gravação, leitura e remoção:

```js title="Operações com localStorage"
// 1. Armazenar uma string
localStorage.setItem('temaPref', 'dark');

// 2. Ler um valor armazenado (retorna string ou null se não existir)
const tema = localStorage.getItem('temaPref');
console.log(tema); //=> "dark"

// 3. Remover uma chave específica
localStorage.removeItem('temaPref');

// 4. Limpar TODOS os dados da origem atual
localStorage.clear();
```

## Serialização de Objetos com JSON

Como a Web Storage API armazena **exclusivamente valores do tipo string**, tentar salvar um objeto JavaScript diretamente resultará na gravação da string inútil `"[object Object]"`.

Para armazenar estruturas de dados complexas (arrays e objetos), devemos serializá-las para JSON na gravação e desserializá-las na leitura:

```js title="Gravando e lendo objetos com JSON"
const usuario = {
  id: 42,
  nome: 'Ana Silva',
  preferencias: { notificacoes: true }
};

// GRAVAÇÃO: Converte o objeto para string JSON
const jsonString = JSON.stringify(usuario);
localStorage.setItem('@app:usuario', jsonString);

// LEITURA: Lê a string e converte de volta para objeto JS
const dadosSalvos = localStorage.getItem('@app:usuario');

if (dadosSalvos) {
  try {
    const usuarioRecuperado = JSON.parse(dadosSalvos);
    console.log(usuarioRecuperado.nome); // "Ana Silva"
  } catch (erro) {
    console.error("Erro ao fazer parse do JSON do localStorage:", erro);
  }
}
```

<Aside type="caution" title="Limites de Cota e Exceções">
Tentar gravar dados além do limite de cota (~5MB) disparará a exceção `QuotaExceededError`. Envolva sempre operações de `setItem` em blocos `try/catch` quando lidar com dados volumosos.
</Aside>

---

<Aside type="caution" title="Dica de IA: Confira a primeira visita no código de armazenamento gerado">
`JSON.parse(localStorage.getItem('items'))` é a linha que quase todo assistente escreve, e ela
funciona em todas as execuções menos na primeira: sem a chave gravada, `getItem()` devolve `null`, o
`parse()` também devolve `null` e o `map()` seguinte quebra a tela. Um valor corrompido produz um
`SyntaxError` igualmente fatal.

**Prompt:** *"Reescreva estas funções de leitura e escrita com valor padrão para chave inexistente e
`try/catch` para JSON inválido, e liste os valores de `localStorage` que quebram a versão atual."*
</Aside>

## Módulo de Armazenamento Reutilizável

Em aplicações reais, abstraímos as chamadas do `localStorage` em um serviço centralizado para evitar duplicação de `JSON.stringify` e `JSON.parse`:

```js title="src/services/storage.js"
export const storage = {
  get(key, defaultValue = null) {
    try {
      const item = localStorage.getItem(key);
      return item ? JSON.parse(item) : defaultValue;
    } catch (error) {
      console.error(`Erro ao ler chave ${key}:`, error);
      return defaultValue;
    }
  },

  set(key, value) {
    try {
      localStorage.setItem(key, JSON.stringify(value));
    } catch (error) {
      console.error(`Erro ao gravar chave ${key}:`, error);
    }
  },

  remove(key) {
    localStorage.removeItem(key);
  }
};
```

## O Evento `storage`

Quando um valor no `localStorage` é alterado, o navegador dispara o evento `storage` em **todas as outras abas ativas do mesmo domínio**:

```js title="Sincronizando estados entre abas"
window.addEventListener('storage', (event) => {
  console.log(`A chave ${event.key} foi alterada!`);
  console.log(`Valor antigo: ${event.oldValue}`);
  console.log(`Novo valor: ${event.newValue}`);
});
```

## Quando usar, e quando não usar?

O Web Storage é síncrono, guarda apenas strings e tem cota de poucos megabytes por origem. Essas três
características definem sozinhas os limites do que faz sentido colocar nele.

A tabela relaciona cada tipo de dado ao mecanismo de armazenamento adequado:

| Situação | Escolha | Por quê |
| --- | --- | --- |
| Preferência simples que deve sobreviver ao fechamento do navegador | `localStorage` | Persiste por origem, sem data de validade |
| Rascunho válido apenas enquanto a aba estiver aberta | `sessionStorage` | Some sozinho, sem código de limpeza |
| Credencial de sessão | Cookie `HttpOnly` no servidor | O JavaScript não deve conseguir ler o valor |
| Coleção grande, busca por índice ou dados binários | IndexedDB | Assíncrono e sem o teto de poucos megabytes |
| Cache de respostas HTTP | Cache API com *service worker* | Guarda a resposta inteira, com cabeçalhos e status |
| Estado que precisa ser o mesmo em outro dispositivo | Servidor | O armazenamento local não sai daquele navegador |

A quarta linha marca o ponto de virada. Enquanto o dado couber em algumas chaves e for lido de uma
vez, `localStorage` é a escolha mais simples; a partir do momento em que se quer consultar por campo
ou percorrer milhares de registros, o acesso síncrono passa a travar a interface.

## Exercício

Os itens abaixo exercitam serialização, valor ausente e o limite de cota do armazenamento:

1. Qual a diferença fundamental de persistência entre `localStorage` e `sessionStorage`?
2. Por que a chamada `localStorage.setItem('usuario', { nome: 'Ana' })` resulta em um erro de gravação sem utilidade? Como corrigir?
3. O evento `storage` é disparado na mesma aba onde a alteração foi realizada?

<details>
  <summary>Possível resposta</summary>

  1. O `localStorage` mantém os dados gravados no disco do usuário indefinidamente, mesmo após fechar o navegador. O `sessionStorage` apaga os dados assim que a aba ou janela correspondente for fechada.

  2. Porque a Web Storage API converte tudo para string por padrão. Sem o `JSON.stringify()`, o objeto é convertido para a string `"[object Object]"`. A forma correta é: `localStorage.setItem('usuario', JSON.stringify({ nome: 'Ana' }))`.

  3. Não. O evento `storage` é disparado apenas nas **outras abas ou janelas** abertas na mesma origem, permitindo sincronizar o estado entre abas diferentes.
</details>

## Desafio

Crie uma função `salvarHistoricoBusca(termo)` que mantenha um array dos últimos 5 termos pesquisados no `localStorage` sob a chave `@app:historico_buscas`, garantindo que não haja termos duplicados e que a lista não exceda 5 itens.

<details>
  <summary>Possível resposta</summary>

  ```js title="Histórico de busca com limite de itens"
  function salvarHistoricoBusca(termo) {
    const CHAVE = '@app:historico_buscas';
    let historico = JSON.parse(localStorage.getItem(CHAVE)) || [];

    // Remove duplicados se já existir
    historico = historico.filter(item => item !== termo);

    // Adiciona o novo termo no início
    historico.unshift(termo);

    // Limita a no máximo 5 itens
    if (historico.length > 5) {
      historico.pop();
    }

    localStorage.setItem(CHAVE, JSON.stringify(historico));
  }
  ```
</details>
