O **GraphQL** é uma linguagem de consulta (*query language*) para APIs e um ambiente de execução (*runtime*) no servidor para responder a essas consultas. Criado pelo Facebook, o GraphQL oferece uma alternativa às APIs REST tradicionais, permitindo que o cliente declare na requisição a estrutura exata dos dados que deseja receber.

Materiais: [slides do tópico](../../../../slides/courses/web-api/http/graphql/) e [mapa mental](../../../../mindmaps/courses/web-api/http/graphql/).

Como o REST, o GraphQL **não é uma interface do navegador**. Ele é uma linguagem de consulta que
viaja como texto dentro do corpo de uma requisição comum, enviada pela [Fetch API](../fetch/). Não há
objeto `GraphQL` no JavaScript: o que muda em relação ao REST é o formato do que se envia e do que se
recebe, não o modo de enviar.

## Objetivo

Compreender o GraphQL como uma alternativa ao REST na qual o cliente descreve os campos que quer receber. Ao final do tópico, o leitor deve ser capaz de:

- Contrastar REST e GraphQL quanto a número de rotas, *over-fetching* e *under-fetching*.
- Ler a anatomia de uma *query*, com operação, campos aninhados e variáveis.
- Diferenciar *query* de *mutation* pelo efeito sobre os dados.
- Enviar uma operação GraphQL por `fetch()`, com `POST` e corpo JSON.
- Interpretar a resposta, na qual o campo `errors` pode vir preenchido junto de um status 200.

## REST vs GraphQL

Enquanto uma API REST possui múltiplos endpoints fixos (ex: `/users`, `/posts`), o GraphQL expõe **um único endpoint** (geralmente `/graphql`), aceitando requisições HTTP POST contendo a consulta desejada.

| Problema / Característica | Arquitetura REST | Arquitetura GraphQL |
| --- | --- | --- |
| **Endpoints** | Múltiplos (`/users`, `/posts/1`) | Único (`/graphql`) |
| **Seleção de Campos** | Servidor decide o que retorna | Cliente escolhe os campos exatos |
| **Over-fetching** (trazer dados demais) | Comum (retorna todos os campos) | Eliminado (retorna apenas o solicitado) |
| **Under-fetching** (requisições demais) | Requer chamadas em cascata | Resolvido em uma única query aninhada |

## Formato de uma Query GraphQL

No GraphQL, as consultas são escritas em uma sintaxe declarativa semelhante a objetos JSON sem valores:

```graphql title="Sintaxe de uma Query GraphQL"
# Solicita apenas o nome e o email do usuário de ID 10
query {
  user(id: "10") {
    name
    email
  }
}
```

**Resposta retornada pelo servidor:**

```json title="Resposta em formato JSON"
{
  "data": {
    "user": {
      "name": "Ana Silva",
      "email": "ana@exemplo.com"
    }
  }
}
```

## Quando usar, e quando não usar?

GraphQL resolve um problema específico, o de clientes que precisam de recortes diferentes dos mesmos
dados, e cobra por isso em complexidade de servidor, de cache e de observabilidade. Adotá-lo fora
desse cenário troca um problema pequeno por um maior.

A tabela contrapõe os casos em que GraphQL vence àqueles em que REST continua sendo a resposta certa:

| Situação | Escolha | Por quê |
| --- | --- | --- |
| Telas diferentes consomem recortes distintos da mesma entidade | GraphQL | O cliente pede só os campos que vai exibir |
| Uma tela precisa de dados de três recursos relacionados | GraphQL | Uma requisição substitui três idas ao servidor |
| CRUD direto sobre poucos recursos | REST | O ganho não paga o *schema*, os *resolvers* e a camada extra |
| Upload de arquivos e respostas binárias | REST | GraphQL trafega JSON e precisa de especificação adicional |
| Cache de rede e CDN na frente da API | REST | O `POST` único do GraphQL não é cacheável por URL |

A última linha costuma decidir a discussão em aplicações públicas de leitura intensa. Em REST, cada
recurso tem URL própria e o cache do navegador e da CDN funcionam de graça; em GraphQL, o cache
precisa ser construído na camada de cliente.

## Executando Queries GraphQL via Fetch API

Embora existam bibliotecas clientes avançadas (como *Apollo Client* e *Relay*), é totalmente possível consumir APIs GraphQL no front-end utilizando apenas a `Fetch API` nativa, enviando uma requisição `POST` com um payload JSON contendo a propriedade `query`:

```js title="Executando uma Query GraphQL com fetch"
async function buscarPaisesComGraphQL() {
  const query = `
    query {
      countries(filter: { code: { eq: "BR" } }) {
        name
        capital
        currency
      }
    }
  `;

  try {
    const resposta = await fetch('https://countries.trevorblades.com/', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json'
      },
      body: JSON.stringify({ query })
    });

    const resultado = await resposta.json();
    console.log(resultado.data.countries[0]);
  } catch (erro) {
    console.error('Erro ao consultar GraphQL:', erro);
  }
}

buscarPaisesComGraphQL();
```

<Aside type="tip" title="Mutations em GraphQL">
Operações de criação, edição ou exclusão no GraphQL são chamadas de **Mutations**. Elas seguem o mesmo formato de envio via HTTP `POST`, substituindo a palavra-chave `query` por `mutation`.
</Aside>

Assistentes de código costumam assumir que um status HTTP 200 garante que a consulta teve sucesso, ignorando o campo `errors` no corpo da resposta:

<Aside type="caution" title="Dica de IA: Servidores GraphQL retornam erros no corpo com status HTTP 200">
Ao consumir GraphQL com a Fetch API, assistentes frequentemente checam apenas `if (!response.ok)` e tentam acessar `result.data` diretamente. No padrão GraphQL, falhas de sintaxe, campos inexistentes ou erros de execução retornam com status `200 OK` trazendo a lista de falhas na propriedade `errors`.

**Prompt:** *"Adicione validação para `if (resultado.errors) throw new Error(...)` antes de acessar `resultado.data`, e refatore a chamada para enviar parâmetros dinâmicos no campo `variables` do corpo da requisição."*
</Aside>

## Executando

Siga os passos para executar uma consulta GraphQL real diretamente no console do seu navegador:

<Steps>
1. Abra o navegador com <kbd>F12</kbd> e clique na aba **Console**.
2. Cole o código a seguir e pressione <kbd>Enter</kbd>:
   ```js title="Query de países por continente"
   const res = await fetch('https://countries.trevorblades.com/', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({
       query: '{ country(code: "BR") { name capital currency } }'
     })
   });
   const dados = await res.json();
   console.log(dados.data.country);
   ```
3. Observe o objeto retornado no console com o nome do país ("Brazil"), capital ("Brasília") e moeda ("BRL").
</Steps>

## Exercício

Os itens abaixo exercitam a escrita de *queries* e a leitura da resposta, na qual `errors` pode vir preenchido com status 200:

1. O que são os problemas de *over-fetching* e *under-fetching* e como o GraphQL os soluciona?
2. Qual método HTTP e formato de corpo são utilizados para enviar consultas GraphQL usando o `fetch` nativo?

<details>
  <summary>Possível resposta</summary>

  1. *Over-fetching* ocorre quando a API retorna mais dados do que o necessário (ex: baixar 50 campos de um usuário quando só precisamos do nome). *Under-fetching* ocorre quando um endpoint não traz dados suficientes, exigindo que o front-end faça várias requisições adicionais. O GraphQL soluciona ambos permitindo que o cliente solicite exatamente os campos necessários em uma única requisição.

  2. Utiliza-se o método HTTP `POST`, enviando no corpo da requisição um JSON com a propriedade `query` contendo a string de consulta: `{ "query": "{ ... }" }`.
</details>

## Perguntas de revisão

1. **Qual a diferença entre uma `Query` e uma `Mutation` no GraphQL?**
   <details>
     <summary>Possível resposta</summary>
     Uma `Query` é usada para leitura de dados (equivalente ao GET). Uma `Mutation` é usada para criar, atualizar ou excluir dados (equivalente a POST, PUT, DELETE).
   </details>
