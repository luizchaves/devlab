O modelo **REST (Representational State Transfer)** é a arquitetura padrão mais utilizada na Web para a construção de APIs. Em um sistema RESTful, os dados e funcionalidades da aplicação são organizados e expostos como **Recursos** acessíveis via URLs padronizadas e manipulados através dos métodos semânticos do protocolo HTTP.

Materiais: [slides do tópico](../../../../slides/courses/web-api/http/rest/) e [mapa mental](../../../../mindmaps/courses/web-api/http/rest/).

REST não é uma interface do navegador. Não existe `rest` nem `REST()` para chamar no JavaScript: o
que existe é um **acordo sobre como o servidor organiza rotas, verbos e códigos de status**. Quem faz
a chamada continua sendo a [Fetch API](../fetch/); o REST diz apenas como aquela URL e aquele corpo
devem ser desenhados. A [visão geral do guia](../../#os-três-sentidos-da-palavra-api) detalha
essa separação.

## Objetivo

Compreender o REST como um conjunto de restrições arquiteturais e consumir uma API que as respeita. Ao final do tópico, o leitor deve ser capaz de:

- Enunciar os princípios do REST, com destaque para recursos identificados por URI e para a ausência de estado no servidor.
- Mapear as operações CRUD nos verbos HTTP `GET`, `POST`, `PUT`, `PATCH` e `DELETE`.
- Interpretar as famílias de códigos de status e escolher o código correto para cada resposta.
- Diferenciar `PUT` de `PATCH` pelo que cada um faz com os campos não enviados.
- Testar uma API REST com um cliente HTTP antes de escrever a chamada no front-end.

## Princípios da Arquitetura REST

Uma API é considerada RESTful quando segue as restrições arquiteturais estabelecidas pelo protocolo HTTP:

1. **Recursos identificados por URLs**: Cada entidade do sistema (ex: usuários, produtos, pedidos) possui um identificador único (URI).
2. **Uso semântico dos Verbos HTTP**: Operações de leitura, criação, atualização e exclusão utilizam os métodos nativos do protocolo (`GET`, `POST`, `PUT`, `DELETE`).
3. **Comunicação Sem Estado (*Stateless*)**: Cada requisição feita ao servidor deve conter todas as informações necessárias para ser processada, sem depender de sessões salvas na memória do servidor.
4. **Representações padronizadas**: Os dados são transmitidos em formatos leves e padronizados, predominantemente **JSON**.

## Mapeamento de Verbos HTTP e Operações CRUD

Em REST, a URL nomeia o **recurso no plural** (ex: `/produtos`), enquanto o **verbo HTTP** define a ação a ser realizada sobre ele:

| Verbo HTTP | Exemplo de Rota | Ação CRUD | Código de Status Típico | Idempotente? |
| --- | --- | --- | --- | --- |
| **`GET`** | `/api/produtos` | Ler todos os produtos | `200 OK` | Sim |
| **`GET`** | `/api/produtos/42` | Ler o produto de ID 42 | `200 OK` ou `404 Not Found` | Sim |
| **`POST`** | `/api/produtos` | Criar um novo produto | `201 Created` | Não |
| **`PUT`** | `/api/produtos/42` | Atualizar totalmente o produto 42 | `200 OK` | Sim |
| **`PATCH`** | `/api/produtos/42` | Atualizar parcialmente o produto 42 | `200 OK` | Não |
| **`DELETE`** | `/api/produtos/42` | Excluir o produto 42 | `204 No Content` | Sim |

Assistentes de código frequentemente sugerem verbos de ação na URL ou utilizam `POST` para qualquer operação, desrespeitando as convenções REST:

<Aside type="caution" title="Dica de IA: Use substantivos na URL e verbos HTTP semânticos">
Ao modelar rotas e chamadas de API, assistentes costumam gerar padrões RPC como `POST /api/atualizarUsuario` ou `GET /api/excluirUsuario?id=42`. Em arquiteturas RESTful, a URL nomeia o recurso no plural (`/api/usuarios/42`) e o verbo HTTP (`PATCH`, `DELETE`) define a ação executada.

**Prompt:** *"Refatore estas rotas para seguir o padrão RESTful, substituindo verbos na URL por substantivos no plural e utilizando os métodos HTTP correspondentes (`GET`, `POST`, `PATCH`, `DELETE`)."*
</Aside>

## Códigos de Status HTTP (*HTTP Status Codes*)

Os **códigos de status HTTP** são códigos numéricos de três dígitos retornados pelo servidor para indicar o resultado de uma solicitação HTTP. Eles são divididos em cinco categorias principais:

- **1xx (Informacional)**: Respostas de informação indicando que a requisição foi recebida e está em processamento.
- **2xx (Sucesso)**: Respostas de sucesso indicando que a requisição foi aceita e processada com êxito.
- **3xx (Redirecionamento)**: Respostas de redirecionamento indicando que o cliente precisa tomar ações adicionais para concluir a solicitação.
- **4xx (Erro do Cliente)**: Respostas de erro do cliente indicando sintaxe incorreta, falta de autenticação ou recurso inexistente.
- **5xx (Erro do Servidor)**: Respostas de erro do servidor indicando falha interna ao processar uma solicitação válida.

Os códigos se agrupam por família, e a família já responde de quem é o problema. A tabela reúne os que aparecem no dia a dia de uma API de aplicação, com o significado que o cliente deve atribuir a cada um:

| Código | Nome | Significado |
| --- | --- | --- |
| **`200`** | **OK** | Solicitação gerada com sucesso. |
| **`201`** | **Created** | Solicitação gerada com sucesso e novo recurso foi criado. |
| **`204`** | **No Content** | Solicitação gerada com sucesso e sem conteúdo para enviar. |
| **`400`** | **Bad Request** | Solicitação não compreendida por motivos de erro. |
| **`401`** | **Unauthorized** | Solicitação bloqueada sem credenciais de autenticação válidas. |
| **`404`** | **Not Found** | O servidor não pode encontrar o recurso solicitado. |
| **`500`** | **Internal Server Error** | O servidor encontrou uma situação com a qual não sabe lidar. |

<Aside type="note" title="Referência Oficial de Códigos">
Consulte a lista completa e detalhada de respostas HTTP em [Exemplos de Códigos de Status HTTP (MDN Web Docs)](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status).
</Aside>

## Ferramentas de Teste e Consumo de APIs

Para testar e documentar rotas REST antes ou durante a integração do front-end, utilizam-se clientes HTTP dedicados:

- **Clientes GUI**: Postman, Insomnia, Bruno, Hoppscotch.
- **Clientes de Linha de Comando (CLI)**: `curl`, `httpie`.
- **Extensões de IDE**: *REST Client* para VS Code (arquivos `.http` ou `.rest`).

Para executar requisições diretamente do editor de código sem depender de ferramentas externas, um arquivo `.http` versionado junto do projeto documenta as chamadas e permite executá-las com um único clique:

```http title="requests.http"
@baseUrl = https://jsonplaceholder.typicode.com

### Listar todos os posts
GET {{baseUrl}}/posts

### Criar um novo post
POST {{baseUrl}}/posts
Content-Type: application/json

{
  "title": "Novo artigo DevLab",
  "body": "Conteúdo sobre arquitetura REST",
  "userId": 1
}
```

## Quando usar, e quando não usar?

REST é o padrão de fato para APIs de aplicação, e a decisão relevante acontece em uma escala menor:
qual verbo e qual código de status usar em cada operação. Errar aí produz uma API que funciona e
mente sobre o que fez.

A tabela reúne as decisões que mais aparecem em revisão de código:

| Situação | Escolha | Em vez de |
| --- | --- | --- |
| Substituir um recurso por completo | `PUT` | `PATCH`, que sugere alteração parcial |
| Alterar um campo isolado | `PATCH` | `PUT`, que apaga os campos não enviados |
| Criação bem-sucedida de um recurso | `201 Created` com `Location` | `200 OK`, que não informa onde o recurso ficou |
| Requisição com corpo inválido | `422` ou `400` | `500`, que atribui ao servidor um erro do cliente |
| Busca com filtros, ordenação e paginação | `GET` com *query string* | `POST` com filtros no corpo, que perde cache e histórico |
| Operação que não é criar, ler, atualizar nem apagar | Recurso próprio para a ação | Verbo inventado ou `/api/fazerAlgo` |

As duas últimas linhas marcam o limite do estilo. Nem toda operação cabe em CRUD, e a saída em REST é
modelar a própria ação como recurso (`POST /pedidos/42/cancelamentos`), não pendurar um verbo na URL.

## Exercício

Os itens exercitam a escolha do verbo e do código de status, que é onde a maior parte dos erros de projeto aparece:

1. O que diferencia um endpoint REST bem projetado (ex: `/usuarios`) de um estilo antigo RPC (ex: `/criarUsuario` ou `/excluirUsuario`)?
2. Qual o código de status HTTP correto para indicar que uma requisição POST criou um novo registro com sucesso?
3. O que significa um método HTTP ser **idempotente**?

<details>
  <summary>Possível resposta</summary>

  1. Em REST, as URLs nomeiam apenas **recursos no plural** (`/usuarios`), e a ação é definida pelo verbo HTTP (`GET`, `POST`, `DELETE`). No estilo RPC, o verbo da ação é colocado na própria URL (`/criarUsuario`), o que viola o princípio de identificação de recursos.

  2. O código de status `201 Created`.

  3. Significa que fazer a mesma requisição uma ou múltiplas vezes produzirá exatamente o mesmo resultado no servidor. `GET`, `PUT` e `DELETE` são idempotentes; `POST` não é idempotente (pois cada chamada criará um novo registro).
</details>

## Perguntas de revisão

Teste seus conhecimentos sobre modelagem de recursos, métodos HTTP e convenções da arquitetura REST:

1. **Qual a diferença entre os métodos `PUT` e `PATCH`?**
   <details>
     <summary>Possível resposta</summary>
     O `PUT` é utilizado para substituir o recurso por completo (se um campo for omitido, ele será apagado ou resetado). O `PATCH` realiza uma atualização parcial, modificando apenas os campos explicitamente enviados na requisição.
   </details>

2. **Por que os métodos `GET`, `PUT` e `DELETE` são considerados idempotentes, enquanto o `POST` não é?**
   <details>
     <summary>Possível resposta</summary>
     Porque executar requisições `GET`, `PUT` ou `DELETE` múltiplas vezes produz o mesmo efeito no estado do servidor que executá-las uma única vez. Já o `POST` cria um novo recurso a cada invocação subsequente.
   </details>
