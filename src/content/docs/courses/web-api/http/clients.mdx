No desenvolvimento Web moderno, a comunicação entre a interface (front-end) e os servidores de banco de dados ou APIs é realizada através de **clientes HTTP** e **ferramentas de teste**. Existem diferentes ecossistemas disponíveis, variando desde soluções nativas do navegador até utilitários de linha de comando, extensões de IDE e plataformas completas com interface gráfica.

Materiais: [slides do tópico](../../../../slides/courses/web-api/http/clients/) e [mapa mental](../../../../mindmaps/courses/web-api/http/clients/).

Vale a distinção antes de começar: as ferramentas deste tópico **não são Web APIs**. Insomnia, `curl`
e `axios` são programas e bibliotecas externas ao navegador, que falam o mesmo protocolo HTTP que a
[Fetch API](../fetch/) fala. Estudá-las é entender o ecossistema em volta da chamada, não uma
interface nova do navegador.

## Objetivo

Situar a Fetch API dentro do ecossistema maior de ferramentas de comunicação HTTP, do cliente gráfico à camada de serviços do front-end. Ao final do tópico, o leitor deve ser capaz de:

- Comparar os protocolos de API mais usados (SOAP, REST, GraphQL, gRPC e WebSockets) pelo problema que cada um resolve.
- Escolher entre clientes GUI, CLI e de IDE para testar um endpoint durante o desenvolvimento.
- Comparar `fetch`, `axios` e `ky` por dependência, ergonomia e tratamento de erro.
- Localizar APIs públicas confiáveis para praticar integração.
- Isolar o acesso HTTP em uma camada de serviços (*service layer*) em vez de espalhar `fetch()` pela interface.

## Panorama dos Protocolos de API

As APIs de comunicação entre sistemas evoluíram para atender a diferentes necessidades de desempenho, tipagem e tempo real:

| Protocolo / Estilo | Formato de Dados | Estilo de Comunicação | Caso de Uso Principal |
| --- | --- | --- | --- |
| **REST** | JSON, XML | Requisicão / Resposta (HTTP) | Padrão dominante da Web para aplicações web e móveis. |
| **GraphQL** | JSON | Consulta declarativa (HTTP) | Front-ends complexos que precisam buscar dados sob medida. |
| **gRPC** | Protocol Buffers (Binário) | RPC sobre HTTP/2 | Comunicação microsserviço-a-microsserviço de alta performance. |
| **WebSockets** | Texto, Binário | Bidirecional Full-Duplex | Chat, notificações em tempo real, dashboards ao vivo. |
| **SOAP** | XML | Mensagens estruturadas (HTTP/SMTP) | Sistemas corporativos legados, bancos e setor governamental. |

<Aside type="note" title="Evolução Arquitetural">
Para aprofundar na história e comparação arquitetural de cada protocolo, confira o guia [The Evolving Landscape of API Protocols in 2023 (ByteByteGo)](https://bytebytego.com/guides/the-evolving-landscape-of-api-protocols-in-2023/).
</Aside>

## Ecossistema de Clientes HTTP

Um **Cliente HTTP** é a ferramenta ou código responsável por compor, enviar e receber respostas HTTP. Eles se dividem em quatro categorias principais:

### Interface Gráfica (GUI)

Softwares com interface visual rica para construção visual de requisições, testes de cabeçalhos e inspeção de respostas:

- **[Postman](https://www.postman.com/)**: Plataforma colaborativa completa com suporte a testes automatizados, coleções e documentação.
- **[Insomnia](https://insomnia.rest/)**: Cliente REST e GraphQL leve, responsivo e focado na experiência do desenvolvedor.
- **[Bruno](https://www.usebruno.com/)**: Cliente 100% local e nativo do Git, que armazena coleções como arquivos em texto puro (`.bru`) no próprio repositório.
- **[Hoppscotch](https://hoppscotch.io/)**: Cliente web open-source leve e acessível diretamente pelo navegador.
- **[Paw (RapidAPI Client)](https://paw.cloud/)**: Cliente macOS nativo e de nível profissional para desenvolvimento de APIs.
- **[Burp Suite](https://portswigger.net/burp)**: Plataforma profissional e proxy de interceptação HTTP/HTTPS amplamente utilizado para testes de segurança, auditoria de APIs e análise detalhada de tráfego de rede.

### Linha de Comando (CLI)

Utilitários de terminal ideais para scripts automatizados, ambientes de servidor (CI/CD) e testes rápidos de rede:

- **[curl](https://curl.se/)**: A ferramenta universal padrão em sistemas UNIX e Windows para transferência de dados via URLs.
- **[wget](https://www.gnu.org/software/wget/)**: Utilitário robusto de download de arquivos e navegação HTTP/FTP.
- **[HTTPie](https://httpie.io/)**: Cliente HTTP amigável para o terminal com sintaxe humana e saída colorida formatada.
- **[xh](https://github.com/ducaale/xh)**: Reimplementação ultra-rápida do HTTPie escrita em Rust.

### Integrados à IDE

Extensões que permitem disparar requisições HTTP diretamente de dentro do seu editor de código sem alternar de janela:

- **[VS Code REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client)**: Executa chamadas a partir de arquivos `.http` ou `.rest` versionáveis no projeto.
- **[Thunder Client](https://www.thunderclient.com/)**: Extensão leve com interface gráfica integrada diretamente no VS Code.
- **[JetBrains HTTP Client](https://www.jetbrains.com/help/idea/http-client-in-product-code-editor.html)**: Cliente nativo integrado às IDEs JetBrains (WebStorm, IntelliJ IDEA, PyCharm).
- **[REST Client para Vim / Neovim](https://github.com/rest-nvim/rest.nvim)**: Plugin para execução de requisições HTTP dentro do Neovim.

### Bibliotecas JavaScript (Código)

APIs e pacotes utilizados dentro da aplicação para fazer chamadas assíncronas ao backend:

- **[Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API)**: API nativa moderna do navegador e do Node.js baseada em Promises.
- **[Axios](https://axios-http.com/)**: Cliente HTTP baseado em Promises para Node.js e navegador com parse automático de JSON e interceptores (disponível no [Guia de Pacotes JavaScript](../../../npm/http/axios/)).

Assistentes de código frequentemente sugerem instalar pacotes externos como Axios para integrações simples que a plataforma web resolve nativamente:

<Aside type="tip" title="Dica de IA: Prefira a Fetch API nativa antes de adicionar bibliotecas">
Ao solicitar integração com APIs HTTP, assistentes costumam sugerir a instalação do `axios`. A `fetch()` nativa é padrão em todos os navegadores modernos e no Node.js (versão 18+), dispensando dependências adicionais no `package.json`.

**Prompt:** *"Reescreva esta camada de comunicação utilizando exclusivamente a Fetch API nativa, encapsulando a checagem de `response.ok`, serialização de JSON e headers padrão em uma função utilitária `request()`."*
</Aside>

## Tabela Comparativa de Bibliotecas no Código JS

A escolha entre as bibliotecas se resume a quanto do trabalho repetitivo você quer escrever à mão. A tabela compara os quatro caminhos linha a linha, e as duas linhas decisivas são a do tratamento de erro por status e a da dependência externa:

| Recurso / Característica | XMLHttpRequest (XHR) | Fetch API | Axios |
| --- | --- | --- | --- |
| **Status** | Legado | Padrão Nativo Moderno | Biblioteca Externa (npm) |
| **Sintaxe** | Baseado em Eventos/Callbacks | Baseado em Promises | Baseado em Promises |
| **Parse de JSON** | Manual (`JSON.parse`) | `await res.json()` | Automático (`res.data`) |
| **Erros 4xx/5xx** | Trata como sucesso de rede | Trata como sucesso (`!res.ok`) | Rejeita a Promise |
| **Cancelamento** | `xhr.abort()` | `AbortController` | `AbortController` / CancelToken |
| **Interceptores** | Não | Não | Sim |

## Arquitetura: A Camada de Serviços (*Service Layer*)

Independente do cliente HTTP escolhido (`fetch` ou `axios`), **nunca insira chamadas de rede diretamente dentro do código dos seus componentes visuais ou handlers de botões**.

A boa prática de arquitetura exige criar uma **Camada de Serviço** isolada que encapsule todas as URLs, cabeçalhos de autenticação e detalhes de comunicação HTTP:

```js title="src/services/api.js (Abstração com Fetch)"
const BASE_URL = 'https://api.exemplo.com/v1';

async function request(endpoint, options = {}) {
  const defaultHeaders = {
    'Content-Type': 'application/json',
    'Accept': 'application/json'
  };

  const config = {
    ...options,
    headers: { ...defaultHeaders, ...options.headers }
  };

  const response = await fetch(`${BASE_URL}${endpoint}`, config);

  if (!response.ok) {
    throw new Error(`Erro de API (${response.status}): ${response.statusText}`);
  }

  // Trata respostas sem corpo (204 No Content)
  if (response.status === 204) return null;

  return await response.json();
}

export const produtoService = {
  listar: () => request('/produtos'),
  buscarPorId: (id) => request(`/produtos/${id}`),
  criar: (dados) => request('/produtos', { method: 'POST', body: JSON.stringify(dados) }),
  excluir: (id) => request(`/produtos/${id}`, { method: 'DELETE' })
};
```

<Aside type="tip" title="Benefício da Abstração">
Se no futuro o projeto precisar trocar o `fetch` nativo pelo `axios` (ou vice-versa), você precisará alterar apenas o arquivo `src/services/api.js`. Toda a interface visual permanecerá intacta.
</Aside>

## Quando usar, e quando não usar?

Este tópico apresenta um ecossistema, e a decisão prática é sempre a mesma: usar o que já existe no
navegador, ou trazer uma ferramenta que resolve algo que ele não resolve.

A tabela indica a escolha por etapa do trabalho, da exploração da API até o código que vai para
produção:

| Situação | Escolha | Em vez de |
| --- | --- | --- |
| Explorar uma API desconhecida | Cliente GUI (Insomnia, Bruno, Postman) | Escrever `fetch()` para descobrir o formato da resposta |
| Documentar as requisições junto do código | Arquivo `.http` versionado | Coleção exportada, que fica fora do controle de versão |
| Conferir cabeçalhos e status rapidamente | `curl -i` ou HTTPie | Abrir um cliente gráfico para uma chamada só |
| Código de produção com poucas chamadas | `fetch()` nativo | Biblioteca externa, que acrescenta dependência sem ganho |
| Muitas chamadas com a mesma configuração | Camada de serviços sobre `fetch()` | `axios` só para ter uma URL base |
| Interceptadores, erro por status e progresso | `axios` ou `ky` | Reimplementar cada recurso à mão |

A quarta e a quinta linhas são as que decidem se o projeto ganha uma dependência. Antes de instalar
um cliente HTTP, verifique se o que falta é mesmo um recurso da biblioteca ou apenas a camada de
serviços que ainda não foi escrita.

## Perguntas de revisão

Teste seus conhecimentos sobre ferramentas de consumo HTTP, protocolos e organização da camada de serviços:

### Protocolos e ferramentas

As questões a seguir avaliam o uso e a distinção entre ferramentas de teste e estilos de API:

1. **O que distingue REST de GraphQL do ponto de vista do cliente?**

<details>
  <summary>Possível resposta</summary>

  Em REST, o servidor define o formato de cada recurso e o cliente combina rotas; em GraphQL, o
  cliente descreve os campos que quer em uma única requisição.
</details>

2. **Em que situação o gRPC costuma ser preferido?**

<details>
  <summary>Possível resposta</summary>

  Na comunicação entre serviços do próprio back-end, onde o formato binário e o contrato gerado
  compensam a perda de legibilidade.
</details>

3. **Qual a vantagem de um arquivo `.http` sobre uma coleção exportada de cliente gráfico?**

<details>
  <summary>Possível resposta</summary>

  Ele fica versionado junto do código, aparece no *diff* e é executado sem sair do editor.
</details>

4. **Quando um cliente de linha de comando é mais prático que um gráfico?**

<details>
  <summary>Possível resposta</summary>

  Em conferências rápidas de status e cabeçalhos, e em automação, onde a chamada precisa entrar em
  um script.
</details>

### Bibliotecas e camada de serviços

As questões a seguir avaliam bibliotecas HTTP e o encapsulamento de chamadas na arquitetura front-end:

5. **O que `axios` e `ky` fazem que a Fetch API não faz sozinha?**

<details>
  <summary>Possível resposta</summary>

  Rejeitam automaticamente em respostas 4xx e 5xx, oferecem interceptadores e, no caso do `axios`,
  expõem progresso de envio.
</details>

6. **Por que uma camada de serviços costuma bastar no lugar de uma biblioteca?**

<details>
  <summary>Possível resposta</summary>

  Porque o que normalmente falta é concentrar URL base, cabeçalhos e tratamento de erro, e isso são
  poucas linhas sobre o `fetch()` nativo.
</details>

7. **Que problema a camada de serviços resolve na organização do front-end?**

<details>
  <summary>Possível resposta</summary>

  Ela isola o acesso HTTP do código de interface, de modo que a tela passe a tratar apenas de exibir
  o resultado.
</details>

8. **Por que APIs públicas sem chave são úteis no aprendizado?**

<details>
  <summary>Possível resposta</summary>

  Porque permitem praticar integração e tratamento de erro antes de existir um back-end próprio, sem
  cadastro nem configuração de credencial.
</details>
