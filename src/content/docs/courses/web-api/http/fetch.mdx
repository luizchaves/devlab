A **Fetch API** é a interface padrão nativa do navegador (e disponível no Node.js a partir da versão 18) para realizar requisições HTTP assíncronas pela rede. Ela substituiu a antiga e verbosa API `XMLHttpRequest`, fornecendo uma abstração limpa baseada em **Promises**.

## Objetivo

Dominar o consumo de APIs HTTP no front-end com a Fetch API, do `GET` básico à renderização na interface, tratamento de erros de status, cancelamento de requisições e envio de dados complexos. Ao final do tópico, o leitor deve ser capaz de:

- Explicar a natureza assíncrona do `fetch()` e a relação dele com o *event loop*.
- Percorrer o fluxo `fetch()` -> `Response` -> leitura do corpo -> renderização na tela.
- Justificar por que status `404` ou `500` não rejeitam a Promise e exigem a checagem explícita de `response.ok`.
- Implementar as quatro operações CRUD com `method`, `headers` e `body`.
- Montar parâmetros de consulta com `URLSearchParams` em vez de concatenar strings.
- Cancelar requisições em andamento com `AbortController` e tratar o erro `AbortError`.

## Natureza Assíncrona e Event Loop

A comunicação com servidores remotos via rede é uma operação de entrada e saída (*I/O*) não bloqueante. O método `fetch()` não trava a execução da página nem paralisa a interface do usuário enquanto aguarda os dados do servidor.

Em vez disso, ele delega a tarefa de rede para o navegador e retorna uma **Promise**. Quando a resposta do servidor chega, o navegador envia o resultado para a fila de *microtasks* do Event Loop, permitindo que a aplicação trate os dados sem causar congelamento (*freezing*) na tela. Por isso, a sintaxe padrão recomendada em todo o guia é o uso de `async/await` com blocos `try/catch`.

<Aside type="note" title="Evolução Histórica: Do XMLHttpRequest (XHR) ao fetch()">
Antes da padronização do `fetch()`, as requisições assíncronas no navegador eram feitas através da API `XMLHttpRequest` (XHR), que popularizou o termo AJAX nos anos 2000. O XHR dependia de instanciação manual, múltiplos callbacks de eventos (`onreadystatechange`, `onload`, `onerror`) e checagem de estados numéricos complexos (`readyState` 1 a 4).

O `fetch()` modernizou esse cenário ao introduzir uma arquitetura nativa baseada em **Promises**, integração com `async/await` e leitura de corpos em formato de *streams*. Hoje, o XHR é considerado legado para novos projetos, sendo utilizado principalmente por bibliotecas legadas ou quando há necessidade específica de medir o progresso de envio em uploads de arquivos (`xhr.upload.onprogress`).
</Aside>

## A Função `fetch` e a Classe `Response`

A função `fetch()` aceita uma URL de destino e um objeto opcional de opções de configuração. Ela retorna uma Promise que resolve em um objeto do tipo `Response`:

```js title="Assinatura da função fetch"
fetch(url, options)
```

O diagrama abaixo ilustra o fluxo de execução do `fetch()` e o momento da verificação de status:

<Mermaid title="Fluxo de Execução do fetch e Parse do JSON">
{`
flowchart TD
  Req["fetch(url, options)"] -- "Requisição Assíncrona" --> Net["Servidor Remoto / API"]
  Net -- "Retorna Objeto Response" --> Res["const res = await fetch(...)"]
  Res --> Check{res.ok === true?}
  Check -- "Sim" --> Parse["await res.json()"]
  Check -- "Não (404, 500)" --> Err["throw new Error(res.status)"]
  Parse --> Data["Dados JS prontos para uso"]
`}
</Mermaid>

## Do Disparo até a Tela: Ciclo de Vida na Interface

Uma chamada de rede em uma interface gráfica não termina quando a resposta chega. Ela passa por quatro momentos distintos, e cada um deles pode falhar de uma forma diferente: a requisição pode não sair por queda de conexão, o servidor pode responder com status de erro, o corpo pode não ser o JSON esperado e a renderização pode receber um valor ausente.

O diagrama a seguir separa esses quatro momentos e mapeia onde cada tipo de falha se manifesta:

<Mermaid title="Os quatro momentos de uma chamada fetch em uma interface">
{`
flowchart TD
  A[Gesto do usuário] --> B["fetch(url)"]
  B -->|rede indisponível ou CORS| E1[catch]
  B --> C[Response recebida]
  C -->|"response.ok === false"| E2["Erro de aplicação (404, 422, 500)"]
  C -->|ok| D["response.json()"]
  D -->|corpo inválido| E1
  D --> F[Renderização na tela]
`}
</Mermaid>

O ramo que mais gera confusão é o intermediário: códigos como `404` ou `500` chegam como respostas válidas do ponto de vista do transporte de rede. A Promise resolve normalmente e o bloco `catch` não é acionado sozinho. Sem a checagem de `response.ok`, o código tentará processar a mensagem de erro do servidor como se fosse a lista de dados esperada.

O trecho abaixo apresenta o padrão mínimo para cobrir ambas as falhas:

```js title="Chamada robusta com tratamento de falhas de rede e de aplicação"
async function carregarItens() {
  try {
    const response = await fetch('/api/itens');
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const dados = await response.json();
    renderizarNaTela(dados);
  } catch (error) {
    exibirMensagemErro(error.message);
  }
}
```

## Operações CRUD com `fetch`

A Fetch API suporta todos os verbos e operações do ciclo CRUD (*Create, Read, Update, Delete*) através da configuração do objeto de opções. As subseções a seguir detalham a estrutura de requisição e resposta para cada um dos métodos HTTP fundamentais:

### Leitura de Dados (GET)

A requisição do tipo GET é o padrão do `fetch` caso nenhum segundo parâmetro seja fornecido:

```js title="GET - Consultando uma API"
async function buscarUsuarios() {
  try {
    const resposta = await fetch('https://jsonplaceholder.typicode.com/users');

    // VERIFICAÇÃO CRÍTICA: fetch NÃO lança exceções em status 404 ou 500!
    if (!resposta.ok) {
      throw new Error(`Erro HTTP! Status: ${resposta.status}`);
    }

    const usuarios = await resposta.json();
    console.log(usuarios);
  } catch (erro) {
    console.error('Falha na requisição de rede:', erro);
  }
}

buscarUsuarios();
```

<Aside type="caution" title="Armadilha Crítica do fetch">
Uma Promise retornada pelo `fetch()` **NÃO é rejeitada** em caso de erro HTTP como `404 Not Found` ou `500 Internal Server Error`. A Promise só é rejeitada se houver uma falha real de rede (ex: perda de conexão ou endereço inexistente). Sempre verifique a propriedade `resposta.ok`!
</Aside>

### Envio de Dados (POST)

Para enviar dados em formato JSON para uma API, três configurações no objeto de opções são obrigatórias:

1. `method: 'POST'`
2. `headers: { 'Content-Type': 'application/json' }`
3. `body: JSON.stringify(dados)`

O exemplo a seguir demonstra o cadastro de um novo recurso:

```js title="POST - Criando um recurso"
async function criarUsuario(novoUsuario) {
  const opcoes = {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify(novoUsuario)
  };

  const resposta = await fetch('https://jsonplaceholder.typicode.com/users', opcoes);

  if (!resposta.ok) {
    throw new Error(`Erro ao criar usuário: ${resposta.status}`);
  }

  const usuarioCriado = await resposta.json();
  return usuarioCriado;
}
```

### Atualização (PUT e PATCH) e Remoção (DELETE)

As operações de alteração e exclusão seguem o mesmo padrão de configuração do `POST`, ajustando o verbo semântico e o corpo da mensagem:

```js title="PUT, PATCH e DELETE"
// PUT - Atualização completa do recurso
await fetch('https://api.com/users/1', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ nome: 'Ana Silva', email: 'ana@email.com' })
});

// DELETE - Remoção do recurso
const resDelete = await fetch('https://api.com/users/1', {
  method: 'DELETE'
});

// Respostas 204 No Content não possuem corpo: não chame .json() nelas!
if (resDelete.status === 204) {
  console.log('Recurso excluído com sucesso!');
}
```

---

<Aside type="caution" title="Dica de IA: Exija a checagem de status antes de aceitar a função gerada">
A omissão mais frequente em código de `fetch()` gerado por assistentes de IA é a ausência do `if (!response.ok)`. O trecho funciona no primeiro teste manual de caminho feliz e quebra em produção com `data.map is not a function`.

**Prompt recomendado:** *"Reescreva esta função lançando erro com o código de status quando `response.ok` for falso, e implemente o tratamento com try/catch exibindo feedback visual na interface."*
</Aside>

## Montando Query Strings com `URLSearchParams`

Evite concatenar strings manualmente para passar parâmetros de filtro e paginação na URL. Utilize o utilitário nativo `URLSearchParams` para codificar caracteres especiais de forma segura:

```js title="Construção segura de query parameters"
const parametros = new URLSearchParams({
  page: 1,
  limit: 10,
  busca: 'desenvolvimento web'
});

const url = `https://api.com/produtos?${parametros.toString()}`;
// Resultado: https://api.com/produtos?page=1&limit=10&busca=desenvolvimento+web

const resposta = await fetch(url);
```

## Entendendo o CORS (Cross-Origin Resource Sharing)

O **CORS** é um mecanismo de segurança implementado pelos navegadores que restringe requisições HTTP feitas via scripts para um domínio (origem) diferente daquele que serviu a página atual.

O diagrama abaixo apresenta a validação de cabeçalhos efetuada pelo navegador:

<Mermaid title="Fluxo de Verificação do CORS pelo Navegador">
{`
flowchart TD
  App["Aplicação Web (meusite.com)"] -- "fetch('https://api.com/dados')" --> Browser["Navegador"]
  Browser -- "Requisição HTTP (com Origin: meusite.com)" --> API["Servidor API (api.com)"]
  API -- "Resposta com Access-Control-Allow-Origin" --> Browser
  Browser -- "Valida se meusite.com foi permitido" --> Decision{Permitido?}
  Decision -- "Sim" --> Deliver["Entrega dados ao JS"]
  Decision -- "Não" --> Block["Bloqueia no JS (CORS Error)"]
`}
</Mermaid>

Se a API remota não retornar o cabeçalho `Access-Control-Allow-Origin` autorizando a origem do seu site, o navegador **bloqueará o acesso à resposta** por motivos de segurança.

## Cancelando Requisições com `AbortController`

Em buscas dinâmicas com digitação ou ao trocar rapidamente de página, requisições antigas que ainda estão em trânsito devem ser canceladas para evitar concorrência desordenada (*race conditions*) ou desperdício de banda. Isso é controlado com a API `AbortController`:

```js title="Cancelando requisições com AbortController"
const controller = new AbortController();
const signal = controller.signal;

async function buscarDadosComTimeout() {
  try {
    // Cancela automaticamente após 5 segundos
    const timer = setTimeout(() => controller.abort(), 5000);

    const resposta = await fetch('https://api.com/dados-demorados', { signal });
    clearTimeout(timer);

    const dados = await resposta.json();
    return dados;
  } catch (erro) {
    if (erro.name === 'AbortError') {
      console.warn('A requisição foi cancelada por ter excedido o tempo limite!');
    } else {
      console.error('Outro erro de rede:', erro);
    }
  }
}
```

## Quando usar, e quando não usar?

A Fetch API é nativa, não adiciona dependências ao projeto e atende à grande maioria das necessidades de comunicação cliente-servidor. A decisão prática consiste em identificar quando a aplicação demanda recursos arquiteturais mais avançados.

A tabela compara os principais cenários de uso e decisões no front-end:

| Situação | Escolha | Por quê |
| --- | --- | --- |
| Requisições comuns em qualquer projeto | `fetch()` nativo | Sem dependência, disponível no navegador e no Node.js |
| Muitas chamadas com a mesma base e cabeçalhos | Camada de serviços sobre `fetch()` | Concentra configuração e tratamento de erro sem dependências |
| Interceptadores globais de requisição e resposta | `axios` ou `ky` | Tratamento automático de 4xx/5xx e transformação de dados |
| Barra de progresso de upload | `XMLHttpRequest` ou `axios` | `fetch()` não expõe evento de progresso no upload de arquivos |
| Cache, revalidação e estado em componentes | TanStack Query ou SWR | Gerenciamento de cache e sincronização reativa de tela |

## Exercício

Os itens exercitam as quatro operações CRUD e o tratamento de erro que a API não faz sozinha:

1. Por que uma requisição `fetch()` que retorna o código de status HTTP `404 Not Found` **não** cai no bloco `catch` de um `try/catch`?
2. Quais são as três configurações fundamentais necessárias para enviar dados em formato JSON utilizando o método `POST` no `fetch`?
3. O que é e para que serve o `AbortController`?

<details>
  <summary>Possível resposta</summary>

  1. Porque a Fetch API considera como "rejeição" apenas falhas físicas de rede (sem conexão, falha de DNS ou erro de CORS). Respostas HTTP válidas retornadas pelo servidor (mesmo com erros 4xx ou 5xx) resolvem a Promise normalmente.

  2. As três configurações são:
     - `method: 'POST'`
     - `headers: { 'Content-Type': 'application/json' }`
     - `body: JSON.stringify(dados)`

  3. O `AbortController` é uma API nativa que permite abortar ou cancelar requisições HTTP em andamento, sendo usada para timeouts ou para cancelar buscas anteriores quando o usuário digita um novo termo.
</details>

## Desafio

Escreva uma função `buscarComRetry(url, tentativas)` que tente realizar um `fetch(url)` até o número máximo de tentativas especificado. Se a resposta não for `.ok`, a função deve aguardar 1 segundo e tentar novamente antes de lançar o erro final.

<details>
  <summary>Possível resposta</summary>

  ```js title="Nova tentativa com espera crescente"
  async function buscarComRetry(url, tentativas = 3) {
    for (let i = 1; i <= tentativas; i++) {
      try {
        console.log(`Tentativa ${i} de ${tentativas}...`);
        const res = await fetch(url);
        if (res.ok) {
          return await res.json();
        }
      } catch (erro) {
        if (i === tentativas) throw erro;
      }
      // Aguarda 1 segundo antes da próxima tentativa
      await new Promise(resolve => setTimeout(resolve, 1000));
    }
    throw new Error(`Falha após ${tentativas} tentativas.`);
  }
  ```
</details>

## Perguntas de revisão

Teste seus conhecimentos sobre o funcionamento assíncrono, a classe `Response` e o tratamento de requisições com a Fetch API:

### Resposta e Erros HTTP

As questões a seguir avaliam a interpretação de códigos de status e respostas do servidor:

1. **Qual propriedade da interface `Response` retorna `true` apenas se o código de status HTTP estiver na faixa de `200` a `299`?**
   <details>
     <summary>Possível resposta</summary>
     A propriedade `response.ok`.
   </details>

2. **O que acontece ao chamar o método `response.json()` em uma resposta com código HTTP `204 No Content`?**
   <details>
     <summary>Possível resposta</summary>
     Como uma resposta `204` não possui corpo textual, tentar fazer o parse com `.json()` resultará em um erro de sintaxe (*SyntaxError: Unexpected end of JSON input*).
   </details>

3. **Por que `response.json()` retorna uma Promise em vez de devolver o objeto JavaScript imediatamente?**
   <details>
     <summary>Possível resposta</summary>
     Porque o corpo da resposta chega em fluxo (*stream*) pela rede e pode ainda não ter sido totalmente transferido quando os cabeçalhos HTTP já estão disponíveis.
   </details>

### Cancelamento e Interface

As questões a seguir avaliam o controle de fluxo, cancelamento de requisições e estados de tela:

1. **Como cancelar uma requisição `fetch()` em andamento caso a ação do usuário seja interrompida?**
   <details>
     <summary>Possível resposta</summary>
     Utilizando uma instância de `AbortController`, vinculando seu sinal através da opção `{ signal: controller.signal }` na chamada do `fetch()` e executando `controller.abort()` quando a requisição precisar ser cancelada.
   </details>

2. **Quais são os três estados visuais fundamentais que uma interface deve representar durante uma chamada assíncrona?**
   <details>
     <summary>Possível resposta</summary>
     Os estados de carregamento (*loading*), sucesso (com os dados renderizados) e erro (com mensagem descritiva para o usuário), evitando que a tela permaneça estática ou silenciosa durante falhas.
   </details>
