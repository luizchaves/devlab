Aplicações web diferentes repetem as mesmas tarefas: reagir a um clique, buscar dados de um servidor,
montar uma lista, validar um formulário, lembrar de uma preferência. Este tópico percorre essas
tarefas na ordem em que aparecem em um projeto e diz, para cada uma, qual Web API resolve e onde ela
é estudada em profundidade no guia.

## Objetivo

Formar um mapa de entrada para o guia, ligando o que uma aplicação front-end precisa fazer às
interfaces que o navegador oferece para isso. Ao final do tópico, o leitor deve ser capaz de:

- Nomear a Web API responsável por cada funcionalidade recorrente de uma aplicação vanilla.
- Reconhecer o trecho mínimo de código de cada uma dessas tarefas.
- Identificar quais dessas funcionalidades o HTML e o CSS já resolvem sem JavaScript.
- Localizar, no guia, a página que aprofunda cada API citada aqui.
- Ler uma aplicação pequena e apontar qual API sustenta cada parte dela.

## O mapa por funcionalidade

Ao projetar ou construir uma aplicação front-end, o desenvolvedor pensa em termos de **necessidades de negócio e funcionalidades para o usuário**: *"preciso persistir o tema escolhido"*, *"preciso buscar dados sem recarregar a tela"*, *"preciso validar o e-mail antes do envio"*, *"preciso alertar o usuário mesmo com a aba em segundo plano"*.

O navegador, por outro lado, expõe essas capacidades por meio de **Web APIs nativas** (`localStorage`, `fetch()`, Constraint Validation, `Notification`). Conhecer o catálogo da plataforma permite resolver problemas reais aproveitando a infraestrutura embutida no ambiente, sem instalar dependências desnecessárias, reduzindo o tamanho final do pacote de scripts e usufruindo da otimização nativa de motores compilados em C++ e Rust.

As tabelas a seguir formam o **índice orientado a problemas** deste tópico e do guia completo. Para cada tarefa prática, você encontra a interface responsável, o mecanismo utilizado e o link para a página que aprofunda o assunto.

Elas estão organizadas em seis famílias de recursos, seguindo a ordem de complexidade em que uma aplicação web costuma demandá-las: da manipulação estrutural básica até a comunicação assíncrona, segurança e sensores do dispositivo.

<Aside type="note" title="Origem das Web APIs: Especificações vs Documentação">
Embora a **MDN Web Docs** (mantida pela comunidade e pela Mozilla) seja a fonte de documentação mais consultada por desenvolvedores, ela é uma camada de documentação explicativa, e não o órgão que cria as normas. As Web APIs nascem de especificações técnicas padronizadas por consórcios e grupos abertos:

- **W3C (World Wide Web Consortium)**: Define padrões essenciais de acessibilidade (ARIA), arquitetura web, segurança e integração com dispositivos.
- **WHATWG (Web Hypertext Application Technology Working Group)**: Mantém os padrões vivos (*Living Standards*) do HTML, da manipulação da árvore DOM e da Fetch API.
- **TC39 / Ecma International**: Padroniza as regras da linguagem JavaScript (ECMAScript) e seus tipos nativos.
- **IETF (Internet Engineering Task Force)**: Normatiza protocolos de rede subjacentes como HTTP, HTTPS e WebSockets.

Os motores dos navegadores (V8 no Chromium/Node.js, SpiderMonkey no Firefox, WebKit no Safari) implementam essas especificações diretamente em código de baixo nível (C++ e Rust), expondo os objetos globais e métodos de forma padronizada ao JavaScript.
</Aside>

### Estrutura, interação e formulários

É o grupo que sustenta todos os outros. Sem selecionar elementos e reagir a eventos, nada do que vem
depois chega à tela:

| Funcionalidade | Web API responsável | Onde estudar |
| --- | --- | --- |
| Encontrar e alterar o conteúdo de elementos | `querySelector`, `textContent`, `innerHTML` | [Manipulação do DOM](../dom/manipulation/) |
| Alterar estilos e classes visuais | `classList`, `style`, `setProperty` | [Manipulação do DOM](../dom/manipulation/) |
| Reagir a clique, tecla e envio de formulário | `addEventListener` e o objeto `Event` | [Eventos e Interatividade](../dom/events/) |
| Atender itens que ainda não existem | Delegação de eventos com `closest()` | [Eventos e Interatividade](../dom/events/) |
| Montar listas e cartões a partir dos dados | `createElement`, `DocumentFragment`, `<template>` | [Elementos Dinâmicos](../dom/dynamic-elements/) |
| Validar um formulário antes de enviar | Constraint Validation e `FormData` | [Formulários e Validação](../dom/forms/) |
| Rolar até uma seção e medir a posição | `scrollIntoView()`, `scrollY`, `scroll-behavior` | [Rolagem e Posicionamento](../dom/scroll/) |
| Executar o script no momento certo | `defer`, `type="module"`, `DOMContentLoaded` | [Ciclo de Vida da Página](../browser/lifecycle/) |
| Consultar o ambiente e depurar | `window`, `location`, `navigator`, `console` | [Objetos do Navegador](../browser/objects/) |

As três primeiras linhas respondem por grande parte do código de uma aplicação vanilla: selecionar elementos, manipular texto/classes e escutar eventos. A última é a menos lembrada e a mais útil na depuração: `console.table()` e `console.time()` resolvem em uma linha o que costuma virar meia dúzia de `console.log()`.

<Aside type="tip" title="O que é uma Aplicação Vanilla?">
O termo **Vanilla** (como em *Vanilla JavaScript* ou *Vanilla Web*) refere-se ao desenvolvimento web construído exclusivamente com as tecnologias e interfaces nativas da plataforma (**HTML, CSS e JavaScript puro**), sem depender de frameworks ou bibliotecas externas de abstração (como React, Vue, Angular ou jQuery).

Dominar o desenvolvimento *vanilla* é essencial: frameworks e ferramentas do mercado evoluem constantemente, mas todos eles utilizam sob o capô exatamente as mesmas Web APIs nativas explicadas ao longo deste guia.
</Aside>

### Dados e comunicação

Assim que a página deixa de ter os dados dentro do HTML, este grupo entra. É também onde aparecem os
erros que só se manifestam em produção:

| Funcionalidade | Web API responsável | Onde estudar |
| --- | --- | --- |
| Buscar dados de um servidor | Fetch API e a classe `Response` | [Fetch API](../http/fetch/) |
| Consumir uma API de recursos | Arquitetura REST, verbos e códigos de status | [REST API](../http/rest/) |
| Pedir só os campos necessários | GraphQL sobre `fetch()` | [GraphQL](../http/graphql/) |
| Testar endpoints e organizar as chamadas | Clientes HTTP e camada de serviços | [Clientes HTTP](../http/clients/) |
| Entender por que o navegador bloqueou a resposta | *Same-Origin Policy* e CORS | [CORS e Segurança](../http/cors/) |
| Receber atualizações em tempo real | WebSocket (`wss://`) | [WebSockets API](../http/websockets/) |
| Receber fluxo de eventos contínuos do servidor | Server-Sent Events (`EventSource`) | [Server-Sent Events (SSE)](../http/sse/) |

Este grupo é o único em que nem tudo é interface do navegador. Apenas a Fetch API, o Server-Sent Events (`EventSource`) e o WebSocket são
objetos que o JavaScript chama; REST e GraphQL são convenções que o servidor segue, os clientes HTTP
são ferramentas externas e o CORS é uma política. A
[visão geral do guia](../#os-três-sentidos-da-palavra-api) explica essa distinção com um
diagrama de uma requisição inteira.

A quinta linha, aliás, não é uma funcionalidade que se implementa, é um obstáculo que se atravessa: o
bloqueio de CORS aparece na primeira integração com uma API de outro domínio, e a correção está
sempre no servidor.

### Estado, navegação e renderização

Este grupo responde por tudo que precisa sobreviver a um clique, a um recarregamento ou a uma troca
de tela:

| Funcionalidade | Web API responsável | Onde estudar |
| --- | --- | --- |
| Guardar preferências e rascunhos | Web Storage (`localStorage`, `sessionStorage`) | [Local Storage](../storage/local-storage/) |
| Manter uma sessão autenticada | Cookies com `HttpOnly`, `Secure` e `SameSite` | [Cookies e Sessão](../storage/cookies/) |

| Fazer o mesmo código rodar no servidor | Guardas de escopo e hidratação | [Server-Side Rendering](../browser/ssr/) |

A última linha é a que costuma pegar de surpresa quem sai do JavaScript puro para um framework: todo
acesso a `window`, `document` ou `localStorage` escrito nas linhas acima quebra quando o mesmo

### Mídia, voz e dispositivo

O grupo menos usado, e o que mais depende de permissão e de suporte do aparelho. Um projeto pode
passar inteiro sem tocar em nenhuma destas:

| Funcionalidade | Web API responsável | Onde estudar |
| --- | --- | --- |
| Desenhar formas, gráficos e animação em pixels | Canvas API e contexto 2D | [Canvas API](../media/canvas/) |
| Ler um texto em voz alta | Web Speech (`speechSynthesis`) | [Web Speech API](../media/web-speech/) |

Três das quatro exigem gesto do usuário ou permissão explícita, e a Geolocation guarda a decisão dele

### Observação e desempenho

O último grupo entra quando a aplicação cresce e a interface começa a engasgar:

| Funcionalidade | Web API responsável | Onde estudar |
| --- | --- | --- |
| Carregar conteúdo ao chegar perto dele | `IntersectionObserver` | [Observadores](../browser/observers/) |
| Reagir ao tamanho de um elemento | `ResizeObserver` | [Observadores](../browser/observers/) |
| Detectar alterações feitas na árvore DOM | `MutationObserver` | [Observadores](../browser/observers/) |
| Saber se a aba está visível | `visibilitychange` e `document.hidden` | [Ciclo de Vida da Página](../browser/lifecycle/) |

| Acelerar um algoritmo numérico intensivo | WebAssembly | [WebAssembly](../browser/webassembly/) |

As duas últimas linhas estão em ordem de tentativa, e não de preferência: o worker resolve o problema
de a tela travar, e o WebAssembly resolve o de a conta ser lenta. São problemas diferentes, e o
primeiro é muito mais comum.

## Funcionalidades Recorrentes em Código

A seguir, analisamos a implementação prática das tarefas mais recorrentes em aplicações front-end vanilla, com trechos mínimos de código, alternativas nativas e um exemplo integrador que reúne esses padrões.

### Reagir ao que o usuário faz

Toda interatividade começa no mesmo ponto: um ouvinte registrado em um elemento, que executa uma
função quando algo acontece. É a API mais usada de todas, e a primeira a ser aprendida.

O trecho abaixo é a forma mínima, com o objeto `Event` chegando ao tratador:

```js title="Ouvinte mínimo de clique"
document.querySelector('#salvar').addEventListener('click', (event) => {
  event.preventDefault();
  console.log('clicou em', event.currentTarget.id); // 'salvar'
});
```

O detalhe que muda a escala do código é a **delegação**. Em vez de um ouvinte por elemento, registra-se
um único ouvinte no contêiner, que atende inclusive os itens criados depois:

```js title="Delegação em uma lista que ainda vai crescer"
document.querySelector('#lista').addEventListener('click', (event) => {
  const botao = event.target.closest('button[data-id]');
  if (!botao) return;

  remover(Number(botao.dataset.id));
});
```

A linha 2 é o que faz o padrão funcionar: `closest()` sobe a partir do elemento clicado até encontrar
o botão, mesmo que o clique tenha caído em um ícone dentro dele. O tópico
[Eventos e Interatividade](../dom/events/) aprofunda as fases de propagação e as opções do ouvinte.

### Carregar conteúdo dinâmico

Poucas aplicações nascem com os dados dentro do HTML. O normal é a página subir vazia e buscar o
conteúdo em seguida, o que introduz três estados que a interface precisa representar: carregando,
carregado e falhou.

O trecho abaixo cobre os três, e a linha 4 é a que mais falta em código de exemplo encontrado por aí:

```js title="Carga de dados com os três estados na tela"
async function carregar() {
  status.textContent = 'Carregando…';
  try {
    const resposta = await fetch('/api/investimentos');
    if (!resposta.ok) throw new Error(`HTTP ${resposta.status}`);

    render(await resposta.json());
    status.textContent = '';
  } catch (erro) {
    status.textContent = `Não foi possível carregar: ${erro.message}`;
  }
}
```

Sem o `if (!resposta.ok)`, um erro 500 do servidor é tratado como sucesso, porque o `fetch()` só
rejeita quando a requisição nem chega a completar. O tópico [Fetch API](../http/fetch/) detalha esse
comportamento, os verbos HTTP e o cancelamento com `AbortController`.

### Montar e atualizar a tela

Com os dados em mãos, a próxima tarefa é transformá-los em elementos. Inserir um por um dentro de um
laço funciona e é lento: cada inserção no documento pode provocar um novo cálculo de layout.

A saída é montar o lote fora da árvore e inseri-lo de uma vez:

```js title="Lista construída em um DocumentFragment"
const fragmento = document.createDocumentFragment();

for (const item of investimentos) {
  const li = document.createElement('li');
  li.textContent = `${item.name} · ${item.amount}`;
  fragmento.append(li);
}

lista.replaceChildren(fragmento);
```

O `textContent` da linha 5 não é preferência de estilo. Como o nome vem de fora da página, usar
`innerHTML` ali executaria qualquer marcação vinda junto do dado. O tópico
[Elementos Dinâmicos](../dom/dynamic-elements/) trata do `<template>` e do custo de cada técnica.

### Alterar estilos e classes (CSS via JavaScript)

Atualizar o aspecto visual de elementos em resposta a ações do usuário é indispensável em qualquer interface. O navegador disponibiliza duas formas principais de controlar o CSS a partir do JavaScript:

1. **Manipulação de classes via `classList` (Abordagem recomendada)**: O JavaScript não deve conter valores de cores, sombras ou espaçamentos embutidos em strings. Em vez disso, o design mora no CSS em classes semânticas (`.ativo`, `.oculto`, `.erro`, `.tema-escuro`), e o script apenas alterna essas classes no elemento:

```js title="Controle de estados visuais com classList"
const cartao = document.querySelector('.card');

// Adiciona ou remove uma ou mais classes
cartao.classList.add('destaque');
cartao.classList.remove('oculto');

// Alterna a classe (adiciona se ausente, remove se presente)
// O segundo argumento opcional força o estado com base em um booleano
cartao.classList.toggle('selecionado', item.estaAtivo);

// Consulta se uma classe está aplicada
if (cartao.classList.contains('destaque')) {
  console.log('Elemento em evidência');
}
```

2. **Estilos inline e Variáveis CSS via `element.style`**: Usado quando o valor visual é estritamente dinâmico e calculado em tempo de execução pela lógica do script (como porcentagem de uma barra de progresso, coordenadas em drag-and-drop ou temas customizados via CSS Custom Properties):

```js title="Estilo inline dinâmico e variáveis CSS"
const barraProgresso = document.querySelector('#progresso');

// Estilo inline direto para grandezas contínuas calculadas
barraProgresso.style.width = `${porcentagem}%`;

// Variáveis CSS globais (Custom Properties) para temas dinâmicos
document.documentElement.style.setProperty('--cor-destaque', '#007acc');
```

<Aside type="tip" title="Separando responsabilidades entre CSS e JS">
A regra de ouro é: se o estado visual já pode ser previsto e desenhado com antecedência, crie uma classe no arquivo `.css` e use `classList`. Deixe a propriedade `element.style` exclusivamente para valores numéricos contínuos ou calculados em tempo real. O tópico [Manipulação do DOM](../dom/manipulation/) aprofunda o `classList`, a leitura com `getComputedStyle()` e o custo de reflows no navegador.
</Aside>

### Validar um formulário

Validação é a funcionalidade em que mais se escreve código desnecessário. O HTML já declara as regras
(`required`, `minlength`, `min`, `type="email"`, `pattern`), e o navegador já traduz as mensagens para
o idioma do usuário.

O papel do JavaScript é perguntar se está válido e decidir onde mostrar a mensagem:

```js title="Validação apoiada nas regras do HTML"
form.addEventListener('submit', (event) => {
  event.preventDefault();

  if (!form.checkValidity()) {
    const invalido = form.querySelector(':invalid');
    erro.textContent = invalido.validationMessage;
    invalido.focus();
    return;
  }

  const dados = new FormData(form);
  enviar(Object.fromEntries(dados));
});
```

Duas interfaces aparecem aqui. A **Constraint Validation API** entrega `checkValidity()`,
`validationMessage` e o seletor `:invalid`, que também serve para estilizar o campo no CSS. E o
`FormData` lê todos os campos pelo atributo `name`, sem um `querySelector` por campo.

Regras que o HTML não expressa, como "as duas senhas precisam coincidir", entram por
`setCustomValidity()` sem abandonar o mecanismo nativo. O tópico
[Formulários e Validação](../dom/forms/) trata dessas regras, do objeto `validity` e da diferença
entre `:invalid` e `:user-invalid`.

### Reagir à rolagem e ao tamanho

Rolagem é a área em que a solução antiga e a moderna mais divergem. O ouvinte de `scroll` dispara
dezenas de vezes por segundo e obriga o código a calcular posições a cada disparo; o
`IntersectionObserver` avisa apenas quando um elemento entra ou sai da área visível.

O trecho abaixo carrega conteúdo quando o fim da lista se aproxima, que é o padrão de rolagem
infinita:

```js title="Carregamento ao aproximar do fim da lista"
const observador = new IntersectionObserver((entradas) => {
  for (const entrada of entradas) {
    if (entrada.isIntersecting) carregarProximaPagina();
  }
}, { rootMargin: '200px' });

observador.observe(document.querySelector('#fim-da-lista'));
```

O `rootMargin` da linha 4 antecipa o disparo em 200 pixels, para que o conteúdo chegue antes de o
usuário alcançar o fim. Já o movimento em si, rolar até uma seção, não precisa de biblioteca nem de
animação escrita à mão:

```js title="Rolagem suave até um elemento"
document.querySelector('#secao-precos').scrollIntoView({ behavior: 'smooth', block: 'start' });
```

O mesmo efeito é obtido só com CSS, aplicando `scroll-behavior: smooth` no elemento raiz, e assim
vale também para os links de âncora comuns. O tópico
[Rolagem e Posicionamento](../dom/scroll/) reúne as medidas do documento, os pontos de parada com
`scroll-snap` e o índice que destaca a seção em leitura, e o de
[Observadores](../browser/observers/) trata dos três observadores em profundidade.

### Lembrar do usuário entre visitas

Uma aplicação que esquece tudo a cada recarregamento parece quebrada. O navegador oferece três
lugares para guardar estado, e a escolha entre eles não é de tamanho, é de **quem precisa ler o
dado**.

A tabela resume a decisão, que aparece em quase todo projeto:

| Dado | Onde guardar | Por quê |
| --- | --- | --- |
| Tema, idioma, ordenação da lista | `localStorage` | Só o navegador precisa, e deve sobreviver ao fechamento |
| Rascunho válido até fechar a aba | `sessionStorage` | Expira sozinho, sem código de limpeza |
| Sessão autenticada | Cookie `HttpOnly` | O servidor precisa a cada requisição, e o script não deve ler |
| Dados que o usuário verá em outro aparelho | Servidor | Nada guardado no navegador atravessa dispositivos |

A leitura precisa tratar dois casos que sempre acontecem, a primeira visita e o dado corrompido:

```js title="Leitura tolerante do armazenamento"
function ler(chave, padrao = []) {
  try {
    return JSON.parse(localStorage.getItem(chave)) ?? padrao;
  } catch {
    return padrao;
  }
}
```

Os tópicos [Local Storage](../storage/local-storage/) e [Cookies e Sessão](../storage/cookies/)
aprofundam cada mecanismo e os atributos de segurança do cookie.

### Trocar de tela sem recarregar

Assim que a aplicação tem mais de uma tela, surge a pergunta de como trocar entre elas mantendo a URL
compartilhável. A History API altera a barra de endereços sem disparar requisição, e o evento
`popstate` avisa quando o usuário aperta o botão voltar.

```js title="Troca de rota e retorno pelo botão voltar"
function irPara(caminho) {
  history.pushState({ caminho }, '', caminho);
  renderizar(caminho);
}

window.addEventListener('popstate', (event) => {
  renderizar(event.state?.caminho ?? location.pathname);
});
```

Há uma condição que não está no código: o servidor precisa devolver o mesmo HTML para qualquer
caminho, senão a URL funciona ao ser navegada e retorna 404 ao ser colada na barra de endereços. O
tópico [History API](../browser/history/) detalha esse ponto.

### O que o HTML e o CSS já resolvem?

Boa parte do que se escreve em JavaScript hoje é reimplementação de algo que a plataforma passou a
oferecer. Antes de codificar qualquer uma das funcionalidades abaixo, vale conferir se a versão
nativa atende.

A tabela lista os casos em que a solução nativa venceu, com o que se ganha ao adotá-la:

| Funcionalidade | Solução nativa | O que se ganha |
| --- | --- | --- |
| Acordeão e seções recolhíveis | `<details>` e `<summary>` | Teclado, busca da página e zero JavaScript |
| Janela modal | `<dialog>` com `showModal()` | Foco preso, `Esc`, `::backdrop` e camada superior |
| Balão de dica ou menu suspenso | Atributo `popover` | Fechamento ao clicar fora, sem `z-index` |
| Rolagem suave | `scroll-behavior: smooth` | Funciona também nos links de âncora |
| Imagem fora da área visível | `loading="lazy"` | Nenhum observador a escrever |
| Validação de campo obrigatório | `required` e `:invalid` | Mensagem traduzida pelo navegador |
| Máscara simples de formato | `pattern` e `inputmode` | Teclado adequado no celular |
| Carrossel com pontos de parada | `scroll-snap-type` no CSS | Rolagem nativa, com toque e teclado |

A linha do `<details>` é a mais direta de aplicar em um projeto existente. A do `popover` é a mais
recente, e vale conferir o suporte nos navegadores que o projeto atende antes de adotá-la.

<Aside type="tip" title="A pergunta que vem antes de escrever JavaScript">
Diante de qualquer funcionalidade desta página, pergunte primeiro se ela existe em HTML ou CSS. O
código que não é escrito não tem defeito, não precisa de teste e continua funcionando quando o
JavaScript falha ao carregar.
</Aside>

## Exercício

Os itens abaixo acrescentam ao exemplo funcionalidades que aparecem na tabela do início do tópico:

1. Mostre o total investido, somando os valores e formatando com `toLocaleString`.
2. Acrescente um campo de busca que filtre a lista enquanto o usuário digita.
3. Impeça o cadastro de um nome já existente usando `setCustomValidity()`.
4. Adicione um botão que copie o resumo da carteira com a Clipboard API.
5. Faça a lista rolar até o item recém-adicionado com `scrollIntoView()`.

O item 3 é o que mais exige atenção, porque a regra não existe em HTML e precisa conviver com as que
existem:

<details>
  <summary>Possível resposta</summary>

  A verificação roda a cada digitação e alimenta a validação nativa em vez de substituí-la:

  ```js title="Nome duplicado como regra de validação"
  campoNome.addEventListener('input', () => {
    const duplicado = investments.some((item) => item.name === campoNome.value.trim());
    campoNome.setCustomValidity(duplicado ? 'Já existe um investimento com esse nome.' : '');
  });
  ```

  Com a mensagem definida, `form.checkValidity()` passa a devolver `false`, o seletor `:invalid`
  passa a casar com o campo e o restante do código de envio continua igual.
</details>

## Perguntas de revisão

Teste seus conhecimentos sobre o panorama geral de APIs do navegador e decisões de arquitetura front-end:

### Escolha da API

As questões a seguir avaliam a identificação da Web API nativa adequada para cada funcionalidade:

1. **Qual API sustenta praticamente todas as outras funcionalidades desta página?**

<details>
  <summary>Possível resposta</summary>

  O DOM, junto do registro de eventos. Buscar dados, validar formulário e guardar estado só viram
  interface depois de passar por seleção e alteração de elementos.
</details>

2. **Por que `IntersectionObserver` substituiu o ouvinte de `scroll` em rolagem infinita?**

<details>
  <summary>Possível resposta</summary>

  Porque ele notifica apenas quando o elemento entra ou sai da área visível, em vez de executar código
  a cada quadro de rolagem e calcular posições à mão.
</details>

3. **Onde deve ficar um token de sessão, e por quê?**

<details>
  <summary>Possível resposta</summary>

  Em um cookie `HttpOnly`, que o JavaScript não consegue ler. Em `localStorage`, qualquer script
  injetado na página teria acesso a ele.
</details>

4. **O que a History API exige do servidor para funcionar?**

<details>
  <summary>Possível resposta</summary>

  Que ele devolva o mesmo HTML para qualquer caminho, senão as URLs criadas com `pushState()` retornam
  404 ao serem acessadas diretamente.
</details>

### Plataforma antes do código

As questões a seguir avaliam o aproveitamento de recursos nativos da plataforma web antes de criar código JavaScript:

5. **O que a Constraint Validation API entrega que uma cadeia de `if` não entrega?**

<details>
  <summary>Possível resposta</summary>

  Mensagens já traduzidas para o idioma do usuário, o seletor `:invalid` para estilização e validação
  que continua existindo mesmo sem JavaScript.
</details>

6. **Para que serve o `FormData` no envio de um formulário?**

<details>
  <summary>Possível resposta</summary>

  Para ler todos os campos de uma vez pelo atributo `name`, dispensando um `querySelector` por campo.
</details>

7. **Cite três funcionalidades desta página que o HTML ou o CSS resolvem sem JavaScript.**

<details>
  <summary>Possível resposta</summary>

  Seções recolhíveis com `<details>`, rolagem suave com `scroll-behavior`, carregamento tardio de
  imagem com `loading="lazy"`. Modal com `<dialog>` e validação com `required` também contam.
</details>

8. **Por que o exemplo usa `textContent` e não `innerHTML` ao montar a lista?**

<details>
  <summary>Possível resposta</summary>

  Porque o nome vem de fora da página. Com `innerHTML`, qualquer marcação presente no dado seria
  interpretada, o que abre caminho para injeção de script.
</details>
