O **Guia de Web APIs** estuda as interfaces nativas que o navegador disponibiliza para que o JavaScript interaja com a página, a rede, o armazenamento e os recursos do sistema operacional.

O [Guia de ECMAScript](../ecmascript/) ensina a sintaxe e a lógica da linguagem. Este guia explica o **ambiente de execução do navegador**. Uma aplicação web moderna nasce do encontro entre os dois: ECMAScript fornece a sintaxe, objetos e Promises; as Web APIs fornecem `window`, `document`, `fetch`, `localStorage`, `WebSocket`, eventos e sensores do dispositivo.

<Aside type="tip" title="Modelo Mental">
A linguagem JavaScript define *como* escrever a lógica; o navegador define *quais recursos do sistema* essa lógica pode acessar.
</Aside>

## Duas coisas diferentes chamadas de API

O nome deste guia é ambíguo de propósito, porque o mercado usa o mesmo termo para duas coisas que não
se parecem. Desfazer essa ambiguidade cedo evita a confusão mais comum de quem estuda o assunto.

A primeira acepção é a da MDN: **Web API é uma interface que o navegador expõe ao JavaScript**.
`fetch()`, `localStorage`, `document`, `WebSocket`, `EventSource` e `navigator.geolocation` existem porque o
navegador os implementou, e você os chama diretamente do código da página.

A segunda é a do dia a dia de back-end: **API web é um serviço acessível por HTTP**. REST e GraphQL
descrevem como esse serviço organiza rotas e respostas; eles não são objetos que o JavaScript chama.

A tabela separa o que este guia cobre em cada acepção:

| Assunto | O que é, tecnicamente | Você chama no código? |
| --- | --- | --- |
| `fetch()`, `WebSocket`, `EventSource` | Interface implementada pelo navegador | Sim, é um objeto ou função |
| `document`, `localStorage`, `navigator` | Interface implementada pelo navegador | Sim |
| [REST](http/rest/) | Estilo arquitetural de um serviço HTTP | Não; é a convenção que o servidor segue |
| [GraphQL](http/graphql/) | Linguagem de consulta e execução no servidor | Não; você a envia como texto por `fetch()` |
| [CORS](http/cors/) | Política de segurança configurada no servidor | Não; é uma regra de autorização via cabeçalhos |
| [Clientes HTTP](http/clients/) | Ferramentas e bibliotecas | Não são do navegador; `axios` e Insomnia são externos |
| [SSR](browser/ssr/) | Estratégia de renderização no servidor | Não; é o servidor gerando o HTML antes do envio |

A coluna da direita é o critério prático. Se existe um identificador que você digita e o navegador
entende sozinho, é uma Web API do navegador. Se é uma convenção, uma política ou uma ferramenta, não
é: é algo que **acompanha** a chamada, sem ser chamado.

O diagrama mostra onde cada um entra em uma única requisição:

<Mermaid title="Uma requisição e o papel de cada conceito: API do navegador, política, arquitetura e ferramenta">
{`
flowchart TD
  A["Seu código<br/>fetch(url, options)"] -->|"Web API do navegador"| B[Navegador]
  B -->|"CORS: política aplicada aqui"| C[Requisição HTTP]
  C -->|"REST ou GraphQL:<br/>como a rota e o corpo são organizados"| D[Servidor]
  D --> E[Resposta]
  E --> A
  F["Insomnia, curl, axios<br/>ferramentas"] -.->|"substituem seu código,<br/>não o navegador"| C
`}
</Mermaid>

O CORS é o caso mais curioso dos quatro, porque ele é ao mesmo tempo do navegador e do servidor: a
regra é aplicada pelo navegador, e a autorização vem em cabeçalhos que só o servidor pode enviar. É
por isso que ele é agrupado junto com os conceitos que exigem configuração e resposta do servidor.

A navegação lateral reflete essa separação: a trilha **Comunicação de Rede › APIs do Navegador** reúne o que se chama
do código (`fetch`, `WebSocket`, `EventSource`), e **Comunicação de Rede › Fundamentos de Rede** reúne as convenções, ferramentas e estratégias que
acompanham a chamada (`fetch`, `CORS`, `REST`, `GraphQL` e `SSR`).

## Roteiro Sugerido de Estudos

Se esta é a sua primeira passagem pelo guia, comece por [O que uma Aplicação Front-end Faz?](common-features/): a página liga cada funcionalidade recorrente de uma aplicação vanilla à Web API que a resolve, e serve de índice por problema para tudo o que vem depois.

A ordem abaixo parte do que sustenta todo o resto, o carregamento da página e o DOM, e avança para rede, armazenamento e recursos do dispositivo:

<Steps>
1. **Fundamentos do Ambiente**: Comece por [Ciclo de Vida da Página](browser/lifecycle/) e [Objetos do Navegador](browser/objects/) para entender quando o código é executado e quais objetos globais existem.
2. **Navegação e Interface**: Explore a [History API](browser/history/) para navegação SPA e a [Dialog API](browser/modern-apis/dialog/) para modais nativos.
3. **DOM e Interatividade**: Domine a [Manipulação do DOM](dom/manipulation/), [Eventos](dom/events/), [Elementos Dinâmicos](dom/dynamic-elements/), [Formulários e Validação](dom/forms/) e [Rolagem e Posicionamento](dom/scroll/).
4. **Armazenamento de Dados**: Estude [Local Storage](storage/local-storage/) e [Cookies](storage/cookies/) para gerenciar estados e sessões no cliente.
5. **Rede e Comunicação**: Consuma dados assíncronos com a [Fetch API](http/fetch/), receba eventos em streaming com [Server-Sent Events](http/sse/), comunique-se em tempo real com a [WebSockets API](http/websockets/), entenda [CORS e Segurança](http/cors/), [REST API](http/rest/), [GraphQL](http/graphql/) e renderização no servidor com [Server-Side Rendering (SSR)](browser/ssr/).
6. **Segurança no Front-end**: Entenda os vetores de ataque em [OWASP e Segurança no Cliente](security/client-side/) e aplique defesas contra XSS, CSRF e armazenamento inseguro.
7. **Recursos do Dispositivo e Desempenho**: Experimente [Geolocation](browser/modern-apis/geolocation/), [Notifications](browser/modern-apis/notification/), [Vibration](browser/modern-apis/vibration/), [Observadores](browser/observers/) e [Web Workers](browser/workers/) para tarefas pesadas, e feche com [WebAssembly](browser/webassembly/) quando nem outra thread resolver.
</Steps>

## Decisões Frequentes de Arquitetura

A tabela funciona como índice por problema: localize a necessidade na primeira coluna e siga para a API indicada. A terceira coluna traz o cuidado que costuma ser descoberto tarde demais em cada caso:

| Problema / Necessidade | API Indicada | Cuidados Principais |
| --- | --- | --- |
| Executar código após carregamento do HTML | `DOMContentLoaded`, `defer`, `type="module"` | Garantir que a árvore DOM já foi construída antes da consulta. |
| Alterar conteúdo, atributos e estilos | `document.querySelector`, `classList` | Verificar se o elemento consultado existe antes da manipulação. |
| Reagir a cliques, teclas e formulários | `addEventListener` | Tratar `preventDefault()` e vazamento de memória em listeners. |
| Navegação SPA sem recarregar a página | `history.pushState()`, `popstate` | Configurar o servidor para fallback de rotas (404/index.html). |
| Guardar preferências locais do usuário | `localStorage` | Serializar com `JSON.stringify()` e limitar dados não sensíveis. |
| Comunicação em tempo real full-duplex | `WebSocket` (`wss://`) | Gerenciar reconexões automáticas e serialização de mensagens. |
| Requisitar dados de um servidor HTTP | `fetch()` | `fetch()` não rejeita Promises para erros HTTP 404/500 (checar `res.ok`). |
| Notificar o usuário fora da aba | `Notification` | Requer protocolo `https://` e permissão prévia do usuário. |
| Feedback tátil em dispositivos móveis | `navigator.vibrate()` | Requer ação/gesto prévio do usuário e suporte do hardware. |
| Tratar cálculos pesados sem travar a UI | `Web Worker` | Código roda em thread separada; comunicação via `postMessage()`. |
| Executar algoritmo numérico intensivo ou biblioteca em C/Rust | `WebAssembly` | O módulo não acessa o DOM; só troca números com o JavaScript. |
