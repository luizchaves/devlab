A **Notification API** permite que uma página solicite permissão para exibir notificações do sistema
operacional. A mensagem aparece fora da área visual da página e precisa ser usada com cuidado.

## Objetivo

Compreender o fluxo de permissão das notificações do navegador e a diferença entre a notificação efêmera e a persistente. Ao final do tópico, o leitor deve ser capaz de:

- Consultar `Notification.permission` e solicitar autorização com `requestPermission()`.
- Criar uma notificação simples com `new Notification()` e reagir ao clique do usuário.
- Explicar por que pedir permissão no carregamento da página costuma resultar em bloqueio definitivo.
- Reconhecer quando a notificação precisa de um *service worker* para sobreviver ao fechamento da aba.
- Escolher entre notificação do sistema e aviso na própria página conforme a urgência da mensagem.

## O contrato de permissão

A notificação é a única API deste catálogo capaz de alcançar o usuário quando ele não está olhando
para a página. Esse alcance é exatamente o que a torna sensível, e o navegador o condiciona a uma
permissão de três estados, guardada por origem.

<Mermaid title="Estados da permissão de notificação e as transições possíveis">
{`
flowchart TD
  A["permission === 'default'"] -->|requestPermission| B{Escolha do usuário}
  B -->|Permitir| C["'granted'<br/>new Notification funciona"]
  B -->|Bloquear| D["'denied'<br/>pedidos futuros falham em silêncio"]
  D -.->|só pelas configurações<br/>do navegador| A
`}
</Mermaid>

A seta tracejada é a parte que importa. De `denied` não se volta por código: nenhum novo
`requestPermission()` exibe o diálogo outra vez. Um pedido feito na hora errada não custa uma recusa,
custa o recurso inteiro para aquele site.

Daí a regra prática do tópico: consulte o estado antes de pedir, e peça só quando o usuário acabou de
demonstrar interesse em ser avisado.

```js title="Pedido condicionado ao estado atual"
async function notifyOnFinish(message) {
  if (Notification.permission === 'denied') return;

  if (Notification.permission === 'default') {
    const result = await Notification.requestPermission();
    if (result !== 'granted') return;
  }

  new Notification('Processamento concluído', { body: message });
}
```

A saída antecipada da linha 2 evita a chamada inútil, e a da linha 6 respeita a recusa sem insistir. O
`new Notification()` só é alcançado quando a permissão está de fato concedida.

## Modelo da API

Notificação é um recurso sensível porque disputa atenção do usuário mesmo quando ele não está olhando
para a aba.

| Recurso | Papel |
| --- | --- |
| `Notification.permission` | Estado atual: `default`, `granted` ou `denied` |
| `Notification.requestPermission()` | Solicita autorização ao usuário |
| `new Notification(titulo, opcoes)` | Cria uma notificação não persistente |
| `notification.onclick` | Reage a clique na notificação |
| `ServiceWorkerRegistration.showNotification()` | Exibe notificação persistente via service worker |

<Aside type="caution" title="Peça permissão na hora certa">
Não solicite permissão assim que a página carrega. O melhor momento é depois de uma ação que mostre
intenção, como clicar em "avisar quando terminar".
</Aside>

## Cuidados práticos

Em muitos navegadores, o construtor `Notification()` funciona apenas em desktop. Para mobile e
notificações mais robustas, o caminho costuma envolver service worker.

| Situação | Cuidado |
| --- | --- |
| Página comum aberta | `new Notification()` pode bastar em desktop |
| App instalado ou PWA | Use service worker para notificações persistentes |
| Usuário negou permissão | Não peça repetidamente |
| Conteúdo sensível | Evite expor dados privados no texto da notificação |

## Quando usar, e quando não usar?

Uma notificação do sistema interrompe o usuário fora do navegador. Ela se justifica quando o assunto
sobreviveu à saída da aba, e não quando a informação está visível na própria tela que ele está
olhando.

A tabela indica o canal correto para cada tipo de aviso:

| Situação | Escolha | Em vez de |
| --- | --- | --- |
| Processamento longo que terminou com a aba em segundo plano | `new Notification()` | Mensagem na página, que o usuário não está vendo |
| Mensagem nova em um chat aberto em outra aba | `new Notification()` | Apenas o contador no título da aba |
| Erro de validação de formulário | Aviso ao lado do campo | Notificação, que tira o usuário do contexto do erro |
| Confirmação de uma ação que ele acabou de fazer | Aviso na própria página | Notificação, redundante com o que está na tela |
| Aviso que precisa chegar com o site fechado | *Push* com *service worker* | `new Notification()`, que morre junto com a página |
| Pedir permissão logo na primeira visita | Não fazer | O bloqueio resultante é permanente |

A quinta linha é a que separa as duas famílias de notificação. O `new Notification()` deste tópico só
existe enquanto a página existe; para alcançar o usuário depois que ele fechou o site, é preciso um
*service worker* registrado e uma assinatura de *push*.

## Perguntas de revisão

Responda às questões a seguir para avaliar a compreensão sobre o ciclo de permissão, exibição e boas práticas da Notifications API.

### Permissão

Questões sobre o fluxo de autorização e estados de permissão:

1. **Quais são os três valores possíveis de `Notification.permission`?**

<details>
  <summary>Possível resposta</summary>

  `default` (ainda não decidido), `granted` (permitido) e `denied` (bloqueado).
</details>

2. **O que acontece ao chamar `requestPermission()` quando o estado já é `denied`?**

<details>
  <summary>Possível resposta</summary>

  Nada visível: o diálogo não é exibido e a Promise resolve com `denied`. Só o usuário reverte isso nas
  configurações do site.
</details>

3. **Por que consultar `Notification.permission` antes de pedir?**

<details>
  <summary>Possível resposta</summary>

  Para não chamar o pedido inutilmente quando já há decisão registrada, e para reagir de forma
  adequada a cada estado.
</details>

4. **Por que pedir permissão no carregamento da página costuma resultar em bloqueio?**

<details>
  <summary>Possível resposta</summary>

  Porque o usuário ainda não sabe o que será notificado e recusa por precaução, e essa recusa é
  permanente para o site.
</details>

### Uso e alcance

Questões sobre limites do contexto de aba e decisões de produto:

5. **Qual a diferença entre `new Notification()` e `showNotification()` do *service worker*?**

<details>
  <summary>Possível resposta</summary>

  A primeira só existe enquanto a página está aberta; a segunda é persistente e funciona mesmo com o
  site fechado.
</details>

6. **Como reagir ao clique do usuário em uma notificação?**

<details>
  <summary>Possível resposta</summary>

  Atribuindo um manipulador a `notification.onclick`, normalmente para focar a aba correspondente com
  `window.focus()`.
</details>

7. **Por que um erro de validação não deve virar notificação?**

<details>
  <summary>Possível resposta</summary>

  Porque o usuário está olhando para o formulário. A mensagem deve aparecer junto do campo que causou o
  erro, e não fora do navegador.
</details>

8. **Em que momento da interação faz sentido pedir a permissão?**

<details>
  <summary>Possível resposta</summary>

  Logo depois de o usuário demonstrar interesse em ser avisado, como ao ativar um alerta ou iniciar um
  processamento longo.
</details>
