A disciplina de Programação para Web 2 tem como objetivo principal proporcionar uma compreensão prática e aplicada do desenvolvimento front-end de aplicações Web modernas. Dada a ampla variedade de tópicos abordados ao longo do semestre, o projeto final é a oportunidade ideal para integrar os conceitos de sala de aula e explorar novos recursos e tecnologias.

O projeto final é uma atividade **obrigatória** para todos os estudantes da disciplina e será desenvolvido de forma incremental ao longo do curso, dividindo-se nas seguintes etapas gerais:

<Steps>

1. **Concepção, Proposta e Pitch Inicial**
   - Formação da equipe, escolha do tema (livre), desenvolvimento de telas estáticas (HTML/CSS), cadastro no portal `ifpb/projects` via Pull Request e apresentação do Pitch inicial (5 min).

2. **Projeto 1.1 — Front-end Vanilla (10 pontos)**
   - Desenvolvimento da interface dinâmica manipulando o DOM, consumo de dados locais ou API simulada com `json-server` (ou LocalStorage), tratamento de eventos do usuário, organização modular com ESM e uso do Vite (template vanilla).

3. **Projeto 1.2 — Front-end React & Supabase (10 pontos)**
   - Reconstrução da aplicação com Next.js (App Router), TypeScript e React, integração com Supabase para autenticação e persistência em banco PostgreSQL, formulários validados com React Hook Form e Zod, e gerência de estado com Context API/Zustand e TanStack Query.

</Steps>

## Definição e Estruturação do Projeto

Nesta etapa inicial, as equipes realizarão o planejamento, concepção visual e estruturação da proposta do projeto.

<Steps>

1. **Formação da Equipe**
   - Escolha os integrantes que farão parte da equipe do projeto (máximo de **3 integrantes**).

2. **Definição do Tema e Escopo**
   - O tema do projeto é **livre**.
   - No que diz respeito ao escopo, os membros da equipe serão responsáveis por definir o domínio de negócio, o layout, as funcionalidades e a navegabilidade.
   - **Boa Prática para Definição de Escopo:** Para entender como delimitar o problema, entender os fluxos do usuário e definir o escopo de forma clara e profissional, consulte este artigo de estudo de caso: [Conectando estabelecimentos de beleza a clientes durante a quarentena com segurança (Medium)](https://medium.com/@nativasconcelos/conectando-estabelecimentos-de-beleza-a-clientes-durante-a-quarentena-com-seguran%C3%A7a-ebf0584b1de1).

3. **Benchmarking e Inspiração**
   - Identifique ferramentas existentes no mercado relacionadas ao tema escolhido e analise suas principais funcionalidades (*features*).
   - Ferramentas de mercado (ex: Kinvo, Gorila, Status Invest, Trademap) servem como excelente referência para projetos na área de investimentos/finanças.
   - Para explorar e se inspirar nos trabalhos desenvolvidos na disciplina, consulte a galeria geral de [Projetos de Programação para Web 2 (PW2)](https://ifpb.github.io/projects/codes/pw2-csbes-jp/1/).

4. **Identidade do Projeto**
   - Defina um nome e codinome único e marcante para o sistema (ex: `investapp`, `assettracker`, `finwallet`) e desenvolva uma logo para o projeto.

5. **Criação do Repositório e Telas Estáticas**
   - Crie um repositório público no GitHub para o projeto.
   - **Dica de nome do repositório:** Utilize o próprio codinome do projeto em letras minúsculas, usando hífens se necessário (ex: `investapp` ou `asset-tracker`). Isso mantém a URL limpa (ex: `github.com/usuario/investapp`), facilita a configuração do GitHub Pages (`usuario.github.io/investapp`) e alinha o repositório diretamente com o arquivo YAML (`investapp.yml`).
   - O repositório deve conter:
     - **Telas iniciais do projeto:** desenvolvidas de forma estática, utilizando apenas **HTML e CSS** (opcionalmente com apoio de uma biblioteca ou framework CSS, como Tailwind CSS, Bootstrap, DaisyUI, etc.);
     - **Página de Índice (`index.html`):** crie um arquivo `index.html` na raiz do projeto que funcione como menu/índice com links de navegação para todas as demais telas `.html` desenvolvidas (ex: atalhos para `login.html`, `dashboard.html`, `assets.html`, `reports.html`), permitindo visualizar todo o fluxo visual facilmente ao acessar o GitHub Pages;
     - **Arquivo `README.md`:** apresentando a proposta do projeto, seu propósito, equipe, suas principais funcionalidades e a estratégia/hipóteses técnicas para obtenção de dados reais.
   - **Configuração do Repositório no GitHub (About & Topics):**
     - Na página do seu repositório no GitHub, clique no ícone de engrenagem no canto superior direito da seção **About**;
     - Preencha o campo **Description** com o objetivo do projeto;
     - Preencha o campo **Website** com o link da aplicação no GitHub Pages (ex: `https://usuario.github.io/investapp/`);
     - Adicione os **Topics (Tópicos)** obrigatoriamente com as tags `ifpb` e `ifpb-csbes-jp-pw2` (além de tags como `html`, `css`, `javascript`, `react`, `supabase`).

6. **Envio da Proposta por Pull Request (PR) em `ifpb/projects`**
   - Ao final desta etapa, cadastre os integrantes e o projeto enviando um **Pull Request (PR)** para o repositório [ifpb/projects](https://github.com/ifpb/projects) e submeta o link do repositório da equipe no **GitHub Projects** da disciplina.

</Steps>

<Aside type="note" title="Foco da Etapa Inicial: Interface Estática e Dados Fictícios">
  As telas desenvolvidas nesta etapa devem utilizar **dados fictícios (*mock data*)** e **não precisam estar efetivamente operacionais** com integração de back-end por enquanto. O objetivo principal é construir e avaliar a interface do sistema, com atenção à organização das informações, estrutura dos componentes e fluxo de navegação.

  Contudo, além da interface estática, a equipe deve incluir na documentação e no Pitch o seu **planejamento inicial para a obtenção de dados reais**. Embora não seja obrigatório ter a resposta definitiva neste momento, é muito importante que a equipe apresente **hipóteses e estratégias técnicas iniciais**, demonstrando ter uma ideia clara do caminho para obtê-los futuramente (ex: consumo de APIs de cotações financeiras em tempo real, importação de extratos em arquivos CSV/OFX ou modelagem em Banco de Dados com Supabase).
</Aside>

### Sugestão de Uso de IA e Prompts

O uso de assistentes de Inteligência Artificial (como ChatGPT, Claude, Gemini ou Copilot) é altamente incentivado para acelerar o brainstorming, prototipagem e estruturação da documentação. Veja abaixo alguns exemplos de prompts que a equipe pode utilizar adaptados para um exemplo de **Gerenciamento de Investimentos (InvestApp)**:

#### 1. Brainstorming de Temas e Benchmarking
```text title="Prompt: Ideias de Projeto e Análise de Mercado"
Atue como um Arquiteto de Software e Engenheiro de Produto Financeiro.
Preciso de 3 ideias de projetos web para gestão de investimentos pessoais 
e controle de carteira de ativos (ex: Ações, FIIs, Renda Fixa, Cripto).

Para cada ideia, apresente:
1. O problema atual enfrentado pelos investidores (ex: planilhas manuais);
2. As funcionalidades principais (features) da solução Web proposta;
3. Ferramentas de mercado existentes para benchmarking comparativo 
   (ex: Kinvo, Gorila, Status Invest, Trademap).
```

#### 2. Nome, Slogan e Identidade Visual (Logo)
```text title="Prompt: Nome e Conceito de Logo"
Somos uma equipe de estudantes desenvolvendo um sistema Web para 
[descreva a ideia, ex: gestão de carteira de investimentos e proventos].

Sugira:
- 5 nomes curtos, modernos e marcantes para o projeto;
- Um slogan em português para o projeto;
- Ideia de conceito visual para a logo e um exemplo em código SVG 
  simples representando o ícone do projeto.
```

#### 3. Geração de Layout HTML/CSS Estático com Dados Fictícios
```text title="Prompt: Interface Estática e Layout em HTML/CSS"
Crie o código HTML5 e Tailwind CSS de uma tela inicial (Dashboard) 
estática para um sistema Web de [tema, ex: controle de investimentos].

A tela deve incluir:
1. Menu de navegação lateral (Sidebar) com logo e links de navegação;
2. Cabeçalho superior com barra de busca, título e perfil do usuário;
3. 4 cards de métricas com dados fictícios (ex: Patrimônio Total 
   "R$ 45.850,00", Rentabilidade "+12.4%", Proventos "R$ 380,00/mês", 
   Reserva "R$ 10.000,00");
4. Uma seção destacada listando funcionalidades principais do sistema 
   (ex: alocação por classe de ativos, extrato de proventos, calculadora 
   de preço médio e histórico de rentabilidade);
5. Uma tabela estilizada com 5 ativos da carteira (ex: Ticker, Tipo, 
   Quantidade, Preço Médio, Cotação Atual, Rentabilidade e Ações).

Importante: Apenas HTML e CSS estáticos com Tailwind, sem JavaScript 
funcional por enquanto.
```

#### 4. Estrutura do README.md do Repositório
```text title="Prompt: Geração da Documentação do Repositório"
Gere o conteúdo em Markdown para o arquivo README.md do projeto

8. Seção "Estratégia para Obtenção de Dados Reais (Hipóteses Técnicas)"
```

### Estrutura do `README.md` e Organização do Repositório do Projeto

Além do cadastro no portal `ifpb/projects`, o repositório próprio do projeto deve ser mantido organizado e estruturado desde o início. A documentação inicial no `README.md` **será evoluída continuamente ao longo do tempo**, acompanhando as entregas e novas etapas do projeto.

### Organização Inicial de Diretórios

Para manter os artefatos organizados e a raiz (*root*) do repositório limpa, recomenda-se armazenar toda a documentação do sistema dentro da pasta **`docs/`** (detalhamento das *features*, requisitos, histórias de usuário e notas de arquitetura). Para os protótipos de interface e artefatos visuais (esboços, wireframes, prints de telas estáticas ou arquivos de design), utilize a subpasta **`docs/prototypes/`** (ou alternativas como **`docs/design/`** ou **`docs/mockups/`**).

### Cadastro e Envio da Proposta via Pull Request (`ifpb/projects`)

O cadastro e apresentação oficial da proposta são feitos através de um **Pull Request (PR)** no repositório [ifpb/projects](https://github.com/ifpb/projects), que serve como portal de projetos do IFPB.

Conforme a documentação oficial do [ifpb/projects](https://github.com/ifpb/projects/blob/main/README.md), siga os passos abaixo para cadastrar a equipe e o projeto:

<Steps>

1. **Fazer Fork e Clone do Repositório `ifpb/projects`**
   - Como os estudantes não possuem permissão de escrita direta na organização `ifpb/`, o primeiro passo é realizar um **Fork**.
   - O Fork cria uma cópia pessoal do repositório [ifpb/projects](https://github.com/ifpb/projects) dentro do seu próprio perfil do GitHub.
   - Com isso, você pode editar e adicionar os seus arquivos livremente na sua cópia e, posteriormente, enviar um **Pull Request (PR)** solicitando a inclusão das suas alterações no repositório oficial `ifpb/projects`.
   - Clone essa cópia (fork) para a sua máquina local para trabalhar nos arquivos ou efetue o upload e a edição dos arquivos diretamente através da interface web do GitHub.

2. **Cadastro de Pessoas (Integrantes da Equipe)**
   - **Arquivo Individual:** Cada estudante da equipe deve criar e enviar o seu próprio arquivo YAML individual no diretório `src/content/people/`, nomeado no formato `nome-sobrenome-matricula.yml`.
   - **Perfis Necessários:** Os endereços de perfil no **GitHub** (`addresses.github`) e no **LinkedIn** (`addresses.linkedin`) são necessários. Recomenda-se [personalizar a URL do seu perfil público no LinkedIn](https://www.linkedin.com/help/linkedin/answer/a542685) (ex: `linkedin.com/in/nome-sobrenome`) para torná-la profissional e fácil de memorizar.
   - **Foto de Perfil e Avatar:** Caso ainda não possua uma foto de perfil adequada no GitHub, é highly recomendável cadastrar uma foto profissional no seu perfil. O campo `avatar.github` é preenchido no formato `https://github.com/usuario.png` (ao abrir esse link no navegador, ele redireciona para a URL do *GitHub User Content* `https://avatars.githubusercontent.com/u/ID`, que mantém o ID permanente do usuário mesmo se o username for modificado).
   - **Campos Opcionais:** Outros links e redes profissionais (como `homepage`, `instagram`, `bluesky`, `lattes`, etc.) são opcionais e a lista completa de campos disponíveis pode ser consultada no [README oficial do ifpb/projects](https://github.com/ifpb/projects/blob/main/README.md).

   ```yaml title="src/content/people/joao-silva-20241370001.yml"
   name:
     compact: João Silva
     full: João da Silva Santos
   avatar:
     github: https://github.com/joaosilva.png
     githubUC: https://avatars.githubusercontent.com/u/12345678
   occupations:
     - id: 20241370001
       type: student
       course: csbes-jp
       isFinished: false
   addresses:
     github: https://github.com/joaosilva
     linkedin: https://www.linkedin.com/in/joao-silva/
     email: joao.silva@estudante.ifpb.edu.br
   ```

   <Aside type="tip" title="Dica: Importância da Foto de Perfil Profissional">
     Ter uma foto de perfil profissional é importante para construir uma identidade digital consistente e facilitar o reconhecimento no ambiente acadêmico e profissional. No GitHub, assim como no LinkedIn, uma boa foto transmite cuidado com a apresentação do perfil e contribui para uma imagem mais profissional, especialmente quando o perfil é utilizado como portfólio por recrutadores e empresas. Por isso, recomenda-se utilizar, sempre que possível, a mesma foto profissional no GitHub e no LinkedIn, mantendo uma identidade visual coerente em seus principais canais profissionais.
   </Aside>

3. **Cadastro do Projeto**
   - **Responsável pelo Cadastro:** Apenas **um integrante da equipe** precisa criar o arquivo YAML do projeto no diretório `src/content/projects/` com o nome `titulo-do-projeto.yml` (ex: `investapp.yml`).
   - **Atualizações Futuras:** Caso ocorram mudanças durante o desenvolvimento (como adicionar a URL do `homepage`, atualizar a imagem de `preview` ou alterar `tags`), qualquer integrante pode enviar **novos Pull Requests (PRs)** para atualizar o arquivo do projeto no portal.
   - **Requisitos de Endereços (`addresses`):** O campo `repository` é o mínimo aceitável, porém os campos `preview` (imagem de exibição), `homepage` (site no ar) e `workflow` (gerenciador de tarefas) são **altamente recomendados**:
     - `addresses.preview`: link da imagem de prévia armazenada no próprio repositório do projeto (ex: `preview.png` na raiz);
     - `addresses.homepage`: link do site estático publicado (ex: no GitHub Pages);
     - `addresses.workflow`: link público para o gerenciador de tarefas, quadro Kanban e acompanhamento do fluxo de trabalho da equipe, de preferência utilizando o **GitHub Projects** (consulte a [listagem de projetos com workflow em ifpb/projects](https://ifpb.github.io/projects/codes/workflow/1/) para ver exemplos);
     - `addresses.design`: link opcional do protótipo/design (Figma, Canva, etc.);
     - `category.subject`: código da disciplina (`pw2-csbes-jp`);
     - `category.period`: período letivo atual (`2026.2`);
     - `tags`: lista de tecnologias e temas sempre em **letras minúsculas e sem espaços** (ex: `html`, `css`, `javascript`, `react`, `supabase`, `investimentos`);
     - `owners`: lista com as matrículas dos integrantes da equipe.

   <Aside type="tip" title="Dica: Como Ativar o GitHub Pages no Repositório">
     Para obter a URL do `addresses.homepage`, ative a hospedagem estática no GitHub: acesse o repositório do seu projeto no GitHub, vá em **Settings** > **Pages**, em **Build and deployment / Branch** selecione a branch `main` e a pasta `/ (root)` e clique em **Save**. O site será publicado no endereço `https://usuario.github.io/nome-do-projeto/`. Note que a publicação **não é instantânea**: você pode acompanhar a compilação, o status da publicação e a geração da URL acessando a aba **Actions** do seu repositório.
   </Aside>

   <Aside type="tip" title="Dica: Como Criar uma Imagem de Preview de Qualidade">
     Para configurar o campo `addresses.preview`, capture uma boa imagem da tela principal (Dashboard) do sistema:
     - **Armazenamento no Próprio Repositório:** A imagem de preview deve ser armazenada diretamente no repositório do projeto da equipe (ex: salvando o arquivo `preview.png` na raiz). Isso evita dependência de serviços externos de hospedagem de imagens e mantém os ativos visuais sempre versionados e acessíveis junto ao código.
     - **Proporção e Resolução:** Prefira a proporção 16:9 ou 16:10 (ex: **1280×720px** ou **1920×1080px**).
     - **Redimensionamento (Resize):** Se capturar a imagem em monitores de alta resolução (4K ou telas Retina), redimensione as dimensões para a largura máxima de 1280px.
     - **Otimização e Tamanho do Arquivo:** Comprima a imagem (em formato PNG ou JPG) para manter o arquivo leve, idealmente **abaixo de 500 KB** (evite imagens pesadas acima de 1 MB para não comprometer o tempo de carregamento no portal). Ferramentas gratuitas como [TinyPNG](https://tinypng.com/), [Squoosh](https://squoosh.app/) ou [ILoveIMG](https://www.iloveimg.com/resize-image) ajudam a redimensionar e otimizar sem perder qualidade.
     - **Captura Limpa:** Capture apenas a área útil da aplicação, omitindo barras de endereço, abas do navegador ou elementos do sistema operacional.
     - **URL Direta:** Utilize o link da imagem salva no seu repositório adicionando o parâmetro `?raw=true` (ex: `https://github.com/usuario/nome-do-projeto/blob/main/preview.png?raw=true`) ou a URL crua (`https://raw.githubusercontent.com/usuario/nome-do-projeto/main/preview.png`).
   </Aside>

   <Aside type="caution" title="Cuidado: Não Envie o Código-Fonte do Projeto para o ifpb/projects">
     O código-fonte da aplicação, arquivos `.html`, `.css`, `.js`, imagens, protótipos e documentos pertencem **estritamente ao repositório individual da equipe** (ex: `github.com/usuario/investapp`) e **NÃO devem ser enviados ao repositório `ifpb/projects`**.

     No Pull Request para o `ifpb/projects`, envie **apenas e exclusivamente os arquivos de cadastro em formato YAML**:
     - `src/content/people/nome-sobrenome-matricula.yml` (arquivo de cadastro de cada integrante);
     - `src/content/projects/titulo-do-projeto.yml` (arquivo com as informações e links do projeto).
   </Aside>

4. **Realizar Commit, Push e Abrir o Pull Request (PR)**
   - **Padrão da Mensagem de Commit:** Ao realizar o commit dos arquivos adicionados (`src/content/people/` e `src/content/projects/`), utilize o prefixo `content:` indicando o nome do estudante e do projeto, por exemplo:
     - `git commit -m "content: add student joao-silva and project investapp"`
     - `git commit -m "content: add investapp project"`
   - Envie as alterações para o seu fork (`git push origin main`) e abra um **Pull Request (PR)** para a branch `main` do repositório oficial [ifpb/projects](https://github.com/ifpb/projects).
   - **Análise e Aprovação:** Após enviar o PR, aguarde a revisão no repositório `ifpb/projects`. Os mantenedores irão analisar o PR e, se necessário, solicitarão ajustes nos comentários antes de aprovar e integrar (*merge*) a proposta ao portal.
   - Além do PR, inclua o link do repositório do projeto no **GitHub Projects** da turma.

   <Aside type="tip" title="Dica: Como Abrir um Pull Request (PR) no GitHub">
     Para abrir o Pull Request após fazer commit e push dos arquivos no seu fork:
     1. Acesse a página do seu fork no GitHub (ex: `https://github.com/seu-usuario/projects`);
     2. O GitHub costuma exibir um banner destacado com o botão verde **"Compare & pull request"**;
     3. Se o banner não aparecer, vá na aba **"Pull requests"** e clique no botão **"New pull request"**;
     4. Verifique se o repositório de destino (*base repository*) é `ifpb/projects` (branch `main`) e o de origem (*head repository*) é o seu fork `seu-usuario/projects` (branch `main`);
     5. Preencha o título do PR utilizando o prefixo `content:` (ex: `content: add student joao-silva and project investapp`) e clique em **"Create pull request"**.
   </Aside>

   <Aside type="caution" title="Importante: Verificação de Links, Atualização do Fork e Remoção por Inatividade">
     - **Verificação Prévia:** Antes de submeter o PR, valide e certifique-se de que todos os endereços (`repository`, `homepage`, `preview`, `linkedin`, etc.) estão funcionais e acessíveis publicamente.
     - **Sincronização do Fork:** Se você já possui um fork antigo do `ifpb/projects`, lembre-se de sincronizá-lo com a branch `main` do repositório oficial (botão **Fetch upstream / Sync fork** no GitHub) antes de criar a sua branch ou fazer novos commits.
     - **Atualização Contínua:** Sempre que houver qualquer alteração nas URLs do projeto (novo repositório, atualização do GitHub Pages ou novos links), envie um novo PR atualizando o arquivo YAML correspondente.
     - **Remoção Automática de Links Quebrados:** Repositórios e perfis de pessoas que apresentarem **links inativos ou quebrados serão automaticamente removidos** da listagem do portal `ifpb/projects`.
   </Aside>

</Steps>

Para estruturar a fala da equipe de maneira objetiva e dentro do tempo estipulado, recomenda-se organizar a apresentação nos seguintes passos:

### Projeto 1.1 — Front-end Vanilla (10 pontos)

Esta atividade consiste em desenvolver a primeira etapa do projeto da disciplina, especificamente implementando o front-end de uma aplicação Web conforme a proposta definida. Mostre no código como foram aplicados os seguintes aspectos:

| Critério | Descrição | Pontuação |
| :--- | :--- | :---: |
| **Uso de Programação Funcional** | Transformação de dados com `map()`, `filter()` e/ou `reduce()`. | **1,5 pts** |
| **Uso de ESM (ECMAScript Modules)** | Organização do código com `import` e `export` e separação de responsabilidades. | **1,0 pt** |
| **Estruturação de Dados** | Organização dos dados em arrays em memória ou persistência com LocalStorage (ou `json-server`). | **2,0 pts** |
| **Manipulação do DOM e Componentes Dinâmicos** | Criação manual de componentes (`createElement`, `appendChild`, etc.) e CRUD. | **2,0 pts** |
| **Tratamento de Eventos** | Captura de cliques, submissão de formulários e alterações em campos. | **2,0 pts** |
| **Uso do Vite (Template Vanilla)** | Configuração e execução do projeto com o template vanilla do Vite. | **1,5 pts** |
| **Uso de Bibliotecas** | Biblioteca auxiliar e sua finalidade no projeto. | *opcional* |

#### Aspectos a Demonstrar no Código

- **Uso de Programação Funcional — 1,5 pts:** Como foram utilizados métodos de programação funcional, como `Array.map()`, `Array.filter()` e/ou `Array.reduce()`, para manipulação e transformação de dados dentro da aplicação?
- **Uso de ESM (ECMAScript Modules) — 1 pt:** Como o código JavaScript foi organized utilizando ESM (ECMAScript Modules), demonstrando a separação de responsabilidades entre arquivos e o uso de `import` e `export`?
- **Estruturação de Dados (LocalStorage ou JSON/Array) — 2 pts:** Como os dados utilizados na aplicação foram organizados e manipulados, seja por meio de arrays em memória ou utilizando persistência com LocalStorage (ou `json-server`)?
- **Manipulação do DOM e Criação de Componentes Dinâmicos — 2 pts:** Como o DOM foi manipulado para construção da interface? Descreva como os componentes foram criados dinamicamente de forma manual (sem uso de frameworks como Angular, React ou Vue), utilizando métodos como `createElement`, `appendChild` ou similares, a partir dos dados da aplicação. (Tente incluir no mínimo um CRUD.)
- **Tratamento de Eventos — 2 pts:** Como os eventos de interação do usuário (como cliques em botões, submissão de formulários ou mudanças em campos) foram tratados no JavaScript?
- **Uso do Vite (Template Vanilla) — 1,5 pts:** Como foi realizada a configuração e utilização do Vite com o template vanilla para criação e execução do projeto?
- **Uso de Bibliotecas (opcional):** Foi utilizada alguma biblioteca auxiliar (exceto frameworks de componentes como Angular, React ou Vue)? Se sim, explique qual foi utilizada e sua finalidade no projeto.
