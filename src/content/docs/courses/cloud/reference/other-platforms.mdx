Este tópico reúne plataformas relevantes que aparecem em decisões reais, mas que não precisam de uma trilha completa neste guia neste momento. Elas entram como vocabulário de comparação: cada uma ensina uma forma diferente de publicar, executar ou persistir dados.

## Objetivo

Compreender onde GitHub Pages, Fly.io, Heroku, Azure Static Web Apps, Google Cloud Run, Appwrite e PocketBase se encaixam no mapa de computação em nuvem para aplicações web. Ao final do tópico, o leitor deve ser capaz de:

- Classificar plataformas por hospedagem estática, PaaS, containers, BaaS e edge.
- Reconhecer qual decisão cada plataforma ensina melhor.
- Evitar escolher uma ferramenta apenas por popularidade.
- Comparar opções com Vercel, Netlify, Cloudflare, Supabase e Firebase.
- Indicar quando uma plataforma merece estudo próprio no projeto.

## Mapa Rápido

As plataformas abaixo não competem todas entre si. Algumas publicam front-end, outras rodam back-end, outras gerenciam dados e outras fazem uma combinação dessas camadas.

<Mermaid title="Famílias de plataformas complementares">
{`
flowchart TD
  Need["Necessidade do projeto"] --> Static["Site estático<br/>GitHub Pages, Azure SWA"]
  Need --> PaaS["PaaS<br/>Heroku, Fly.io"]
  Need --> Containers["Containers serverless<br/>Cloud Run"]
  Need --> BaaS["BaaS<br/>Appwrite, PocketBase"]
  Need --> Full["Combinação<br/>Vercel, Netlify, Cloudflare"]
`}
</Mermaid>

O mapa é propositalmente simples. Ele serve para reduzir confusão antes de entrar nos detalhes de cobrança, limite, região e runtime.

## Plataformas

A tabela resume o papel didático de cada opção. A coluna mais importante é "melhor para aprender", porque o guia prioriza decisões que transferem conhecimento para outros contextos.

| Plataforma | Família | Melhor para aprender | Quando usar |
| --- | --- | --- | --- |
| **GitHub Pages** | Hospedagem estática | Publicação gratuita junto do repositório. | Documentação, portfólio, página de projeto e site estático simples. |
| **Fly.io** | PaaS global | Aplicações próximas do usuário, máquinas leves e regiões. | APIs e apps que precisam rodar em regiões específicas. |
| **Heroku** | PaaS clássico | Dynos, add-ons, Procfile e maturidade de plataforma. | Times que valorizam simplicidade operacional e ecossistema maduro. |
| **Azure Static Web Apps** | Hospedagem estática com APIs | Integração Microsoft, GitHub Actions e APIs serverless. | Organizações que já usam Azure, Microsoft Entra ID ou governança Microsoft. |
| **Google Cloud Run** | Containers serverless | Publicar qualquer container com escala automática. | APIs, workers HTTP e jobs containerizados sem gerenciar cluster. |
| **Appwrite** | BaaS open-source | Auth, banco de documentos, storage e functions em alternativa auto-hospedável. | Projetos que querem BaaS com opção gerenciada ou própria infraestrutura. |
| **PocketBase** | BaaS compacto | SQLite, auth e painel em um binário único. | Protótipos, aplicações pequenas e ensino de BaaS auto-hospedado. |

## Leitura Por Decisão

Use esta seção quando o projeto tiver um requisito claro e você precisar escolher uma família.

| Requisito | Opções naturais | Evite quando |
| --- | --- | --- |
| Publicar documentação ou site do projeto | GitHub Pages, Netlify, Vercel, Cloudflare Pages | O site precisa de reescrita avançada, sessão no servidor ou funções. |
| Publicar API Express com processo permanente | Render, Railway, Heroku, Fly.io | A lógica cabe em uma function curta e esporádica. |
| Publicar container sem administrar cluster | Google Cloud Run, Fly.io, Render | O time não tem processo de build de imagem ou precisa só de arquivos estáticos. |
| Usar BaaS auto-hospedável | Appwrite, PocketBase, Supabase | A instituição prefere serviço totalmente gerenciado e sem operação própria. |
| Integrar com ecossistema corporativo | AWS Amplify, Azure Static Web Apps, Google Cloud Run | O projeto didático precisa de simplicidade acima de governança. |

## Observações Por Plataforma

As notas abaixo ajudam a reconhecer o formato mental de cada serviço sem transformar a página em tutorial.

| Plataforma | Modelo mental | Risco comum |
| --- | --- | --- |
| **GitHub Pages** | O repositório vira site. | Tratar como hosting de aplicação dinâmica. |
| **Fly.io** | Rode processos perto dos usuários. | Subestimar rede, volume, região e operação. |
| **Heroku** | Publique um app como dyno e componha add-ons. | Ignorar custo contínuo e limites de plano. |
| **Azure Static Web Apps** | Front-end estático com integração Azure e APIs. | Escolher só pela conta Microsoft sem precisar do ecossistema. |
| **Cloud Run** | Container HTTP que escala automaticamente. | Levar complexidade de container para app que era só estático. |
| **Appwrite** | BaaS completo com opção open-source. | Assumir que auto-hospedar remove custo operacional. |
| **PocketBase** | BaaS em SQLite e arquivo único. | Usar em domínio que precisa de alta escala ou governança pesada. |

<Aside type="tip" title="Escolha pelo custo de trocar depois">
  A pergunta decisiva não é qual plataforma tem mais recursos. É qual escolha será mais cara de desfazer: modelo de dados, autenticação, formato de deploy, runtime, storage ou conta corporativa.
</Aside>

## Quando Criar Página Própria?

Uma plataforma deve ganhar página própria quando ela ensina uma decisão que ainda não foi coberta por outra página do guia.

| Plataforma | Deve virar trilha própria quando |
| --- | --- |
| **GitHub Pages** | O curso precisar aprofundar GitHub Actions, base path e publicação de documentação. |
| **Fly.io** | O curso discutir regiões, volumes, processos longos e aplicações próximas do usuário. |
| **Heroku** | O curso comparar PaaS clássico, Procfile, dynos, add-ons e pipelines. |
| **Azure Static Web Apps** | O curso estiver em contexto Microsoft ou autenticação corporativa. |
| **Cloud Run** | O curso introduzir containers como unidade de deploy. |
| **Appwrite** | O curso comparar BaaS open-source com permissões por documento. |
| **PocketBase** | O curso ensinar auto-hospedagem leve, SQLite e operação mínima. |

## Executando

Use a página como checklist de decisão antes de adotar uma plataforma nova.

<Steps>
1. Classifique a aplicação: site estático, API, worker, container ou BaaS.
2. Escreva onde ficam dados, autenticação, arquivos e segredos.
3. Liste o que a plataforma cobra: build, execução, tráfego, banco, storage ou instância.
4. Verifique se há export de dados e plano de saída.
5. Compare com uma alternativa já coberta no guia.
6. Registre a decisão antes de implementar a integração.
</Steps>

## Exercício

Qual plataforma da tabela você escolheria para publicar apenas a documentação de um projeto open-source, e por quê?

<details>
  <summary>Possível resposta</summary>

  GitHub Pages é uma escolha natural, porque a documentação vive no mesmo repositório, o custo inicial é baixo e não há necessidade de servidor. Se o projeto precisar de previews avançados, redirects ou functions, Netlify, Vercel ou Cloudflare Pages entram como alternativas.
</details>

## Desafio

Compare Render, Railway, Fly.io, Heroku e Cloud Run para publicar uma API Express com PostgreSQL. Escolha uma e descarte duas com motivo verificável.

<details>
  <summary>Possível resposta</summary>

  Uma resposta consistente poderia escolher Render pela separação explícita entre web service, banco e cron job. Poderia descartar Cloud Run se o time ainda não tem pipeline de container e descartar Fly.io se a aplicação não precisa de regiões específicas. O importante é amarrar a escolha ao requisito, não ao gosto pela plataforma.
</details>

## Perguntas de revisão

1. **Qual é o limite natural do GitHub Pages?**
   <details>
     <summary>Possível resposta</summary>
     Ele publica arquivos estáticos, mas não executa código de servidor nem resolve sozinho casos dinâmicos que exigem runtime.
   </details>

2. **Quando Cloud Run é uma boa opção?**
   <details>
     <summary>Possível resposta</summary>
     Quando a aplicação já cabe bem em um container HTTP e o time quer escala automática sem administrar cluster.
   </details>

3. **Por que PocketBase é interessante didaticamente?**
   <details>
     <summary>Possível resposta</summary>
     Porque mostra um BaaS funcionando como um binário único com SQLite, tornando visíveis operação, arquivo de banco, backup e limites.
   </details>
