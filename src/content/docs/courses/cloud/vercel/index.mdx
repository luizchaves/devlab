A **Vercel** é uma plataforma para publicar, executar e operar aplicações web. Ela ficou conhecida pelo fluxo direto com Next.js, mas o recorte da plataforma é maior: projetos Git, deployments imutáveis, CDN, funções, ambientes, domínios, storage, observabilidade e proteção de tráfego.

## Objetivo

Compreender a Vercel como plataforma de aplicação, não apenas como botão de deploy, para decidir quais produtos usar em um front-end, quais responsabilidades continuam no BaaS e quais exigem função ou back-end próprio. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar projeto, deployment, ambiente e domínio.
- Explicar onde entram CDN, funções, storage e variáveis de ambiente.
- Escolher entre Vercel pura, Vercel com Supabase/Firebase e API própria.
- Reconhecer limites de função, cache, custo e observabilidade.
- Planejar publicação com preview, proteção e rollback.

## Mapa da Plataforma

A Vercel organiza uma aplicação em torno do projeto. O projeto conecta o repositório, define ambientes, produz deployments e distribui a versão publicada pela rede de entrega.

<Mermaid title="Mapa de produtos da Vercel em uma aplicação web">
{`
flowchart TD
  Git["Git<br/>GitHub, GitLab ou Bitbucket"] --> Project["Projeto Vercel"]
  Project --> Deploy["Deployments<br/>preview e produção"]
  Deploy --> CDN["CDN<br/>assets e cache"]
  Deploy --> Functions["Functions<br/>server-side sob demanda"]
  Project --> Env["Ambientes<br/>local, preview e produção"]
  Project --> Domains["Domínios<br/>DNS e TLS"]
  Functions --> Storage["Storage e Marketplace<br/>Blob, Postgres, KV, terceiros"]
  Project --> Operate["Operação<br/>observability, firewall e rollback"]
`}
</Mermaid>

O diagrama revela uma divisão importante: Vercel é excelente para entregar e executar a aplicação, mas nem sempre deve ser a dona do domínio de dados. Um CRUD com usuários pode usar Supabase ou Firebase; uma rota curta com segredo pode usar Functions; uma API extensa pode continuar em Express.

## Produtos e Recursos

Os produtos abaixo formam o núcleo que um desenvolvedor web encontra primeiro. A coluna "decisão" é a pergunta que cada produto obriga a responder no projeto:

| Produto | O que entrega | Decisão de arquitetura |
| --- | --- | --- |
| **Projects** | Configuração central de repositório, builds, domínios e ambientes. | O que é uma aplicação independente e o que é apenas pacote interno? |
| **Deployments** | Versões imutáveis para preview e produção. | Quando uma versão está pronta para receber tráfego real? |
| **CDN** | Entrega de assets, cache, compressão e revalidação perto do usuário. | Que resposta pode ser cacheada e por quanto tempo? |
| **Functions** | Código server-side sob demanda, com variáveis privadas. | Qual regra não pode rodar no navegador? |
| **Storage e Marketplace** | Blob, bancos, caches e integrações provisionadas como serviços. | Qual estado pertence à Vercel e qual pertence a um BaaS especializado? |
| **Domains** | Domínios personalizados, DNS e certificados TLS. | Qual URL é produção, preview ou ambiente temporário? |
| **Observability e Firewall** | Métricas, erros, tráfego e regras de proteção. | Como detectar erro real e bloquear tráfego indesejado? |

## Aplicações Típicas

A Vercel é muito boa quando o produto depende de publicação frequente e revisão visual. Ela não obriga a colocar tudo dentro dela.

| Aplicação | Arquitetura comum | Por que funciona |
| --- | --- | --- |
| SPA Vite com BaaS | Vercel + Supabase ou Firebase | Vercel publica o front; o BaaS cuida de dados e auth. |
| Aplicação Next.js | Vercel + Functions + CDN | Renderização, rotas e cache ficam integrados ao framework. |
| Site institucional | Vercel + CDN | Build estático e cache agressivo entregam custo baixo. |
| Dashboard com API própria | Vercel no front + Express em outro host | A API grande fica onde camadas e processos longos são mais claros. |
| Produto com webhooks | Vercel Functions + banco externo | Segredos e validação rodam no servidor sob demanda. |

<Aside type="tip" title="Escolha a dona de cada responsabilidade">
  Uma arquitetura saudável não pergunta "usar Vercel ou Supabase?". Ela pergunta: quem entrega o front-end, quem guarda dados, quem autentica, quem executa segredo e quem observa produção.
</Aside>

## Quando Usar, e Quando Não Usar?

Use Vercel quando o fluxo de deploy por Git, previews e entrega global for central para o projeto. Reconsidere quando o trabalho principal for processamento contínuo, filas longas, conexão persistente intensa ou uma API de domínio grande.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Front-end com revisões por pull request | **Vercel** | Cada branch ganha preview e produção vira promoção. |
| Segredo curto usado por uma tela | **Vercel Functions** | A chave fica no servidor e o front recebe só o resultado. |
| Banco, autenticação e autorização | **BaaS integrado** | Supabase ou Firebase são mais diretos para dados e identidade. |
| API extensa com jobs longos | **Back-end próprio ou PaaS de API** | Funções isoladas deixam de ser confortáveis quando viram todo o domínio. |

## Executando

Estude a Vercel em camadas, para não confundir publicação com aplicação completa:

<Steps>
1. Publique uma aplicação estática e entenda o [ciclo de deployments](deployments/).
2. Acrescente uma [função](functions/) para uma operação com segredo.
3. Revise [CDN e cache](cdn/) para saber por que uma mudança aparece para uns usuários antes de outros.
4. Escolha [storage](storage/) quando arquivos, banco ou cache forem necessários.
5. Configure [ambientes e variáveis](environments/) antes de abrir preview para outras pessoas.
</Steps>

## Exercício

Explique quais responsabilidades a Vercel assumiria em uma versão cloud do InvestApp e quais continuariam em Supabase ou Firebase.

<details>
  <summary>Possível resposta</summary>

  A Vercel pode assumir build, deploy, CDN, domínio, preview e funções curtas. Supabase ou Firebase continuam responsáveis por dados, autenticação, autorização e arquivos quando esses serviços já resolvem melhor o domínio.
</details>

## Desafio

Planeje uma arquitetura para um app de carteira de investimentos com Vercel, Supabase e uma função serverless. Liste onde ficam front-end, login, banco, upload de avatar, cotação externa e variáveis.

<details>
  <summary>Possível resposta</summary>

  O front-end fica na Vercel. Login, tabelas, RLS e avatar ficam no Supabase. A cotação externa fica em Vercel Function para proteger a chave do provedor. Variáveis públicas apontam para URL e anon key; variáveis privadas guardam tokens de serviços externos.
</details>

## Perguntas de revisão

1. **Por que deployment não é sinônimo de produção?**
   <details>
     <summary>Possível resposta</summary>
     Porque um deployment é uma versão publicada. Ela pode ser preview, teste ou produção, dependendo de qual URL e ambiente apontam para ela.
   </details>

2. **Qual responsabilidade a Vercel não elimina em uma aplicação com BaaS?**
   <details>
     <summary>Possível resposta</summary>
     A decisão de autorização. Mesmo com front publicado na Vercel, dados precisam de RLS, Security Rules ou validação server-side.
   </details>
