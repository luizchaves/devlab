O **Amplify Data** permite declarar modelos de dados e gerar uma API para a aplicação, com autorização integrada ao Auth. Ele é uma alternativa de BaaS dentro da AWS, mas não deve ser confundido com PostgreSQL ou com uma API Express escrita manualmente.

## Objetivo

Compreender Amplify Data como camada de dados orientada a modelos e regras. Ao final do tópico, o leitor deve ser capaz de:

- Explicar a relação entre modelo, API e storage por trás do Amplify.
- Diferenciar autorização por dono, usuário autenticado e grupo.
- Reconhecer quando o modelo serve ao domínio.
- Comparar Amplify Data com Firestore e Supabase.
- Planejar migração e portabilidade antes de acoplar o app.

## Modelo e API

Amplify Data parte da declaração dos modelos. A plataforma usa essa declaração para criar recursos, API e cliente tipado para o front-end.

<Mermaid title="Amplify Data do modelo ao cliente">
{`
flowchart TD
  Schema["Modelo declarado"] --> Backend["Backend Amplify"]
  Backend --> API["API gerada"]
  Backend --> Store["Armazenamento AWS"]
  Auth["Amplify Auth"] --> Rules["Regras de autorização"]
  Rules --> API
  API --> App["Aplicação"]
`}
</Mermaid>

Esse fluxo reduz código de infraestrutura, mas torna a declaração de modelos e autorização parte central do projeto.

## Autorização

A autorização decide quem pode ler e escrever cada modelo. As regras mais comuns partem de identidade autenticada, dono do registro e grupos.

| Tipo de regra | Uso típico | Risco |
| --- | --- | --- |
| **Pública** | Conteúdo aberto. | Expor dado que deveria ser privado. |
| **Autenticado** | Qualquer usuário logado acessa. | Usuários podem ver dados uns dos outros se a regra for ampla. |
| **Dono** | Cada usuário acessa o próprio registro. | Precisa testar escrita com dono falso. |
| **Grupo** | Admin, professor, suporte. | Grupo errado vira privilégio indevido. |
| **Custom** | Regra com função ou integração. | Complexidade se aproxima de back-end próprio. |

## Trecho Conceitual

O exemplo abaixo mostra a intenção de uma entidade protegida por dono. Ele não substitui a leitura da sintaxe oficial da versão usada no projeto.

```txt title="Modelo conceitual com dono"
Portfolio {
  id: ID
  name: String
  owner: User
  authorization: owner can create, read, update, delete
}
```

A regra importante é que o dono precisa ser aplicado tanto na leitura quanto na escrita. Proteger só a leitura ainda permite gravar dado no nome de outra pessoa.

<Aside type="caution" title="Dica de IA: Exija testes de acesso cruzado">
  Código gerado para BaaS costuma demonstrar CRUD feliz com um usuário só. Isso não prova isolamento.

  **Prompt:** *"Crie testes manuais para Amplify Data com dois usuários: o usuário A não pode ler, alterar, criar em nome de, nem apagar registros do usuário B."*
</Aside>

## Critérios de Uso

Use Data quando o app já está em Amplify e as regras de acesso cabem bem no modelo declarado.

| Cenário | Encaixa bem? | Motivo |
| --- | --- | --- |
| CRUD de app web ou mobile | **Sim** | Modelo, API e cliente ficam integrados. |
| Dados por usuário ou grupo | **Sim** | Auth e autorização trabalham juntos. |
| Relatórios SQL complexos | **Talvez não** | Supabase ou API com PostgreSQL pode ser mais natural. |
| Domínio com transações ricas | **Cuidado** | Pode exigir lógica custom e perder simplicidade. |

## Executando

Modele Data como contrato do domínio.

<Steps>
1. Liste entidades e relações do app.
2. Defina quem cria, lê, atualiza e apaga cada modelo.
3. Prefira regras simples antes de lógica custom.
4. Teste acesso cruzado com usuários diferentes.
5. Documente export, migração e dependência do ecossistema AWS.
</Steps>

## Exercício

Por que Amplify Data não deve ser escolhido apenas por gerar API rapidamente?

<details>
  <summary>Possível resposta</summary>

  Porque o custo real da escolha está no modelo de dados, nas regras de autorização e na portabilidade. Gerar API rápido ajuda, mas não corrige um modelo inadequado.
</details>

## Desafio

Compare Amplify Data e Supabase para relatórios de investimento por mês, categoria e usuário.

<details>
  <summary>Possível resposta</summary>

  Supabase tende a encaixar melhor quando relatórios exigem SQL, agregações e relações. Amplify Data pode servir se o app já está em AWS e as consultas necessárias forem previstas no modelo.
</details>

## Perguntas de revisão

1. **Qual parte de Amplify Data substitui código de servidor?**
   <details>
     <summary>Possível resposta</summary>
     A API gerada a partir dos modelos e das regras de autorização substitui rotas CRUD repetitivas.
   </details>

2. **Quando regra custom indica alerta de arquitetura?**
   <details>
     <summary>Possível resposta</summary>
     Quando quase toda regra precisa virar função ou integração, talvez o domínio peça uma API própria.
   </details>
