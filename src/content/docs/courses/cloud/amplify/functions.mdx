**Amplify Functions** adiciona lógica de servidor a uma aplicação Amplify, normalmente por meio de AWS Lambda. Ela serve para integrações privadas, validações que não cabem no cliente, eventos, customizações e código que precisa acessar segredos.

## Objetivo

Compreender Functions como escape hatch controlado dentro do Amplify. Ao final do tópico, o leitor deve ser capaz de:

- Identificar quando uma regra precisa de servidor.
- Explicar a relação entre Function, Auth, Data e Storage.
- Planejar segredos, permissões e eventos.
- Diferenciar função curta de API própria.
- Reconhecer quando lógica custom excessiva indica arquitetura errada.

## Papel da Function

Function entra quando o front-end ou a regra declarativa não bastam. Ela executa código em ambiente de servidor e pode acessar recursos AWS com permissões específicas.

<Mermaid title="Function conectando recursos Amplify">
{`
flowchart TD
  App["Aplicação"] --> Function["Amplify Function"]
  Function --> Secret["Segredos"]
  Function --> Data["Amplify Data"]
  Function --> Storage["Storage"]
  Function --> External["API externa"]
`}
</Mermaid>

O ponto mais importante é permissão mínima. A função deve acessar apenas os recursos necessários para a tarefa.

## Casos de Uso

Use Function quando há segredo, integração ou regra que precisa rodar fora do navegador.

| Cenário | Function serve? | Motivo |
| --- | --- | --- |
| Chamar gateway de pagamento | **Sim** | Token e assinatura ficam no servidor. |
| Enviar e-mail transacional | **Sim** | Provedor externo exige segredo. |
| Validar regra antes de gravar | **Sim, com cuidado** | Pode complementar Data quando a regra é imperativa. |
| CRUD simples de entidade | **Não é o primeiro caminho** | Data costuma resolver sem função. |
| API grande com muitas rotas | **Talvez não** | Um back-end próprio pode ser mais organizado. |

## Trecho Conceitual

Uma Function pequena deve ter contrato claro: evento de entrada, validação, segredo, chamada externa e resposta.

```ts title="Contrato conceitual de Function"
type SendEmailInput = {
  to: string;
  template: 'welcome' | 'receipt';
  userId: string;
};

type SendEmailResult = {
  status: 'queued' | 'rejected';
};
```

Esse contrato evita que a Function vire depósito de lógica solta. Quando a entrada e a saída não cabem em poucas linhas, talvez a aplicação precise de um serviço próprio.

<Aside type="caution" title="Dica de IA: Peça permissões mínimas junto do código">
  Assistentes podem gerar função que acessa tudo por conveniência. Em AWS, permissão ampla é dívida de segurança.

  **Prompt:** *"Para esta Amplify Function, liste os recursos AWS acessados, proponha permissões mínimas e mostre quais variáveis ou segredos não podem aparecer no front-end."*
</Aside>

## Executando

Projete Functions como complemento, não como substituto de arquitetura.

<Steps>
1. Defina por que a lógica precisa de servidor.
2. Escreva o contrato de entrada e saída.
3. Liste segredos e permissões mínimas.
4. Trate erro de validação, permissão e provedor externo.
5. Monitore logs, custo e frequência de execução.
</Steps>

## Exercício

Quando uma regra deve ficar em Data e quando deve virar Function?

<details>
  <summary>Possível resposta</summary>

  Regras declarativas de acesso, como dono ou grupo, devem ficar em Data. Regras que chamam serviço externo, usam segredo ou exigem fluxo imperativo podem virar Function.
</details>

## Desafio

Planeje uma Function para emitir recibo de aporte no InvestApp. Liste entrada, segredo, serviço externo e erros.

<details>
  <summary>Possível resposta</summary>

  Entrada: `investmentId` e usuário autenticado. A função consulta o registro permitido, usa segredo do provedor de e-mail ou PDF, gera recibo e retorna status. Erros: registro inexistente, usuário sem permissão, segredo ausente e falha do provedor.
</details>

## Perguntas de revisão

1. **Por que Function é um escape hatch?**
   <details>
     <summary>Possível resposta</summary>
     Porque ela permite escrever lógica de servidor quando recursos declarativos ou o front-end não bastam, mas não deve virar lugar para todo CRUD.
   </details>

2. **Qual risco existe em dar permissão ampla para uma Function?**
   <details>
     <summary>Possível resposta</summary>
     Se a função for explorada ou tiver bug, ela poderá acessar recursos além do necessário, ampliando o dano.
   </details>
