O **Guia de Computação em Nuvem** trata da infraestrutura que a aplicação não hospeda: banco de dados gerenciado, autenticação como serviço, armazenamento de arquivos, APIs geradas pela própria plataforma, hospedagem por CDN e funções sob demanda. O recorte é o do desenvolvedor web, não o do administrador de infraestrutura. O que interessa aqui é o que uma aplicação consome por SDK, por HTTP ou por `git push`, e qual parte do back-end deixa de ser escrita quando a plataforma já a oferece pronta.

Essa é uma decisão diferente da que o [Guia de Pacotes JavaScript](../npm/) discute. Um pacote é código instalado no projeto e executado na sua máquina; um serviço de nuvem é um sistema remoto, com estado próprio, cobrança própria e disponibilidade fora do seu controle. O pacote cliente (`@supabase/supabase-js`, `firebase`) é apenas a porta de entrada para ele.

<Aside type="tip" title="Modelo Mental">
Adotar uma plataforma de nuvem não elimina o back-end: transfere a responsabilidade por ele. As regras de negócio, o modelo de dados e as políticas de acesso continuam sendo decisões suas, agora expressas na configuração da plataforma em vez de em código no seu servidor.
</Aside>

## O Lugar da Nuvem na Aplicação

Uma aplicação web tem sempre as mesmas necessidades: guardar dados, identificar quem está usando, servir arquivos e responder a requisições. O que muda entre uma arquitetura e outra é **quem executa cada uma dessas partes**.

O diagrama abaixo contrasta os dois caminhos que este guia e o [Guia de Express.js](../expressjs/) cobrem, a partir do mesmo front-end:

<Mermaid title="Back-end próprio e Backend as a Service a partir do mesmo front-end">
{`
flowchart TD
  A["Front-end<br/>navegador"] --> B["Back-end próprio<br/>Express, rotas e regras"]
  A --> C["Plataforma BaaS<br/>SDK ou HTTP"]
  B --> D["Banco de dados<br/>que você opera"]
  B --> E["Autenticação<br/>que você escreve"]
  C --> F["Banco gerenciado<br/>Postgres ou Firestore"]
  C --> G["Auth gerenciada<br/>sessões e tokens"]
  C --> H["Storage e tempo real<br/>arquivos e assinaturas"]
`}
</Mermaid>

Os dois caminhos resolvem o mesmo problema com custos diferentes. No back-end próprio, cada rota é código que você escreve, testa e mantém, e nada acontece sem que você tenha escrito. No BaaS, a rota já existe assim que a tabela existe, e a segurança passa a depender inteiramente da configuração: uma política de acesso ausente no Supabase ou uma regra permissiva no Firestore expõe os dados diretamente ao navegador.

| Responsabilidade | Com back-end próprio | Com BaaS |
| --- | --- | --- |
| **Rotas da API** | Você escreve cada rota e seu contrato. | A plataforma gera a partir do esquema de dados. |
| **Autenticação** | Você implementa hash, sessão e emissão de token. | O serviço emite e valida o token; você só o consome. |
| **Autorização** | Middleware no servidor, sob seu controle. | Políticas declarativas (RLS, Security Rules) na plataforma. |
| **Chave de acesso** | Segredo fica no servidor, nunca no navegador. | A chave pública viaja no front-end, então a política é a única defesa. |
| **Custo** | Servidor e banco que você provisiona. | Cobrança por uso, com limites que escalam sozinhos. |

Na prática, a pergunta que decide entre os dois não é "qual é mais moderno", e sim quanto da lógica de negócio precisa rodar em um lugar em que o usuário não possa interferir.

## Roteiro Sugerido de Estudos

Cada plataforma é autocontida, então é possível estudar apenas a que o projeto usa. Se o objetivo é comparar BaaS, comece pelo Supabase e pelo Firebase. Se o objetivo é publicação de front-end, vá para Vercel, Netlify, Cloudflare e a página de hospedagem estática da seção Recursos. Se o objetivo é publicar uma API própria, siga por Render, Railway e pelas outras plataformas de PaaS e containers. Quando o foco for código de aplicação, use a seção **Na Prática**.

<Steps>
1. **Vocabulário e fronteiras**: Comece por [Computação em Nuvem](foundations/cloud-computing/), [Comparação de Serviços](foundations/service-comparison/) e [Backend as a Service](foundations/baas/) para saber o que cada modelo terceiriza, quais recursos aparecem em cada plataforma e onde o BaaS para.
2. **Um recurso de cada vez**: Passe pela seção Recursos, de [Hospedagem Estática](resources/static-hosting/) a [Containers e PaaS](resources/containers-paas/), para conhecer cada serviço atravessando as plataformas antes de escolher uma.
3. **Panorama da plataforma**: Leia a [visão geral do Supabase](supabase/), a [visão geral do Firebase](firebase/), a [visão geral da Vercel](vercel/), a [visão geral do Netlify](netlify/), [Cloudflare](cloudflare/) ou [AWS Amplify](amplify/) para conhecer os serviços que cada uma reúne.
4. **Dados e identidade**: No Supabase, siga por [Database API](supabase/api/) e [Supabase Auth](supabase/auth/). No Firebase, siga por [Cloud Firestore](firebase/firestore/) e [Firebase Auth](firebase/auth/).
5. **Arquivos e eventos**: Complete o BaaS com [Supabase Storage](supabase/storage/), [Supabase Realtime](supabase/realtime/), [Cloud Storage](firebase/storage/) e [Cloud Functions](firebase/functions/).
6. **Publicação de front-end**: Coloque a aplicação no ar com [Hospedagem Estática](resources/static-hosting/), [Vercel Deployments](vercel/deployments/), [Netlify Deployments](netlify/deployments/) ou [Cloudflare](cloudflare/), e acrescente [Funções Serverless](resources/serverless-functions/) quando algum segredo não puder chegar ao navegador.
7. **Back-end próprio**: Use [Render](render/) e [Railway](railway/) quando a aplicação tiver API Express, worker, cron job ou banco próprio, e consulte [Outras Plataformas](reference/other-platforms/) para Fly.io, Heroku, Cloud Run, Azure Static Web Apps, GitHub Pages, Appwrite e PocketBase.
8. **Aplicação incremental**: Use [InvestApp Cloud](practice/investapp/) para estudar código, variáveis de ambiente, módulos de serviço e decisões de segurança em etapas cumulativas.
9. **Consulta rápida**: Use o [Mapa de Plataformas](reference/platform-map/) para justificar a escolha antes de começar um projeto novo.
</Steps>
