O **Supabase Auth** é o serviço integrado de gestão de identidades e autenticação do Supabase. Ele fornece autenticação completa por e-mail/senha, links mágicos de acesso (*Magic Links*), provedores sociais (Google, GitHub, Apple) e emissão automática de tokens **JWT** (*JSON Web Tokens*) integrados diretamente com as políticas de segurança RLS do PostgreSQL.

## Objetivo

Construir o ciclo completo de autenticação de uma aplicação com o Supabase Auth, do cadastro do usuário à política que amarra cada linha da tabela ao dono dela, entendendo que identidade e autorização são duas etapas distintas do mesmo fluxo. Ao final do tópico, o leitor deve ser capaz de:

- Implementar cadastro, login e logout com `signUp`, `signInWithPassword` e `signOut`.
- Reagir a mudanças de sessão com `onAuthStateChange` em vez de consultar o estado manualmente.
- Explicar como o token JWT chega ao PostgreSQL e vira `auth.uid()` dentro de uma política.
- Escrever a política RLS que restringe cada linha ao usuário que a criou.
- Reconhecer por que autenticar no front-end não protege dado algum sem a política correspondente.

## Arquitetura de Autenticação do Supabase

O Supabase Auth lida com a emissão e renovação automática dos tokens JWT no cliente:

<Mermaid title="Fluxo de Autenticação com Supabase Auth">
{`
flowchart TD
  User["Usuário (Formulário de Login)"] -- "email + senha" --> SDK["supabase.auth.signInWithPassword()"]
  SDK -- "Autentica via GoTrue API" --> AuthServer["Supabase Auth Server"]
  AuthServer -- "Retorna JWT AccessToken + User Object" --> SDK
  SDK -- "Persiste JWT no localStorage" --> Browser["Sessão Ativa no Navegador"]
  Browser -- "Requisições com Header Authorization: Bearer JWT" --> Postgres[(PostgreSQL com RLS auth.uid())]
`}
</Mermaid>

<Aside type="tip" title="Integração com RLS no Banco de Dados">
Quando um usuário se autentica com o Supabase Auth, o token JWT gerado carrega a chave `auth.uid()`. Essa chave é lida diretamente pelo PostgreSQL nas regras de RLS, permitindo criar políticas como: *"O usuário só pode ver e alterar os seus próprios investimentos"*.
</Aside>

## 1. Métodos de Autenticação no Front-End

### Cadastro de Novo Usuário (`signUp`)

O método `signUp` cria um novo usuário no banco de dados do Supabase (`auth.users`):

```js title="Cadastrando um usuário com e-mail e senha"
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  import.meta.env.VITE_APP_SUPABASE_URL,
  import.meta.env.VITE_APP_SUPABASE_KEY
);

async function cadastrarUsuario(email, password) {
  const { data, error } = await supabase.auth.signUp({
    email: email,
    password: password,
  });

  if (error) {
    console.error('Erro ao cadastrar:', error.message);
    return null;
  }

  console.log('Usuário criado com sucesso:', data.user);
  return data.user;
}
```

---

### Autenticação com E-mail e Senha (`signInWithPassword`)

O método `signInWithPassword` valida as credenciais e armazena automaticamente a sessão JWT no cliente:

```js title="Realizando o login de um usuário"
async function realizarLogin(email, password) {
  const { data, error } = await supabase.auth.signInWithPassword({
    email: email,
    password: password,
  });

  if (error) {
    console.error('Falha no login:', error.message);
    throw error;
  }

  console.log('Sessão iniciada:', data.session);
  return data.user;
}
```

---

### Encerrar Sessão (`signOut`)

O método `signOut` invalida a sessão atual e limpa os tokens armazenados localmente:

```js title="Realizando o logout do usuário"
async function realizarLogout() {
  const { error } = await supabase.auth.signOut();

  if (error) {
    console.error('Erro ao encerrar sessão:', error.message);
  } else {
    console.log('Sessão encerrada com sucesso.');
    window.location.href = '/login';
  }
}
```

## 2. Verificação de Usuário Ativo e Escuta de Eventos

### Obter o Usuário Atual (`getUser`)

Para verificar se existe um usuário logado na inicialização da página:

```js title="Verificando se o usuário está autenticado"
async function verificarUsuarioLogado() {
  const { data: { user }, error } = await supabase.auth.getUser();

  if (error || !user) {
    console.log('Nenhum usuário autenticado.');
    return null;
  }

  console.log('Usuário ativo:', user.email);
  return user;
}
```

### Escutando Mudanças de Sessão em Tempo Real (`onAuthStateChange`)

Utilize `onAuthStateChange` para reagir automaticamente a eventos de login, logout e renovação de token:

```js title="Escutando eventos de autenticação"
supabase.auth.onAuthStateChange((event, session) => {
  console.log('Evento de Autenticação:', event);

  if (event === 'SIGNED_IN') {
    console.log('Usuário logou:', session.user.email);
  } else if (event === 'SIGNED_OUT') {
    console.log('Usuário deslogou');
  }
});
```

## 3. Protegendo Dados com RLS e `auth.uid()`

Para vincular os registros de uma tabela ao usuário logado, adicione uma coluna `user_id` na tabela e aplique uma regra de RLS:

```sql title="Criando tabela de tarefas vinculada ao usuário"
create table todos (
  id uuid default gen_random_uuid() primary key,
  user_id uuid references auth.users(id) default auth.uid(),
  title text not null,
  completed boolean default false
);

-- Habilita RLS na tabela
alter table todos enable row level security;

-- Política: Usuário só pode acessar seus próprios registros
create policy "Usuários gerenciam suas próprias tarefas"
  on todos
  for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

<Aside type="caution" title="Dica de IA: Esconder a tela não protege a tabela">
  Pedir "proteja a área logada do meu app Supabase" costuma render um `if (!session) location.href = '/login'` e nada mais. Esse desvio é interface: quem abrir o console do navegador, ou chamar a URL do PostgREST direto, continua lendo a tabela inteira enquanto a política RLS não existir. O `using` e o `with check` acima são a proteção real; o redirecionamento apenas evita uma tela vazia.

  **Prompt:** *"Assumindo a tabela `todos` com `user_id` e a política que compara `auth.uid() = user_id`, escreva os passos para eu tentar ler as linhas de outro usuário direto pela API REST, e diga qual resposta HTTP prova que a política está ativa."*
</Aside>

## Quando usar, e quando não usar?

O Supabase Auth resolve identidade, e identidade é só metade do problema. A outra metade é a autorização, que continua sendo escrita por você em SQL. Vale medir a escolha contra as duas alternativas: escrever a autenticação à mão em um servidor próprio, ou usar um provedor de identidade dedicado.

A tabela abaixo indica a escolha por cenário:

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Aplicação de front-end que já usa o banco do Supabase | **Supabase Auth** | O mesmo token vale para o banco: `auth.uid()` chega às políticas sem integração extra. |
| Login social ou *magic link* sem infraestrutura de e-mail | **Supabase Auth** | Provedores e envio de e-mail vêm configurados no console. |
| Regras de sessão próprias, SSO corporativo, SAML, MFA elaborado | **Provedor de identidade dedicado** | Fluxos federados complexos estão fora do que o serviço cobre bem. |
| API própria que precisa validar o usuário | **Back-end próprio** ([Guia de Express.js](../../../expressjs/)) | O servidor precisa verificar a assinatura do JWT; o token do cliente não é prova por si só. |
| Exigência de guardar as credenciais na sua infraestrutura | **Autenticação própria ou auto-hospedagem** | O GoTrue é open-source e pode subir junto do restante da pilha auto-hospedada. |

## Desafio

Uma aplicação com autenticação tem estados que o formulário de login não revela: sessão ausente, sessão válida, sessão expirada enquanto a aba estava aberta, e usuário que fez logout em outra aba. Implemente uma camada de sessão que trate os quatro.

O módulo deve expor `getSession()`, `login()`, `logout()` e uma função que registre um ouvinte de mudanças, mantendo o cabeçalho da página sincronizado com o estado atual sem que nenhum componente consulte o `localStorage` diretamente. Descreva também como você testaria o caso da expiração sem esperar o token vencer.

<details>
  <summary>Possível resposta</summary>

  O `onAuthStateChange` é o centro da solução, porque ele dispara nos quatro casos, inclusive quando outra aba encerra a sessão:

  ```js title="Esboço do módulo de sessão"
  const listeners = new Set();

  supabase.auth.onAuthStateChange((event, session) => {
    for (const listener of listeners) {
      listener({ event, user: session?.user ?? null });
    }
  });

  export function onSessionChange(listener) {
    listeners.add(listener);
    return () => listeners.delete(listener);
  }
  ```

  Os eventos que importam são `SIGNED_IN`, `SIGNED_OUT` e `TOKEN_REFRESHED`; a expiração aparece como uma renovação bem-sucedida ou, quando o *refresh token* também venceu, como um `SIGNED_OUT`. Para testar sem esperar, reduza o tempo de vida do token nas configurações de autenticação do projeto, ou apague a chave da sessão no `localStorage` e force uma chamada ao banco: a resposta `401` é o que a interface precisa tratar.
</details>
