O **Supabase Auth** gerencia identidade: cadastro, login, sessão, provedores externos e emissão de tokens. A autorização dos dados acontece quando esse token chega ao PostgreSQL e é usado em políticas RLS.

## Objetivo

Compreender Supabase Auth como serviço de identidade integrado ao banco, separando autenticação, sessão e autorização para evitar a falsa sensação de segurança de apenas esconder telas. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar autenticação e autorização.
- Explicar como o JWT emitido pelo Auth chega ao PostgreSQL.
- Usar `auth.uid()` como base de políticas por usuário.
- Reconhecer quando login social, link mágico ou e-mail/senha faz sentido.
- Decidir quando Auth gerenciado não basta e um provedor dedicado é necessário.

## Modelo Mental

O usuário entra pelo Supabase Auth. O cliente recebe uma sessão com token. Nas chamadas ao banco, esse token acompanha a requisição e permite que o PostgreSQL descubra o usuário por `auth.uid()`.

<Mermaid title="Identidade do Supabase Auth aplicada por RLS no PostgreSQL">
{`
sequenceDiagram
  participant User as Usuário
  participant Client as Aplicação
  participant Auth as Supabase Auth
  participant DB as PostgreSQL com RLS
  User->>Client: e-mail e senha
  Client->>Auth: login
  Auth-->>Client: sessão com JWT
  Client->>DB: consulta com Authorization
  DB->>DB: auth.uid() na política
  DB-->>Client: apenas linhas permitidas
`}
</Mermaid>

A tela de login melhora a experiência. A política RLS protege o dado. As duas coisas se complementam, mas não são equivalentes.

## Recursos Principais

O Auth cobre fluxos comuns de identidade e entrega um token que outros serviços do Supabase entendem.

| Recurso | O que entrega | Quando usar |
| --- | --- | --- |
| **E-mail e senha** | Cadastro e login tradicionais | Aplicações educacionais, internas e MVPs. |
| **Magic link e OTP** | Entrada sem senha | Produtos em que reduzir fricção vale mais que senha local. |
| **Provedores sociais** | Login com Google, GitHub, Apple e outros | Quando o usuário já tem identidade externa confiável. |
| **JWT de sessão** | Identidade em chamadas ao banco e funções | Base para RLS, Storage e chamadas serverless. |
| **Hooks e templates** | Ajustes em e-mails e eventos | Fluxos de confirmação e recuperação. |

## Pequenos Trechos

O login é só a criação da sessão. O código abaixo não protege tabela nenhuma sozinho:

```js title="Login com e-mail e senha"
const { data, error } = await supabase.auth.signInWithPassword({
  email,
  password,
});

if (error) {
  throw new Error('E-mail ou senha inválidos.');
}

return data.user;
```

A proteção dos dados aparece na política. O exemplo a seguir permite que cada usuário leia apenas as próprias linhas:

```sql title="Política RLS por dono"
alter table investments enable row level security;

create policy "Users read their investments"
  on investments
  for select
  using (auth.uid() = user_id);
```

Para manter a interface sincronizada, a aplicação observa mudanças de sessão:

```js title="Ouvinte de sessão"
supabase.auth.onAuthStateChange((event, session) => {
  const user = session?.user ?? null;
  updateHeader({ event, user });
});
```

<Aside type="caution" title="Dica de IA: Esconder rota não é autorização">
  Assistentes costumam responder "proteja a página" com redirecionamento para login. Isso ajuda
  a navegação, mas não impede acesso direto pela Database API se a tabela estiver sem RLS.

  **Prompt:** *"Além do redirecionamento para `/login`, escreva as políticas RLS necessárias para `investments` e mostre como testar uma leitura direta tentando acessar dados de outro usuário."*
</Aside>

## Aplicações

Supabase Auth é especialmente forte quando a mesma identidade precisa proteger banco, Storage e funções dentro do projeto Supabase.

| Aplicação | Como Auth ajuda | Cuidado |
| --- | --- | --- |
| CRUD por dono | `auth.uid()` simplifica RLS. | A tabela precisa de coluna de dono. |
| Upload privado | A sessão alimenta políticas de Storage. | Caminho do arquivo precisa refletir posse. |
| Função serverless autenticada | JWT pode ser validado antes da ação. | Função administrativa deve validar explicitamente. |
| SSO corporativo complexo | Pode exigir provedor dedicado. | Regras de organização e MFA podem extrapolar o básico. |

## Quando Usar, e Quando Não Usar?

Use Supabase Auth quando o projeto já usa Supabase como BaaS e as regras de acesso cabem em RLS e políticas de Storage. Avalie outro provedor quando o produto exige SAML, governança corporativa complexa, múltiplas organizações ou controles avançados de sessão.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| App com PostgreSQL no Supabase | **Supabase Auth** | O token conversa diretamente com RLS. |
| Login social em MVP | **Supabase Auth** | Provedores comuns ficam no console. |
| Multi-tenant corporativo complexo | **Provedor dedicado ou back-end próprio** | Papéis, organizações e auditoria podem ficar grandes demais. |
| Regra sensível de pagamento | **Edge Function com validação** | Login identifica; a ação sensível ainda precisa de servidor. |

## Exercício

Explique a diferença entre usuário autenticado e usuário autorizado a ler uma linha da tabela.

<details>
  <summary>Possível resposta</summary>

  Usuário autenticado tem identidade confirmada e sessão válida. Usuário autorizado é aquele que passa pela política aplicada ao recurso, por exemplo uma linha com `user_id = auth.uid()`.
</details>

## Desafio

Projete as políticas de uma tabela `investments` com `user_id`, permitindo leitura, criação, atualização e remoção apenas pelo dono.

<details>
  <summary>Possível resposta</summary>

  A política de leitura usa `using (auth.uid() = user_id)`. Criação e atualização precisam de `with check (auth.uid() = user_id)`, para impedir que um usuário grave uma linha atribuída a outro.
</details>

## Perguntas de revisão

1. **O que `auth.uid()` representa dentro de uma política RLS?**
   <details>
     <summary>Possível resposta</summary>
     O identificador do usuário autenticado, extraído do JWT enviado na requisição.
   </details>

2. **Por que autenticação no front-end não basta para proteger dados?**
   <details>
     <summary>Possível resposta</summary>
     Porque o front-end é controlado pelo usuário. A proteção precisa estar no serviço que entrega os dados, como RLS no PostgreSQL.
   </details>
