O **Supabase** é uma plataforma de **Backend as a Service (BaaS)** open-source criada como alternativa ao Firebase. Diferente de plataformas NoSQL fechadas, o Supabase é construído sobre o **PostgreSQL**, o banco de dados relacional mais avançado do mercado, entregando automaticamente APIs REST/GraphQL, autenticação de usuários, escuta em tempo real (*Realtime*) e armazenamento de arquivos.

## Objetivo

Compreender a arquitetura open-source do Supabase, do banco PostgreSQL que sustenta a plataforma até os serviços que ela deriva desse banco, para decidir com critério quando adotar a plataforma em um projeto. Ao final do tópico, o leitor deve ser capaz de:

- Explicar por que o PostgreSQL está no centro da arquitetura e o que isso muda em relação a um BaaS NoSQL.
- Identificar o papel de cada serviço da plataforma: *PostgREST*, *GoTrue*, *Realtime* e *Storage*.
- Diferenciar Supabase e Firebase quanto a modelo de dados, segurança, APIs geradas e portabilidade.
- Reconhecer os cenários em que um BaaS é a escolha errada e um back-end próprio se justifica.

## A Filosofia do Supabase: PostgreSQL no Coração

Enquanto a maioria das plataformas de BaaS tradicionais utilizam bancos de dados proprietários ou estruturas NoSQL orientadas a documentos, o Supabase fornece um **banco de dados PostgreSQL dedicado e completo** para cada projeto:

<Mermaid title="Arquitetura de Serviços da Plataforma Supabase">
{`
flowchart TD
  Client["Aplicação Front-End (Web / Mobile)"] -- "Requisições HTTP / SDK JS" --> Gate["Supabase Gateway"]
  
  subgraph Stack["Ecossistema Supabase (Open Source)"]
    Gate --> PostgREST["PostgREST (Gera REST API Automática)"]
    Gate --> AuthServer["GoTrue (Servidor de Auth & JWT)"]
    Gate --> Realtime["Realtime Engine (WebSockets CDC)"]
    Gate --> Storage["Storage API (Buckets & Arquivos)"]
  end

  PostgREST --> Postgres[(Banco de Dados PostgreSQL)]
  AuthServer --> Postgres
  Realtime --> Postgres
  Storage --> Postgres
`}
</Mermaid>

<Aside type="tip" title="Sem Lock-in de Fornecedor">
Como o Supabase utiliza o PostgreSQL padrão, você tem controle total sobre o banco de dados: pode importar esquemas SQL convencionais, criar índices, funções PL/pgSQL e migrar os dados para qualquer outro servidor Postgres a qualquer momento.
</Aside>

## Comparativo: Supabase vs Firebase

As duas plataformas resolvem o mesmo problema a partir de premissas opostas, e a tabela abaixo isola as cinco diferenças que mais afetam um projeto. Leia a linha do banco de dados primeiro: ela é a que condiciona todas as outras.

| Característica | Supabase | Firebase |
| --- | --- | --- |
| **Código** | 100% Open Source | Código Proprietário (Nuvem Google) |
| **Banco de Dados** | **PostgreSQL** (Relacional, SQL puro, Junções) | **Cloud Firestore** (NoSQL, Documentos JSON) |
| **Segurança de Dados** | **Row Level Security (RLS)** nativo no Postgres | **Security Rules** proprietárias no console |
| **APIs Geradas** | REST (PostgREST) e GraphQL (pg_graphql) | SDKs proprietários |
| **Portabilidade** | Pode ser executado localmente via Docker ou auto-hospedado | Restrito à infraestrutura na nuvem do Google |

## Quando usar, e quando não usar?

O Supabase compensa quando o valor do projeto está nos dados e nas telas, não na lógica entre eles. Ele deixa de compensar no momento em que a regra de negócio precisa rodar em um lugar que o usuário não alcança, porque a chave que o front-end carrega é pública e a única defesa passa a ser a política de acesso escrita no banco.

A tabela abaixo confronta cada cenário com a alternativa que vence nele:

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Protótipo ou MVP que precisa de banco e login em dias | **Supabase** | Tabela criada é rota pronta; a autenticação já vem integrada às políticas do banco. |
| Aplicação de front-end com CRUD e consultas relacionais | **Supabase** | O PostgREST expressa junções, filtros e paginação sem uma linha de servidor. |
| Regra de negócio cara, sigilosa ou com integração a terceiros | **Back-end próprio** ([Guia de Express.js](../../expressjs/)) | O segredo e a decisão ficam no servidor, fora do alcance do navegador. |
| Processamento pesado, agendado ou de longa duração | **Back-end próprio ou fila** | A plataforma cobra e limita por requisição, e não substitui um processo em segundo plano. |
| Equipe sem quem escreva SQL e políticas de acesso | **Firebase** ([visão geral](../firebase/)) | O modelo de documentos e as *Security Rules* pedem menos conhecimento de banco relacional. |
| Dado sob exigência regulatória de residência ou auditoria | **Auto-hospedagem** | O Supabase pode ser executado na sua própria infraestrutura, sem depender da nuvem gerenciada. |

## Desafio

Escolher a plataforma é uma decisão de arquitetura, e ela se defende por escrito. Pegue um projeto seu, real ou imaginado, com pelo menos duas entidades relacionadas e usuários que só podem ver os próprios dados.

Escreva uma página de decisão que responda a quatro perguntas: qual seria o modelo de dados no Supabase e como ele ficaria no Firestore; onde cada regra de autorização seria expressa nas duas plataformas; que parte do sistema, se existir, ainda precisaria de um servidor próprio; e qual seria o custo de sair da plataforma escolhida daqui a dois anos.

<details>
  <summary>Possível resposta</summary>

  Uma decisão bem escrita costuma chegar a três conclusões. **O modelo de dados decide primeiro**: entidades relacionadas com consultas que cruzam tabelas pedem SQL, enquanto dados hierárquicos lidos sempre em bloco cabem bem em documentos. **A autorização mora em lugares diferentes**: no Supabase é uma política RLS que compara `auth.uid()` com uma coluna da tabela; no Firestore é uma regra declarativa por caminho de documento. **O servidor próprio reaparece** sempre que existe segredo (uma chave de API de terceiros), cobrança, ou uma regra que não pode ser reimplementada pelo cliente. Sobre a saída, o Supabase entrega um `pg_dump` que qualquer PostgreSQL importa; do Firestore sai um export proprietário que precisa ser convertido antes de virar tabelas.
</details>

## Perguntas de revisão

1. **Qual é a vantagem do Row Level Security (RLS) do PostgreSQL em relação a validações no código do servidor?**
   <details>
     <summary>Possível resposta</summary>
     O RLS aplica as políticas de segurança diretamente no motor do banco de dados. Qualquer tentativa de acessar ou alterar linhas sem autorização é bloqueada pelo próprio Postgres, independentemente de a chamada vir do client-side ou de uma API.
   </details>

2. **Como o Supabase permite executar projetos localmente durante o desenvolvimento?**
   <details>
     <summary>Possível resposta</summary>
     Através da CLI do Supabase (`supabase init` / `supabase start`), que sobe todo o ecossistema (Postgres, PostgREST, Auth, Storage) em contêineres Docker no seu computador.
   </details>
