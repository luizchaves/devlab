O **Supabase** é uma plataforma de *Backend as a Service* (BaaS) open-source construída sobre o poderoso banco de dados relacional **PostgreSQL**. Um dos seus maiores recursos é a geração automática de uma **API RESTful de altíssimo desempenho** através do motor **PostgREST**, permitindo consultar, inserir, atualizar e remover dados do banco diretamente via requisições HTTP sem escrever código no servidor.

## Objetivo

Compreender como uma tabela do PostgreSQL vira uma API REST sem nenhuma linha de servidor, da criação do esquema à política que autoriza cada linha, exercitando as quatro operações por HTTP puro antes de qualquer SDK entrar em cena. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o papel do PostgREST entre o cliente HTTP e o banco de dados.
- Criar a tabela e a política *Row Level Security* que a torna acessível.
- Traduzir operadores SQL em filtros de URL (`eq`, `gt`, `select`) do PostgREST.
- Executar as operações de criação, leitura, atualização e remoção com `curl` e arquivos `.http`.
- Escolher o cabeçalho `Prefer` adequado ao que a aplicação precisa receber de volta.

## Arquitetura do Supabase API

O PostgREST lê o esquema das tabelas do PostgreSQL e expõe endpoints HTTP nativos instantaneamente:

<Mermaid title="Arquitetura de API Automática do Supabase com PostgREST">
{`
flowchart TD
  Client["Cliente HTTP (cURL / REST Client / Front-End)"] -- "GET /rest/v1/investments?value=gt.10000" --> PostgREST["Engine PostgREST (Supabase)"]
  PostgREST -- "Valida Permissões RLS" --> RLS["Row Level Security Policy"]
  RLS -- "Executa Consulta SQL Nativa" --> Postgres[(Banco de Dados PostgreSQL)]
  Postgres -- "Retorna Linhas em JSON" --> Client
`}
</Mermaid>

<Aside type="tip" title="Serverless e Instantâneo">
Qualquer tabela ou visão (*view*) criada no painel do Supabase torna-se imediatamente um endpoint REST documentado com suporte a filtros, ordenação e relatórios.
</Aside>

## 1. Criando a Tabela no Banco de Dados

No dashboard do Supabase (**Table Editor** ou **SQL Editor**), executamos o script DDL para criar a tabela de investimentos do projeto `invest-app`:

```sql title="Criação da tabela investments no PostgreSQL"
create table investments (
  id uuid not null default gen_random_uuid (),
  name character varying null,
  value bigint null,
  origin character varying null,
  category character varying null,
  interest character varying null,
  created_at timestamp with time zone not null default now(),
  constraint investments_pkey primary key (id)
);
```

Com a tabela criada, vale inserir alguns registros de teste, para que as consultas das próximas seções tenham o que devolver:

```sql title="Inserindo registros iniciais para teste"
insert into investments (name, value, origin, category, interest)
values
  ('Tesouro Selic 2029', 100000, 'Tesouro Nacional', 'Pós', '100% Selic'),
  ('Tesouro IPCA 2029', 10000, 'Tesouro Nacional', 'Pós', 'IPCA + 6,10%');
```

## 2. Configurando Permissões de Acesso (RLS)

Por padrão, o Supabase bloqueia todas as requisições públicas às tabelas por motivos de segurança através do **Row Level Security (RLS)**. Para permitir o acesso de leitura/escrita anônima em nosso ambiente de estudo, criamos uma política permissiva:

```sql title="Habilitando política de acesso público no RLS"
CREATE POLICY "Allow public access"
  ON "public"."investments"
  FOR ALL
  TO public
  USING (true)
  WITH CHECK (true);
```

<Aside type="caution" title="Dica de IA: Uma política permissiva é ambiente de estudo, não configuração de produção">
  A política acima libera leitura e escrita para qualquer pessoa que tenha a chave anônima, que viaja no front-end e é pública por natureza. Assistentes tendem a reproduzir exatamente esse `USING (true)` quando o pedido é "resolva o erro de permissão do Supabase", porque ele de fato faz o erro sumir, e com ele a única defesa da tabela.

  **Prompt:** *"Reescreva esta política RLS da tabela `investments` para que cada usuário autenticado só leia e altere as próprias linhas usando `auth.uid()`; liste as consultas que passam a falhar e o que precisa mudar na tabela."*
</Aside>

## 3. Mapeamento de Rotas e Filtros de URL (PostgREST)

O PostgREST mapeia os operadores de comparação SQL diretamente em parâmetros de consulta na URL:

| Método | Caminho da URL | Status | Operação Realizada |
| --- | --- | --- | --- |
| **`POST`** | `/rest/v1/investments` | `201` | Cria um novo registro de investimento |
| **`GET`** | `/rest/v1/investments?select=*` | `200` | Retorna todos os investimentos e todas as colunas |
| **`GET`** | `/rest/v1/investments?value=gt.10000` | `200` | Filtra investimentos com valor maior que 10.000 (`gt`) |
| **`GET`** | `/rest/v1/investments?id=eq.1` | `200` | Filtra investimento pelo campo `id` igual a 1 (`eq`) |
| **`PATCH`** | `/rest/v1/investments?id=eq.1` | `200` | Atualiza parcialmente o investimento 1 |
| **`DELETE`** | `/rest/v1/investments?id=eq.1` | `204` | Exclui o investimento com `id` igual a 1 |

## Quando usar, e quando não usar?

Falar com o PostgREST por HTTP puro é a forma mais direta de entender o que a plataforma expõe, e continua útil bem depois do aprendizado. O limite aparece quando a chamada precisa de sessão de usuário, de reação a mudanças ou de uma consulta que a URL não expressa.

A tabela abaixo mostra onde cada caminho ganha:

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Explorar a API, testar filtros, documentar o contrato | **`.http` ou `curl`** | Nenhuma dependência instalada, e a requisição inteira fica visível e versionável. |
| Integrar de uma linguagem sem SDK oficial | **API REST** | Qualquer cliente HTTP serve; o contrato é o próprio PostgREST. |
| CRUD do front-end com usuário autenticado | **[Supabase Client](../client/)** | O SDK anexa e renova o token da sessão a cada chamada. |
| Reagir a mudanças na tabela sem recarregar | **[Supabase Client](../client/)** | O canal Realtime não existe na API REST. |
| Consulta com lógica que a URL não expressa | **Função SQL (RPC)** | A regra fica no banco e é chamada por uma única rota `/rest/v1/rpc/…`. |

## Desafio

Os filtros vistos até aqui cobrem igualdade e comparação, mas o PostgREST vai bem além disso. Monte uma coleção `.http` com cinco requisições que a página não mostrou, cada uma resolvendo uma pergunta de negócio da carteira de investimentos.

As perguntas são: quais investimentos têm valor entre 5.000 e 50.000; quais pertencem às categorias `Pós` ou `Fixa`; quais têm no nome a palavra "Tesouro", sem diferenciar maiúsculas; os cinco maiores valores em ordem decrescente; e quantos investimentos existem por categoria, sem trazer as linhas.

<details>
  <summary>Possível resposta</summary>

  As quatro primeiras saem de operadores e modificadores da própria URL:

  ```http title="Esboço das requisições"
  GET {{host}}/rest/v1/investments?value=gte.5000&value=lte.50000
  GET {{host}}/rest/v1/investments?category=in.("Pós","Fixa")
  GET {{host}}/rest/v1/investments?name=ilike.*Tesouro*
  GET {{host}}/rest/v1/investments?select=name,value&order=value.desc&limit=5
  ```

  A quinta é a que revela o limite do formato: agregação por grupo não cabe em parâmetros de URL. A saída é criar uma visão (`create view investments_by_category as select category, count(*) …`), que o PostgREST publica como uma nova rota, ou uma função SQL chamada por `POST /rest/v1/rpc/…`. A regra continua morando no banco, e a URL só a invoca.
</details>

## Perguntas de revisão

1. **Qual é o papel do motor PostgREST na arquitetura do Supabase?**
   <details>
     <summary>Possível resposta</summary>
     O PostgREST lê a estrutura de tabelas, visões e relacionamentos do PostgreSQL e gera automaticamente uma API RESTful de alta performance sem necessidade de backend customizado.
   </details>

2. **Para que serve o cabeçalho `Prefer: return=representation` em uma requisição `POST`?**
   <details>
     <summary>Possível resposta</summary>
     Ele instrui o PostgREST a retornar o registro recém-criado no corpo da resposta HTTP (incluindo o `id` e campos auto-gerados como `created_at`).
   </details>
