A **Database API** do Supabase é a camada HTTP gerada a partir do PostgreSQL. Tabelas, visões e funções SQL viram endpoints REST, e toda chamada continua passando pelas permissões do banco, especialmente pelas políticas de *Row Level Security* (RLS).

## Objetivo

Compreender a Database API como uma interface sobre o PostgreSQL, não como um servidor separado escrito à mão, para decidir quando consumir dados direto do cliente e quando mover a regra para SQL, função ou back-end próprio. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o papel do PostgREST na exposição de tabelas, visões e funções.
- Ler uma URL da Database API como uma consulta filtrada.
- Relacionar `apikey`, JWT de usuário e políticas RLS.
- Reconhecer operações que pedem RPC, Edge Function ou back-end próprio.
- Diferenciar guia de serviço e etapa prática do InvestApp.

## Modelo Mental

O PostgREST lê o esquema do banco e transforma recursos do PostgreSQL em recursos HTTP. A aplicação chama uma URL; o Supabase autentica a requisição; o PostgreSQL aplica permissões; o resultado volta como JSON.

<Mermaid title="Fluxo de uma requisição pela Database API do Supabase">
{`
flowchart TD
  Browser["Cliente HTTP<br/>SDK, fetch ou curl"] --> Gateway["Supabase Gateway"]
  Gateway --> PostgREST["PostgREST<br/>traduz HTTP para SQL"]
  PostgREST --> RLS["RLS e permissões<br/>no PostgreSQL"]
  RLS --> Database[(PostgreSQL)]
  Database --> PostgREST
  PostgREST --> Browser
`}
</Mermaid>

Esse desenho muda a responsabilidade do projeto. A rota deixa de ser código Express, mas a autorização não desaparece. Ela passa a morar no banco.

## Recursos Principais

A Database API cobre bem CRUD, filtros, ordenação, paginação, projeção de colunas, relacionamentos conhecidos pelo banco e chamadas RPC para funções SQL.

A tabela abaixo separa os recursos pelo tipo de decisão que o desenvolvedor precisa tomar:

| Recurso | O que resolve | Cuidado |
| --- | --- | --- |
| **Endpoint por tabela** | CRUD direto em `/rest/v1/<tabela>` | Sem RLS correta, a chave pública expõe dados. |
| **Filtros de URL** | Igualdade, comparação, busca por padrão e ordenação | A URL vira parte do contrato da aplicação. |
| **Projeção com `select`** | Reduzir colunas e carregar relações | Selecionar tudo é simples, mas pode vazar campo desnecessário. |
| **RPC** | Executar função SQL por HTTP | Boa para regra dentro do banco, ruim para regra que chama serviços externos. |
| **Headers `Prefer`** | Controlar retorno de escrita | Criar sem retorno é mais leve; criar com representação facilita a interface. |

## Pequenos Trechos

O exemplo abaixo mostra a forma mínima de uma leitura. O ponto importante é o filtro `category=eq.Renda%20Fixa`, que representa a condição aplicada pelo PostgREST:

```http title="Leitura filtrada pela Database API"
GET https://seu-projeto.supabase.co/rest/v1/investments?select=id,name,amount&category=eq.Renda%20Fixa
apikey: sua_anon_key
Authorization: Bearer jwt_do_usuario
```

Uma escrita que precisa do registro final usa `Prefer: return=representation`. Isso é útil quando o banco gera `id`, `created_at` ou valores padrão:

```http title="Criação retornando a linha gravada"
POST https://seu-projeto.supabase.co/rest/v1/investments
apikey: sua_anon_key
Authorization: Bearer jwt_do_usuario
Content-Type: application/json
Prefer: return=representation

{ "name": "Tesouro Selic", "amount": 10000, "category": "Renda Fixa" }
```

Quando a regra é uma operação de banco, uma função SQL pode virar rota RPC:

```sql title="Função SQL exposta por RPC"
create function portfolio_total(owner_id uuid)
returns numeric
language sql
stable
as $$
  select coalesce(sum(amount), 0)
  from investments
  where user_id = owner_id;
$$;
```

<Aside type="caution" title="Dica de IA: A política é parte do exemplo, não rodapé">
  Código gerado para PostgREST frequentemente mostra só a URL e os headers. Sem política RLS,
  o exemplo ensina acesso direto ao banco sem ensinar a barreira que torna esse acesso aceitável.

  **Prompt:** *"Para esta chamada em `/rest/v1/investments`, escreva a política RLS mínima que permite ao usuário autenticado ler apenas linhas em que `user_id = auth.uid()`, e mostre uma chamada que deve falhar para outro usuário."*
</Aside>

## Aplicações

A Database API funciona melhor quando a aplicação precisa expor dados que já cabem no modelo relacional do PostgreSQL. Ela combina especialmente bem com front-ends estáticos e aplicações internas pequenas, desde que as políticas sejam tratadas como parte do back-end.

| Aplicação | Como a API ajuda | Limite |
| --- | --- | --- |
| Painel CRUD autenticado | Tabelas viram endpoints rapidamente. | Regra complexa de negócio pode ficar espalhada entre cliente e RLS. |
| Protótipo com dados relacionais | SQL, índices e filtros já existem. | Política permissiva de estudo não serve para produção. |
| Integração por HTTP | Qualquer linguagem chama a API. | Fluxos com segredo exigem função ou servidor. |
| Relatório simples | Visões SQL expostas como leitura. | Agregação pesada ou assíncrona pede camada dedicada. |

## Quando Usar, e Quando Não Usar?

Use a Database API quando a regra de acesso cabe em SQL e quando o cliente pode falar com o banco sem carregar segredo administrativo. Evite quando a operação depende de uma chave privada, de uma decisão antifraude, de pagamento ou de processamento longo.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| CRUD por usuário com RLS clara | **Database API** | A política do banco é suficiente para isolar dados. |
| Consulta relacional ou visão SQL | **Database API ou RPC** | O PostgreSQL resolve perto dos dados. |
| Pagamento, e-mail ou webhook | **Edge Function** | O segredo não pode ir ao navegador. |
| API extensa com muitas regras | **Back-end próprio** | Camadas, testes e observabilidade ficam mais explícitos. |

## Exercício

Explique por que a chave `anon` pode aparecer no navegador, mas a segurança ainda depende de RLS.

<details>
  <summary>Possível resposta</summary>

  A chave `anon` identifica o projeto e permite acesso público controlado. Ela não é segredo, porque o front-end precisa carregá-la. Quem decide quais linhas podem ser lidas ou escritas é a política RLS aplicada pelo PostgreSQL.
</details>

## Desafio

Escolha uma entidade de um projeto seu e escreva duas versões de acesso: uma por tabela direta e outra por função RPC. Justifique qual delas deixa a regra mais clara.

<details>
  <summary>Possível resposta</summary>

  A tabela direta é melhor quando o cliente só precisa filtrar e paginar linhas autorizadas. A RPC é melhor quando a regra envolve agregação, cálculo ou transação que deve acontecer perto do banco e ser chamada como uma operação única.
</details>

## Perguntas de revisão

1. **Qual é o papel do PostgREST no Supabase?**
   <details>
     <summary>Possível resposta</summary>
     Ele lê o esquema do PostgreSQL e expõe tabelas, visões e funções como uma API REST, respeitando permissões e RLS.
   </details>

2. **Quando a Database API não é o lugar certo para uma operação?**
   <details>
     <summary>Possível resposta</summary>
     Quando a operação precisa de segredo, chamada a serviço externo, processamento longo ou regra que não deve ser controlada pelo cliente.
   </details>
