O **Netlify Forms** captura submissões de formulários HTML sem exigir que o projeto crie uma API, banco e painel administrativo próprios. Ele é útil para contato, newsletter, inscrição e pesquisas simples.

## Objetivo

Compreender quando Forms substitui uma rota própria e quando o domínio exige um back-end real. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o papel do atributo `data-netlify`.
- Identificar formulários bons para captura gerenciada.
- Reconhecer limites de validação e regra de negócio.
- Planejar spam, confirmação e notificação.
- Decidir quando integrar Forms com Functions.

## Fluxo de Captura

O recurso funciona melhor quando a submissão é uma entrada simples que precisa ser recebida, armazenada e revisada. A plataforma identifica o formulário no HTML publicado e passa a coletar submissões.

<Mermaid title="Fluxo de Netlify Forms">
{`
flowchart LR
  User["Usuário"] --> Form["Formulário HTML"]
  Form --> Netlify["Netlify Forms"]
  Netlify --> Dashboard["Submissões"]
  Netlify --> Notification["Notificação ou integração"]
`}
</Mermaid>

Esse modelo evita criar um endpoint só para receber mensagens, mas não remove a necessidade de pensar em validação, consentimento, privacidade e abuso.

## Trecho Mínimo

Um formulário simples declara `method="POST"` e `data-netlify="true"`. O nome do formulário ajuda a identificar as submissões.

```html
<form name="contact" method="POST" data-netlify="true">
  <label>
    Nome
    <input type="text" name="name" required />
  </label>

  <label>
    E-mail
    <input type="email" name="email" required />
  </label>

  <label>
    Mensagem
    <textarea name="message" required></textarea>
  </label>

  <button type="submit">Enviar</button>
</form>
```

Em frameworks que renderizam rotas dinamicamente, confirme se o formulário aparece no HTML que o Netlify consegue analisar no build. Essa validação evita descobrir tarde que nenhuma submissão foi registrada.

## Quando Usar

Forms é uma boa solução quando a submissão é simples e o processamento pode acontecer depois.

| Cenário | Forms funciona bem? | Motivo |
| --- | --- | --- |
| Contato institucional | **Sim** | A equipe precisa receber e revisar mensagens. |
| Inscrição em evento pequeno | **Sim** | A submissão pode virar planilha, notificação ou triagem. |
| Newsletter simples | **Talvez** | Pode servir como captura inicial, mas provedores de e-mail cuidam melhor de listas. |
| Checkout ou pagamento | **Não** | Exige transação, idempotência, segurança e auditoria. |
| Cadastro com conta de usuário | **Não** | Precisa de autenticação, banco e regras de domínio. |

## Spam e Validação

Validação no HTML melhora a experiência, mas não é segurança. Qualquer pessoa pode enviar uma requisição manual para o endpoint. Use proteção contra spam, campos obrigatórios e revisão das submissões quando a entrada vem de público aberto.

<Aside type="tip" title="Forms pode ser a primeira versão de uma feature">
  Em uma fase inicial, Forms pode validar demanda por contato, interesse ou inscrição sem criar back-end. Quando a submissão passar a acionar regra de negócio, pagamento, conta ou fluxo transacional, migre para Function, API ou BaaS.
</Aside>

## Integração Com Functions

Forms pode fazer parte de um fluxo maior. Um padrão comum é capturar a submissão e acionar uma Function para normalizar dados, enviar notificação rica ou integrar com CRM.

| Necessidade | Possível desenho |
| --- | --- |
| Notificação simples | Form gerenciado pela plataforma. |
| Enviar e-mail formatado | Form mais Function com provedor de e-mail. |
| Criar lead em CRM | Form mais Function que chama API externa. |
| Validar regra de domínio antes de aceitar | Function ou back-end próprio no lugar de Forms simples. |

## Executando

Use Forms quando a simplicidade for parte do requisito, não apenas por conveniência.

<Steps>
1. Defina quais campos são realmente necessários.
2. Crie o formulário com `name`, `method="POST"` e `data-netlify="true"`.
3. Valide a presença do formulário no HTML publicado.
4. Configure proteção contra spam e notificações.
5. Teste uma submissão em deploy preview.
6. Revise privacidade, retenção de dados e responsáveis pelo atendimento.
</Steps>

## Exercício

Por que Forms não é uma boa base para um checkout?

<details>
  <summary>Possível resposta</summary>

  Porque checkout exige transação, confirmação de pagamento, idempotência, antifraude, auditoria e integração segura. Forms captura submissões, mas não modela esse fluxo de negócio.
</details>

## Desafio

Projete um formulário de interesse para uma versão beta do InvestApp. Liste campos mínimos, fluxo de notificação e critério para migrar para uma API própria.

<details>
  <summary>Possível resposta</summary>

  Campos mínimos: nome, e-mail e perfil de investidor. A submissão pode gerar notificação para a equipe. A migração para API própria acontece quando o cadastro precisar criar conta, enviar convite automatizado ou registrar consentimento em banco com auditoria.
</details>
