O **Cloudflare Pages** publica front-ends estáticos e aplicações web a partir de um repositório Git, servindo o resultado pela rede global da Cloudflare. Ele se aproxima de Vercel e Netlify na experiência de deploy, mas fica naturalmente perto de Workers, KV, D1, R2, DNS e cache.

## Objetivo

Compreender Cloudflare Pages como camada de publicação de front-end dentro de uma plataforma orientada à borda. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o caminho entre commit, build e CDN.
- Diferenciar Pages, Workers e static assets.
- Planejar redirects, headers e variáveis de ambiente.
- Reconhecer quando Pages é suficiente e quando precisa de Worker.
- Comparar Pages com Vercel Deployments e Netlify Deployments.

## Fluxo de Publicação

Pages segue o mesmo modelo mental de hospedagem estática: a plataforma roda o build, publica a pasta de saída e distribui arquivos pelo CDN.

<Mermaid title="Deploy de front-end no Cloudflare Pages">
{`
flowchart TD
  Git["Repositório Git"] --> Build["Build command"]
  Build --> Output["Pasta de saída"]
  Output --> Preview["Preview deployment"]
  Output --> CDN["Cloudflare CDN"]
  CDN --> User["Usuário"]
`}
</Mermaid>

O diferencial aparece quando a aplicação precisa de lógica próxima da borda. Pages pode ser combinado com Workers para APIs curtas, autenticação leve, proxy e transformação de respostas.

## Recursos

A tabela separa recursos de publicação, roteamento e integração. Ela ajuda a evitar a ideia de que Pages é apenas um host de arquivos.

| Recurso | O que resolve | Aplicação típica |
| --- | --- | --- |
| **Build por Git** | Publica a partir de commits e branches. | Front-end versionado por pull request. |
| **Preview deployments** | Gera URLs revisáveis antes de produção. | Revisão de interface e rotas. |
| **CDN global** | Entrega assets perto do usuário. | Sites públicos e documentação. |
| **Redirects e headers** | Controla resposta antes do JavaScript. | SPA, migração de URL e segurança. |
| **Integração com Workers** | Acrescenta lógica serverless. | Segredos, proxy e APIs curtas. |

## Configuração Típica

Um projeto Pages precisa declarar o comando de build e a pasta publicada. Em frameworks como Astro e Vite, a pasta costuma ser `dist`.

```txt title="Contrato de build no Pages"
Framework preset: Astro ou Vite
Build command: pnpm build
Build output directory: dist
Environment variables: PUBLIC_API_URL, PUBLIC_SUPABASE_URL
```

Variáveis públicas entram no build e podem chegar ao navegador. Segredos devem ficar em Workers ou outro runtime de servidor.

<Aside type="caution" title="Dica de IA: Separe variável de build e segredo">
  Assistentes frequentemente sugerem colocar qualquer token em variável da plataforma. Em front-end estático, variável usada no build pode ir para o bundle.

  **Prompt:** *"Classifique estas variáveis de Cloudflare Pages entre públicas de build e privadas de Worker; explique quais podem aparecer no navegador e quais exigem runtime de servidor."*
</Aside>

## Critérios de Uso

Pages é uma boa escolha quando a aplicação é centrada no front-end e o time quer a rede da Cloudflare como base.

| Cenário | Use Pages? | Motivo |
| --- | --- | --- |
| Documentação, blog ou site Astro | **Sim** | Build estático e CDN resolvem a entrega. |
| SPA com BaaS | **Sim** | Front-end fica em Pages e dados em Supabase ou Firebase. |
| API curta com segredo | **Sim, com Worker** | Pages publica a interface e Worker protege o segredo. |
| API Express extensa | **Não como peça principal** | Render, Railway ou Cloud Run representam melhor um processo de servidor. |

## Executando

Use Pages como primeira camada da arquitetura Cloudflare.

<Steps>
1. Confirme o framework e a pasta de saída.
2. Configure build command e variáveis públicas.
3. Teste preview deployment em branch.
4. Adicione redirects e headers para rotas e segurança.
5. Mova segredos para Workers quando houver lógica de servidor.
</Steps>

## Exercício

Por que Pages não deve guardar uma chave administrativa do Supabase no build?

<details>
  <summary>Possível resposta</summary>

  Porque variáveis usadas pelo front-end podem ser incorporadas ao JavaScript publicado. Chaves administrativas precisam ficar em Workers, Functions ou outro código de servidor.
</details>

## Desafio

Planeje a publicação de um painel do InvestApp em Pages com Supabase como BaaS e um Worker para cotações privadas.

<details>
  <summary>Possível resposta</summary>

  Pages publica o front-end e usa apenas URL e chave pública do Supabase. Supabase guarda dados e aplica RLS. Worker recebe chamadas do front-end, lê o token privado do provedor de cotações e devolve apenas o resultado.
</details>

## Perguntas de revisão

1. **Quando Pages precisa ser combinado com Workers?**
   <details>
     <summary>Possível resposta</summary>
     Quando a aplicação precisa de segredo, proxy, autenticação leve ou lógica que não pode rodar no navegador.
   </details>

2. **Qual é a função do preview deployment?**
   <details>
     <summary>Possível resposta</summary>
     Permitir revisar uma versão publicada antes de promover para produção.
   </details>
