A **Cloudflare** combina rede global, DNS, CDN, hospedagem estática, funções de borda e serviços de dados. No guia, ela entra como a plataforma que ajuda a enxergar a arquitetura a partir da borda: a requisição pode ser respondida, roteada, transformada ou persistida perto do usuário.

## Objetivo

Compreender a Cloudflare como plataforma de entrega e execução distribuída, separando CDN, Pages, Workers, storage e bancos serverless. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar Cloudflare Pages, Workers, D1, R2 e KV.
- Explicar por que a borda muda decisões de latência e cache.
- Escolher quando usar Pages em vez de Vercel ou Netlify.
- Reconhecer limites de consistência, runtime e acoplamento à plataforma.
- Planejar uma aplicação com front-end estático, função de borda e dados gerenciados.

## Mapa da Plataforma

Cloudflare começou como infraestrutura de rede e cresceu para uma plataforma de desenvolvimento. Essa origem explica por que DNS, cache, segurança e execução de código aparecem tão integrados.

<Mermaid title="Produtos centrais da Cloudflare para aplicações web">
{`

  DNS["DNS e domínio"] --> CDN["CDN e cache"]

Pense na plataforma como uma pilha em que a requisição passa primeiro pela rede. Pages publica a aplicação, Workers executa lógica, e os produtos de dados entram quando a lógica precisa persistir ou consultar estado.

## Produtos e Recursos

A tabela abaixo usa uma leitura prática: qual responsabilidade cada produto assumiria em uma aplicação web.

| Produto | O que resolve | Aplicações típicas | Atenção |
| --- | --- | --- | --- |
| **Pages** | Deploy de front-end e sites estáticos. | Astro, Vite, documentação, landing pages e SPAs. | Rewrites e funções precisam ser planejados junto do build. |
| **Workers** | Funções serverless na borda. | APIs curtas, proxy, autenticação leve, transformação de resposta. | Runtime de borda não é igual a um servidor Node completo. |
| **D1** | Banco SQL serverless com semântica SQLite. | Projetos pequenos e médios que querem SQL perto de Workers. | Avalie limites, migrações e consistência antes de colocar domínio crítico. |
| **R2** | Armazenamento de objetos. | Imagens, exports, anexos e arquivos gerados. | Permissões e URLs assinadas ainda precisam de desenho cuidadoso. |
| **KV** | Dados chave-valor distribuídos. | Flags, configuração, cache e leitura muito frequente. | Não é banco relacional nem fonte ideal para transação. |
| **Queues e Workflows** | Trabalho assíncrono e processos duráveis. | Importações, webhooks, retries e orquestrações. | Exige idempotência e observabilidade. |
| **Workers AI** | Inferência serverless integrada a Workers. | Classificação, resumo, busca semântica e automações com IA. | Custo, privacidade e limites de entrada precisam ser explícitos. |
| **CDN e DNS** | Entrega, cache, domínio e proteção. | Sites públicos, APIs, assets e segurança de borda. | Cache mal invalidado parece bug de aplicação. |

## Critérios de Uso

Cloudflare é forte quando a rede é parte do produto, não só o lugar que entrega arquivos.

| Cenário | Cloudflare encaixa bem? | Motivo |
| --- | --- | --- |
| Site estático global | **Sim** | Pages e CDN resolvem publicação e entrega. |
| API curta sensível a latência | **Sim** | Workers executa perto do usuário. |
| Arquivos grandes com custo de saída relevante | **Sim** | R2 é uma opção forte para object storage. |
| CRUD relacional simples próximo da borda | **Talvez** | D1 pode servir, mas avalie maturidade, limites e migrações. |
| Back-end Node com bibliotecas pesadas | **Talvez não** | Runtime de borda tem restrições próprias. |
| Aplicação com domínio extenso e jobs longos | **Não como única peça** | Use serviço dedicado, filas ou PaaS junto. |

<Aside type="caution" title="Dica de IA: Não misture runtime de borda com Node.js completo">
  Assistentes costumam sugerir `fs`, conexões persistentes ou bibliotecas Node em Workers. Antes de aceitar, peça uma revisão do runtime alvo e das APIs disponíveis.

  **Prompt:** *"Revise este código para Cloudflare Workers e liste toda dependência de API exclusiva do Node.js, sugerindo uma alternativa baseada em `Request`, `Response`, bindings e APIs Web."*
</Aside>

## Executando

Estude Cloudflare pelo caminho da requisição, porque isso revela a diferença dela em relação a plataformas centradas apenas em deploy.

<Steps>
1. Publique um front-end em Pages.
2. Adicione um Worker para uma rota curta com segredo ou transformação de resposta.
3. Classifique dados entre D1, R2, KV e serviço externo.
4. Configure cache e headers com uma regra explícita de invalidação.
5. Valide local, preview e produção, prestando atenção ao runtime de borda.
</Steps>

## Exercício

Por que KV não deve ser tratado como substituto direto de um banco relacional?

<details>
  <summary>Possível resposta</summary>

  Porque KV guarda pares chave-valor e favorece leitura distribuída. Ele não modela relações, junções, transações e consultas ricas como um banco relacional.
</details>

## Desafio

Planeje uma arquitetura para o InvestApp usando Cloudflare Pages para o front-end, Workers para uma integração privada e Supabase para dados principais. Explique por que D1 não foi escolhido para a carteira do usuário.

<details>
  <summary>Possível resposta</summary>

  Pages publica a interface, Workers protege segredos e normaliza chamadas externas, e Supabase guarda carteiras, usuários e permissões com PostgreSQL e RLS. D1 poderia servir protótipos ou dados auxiliares, mas a carteira exige autorização por usuário, relações e consultas que já estão bem resolvidas no Supabase.
</details>

## Perguntas de revisão

1. **Qual é a diferença entre Pages e Workers?**
   <details>
     <summary>Possível resposta</summary>
     Pages publica o front-end e assets. Workers executa código serverless na borda para responder, transformar ou rotear requisições.
   </details>

2. **Quando R2 é mais adequado do que D1?**
   <details>
     <summary>Possível resposta</summary>
     Quando o dado é um objeto ou arquivo, como imagem, export ou anexo, e não uma entidade relacional consultada por campos.
   </details>

3. **Por que cache precisa de estratégia de invalidação?**
   <details>
     <summary>Possível resposta</summary>
     Porque cache velho pode servir resposta antiga mesmo depois do código ou dos dados mudarem, parecendo erro de aplicação.
   </details>
