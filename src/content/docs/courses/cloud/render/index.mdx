O **Render** é uma plataforma como serviço para publicar sites estáticos, APIs, serviços privados, workers, cron jobs e bancos gerenciados. No guia, ele representa o caminho em que a aplicação continua tendo um back-end próprio, mas o time não administra máquinas manualmente.

## Objetivo

Compreender Render como PaaS para aplicações web e APIs, identificando quando ele é mais adequado do que BaaS, hospedagem estática ou functions isoladas. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar Static Sites, Web Services, Private Services, Workers e Cron Jobs.
- Explicar por que Render combina bem com APIs Express.
- Planejar variáveis, build, start command e banco gerenciado.
- Reconhecer quando usar serviço sempre ativo em vez de função serverless.
- Comparar Render com Railway, Heroku, Vercel e Netlify.

## Mapa da Plataforma

Render organiza a infraestrutura em serviços. Cada serviço tem tipo, comando de build, comando de inicialização, variáveis e escalabilidade próprios.

<Mermaid title="Tipos de serviço no Render">
{`
flowchart TD
  Project["Projeto"] --> Static["Static Site<br/>front-end"]
  Project --> Web["Web Service<br/>API pública"]
  Project --> Private["Private Service<br/>rede interna"]
  Project --> Worker["Background Worker<br/>processo sem HTTP"]
  Project --> Cron["Cron Job<br/>execução agendada"]
  Project --> Data["Postgres e Key Value<br/>dados gerenciados"]
`}
</Mermaid>

Essa organização é didática para quem vem do Express: o servidor continua existindo como processo, mas deploy, domínio, HTTPS, logs e variáveis ficam na plataforma.

## Produtos e Recursos

Render cobre tanto front-end quanto back-end, mas seu valor principal aparece quando há processo de servidor real.

| Produto | O que resolve | Aplicações típicas | Atenção |
| --- | --- | --- | --- |
| **Static Sites** | Build e publicação de front-end. | Astro, Vite, documentação e SPAs. | Para sites puros, Netlify ou Vercel também servem bem. |
| **Web Services** | Processo HTTP sempre disponível. | APIs Express, Fastify, Rails, Django e serviços com rotas. | Custo existe enquanto o serviço fica provisionado. |
| **Private Services** | Serviço acessível apenas dentro da rede privada. | APIs internas, processadores e integrações entre serviços. | A arquitetura já fica mais operacional. |
| **Background Workers** | Processo contínuo sem receber HTTP. | Filas, consumidores e tarefas assíncronas. | Precisa de broker, fila ou fonte de trabalho. |
| **Cron Jobs** | Execuções agendadas. | Limpeza, relatórios, sincronização e importação periódica. | Não substitui fila para trabalho sob demanda. |
| **Postgres e Key Value** | Dados gerenciados próximos da aplicação. | Banco relacional e cache/estado simples. | Backups, migrações e limites continuam importando. |

## Quando Usar?

Render é forte quando a aplicação já tem back-end próprio, principalmente APIs com várias rotas e domínio organizado em camadas.

| Cenário | Render encaixa bem? | Motivo |
| --- | --- | --- |
| API Express da TaskAPI ou InvestApp | **Sim** | O processo HTTP é o centro da aplicação. |
| Worker que consome fila | **Sim** | Precisa rodar continuamente, sem depender de requisição. |
| Job diário de importação | **Sim** | Cron Job expressa a agenda diretamente. |
| Site estático simples | **Talvez** | Funciona, mas Vercel, Netlify e Pages costumam ser mais focados nisso. |
| Função curta para proteger um segredo | **Talvez não** | Serverless pode ser mais simples e barato se não houver API inteira. |

<Aside type="tip" title="Render é boa ponte entre Express local e produção">
  Depois que a turma entende `npm start`, porta HTTP, variáveis e banco, Render deixa a publicação mais concreta do que uma função isolada. O mesmo processo que roda localmente passa a ter domínio, logs e ambiente de produção.
</Aside>

## Render, Railway e Heroku

Essas três plataformas ficam na mesma família: publicar aplicações como serviços, sem administrar servidor bruto.

| Plataforma | Semelhança | Diferença relevante |
| --- | --- | --- |
| **Render** | PaaS com web services, workers e banco. | Organização explícita por tipos de serviço. |
| **Railway** | PaaS com projetos, serviços e bancos. | Experiência muito visual e rápida para compor serviços. |
| **Heroku** | PaaS clássico com dynos e add-ons. | Ecossistema maduro e modelo histórico de Procfile/dynos. |

## Configuração Mental

Uma API Express publicada no Render precisa responder a quatro perguntas: como instalar, como construir, como iniciar e em qual porta escutar.

```txt title="Contrato de publicação de uma API"
Install command: pnpm install --frozen-lockfile
Build command: pnpm build
Start command: pnpm start
Environment: DATABASE_URL, JWT_SECRET, PORT
```

O `PORT` normalmente é fornecido pela plataforma. O código da API deve ler a variável e não fixar uma porta de produção.

## Executando

Use Render quando quiser estudar produção de uma API como processo.

<Steps>
1. Separe front-end estático e API, se eles tiverem ciclos diferentes.
2. Publique a API como Web Service.
3. Configure variáveis privadas e banco gerenciado.
4. Rode migrações antes ou durante o deploy, conforme a política do projeto.
5. Adicione worker ou cron job apenas quando existir trabalho fora do request HTTP.
6. Monitore logs, saúde da aplicação e consumo.
</Steps>

## Exercício

Por que uma API Express com 40 rotas pode ser mais confortável em Render do que espalhada em 40 functions?

<details>
  <summary>Possível resposta</summary>

  Porque o roteamento, os middlewares, os serviços, a conexão com banco, os testes e os logs ficam organizados em um processo único. Functions são ótimas para rotas curtas, mas podem fragmentar uma API grande.
</details>

## Desafio

Planeje a publicação da TaskAPI no Render. Liste quais variáveis entram no ambiente, qual serviço recebe HTTP e se faria sentido adicionar cron job.

<details>
  <summary>Possível resposta</summary>

  A API entra como Web Service, lendo `PORT`, `DATABASE_URL` e `JWT_SECRET`. O banco pode ser Render Postgres ou outro PostgreSQL gerenciado. Cron job só faz sentido se existir tarefa periódica, como limpeza de sessões expiradas ou relatório diário.
</details>

## Perguntas de revisão

1. **Qual é a diferença entre Web Service e Background Worker?**
   <details>
     <summary>Possível resposta</summary>
     Web Service recebe requisições HTTP. Background Worker executa processo contínuo sem rota pública, normalmente consumindo fila ou tarefa assíncrona.
   </details>

2. **Quando uma Function é mais adequada do que Render?**
   <details>
     <summary>Possível resposta</summary>
     Quando existe apenas uma rota curta, esporádica e sem necessidade de processo sempre ativo.
   </details>

3. **Por que porta fixa no código atrapalha deploy?**
   <details>
     <summary>Possível resposta</summary>
     Porque a plataforma normalmente injeta a porta via variável de ambiente. Fixar uma porta pode impedir o roteamento correto em produção.
   </details>
