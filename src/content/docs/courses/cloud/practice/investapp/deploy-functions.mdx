Nesta etapa, o InvestApp Cloud sai do `localhost`. O front-end é publicado como site estático, as variáveis públicas entram no build e uma função serverless aparece para proteger operações que não podem rodar no navegador.

## Objetivo

Publicar o InvestApp Cloud e separar variáveis públicas de segredos privados, usando Vercel, Netlify ou Cloudflare Pages como destinos de estudo. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o caminho entre build, `dist/` e CDN.
- Configurar redirects para rotas internas de SPA.
- Diferenciar variável pública de build e segredo de função.
- Identificar quando Supabase ou Firebase dispensam função e quando não dispensam.
- Testar uma função localmente antes de publicar.

## Quando a Função Entra?

Supabase e Firebase permitem CRUD direto do front-end quando RLS ou Security Rules estão corretas. Uma função entra quando o trabalho exige segredo, validação confiável ou webhook externo.

<Mermaid title="Front-end publicado, BaaS e função serverless">
{`
flowchart TD
  Browser["InvestApp no CDN"] --> BaaS["Supabase ou Firebase<br/>dados e auth"]
  Browser --> Function["Função serverless<br/>segredos e webhooks"]
  Function --> Provider["Serviço externo"]
  Function --> BaaS
`}
</Mermaid>

<Aside type="danger" title="Segredo não atravessa o build">
  Tudo que entra em variável pública de front-end vira JavaScript publicado. Chaves administrativas, tokens de pagamento e credenciais de e-mail pertencem à função, não ao bundle.
</Aside>

## Executando

Feche a trilha validando publicação e função:

<Steps>
1. Gere o build local do front-end com as variáveis públicas corretas.
2. Publique em Vercel ou Netlify e abra a URL de preview.
3. Recarregue uma rota interna para validar rewrites.
4. Teste CRUD contra Supabase ou Firebase no ambiente publicado.
5. Crie uma função mínima para uma operação com segredo, como cotação ou e-mail.
</Steps>

## Exercício

Quando o InvestApp usando Supabase precisa de uma função serverless, mesmo com RLS configurado?

<details>
  <summary>Possível resposta</summary>

  Quando a operação usa segredo ou regra confiável fora do alcance do cliente, como chamar API paga, validar webhook, enviar e-mail com token privado ou usar a `service_role`.
</details>

## Desafio

Publique uma versão de estudo do InvestApp Cloud e escreva um relatório curto com URL de preview, variáveis públicas usadas, regra de rewrite, fluxo testado e uma operação que exigiria função.

<details>
  <summary>Possível resposta</summary>

  O relatório deve incluir a URL publicada, confirmar que `/dashboard` recarrega sem 404, listar `VITE_SUPABASE_URL` ou configuração Firebase como pública, registrar criação e listagem de um investimento e apontar uma função para e-mail ou cotação externa.
</details>

## Perguntas de revisão

1. **Por que uma chave `service_role` do Supabase não pode ficar em variável `VITE_`?**
   <details>
     <summary>Possível resposta</summary>
     Porque variáveis `VITE_` entram no bundle. A `service_role` ignora RLS e daria acesso administrativo ao banco.
   </details>

2. **Qual problema o rewrite de SPA resolve?**
   <details>
     <summary>Possível resposta</summary>
     Resolve o 404 ao recarregar uma rota interna que não existe como arquivo físico no servidor.
   </details>
