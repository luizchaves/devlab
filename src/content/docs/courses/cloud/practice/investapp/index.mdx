O **InvestApp Cloud** é a trilha prática do guia de computação em nuvem. Assim como o InvestApp do [Guia de Express.js](../../../expressjs/practice/investapp/), ele evolui em etapas: primeiro a aplicação usa serviços BaaS para dados e identidade, depois é publicada em plataformas de hospedagem e recebe funções para operações que não podem rodar no navegador.

## Objetivo

Construir uma versão em nuvem do InvestApp por etapas cumulativas, substituindo partes do back-end próprio por serviços gerenciados sem perder clareza sobre dados, autenticação, arquivos, publicação e segredos. Ao final do tópico, o leitor deve ser capaz de:

- Explicar quais responsabilidades saem do Express e passam para um BaaS.
- Integrar Supabase e Firebase como alternativas de persistência e autenticação.
- Publicar o front-end em plataformas como Vercel e Netlify.
- Decidir quando uma função serverless é necessária.
- Comparar a trilha cloud com a trilha de back-end próprio do guia de Express.js.

## Etapas da Trilha

Cada etapa acrescenta uma decisão arquitetural. As etapas de Supabase e Firebase são alternativas didáticas sobre o mesmo domínio, não tecnologias usadas ao mesmo tempo na mesma aplicação final.

## Arquitetura Incremental

A trilha não começa perguntando "qual plataforma é melhor". Ela pergunta qual parte do sistema será terceirizada em cada etapa e qual responsabilidade continua sendo da equipe.

<Mermaid title="Evolução do InvestApp na trilha cloud">
{`
flowchart TD
  Static["Front-end Vite<br/>HTML, CSS e JS"] --> SupaApi["Etapa 1<br/>Supabase API"]
  SupaApi --> SupaClient["Etapa 2<br/>Supabase Client"]
  SupaClient --> Firebase["Etapa 3<br/>Firebase Firestore"]
  Firebase --> Deploy["Etapa 4<br/>Deploy e Functions"]
  SupaApi --> Lessons["Lição comum<br/>política é back-end"]
  Firebase --> Lessons
`}
</Mermaid>

O fio condutor é o mesmo investimento cadastrado na interface. O que muda é quem guarda, quem autoriza e onde o código confiável roda.

<Aside type="note" title="Comparação com o guia de Express.js">
  No guia de Express.js, o InvestApp constrói rotas, banco, autenticação e Docker dentro de uma API própria. Nesta trilha, o mesmo domínio serve para estudar a troca: parte do servidor vira configuração de Supabase ou Firebase, e outra parte reaparece como função serverless.
</Aside>

## Executando

Estude a trilha como uma sequência de versões, mesmo quando as tecnologias forem alternativas:

<Steps>
1. Comece pela [Supabase API](supabase-api/) para ver uma tabela virar endpoint REST.
2. Continue em [Supabase Client](supabase-client/) para conectar a interface ao BaaS por SDK.
3. Compare com [Firebase Firestore](firebase-firestore/) para sentir a diferença entre tabela relacional e documentos.
4. Feche em [Publicação e funções](deploy-functions/) para decidir onde hospedar e quando adicionar código serverless.
</Steps>

## Exercício

Compare a etapa `InvestApp: Prisma ORM` do guia de Express.js com a etapa `Supabase API` desta trilha. O que muda na responsabilidade da aplicação?

<details>
  <summary>Possível resposta</summary>

  Com Prisma, a aplicação Express continua dona das rotas, validações e autorização antes de consultar o banco. Com Supabase API, a rota é gerada pela plataforma e a segurança passa a depender de RLS, porque o cliente consegue falar diretamente com o banco via PostgREST.
</details>

## Desafio

Escreva uma matriz de decisão para o InvestApp com três versões: Express próprio, Supabase e Firebase. Compare modelo de dados, autenticação, autorização, upload de avatar, publicação e saída futura da plataforma.

<details>
  <summary>Possível resposta</summary>

  Uma matriz consistente mostra Express como maior controle e maior manutenção, Supabase como caminho relacional com RLS e boa portabilidade, e Firebase como caminho de documentos com sincronização/offline fortes e maior custo de migração para fora da plataforma.
</details>

## Perguntas de revisão

1. **Por que as etapas de Supabase e Firebase são alternativas didáticas?**
   <details>
     <summary>Possível resposta</summary>
     Porque as duas resolvem dados e identidade para o mesmo domínio, mas partem de modelos diferentes. Usá-las juntas no mesmo CRUD inicial duplicaria responsabilidade.
   </details>

2. **Qual responsabilidade não desaparece quando o back-end próprio sai?**
   <details>
     <summary>Possível resposta</summary>
     A autorização. Ela muda de lugar, indo para RLS, Security Rules ou funções, mas continua sendo decisão do projeto.
   </details>
