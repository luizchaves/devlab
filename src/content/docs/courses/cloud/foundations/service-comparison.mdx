Este tópico fecha os fundamentos do guia reunindo o **vocabulário dos recursos de nuvem** e comparando as plataformas por **recurso oferecido**, não por marca. A pergunta deixa de ser "qual plataforma é melhor?" e passa a ser "quais plataformas resolvem esta necessidade, e com que tipo de compromisso?".

## Objetivo

Compreender a cobertura de recursos entre plataformas de nuvem para aplicações web, usando uma matriz comparativa como ponto de partida para escolher, combinar ou descartar serviços. Ao final do tópico, o leitor deve ser capaz de:

- Reconhecer os principais termos de recursos de nuvem (hospedagem, funções, bancos, autenticação, storage, filas, observabilidade, analytics, audit log) e saber em qual página do guia cada um é aprofundado.
- Diferenciar recursos nativos, recursos parciais e recursos por integração.
- Identificar quais plataformas resolvem hospedagem, dados, autenticação, storage e execução.
- Reconhecer quando duas plataformas oferecem o mesmo nome para modelos diferentes.
- Justificar uma escolha por capacidade necessária, e não por popularidade.
- Usar o mapa como entrada para uma decisão arquitetural mais detalhada.

## Leitura da Comparação

A tabela usa quatro marcações. Elas não medem qualidade, plano gratuito, limite de uso ou preço. Elas indicam apenas se a plataforma oferece aquele recurso como parte natural da sua proposta.

| Marcação | Significado |
| --- | --- |
| **Sim** | O recurso é parte central da plataforma. |
| **Parcial** | O recurso existe, mas com escopo limitado ou foco diferente. |
| **Integração** | A plataforma normalmente usa outro serviço para resolver. |
| **Não** | O recurso não é objetivo daquela plataforma. |

Um recurso "Sim" ainda pode ser a escolha errada. Banco, autenticação e storage precisam ser avaliados por modelo de dados, autorização, região, custo, limite e plano de saída.

<Aside type="tip" title="A mesma palavra pode esconder produtos diferentes">
  "Functions", "Database" e "Storage" aparecem em muitas plataformas, mas não significam a mesma coisa. Uma function de borda, uma rota serverless Node.js e um container HTTP escalável resolvem problemas parecidos com restrições diferentes.
</Aside>

## Leitura por Necessidade

Quando o projeto tem um requisito claro, a escolha começa pela linha certa da tabela. A plataforma final pode ser uma combinação.

| Necessidade do projeto | Candidatas iniciais | Pergunta que decide |
| --- | --- | --- |
| Publicar front-end com preview por PR | Vercel, Netlify, Cloudflare Pages, Amplify, Render, Railway. | O projeto é só estático, híbrido, JAMstack ou parte de stack maior? |
| Guardar dados relacionais com autorização por usuário | Supabase, Render Postgres, Railway Postgres, Heroku Postgres, D1, PocketBase. | A aplicação fala direto com o banco via política ou por uma API própria? |
| Guardar documentos com sincronização e SDKs | Firebase, Appwrite, Amplify Data, PocketBase. | A modelagem acompanha telas e documentos, ou exige consultas relacionais? |
| Proteger segredo de API externa | Vercel Functions, Netlify Functions, Cloudflare Workers, Firebase Functions, Amplify Functions. | A execução precisa de Node completo, borda, integração AWS ou proximidade com o BaaS? |
| Publicar uma API Express completa | Render, Railway, Heroku, Fly.io, Cloud Run. | O time quer processo permanente, container, região específica ou simplicidade de PaaS? |
| Receber formulário simples | Netlify Forms, ou function em Vercel, Cloudflare, Firebase, Azure. | A submissão só precisa ser capturada ou dispara regra de negócio? |
| Rodar algo na própria infraestrutura | Supabase, Appwrite, PocketBase, ou API própria em PaaS/servidor. | Auto-hospedagem é requisito real ou apenas preferência? |

## Armadilhas de Comparação

Comparar por checklist pode enganar. A tabela diz que duas plataformas têm "storage", mas uma pode ser pensada para objeto público, outra para arquivo privado por usuário e outra para blob auxiliar de função.

| Armadilha | Como evitar |
| --- | --- |
| Comparar nome de recurso em vez de modelo. | Leia runtime, permissões, limites e forma de cobrança. |
| Tratar plano gratuito como arquitetura. | Faça a projeção para produção, mesmo que o projeto seja didático. |
| Usar BaaS sem política de acesso. | Considere política como parte obrigatória do back-end. |
| Usar serverless para trabalho longo. | Verifique limite de tempo, retries, filas e observabilidade. |
| Escolher container para site estático. | Use container quando o runtime for requisito, não quando o build basta. |

## Executando

Use esta comparação como roteiro de decisão antes de criar conta, instalar SDK ou escrever código de integração.

<Steps>
1. Liste as capacidades necessárias: hosting, auth, dados, storage, realtime, funções, jobs e containers.
2. Marque quais capacidades precisam ser nativas e quais podem vir por integração.
3. Escolha uma plataforma por camada, evitando exigir que uma única ferramenta resolva tudo.
4. Verifique o modelo de autorização antes de expor qualquer chave pública ao front-end.
5. Consulte a página específica da plataforma escolhida.
6. Registre no projeto quais recursos foram escolhidos e qual seria o plano de saída.
</Steps>

Use as matrizes para responder às perguntas abaixo. A resposta deve citar pelo menos duas plataformas candidatas e um critério de descarte.

1. Um projeto precisa de front-end estático, login, dados por usuário e upload de imagens. Quais combinações aparecem?
2. Uma API Express já existe, tem PostgreSQL e precisa de cron job diário. Quais plataformas combinam melhor?
3. Um site de documentação precisa apenas publicar conteúdo a cada `git push`. Qual opção simples basta?

<details>
  <summary>Possível resposta</summary>

  1. Vercel ou Netlify com Supabase é uma combinação forte se o projeto quer SQL, Auth e Storage. Firebase Hosting com Firebase Auth, Firestore e Storage também serve se o modelo de documentos encaixar melhor. GitHub Pages seria descartado porque não resolve auth, dados e upload.

  2. Render e Railway são candidatas naturais, porque publicam Web Services e bancos. Heroku também cabe como PaaS clássico. Vercel ou Netlify seriam descartadas se a API for extensa e mais confortável como processo permanente.

  3. GitHub Pages basta quando é apenas documentação estática no próprio repositório. Netlify, Vercel ou Cloudflare Pages entram se houver previews, redirects, headers ou funções.
</details>

## Desafio

Monte uma matriz para o InvestApp com oito capacidades: front-end, API, autenticação, banco relacional, upload de avatar, realtime, função com segredo e job agendado. Para cada capacidade, escolha uma plataforma principal e uma alternativa.

<details>
  <summary>Possível resposta</summary>

  Uma composição possível: Vercel ou Netlify para front-end, Supabase para autenticação, banco relacional, upload e realtime, e Vercel Function ou Netlify Function para segredo. Se o InvestApp mantiver uma API Express completa, Render ou Railway podem assumir API e job agendado, deixando Supabase apenas como banco ou trocando por Postgres gerenciado.
</details>

## Perguntas de revisão

1. **Por que "tem database" não basta para escolher uma plataforma?**
   <details>
     <summary>Possível resposta</summary>
     Porque database pode significar PostgreSQL, SQLite serverless, documentos, chave-valor ou banco integrado a um BaaS. O modelo de dados e autorização muda completamente.
   </details>

2. **Quando uma plataforma de hosting precisa ser combinada com BaaS?**
   <details>
     <summary>Possível resposta</summary>
     Quando ela publica muito bem o front-end, mas não oferece como produto central banco, autenticação e regras de acesso por usuário.
   </details>

3. **Qual é a diferença entre recurso nativo e recurso por integração?**
   <details>
     <summary>Possível resposta</summary>
     Recurso nativo faz parte da plataforma e do seu fluxo normal. Recurso por integração depende de outro serviço, SDK, credencial ou produto externo.
   </details>

4. **Por que auto-hospedagem não significa custo zero?**
   <details>
     <summary>Possível resposta</summary>
     Porque alguém precisa cuidar de atualização, backup, disponibilidade, segurança, monitoramento e recuperação de falha.
   </details>
