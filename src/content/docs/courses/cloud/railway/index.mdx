O **Railway** é uma plataforma para publicar aplicações e serviços com foco em velocidade de configuração. Ele organiza a infraestrutura em projetos, serviços, bancos, variáveis, domínios e deploys, com uma experiência visual que ajuda a compor aplicações full-stack rapidamente.

## Objetivo

Compreender Railway como PaaS orientado a projetos e serviços, identificando quando ele acelera o deploy de aplicações full-stack e quando uma plataforma mais explícita pode ser melhor. Ao final do tópico, o leitor deve ser capaz de:

- Explicar a relação entre projeto, serviço, banco e variável.
- Reconhecer deploy por Git, CLI, template e Docker image.
- Planejar uma API Express com banco gerenciado no mesmo projeto.
- Comparar Railway com Render, Heroku, Vercel e Netlify.
- Identificar riscos de custo, acoplamento e configuração implícita.

## Mapa da Plataforma

Railway trabalha com um canvas de projeto. Cada bloco representa um serviço ou recurso, e as variáveis conectam esses blocos sem exigir que o desenvolvedor monte rede e servidor manualmente.

<Mermaid title="Projeto Railway com serviços conectados">
{`
flowchart TD
  Project["Projeto Railway"] --> Front["Front-end"]
  Project --> API["API Express"]
  Project --> DB["Postgres"]
  Project --> Worker["Worker"]
  API --> DB
  Worker --> DB
  Project --> Vars["Variáveis e domínios"]
`}
</Mermaid>

Essa visualização é ótima para protótipos, hackathons e projetos didáticos, porque torna a topologia visível. Em produção, o mesmo conforto precisa vir acompanhado de revisão de custo, backup e observabilidade.

## Produtos e Recursos

Railway não força um único tipo de aplicação. Ele permite publicar serviços diferentes e conectá-los em um mesmo projeto.

| Recurso | O que resolve | Aplicações típicas | Atenção |
| --- | --- | --- | --- |
| **Services** | Deploy de aplicações, APIs e workers. | Express, Fastify, bots, filas e serviços internos. | Cada serviço precisa de start command e variáveis corretas. |
| **Databases** | Bancos gerenciados conectados ao projeto. | PostgreSQL, Redis-like e persistência de desenvolvimento. | Planeje backup, migração e ambiente de produção. |
| **Deployments** | Publicação por Git, CLI, template ou Docker. | Projetos full-stack e APIs com deploy rápido. | Automação rápida pode esconder detalhes de build. |
| **Variables** | Configuração por ambiente e conexão entre serviços. | `DATABASE_URL`, tokens, URLs internas e segredos. | Nunca trate variável injetada como substituta de política de acesso. |
| **Domains** | Endereço público para serviços HTTP. | APIs, front-ends e webhooks. | Domínios e CORS precisam acompanhar cada ambiente. |

## Quando Usar

Railway faz sentido quando o projeto precisa de mais que hospedagem estática, mas o time não quer administrar infraestrutura manualmente.

| Cenário | Railway encaixa bem? | Motivo |
| --- | --- | --- |
| API Express com PostgreSQL | **Sim** | Serviço e banco podem viver no mesmo projeto. |
| Protótipo full-stack rápido | **Sim** | Templates e deploy por Git reduzem atrito inicial. |
| Worker ou bot simples | **Sim** | Um serviço sem HTTP pode rodar junto dos demais. |
| Site estático puro | **Talvez** | Funciona, mas Vercel, Netlify e Pages são mais focados em front-end. |
| Organização com governança rígida | **Depende** | Avalie permissões, ambientes, auditoria e processo de mudança. |

<Aside type="caution" title="Cuidado com infraestrutura fácil demais">
  Uma plataforma rápida reduz a fricção para criar serviço, banco e variável. Isso é ótimo para aprender, mas em produção cada bloco precisa ter dono, custo, backup e plano de saída.
</Aside>

## Comparação Com Render

Render e Railway ocupam a mesma família de decisão, mas ensinam ângulos diferentes.

| Critério | Render | Railway |
| --- | --- | --- |
| Organização | Tipos de serviço mais explícitos. | Projeto visual com serviços conectados. |
| Didática | Bom para explicar processo HTTP, worker e cron. | Bom para mostrar topologia de uma aplicação. |
| Velocidade inicial | Simples, mas mais declarativo. | Muito rápido para prototipar. |
| Produção | Forte para serviços separados e previsíveis. | Forte quando o time controla bem variáveis, custos e ambientes. |

## Contrato de Deploy

Uma API no Railway precisa declarar como inicia e quais valores recebe do ambiente. O contrato abaixo serve como checklist, não como arquivo específico da plataforma.

```txt title="Contrato de serviço Railway"
Service: invest-api
Start command: pnpm start
Public domain: https://invest-api.example
Variables: DATABASE_URL, JWT_SECRET, NODE_ENV
Database: Postgres conectado ao projeto
```

O ponto decisivo é não deixar a aplicação depender de configuração invisível. O serviço deve continuar explicável por comandos, variáveis e conexões documentadas.

## Executando

Use Railway para estudar aplicações compostas por mais de um serviço.

<Steps>
1. Crie um projeto com API e banco.
2. Configure o serviço pelo repositório Git ou por Docker image.
3. Declare start command e variáveis obrigatórias.
4. Conecte a API ao banco por `DATABASE_URL`.
5. Publique um domínio e ajuste CORS se houver front-end separado.
6. Revise logs, métricas, consumo e estratégia de backup.
</Steps>

## Exercício

Qual pergunta diferencia um projeto bom para Railway de um projeto bom para Netlify?

<details>
  <summary>Possível resposta</summary>

  A pergunta é se existe processo de back-end próprio. Se o projeto é principalmente front-end com algumas functions e forms, Netlify encaixa bem. Se há API, banco, worker e serviços conectados, Railway fica mais natural.
</details>

## Desafio

Modele o MonitorApp em Railway com front-end, API, banco e worker de monitoramento. Indique quais serviços precisam de domínio público.

<details>
  <summary>Possível resposta</summary>

  O front-end e a API precisam de domínio público. O banco deve ficar privado ao projeto. O worker não precisa de domínio, porque executa tarefas internas e conversa com o banco ou a API por variáveis e rede interna.
</details>

## Perguntas de revisão

1. **O que é um serviço no Railway?**
   <details>
     <summary>Possível resposta</summary>
     É uma unidade publicável, como API, front-end, worker ou aplicação containerizada, com deploy, variáveis e configuração próprias.
   </details>

2. **Por que variáveis conectam a topologia do projeto?**
   <details>
     <summary>Possível resposta</summary>
     Porque URLs, credenciais e endereços internos permitem que serviços e bancos se encontrem sem valores fixos no código.
   </details>

3. **Quando Render pode ser preferível?**
   <details>
     <summary>Possível resposta</summary>
     Quando o time quer uma separação mais explícita entre web service, worker, cron job e banco, com menos configuração implícita.
   </details>
