O **Firebase Auth** é o serviço de identidade do Firebase. Ele cuida de cadastro, login, provedores externos, persistência de sessão e emissão de tokens. A proteção dos dados acontece quando Firestore, Storage ou uma função usam essa identidade para autorizar acesso.

## Objetivo

Compreender Firebase Auth como serviço de identidade conectado ao restante da plataforma, separando sessão de usuário e autorização de recursos. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar login, sessão e autorização.
- Explicar o papel do `uid` nas regras do Firebase.
- Reconhecer provedores de autenticação adequados para cada projeto.
- Usar observadores de sessão como mecanismo de interface, não de segurança.
- Decidir quando regras, custom claims ou back-end próprio são necessários.

## Modelo Mental

O Firebase Auth emite uma identidade. Firestore, Storage e Functions decidem o que fazer com ela. O cliente pode esconder telas, mas quem protege dados são as regras e o código confiável.

<Mermaid title="Identidade do Firebase Auth aplicada aos serviços">
{`
flowchart TD
  User["Usuário"] --> Auth["Firebase Auth<br/>login e sessão"]
  Auth --> Token["ID token<br/>uid e claims"]
  Token --> Client["Aplicação web"]
  Client --> Firestore["Firestore<br/>Security Rules"]
  Client --> Storage["Storage<br/>Security Rules"]
  Client --> Function["Cloud Function<br/>validação no servidor"]
`}
</Mermaid>

O `uid` é o identificador estável que aparece nas regras. Ele permite expressar decisões como "um usuário só lê o próprio perfil" ou "um arquivo só pode ser escrito pelo dono".

## Recursos Principais

Firebase Auth cobre vários caminhos de entrada e permite que a aplicação escolha o equilíbrio entre fricção, segurança e contexto do usuário.

| Recurso | O que entrega | Quando usar |
| --- | --- | --- |
| **E-mail e senha** | Cadastro tradicional | Sistemas educacionais e MVPs simples. |
| **Provedores sociais** | Login com Google, GitHub, Microsoft e outros | Quando a conta externa reduz atrito. |
| **Telefone e login anônimo** | Entrada rápida em apps móveis | Fluxos temporários ou verificação por número. |
| **Persistência de sessão** | Usuário continua logado entre abas e visitas | Aplicações com experiência recorrente. |
| **Custom claims** | Papéis simples no token | Autorizações por perfil, como admin ou professor. |

## Pequenos Trechos

O cadastro cria usuário e normalmente já inicia sessão. O trecho é pequeno de propósito: detalhes de formulário pertencem à etapa prática.

```js title="Cadastro mínimo com Firebase Auth"
const credential = await createUserWithEmailAndPassword(auth, email, password);
const user = credential.user;

console.log(user.uid);
```

O observador de sessão mantém a interface atualizada. Ele não substitui regra de segurança:

```js title="Observador de sessão"
onAuthStateChanged(auth, (user) => {
  renderUserMenu(user ? { email: user.email, uid: user.uid } : null);
});
```

No Firestore, a regra usa a identidade autenticada para proteger o documento:

```txt title="Security Rule usando request.auth.uid"
match /users/{uid} {
  allow read, update: if request.auth != null
    && request.auth.uid == uid;
}
```

<Aside type="caution" title="Dica de IA: O observador não é barreira de segurança">
  Código gerado costuma redirecionar o usuário deslogado e parar aí. Se a regra do Firestore
  estiver permissiva, qualquer cliente com a configuração pública do projeto ainda lê os dados.

  **Prompt:** *"Além do `onAuthStateChanged`, escreva a Security Rule que impede um usuário de ler `users/{uid}` quando `{uid}` não é igual a `request.auth.uid`, e descreva um teste negativo no emulador."*
</Aside>

## Aplicações

Firebase Auth é mais forte quando a identidade alimenta Firestore, Storage, Cloud Functions e aplicativos móveis no mesmo projeto.

| Aplicação | Como Auth ajuda | Cuidado |
| --- | --- | --- |
| Perfil de usuário | `uid` vira chave do documento. | Dados públicos e privados podem precisar de documentos separados. |
| Dados por dono | Regras com `request.auth.uid`. | Caminho e campos devem facilitar a regra. |
| Upload privado | Storage usa a mesma identidade. | Caminhos como `receipts/{uid}/...` simplificam autorização. |
| Papéis simples | Custom claims alimentam regras. | Hierarquias complexas podem ficar difíceis de manter. |

## Quando Usar, e Quando Não Usar?

Use Firebase Auth quando o projeto já vive no ecossistema Firebase ou precisa de SDKs consistentes entre web e mobile. Avalie alternativas quando a aplicação depende de banco relacional, SSO corporativo complexo ou regras de autorização difíceis de expressar em *Security Rules*.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| App web ou mobile com Firestore | **Firebase Auth** | O `uid` chega direto às regras. |
| Login social rápido | **Firebase Auth** | Provedores comuns ficam integrados ao console. |
| Dados em PostgreSQL no Supabase | **Supabase Auth** | O token conversa melhor com RLS do banco. |
| Autorização corporativa complexa | **Provedor dedicado ou back-end próprio** | Papéis, organizações e auditoria podem extrapolar as regras simples. |

## Exercício

Explique por que `user.uid` costuma aparecer no caminho do documento ou em um campo de dono.

<details>
  <summary>Possível resposta</summary>

  Porque as regras precisam comparar o recurso acessado com `request.auth.uid`. Colocar o `uid` no caminho ou no campo de dono torna essa comparação direta.
</details>

## Desafio

Defina a estratégia de identidade de uma aplicação com usuários comuns e administradores. Diga o que fica em documento público, documento privado e custom claim.

<details>
  <summary>Possível resposta</summary>

  Dados públicos, como nome de exibição, podem ficar em `profiles/{uid}`. Dados privados ficam em `users/{uid}` com regra por dono. O papel `admin` pode virar custom claim quando precisa ser lido por regras ou funções.
</details>

## Perguntas de revisão

1. **O que `request.auth.uid` representa em uma Security Rule?**
   <details>
     <summary>Possível resposta</summary>
     O identificador do usuário autenticado, derivado do token emitido pelo Firebase Auth.
   </details>

2. **Por que esconder uma tela para usuário deslogado não protege o banco?**
   <details>
     <summary>Possível resposta</summary>
     Porque o cliente é editável. A proteção precisa estar no serviço, por meio de Security Rules ou código server-side.
   </details>
