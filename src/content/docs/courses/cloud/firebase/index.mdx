O **Google Firebase** é uma plataforma de **Backend as a Service (BaaS)** abrangente que fornece infraestrutura completa na nuvem para aplicações web e móveis. Em vez de construir, configurar e manter servidores, bancos de dados e sistemas de autenticação do zero, o desenvolvedor utiliza os SDKs e APIs do Firebase para integrar recursos diretamente no front-end.

## Objetivo

Compreender o Firebase como plataforma de Backend as a Service, do contraste com a arquitetura tradicional de servidor até o recorte de serviços que uma aplicação web consome, para reconhecer os projetos em que a plataforma acelera a entrega e aqueles em que ela atrapalha. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o que muda na arquitetura de uma aplicação quando o servidor próprio é substituído por um BaaS.
- Identificar o papel de cada serviço do ecossistema: *Cloud Firestore*, *Firebase Auth*, *Cloud Storage* e *Cloud Functions*.
- Comparar o modelo de documentos do Firestore com o modelo relacional de um back-end tradicional.
- Justificar a escolha entre Firebase, Supabase e back-end próprio a partir das restrições do projeto.

## O que é um Backend as a Service (BaaS)?

Em uma arquitetura tradicional, o desenvolvimento web exige a criação de uma camada de servidor (API em Node.js, Python, Java, etc.) para conectar o front-end ao banco de dados e gerenciar segurança, sessões e uploads.

Com um **BaaS**, a nuvem abstrai essa camada inteira. A aplicação front-end comunica-se diretamente com os serviços da nuvem através de SDKs seguros:

<Mermaid title="Arquitetura Tradicional vs Arquitetura BaaS (Firebase)">
{`
flowchart TD
  subgraph Tradicional["Arquitetura Tradicional"]
    Front1["Front-End"] --> Server["Servidor Backend (Express / Django)"]
    Server --> DB1[(Banco de Dados)]
    Server --> Auth1["Sistema de Auth"]
  end

  Tradicional ~~~ BaaS

  subgraph BaaS["Arquitetura BaaS (Firebase)"]
    Front2["Front-End (Browser)"] -- "Firebase SDK" --> Cloud["Plataforma Firebase Cloud"]
    Cloud --> Firestore[(Cloud Firestore)]
    Cloud --> Auth2["Firebase Auth"]
    Cloud --> Storage["Cloud Storage"]
  end
`}
</Mermaid>

<Aside type="tip" title="Foco no Front-End e Regras de Negócio">
O uso de BaaS reduz drasticamente o tempo de prototipagem e desenvolvimento (*time-to-market*), permitindo que equipes pequenas entreguem produtos completos com persistência e autenticação em tempo recorde.
</Aside>

## Comparativo: Quando Escolher o Firebase?

A comparação com uma arquitetura tradicional mostra onde a plataforma economiza trabalho e onde ela troca uma coisa por outra. As duas primeiras linhas explicam a adoção; as três seguintes explicam o preço.

| Característica | Firebase (BaaS) | Backend Tradicional (Node.js + PostgreSQL) |
| --- | --- | --- |
| **Modelo de Banco** | NoSQL Orientado a Documentos (Firestore) | Relacional (Tabelas, Chaves Estrangeiras, SQL) |
| **Manutenção de Servidor** | Zero (100% gerenciado pela nuvem Google) | Alta (requer provisionar servidores, Docker, CI/CD) |
| **Tempo de Prototipagem** | Extremamente rápido (horas/dias) | Moderado (semanas/meses) |
| **Sincronização em Tempo Real** | Nativa (`onSnapshot`) | Requer infraestrutura WebSockets / Socket.io |
| **Custo Inicial** | Gratuito (Plano Spark com limites generosos) | Requer servidor VPS/PaaS desde o início |

## Quando usar, e quando não usar?

O comparativo acima mostra o que a plataforma entrega, mas não o que ela cobra em troca. O preço do Firebase aparece em três lugares: o modelo de documentos, que desincentiva consultas que cruzam entidades; as *Security Rules*, que passam a ser a única barreira entre o navegador e os dados; e o formato proprietário dos dados, que torna a saída da plataforma um projeto de migração, não uma exportação.

A tabela abaixo indica o que escolher em cada cenário, e contra o quê:

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Aplicação com estado compartilhado ao vivo entre usuários | **Firebase** | O `onSnapshot` do Firestore entrega sincronização em tempo real sem infraestrutura própria de WebSocket. |
| Aplicativo móvel com uso offline e sincronização posterior | **Firebase** | O SDK mantém cache local e reconcilia as escritas quando a conexão volta. |
| Dados fortemente relacionados, com relatórios e agregações | **Supabase** ([visão geral](../supabase/)) | Junções, agregações e SQL ad hoc são nativos no PostgreSQL e caros de emular em documentos. |
| Regra de negócio que não pode ser burlada pelo cliente | **Cloud Functions ou back-end próprio** | Uma regra escrita apenas no front-end é sugestão, não garantia: o cliente é editável. |
| Projeto com exigência de portabilidade ou auto-hospedagem | **Supabase ou back-end próprio** | O Firestore não roda fora da infraestrutura do Google, e o export não é um dump de banco padrão. |
| Volume alto de leituras repetidas do mesmo dado | **Cache ou banco relacional** | A cobrança do Firestore é por documento lido, então o custo cresce com o tráfego, não com o dado guardado. |

1. Qual a principal vantagem de adotar uma plataforma BaaS como o Firebase em um projeto de desenvolvimento web?
2. Em qual modelo de banco de dados o Cloud Firestore armazena suas informações?

<details>
  <summary>Possível resposta</summary>

  1. Eliminar a necessidade de construir e manter uma infraestrutura de servidor backend própria para autenticação e banco de dados, reduzindo drasticamente o tempo de desenvolvimento.

  2. No modelo NoSQL orientado a **Coleções** e **Documentos**.
</details>

## Desafio

O modelo de documentos não é o modelo relacional com outro nome, e a diferença aparece assim que os dados se relacionam. Considere uma aplicação de investimentos em que cada usuário tem uma carteira, cada carteira tem vários ativos, e cada ativo acumula um histórico de cotações.

Projete essa base duas vezes: uma como coleções e documentos do Firestore, outra como tabelas do PostgreSQL. Depois, responda a três perguntas com a sua modelagem na mão: quantas leituras o Firestore cobra para montar a tela que lista os ativos de um usuário com a última cotação de cada um; qual duplicação de dados você aceitaria para reduzir esse número; e como ficaria a regra de segurança que impede um usuário de ler a carteira de outro, nas duas plataformas.

<details>
  <summary>Possível resposta</summary>

  No modelo relacional, a tela é uma consulta com junção entre `users`, `assets` e a última linha de `quotes` por ativo. No Firestore, a mesma tela custa uma leitura por documento retornado, e o histórico em uma subcoleção obriga a uma consulta adicional por ativo, o que leva à **desnormalização**: gravar a última cotação como campo do próprio documento do ativo, aceitando escrever o valor em dois lugares para ler em um só. Essa troca é a decisão central do modelo de documentos, e ela é feita a partir das telas, não das entidades.

  A segurança segue caminhos distintos. No Firestore, a regra compara `request.auth.uid` com o dono no caminho do documento, o que empurra a modelagem para caminhos como `users/{uid}/assets/{assetId}`. No PostgreSQL do Supabase, a política RLS compara `auth.uid()` com a coluna `user_id`, e a estrutura das tabelas não precisa mudar por causa dela.
</details>

## Perguntas de revisão

1. **Qual é o papel do Cloud Functions dentro do ecossistema Firebase?**
   <details>
     <summary>Possível resposta</summary>
     Permite executar código backend personalizado em ambiente serverless em resposta a eventos acionados pelo Firestore, Auth ou requisições HTTP sem precisar manter um servidor ligado 24/7.
   </details>

2. **Como o Firebase Auth garante que requisições ao Firestore sejam seguras no lado do cliente?**
   <details>
     <summary>Possível resposta</summary>
     Através das Regras de Segurança (*Security Rules*) do Firestore na nuvem, que validam a identidade do usuário autenticado (`request.auth.uid`) antes de conceder permissão de leitura ou escrita.
   </details>
