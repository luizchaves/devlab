O **Firebase Hosting** publica sites estáticos e aplicações web em uma CDN gerenciada pelo Google. Ele se integra ao mesmo projeto que já contém Auth, Firestore, Storage e Functions.

## Objetivo

Compreender o papel do Firebase Hosting na entrega de front-ends, separando arquivos estáticos, rewrites e integração com funções. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o que é servido como arquivo estático.
- Configurar rewrites para aplicações de página única.
- Diferenciar variável pública do front-end e segredo de função.
- Relacionar Hosting e Cloud Functions quando uma rota precisa de servidor.
- Decidir quando usar Firebase Hosting, Vercel, Netlify ou Cloudflare Pages.

## Do Build ao CDN

O Firebase Hosting recebe a pasta gerada pelo build e distribui os arquivos por CDN. Em uma aplicação Vite, essa pasta costuma ser `dist/`.

<Mermaid title="Publicação de front-end pelo Firebase Hosting">
{`
flowchart TD
  Repo["Projeto web"] --> Build["npm run build"]
  Build --> Dist["dist/<br/>HTML, CSS e JS"]
  Dist --> Hosting["Firebase Hosting"]
  Hosting --> CDN["CDN e TLS gerenciados"]
  CDN --> Browser["Navegador"]
`}
</Mermaid>

Como em qualquer hospedagem estática, o JavaScript publicado é público. Segredos e operações privilegiadas ficam em Cloud Functions.

<Aside type="danger" title="Variável pública não é segredo">
  A configuração web do Firebase identifica o projeto e permite que o SDK encontre os serviços. Ela não substitui regras de segurança. Qualquer valor embutido no front-end pode ser lido por quem abre o site publicado.
</Aside>

## Rewrites e Funções

Aplicações de página única precisam de rewrite para que `/dashboard` carregue o mesmo `index.html` quando o usuário recarrega a aba. Rotas que precisam de servidor podem ser encaminhadas para uma Cloud Function.

| Necessidade | Configuração | Resultado |
| --- | --- | --- |
| Rota interna de SPA | Rewrite para `index.html` | O roteador do front-end assume depois do carregamento. |
| API curta com segredo | Rewrite para função HTTP | O servidor roda fora do navegador. |
| Arquivo estático | Publicação direta | CDN entrega o arquivo sem função. |

## Executando

O fluxo de publicação é curto, mas a validação precisa testar rota interna e regras:

<Steps>
1. Gere o build da aplicação com o comando do projeto.
2. Configure a pasta pública, normalmente `dist`.
3. Adicione rewrite para `index.html` se a aplicação usa roteamento client-side.
4. Publique no Firebase Hosting.
5. Abra uma rota interna diretamente pela URL publicada para confirmar que ela não devolve 404.
</Steps>

## Exercício

Por que uma aplicação SPA precisa de rewrite para `index.html` em produção?

<details>
  <summary>Possível resposta</summary>

  Porque a rota interna não existe como arquivo físico no servidor. O Hosting precisa entregar `index.html`, e o JavaScript da aplicação decide qual tela renderizar.
</details>

## Desafio

Defina uma arquitetura em que o Firebase Hosting entrega o front-end do InvestApp e uma Cloud Function atende `/api/quote` com uma chave privada.

<details>
  <summary>Possível resposta</summary>

  O build do front-end vai para Hosting. A rota `/api/quote` é reescrita para uma função HTTP que lê a chave do ambiente, consulta o provedor externo e devolve apenas a cotação calculada. A chave nunca entra no bundle.
</details>

## Perguntas de revisão

1. **O que o Firebase Hosting serve diretamente?**
   <details>
     <summary>Possível resposta</summary>
     Arquivos gerados pelo build, como HTML, CSS, JavaScript, imagens e assets.
   </details>

2. **Quando uma rota do Hosting deve apontar para Cloud Functions?**
   <details>
     <summary>Possível resposta</summary>
     Quando ela precisa executar código no servidor, acessar segredo ou aplicar uma regra que não pode ficar no navegador.
   </details>
