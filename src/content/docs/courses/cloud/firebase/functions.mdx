O **Cloud Functions for Firebase** executa código serverless em resposta a requisições HTTP, mudanças no Firestore, eventos do Auth, uploads no Storage e tarefas agendadas. Ele é o lugar do código que precisa ficar fora do navegador.

## Objetivo

Compreender quando uma aplicação Firebase precisa de função serverless, distinguindo regra de segurança, gatilho de evento e integração com segredo. Ao final do tópico, o leitor deve ser capaz de:

- Explicar a diferença entre código do SDK cliente e código de função.
- Identificar gatilhos HTTP, Firestore, Auth, Storage e Scheduler.
- Reconhecer quando usar o Admin SDK com responsabilidade.
- Planejar idempotência para eventos repetidos.
- Decidir entre Cloud Functions, back-end próprio e regras declarativas.

## Eventos que Chamam Código

No Firebase, parte da lógica pode reagir ao que aconteceu em outro serviço. Um documento criado no Firestore pode disparar uma função; um usuário cadastrado no Auth pode gerar perfil inicial; um upload no Storage pode criar miniatura.

<Mermaid title="Gatilhos comuns de Cloud Functions for Firebase">
{`
flowchart TD
  HTTP["Requisição HTTP"] --> Fn["Cloud Function"]
  Firestore["Mudança no Firestore"] --> Fn
  Auth["Usuário criado no Auth"] --> Fn
  Storage["Arquivo enviado ao Storage"] --> Fn
  Schedule["Agendamento"] --> Fn
  Fn --> Admin["Admin SDK<br/>acesso privilegiado"]
  Admin --> Project["Serviços do projeto Firebase"]
`}
</Mermaid>

O Admin SDK é poderoso justamente porque ignora as regras pensadas para clientes. Isso é útil para tarefas internas, mas exige validação explícita na função.

<Aside type="caution" title="Dica de IA: Peça idempotência para gatilhos de evento">
  Funções acionadas por eventos podem rodar novamente em caso de falha ou repetição de entrega. Código gerado costuma assumir execução única e cria duplicatas em e-mails, cobranças ou documentos derivados.

  **Prompt:** *"Reescreva esta função acionada por criação de documento para ser idempotente; use um identificador estável do evento e mostre o que acontece se o mesmo evento for entregue duas vezes."*
</Aside>

## Quando Usar

Uma função entra quando a decisão precisa rodar em ambiente confiável ou quando um evento de serviço deve produzir outro efeito.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Validar webhook de pagamento | **Função HTTP** | A assinatura e o segredo ficam no servidor. |
| Criar perfil ao cadastrar usuário | **Gatilho de Auth** | O evento nasce no serviço de identidade. |
| Gerar miniatura após upload | **Gatilho de Storage** | O processamento acontece depois que o arquivo chega. |
| Bloquear leitura de documentos por dono | **Security Rules** | Autorização de acesso direto deve ficar na regra, não em função. |
| API extensa e persistente | **Back-end próprio** | Muitas rotas e regras complexas tendem a ficar mais claras em um servidor dedicado. |

## Executando

Antes de publicar uma função, defina seu gatilho e seu contrato:

<Steps>
1. Escolha o evento: HTTP, Firestore, Auth, Storage ou agendamento.
2. Liste os dados recebidos e o que precisa ser validado antes de agir.
3. Defina se a função usará Admin SDK e quais efeitos isso permite.
4. Torne a operação idempotente quando o evento puder ser repetido.
5. Teste no emulador antes do deploy.
</Steps>

## Exercício

Por que uma função que usa Admin SDK não deve confiar apenas no `uid` enviado pelo corpo da requisição?

<details>
  <summary>Possível resposta</summary>

  Porque o corpo é controlado pelo cliente. Como o Admin SDK tem acesso privilegiado, a função precisa validar o token ou derivar a identidade de uma fonte confiável antes de executar a ação.
</details>

## Desafio

Projete uma função para criar um documento `profiles/{uid}` quando um usuário novo é criado no Firebase Auth. Ela deve evitar duplicação caso o evento seja entregue duas vezes.

<details>
  <summary>Possível resposta</summary>

  A função usa o `uid` do evento como chave do documento e faz uma escrita idempotente em `profiles/{uid}`. Se o documento já existir, ela não cria outro perfil; no máximo atualiza campos seguros como `updatedAt`.
</details>

## Perguntas de revisão

1. **Qual é a diferença entre Security Rules e Cloud Functions?**
   <details>
     <summary>Possível resposta</summary>
     Security Rules autorizam acesso direto de clientes aos serviços. Cloud Functions executam código serverless em resposta a HTTP ou eventos.
   </details>

2. **Por que gatilhos de evento precisam ser idempotentes?**
   <details>
     <summary>Possível resposta</summary>
     Porque a entrega pode ser repetida. Se a função assumir execução única, pode duplicar efeitos como documentos, e-mails ou cobranças.
   </details>
