O **Cloud Firestore** é o banco de dados de documentos do Firebase. Ele organiza dados em coleções e documentos, sincroniza mudanças em tempo real, oferece cache offline nos SDKs e protege acesso por *Security Rules*.

## Objetivo

Compreender o Firestore como banco orientado ao formato de leitura da aplicação, não como uma tabela SQL com sintaxe diferente, para modelar dados, consultas e regras sem depender de gambiarras no cliente. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar coleção, documento e subcoleção.
- Explicar por que o `id` do documento fica fora dos dados.
- Planejar consultas a partir das telas que a aplicação precisa carregar.
- Relacionar índices e *Security Rules* ao desenho dos caminhos.
- Reconhecer quando um banco relacional é uma escolha melhor.

## Modelo Mental

No Firestore, um documento é a unidade de leitura, escrita e cobrança. Coleções agrupam documentos, e subcoleções criam novos agrupamentos abaixo de um documento.

<Mermaid title="Modelo de coleções e documentos no Cloud Firestore">
{`
flowchart TD
  Users["coleção users"] --> Ana["documento users/ana"]
  Ana --> Profile["campos<br/>name, email"]
  Ana --> Investments["subcoleção investments"]
  Investments --> Asset["documento investments/asset-1"]
  Asset --> Fields["campos<br/>name, amount, category"]
`}
</Mermaid>

Esse modelo incentiva desenhar o dado pela tela que será lida. Se a tela precisa listar todos os investimentos do usuário, faz sentido que o caminho ou o campo de dono torne essa consulta direta.

## Recursos Principais

O Firestore combina banco de documentos, consultas indexadas, sincronização e regras declarativas. A tabela abaixo mostra como esses recursos afetam arquitetura:

| Recurso | O que resolve | Cuidado |
| --- | --- | --- |
| **Coleções e documentos** | Estrutura flexível em JSON | Flexível não significa sem modelagem. |
| **Subcoleções** | Dados naturalmente pertencentes a um documento | Consultas globais ficam menos diretas. |
| **Consultas indexadas** | Filtros e ordenação previsíveis | Algumas combinações exigem índice composto. |
| **Listeners em tempo real** | Atualização automática da interface | É preciso carregar estado inicial e lidar com reconexão. |
| **Cache offline** | Uso temporário sem rede | Conflitos e sincronização continuam sendo decisões do app. |
| **Security Rules** | Autorização no serviço | Regra permissiva expõe dados direto pelo SDK. |

## Pequenos Trechos

A leitura de uma coleção usa funções do SDK modular. O `id` precisa ser reunido aos campos porque ele pertence ao caminho do documento:

```js title="Leitura de documentos com id"
const snapshot = await getDocs(collection(db, 'investments'));

const investments = snapshot.docs.map((item) => ({
  id: item.id,
  ...item.data(),
}));
```

Uma consulta filtrada deve nascer de uma pergunta de tela. O exemplo abaixo lista investimentos de um usuário em uma categoria específica:

```js title="Consulta por dono e categoria"
const q = query(
  collection(db, 'investments'),
  where('user_id', '==', user.uid),
  where('category', '==', 'Renda Fixa')
);
```

As regras de segurança precisam expressar a mesma posse no serviço, e não apenas na interface:

```txt title="Security Rule por dono do documento"
match /investments/{investmentId} {
  allow read, update, delete: if request.auth != null
    && request.auth.uid == resource.data.user_id;

  allow create: if request.auth != null
    && request.auth.uid == request.resource.data.user_id;
}
```

<Aside type="caution" title="Dica de IA: Firestore não faz junção escondida">
  Assistentes costumam traduzir uma consulta SQL para várias leituras no cliente e chamar isso de solução. Funciona com poucos documentos, mas muda custo, latência e consistência.

  **Prompt:** *"Para esta tela de carteira, conte quantos documentos o Firestore precisa ler, diga quais dados devem ser desnormalizados e indique quais consultas exigem índice composto."*
</Aside>

## Aplicações

O Firestore favorece aplicações em que a tela lê documentos previsíveis, usuários editam dados ao vivo e o offline importa. Ele é menos confortável para relatórios, junções e exploração ad hoc.

| Aplicação | Como Firestore ajuda | Limite |
| --- | --- | --- |
| App móvel com offline | SDK mantém cache e sincroniza depois. | Conflitos precisam de regra clara. |
| Quadro colaborativo ou painel ao vivo | Listeners atualizam a tela. | Eventos não substituem modelagem. |
| CRUD simples por usuário | Documento por item e regra por dono. | Relatórios agregados ficam caros. |
| Busca e analytics | **Melhor usar serviço dedicado** | Firestore não é motor de busca textual nem banco analítico. |

## Quando Usar, e Quando Não Usar?

Use Firestore quando o dado acompanha telas, documentos e sincronização. Prefira banco relacional quando o sistema depende de relações fortes, agregações frequentes, joins, relatórios ou migração simples para outra infraestrutura.

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Dados lidos por documento ou coleção pequena | **Firestore** | A leitura é direta e previsível. |
| Uso offline e atualização ao vivo | **Firestore** | O SDK já oferece esses recursos. |
| Carteira com agregações e relatórios SQL | **Supabase ou PostgreSQL** | Junções e somatórios são nativos no relacional. |
| Busca textual rica | **Serviço de busca** | Firestore filtra campos, mas não substitui busca full-text. |

## Exercício

Explique a diferença entre guardar investimentos em `investments/{id}` com campo `user_id` e em `users/{uid}/investments/{id}`.

<details>
  <summary>Possível resposta</summary>

  A coleção global facilita consultas administrativas, mas exige regras por campo `user_id`. A subcoleção coloca o dono no caminho, simplificando regras por usuário, mas torna consultas globais mais específicas.
</details>

## Desafio

Modele a tela "minha carteira" do InvestApp no Firestore. Defina caminho, campos mínimos, regra de segurança e uma consulta principal.

<details>
  <summary>Possível resposta</summary>

  Uma opção é `users/{uid}/investments/{investmentId}` com campos `name`, `amount`, `category`, `created_at` e `updated_at`. A regra compara `{uid}` com `request.auth.uid`, e a consulta lê a subcoleção do usuário ordenada por `created_at`.
</details>

## Perguntas de revisão

1. **Qual é a unidade de leitura e cobrança no Firestore?**
   <details>
     <summary>Possível resposta</summary>
     O documento. Consultas que retornam muitos documentos geram muitas leituras.
   </details>

2. **Por que Security Rules são parte da arquitetura, não detalhe de console?**
   <details>
     <summary>Possível resposta</summary>
     Porque o cliente fala diretamente com o serviço. As regras são a barreira que impede leitura e escrita indevidas.
   </details>
