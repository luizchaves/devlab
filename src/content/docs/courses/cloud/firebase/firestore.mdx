O **Cloud Firestore** é o banco de dados NoSQL orientado a documentos do **Google Firebase**. Projetado para armazenar e sincronizar dados entre aplicações cliente e servidor em tempo real, o Firestore organiza os dados em **coleções** que contêm **documentos**, com suporte a consultas ricas, transações e regras de segurança na nuvem.

## Objetivo

Compreender o modelo de coleções e documentos do Cloud Firestore e traduzi-lo em um módulo de serviço que a aplicação consome, do `addDoc` que cria o documento ao `where` que filtra a consulta, reconhecendo onde esse modelo difere de uma tabela relacional. Ao final do tópico, o leitor deve ser capaz de:

- Descrever a hierarquia de coleções, documentos e subcoleções do Firestore.
- Inicializar o SDK do Firebase a partir de variáveis de ambiente do projeto.
- Implementar as quatro operações com `addDoc`, `getDocs`, `updateDoc` e `deleteDoc`.
- Compor consultas filtradas com `query()` e `where()` e reconhecer seus limites.
- Explicar por que o identificador do documento vive fora dos dados e precisa ser reunido a eles na leitura.

## Modelo de Dados NoSQL do Firestore

Diferente dos bancos relacionais (SQL), o Firestore não utiliza tabelas ou linhas. Os dados são organizados em **Coleções** que abrigam **Documentos** em formato similar a JSON:

  end
  
  Doc1 --- Doc1Content
`}

### Criar um Documento (`create`)

O `addDoc` insere o documento e deixa o Firestore gerar o identificador. Repare na linha 14: uma data precisa virar objeto `Date` antes de ser gravada, porque o SDK a converte em *Timestamp*, e uma string ficaria armazenada como texto. Como o `id` só existe depois da escrita, a linha 20 o reúne aos dados para devolver o registro completo:

<SourceCode path="examples/courses/cloud/firebase-firestore/invest-app/js/services/storage.js" lines="13-21" mark={[14, 20]} />

A chamada a partir da aplicação envia apenas o nome da coleção e o objeto:

```js title="Exemplo de chamada para criar investimento"
import API from './services/storage.js';

const investment = {
  name: 'Tesouro Selic 2029',
  value: 10000,
  origin: 'Tesouro Direto',
  category: 'Pós',
  interest: '100% Selic',
  created_at: '2021-09-10T00:00:00-03:00',
};

await API.create('investments', investment);
```

### Ler e Filtrar Documentos (`read`)

A mesma função atende à listagem e à consulta filtrada. O filtro é montado na linha 31 com `query()` e `where()`, e não na URL como no PostgREST. A linha 38 é a que mais revela o modelo do Firestore: o identificador não faz parte dos dados do documento, então precisa ser reunido a eles a cada leitura:

<SourceCode path="examples/courses/cloud/firebase-firestore/invest-app/js/services/storage.js" lines="23-41" mark={[31, 38]} />

Do lado de quem chama, a diferença entre listar tudo e filtrar é a presença dos dois últimos argumentos:

```js title="Exemplo de busca de investimentos"
import API from './services/storage.js';

// Busca todos os investimentos
const todos = await API.read('investments');

// Busca investimentos filtrados pela categoria 'Pós'
const pos = await API.read('investments', 'category', 'Pós');
```

<Aside type="caution" title="Dica de IA: Confirme se a consulta sugerida existe no Firestore">
  Consultas que um banco relacional resolve sem esforço não têm equivalente aqui, e assistentes preenchem a lacuna com código plausível: `where` com `OR` entre campos diferentes, `like` para busca textual, ou ordenação por um campo enquanto se filtra por outro sem o índice composto correspondente. O erro só aparece em tempo de execução, quando o Firestore recusa a consulta.

  **Prompt:** *"Para a coleção `investments` com os campos `category`, `value` e `created_at`, liste quais destas consultas o Firestore aceita sem índice composto, quais exigem índice e quais são impossíveis; para as impossíveis, mostre como reorganizar os dados."*
</Aside>

### Atualizar um Documento (`update`)

O `updateDoc` precisa de uma referência direta ao documento, construída na linha 46 a partir da coleção e do `id`. Diferente do `setDoc`, ele mescla os campos enviados com os que já existem, em vez de substituir o documento inteiro:

<SourceCode path="examples/courses/cloud/firebase-firestore/invest-app/js/services/storage.js" lines="43-51" mark={[46]} />

A chamada envia o `id` dentro do próprio objeto de dados:

```js title="Exemplo de atualização de investimento"
import API from './services/storage.js';

await API.update('investments', { id: 'ID_DO_DOCUMENTO', value: 15000 });
```

A remoção segue o mesmo par de passos: montar a referência e aplicar a operação. O `deleteDoc` não devolve o documento apagado, e apagar algo inexistente não é erro:

## Quando usar, e quando não usar?

O Firestore é excelente no que foi projetado para fazer, e desconfortável fora disso. Ele foi desenhado para leituras rápidas e previsíveis de dados moldados pela tela que os exibe, com sincronização entre dispositivos. Consultas exploratórias, relatórios e agregações não são o seu terreno.

A tabela abaixo confronta cada necessidade com a opção que a atende melhor:

| Cenário | Escolha | Por quê |
| --- | --- | --- |
| Dados que precisam aparecer ao vivo em várias telas | **Firestore** | O `onSnapshot` entrega as mudanças sem polling nem servidor de WebSocket. |
| Aplicativo que precisa funcionar sem conexão | **Firestore** | O SDK mantém cache local e sincroniza quando a rede volta. |
| Consultas que cruzam entidades, agregam ou somam | **[Supabase](../../supabase/)** ou outro banco relacional | Junções e agregações são nativas em SQL e custosas de emular em documentos. |
| Busca textual dentro do conteúdo dos documentos | **Serviço de busca dedicado** | O Firestore não indexa texto livre; só compara valores. |
| Relatório sobre um volume grande de registros | **Exportar para um banco analítico** | A cobrança é por documento lido, o que torna varreduras caras. |
| Migração futura para outra infraestrutura | **Banco relacional gerenciado** | O export do Firestore é proprietário e exige conversão antes de virar tabelas. |

## Desafio

A função `read` desta página traz a coleção inteira a cada chamada, e cada documento devolvido é cobrado. Reescreva a leitura para paginar os resultados com `orderBy`, `limit` e `startAfter`, mantendo a assinatura simples para quem chama.

Além da paginação, resolva um problema que o modelo de documentos impõe: a tela precisa mostrar o total de investimentos por categoria, e percorrer todos os documentos para contar é justamente o que se quer evitar. Descreva a estratégia e o preço que ela cobra.

<details>
  <summary>Possível resposta</summary>

  A paginação do Firestore é por cursor, não por deslocamento: não existe "pule 200 registros", existe "continue a partir deste documento". Quem chama guarda o último documento da página anterior e o devolve na chamada seguinte:

  ```js title="Esboço da leitura paginada"
  async function readPage(resource, { pageSize = 10, cursor } = {}) {
    const colRef = collection(db, resource);
    const constraints = [orderBy('created_at', 'desc'), limit(pageSize)];

    if (cursor) {
      constraints.push(startAfter(cursor));
    }

    const snapshot = await getDocs(query(colRef, ...constraints));
    const items = snapshot.docs.map((docRef) => ({ ...docRef.data(), id: docRef.id }));

    return { items, cursor: snapshot.docs.at(-1) ?? null };
  }
  ```

  Para o total por categoria há dois caminhos. O `getCountFromServer()` conta sem transferir os documentos e é o mais simples, embora ainda cobre pela contagem. O caminho tradicional é manter um documento de contadores atualizado a cada escrita, com `increment()`, dentro de uma transação ou de uma *Cloud Function*. O preço é a consistência: o contador pode divergir se uma escrita falhar depois da outra, e reconciliá-lo exige justamente a varredura que ele foi criado para evitar.
</details>

## Perguntas de revisão

1. **O que acontece se usarmos `addDoc` em vez de `setDoc` para inserir dados no Firestore?**
   <details>
     <summary>Possível resposta</summary>
     O `addDoc` gera automaticamente um ID alfanumérico único para o novo documento, enquanto o `setDoc` exige que você forneça um ID manualmente.
   </details>

2. **Como obter atualizações em tempo real do banco de dados sempre que um documento for alterado por outro usuário?**
   <details>
     <summary>Possível resposta</summary>
     Utilizando a função `onSnapshot(docRef, (doc) => { ... })` em vez de `getDocs()`.
   </details>
