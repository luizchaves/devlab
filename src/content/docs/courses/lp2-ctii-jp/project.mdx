O projeto da disciplina é desenvolvido de forma incremental ao longo do semestre. Cada
bimestre tem duas entregas (B1.1, B1.2, B2.1, ...), e cada uma acrescenta uma camada à
aplicação: primeiro o front-end, depois o back-end em Node.js, a persistência em banco
de dados, a autenticação de usuários, validação, envio de e-mail, upload de arquivos e,
por fim, os testes automatizados.

O tema do projeto é **livre**, mas precisa ser definido pela equipe antes da primeira
entrega e mantido ao longo de todas as etapas: é a mesma aplicação que ganha camadas a
cada bimestre. Escolha um domínio com ao menos um recurso que possa ser cadastrado,
listado, editado e removido (investimentos, tarefas, receitas, eventos, livros...), pois
todas as avaliações partem desse CRUD.

As entregas seguem a ordem abaixo, e cada uma pressupõe a anterior concluída:

<Steps>

1. **[B1.1 - Front-end](#b11---front-end)**
   - Páginas estilizadas, dados em JSON, interface gerada dinamicamente, módulos ESM e
     eventos.

2. **[B1.2 - Back-end e Integração com o Front-end](#b12---back-end-e-integração-com-o-front-end)**
   - API REST com Express e dados em memória, testes com REST Client e consumo com
     `fetch`.

3. **[B2.1 - Banco de Dados com SQL](#b21---banco-de-dados-com-sql)**
   - Modelagem relacional, MVC, migration e seed em SQL e CRUD com consultas
     parametrizadas.

4. **[B2.2 - Banco de Dados com Prisma](#b22---banco-de-dados-com-prisma)**
   - `schema.prisma`, diagrama ERD, migrations, seed, Prisma Client e CRUD pelo front-end.

5. **[B3.1 - Autenticação de usuário](#b31---autenticação-de-usuário)**
   - Hash de senha, cadastro e login, sessão ou JWT, middleware de proteção e front
     autenticado.

6. **[B3.2 - Validação e Envio de E-mail](#b32---validação-e-envio-de-e-mail)**
   - Schemas com Zod, middleware genérico, respostas `400`, serviço de e-mail e retorno
     no front.

7. **[B4.1 - Upload de Arquivos](#b41---upload-de-arquivos)**
   - Multer com limites e filtros, rotas protegidas, arquivo associado ao usuário e
     `FormData`.

8. **[B4.2 - Testes Automatizados](#b42---testes-automatizados)**
   - Unidade, rotas com Supertest, front com Vitest, E2E com Playwright e cobertura com
     piso.

</Steps>

Esta página reúne o enunciado de cada etapa, com os aspectos que devem aparecer no
código e a pontuação de cada item. As etapas mais recentes ficam no topo, e cada uma
termina com uma dica de prompt para autoavaliação com um assistente de IA.

<Aside type="note" title="Regras comuns a todas as etapas">
Mantenha o repositório atualizado até o dia da apresentação. Cada integrante deverá
estar preparado para responder questionamentos sobre o projeto e para demonstrar, no
código, como cada aspecto cobrado foi implementado.
</Aside>

## B4.2 - Testes Automatizados

Esta atividade consiste em evoluir o projeto da disciplina, especificamente aplicando os
conceitos de testes automatizados em uma aplicação Web integrada ao back-end em
Node.js/Express.js. O comportamento da aplicação não muda nesta etapa: o que entra é a
garantia de que ele continua valendo depois da próxima alteração, com testes de unidade,
de rotas, de front-end e de ponta a ponta, além de cobertura com piso mínimo.

Mostre no código como foram aplicados os seguintes aspectos:

<Steps>

1. **Testes de Unidade (20pts)**

   Quais funções puras do projeto foram testadas de forma isolada? Demonstre testes
   escritos com `node:test` (ou ferramenta equivalente) sobre schemas de validação,
   funções utilitárias (ex.: formatação de valores, parser de cookies) e regras de
   negócio, cobrindo o caminho válido, entradas inválidas e casos de borda (valor ausente,
   string vazia, encoding inválido). Os testes de unidade não podem depender de servidor,
   banco ou rede.

2. **Testes de Rotas da API (20pts)**

   Como as rotas foram testadas sem abrir porta? Demonstre a separação entre o `app`
   (exportado) e o `listen`, e os testes com `supertest` que exercitam as principais rotas
   da API, incluindo criação, consulta, atualização e remoção, respostas de erro (`400`,
   `401`, `404`, `409`) e ao menos uma regra crítica de autorização (ex.: um usuário não
   acessa os dados de outro). A suíte deve poder ser executada repetidas vezes sem falhar
   por dados duplicados, e nenhum e-mail real pode ser enviado durante os testes.

3. **Testes do Front-end com Mocks (20pts)**

   Como os módulos JavaScript do front-end foram testados sem navegador? Demonstre testes
   com Vitest e JSDOM (ou equivalente) sobre o módulo que fala com a API, substituindo
   `fetch` e `localStorage` por dublês (mocks) e verificando a URL, o método, os
   cabeçalhos (ex.: `Authorization`) e o tratamento das respostas de sucesso e de erro.

4. **Testes de Ponta a Ponta (20pts)**

   Como um fluxo completo do usuário foi verificado no navegador? Demonstre ao menos um
   teste E2E com Playwright (ou equivalente) que percorre cadastro ou login, criação de um
   registro pela interface e verificação do resultado na tela, utilizando localizadores
   por papel acessível (`getByRole`, `getByLabel`) e dados isolados por execução.
   Apresente o arquivo de configuração e como o servidor é iniciado para o teste.

5. **Cobertura e Scripts de Execução (20pts)**

   Como a qualidade da suíte é medida e mantida? Demonstre os scripts do `package.json`
   para executar cada tipo de teste (`test`, `front:test`, `e2e`, `coverage`), o relatório
   de cobertura do servidor e do front-end com as linhas não cobertas por arquivo, e um
   piso de cobertura configurado que faz o comando falhar quando a suíte regride. Explique
   a separação entre os testes rápidos (executados a cada alteração) e os fluxos
   completos.

</Steps>

Também serão avaliados organização dos arquivos de teste, nomes descritivos dos casos,
separação de responsabilidades, clareza e qualidade do código, documentação mínima, uso
adequado de TypeScript, variáveis de ambiente, instruções de execução e o quanto a
aplicação precisou mudar para ser testável (quanto menos, melhor).

Mantenha o repositório atualizado até o dia da apresentação. Cada integrante deverá
estar preparado para executar a suíte ao vivo, explicar o que cada tipo de teste garante,
demonstrar sua implementação no código e responder questionamentos sobre as decisões
adotadas no projeto.

## B4.1 - Upload de Arquivos

Esta atividade consiste em evoluir o projeto da disciplina, especificamente aplicando os
conceitos de upload de arquivos em uma aplicação Web integrada ao back-end em
Node.js/Express.js. O projeto deverá permitir que o usuário autenticado envie ao menos
um arquivo (ex.: imagem de avatar do perfil ou anexo de um registro), armazená-lo com
segurança no servidor, associá-lo ao registro correspondente no banco e exibi-lo na
interface.

Mostre no código como foram aplicados os seguintes aspectos:

<Steps>

1. **Configuração do Upload com Multer (20pts)**

   Como o recebimento de `multipart/form-data` foi configurado? Demonstre a configuração
   do Multer (ou equivalente) com destino em disco, nome de arquivo **gerado pelo
   servidor** (nunca o nome enviado pelo cliente, para evitar sobrescrita e caminhos
   maliciosos), limite de tamanho (ex.: 2 MB) e filtro por tipo MIME com lista permitida
   (ex.: `image/jpeg`, `image/png`, `image/gif`). Explique o que acontece com um arquivo
   recusado: a resposta deve ser `400` e nada pode ser gravado em disco.

2. **Rotas de Upload Protegidas (20pts)**

   Quais rotas recebem o arquivo e como elas foram protegidas? Demonstre as rotas de envio
   e de atualização (ex.: `POST` e `PUT /api/users/image`) com o middleware de
   autenticação executando **antes** do Multer, de modo que uma requisição sem token
   receba `401` sem processar o arquivo. Mostre a resposta `201` com o caminho público do
   arquivo e o tratamento dos erros de tamanho e de tipo no middleware de erros da
   aplicação.

3. **Persistência e Associação ao Usuário (20pts)**

   Como o arquivo foi ligado ao registro no banco? Demonstre o model (ex.: `Image`) no
   `schema.prisma` com o relacionamento com o usuário autenticado, a migration
   correspondente e a regra de um arquivo por registro: um novo envio atualiza o caminho
   em vez de criar um segundo registro. Mostre também como a pasta de uploads é servida
   como conteúdo estático e como ela fica fora do controle de versão (`.gitignore`),
   mantendo a estrutura necessária para a aplicação subir do zero.

4. **Testes das Rotas de Upload (20pts)**

   Como o projeto demonstra que o upload funciona corretamente? Apresente testes
   utilizando arquivos `requests.http` com a extensão REST Client do VSCode, contemplando,
   no mínimo: envio sem autenticação (`401`), envio válido (`201`), acesso ao caminho
   devolvido pela API (a imagem é exibida), arquivo maior que o limite (`400`), tipo não
   permitido (`400`) e reenvio pelo mesmo usuário (caminho atualizado). Mostre como o
   token e o arquivo são informados na requisição `multipart/form-data`.

5. **Upload e Exibição no Front-end (20pts)**

   Como o front-end envia e exibe o arquivo? Demonstre o formulário com `<input
   type="file">` e o envio com `FormData` pelo `fetch` (sem definir `Content-Type`
   manualmente), a inclusão do token na requisição, a pré-visualização ou o retorno visual
   após o envio, a exibição dos erros de tamanho e tipo ao usuário e o uso do arquivo
   enviado nas demais telas da aplicação (ex.: avatar no cabeçalho, na lista ou no
   perfil).

</Steps>

Também serão avaliados organização dos arquivos, separação de responsabilidades,
clareza e qualidade do código, documentação mínima, uso adequado de TypeScript,
variáveis de ambiente, segurança das informações sensíveis, tratamento de erros,
instruções de execução, experiência do usuário, responsividade e qualidade
visual/estilização da aplicação.

Mantenha o repositório atualizado até o dia da apresentação. Cada integrante deverá
estar preparado para explicar o caminho de um arquivo desde o formulário até o disco e
o banco, demonstrar sua implementação no código e responder questionamentos sobre as

## B3.2 - Validação e Envio de E-mail

Esta atividade consiste em evoluir o projeto da disciplina, especificamente aplicando
os conceitos de validação de dados e de envio de e-mail em uma aplicação Web integrada
ao back-end em Node.js/Express.js. O projeto deverá garantir que nenhum dado inválido
chegue aos Controllers, Models ou ao banco, e deverá notificar o usuário por e-mail em
ao menos um evento da aplicação, como a confirmação de cadastro.

Mostre no código como foram aplicados os seguintes aspectos:

<Steps>

1. **Schemas de Validação e Middleware Genérico (20pts)**

   Como a validação foi organizada no back-end? Demonstre os schemas criados com uma
   biblioteca de validação (ex.: Zod) para as fontes de entrada da requisição (`body`,
   `params` e `query`), com regras como campos obrigatórios, tamanho mínimo, formato
   (UUID, e-mail) e valores numéricos positivos. Apresente um middleware genérico de
   validação (ex.: `validate(schema)`) que é aplicado na declaração das rotas e que
   executa **antes** do Controller, mostrando que os Controllers e Models não repetem
   verificações manuais com `if`.

2. **Respostas de Erro de Validação (20pts)**

   Como a API responde a dados inválidos? Demonstre que a entrada inválida retorna `400
   Bad Request` com um corpo que identifica **qual campo** falhou e **por quê** (ex.:
   lista de `issues` com `path` e `message`), e que esse tratamento está centralizado no
   middleware de erros da aplicação. Explique a diferença entre `400` (formato inválido),
   `404` (recurso inexistente) e `409` (conflito, como e-mail já cadastrado), com exemplos
   de cada caso no projeto.

3. **Serviço de Envio de E-mail (20pts)**

   Como o envio de e-mail foi implementado? Demonstre a configuração SMTP por variáveis de
   ambiente (`.env` e `.env.example`, sem credenciais no repositório), o serviço isolado
   responsável pelo envio (ex.: `services/SendMail.ts` com Nodemailer) e o uso de uma
   conta de teste em desenvolvimento, com URL de prévia da mensagem no terminal. A
   mensagem deve ter versão em HTML e em texto puro, e a biblioteca de e-mail deve
   aparecer apenas na configuração e no serviço, nunca em rotas ou Controllers.

4. **Integração do E-mail ao Fluxo da Aplicação e Testes (20pts)**

   Em qual evento o e-mail é disparado e como isso foi integrado ao Controller? Demonstre,
   no mínimo, o envio de uma mensagem de boas-vindas após o cadastro bem-sucedido,
   garantindo que um cadastro recusado não envia nada e que uma falha no SMTP não derruba
   a requisição (o cadastro continua respondendo `201` e a falha é registrada no log).
   Apresente testes em arquivos `requests.http` com a extensão REST Client do VSCode,
   contemplando requisições válidas, corpo inválido, parâmetro de rota inválido, query
   inválida e o cadastro que dispara o e-mail.

5. **Validação e Retorno ao Usuário no Front-end (20pts)**

   Como o front-end dá retorno imediato ao usuário? Demonstre a validação nativa do HTML
   nos formulários (`required`, `minlength`, `type="email"`, `pattern`) e a validação com
   JavaScript (ex.: confirmação de senha com `setCustomValidity`), a exibição dos erros
   retornados pela API **no campo correspondente** (ex.: e-mail já cadastrado) e mensagens
   de sucesso ou de erro genérico (ex.: toast). Explique por que a validação do front-end
   é retorno ao usuário e não proteção, e por que as mesmas regras são repetidas na API e
   no banco.

</Steps>

Também serão avaliados organização dos arquivos, separação de responsabilidades,
clareza e qualidade do código, documentação mínima, uso adequado de TypeScript,
variáveis de ambiente, segurança das informações sensíveis, tratamento de erros,
instruções de execução, experiência do usuário, responsividade e qualidade
visual/estilização da aplicação.

Mantenha o repositório atualizado até o dia da apresentação. Cada integrante deverá

## B3.1 - Autenticação de usuário

Esta atividade consiste em evoluir o projeto da disciplina, especificamente aplicando
os conceitos de autenticação (Auth) em uma aplicação Web integrada ao back-end em
Node.js/Express.js. O projeto deverá implementar o processo de identificação do
usuário, autenticação, manutenção da sessão/token e proteção de recursos da aplicação.

Mostre no código como foram aplicados os seguintes aspectos:

<Steps>

1. **Modelagem de Usuários e Segurança das Credenciais (20pts)**

   Como foi realizada a modelagem dos usuários da aplicação? Apresente os atributos
   necessários para autenticação e explique como as credenciais são armazenadas de forma
   segura. Demonstre obrigatoriamente o uso de hash de senha, utilizando uma solução
   adequada, como bcrypt, scrypt ou argon2, garantindo que senhas nunca sejam armazenadas
   em texto puro. Explique também as validações e restrições aplicadas aos dados do
   usuário, como unicidade do e-mail/login.

2. **Cadastro e Autenticação de Usuários (20pts)**

   Como foram implementados os fluxos de cadastro (signup/register) e autenticação
   (signin/login)? Demonstre as rotas, Controllers e demais componentes responsáveis por
   receber e validar as credenciais, consultar o usuário, comparar a senha informada com
   seu hash e retornar respostas HTTP adequadas. Devem ser tratados também cenários de
   erro, como usuário inexistente, senha incorreta, dados inválidos e tentativa de
   cadastro com e-mail/login já existente.

3. **Sessão/Token e Proteção de Rotas com Middleware (20pts)**

   Como a aplicação mantém o estado de autenticação do usuário? Demonstre a estratégia
   adotada, utilizando sessão ou token (ex.: JWT), e explique seu funcionamento.
