Até aqui os dados moravam em um array e desapareciam a cada reinício. Esta aula troca o
model em memória por um banco SQLite real — usando o módulo `node:sqlite`, que vem com o

Materiais: [slides da aula](../../../../slides/courses/expressjs/persistence/node-sqlite/) e [mapa mental](../../../../mindmaps/courses/expressjs/persistence/node-sqlite/).

## Objetivo

Ao final você saberá abrir uma conexão SQLite a partir do Node, executar consultas com
*statements* preparados, escrever migrations e seeders, e reescrever a camada de model sem
tocar em controllers nem em rotas.

## Por que começar sem ORM

Um ORM esconde o SQL — e esconder algo que não se conhece é como se aprende a depender de
mágica. Escrever as consultas primeiro dá três coisas:

| Ganho                          | Por quê                                                       |
| ------------------------------ | ------------------------------------------------------------- |
| Entender o que o ORM gera      | `include` deixa de ser mágica quando você já escreveu o `JOIN` |
| Diagnosticar desempenho        | consulta lenta se lê no SQL, não na chamada do ORM             |
| Trabalhar em projeto sem ORM   | scripts, migrações e relatórios costumam ser SQL puro          |

<Aside type="note" title="O ORM vem na aula seguinte">
  A trilha é deliberada: SQL puro aqui, [Prisma](../prisma/) na sequência. As duas versões
  resolvem o mesmo problema, e a comparação só é possível depois de ver as duas.
</Aside>

## O módulo `node:sqlite`

Desde o Node 22.5, o SQLite vem embutido. Não há `npm install`, arquivo binário para
compilar nem servidor de banco para subir — o banco é um arquivo no disco.

```ts title="Primeiro contato" showLineNumbers {1,3,6}
import { DatabaseSync } from 'node:sqlite';

const db = new DatabaseSync('src/database/db.sqlite');

db.exec(`CREATE TABLE IF NOT EXISTS investments (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  name   TEXT    NOT NULL,
  amount INTEGER NOT NULL
)`);

const insert = db.prepare('INSERT INTO investments (name, amount) VALUES (?, ?)');
const { lastInsertRowid } = insert.run('Tesouro Selic 2029', 20000);

const rows = db.prepare('SELECT * FROM investments').all();
```

| Método                | Devolve                                    | Use para              |
| --------------------- | ------------------------------------------ | --------------------- |
| `db.exec(sql)`        | nada                                       | DDL: `CREATE`, `DROP` |
| `stmt.run(...params)` | `{ changes, lastInsertRowid }`             | `INSERT`, `UPDATE`, `DELETE` |
| `stmt.get(...params)` | a primeira linha, ou `undefined`           | busca por id          |
| `stmt.all(...params)` | array de linhas                            | listagens             |

<Aside type="caution" title="`DatabaseSync` é síncrono de verdade">
  O nome não é decorativo: cada consulta **bloqueia o event loop**. Para SQLite local e
  consultas pequenas isso é aceitável e até mais rápido que a alternativa assíncrona. Para
  consultas pesadas, o bloqueio trava a aplicação inteira — é o momento de paginar, indexar
  ou trocar de banco.
</Aside>

## Statements preparados e injeção de SQL

A diferença entre `?` e concatenação não é estilo — é a fronteira entre um sistema seguro e
um invadido:

<Tabs syncKey="sql-injection">
  <TabItem label="Vulnerável">
    ```ts title="Nunca faça isso" showLineNumbers {2}
    // req.query.name === "x'; DROP TABLE investments; --"
    const sql = `SELECT * FROM investments WHERE name = '${name}'`;

    db.exec(sql); // executa os dois comandos
    ```
  </TabItem>

  <TabItem label="Seguro">
    ```ts title="Statement preparado" showLineNumbers {1,3}
    const stmt = db.prepare('SELECT * FROM investments WHERE name = ?');

    // O valor é enviado separado do comando: nunca vira SQL.
    const rows = stmt.all(name);
    ```
  </TabItem>
</Tabs>

<Mermaid title="Por que o statement preparado impede injeção de SQL">
{`
flowchart TD
  A["Entrada do usuário<br/>x'; DROP TABLE …"] --> B{"Como chega ao banco?"}
  B -->|"concatenada na string"| C["O banco recebe UM texto<br/>e interpreta tudo como comando"]
  B -->|"como parâmetro (?)"| D["O banco recebe comando + valor<br/>separados"]
  C --> E["Tabela apagada"]
  D --> F["Busca por um nome esquisito<br/>e nada mais"]
`}
</Mermaid>

Parâmetros também podem ser nomeados, o que ajuda em consultas com muitos campos:

```ts title="Parâmetros nomeados" showLineNumbers
const stmt = db.prepare(
  'INSERT INTO investments (name, amount) VALUES (:name, :amount)',
);

stmt.run({ name: 'CDB Inter', amount: 15000 });
```

<Aside type="danger" title="O que `?` não protege">
  Parâmetros substituem **valores**, nunca nomes de tabela ou de coluna. `ORDER BY ?` não
  funciona, e concatenar o nome da coluna reabre a porta — por isso a aula de
  [Paginação](../../api/pagination/) usa lista de campos permitidos.
</Aside>

## Um invólucro de promessas

O restante da aplicação é `async`. Envolver o `DatabaseSync` em uma interface de promessas
mantém o model uniforme e permite trocar o driver depois sem mexer nos chamadores:

```ts title="src/database/database.ts" showLineNumbers {8,14,20}
import { DatabaseSync } from 'node:sqlite';

function wrap(database: DatabaseSync) {
  return {
    async run(sql: string, params: unknown[] = []) {
      const { changes, lastInsertRowid } = database.prepare(sql).run(...params);

      return { changes, lastId: Number(lastInsertRowid) };
    },

    async get<T>(sql: string, params: unknown[] = []) {
      return database.prepare(sql).get(...params) as T | undefined;
    },

    async all<T>(sql: string, params: unknown[] = []) {
      return database.prepare(sql).all(...params) as T[];
    },

    async close() {
      database.close();
    },
  };
}

export const Database = {
  async connect(file = 'src/database/db.sqlite') {
    return wrap(new DatabaseSync(file));
  },
};
```

## Migrations e seeders

Duas responsabilidades distintas, e confundi-las causa perda de dados:

| Script      | Responsabilidade                    | Roda quando                      |
| ----------- | ----------------------------------- | -------------------------------- |
| Migration   | cria e altera a **estrutura**        | ao evoluir o schema              |
| Seeder      | insere **dados** iniciais            | ao preparar um ambiente de teste |

```ts title="src/database/migration.ts" showLineNumbers
import { Database } from '#database/database.ts';

export async function up() {
  const db = await Database.connect();

  await db.run(`
    CREATE TABLE IF NOT EXISTS investments (
      id        INTEGER  PRIMARY KEY AUTOINCREMENT,
      name      TEXT     NOT NULL,
      amount    INTEGER  NOT NULL CHECK (amount > 0),
      createdAt DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    )
  `);
}
```

```ts title="src/database/seeders.ts" showLineNumbers {6}
import seeders from '#database/seeders.json' with { type: 'json' };
import { Database } from '#database/database.ts';

export async function seed() {
  const db = await Database.connect();
  const sql = 'INSERT INTO investments (name, amount) VALUES (?, ?)';

  for (const { name, amount } of seeders.investments) {
    await db.run(sql, [name, amount]);
  }
}
```

Os scripts do `package.json` transformam isso em comandos memorizáveis:

```json title="package.json" showLineNumbers {3-6}
{
  "scripts": {
    "db:migrate": "node src/database/migrate.ts",
    "db:seed": "node src/database/seed.ts",
    "db:load": "npm run db:migrate && npm run db:seed",
    "db:drop": "node --eval \"require('node:fs').rmSync('src/database/db.sqlite', { force: true })\""
  }
}
```

<Aside type="caution" title="`db:drop` apaga tudo, sem perguntar">
  Em desenvolvimento é conveniente; apontado para um banco de produção, é catastrófico.
  Scripts destrutivos devem depender de `DATABASE_URL` e não de um caminho fixo — veja
  [Configuração](../../architecture/config/).
</Aside>

## O model reescrito

Esta é a prova de que a arquitetura em camadas valeu a pena: **só o model muda**. Controller,
router e middlewares permanecem intactos.

```ts title="src/models/investment-model.ts" del={1-3} ins={5-11}
export function findAll() {
  return investments;
}

export async function findAll(): Promise<Investment[]> {
  const db = await Database.connect();

  return db.all<Investment>('SELECT * FROM investments ORDER BY id');
}
```

O CRUD completo cabe em quatro consultas:

```ts title="src/models/investment-model.ts" showLineNumbers {4,10,17,24}
export async function findById(id: number) {
  const db = await Database.connect();

  return db.get<Investment>('SELECT * FROM investments WHERE id = ?', [id]);
}

export async function create({ name, amount }: InvestmentInput) {
  const db = await Database.connect();

  const { lastId } = await db.run(
    'INSERT INTO investments (name, amount) VALUES (?, ?)',
    [name, amount],
  );

  return findById(lastId);
}

export async function update(id: number, { name, amount }: InvestmentInput) {
  const db = await Database.connect();

  await db.run('UPDATE investments SET name = ?, amount = ? WHERE id = ?', [name, amount, id]);

  return findById(id);
}

export async function remove(id: number) {
  const db = await Database.connect();

  const { changes } = await db.run('DELETE FROM investments WHERE id = ?', [id]);

  return changes > 0;
}
```

<Aside type="tip" title="O controller nem percebe">
  As funções continuam se chamando `findAll`, `findById`, `create`, `update` e `remove`. O
  controller passa a usar `await`, e nada mais muda — inclusive as respostas HTTP. É
  exatamente o efeito que a aula de [MVC](../../architecture/mvc/) prometeu.
</Aside>

## Exercício

Partindo do projeto `express-typescript`:

1. Crie `src/database/database.ts` com o invólucro de promessas.
2. Escreva a migration da tabela `users` com `email` `UNIQUE` e `NOT NULL`.
3. Reescreva `user-model.ts` usando SQL, mantendo os nomes das funções.
4. Ajuste o controller para `await` — e confirme que nada mais precisou mudar.
5. Provoque a violação de `UNIQUE` cadastrando o mesmo e-mail duas vezes e observe o erro
   que chega ao `errorHandler`.

<details>
  <summary>Possível resposta</summary>

  ```ts title="src/models/user-model.ts" showLineNumbers
  export async function create({ name, email }: Required<UserInput>): Promise<User> {
    const db = await Database.connect();

    const { lastId } = await db.run(
      'INSERT INTO users (name, email) VALUES (?, ?)',
      [name, email],
    );

    return { id: lastId, name, email };
  }
  ```

  A segunda inserção do mesmo e-mail lança um erro com código
  `SQLITE_CONSTRAINT_UNIQUE`. Sem tradução, ele vira `500`; traduzido no `errorHandler`,
  vira `409` — como descrito em [Tratamento de Erros](../../api/error-handling/).
</details>

## Perguntas de revisão

### `node:sqlite`

1. **Por que `DatabaseSync` ser síncrono importa em um servidor?**

   <details>
     <summary>Possível resposta</summary>

     Porque cada consulta bloqueia o event loop: enquanto ela roda, nenhuma outra requisição
     é atendida. Para consultas pequenas em SQLite local é aceitável; uma consulta pesada
     trava a aplicação inteira.
   </details>

2. **Qual a diferença entre `db.exec` e `stmt.run`?**

   <details>
     <summary>Possível resposta</summary>

     `exec` executa SQL bruto, aceita vários comandos e não recebe parâmetros — serve para
     DDL. `run` executa um *statement* preparado com parâmetros e devolve `changes` e
     `lastInsertRowid`.
   </details>

### Segurança e organização

3. **Por que `?` impede injeção de SQL?**

   <details>
     <summary>Possível resposta</summary>

     Porque comando e valores viajam separados: o banco compila o comando primeiro e só
     depois recebe os dados. O conteúdo do parâmetro nunca é interpretado como SQL.
   </details>

4. **O que `?` não protege?**

   <details>
     <summary>Possível resposta</summary>

     Nomes de tabela e de coluna, que não podem ser parametrizados. Ordenação e filtros por
     coluna dinâmica exigem uma lista de valores permitidos.
   </details>

5. **Por que o arquivo `db.sqlite` não deve ser versionado?**

   <details>
     <summary>Possível resposta</summary>

     Porque é dado binário que muda a cada requisição: gera conflito em toda fusão e pode
     conter informação real. Migration e seeders são o que se versiona — eles reconstroem o
     banco.
   </details>
