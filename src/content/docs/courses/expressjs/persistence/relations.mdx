Uma tarefa pertence a um projeto, recebe várias tags e tem um dono. Nenhuma entidade de um
sistema real vive sozinha — esta aula trata de declarar essas ligações no schema e de
consultá-las sem disparar cem consultas.

Materiais: [slides da aula](../../../../slides/courses/expressjs/persistence/relations/) e [mapa mental](../../../../mindmaps/courses/expressjs/persistence/relations/).

## Objetivo

Ao final você saberá modelar relações um-para-muitos e muitos-para-muitos, carregar dados
relacionados com `include` e `select`, criar registros ligados em uma única chamada e
escolher o comportamento correto na exclusão.

## O modelo de dados

Antes do schema vem o diagrama. As cardinalidades definem onde fica a chave estrangeira:

| Cardinalidade      | Onde fica a chave estrangeira            | Exemplo                       |
| ------------------ | ---------------------------------------- | ----------------------------- |
| Um-para-muitos     | no lado "muitos"                          | `Task.projectId`              |
| Muitos-para-muitos | em uma tabela de junção                   | `Task` ↔ `Tag`                |
| Um-para-um         | em qualquer lado, com `@unique`           | `User` ↔ `Profile`            |

## Um-para-muitos

A relação é declarada nos dois models, mas só um deles guarda a coluna:

```prisma showLineNumbers {5-6,12}
model Task {
  id        Int      @id @default(autoincrement())
  title     String   @unique
  done      Boolean  @default(false)
  projectId Int?                                                 // a coluna real
  project   Project? @relation(fields: [projectId], references: [id])
}

model Project {
  id    Int    @id @default(autoincrement())
  name  String @unique
  tasks Task[]                                                   // o lado virtual
}
```

<Aside type="note" title="Só um lado vira coluna">
  `projectId` existe na tabela; `project` e `tasks` são campos **virtuais** que o Prisma usa
  para navegar. `Task[]` em `Project` não cria nada no banco — quem guarda a ligação é
  sempre o lado "muitos".
</Aside>

## Muitos-para-muitos

Quando os dois lados podem ter vários do outro, é preciso uma tabela de junção. O Prisma
oferece as duas formas:

<Tabs syncKey="many-to-many">
  <TabItem label="Implícita">
    <SourceCode
      path="examples/courses/expressjs/projects/task-api-prisma/prisma/schema.prisma"
      title="prisma/schema.prisma"
      lines="11-28"
      mark={['tags', 'tasks']}
    />

    O Prisma cria e gerencia a tabela `_TaskTags` sozinho. Simples — mas não dá para
    guardar nada além da ligação.
  </TabItem>

  <TabItem label="Explícita">
    ```prisma showLineNumbers {12-13,15}
    model Task {
      id   Int       @id @default(autoincrement())
      tags TaskTag[]
    }

    model Tag {
      id    Int       @id @default(autoincrement())
      tasks TaskTag[]
    }

    model TaskTag {
      task      Task     @relation(fields: [taskId], references: [id])
      taskId    Int
      tag       Tag      @relation(fields: [tagId], references: [id])
      tagId     Int
      createdAt DateTime @default(now())   // atributo da própria ligação

      @@id([taskId, tagId])
    }
    ```

    Necessária assim que a ligação tiver dados próprios — quando foi criada, por quem, com
    qual peso.
  </TabItem>
</Tabs>

<Aside type="tip" title="Comece implícita, migre quando precisar">
  A forma implícita cobre o caso "apenas ligar A e B". No momento em que aparecer o primeiro
  atributo da ligação, a migração para a forma explícita é inevitável — e é uma migration de
  dados, não só de estrutura.
</Aside>

## Carregando dados relacionados

Por padrão, uma consulta traz apenas as colunas do próprio model. Trazer o relacionado é uma
escolha explícita:

```ts title="include: acrescenta ao resultado completo" showLineNumbers {3-6}
const tasks = await prisma.task.findMany({
  include: {
    tags: true,
    project: true,
    user: { select: { id: true, name: true } },   // sem a senha
  },
});
```

```ts title="select: escolhe exatamente o que sai" showLineNumbers {2-8}
const tasks = await prisma.task.findMany({
  select: {
    id: true,
    title: true,
    done: true,
    tags: { select: { name: true, color: true } },
  },
});
```

| Critério                        | `include`                     | `select`                        |
| ------------------------------- | ----------------------------- | ------------------------------- |
| Campos do próprio model         | todos                         | só os listados                  |
| Relacionamentos                 | acrescentados                 | acrescentados                   |
| Coluna sensível (`password`)    | **vem junto**                 | fica de fora por construção     |
| Podem ser combinados            | não no mesmo nível            | —                               |

A resposta com relações aninhadas é o que o front-end costuma precisar para renderizar sem
uma segunda chamada:

## Filtrando por relação

O `where` navega pelos relacionamentos com três operadores:

```ts title="Filtros relacionais" showLineNumbers {3,9,15}
// Tarefas que têm a tag "urgente"
await prisma.task.findMany({
  where: { tags: { some: { name: 'urgente' } } },
});

// Projetos que têm ao menos uma tarefa em aberto
await prisma.project.findMany({
  where: { tasks: { some: { done: false } } },
});

// Projetos sem nenhuma tarefa
await prisma.project.findMany({
  where: { tasks: { none: {} } },
});
```

| Operador | Significado                                  |
| -------- | -------------------------------------------- |
| `some`   | ao menos um relacionado satisfaz a condição   |
| `every`  | todos os relacionados satisfazem              |
| `none`   | nenhum relacionado satisfaz                   |

## Criando registros ligados

Há três formas de estabelecer a ligação na criação, e a escolha depende de o outro registro
já existir:

```ts title="connect, create e connectOrCreate" showLineNumbers {5,10,17}
// 1. O relacionado já existe: apenas ligue.
await prisma.task.create({
  data: {
    title: 'Revisar a aula de relações',
    priority: 'high',
    tags: { connect: [{ name: 'estudo' }] },
  },
});

// 2. Criar os dois de uma vez, em uma transação implícita.
await prisma.project.create({
  data: {
    name: 'Guia de Express',
    color: '#2563eb',
    tasks: {
      create: [{ title: 'Escrever a etapa 8', priority: 'high' }],
    },
  },
});

// 3. Ligar se existir, criar se não existir — ideal em seeds.
await prisma.task.create({
  data: {
    title: 'Publicar a trilha',
    tags: { connectOrCreate: { where: { name: 'urgente' }, create: { name: 'urgente', color: '#dc2626' } } },
  },
});
```

<Aside type="tip" title="Passar `projectId` direto também funciona">
  `data: { projectId }` é equivalente a `project: { connect: { id } }` e é mais curto. A
  forma com `connect` fica melhor quando a criação é aninhada em vários níveis, ou quando a
  relação é muitos-para-muitos e não existe coluna para atribuir.
</Aside>

## O que acontece na exclusão

Apagar um projeto que tem tarefas não é uma decisão do banco — é uma decisão de produto,
declarada no schema:

| `onDelete`  | Efeito ao apagar o pai                          | Quando usar                          |
| ----------- | ----------------------------------------------- | ------------------------------------ |
| `Restrict`  | impede a exclusão (padrão em campos obrigatórios)| projetos com tarefas dentro          |
| `Cascade`   | apaga os filhos junto                            | tarefas de um usuário apagado        |
| `SetNull`   | zera a chave estrangeira (exige campo opcional)  | tarefa que perde o projeto e continua|

```prisma showLineNumbers {3,7}
model Task {
  // O usuário sai, as tarefas dele saem junto.
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  userId    String

  // O projeto some, a tarefa continua — sem projeto.
  project   Project? @relation(fields: [projectId], references: [id], onDelete: SetNull)
  projectId Int?
}
```

<Aside type="danger" title="`Cascade` apaga em silêncio">
  Um `DELETE /users/1` com cascata pode remover milhares de linhas sem nenhum aviso. Use-o
  onde o filho realmente não faz sentido sem o pai, e prefira `Restrict` quando a exclusão
  precisar ser uma decisão consciente.
</Aside>

## O problema N+1

Buscar a lista e depois o relacionado de cada item dispara uma consulta por registro — dez
usuários viram onze consultas:

```ts title="N+1: uma consulta por tarefa" del={4-6}
const tasks = await prisma.task.findMany();

for (const task of tasks) {
  task.tags = await prisma.tag.findMany({
    where: { tasks: { some: { id: task.id } } },
  });
}
```

```ts title="Com include: o Prisma resolve em duas consultas" ins={2}
const tasks = await prisma.task.findMany({
  include: { tags: true },
});
```

<Aside type="tip" title="Ligue o log e conte">
  `new PrismaClient({ adapter, log: ['query'] })` imprime cada consulta executada. É a forma mais
  direta de descobrir um N+1 escondido — e de confirmar que o `include` o resolveu.
</Aside>

## Perguntas de revisão

### Modelagem

1. **Em uma relação um-para-muitos, qual lado guarda a chave estrangeira?**

   <details>
     <summary>Possível resposta</summary>

     O lado "muitos". `Task.projectId` é uma coluna real; `Project.tasks` é um campo
     virtual que o Prisma usa para navegar e não existe no banco.
   </details>

2. **Quando a relação muitos-para-muitos precisa ser explícita?**

   <details>
     <summary>Possível resposta</summary>

     Assim que a ligação tiver atributos próprios — data de criação, autor, peso. A forma
     implícita só armazena o par de identificadores.
   </details>

### Consultas

3. **Qual a diferença entre `include` e `select`?**

   <details>
     <summary>Possível resposta</summary>

     `include` acrescenta relacionamentos ao resultado completo, trazendo todas as colunas do
     model. `select` lista exatamente o que sai — e é a forma de garantir que uma coluna
     sensível não seja retornada.
   </details>

4. **O que é o problema N+1?**

   <details>
     <summary>Possível resposta</summary>

     Buscar uma lista e, para cada item, disparar outra consulta pelo relacionado: uma
     consulta mais N. O `include` resolve tudo em um número fixo de consultas.
   </details>

5. **Por que `onDelete: Cascade` exige cuidado?**

   <details>
     <summary>Possível resposta</summary>

     Porque apaga silenciosamente todos os registros dependentes — um `DELETE` em um usuário
     pode remover milhares de linhas. `Restrict` torna a exclusão uma decisão consciente.
   </details>
