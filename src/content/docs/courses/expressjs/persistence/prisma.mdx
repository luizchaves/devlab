O Prisma é um ORM: você descreve o modelo de dados em um arquivo, ele gera um cliente
JavaScript com autocomplete e traduz as suas chamadas para o
[SQL](../node-sqlite/) que você já escreveu à mão na aula anterior.

## Objetivo

Ao final você saberá declarar um schema, gerar e aplicar migrations, usar uma instância única
do client e reescrever a camada de model com consultas do Prisma — sem tocar em controllers
nem em rotas.

## O que um ORM troca

Nenhuma ferramenta é grátis. O que se ganha e o que se perde ao sair do SQL puro:

| Aspecto                    | SQL com `node:sqlite`         | Prisma                              |
| -------------------------- | ----------------------------- | ----------------------------------- |
| Modelagem                  | `CREATE TABLE` à mão          | schema declarativo                  |
| Evolução do banco          | scripts próprios              | migrations versionadas e geradas    |
| Autocomplete e tipos       | nenhum — tudo é string        | client tipado a partir do schema    |
| Relacionamentos            | `JOIN` escrito à mão          | `include` / `select`                |
| Troca de banco             | reescrever o SQL              | mudar o `provider`                  |
| Consulta complexa          | controle total                | pode exigir `$queryRaw`             |
| Desempenho                 | previsível                    | depende do que o ORM gera           |

<Aside type="tip" title="Saber o SQL continua sendo obrigatório">
  O Prisma não dispensa entender `JOIN`, índice e plano de execução — ele apenas evita
  escrever a mesma consulta cinquenta vezes. Quando algo ficar lento, o diagnóstico volta a
  ser em SQL.
</Aside>

## O schema

O schema tem três blocos: de onde vem o banco, o que gerar e como são os dados.

<SourceCode
  path="examples/courses/express/projects/prisma/prisma/schema.prisma"
  title="prisma/schema.prisma"
  showLineNumbers
  mark={[15, "23-24"]}
/>

Compare com o `CREATE TABLE` da aula anterior: é a mesma modelagem, declarada de forma mais
curta.

| Atributo no schema           | Equivalente em SQL      |
| ---------------------------- | ----------------------- |
| `@id`                        | `PRIMARY KEY`           |
| `@default(autoincrement())`  | `AUTOINCREMENT`         |
| `@default(cuid())`           | identificador gerado na aplicação |
| `@unique`                    | `UNIQUE`                |
| `String?`                    | coluna que aceita `NULL`|
| `@relation(...)`             | `FOREIGN KEY`           |
| `onDelete: Cascade`          | `ON DELETE CASCADE`     |
| `@@index([campo])`           | `CREATE INDEX`          |

## Configurando a conexão

A URL do banco vive no ambiente, nunca no schema versionado:

```ini title=".env" {1}
DATABASE_URL="file:./dev.db"
PORT=3000
```

<Aside type="caution" title="`.env` nunca vai para o Git">
  Versione apenas o `.env.example`. O arquivo real guarda credenciais e é ignorado pelo
  `.gitignore` — como visto em [Configuração](../../architecture/config/).
</Aside>

<Aside type="note" title="Prisma 6 e Prisma 7">
  O projeto de exemplo usa **Prisma 6**. A partir do **Prisma 7** a configuração mudou: a
  `url` sai do `schema.prisma` e vai para um `prisma.config.ts`, e o `PrismaClient` passa a
  exigir um *driver adapter*:

  ```ts title="src/database/prisma.ts — Prisma 7" showLineNumbers {5-6}
  import 'dotenv/config';
  import { PrismaBetterSqlite3 } from '@prisma/adapter-better-sqlite3';
  import { PrismaClient } from '#generated/prisma/client.ts';

  const adapter = new PrismaBetterSqlite3({ url: `${process.env.DATABASE_URL}` });
  export const prisma = new PrismaClient({ adapter });
  ```

  O modelo de dados e as consultas permanecem os mesmos.
</Aside>

## Migrations

Uma migration é um arquivo SQL versionado que descreve **uma** mudança de estrutura. O
histórico delas é o que permite reconstruir o banco do zero em qualquer máquina.

<Mermaid title="Fluxo de uma alteração de schema com Prisma Migrate">
{`
flowchart TD
  A["Edita prisma/schema.prisma"] --> B["prisma migrate dev --name add_user"]
  B --> C["Gera prisma/migrations/<timestamp>_add_user/migration.sql"]
  C --> D["Aplica no banco local"]
  D --> E["prisma generate<br/>client tipado atualizado"]
  E --> F["O editor já conhece os campos novos"]
`}
</Mermaid>

<Tabs syncKey="prisma-schema-apply">
  <TabItem label="migrate dev">
    ```bash title="Terminal"
    npx prisma migrate dev --name init
    ```

    Gera o arquivo de migration, aplica e regenera o client. É o comando de projeto real:
    o histórico fica versionado.
  </TabItem>

  <TabItem label="db push">
    ```bash title="Terminal"
    npx prisma db push
    ```

    Sincroniza o banco com o schema sem gerar histórico. Rápido e idempotente — bom para
    protótipo e sala de aula, ruim para produção.
  </TabItem>
</Tabs>

<Aside type="danger" title="`migrate reset` apaga os dados">
  `npx prisma migrate reset` derruba o banco, reaplica todas as migrations e roda o seed. Em
  desenvolvimento é o botão de recomeçar; apontado para produção, é perda total.
</Aside>

## Uma instância do client

O `PrismaClient` gerencia um pool de conexões. A aplicação inteira precisa compartilhar
**uma** instância:

<SourceCode path="examples/courses/express/projects/prisma/src/lib/prisma.js" title="src/lib/prisma.js" showLineNumbers />

<Aside type="danger" title="Nunca crie um client por requisição">
  Cada `new PrismaClient()` abre o próprio pool. Instanciar dentro de um controller esgota as
  conexões do banco em poucos minutos de uso — e o sintoma (timeouts intermitentes) não
  aponta para a causa.
</Aside>

## Consultas

Cada método do client corresponde a um comando SQL. O comentário mostra o que é gerado:

```js title="consultas.js" showLineNumbers
// SELECT * FROM User
const todos = await prisma.user.findMany();

// SELECT * FROM User WHERE id = 1
const um = await prisma.user.findUnique({ where: { id: 1 } });

// SELECT … LIMIT 1  — lança se não existir
const obrigatorio = await prisma.user.findUniqueOrThrow({ where: { id: 1 } });

// INSERT INTO User (name, email) VALUES (…)
const novo = await prisma.user.create({
  data: { name: 'Ana', email: 'ana@example.com' },
});

// UPDATE User SET name = 'Ana Silva' WHERE id = 1
const alterado = await prisma.user.update({
  where: { id: 1 },
  data: { name: 'Ana Silva' },
});

// DELETE FROM User WHERE id = 1
await prisma.user.delete({ where: { id: 1 } });
```

Filtros, ordenação, paginação e junções seguem a mesma forma declarativa:

```js title="avancado.js" showLineNumbers {2,10,15}
const filtrados = await prisma.user.findMany({
  where: { name: { startsWith: 'A' } },
  orderBy: { name: 'asc' },
  take: 10, //  LIMIT 10
  skip: 20, //  OFFSET 20
});

// Equivalente a um JOIN: traz o usuário com os posts dele
const comPosts = await prisma.user.findUnique({
  where: { id: 1 },
  include: { posts: true },
});

// Seleciona apenas algumas colunas — o resto nem sai do banco
const nomes = await prisma.user.findMany({ select: { id: true, name: true } });
```

<Aside type="tip" title="`select` não é só economia de rede">
  Em uma tabela de usuários, `select: { id: true, name: true, email: true }` garante que a
  coluna `password` **nunca** saia do banco. É a diferença entre esquecer de remover o campo
  e ele não existir na resposta — voltaremos a isso em
  [Cadastro de Usuário](../../auth/user-registration/).
</Aside>

## Seed

O seed popula o banco com os dados mínimos para a aplicação funcionar: categorias, papéis,
um usuário administrador.

<SourceCode path="examples/courses/express/projects/prisma/prisma/seed.js" title="prisma/seed.js" showLineNumbers collapse="16-21" />

```json title="package.json" showLineNumbers {4}
{
  "prisma": { "seed": "node prisma/seed.js" },
  "scripts": {
    "db:seed": "prisma db seed"
  }
}
```

<Aside type="caution" title="Seed precisa ser idempotente">
  Rodar duas vezes não deve duplicar registros. `upsert` resolve: ele cria se não existir e
  atualiza se existir.
</Aside>

## Exercício

No projeto `express-prisma`:

1. Acrescente ao schema um model `Category` com `id`, `name` (`@unique`) e `color`.
2. Relacione `Category` a `Post`: uma categoria tem vários posts.
3. Rode `prisma migrate dev --name add_category` e observe o SQL gerado.
4. Atualize o seed criando três categorias com `upsert`.
5. Escreva uma consulta que liste os posts publicados com o nome do autor e o da categoria.

<details>
  <summary>Possível resposta</summary>

  ```prisma title="prisma/schema.prisma" showLineNumbers
  model Category {
    id    Int    @id @default(autoincrement())
    name  String @unique
    color String
    posts Post[]
  }

  model Post {
    id         Int      @id @default(autoincrement())
    title      String
    published  Boolean  @default(false)
    authorId   Int
    author     User     @relation(fields: [authorId], references: [id])
    categoryId Int?
    category   Category? @relation(fields: [categoryId], references: [id])
  }
  ```

  ```js title="Consulta" showLineNumbers
  const posts = await prisma.post.findMany({
    where: { published: true },
    select: {
      title: true,
      author: { select: { name: true } },
      category: { select: { name: true } },
    },
  });
  ```

  `categoryId` é opcional (`Int?`) para não invalidar os posts já existentes na migration.
</details>

## Desafio

Compare o SQL gerado por `include: { posts: true }` e por duas consultas separadas. Ative o
log do client com `new PrismaClient({ log: ['query'] })` e observe quantas consultas cada
abordagem dispara ao listar dez usuários com os posts de cada um.

## Perguntas de revisão

### Schema e migrations

1. **Qual a diferença entre `migrate dev` e `db push`?**

   <details>
     <summary>Possível resposta</summary>

     `migrate dev` gera um arquivo SQL versionado, aplica e regenera o client — o histórico
     fica no repositório. `db push` apenas sincroniza o banco com o schema, sem histórico:
     rápido para protótipo, inadequado para produção.
   </details>

2. **Por que o histórico de migrations é versionado no Git?**

   <details>
     <summary>Possível resposta</summary>

     Porque é ele que permite reconstruir o banco do zero em qualquer máquina e aplicar as
     mesmas mudanças, na mesma ordem, em produção.
   </details>

### Client e consultas

3. **Por que uma instância única do `PrismaClient`?**

   <details>
     <summary>Possível resposta</summary>

     Porque cada instância abre o próprio pool de conexões. Criar um client por requisição
     esgota o limite do banco, com sintoma de timeouts intermitentes.
   </details>

4. **Qual a diferença entre `select` e `include`?**

   <details>
     <summary>Possível resposta</summary>

     `select` escolhe **quais campos** trazer (e exclui o resto); `include` acrescenta
     relacionamentos ao resultado completo. `select` é a ferramenta para garantir que uma
     coluna sensível nunca saia do banco.
   </details>

5. **Por que o seed precisa ser idempotente?**

   <details>
     <summary>Possível resposta</summary>

     Porque ele é executado várias vezes — depois de cada `migrate reset`, em cada ambiente
     novo. Com `create`, a segunda execução duplica os registros; com `upsert`, não.
   </details>
