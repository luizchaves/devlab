Um middleware é uma função que recebe `(req, res, next)` e roda **entre** a chegada da
requisição e a resposta. Todo o Express é construído sobre essa ideia — inclusive as
próprias rotas, que são middlewares com método e caminho.

Materiais: [slides da aula](../../../../slides/courses/expressjs/basics/middleware/) e [mapa mental](../../../../mindmaps/courses/expressjs/basics/middleware/).

## Objetivo

Ao final você saberá escrever middlewares de aplicação, de rota e de erro, entender por que
a ordem de registro define o comportamento da aplicação e usar o padrão de fábrica para
criar middlewares configuráveis.

## A assinatura

Um middleware tem três parâmetros e uma obrigação: responder **ou** chamar `next()`.

`next()` passa a requisição adiante. **Sem ele, a requisição trava**: nenhum middleware
seguinte executa e o cliente fica esperando até o timeout.

<Aside type="caution" title="`next()` não interrompe a função">
  `next()` agenda o próximo middleware, mas o código depois dele continua rodando. Use
  `return next()` quando a intenção for encerrar ali:

  ```js del={3} ins={2}
  if (!req.body.email) {
    return next(new HttpError(400, 'E-mail obrigatório'));
    next(new HttpError(400, 'E-mail obrigatório'));
  }
  ```
</Aside>

## A cadeia de responsabilidade

Cada requisição atravessa os middlewares na ordem de registro. Qualquer um pode responder e
encerrar o ciclo; quem não responde delega ao próximo.

<Mermaid title="Cadeia de middlewares de uma requisição no Express">
{`
flowchart TD
  A["Cliente (Request)"] --> B["express.json()<br/>interpreta o corpo"]
  B -->|"next()"| C["logger<br/>registra a requisição"]
  C -->|"next()"| D["taskRouter<br/>tenta casar uma rota"]
  D -->|"respondeu"| G["Cliente (Response)"]
  D -->|"nenhuma rota casou<br/>next()"| E["notFound<br/>cria o erro 404"]
  D -->|"lançou erro<br/>next(err)"| F["errorHandler<br/>traduz o erro em JSON"]
  E -->|"next(err)"| F
  F --> G
`}
</Mermaid>

## Os cinco tipos

O Express classifica os middlewares pelo escopo em que são registrados:

| Tipo             | Registro                                | Alcance                              |
| ---------------- | --------------------------------------- | ------------------------------------ |
| De aplicação     | `app.use(fn)`                           | todas as requisições                 |
| Com caminho      | `app.use('/api', fn)`                   | requisições que começam com `/api`   |
| De rota          | `router.post('/', fn, handler)`         | apenas aquela rota                   |
| De erro          | `app.use((err, req, res, next) => …)`   | quando alguém lança ou chama `next(err)` |
| Embutido/terceiro| `express.json()`, `cors()`, `helmet()`  | conforme o registro                  |

O middleware de rota entra entre o caminho e o handler final, e é a forma mais barata de não
repetir validação. Num `task-router.js` ficaria assim:

```js showLineNumbers {1}
router.post('/', requireJson, validarTarefa, taskController.store);

function validarTarefa(req, res, next) {
  if (!req.body?.title) {
    return res.status(400).json({ message: 'O título é obrigatório' });
  }

  next();
}
```

## Middleware de fábrica

Um middleware que precisa de configuração é escrito como **função que devolve um
middleware**. É o padrão usado por `express.json()`, `cors()` e por qualquer validação
parametrizada — o esqueleto de um `validate.js` genérico:

```js showLineNumbers {1,3}
export function validate(camposObrigatorios) {
  // Executa uma vez, no registro da rota.
  return (req, res, next) => {
    // Executa a cada requisição.
    const faltando = camposObrigatorios.filter((campo) => !req.body?.[campo]);

    if (faltando.length > 0) {
      return res.status(400).json({
        message: `Campos obrigatórios: ${faltando.join(', ')}`,
      });
    }

    next();
  };
}
```

O uso, de volta no router, fica declarativo, e o controller perde os `if` de validação:

```js showLineNumbers {1}
router.post('/', validate(['title']), taskController.store);
```

<Aside type="tip" title="Por que a fábrica, e não um parâmetro extra?">
  O Express chama o middleware com `(req, res, next)` — não há como passar mais nada. A
  fábrica fecha sobre a configuração no momento do registro e devolve a função com a
  assinatura que o Express espera.
</Aside>

## Middleware de erro

É reconhecido pelo Express por ter **quatro** parâmetros, e precisa ser o último registrado.
Ele é o único lugar da aplicação que decide como um erro vira resposta:

/>

Para chegar até ele, um middleware ou controller lança o erro — ou chama `next(erro)`. No
`task-controller.js` é literalmente uma linha:

```js
throw new HttpError(404, 'Tarefa não encontrada');
```

<Aside type="note" title="Express 5 e funções `async`">
  No Express 4, um erro lançado dentro de uma função `async` **não** chegava ao middleware
  de erro: virava uma rejeição não tratada e a requisição travava. Era preciso `try`/`catch`
  em cada rota, ou o pacote `express-async-errors`. O Express 5 encaminha esses erros
  automaticamente — e é por isso que os controllers deste guia não têm `try`/`catch`.
</Aside>

## Embutidos e de terceiros

Alguns middlewares vêm com o Express; outros resolvem preocupações que toda API tem:

| Middleware                          | Origem   | Para que serve                              |
| ----------------------------------- | -------- | ------------------------------------------- |
| `express.json()`                    | embutido | interpreta corpo `application/json`         |
| `express.urlencoded({ extended: true })` | embutido | interpreta formulários HTML            |
| `express.static('public')`          | embutido | serve arquivos estáticos                    |
| `express.text()` / `express.raw()`  | embutido | corpo em texto puro ou binário              |
| [`morgan`](https://www.npmjs.com/package/morgan) | terceiro | log de requisições em formato pronto |
| [`cors`](https://www.npmjs.com/package/cors)     | terceiro | libera requisições de outras origens |
| [`helmet`](https://www.npmjs.com/package/helmet) | terceiro | cabeçalhos de segurança              |
| [`express-rate-limit`](https://www.npmjs.com/package/express-rate-limit) | terceiro | limita requisições por IP |

<Aside type="tip" title="Os de terceiros são só middlewares">
  Nenhum deles faz nada que você não possa escrever: `morgan` é o `logger` desta aula com
  formatos prontos, e `cors` monta três cabeçalhos. As aulas de
  [CORS](../../security/cors/) e [Endurecimento](../../security/hardening/) mostram as duas
  versões — a nativa e a com pacote — para que a escolha seja informada.
</Aside>

## Exercício

Escreva os middlewares abaixo e registre-os na [etapa 3 da TaskAPI](../../practice/taskapi/mvc/):

1. `requestId` — gera um `crypto.randomUUID()`, guarda em `req.id` e devolve no cabeçalho
   `X-Request-Id`.
2. `onlyJson` — responde `415` quando um `POST` ou `PUT` chega sem
   `Content-Type: application/json`.
3. `timeout(ms)` — middleware de fábrica que responde `503` se a requisição passar de `ms`
   sem ter sido respondida.

<details>
  <summary>Possível resposta</summary>

  ```js showLineNumbers
  import { randomUUID } from 'node:crypto';

  export function requestId(req, res, next) {
    req.id = randomUUID();

    // Definido antes do handler: os cabeçalhos ainda não foram enviados.
    res.set('X-Request-Id', req.id);

    next();
  }
  ```

  ```js showLineNumbers
  export function onlyJson(req, res, next) {
    const temCorpo = req.method === 'POST' || req.method === 'PUT';

    if (temCorpo && !req.is('application/json')) {
      return res.status(415).json({ message: 'Content-Type precisa ser application/json' });
    }

    next();
  }
  ```

  ```js showLineNumbers
  export function timeout(ms) {
    return (req, res, next) => {
      const timer = setTimeout(() => {
        if (!res.headersSent) {
          res.status(503).json({ message: 'Tempo de resposta excedido' });
        }
      }, ms);

      // Sem o clear, o timer segura o processo vivo até disparar.
      res.on('finish', () => clearTimeout(timer));

      next();
    };
  }
  ```
</details>

## Desafio

Implemente um middleware de cache em memória para requisições `GET`: na primeira chamada
guarda o corpo da resposta por chave `req.originalUrl`; nas seguintes responde direto do
cache com o cabeçalho `X-Cache: HIT`. Dica: substitua `res.json` por uma função que guarda o
valor antes de chamar a original.

## Perguntas de revisão

### Cadeia

1. **O que acontece se um middleware não chamar `next()` nem responder?**

   <details>
     <summary>Possível resposta</summary>

     A requisição fica pendurada: nenhum middleware seguinte executa e o cliente espera até
     o timeout. Não há erro no servidor — é o sintoma mais difícil de diagnosticar.
   </details>

2. **Por que a ordem de `app.use()` é considerada parte da arquitetura?**

   <details>
     <summary>Possível resposta</summary>

     Porque ela define o que cada camada enxerga. `express.json()` depois do router deixa
     `req.body` vazio; o `errorHandler` antes das rotas nunca é alcançado; o `notFound`
     antes do router bloqueia toda a API.
   </details>

3. **Qual a diferença entre `app.use(fn)` e `app.use('/api', fn)`?**

   <details>
     <summary>Possível resposta</summary>

     O primeiro roda em toda requisição. O segundo só roda quando o caminho **começa** com
     `/api`, e dentro dele `req.baseUrl` vale `'/api'` enquanto `req.path` já vem sem o
     prefixo.
   </details>

### Erros

4. **Como o Express distingue um middleware de erro de um comum?**

   <details>
     <summary>Possível resposta</summary>

     Pela aridade da função: quatro parâmetros declarados. Omitir o `next` final faz o
     Express tratá-lo como middleware comum, e ele nunca recebe o erro.
   </details>

5. **Por que os controllers deste guia não têm `try`/`catch`?**

   <details>
     <summary>Possível resposta</summary>

     Porque o Express 5 encaminha automaticamente ao `errorHandler` os erros lançados dentro
     de funções `async`. O `try`/`catch` só volta a fazer sentido quando o erro precisa ser
     traduzido antes de subir — por exemplo, transformar um erro do Prisma em `404`.
   </details>
