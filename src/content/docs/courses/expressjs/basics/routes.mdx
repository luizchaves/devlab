Roteamento é a decisão de **qual função responde a qual requisição**. Este tópico percorre as
formas de escrever um caminho, os três lugares por onde os dados chegam e a modularização
com `express.Router()`.

Materiais: [slides do tópico](../../../../slides/courses/expressjs/basics/routes/) e [mapa mental](../../../../mindmaps/courses/expressjs/basics/routes/).

## Objetivo

Ao final você saberá declarar rotas com parâmetros, ler dados de `req.params`, `req.query` e
`req.body`, encadear handlers em uma mesma rota e extrair um conjunto de rotas para um
módulo próprio montado sob um prefixo.

## Caminho, método e handler

Uma rota casa quando o **método** e o **caminho** batem. O Express avalia na ordem de
registro e para na primeira que casar:

```js title="Ordem de avaliação" showLineNumbers {1,5}
app.get('/tasks/pending', listPending); // avaliada primeiro
app.get('/tasks/:id', showTask);

// Invertidas, '/tasks/pending' cairia em '/tasks/:id'
// com req.params.id === 'pending'.
```

Os padrões de caminho aceitos pelo Express 5 são poucos e explícitos:

| Padrão            | Casa com                          | Não casa com          |
| ----------------- | --------------------------------- | --------------------- |
| `/tasks`          | `/tasks`                          | `/tasks/1`            |
| `/tasks/:id`      | `/tasks/1`, `/tasks/abc`          | `/tasks`, `/tasks/1/x`|
| `/tasks/:id?`     | `/tasks`, `/tasks/1`              | `/tasks/1/x`          |
| `/files/*splat`   | `/files/a`, `/files/a/b/c.png`    | `/files`              |
| `/^\/ab+c$/`      | `/abc`, `/abbc` (expressão regular)| `/ac`                 |

<Aside type="caution" title="Express 5 mudou os curingas">
  No Express 4 escrevia-se `'*'` e `'/files/*'`. No Express 5 o curinga precisa ser
  **nomeado** (`'/{*splat}'` e `'/files/*splat'`) e o valor chega em `req.params.splat`
  como um array de segmentos. Código antigo copiado da internet costuma quebrar aqui.
</Aside>

## Os três lugares por onde os dados chegam

Uma requisição carrega dados em três posições diferentes, e cada uma tem um uso próprio.

<Mermaid title="Origem dos dados de uma requisição HTTP no Express">
{`
flowchart TD
  A["PUT /tasks/1?notify=true<br/>{ 'title': 'Estudar rotas' }"] --> B["Linha da requisição"]
  A --> C["Corpo da requisição"]
  B --> D["req.params<br/>{ id: '1' }<br/>identifica o recurso"]
  B --> E["req.query<br/>{ notify: 'true' }<br/>modifica a consulta"]
  C --> F["req.body<br/>{ title: 'Estudar rotas' }<br/>envia os dados"]
`}
</Mermaid>

A tabela resume quando usar cada um:

| Origem       | Objeto       | Tipo dos valores | Use para                                         |
| ------------ | ------------ | ---------------- | ------------------------------------------------ |
| Rota         | `req.params` | sempre string    | identificar **qual** recurso: `/tasks/:id`        |
| Query string | `req.query`  | string ou array  | filtrar, ordenar e paginar: `?page=2&sort=name`   |
| Corpo        | `req.body`   | tipos do JSON    | enviar dados de criação e atualização             |

### Parâmetro de rota

O trecho iniciado por `:` vira uma chave em `req.params`, sempre como string:

```js title="Parâmetro de rota" showLineNumbers {2}
app.get('/tasks/:id', (req, res) => {
  const id = Number(req.params.id); // '2' -> 2

  const task = tasks.find((item) => item.id === id);

  if (!task) {
    return res.status(404).json({ message: 'Tarefa não encontrada' });
  }

  res.json(task);
});
```

<Aside type="caution" title="`req.params` é sempre string">
  `/tasks/2` entrega `req.params.id === '2'`. Sem a conversão, `item.id === req.params.id`
  compara número com string e falha silenciosamente — a rota responde `404` para uma tarefa
  que existe.
</Aside>

### Query string

Tudo depois do `?` chega em `req.query` já convertido em objeto. Um mesmo nome repetido vira
array, o que é uma armadilha comum:

```js title="Query string" showLineNumbers {5}
// GET /tasks?page=2&tag=estudo&tag=urgente
app.get('/tasks', (req, res) => {
  const page = Number(req.query.page ?? 1);
  //          => 2
  const tags = [req.query.tag].flat();
  //          => ['estudo', 'urgente']

  res.json({ page, tags });
});
```

### Corpo da requisição

O corpo só existe depois de um middleware interpretá-lo. Cada formato tem o seu:

```js showLineNumbers
app.use(express.json()); // application/json           -> objeto
app.use(express.urlencoded({ extended: true })); // formulário HTML -> objeto
app.use(express.text()); // text/plain                 -> string
app.use(express.raw()); //  application/octet-stream   -> Buffer
```

Registrados esses middlewares, o handler apenas lê `req.body`:

```js title="Corpo JSON" showLineNumbers {2}
app.post('/tasks', (req, res) => {
  const { title } = req.body ?? {};

  if (!title) {
    return res.status(400).json({ message: 'O campo "title" é obrigatório' });
  }

  res.status(201).json({ id: 3, title, done: false });
});
```

## Encadeando handlers

Uma rota aceita vários handlers em sequência. Cada um decide se responde ou se passa adiante
com `next()` — é assim que validação e autorização entram antes do handler final:

```js title="Vários handlers na mesma rota" showLineNumbers {1,4}
app.post('/tasks', requireJson, validateTask, createTask);

// Equivalente, com array:
app.post('/tasks', [requireJson, validateTask], createTask);
```

Quando várias rotas compartilham o caminho, `app.route()` evita repeti-lo:

```js title="app.route()" showLineNumbers
app.route('/tasks/:id')
  .get(showTask)
  .put(updateTask)
  .delete(destroyTask);
```

## Modularizando com `express.Router()`

Um arquivo único funciona bem com três rotas; com trinta, vira um problema. O `Router` é um
mini-aplicativo: tem as próprias rotas e os próprios middlewares, e é montado sob um prefixo.

<Mermaid title="Montagem de routers sob prefixos em uma aplicação Express">
{`
flowchart TD
  A["app"] --> B["app.use('/tasks', taskRouter)"]
  A --> C["app.use('/tags', tagRouter)"]
  B --> D["router.get('/')<br/>→ GET /tasks"]
  B --> E["router.get('/:id')<br/>→ GET /tasks/:id"]
  C --> F["router.get('/')<br/>→ GET /tags"]
`}
</Mermaid>

Dentro do router os caminhos são **relativos ao prefixo**: `'/'` vira `/tasks` e `'/:id'`
vira `/tasks/:id`. O projeto de exemplo separa ainda a montagem da aplicação da subida do
servidor:

A mudança em `app.js` é pequena, mas muda a arquitetura:

```js title="src/app.js" del={2-4} ins={6}
// antes: a rota morava no arquivo da aplicação
app.get('/tasks', (req, res) => {
  res.json(tasks);
});

app.use('/tasks', taskRouter);
```

<Aside type="tip" title="Por que separar `app.js` de `server.js`?">
  Um `app` sem `listen` é testável: a ferramenta de teste importa o `app` e faz requisições
  sem ocupar porta nenhuma. `server.js` fica com a única responsabilidade de subir o
  processo — e é ele que muda quando o deploy exige outra porta ou host.
</Aside>

## Exercício

Ainda na [etapa 2 da TaskAPI](../../practice/taskapi/router/):

1. Crie `src/routes/tag-router.js` com `GET /tags` e `GET /tags/:id`.
2. Monte-o em `app.js` sob o prefixo `/tags`.
3. Acrescente `GET /tags?minTasks=2` filtrando pela query string.
4. Responda `400` quando `minTasks` não for numérico e `404` quando o `id` não existir.

<details>
  <summary>Possível resposta</summary>

  ```js
  import { Router } from 'express';

  const router = Router();

  const tags = [
    { id: 1, name: 'estudo', tasks: 3 },
    { id: 2, name: 'urgente', tasks: 1 },
  ];

  router.get('/', (req, res) => {
    const { minTasks } = req.query;

    if (minTasks === undefined) {
      return res.json(tags);
    }

    const limit = Number(minTasks);

    if (Number.isNaN(limit)) {
      return res.status(400).json({ message: '"minTasks" deve ser numérico' });
    }

    res.json(tags.filter((tag) => tag.tasks >= limit));
  });

  router.get('/:id', (req, res) => {
    const tag = tags.find((item) => item.id === Number(req.params.id));

    if (!tag) {
      return res.status(404).json({ message: 'Tag não encontrada' });
    }

    res.json(tag);
  });

  export default router;
  ```

  Em `app.js`: `app.use('/tags', tagRouter);`
</details>

## Desafio

Escreva uma rota `GET /files/*splat` que devolva os segmentos capturados como array, e uma
rota `GET /tasks/:id?` que responda a lista completa quando o `id` não vier. Verifique em
qual ordem as duas precisam ser registradas para não se anularem.

## Perguntas de revisão

### Parâmetros

1. **Qual a diferença de propósito entre `req.params` e `req.query`?**

   <details>
     <summary>Possível resposta</summary>

     `req.params` identifica **qual** recurso está sendo acessado e faz parte do caminho.
     `req.query` **modifica** a consulta (filtro, ordenação, paginação) e é opcional por
     natureza.
   </details>

2. **Por que `req.query.tag` pode ser um array?**

   <details>
     <summary>Possível resposta</summary>

     Porque a query string aceita o mesmo nome repetido: `?tag=estudo&tag=urgente` vira
     `['estudo', 'urgente']`. Código que assume string quebra quando o cliente repete o
     parâmetro — `[req.query.tag].flat()` normaliza os dois casos.
   </details>

3. **O que falta quando `req.body` é `undefined` em um `POST` com JSON?**

   <details>
     <summary>Possível resposta</summary>

     O `app.use(express.json())` — ou ele foi registrado depois da rota. O corpo não é
     interpretado automaticamente.
   </details>

### Router

4. **Por que o caminho dentro do router é `'/'` e não `'/tasks'`?**

   <details>
     <summary>Possível resposta</summary>

     Porque o prefixo é definido na montagem: `app.use('/tasks', taskRouter)`. Repetir
     `/tasks` dentro do router produziria `/tasks/tasks`. Isso permite remontar o mesmo
     router em outro prefixo — por exemplo, versionar a API em `/api/v1`.
   </details>

5. **Qual a vantagem de `app.js` exportar o `app` sem chamar `listen`?**

   <details>
     <summary>Possível resposta</summary>

     Testes importam o `app` e fazem requisições sem abrir porta, e o mesmo `app` pode ser
     servido por outro processo (serverless, cluster) sem alteração.
   </details>
