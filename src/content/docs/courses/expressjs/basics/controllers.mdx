Um **controller** é a função que responde a uma requisição. Tirá-la de dentro do router
deixa o arquivo de rotas com uma única responsabilidade: dizer *quais caminhos existem*.

Materiais: [slides da aula](../../../../slides/courses/expressjs/basics/controllers/) e [mapa mental](../../../../mindmaps/courses/expressjs/basics/controllers/).

## Objetivo

Ao final você saberá extrair handlers para um controller por recurso, nomear as funções
segundo a convenção usada em qualquer framework MVC e reconhecer quando a lógica cresceu a
ponto de pedir uma camada de serviço.

## O problema

Quando o handler cresce, o arquivo de rotas passa a misturar caminho, validação, acesso a
dados e formatação da resposta — quatro motivos diferentes para o mesmo arquivo mudar:

```js title="src/routes/user-router.js" {3-12}
router.post('/', (req, res) => {
  const { name, email } = req.body ?? {};

  if (!name || !email) {
    return res.status(400).json({ message: 'Campos obrigatórios' });
  }

  const user = { id: nextId, name, email };
  nextId += 1;
  users.push(user);

  res.status(201).json(user);
});
```

Ler esse arquivo para descobrir quais rotas existem exige atravessar a implementação de
todas elas.

## A separação

O router passa a apontar para funções nomeadas, e volta a caber em uma tela:

```js title="src/routes/user-router.js" ins={1,5-7}
import * as userController from '../controllers/user-controller.js';

const router = Router();

router.get('/', userController.index);
router.get('/:id', userController.show);
router.post('/', userController.store);
```

O controller fica com a lógica — e com a decisão de qual status responder:

```js title="src/controllers/user-controller.js" showLineNumbers
export function index(req, res) {
  res.json(User.findAll());
}

export function show(req, res) {
  const user = User.findById(Number(req.params.id));

  if (!user) {
    throw new HttpError(404, 'Usuário não encontrado');
  }

  res.json(user);
}
```

## Nomes convencionais

Usar sempre os mesmos nomes torna qualquer controller previsível: quem abre
`product-controller.js` pela primeira vez já sabe o que vai encontrar.

| Função    | Método HTTP | Caminho      | Ação        |
| --------- | ----------- | ------------ | ----------- |
| `index`   | GET         | `/users`     | Lista todos |
| `show`    | GET         | `/users/:id` | Busca um    |
| `store`   | POST        | `/users`     | Cria        |
| `update`  | PUT         | `/users/:id` | Atualiza    |
| `destroy` | DELETE      | `/users/:id` | Remove      |

<Aside type="note" title="Outros dialetos da mesma convenção">
  Rails usa `index/show/create/update/destroy`; Laravel, `index/show/store/update/destroy`;
  o material de LP2 usa `create/read/readById/update/remove`. O nome exato importa menos do
  que a consistência dentro do projeto — o que não vale é `listarUsuarios` ao lado de
  `show`.
</Aside>

## Quem faz o quê

A separação só funciona se cada camada respeitar o próprio limite. O controller é a
fronteira entre o mundo HTTP e o resto da aplicação:

<Mermaid title="Responsabilidades das camadas em torno do controller">
{`
flowchart TD
  A["Router<br/>quais caminhos existem"] --> B["Controller<br/>traduz HTTP em chamadas de domínio"]
  B --> C["Model<br/>onde os dados estão"]
  B --> D["Resposta HTTP<br/>status + corpo"]
  C --> B
`}
</Mermaid>

O controller **deve**:

- ler `req.params`, `req.query` e `req.body`;
- validar e converter a entrada (`Number(req.params.id)`);
- chamar o model;
- escolher o status e enviar a resposta.

O controller **não deve**:

- conhecer detalhes de SQL ou do ORM — isso é papel do model;
- montar HTML;
- saber em qual caminho está montado — quem define o prefixo é o `app.use()`.

<Aside type="tip" title="Um controller por recurso">
  `user-controller.js`, `product-controller.js`, `order-controller.js`. Se um controller
  precisa importar outro, normalmente falta um model ou um serviço: a regra que os dois
  compartilham não é sobre HTTP.
</Aside>

## Controllers magros

O sinal de que o controller engordou demais é ele conter regra de negócio — algo que
continuaria valendo se a aplicação virasse um script de linha de comando:

```js title="Controller gordo" del={5-11}
export async function store(req, res) {
  const { amount, categoryId } = req.body;

  // Regra de negócio dentro do controller: não é sobre HTTP.
  const category = await Category.findById(categoryId);
  const limite = category.limitePorAporte;
  const total = await Investment.sumByCategory(categoryId);

  if (total + amount > limite) {
    throw new HttpError(409, 'Limite da categoria excedido');
  }

  res.status(201).json(await Investment.create(req.body));
}
```

A mesma rota com a regra extraída para um serviço fica assim — e a regra passa a ser
testável sem subir servidor:

```js title="Controller magro + serviço" ins={1,4}
import * as InvestmentService from '../services/investment-service.js';

export async function store(req, res) {
  const investment = await InvestmentService.criarRespeitandoLimite(req.body);

  res.status(201).json(investment);
}
```

<Aside type="caution" title="Não crie a camada de serviço antes da hora">
  Em um CRUD sem regra própria, um `service` que só repassa a chamada para o model é
  cerimônia sem ganho. Extraia quando a regra existir — não antes.
</Aside>

## Exercício

Partindo do projeto `router`:

1. Crie `src/controllers/product-controller.js` com `index`, `show`, `store` e `destroy`.
2. Deixe `product-router.js` apenas com os cinco `router.<verbo>` apontando para o controller.
3. Faça `store` responder `201` com o produto criado e `400` quando `price` for negativo.
4. Faça `destroy` responder `204` sem corpo.

<details>
  <summary>Possível resposta</summary>

  ```js title="src/controllers/product-controller.js" showLineNumbers
  import * as Product from '../models/product-model.js';

  export function index(req, res) {
    res.json(Product.findAll());
  }

  export function show(req, res) {
    const product = Product.findById(Number(req.params.id));

    if (!product) {
      return res.status(404).json({ message: 'Produto não encontrado' });
    }

    res.json(product);
  }

  export function store(req, res) {
    const { name, price } = req.body ?? {};

    if (!name || typeof price !== 'number' || price < 0) {
      return res.status(400).json({ message: '"name" e "price" (>= 0) são obrigatórios' });
    }

    res.status(201).json(Product.create({ name, price }));
  }

  export function destroy(req, res) {
    if (!Product.remove(Number(req.params.id))) {
      return res.status(404).json({ message: 'Produto não encontrado' });
    }

    res.status(204).end();
  }
  ```
</details>

## Desafio

Reescreva `store` de forma que o controller não tenha nenhum `if` de validação: mova a
checagem para um middleware de fábrica `validate(['name', 'price'])` e a regra de preço não
negativo para o model, que passa a lançar `HttpError`. Compare os dois controllers.

## Perguntas de revisão

### Responsabilidades

1. **Por que o controller não deve conhecer SQL?**

   <details>
     <summary>Possível resposta</summary>

     Porque isso amarra a camada HTTP ao mecanismo de armazenamento: trocar array por SQLite
     ou por Prisma passaria a exigir mudanças em todos os controllers. Com o model no meio,
     muda um arquivo só.
   </details>

2. **Por que o controller não deve saber em qual caminho está montado?**

   <details>
     <summary>Possível resposta</summary>

     Porque o prefixo é decidido no `app.use()`. Um controller que monta URLs com `/users`
     fixo impede remontar o mesmo router em `/api/v1/users`.
   </details>

### Organização

3. **Quando extrair uma camada de serviço?**

   <details>
     <summary>Possível resposta</summary>

     Quando existir regra de negócio que continuaria valendo fora do HTTP, ou quando duas
     rotas precisarem da mesma regra. Em CRUD puro, o serviço vira repasse sem ganho.
   </details>

4. **Qual o problema de um controller importar outro?**

   <details>
     <summary>Possível resposta</summary>

     Controllers falam HTTP; um chamando o outro cria dependência entre recursos por um
     motivo que não é HTTP. O que eles compartilham pertence a um model ou serviço comum.
   </details>
