Um formulário com `<input type="file">` não envia JSON. Esta aula trata do formato que ele
usa, de como recebê-lo no Express e das validações sem as quais o upload vira a rota mais
perigosa da aplicação.

Materiais: [slides da aula](../../../../slides/courses/expressjs/advanced/upload-file/) e [mapa mental](../../../../mindmaps/courses/expressjs/advanced/upload-file/).

## Objetivo

Ao final você saberá receber arquivos com `multipart/form-data`, escolher entre gravar em
disco, em memória ou em armazenamento externo, validar tipo e tamanho, e gerar nomes de
arquivo que não permitam sair do diretório previsto.

## Por que `req.body` chega vazio

Um formulário com arquivo usa um `Content-Type` diferente, que nenhum dos parsers embutidos
do Express interpreta:

| `Content-Type`                      | Conteúdo                      | Middleware               |
| ----------------------------------- | ----------------------------- | ------------------------ |
| `application/json`                  | JSON                          | `express.json()`         |
| `application/x-www-form-urlencoded` | campos de formulário simples  | `express.urlencoded()`   |
| `multipart/form-data`               | campos **e** arquivos binários| nenhum — precisa de pacote|

O corpo `multipart` é um fluxo com fronteiras separando cada parte:

```http title="Corpo multipart/form-data"
POST /users/me/avatar HTTP/1.1
Content-Type: multipart/form-data; boundary=----X

------X
Content-Disposition: form-data; name="description"

Foto de perfil
------X
Content-Disposition: form-data; name="avatar"; filename="eu.png"
Content-Type: image/png

<bytes do arquivo>
------X--
```

<Aside type="note" title="Por que o Express não traz um parser de multipart">
  Porque interpretar esse formato exige decidir **onde os bytes vão parar** — disco, memória
  ou nuvem — e isso é escolha da aplicação, não do framework. Os demais parsers só precisam
  produzir um objeto.
</Aside>

## Recebendo com `multer`

O [`multer`](https://www.npmjs.com/package/multer) é o middleware padrão para `multipart`.
Ele preenche `req.file` (ou `req.files`) e deixa os campos de texto em `req.body`:

<PackageManagerTabs package="multer" />

```ts title="src/config/upload.ts" showLineNumbers {4,9,14-16}
import multer from 'multer';
import { extname, resolve } from 'node:path';
import { randomUUID } from 'node:crypto';

const TIPOS_PERMITIDOS = ['image/png', 'image/jpeg', 'image/webp'];

export const upload = multer({
  storage: multer.diskStorage({
    destination: resolve('uploads'),
    // Nome gerado pelo servidor: o do cliente nunca é usado.
    filename: (_req, file, cb) => cb(null, `${randomUUID()}${extname(file.originalname)}`),
  }),
  limits: { fileSize: 2 * 1024 * 1024, files: 1 },
  fileFilter: (_req, file, cb) =>
    TIPOS_PERMITIDOS.includes(file.mimetype)
      ? cb(null, true)
      : cb(new HttpError(415, 'Formato de imagem não suportado')),
});
```

```ts title="src/routes/user-router.ts" showLineNumbers {3}
router.patch(
  '/me/avatar',
  authenticate,
  upload.single('avatar'),
  userController.updateAvatar,
);
```

<Aside type="danger" title="Nunca use `file.originalname` como nome no disco">
  O cliente escolhe esse valor. `../../.env` grava fora do diretório previsto; `index.html`
  sobrescreve um arquivo servido publicamente; um nome com caracteres de controle quebra o
  sistema de arquivos. Gere o nome no servidor e guarde o original apenas como metadado.
</Aside>

## Onde os bytes ficam

Três estratégias, com trocas diferentes:

<Tabs syncKey="upload-storage">
  <TabItem label="Disco">
    ```ts title="Grava direto no sistema de arquivos"
    multer({ storage: multer.diskStorage({ destination: resolve('uploads') }) });
    ```

    Simples e barato. Não sobrevive a um contêiner efêmero nem funciona com várias
    instâncias sem volume compartilhado.
  </TabItem>

  <TabItem label="Memória">
    ```ts title="Mantém em Buffer para processar antes de gravar"
    multer({ storage: multer.memoryStorage(), limits: { fileSize: 2 * 1024 * 1024 } });
    ```

    Útil para redimensionar ou validar antes de persistir. Perigoso sem `limits`: cada
    upload ocupa RAM.
  </TabItem>

  <TabItem label="Externo">
    ```ts title="Envia para armazenamento de objetos"
    // memoryStorage + SDK do provedor (S3, R2, Supabase Storage)
    await storage.upload(bucket, chave, req.file.buffer, { contentType: req.file.mimetype });
    ```

    O que se usa em produção: escala, sobrevive ao deploy e serve por CDN.
  </TabItem>
</Tabs>

| Critério                    | Disco        | Memória      | Externo        |
| --------------------------- | ------------ | ------------ | -------------- |
| Complexidade                | baixa        | baixa        | média          |
| Sobrevive ao redeploy       | com volume   | não          | sim            |
| Várias instâncias           | não          | não          | sim            |
| Consumo de RAM              | baixo        | alto         | alto (temporário) |
| Serve por CDN               | não          | não          | sim            |

## O que guardar no banco

O arquivo fica no armazenamento; o banco guarda os **metadados** e a referência:

```prisma title="prisma/schema.prisma" showLineNumbers {4,6}
model Image {
  id        String   @id @default(cuid())
  key       String   @unique          // nome gerado no armazenamento
  original  String                    // nome enviado pelo cliente, só informativo
  mimeType  String
  size      Int
  createdAt DateTime @default(now())
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

<Aside type="caution" title="Não guarde a URL completa">
  A URL muda quando o domínio, o bucket ou o CDN mudam. Guarde a **chave** e monte a URL na
  aplicação a partir de uma variável de ambiente.
</Aside>

## Validação de verdade

`fileFilter` olha o `Content-Type` enviado pelo **cliente** — que é escolhido por ele. Para
confiar no tipo, é preciso olhar os primeiros bytes do arquivo:

```ts title="Assinatura de arquivo (magic number)" showLineNumbers {1,7}
const ASSINATURAS: Record<string, number[]> = {
  'image/png': [0x89, 0x50, 0x4e, 0x47],
  'image/jpeg': [0xff, 0xd8, 0xff],
};

function tipoConfere(buffer: Buffer, mimeType: string): boolean {
  const assinatura = ASSINATURAS[mimeType];

  return assinatura?.every((byte, i) => buffer[i] === byte) ?? false;
}
```

| Verificação                | Protege de                                        |
| -------------------------- | ------------------------------------------------- |
| `limits.fileSize`          | esgotamento de disco e memória                     |
| `limits.files`             | envio de centenas de arquivos em uma requisição    |
| `fileFilter` por MIME      | envio acidental do formato errado                  |
| Assinatura nos bytes       | `.php` renomeado para `.png`                       |
| Nome gerado no servidor    | travessia de diretório e sobrescrita               |
| Diretório fora de `public/`| execução do que foi enviado                        |

<Aside type="danger" title="Nunca sirva o diretório de upload como estático executável">
  Se `uploads/` estiver dentro de `public/` e o servidor executar o que houver ali, um
  arquivo enviado vira código rodando no seu servidor. Guarde fora da raiz pública e sirva
  por uma rota que valide o acesso.
</Aside>

## Servindo o arquivo

A rota de leitura precisa resolver o caminho e **confirmar** que ele continua dentro do
diretório permitido:

```ts title="src/controllers/image-controller.ts" showLineNumbers {4,6-8}
export async function show(req: Request<{ key: string }>, res: Response) {
  const base = resolve('uploads');
  // resolve() normaliza `..`; o startsWith confirma que não escapou.
  const caminho = resolve(base, req.params.key);

  if (!caminho.startsWith(`${base}/`)) {
    throw new HttpError(400, 'Caminho inválido');
  }

  res.sendFile(caminho);
}
```

## Exercício

No projeto `express-auth`:

1. Instale o `multer` e crie `src/config/upload.ts` com nome gerado por `randomUUID`.
2. Aceite apenas PNG e JPEG, com no máximo 2 MB.
3. Crie `PATCH /users/me/avatar` protegida por `authenticate`.
4. Traduza o erro `LIMIT_FILE_SIZE` do multer para `413`.
5. Tente enviar um arquivo com `filename="../../.env"` e confirme que ele é gravado com o
   nome gerado.

<details>
  <summary>Possível resposta</summary>

  ```ts title="src/middlewares/error-handler.ts" showLineNumbers {2}
  // O multer usa `code` para sinalizar o motivo da recusa.
  if ((error as { code?: string }).code === 'LIMIT_FILE_SIZE') {
    return res.status(413).json({
      error: { status: 413, message: 'Arquivo maior que o limite de 2 MB' },
    });
  }
  ```

  O `filename` malicioso é inofensivo porque `originalname` só é usado como metadado: o
  nome no disco vem de `randomUUID()` + a extensão validada.
</details>

## Desafio

Troque o `diskStorage` por `memoryStorage`, valide a assinatura dos bytes antes de gravar e
gere uma miniatura de 128×128 com [`sharp`](https://www.npmjs.com/package/sharp). Meça o
consumo de memória com dez uploads simultâneos de 2 MB e explique por que `limits` deixa de
ser opcional nesse desenho.

## Perguntas de revisão

### Formato

1. **Por que `express.json()` não resolve o upload?**

   <details>
     <summary>Possível resposta</summary>

     Porque o corpo é `multipart/form-data`, um fluxo com partes e fronteiras, e não JSON.
     Interpretá-lo exige decidir onde os bytes serão gravados — escolha da aplicação, não do
     framework.
   </details>

2. **O que `req.file` contém e o que ele não contém?**

   <details>
     <summary>Possível resposta</summary>

     Contém metadados: nome gerado, nome original, MIME declarado, tamanho e caminho (ou
     `buffer`, em memória). Não contém garantia de que o MIME declarado corresponde ao
     conteúdo real.
   </details>

### Segurança

3. **Por que nunca usar o nome enviado pelo cliente?**

   <details>
     <summary>Possível resposta</summary>

     Porque ele pode conter `..` e escapar do diretório, sobrescrever arquivos existentes ou
     carregar caracteres que quebram o sistema de arquivos. O nome é gerado pelo servidor.
   </details>

4. **Por que verificar a assinatura dos bytes se o `Content-Type` já foi validado?**

   <details>
     <summary>Possível resposta</summary>

     Porque o `Content-Type` é declarado pelo cliente e pode mentir. Os primeiros bytes do
     arquivo são a única evidência do formato real.
   </details>

5. **Qual o risco de guardar uploads dentro de `public/`?**

   <details>
     <summary>Possível resposta</summary>

     O arquivo passa a ser servido diretamente, sem verificação de permissão — e, em
     servidores que executam certos formatos, um arquivo enviado vira código rodando no
     servidor.
   </details>
