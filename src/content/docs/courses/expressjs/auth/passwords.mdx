Antes de escrever a rota de cadastro, é preciso responder a uma pergunta: onde a senha é
guardada? A resposta certa é **em lugar nenhum** — o que se guarda é uma prova de que a
pessoa a conhece.

## Objetivo

Ao final você entenderá por que uma senha nunca é armazenada, o que sal e custo de
computação resolvem, qual a diferença entre uma função de hash e uma função de derivação de
chave, e saberá implementar hash e verificação com `node:crypto` — sem nenhuma dependência.

## O que nunca fazer

Três abordagens erradas aparecem em ordem crescente de sofisticação, e todas falham:

| Abordagem                   | Por que falha                                                     |
| --------------------------- | ----------------------------------------------------------------- |
| Guardar a senha em texto     | um vazamento do banco entrega todas as contas de imediato          |
| Criptografar a senha         | criptografia é reversível: quem tem a chave lê tudo                 |
| `MD5` ou `SHA-256` da senha  | são rápidas de propósito — bilhões de tentativas por segundo em GPU |

<Aside type="danger" title="Criptografar não é o mesmo que fazer hash">
  Criptografia existe para ser **desfeita** com a chave certa; hash é de mão única. Guardar
  senha criptografada significa que existe uma chave em algum lugar capaz de revelar todas
  elas — e essa chave costuma estar no mesmo servidor.
</Aside>

## Hash de mão única

Uma função de hash transforma qualquer entrada em uma saída de tamanho fixo, sem caminho de
volta. O servidor guarda o hash e, no login, repete o cálculo e compara:

<Mermaid title="Cadastro e login com hash de senha">
{`
flowchart TD
  subgraph C["Cadastro"]
    A1["senha em texto"] --> A2["hash(senha)"]
    A2 --> A3[("banco guarda<br/>apenas o hash")]
  end
  subgraph L["Login"]
    B1["senha enviada"] --> B2["hash(senha enviada)"]
    A3 --> B3{"os hashes<br/>são iguais?"}
    B2 --> B3
    B3 -->|sim| B4["autenticado"]
    B3 -->|não| B5["401"]
  end
`}
</Mermaid>

O servidor nunca precisa saber a senha — só precisa saber se quem está do outro lado a
conhece. Por isso um sistema bem construído **não consegue** enviar sua senha por e-mail;
ele só consegue oferecer um link para trocá-la.

## Por que `SHA-256` não basta

O hash resolve a irreversibilidade, mas cria dois problemas novos.

**Primeiro: senhas iguais geram hashes iguais.** Duas pessoas com a senha `123456` têm o
mesmo valor no banco, e uma tabela pré-calculada — *rainbow table* — traduz o hash de volta
instantaneamente.

**Segundo: velocidade é uma vantagem do atacante.** `SHA-256` foi projetada para ser rápida.
Uma GPU calcula bilhões por segundo; testar todas as senhas de oito caracteres vira questão
de horas.

| Algoritmo             | Tentativas por segundo (GPU, ordem de grandeza) |
| --------------------- | ------------------------------------------------ |
| `MD5`                 | dezenas de bilhões                               |
| `SHA-256`             | bilhões                                          |
| `bcrypt` (custo 12)   | dezenas de milhares                              |
| `Argon2id` (64 MiB)   | milhares                                         |

## O sal

O sal é um valor aleatório gerado **por senha**, misturado antes do hash e guardado junto
dele. Ele resolve o primeiro problema:

```txt title="Mesma senha, hashes diferentes"
senha: "123456"   sal: a3f1…   ->  hash: 9c2b…
senha: "123456"   sal: 7d40…   ->  hash: e18a…
```

<Aside type="note" title="O sal não é segredo">
  Ele fica em texto claro ao lado do hash — precisa estar, porque é necessário para
  reconstruir o cálculo na verificação. O que ele impede é o **pré-cálculo**: uma tabela
  teria de ser refeita para cada sal, e o ataque deixa de ser em massa.
</Aside>

## O custo de computação

O segundo problema exige uma função deliberadamente **lenta**. É isso que distingue uma
função de hash comum de uma *função de derivação de chave* (KDF): a KDF recebe parâmetros de
custo que a tornam cara de calcular.

| Parâmetro     | O que aumenta                        | Encarece o ataque com          |
| ------------- | ------------------------------------ | ------------------------------ |
| Iterações     | tempo de CPU                         | qualquer hardware              |
| Memória       | RAM necessária por cálculo           | GPU e ASIC, que têm pouca RAM  |
| Paralelismo   | threads usadas                       | ajusta o custo ao servidor     |

Um login que leva 200 ms é imperceptível para o usuário — e transforma um ataque de horas
em um ataque de anos.

<Aside type="tip" title="Calibre pelo seu servidor">
  A recomendação prática é escolher os parâmetros de modo que um hash leve entre 100 ms e
  500 ms na máquina de produção. Menos que isso é barato demais para o atacante; muito mais
  vira negação de serviço na sua própria rota de login.
</Aside>

## As três KDFs usadas na prática

| KDF        | Ano  | Custo de memória | Disponível no Node        | Situação                          |
| ---------- | ---- | ---------------- | ------------------------- | --------------------------------- |
| `bcrypt`   | 1999 | fixo e baixo     | pacote `bcrypt`           | aceitável, ainda muito usado      |
| `scrypt`   | 2009 | configurável     | `node:crypto` nativo      | boa opção, disponível há anos     |
| `Argon2id` | 2015 | configurável     | `node:crypto` (Node 24+)  | **recomendação atual** (OWASP)    |

<Aside type="note" title="Por que este guia mostra o bcrypt antes de não usá-lo">
  Praticamente todo código Express que você vai encontrar usa `bcrypt.hash` e
  `bcrypt.compare`. Entender o que essas duas linhas fazem — sal embutido, custo em
  `saltRounds`, comparação — é o que permite ler esse código e decidir conscientemente usar
  outra coisa.
</Aside>

O `bcrypt` embute sal e custo no próprio resultado:

```txt title="Anatomia de um hash bcrypt"
$2b$10$13Aak6RFaLSM2BWra67RA.KElfrt41YQsTjy9nul0bxBhXI2vjiPe
 │  │  └──────────────────┬─────────────────────────────────
 │  │                     └─ sal (22 chars) + hash (31 chars)
 │  └─ custo: 2^10 iterações
 └─ versão do algoritmo
```

```js title="Com o pacote bcrypt" showLineNumbers
const hash = await bcrypt.hash('senha-secreta', 10);
//=> $2b$10$13Aak6RFaLSM2BWra67RA.KElfrt41…

const ok = await bcrypt.compare('senha-secreta', hash);
//=> true
```

A limitação do `bcrypt` é o custo de memória fixo e baixo, que o torna vulnerável a hardware
dedicado — e é exatamente o que o Argon2 foi projetado para resolver.

## Implementando com `node:crypto`

O `bcrypt` é uma dependência nativa que precisa compilar em cada plataforma. Desde o Node 24
existe `argon2Sync` embutido, e o mesmo formato de saída pode ser reproduzido sem nenhum
pacote.

### O formato PHC

O segredo de um hash portável é guardar **os parâmetros junto do resultado**. O formato PHC
é o padrão que `bcrypt`, `scrypt` e `argon2` seguem:

```txt title="Formato PHC de um hash Argon2id"
$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
 │        │    │                │            └─ hash em base64
 │        │    │                └─ sal em base64
 │        │    └─ memória (KiB), passagens, paralelismo
 │        └─ versão do Argon2
 └─ algoritmo
```

<Aside type="tip" title="Por isso o hash antigo continua válido">
  Guardar os parâmetros junto permite endurecer os custos amanhã sem invalidar os hashes de
  hoje: a verificação usa os parâmetros que vieram no próprio registro.
</Aside>

## Comparação em tempo constante

A última linha é a menos óbvia e a mais importante. `===` compara byte a byte e **para no
primeiro diferente** — o tempo de resposta revela quantos bytes iniciais estavam certos, e
com medições suficientes um atacante reconstrói o valor.

<Mermaid title="Por que a comparação ingênua vaza informação">
{`
flowchart TD
  A["Comparação com ==="] --> B["Para no primeiro byte diferente"]
  B --> C["Tempo de resposta varia<br/>conforme o prefixo acertado"]
  C --> D["Ataque de temporização<br/>descobre byte a byte"]
  E["timingSafeEqual"] --> F["Percorre todos os bytes sempre"]
  F --> G["Tempo constante<br/>nada é revelado"]
`}
</Mermaid>

```ts title="A diferença" del={2} ins={5}
// Vaza informação pelo tempo de execução
return hashArmazenado === hashCalculado;

// Tempo constante, independente de onde está a diferença
return timingSafeEqual(hashArmazenado, hashCalculado);
```

<Aside type="caution" title="`timingSafeEqual` exige buffers do mesmo tamanho">
  Ele lança se os comprimentos diferirem — por isso o código compara `length` antes. E o
  próprio comprimento não é segredo: o hash tem tamanho fixo conhecido.
</Aside>

## Nativo ou pacote?

    Nada para instalar, nada para compilar, nada para atualizar por CVE. Exige Node 24 para

  </TabItem>

  <TabItem label="Pacote">

    troca, uma dependência nativa que compila em cada plataforma.
  </TabItem>

| Critério                    | `node:crypto`          | `bcrypt` / `argon2`         |
| --------------------------- | ---------------------- | --------------------------- |
| Dependências                | nenhuma                | uma, com binário nativo     |
| Instalação em CI e Docker   | trivial                | exige toolchain de compilação |
| Padrões seguros             | você define            | já vêm calibrados           |
| Entendimento do que ocorre  | explícito              | encapsulado                 |
| Node mínimo (Argon2)        | 24                     | qualquer                    |

<Aside type="tip" title="A escolha informada é o objetivo">
  Usar o pacote depois de ter escrito a versão nativa é uma decisão; usar o pacote sem saber
  o que ele faz é sorte. Em projeto real, `argon2` ou `bcrypt` são escolhas perfeitamente
  razoáveis.
</Aside>

## Exercício

No projeto `express-auth`:

1. Rode os testes e confirme que dois hashes da mesma senha são diferentes.
2. Meça o tempo de `hashPassword` com `console.time`.
3. Reduza `MEMORY_KIB` para `4096` e meça de novo. Quanto mais rápido ficou — e o que isso
   significa para um atacante?
4. Troque `timingSafeEqual` por `===` e explique por que os testes **continuam passando**.
5. Volte os dois valores e escreva um teste que rejeite um hash com versão diferente de 19.

<details>
  <summary>Possível resposta</summary>

  ```ts title="Medindo o custo" showLineNumbers
  console.time('hash');
  hashPassword('senha-secreta');
  console.timeEnd('hash');
  //=> hash: 61.2ms   (m=65536)
  //=> hash: 4.8ms    (m=4096)
  ```

  Treze vezes mais rápido significa treze vezes mais tentativas por segundo para quem tem o
  banco vazado.

  Os testes continuam passando com `===` porque eles verificam **correção**, não segurança:
  a comparação ingênua devolve o mesmo booleano. O que muda é o tempo de resposta, e nenhum
  teste funcional observa tempo. É justamente por isso que essa classe de falha sobrevive à
  revisão de código.
</details>

## Desafio

Implemente `needsRehash(storedHash)`, que devolve `true` quando o hash foi gerado com
parâmetros mais fracos que os atuais. Use-a no login: quando a senha estiver correta **e** o
hash estiver defasado, regrave-o com os parâmetros novos. Explique por que esse é o único
momento em que o *rehash* é possível.

## Perguntas de revisão

### Fundamentos

1. **Por que não se guarda a senha criptografada?**

   <details>
     <summary>Possível resposta</summary>

     Porque criptografia é reversível: existe uma chave capaz de revelar todas as senhas, e
     ela costuma estar no mesmo servidor. Hash é de mão única — não há o que revelar.
   </details>

2. **O que o sal impede, exatamente?**

   <details>
     <summary>Possível resposta</summary>

     O pré-cálculo. Sem sal, uma tabela pronta traduz hashes conhecidos de volta para senhas,
     e senhas iguais têm hashes iguais. Com um sal por registro, a tabela teria de ser
     refeita para cada usuário.
   </details>

3. **Por que uma função de hash lenta é desejável?**

   <details>
     <summary>Possível resposta</summary>

     Porque o custo recai sobre quem faz bilhões de tentativas, não sobre o usuário que faz
     uma. 200 ms são imperceptíveis no login e multiplicam por milhões o tempo de um ataque
     de força bruta.
   </details>

### Implementação

4. **Por que os parâmetros ficam guardados dentro do hash?**

   <details>
     <summary>Possível resposta</summary>

     Para que a verificação possa refazer o cálculo exatamente como ele foi feito, mesmo
     depois de os padrões terem sido endurecidos. É o que permite aumentar o custo sem
     invalidar os registros antigos.
   </details>

5. **Por que `timingSafeEqual` em vez de `===`?**

   <details>
     <summary>Possível resposta</summary>

     Porque `===` para no primeiro byte diferente, e o tempo de resposta revela o tamanho do
     prefixo correto. Com medições repetidas, o valor é reconstruído byte a byte.
     `timingSafeEqual` percorre tudo sempre.
   </details>
