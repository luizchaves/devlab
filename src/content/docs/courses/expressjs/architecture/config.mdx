Porta, URL do banco, segredo de token, endereço de SMTP: uma API precisa de valores que
mudam entre a sua máquina, a do colega e o servidor de produção. Este tópico mostra onde eles
devem morar — e por que nunca no código.

Materiais: [slides do tópico](../../../../slides/courses/expressjs/architecture/config/) e [mapa mental](../../../../mindmaps/courses/expressjs/architecture/config/).

## Objetivo

Ao final você saberá carregar variáveis de ambiente sem dependências, separar `.env` de
`.env.example`, validar a configuração na inicialização e reconhecer o que é segredo e o que
não é.

## Por que não no código?

Um valor escrito direto no arquivo cria três problemas de uma vez:

```js title="O que não fazer" del={2,5}
const app = express();
const JWT_SECRET = 'abc123'; // vai para o Git, e todo mundo vê

app.listen(3000, () => {
  //         ^ a porta de produção é outra, e não dá para mudar sem editar código
});
```

1. **Segredo versionado.** Uma vez enviado ao Git, o valor está no histórico para sempre —
   apagar a linha depois não resolve.
2. **Mesmo código, ambientes diferentes.** Desenvolvimento aponta para SQLite local;
   produção, para Postgres. Se o valor está no código, são duas versões do código.
3. **Impossível de operar.** Trocar a porta ou a URL do banco passa a exigir um novo deploy.

A regra que resolve os três é a mesma há mais de uma década: **configuração vive no
ambiente**, não no código.

## `process.env` e `--env-file`

O Node expõe as variáveis de ambiente em `process.env`. Elas podem vir do shell, do
orquestrador de produção — ou de um arquivo `.env` carregado nativamente:

<Tabs syncKey="env-loading">
  <TabItem label="Node nativo">
    ```bash title="Terminal"
    node --env-file=.env src/server.ts
    ```

    ```json title="package.json" {3}
    {
      "scripts": {
        "dev": "node --env-file-if-exists=.env --watch src/server.ts"
      }
    }
    ```
  </TabItem>

  <TabItem label="dotenv">
    <PackageManagerTabs package="dotenv" />

    ```js {1}
    import 'dotenv/config';

    // A partir daqui, process.env já traz o conteúdo do .env
    ```
  </TabItem>
</Tabs>

| Critério                        | `--env-file`         | `dotenv`                       |
| ------------------------------- | -------------------- | ------------------------------ |
| Dependência                     | nenhuma              | uma dependência de produção    |
| Versão mínima do Node           | 20.6                 | qualquer                       |
| Falha se o arquivo não existir  | sim (`--env-file`)   | não                            |
| Variante tolerante              | `--env-file-if-exists` | comportamento padrão         |
| Carrega antes de qualquer import| sim                  | depende da ordem dos imports   |

<Aside type="tip" title="A flag carrega antes do primeiro import">
  Com `dotenv`, um módulo importado **antes** do `import 'dotenv/config'` já lê
  `process.env` vazio — bug clássico em arquivos que criam o client do banco no topo. A flag
  do Node não tem esse problema: as variáveis existem antes de o primeiro módulo carregar.
</Aside>

## `.env` e `.env.example`

São dois arquivos com papéis opostos, e confundi-los é o erro mais comum:

| Arquivo        | Vai para o Git? | Contém                                              |
| -------------- | --------------- | --------------------------------------------------- |
| `.env`         | **não**         | os valores reais desta máquina, incluindo segredos   |
| `.env.example` | **sim**         | a lista de variáveis com valores de exemplo ou vazios|

```ini title=".env.example"
NODE_ENV=development
PORT=3000

DATABASE_URL="file:./prisma/dev.db"

# Minimo de 32 caracteres. Gere o seu com: openssl rand -hex 32
JWT_SECRET="troque-este-segredo-de-desenvolvimento-com-32-chars"
JWT_EXPIRES_IN=3600

# Origens autorizadas a ler as respostas, separadas por virgula.
CORS_ORIGINS="http://localhost:5173"

RATE_LIMIT_MAX=100
RATE_LIMIT_WINDOW_MS=60000

LOG_LEVEL=info
```

```txt title=".gitignore" {2}
node_modules
.env
```

Quem clona o projeto roda `cp .env.example .env` e preenche os valores. O `.env.example`
funciona como documentação executável: se uma variável nova não aparece nele, a próxima
pessoa descobre a ausência por um erro em execução.

<Aside type="danger" title="Segredo que vazou é segredo queimado">
  Se um `.env` foi enviado ao Git, remover o arquivo não basta — o valor continua no
  histórico e em qualquer clone. O procedimento correto é **rotacionar**: gerar um segredo
  novo e invalidar o antigo.
</Aside>

## Um módulo de configuração

## O que muda entre ambientes?

`NODE_ENV` é a variável que o próprio Express observa: em `production` ele desliga páginas
de erro detalhadas e liga o cache de views.

| Aspecto                    | Desenvolvimento              | Produção                             |
| -------------------------- | ---------------------------- | ------------------------------------ |
| `NODE_ENV`                 | `development`                | `production`                          |
| Origem das variáveis       | arquivo `.env`               | ambiente do orquestrador/PaaS         |
| Banco                      | SQLite local                 | Postgres gerenciado                   |
| Mensagem de erro `5xx`     | pode detalhar                | genérica, detalhe só no log           |
| Segredo de token           | padrão de conveniência       | obrigatório, aleatório e rotacionável |
| Log                        | legível por humano           | JSON estruturado                      |

<Aside type="caution" title="`NODE_ENV=production` não é só uma etiqueta">
  Bibliotecas mudam de comportamento com base nela. Rodar produção sem definir `NODE_ENV`
  mantém verificações caras de desenvolvimento ligadas e pode expor stack traces.
</Aside>

## Exercício

Partindo da [etapa 9 da TaskAPI](../../practice/taskapi/auth/), que ainda lê `process.env`
espalhado:

1. Crie `.env.example` com `PORT` e `NODE_ENV` e acrescente `.env` ao `.gitignore`.
2. Escreva `src/config.ts` com a função `required` e exporte `port` e `isProduction`.
3. Faça `server.ts` usar `config.port`.
4. Acrescente `DATABASE_URL` como obrigatória e confirme que a aplicação recusa subir sem
   ela.
5. Ajuste o script `dev` para `node --env-file-if-exists=.env --watch src/server.ts`.

Depois compare com a [etapa 10](../../practice/taskapi/hardening/), que faz o mesmo com um
schema Zod em vez da função `required`.

<details>
  <summary>Possível resposta</summary>

  ```ts showLineNumbers
  function required(nome: string): string {
    const valor = process.env[nome];

    if (!valor) {
      throw new Error(`Variável de ambiente obrigatória ausente: ${nome}`);
    }

    return valor;
  }

  export const config = {
    port: Number(process.env.PORT ?? 3000),
    databaseUrl: required('DATABASE_URL'),
    isProduction: process.env.NODE_ENV === 'production',
  };
  ```

  Sem `DATABASE_URL`, o `import` de `config.ts` lança e o processo termina com código
  diferente de zero — o comportamento desejado.
</details>

## Desafio

Faça `config.ts` validar também o **formato**: `PORT` precisa ser um inteiro entre 1 e 65535
e `JWT_SECRET` precisa ter ao menos 32 caracteres. Compare a sua validação manual com o
schema da [etapa 10](../../practice/taskapi/hardening/) e conte as linhas de cada uma.

## Perguntas de revisão

### Ambiente

1. **Por que remover o `.env` do repositório não resolve um vazamento?**

   <details>
     <summary>Possível resposta</summary>

     Porque o valor continua no histórico do Git e em todos os clones já feitos. A única
     resposta eficaz é rotacionar o segredo, invalidando o antigo.
   </details>

2. **Qual a diferença entre `--env-file` e `--env-file-if-exists`?**

   <details>
     <summary>Possível resposta</summary>

     O primeiro falha se o arquivo não existir; o segundo segue adiante. Em produção, onde
     as variáveis vêm do orquestrador e não há `.env`, a variante tolerante é a correta.
   </details>

3. **Por que carregar o `.env` com `dotenv` pode chegar tarde demais?**

   <details>
     <summary>Possível resposta</summary>

     Porque os imports do módulo são resolvidos antes do corpo dele executar. Um módulo que
     lê `process.env` no topo e é importado antes do `import 'dotenv/config'` enxerga
     `undefined`.
   </details>

### Configuração

4. **Qual a vantagem de um módulo `config` sobre `process.env` espalhado?**

   <details>
     <summary>Possível resposta</summary>

     Os valores ficam tipados e convertidos em um lugar só, e a ausência de uma variável
     obrigatória derruba a aplicação na inicialização, não na primeira requisição que a usa.
   </details>

5. **Por que `JWT_SECRET` pode ter valor padrão em desenvolvimento, mas não em produção?**

   <details>
     <summary>Possível resposta</summary>

     Porque em desenvolvimento o padrão evita atrito e o dado não é real. Em produção, um
     segredo padrão é público — qualquer pessoa que conheça o projeto consegue forjar tokens
     válidos.
   </details>
