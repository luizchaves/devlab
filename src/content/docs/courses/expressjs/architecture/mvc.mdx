Os tópicos anteriores separaram rotas, controllers e middlewares por conveniência. Este tópico
nomeia o resultado (**MVC**) e mostra por que a direção das dependências entre as camadas
é o que dá valor à separação.

Materiais: [slides do tópico](../../../../slides/courses/expressjs/architecture/mvc/) e [mapa mental](../../../../mindmaps/courses/expressjs/architecture/mvc/).

## Objetivo

Ao final você saberá organizar uma aplicação Express em camadas com responsabilidade única,
justificar em qual arquivo cada linha de código deve morar e trocar a camada de dados
— memória por banco — sem tocar em nenhuma outra.

## As quatro peças

<CardGrid>
  <Card title="Model" icon="database">
    Guarda e recupera os dados. É o único que sabe *onde* eles estão — array, SQLite ou
    Prisma.
  </Card>

  <Card title="Controller" icon="puzzle">
    Traduz HTTP em chamadas de domínio: lê a requisição, chama o model e escolhe o status.
  </Card>

  <Card title="Router" icon="forward-slash">
    Diz apenas quais caminhos existem e qual função responde a cada um.
  </Card>

  <Card title="Middleware" icon="setting">
    Comportamentos transversais: leitura do corpo, log, autenticação e tratamento de erros.
  </Card>
</CardGrid>

<Aside type="note" title="O “V” de View em uma API">
  No MVC clássico a View renderiza HTML. Numa API REST, a representação é o JSON — e quem a
  produz é o `res.json()` do controller. A camada existe; ela só não tem template.
</Aside>

## A direção das dependências

O que torna a separação útil não é ter quatro pastas, e sim o fato de as dependências
apontarem **sempre no mesmo sentido**:

<Mermaid title="Direção das dependências entre as camadas de uma aplicação Express">
{`
flowchart TD
  A["Requisição HTTP"] --> B["app<br/>monta a aplicação e a cadeia de middlewares"]
  B --> C["routes/<br/>quais caminhos existem"]
  C --> D["controllers/<br/>lê a requisição e escolhe a resposta"]
  D --> E["models/<br/>lê e grava os dados"]
  E --> F[("Armazenamento<br/>memória, SQLite, Prisma")]
  D --> G["Resposta JSON"]
  D -. "erro" .-> H["middlewares/error-handler<br/>traduz o erro em resposta"]
  H --> G
`}
</Mermaid>

O router conhece o controller, o controller conhece o model e **o model não conhece
ninguém**. Nenhuma seta sobe. É essa regra que permite trocar a camada de dados sem tocar
nas outras — e é ela que a próximo tópico, de [Prisma](../../persistence/prisma/), exercita.

A tabela torna o limite de cada arquivo verificável em revisão de código:

| Camada        | Pode importar            | Nunca deve conter                              |
| ------------- | ------------------------ | ---------------------------------------------- |
| `routes/`     | controllers, middlewares | lógica de negócio, acesso a dados               |
| `controllers/`| models, erros, tipos     | SQL, `prisma.*`, HTML, o prefixo da rota        |
| `models/`     | acesso a dados, tipos    | `req`, `res`, status HTTP                       |
| `middlewares/`| erros, utilitários       | regra específica de um recurso                  |
| `errors/`     | nada                     | qualquer dependência da aplicação               |

<Aside type="caution" title="`req` dentro do model é o sintoma mais comum">
  Um model que recebe `req` deixou de ser reaproveitável fora do HTTP: ele não pode ser
  chamado por um seed, por um script de importação ou por um teste unitário. Passe os dados
  já extraídos.
</Aside>

## A cadeia montada em `app.ts`

O `app.ts` é o único arquivo que enxerga a aplicação inteira. A ordem em que ele registra os
middlewares **é** a arquitetura em execução:

<Aside type="caution" title="A ordem não é estilo, é comportamento">
  `express.json()` precisa vir antes do router, senão `req.body` chega `undefined`. O
  `notFound` precisa vir depois de todas as rotas, senão bloqueia a API inteira. E o
  `errorHandler` precisa ser o último, senão nunca é alcançado.
</Aside>

## O que mudou desde o tópico de Rotas?

A rota deixou de responder e passou a apenas apontar:

```ts title="src/routes/task-router.ts" del={2-4} ins={6}
// antes: o router respondia
router.get('/', (req, res) => {
  res.json(tasks);
});

router.get('/', taskController.index);
```

## Quando acrescentar uma camada?

MVC não é o fim da linha. Duas camadas aparecem quando o projeto cresce:

| Camada      | Aparece quando                                              | Exemplo                                     |
| ----------- | ----------------------------------------------------------- | ------------------------------------------- |
| `services/` | há regra de negócio que não é sobre HTTP nem sobre armazenamento | "não concluir tarefa com subtarefa aberta" |
| `repositories/` | o mesmo domínio precisa de mais de uma fonte de dados   | cache em memória na frente do banco          |

<Aside type="tip" title="Cerimônia tem custo">
  Em um CRUD sem regra própria, um `service` que apenas repassa a chamada ao model
  acrescenta um arquivo e nenhum significado. Crie a camada quando existir a regra.
</Aside>

## Exercício

Acrescente o recurso **tags** ao projeto, seguindo exatamente a mesma estrutura:

1. `src/types/tag.ts` com `Tag` e `TagInput`;
2. `src/models/tag-model.ts` com `findAll`, `findById`, `create` e `remove`;
3. `src/controllers/tag-controller.ts` com `index`, `show`, `store` e `destroy`;
4. `src/routes/tag-router.ts` apontando para o controller;
5. registro em `app.ts` sob o prefixo `/tags`.

Uma tag tem `id`, `name` e `color`. Rejeite com `400` a criação sem `name` ou com `color`
fora do formato `#rrggbb`, e responda `204` no `DELETE`.

<details>
  <summary>Possível resposta</summary>

  ```ts
  export interface Tag {
    id: number;
    name: string;
    color: string;
  }

  export interface TagInput {
    name?: string;
    color?: string;
  }
  ```

  ```ts
  import type { Request, Response } from 'express';

  import { HttpError } from '#errors/HttpError.ts';
  import * as Tag from '#models/tag-model.ts';
  import type { TagInput } from '#types/tag.ts';

  export function store(req: Request, res: Response) {
    const { name, color } = (req.body ?? {}) as TagInput;

    if (!name || !/^#[0-9a-f]{6}$/i.test(color ?? '')) {
      throw new HttpError(400, 'Os campos "name" e "color" (#rrggbb) são obrigatórios');
    }

    res.status(201).json(Tag.create({ name, color }));
  }
  ```

  Em `app.ts`: `app.use('/tags', tagRouter);` — registrado **antes** do `notFound`.
</details>

## Desafio

Extraia a validação para um middleware de fábrica reutilizável pelos dois recursos:

```ts
export function validate(camposObrigatorios: string[]) {
  return (req: Request, res: Response, next: NextFunction) => {
    // devolve um middleware que valida req.body
  };
}
```

```ts title="src/routes/task-router.ts" ins={1}
router.post('/', validate(['title']), taskController.store);
```

Os controllers devem ficar sem nenhum `if` de validação. Pense: onde esse middleware precisa
ser registrado para que o erro chegue ao `errorHandler`?

## Perguntas de revisão

### Camadas

1. **Por que nenhuma seta do diagrama sobe?**

   <details>
     <summary>Possível resposta</summary>

     Porque uma dependência de baixo para cima amarraria o model ao HTTP: ele deixaria de
     poder ser usado por um seed, um script ou um teste. A direção única é o que permite
     trocar a camada de dados sem tocar nas outras.
   </details>

2. **Um model pode responder `404`?**

   <details>
     <summary>Possível resposta</summary>

     Não. `404` é um conceito HTTP e pertence ao controller. O model devolve `undefined` (ou
     lança um erro de domínio) e o controller traduz isso em status.
   </details>

3. **O que dá errado se `express.json()` for registrado depois do router?**

   <details>
     <summary>Possível resposta</summary>

     O router responde antes de o corpo ser interpretado, e `req.body` chega `undefined` em
     todo `POST` e `PUT` — sem nenhum erro visível no servidor.
   </details>

### Evolução

4. **Quando criar a pasta `services/`?**

   <details>
     <summary>Possível resposta</summary>

     Quando existir regra de negócio que continuaria valendo fora do HTTP, ou que seja
     compartilhada por mais de uma rota. Antes disso, o serviço só repassa chamadas.
   </details>

5. **Trocar array por Prisma exige mudar quais arquivos?**

   <details>
     <summary>Possível resposta</summary>

     Apenas os de `models/` (e a configuração do client). Router, controllers, middlewares e
     o formato das respostas permanecem idênticos — é exatamente o que o tópico de
     [CRUD com Prisma](../../persistence/crud/) demonstra.
   </details>
