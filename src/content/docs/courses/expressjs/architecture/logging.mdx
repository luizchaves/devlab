Enquanto a aplicação roda na sua máquina, o depurador resolve. Depois do deploy, a única
janela para dentro dela é o que ela mesma escreve. Este tópico trata de escrever isso de forma
útil.

Materiais: [slides do tópico](../../../../slides/courses/expressjs/architecture/logging/) e [mapa mental](../../../../mindmaps/courses/expressjs/architecture/logging/).

## Objetivo

Ao final você saberá registrar requisições com um middleware próprio, escolher entre log
legível e log estruturado, correlacionar as linhas de uma mesma requisição e expor um
endpoint de saúde.

## O que registrar?

Um log de requisição só é útil se responder três perguntas: **o que foi pedido**, **o que
foi respondido** e **quanto tempo levou**.

| Campo         | Por quê                                                      |
| ------------- | ------------------------------------------------------------ |
| `method`      | distingue leitura de escrita                                  |
| `url`         | identifica o endpoint                                         |
| `status`      | separa sucesso de erro do cliente e de erro do servidor       |
| `durationMs`  | revela a rota lenta antes de o usuário reclamar               |
| `requestId`   | costura todas as linhas de uma mesma requisição               |
| `userId`      | responde "quem foi afetado" em um incidente                   |

E há o que **nunca** deve ser registrado:

| Nunca logar                   | Por quê                                                    |
| ----------------------------- | ---------------------------------------------------------- |
| Senha, mesmo errada           | vaza credencial em texto puro no arquivo de log             |
| Token, cookie de sessão       | permite personificar o usuário                              |
| `req.body` inteiro em cadastro| carrega senha, CPF e endereço sem que ninguém perceba       |
| Dado pessoal desnecessário    | o log costuma ter retenção e acesso mais amplos que o banco |

<Aside type="danger" title="`console.log(req.body)` no controller de login">
  É a forma mais comum de vazar senha em produção. Se precisar depurar o corpo, registre
  apenas as **chaves** (`Object.keys(req.body)`), nunca os valores.
</Aside>

## Um middleware de log

O middleware precisa medir o tempo até o fim da resposta, e só o evento `finish` sabe qual
foi o status final:

```ts showLineNumbers {2,4,7}
export function logger(req: Request, res: Response, next: NextFunction) {
  const start = process.hrtime.bigint();

  res.on('finish', () => {
    const durationMs = Number(process.hrtime.bigint() - start) / 1e6;

    console.log(
      `${req.method} ${req.originalUrl} ${res.statusCode} ${durationMs.toFixed(1)}ms`,
    );
  });

  next();
}
```

```txt title="Output" frame="terminal"
GET /tasks 200 3.4ms
POST /tasks 201 8.1ms
GET /tasks/99 404 1.2ms
```

<Aside type="note" title="Por que `finish` e não depois do `next()`">
  `next()` apenas agenda o restante da cadeia; o código logo abaixo dele executa antes de a
  resposta existir. `res.statusCode` ali ainda vale o padrão `200`, mesmo em uma requisição
  que vai terminar em `404`.
</Aside>

## Níveis

Nem toda linha tem a mesma importância. Quatro níveis dão conta de uma API de porte médio:

| Nível   | Quando usar                                                    |
| ------- | -------------------------------------------------------------- |
| `debug` | detalhe de investigação — desligado em produção                 |
| `info`  | fatos normais: requisição atendida, aplicação iniciada          |
| `warn`  | algo suspeito que não quebrou: `429`, token expirado, retentativa|
| `error` | falha que exigiu `5xx` — sempre com stack trace no log          |

A regra prática do `errorHandler`: `4xx` é comportamento esperado do cliente e vira `warn`
(ou nada); `5xx` é defeito da aplicação e sempre vira `error`.

```ts showLineNumbers {4,6}
export function errorHandler(error, req, res, next) {
  const status = error instanceof HttpError ? error.status : 500;

  if (status >= 500) {
    // Só o log recebe o stack trace; o cliente recebe a mensagem genérica.
    console.error({ level: 'error', requestId: req.id, stack: error.stack });
  }

  res.status(status).json({
    error: {
      status,
      message: status >= 500 ? 'Erro interno do servidor' : error.message,
      requestId: req.id,
    },
  });
}
```

## Pacotes prontos

Os dois pacotes mais usados fazem exatamente o que os middlewares acima fazem, com mais
opções e melhor desempenho:

| Pacote                                                     | Formato               | Bom para                          |
| ---------------------------------------------------------- | --------------------- | --------------------------------- |
| [`morgan`](https://www.npmjs.com/package/morgan)            | texto, formatos prontos | log de acesso em desenvolvimento |
| [`pino`](https://www.npmjs.com/package/pino) + `pino-http`  | JSON, assíncrono      | produção e agregadores de log     |

```ts showLineNumbers
import morgan from 'morgan';

// 'dev' colore o status; 'combined' é o formato de log de servidor web.
app.use(morgan(config.isProduction ? 'combined' : 'dev'));
```

<Aside type="tip" title="Escrever o próprio primeiro tem valor">
  Depois de escrever o middleware deste tópico, `morgan` deixa de ser mágica: ele é a mesma
  ideia com formatos parametrizados. Essa é a razão de o guia mostrar a versão nativa antes
  do pacote.
</Aside>

## Exercício

Partindo da [etapa 9 da TaskAPI](../../practice/taskapi/auth/), que ainda usa
`console.log`:

1. Crie `src/middlewares/request-id.ts` conforme o tópico e registre-o como **primeiro**
   middleware.
2. Substitua o `console.log` de `app.ts` por um middleware `logger` que meça a duração.
3. Faça o `logger` emitir JSON quando `NODE_ENV === 'production'` e texto caso contrário.
4. Inclua o `requestId` na resposta de erro do `errorHandler`.
5. Acrescente `GET /health` e `GET /ready`.

<details>
  <summary>Possível resposta</summary>

  ```ts showLineNumbers
  import type { NextFunction, Request, Response } from 'express';

  import { config } from '#config.ts';

  export function logger(req: Request, res: Response, next: NextFunction) {
    const start = process.hrtime.bigint();

    res.on('finish', () => {
      const entry = {
        level: 'info',
        time: new Date().toISOString(),
        requestId: req.id,
        method: req.method,
        url: req.originalUrl,
        status: res.statusCode,
        durationMs: Number(process.hrtime.bigint() - start) / 1e6,
      };

      console.log(
        config.isProduction
          ? JSON.stringify(entry)
          : `${entry.method} ${entry.url} ${entry.status} ${entry.durationMs.toFixed(1)}ms`,
      );
    });

    next();
  }
  ```

  O `requestId` precisa ser registrado antes do `logger`; caso contrário `req.id` ainda não
  existe quando a linha é escrita.
</details>

## Desafio

Faça o `logger` **omitir** campos sensíveis: escreva uma função `redact(body)` que substitua
por `'[REDACTED]'` os valores das chaves `password`, `token` e `authorization`, e registre o
corpo redigido nas rotas de `POST`. Explique por que redigir por lista de chaves conhecidas
é mais seguro do que tentar detectar segredos por formato.

## Perguntas de revisão

### Log de requisições

1. **Por que medir a duração dentro de `res.on('finish')`?**

   <details>
     <summary>Possível resposta</summary>

     Porque é o único momento em que a resposta já foi escrita: antes disso `res.statusCode`
     ainda vale o padrão e a duração seria a do agendamento, não a da requisição.
   </details>

2. **Qual o problema de logar `req.body` no cadastro?**

   <details>
     <summary>Possível resposta</summary>

     O corpo carrega a senha em texto puro — e logs costumam ter retenção longa e acesso
     mais amplo que o banco. Logar apenas as chaves preserva a utilidade sem o vazamento.
   </details>

### Operação

3. **Para que serve o request id?**

   <details>
     <summary>Possível resposta</summary>

     Para correlacionar todas as linhas de log de uma mesma requisição, mesmo com dezenas
     acontecendo em paralelo, e para ligar a reclamação do usuário à requisição exata quando
     ele informa o id devolvido na resposta de erro.
   </details>

4. **Por que `4xx` não deve virar `error` no log?**

   <details>
     <summary>Possível resposta</summary>

     Porque `4xx` é comportamento esperado do cliente — um formulário incompleto não é
     defeito do servidor. Tratá-lo como erro enche o log de ruído e esconde os `5xx`, que
     são os que exigem ação.
   </details>

5. **Por que um health check não deve consultar o banco a cada chamada?**

   <details>
     <summary>Possível resposta</summary>

     Porque o orquestrador o chama com alta frequência, e a consulta vira carga constante.
     Separa-se então um teste barato de vida do processo de uma verificação de prontidão
     mais completa e menos frequente.
   </details>
