Autenticação e autorização respondem "quem é" e "o que pode". Sobram os ataques que não
dependem de conta nenhuma: força bruta, injeção, corpo gigante, dependência comprometida.
Esta aula trata deles.

Materiais: [slides da aula](../../../../slides/courses/expressjs/security/hardening/) e [mapa mental](../../../../mindmaps/courses/expressjs/security/hardening/).

## Objetivo

Ao final você saberá aplicar os cabeçalhos de segurança que uma API deve enviar, limitar
requisições e tamanho de corpo, reconhecer as injeções que ainda acontecem em Node e manter
segredos e dependências sob controle.

## O que é preciso defender

Nem toda defesa é sobre invasores sofisticados. As três categorias abaixo cobrem quase tudo
que atinge uma API pequena:

| Categoria                | Exemplo                                       | Defesa principal                  |
| ------------------------ | --------------------------------------------- | --------------------------------- |
| Abuso de recurso         | força bruta no login, upload de 2 GB           | limites de taxa e de tamanho      |
| Injeção                  | SQL, comando de sistema, prototype pollution   | parametrizar e nunca interpolar   |
| Configuração exposta     | segredo no Git, stack trace na resposta        | ambiente e tratamento de erro     |

<Aside type="note" title="Segurança é camada, não interruptor">
  Nenhum item desta aula sozinho torna a API segura. O objetivo é que uma falha em uma
  camada não seja suficiente — princípio de defesa em profundidade.
</Aside>

## Cabeçalhos de segurança

O Express envia por padrão um cabeçalho que só ajuda o atacante:

```http title="Resposta padrão do Express"
X-Powered-By: Express
```

Ele informa a tecnologia e a superfície de ataque. Remover é uma linha:

```ts showLineNumbers {1}
app.disable('x-powered-by');
```

Os demais cabeçalhos instruem o navegador a se proteger:

| Cabeçalho                     | Efeito                                                        |
| ----------------------------- | ------------------------------------------------------------- |
| `Strict-Transport-Security`   | força HTTPS nas próximas visitas                               |
| `X-Content-Type-Options: nosniff` | impede o navegador de adivinhar o tipo do conteúdo         |
| `X-Frame-Options: DENY`       | bloqueia a página dentro de um iframe (*clickjacking*)         |
| `Content-Security-Policy`     | restringe de onde scripts e estilos podem vir                  |
| `Referrer-Policy`             | limita o que vaza na navegação para outros sites               |

<Aside type="tip" title="Para uma API pura, poucos cabeçalhos importam">
  `Content-Security-Policy` e `X-Frame-Options` protegem **páginas**. Numa API que só
  devolve JSON, os que realmente contam são `nosniff`, `HSTS` e a ausência do
  `X-Powered-By`. Se o Express também serve HTML, o conjunto completo passa a valer.
</Aside>

qualquer usuário cai. O limite é por janela de tempo e por chave:

<Aside type="caution" title="`Map` em memória não escala nem sobrevive ao restart">
  Com duas instâncias, cada uma conta separadamente — e o limite efetivo dobra. Em produção,
  o contador precisa ser compartilhado (Redis) — é o que
  [`express-rate-limit`](https://www.npmjs.com/package/express-rate-limit) faz com um
  *store* configurável.
</Aside>

<Aside type="danger" title="Confiar em `req.ip` atrás de proxy">
  Por trás de um balanceador, `req.ip` é o IP do proxy: todos os usuários compartilham o
  mesmo limite. É preciso `app.set('trust proxy', 1)` para que o Express leia
  `X-Forwarded-For` — e esse cabeçalho só é confiável se **o seu** proxy o reescrever.
</Aside>

## Limite de tamanho do corpo

`express.json()` aceita 100 KB por padrão. Um valor generoso demais transforma um `POST` em
esgotamento de memória:

```ts showLineNumbers {1}
app.use(express.json({ limit: '100kb' }));
```

O corpo acima do limite gera um erro que precisa virar `413`:

```ts showLineNumbers {2}
// entity.too.large vem do body-parser, usado por express.json()
if ((error as { type?: string }).type === 'entity.too.large') {
  return res.status(413).json({ error: { status: 413, message: 'Corpo muito grande' } });
}
```

## As injeções que sobram

Cada tipo de injeção tem a mesma raiz — dado do usuário virando código — e a mesma cura:
separar dado de comando.

| Tipo                   | Onde acontece                          | Defesa                                   |
| ---------------------- | -------------------------------------- | ---------------------------------------- |
| SQL                    | consulta montada por concatenação      | *statements* preparados (`?`)            |
| Comando de sistema     | `exec('ping ' + host)`                 | `execFile` com array de argumentos       |
| Caminho de arquivo     | `sendFile('./uploads/' + nome)`        | resolver e conferir o diretório          |
| Prototype pollution    | *merge* profundo de `req.body`         | recusar `__proto__` e `constructor`      |
| XSS refletido          | HTML montado com dado do usuário       | escapar na renderização                  |

```ts title="Comando de sistema" del={2} ins={5}
// Interpola: `8.8.8.8; rm -rf /` vira dois comandos
exec(`ping -c 3 ${req.query.host}`);

// Argumentos separados: o valor nunca é interpretado pelo shell
execFile('ping', ['-c', '3', String(req.query.host)]);
```

<Aside type="caution" title="Prototype pollution é específico de JavaScript">
  Uma função de *merge* recursivo aplicada a `{"__proto__": {"isAdmin": true}}` altera o
  protótipo de `Object` e todo objeto do processo passa a ter `isAdmin`. Use
  `Object.create(null)`, recuse essas chaves ou valide o corpo com um schema — a validação
  com [Zod](../../api/validation/) descarta campos desconhecidos por construção.
</Aside>

## Segredos e dependências

Os dois vetores que não dependem de código escrito por você:

| Risco                          | Sinal                                  | Ação                                     |
| ------------------------------ | -------------------------------------- | ---------------------------------------- |
| `.env` versionado              | o arquivo aparece no `git log`         | rotacionar o segredo, não só apagar       |
| Segredo em log                 | `console.log(req.body)` no login       | redigir campos sensíveis                  |
| Dependência com vulnerabilidade| `npm audit` acusa                      | atualizar; avaliar se o caminho é alcançável |
| Dependência abandonada         | sem publicação há anos                 | substituir antes de virar problema        |
| Instalação em CI               | `npm install` altera o lockfile        | usar `npm ci`                             |

```bash title="Terminal"
npm audit
npm audit fix
npm ci
```

<Aside type="tip" title="Menos dependências, menos superfície">
  Cada pacote instalado é código de terceiros rodando com os privilégios do seu servidor. É
  parte do motivo pelo qual este guia mostra as versões nativas de hash, JWT, CORS e limite
  de requisições antes dos pacotes correspondentes.
</Aside>

## Exercício

Na [etapa 9 da TaskAPI](../../practice/taskapi/auth/), que ainda não tem nenhuma dessas
defesas:

1. Desabilite `x-powered-by` e confirme com `curl -I`.
2. Implemente `securityHeaders` e verifique os cabeçalhos na resposta.
3. Implemente `rateLimit` e aplique `max: 5` em `POST /auth/signin`.
4. Faça seis tentativas de login com senha errada e confirme o `429` com `Retry-After`.
5. Reduza o limite de `express.json()` para `1kb` e traduza `entity.too.large` para `413`.

<details>
  <summary>Possível resposta</summary>

  ```bash title="Terminal"
  for i in $(seq 1 6); do
    curl -s -o /dev/null -w "%{http_code}\n" \
      -X POST localhost:3000/auth/signin \
      -H 'Content-Type: application/json' \
      -d '{"email":"ana@example.com","password":"errada"}'
  done
  ```

  ```txt title="Output"
  401
  401
  401
  401
  401
  429
  ```

  O `429` na sexta tentativa mostra que o limite conta **todas** as requisições, não apenas
  as bem-sucedidas — que é justamente o comportamento necessário contra força bruta.
</details>

## Desafio

Faça o `rateLimit` usar o `userId` como chave em rotas autenticadas e o IP nas públicas.
Discuta: por que limitar por IP na rota de login é insuficiente quando o ataque vem de uma
botnet, e o que mais poderia ser usado como chave?

## Perguntas de revisão

### Limites

1. **Por que a rota de login precisa de um limite mais agressivo que as demais?**

   <details>
     <summary>Possível resposta</summary>

     Porque é a única rota em que cada tentativa tem valor para o atacante: sem limite, a
     força bruta encontra senhas fracas em minutos. Nas demais rotas, o limite protege
     disponibilidade, não credencial.
   </details>

2. **Qual o risco de um limite de corpo generoso?**

   <details>
     <summary>Possível resposta</summary>

     O processo carrega o corpo inteiro na memória antes de interpretá-lo: alguns `POST`
     grandes simultâneos derrubam o servidor sem nenhuma sofisticação.
   </details>

3. **Por que `req.ip` pode ser enganoso?**

   <details>
     <summary>Possível resposta</summary>

     Atrás de um proxy, ele é o IP do proxy — todos os usuários compartilham o mesmo
     contador. É preciso configurar `trust proxy`, e confiar em `X-Forwarded-For` só faz
     sentido quando o próprio proxy o reescreve.
   </details>

### Injeção

4. **Qual a raiz comum de todas as injeções?**

   <details>
     <summary>Possível resposta</summary>

     Dado do usuário sendo interpretado como comando. A cura é sempre a mesma: enviar dado
     e comando por canais separados — parâmetros em SQL, array de argumentos em processos,
     escape na renderização.
   </details>

5. **O que é prototype pollution e por que ela é específica de JavaScript?**

   <details>
     <summary>Possível resposta</summary>

     É alterar `Object.prototype` através de chaves como `__proto__` em um *merge*
     recursivo, fazendo todo objeto do processo herdar propriedades do atacante. Depende do
     modelo de herança por protótipo da linguagem.
   </details>
