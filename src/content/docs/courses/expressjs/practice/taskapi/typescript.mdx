### US05 — Deixar o compilador apontar a quebra · RNF04, RNF10

> **Como** pessoa que mantém a API,
> **quero** tipos no domínio e o `.ts` executado nativamente pelo Node,
> **para** que o `typecheck` aponte a quebra antes de ela chegar à produção, sem instalar um runtime a mais.

```gherkin
Cenário: CA05.1 - O compilador valida o projeto inteiro
  Quando executo npm run typecheck
  Então o comando termina sem nenhum erro

Cenário: CA05.2 - Sem build e sem tsx
  Quando executo npm run dev
  Então o Node sobe os arquivos .ts diretamente
  E não existe nenhum arquivo .js em src/

Cenário: CA05.3 - Imports por subpath
  Quando abro qualquer arquivo de src/
  Então os imports internos começam com "#"
  E o mapa "#*" está declarado no package.json, não no tsconfig.json

Cenário: CA05.4 - Id que não é inteiro
  Quando envio GET /tasks/abc
  Então recebo o status 400
  E a mensagem diz que o id precisa ser um número inteiro
  E o model não é consultado

Cenário: CA05.5 - Só JSON entra
  Quando envio POST /tasks com Content-Type: text/plain
  Então recebo o status 415
  E o controller não é executado

Cenário: CA05.6 - O tipo que entra e o tipo que sai
  Quando abro src/types/task.ts
  Então Task tem id, title e done obrigatórios
  E TaskInput tem todos os campos opcionais
```

### Tasks da etapa

As tarefas abaixo implementam US05 e são a ordem sugerida de execução. As seções seguintes
explicam a decisão por trás de cada uma, e o código completo está ao final da página.

<Steps>

1. **TK04.1 · Criar `tsconfig.json` e modificar `package.json`**: `noEmit`, extensão `.ts` nos imports, o mapa `#*` e o script `typecheck`.
2. **TK04.2 · Criar `src/types/task.ts`**: `Task` e `TaskInput`.
3. **TK04.3 · Criar `src/errors/HttpError.ts`**: a classe sai do middleware e ganha arquivo próprio.
4. **TK04.4 · Migrar as camadas para `.ts`**: `app`, `server`, router, controller, model e `error-handler`, com `parseId` no controller.
5. **TK04.5 · Criar `src/middlewares/require-json.ts`**: recusa com 415 o que não for JSON.

</Steps>

## O que muda nesta etapa?

| Antes (etapa 3) | Agora (etapa 4) |
| --------------- | --------------- |
| `.js` | `.ts` executado nativamente pelo Node |
| Imports relativos (`../models/…`) | *Subpath imports* (`#models/…`) |
| `HttpError` dentro do middleware | `src/errors/HttpError.ts` próprio |
| Sem tipos do domínio | `src/types/task.ts` com `Task` e `TaskInput` |
| Qualquer `Content-Type` aceito | `requireJson` recusa o que não for JSON |
| — | `npm run typecheck` |

Esta é a última etapa em JavaScript puro do guia: da 5 em diante, tudo é TypeScript.

`Content-Type: application/json` antes de chegarem ao controller, rejeitando-as com

## Conceitos abordados

- Execução nativa de `.ts` pelo Node (*type stripping*)
- `tsconfig.json` com `noEmit`, `allowImportingTsExtensions` e `erasableSyntaxOnly`
- *Subpath imports* (`#`) declarados no `package.json`
- Tipagem de `Request`, `Response` e `NextFunction`
- Separação entre o tipo que **entra** (`TaskInput`) e o que **sai** (`Task`)
- `HttpError` e tratamento de erro centralizado
