## O que muda nesta etapa

| Antes (etapa 3) | Agora (etapa 4) |
| --------------- | --------------- |
| `.js` | `.ts` executado nativamente pelo Node |
| Imports relativos (`../models/…`) | *Subpath imports* (`#models/…`) |
| `HttpError` dentro do middleware | `src/errors/HttpError.ts` próprio |
| Sem tipos do domínio | `src/types/task.ts` com `Task` e `TaskInput` |
| Qualquer `Content-Type` aceito | `requireJson` recusa o que não for JSON |
| — | `npm run typecheck` |

Esta é a última etapa em JavaScript puro do guia: da 5 em diante, tudo é TypeScript.

## O tipo que entra e o tipo que sai

`Task` descreve a tarefa como ela sai do model e entra na resposta: os três campos
existem sempre. `TaskInput` descreve o que o cliente **manda**, e por isso todo campo é

| ------ | ------------ | ------------------ | ------- | ------------------- |

| GET    | `/tasks/:id` | —                  | `200`   | `400`, `404`        |

## Testando

O middleware `requireJson` intercepta requisições `POST` sem o cabeçalho
`Content-Type: application/json` antes de chegarem ao controller, rejeitando-as com
`415 Unsupported Media Type`:

<details>
  <summary>Requisição .http correspondente</summary>

  ```http
  ### Testar erro de Content-Type incompativel (415)
  POST http://localhost:3000/tasks
  Content-Type: text/plain

  titulo qualquer
  ```
</details>

<ApiRequest method="POST" path="/tasks" baseUrl="http://localhost:3000" description="Content-Type: text/plain" />

<ApiResponse status={415}>
{`

    "error": {
      "status": 415,
      "message": "Content-Type precisa ser application/json"
    }
  }
`}
</ApiResponse>

Um `id` que não é inteiro nunca chega ao model: `parseId` lança o erro e o
`errorHandler` responde `400 Bad Request`:

</details>

<ApiResponse status={400}>

      "message": "O id precisa ser um numero inteiro"

`}

## Conceitos abordados

- Execução nativa de `.ts` pelo Node (*type stripping*)
- `tsconfig.json` com `noEmit`, `allowImportingTsExtensions` e `erasableSyntaxOnly`
- *Subpath imports* (`#`) declarados no `package.json`
- Tipagem de `Request`, `Response` e `NextFunction`
- Separação entre o tipo que **entra** (`TaskInput`) e o que **sai** (`Task`)
- `HttpError` e tratamento de erro centralizado
