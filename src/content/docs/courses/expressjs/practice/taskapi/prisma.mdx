### US10 — Classificar tarefas com tags · RF03, RNF03

> **Como** cliente HTTP,
> **quero** que cada tarefa venha com as suas tags,
> **para** agrupar o que faço por assunto sem uma segunda requisição.

```gherkin
Cenário: CA10.1 - As tags vêm junto
  Quando envio GET /tasks/1
  Então o corpo traz "tags" com id, name e color de cada uma
  E não preciso de uma segunda requisição

Cenário: CA10.2 - A relação está no schema
  Quando abro prisma/schema.prisma
  Então Task e Tag estão declaradas com relação muitos-para-muitos
  E a tabela de junção não está escrita à mão

Cenário: CA10.3 - O banco é reconstruível
  Quando executo npx prisma migrate deploy em um banco vazio
  Então o histórico de prisma/migrations recria todas as tabelas
  E prisma/dev.db está no .gitignore

Cenário: CA10.4 - O seed é idempotente
  Quando executo npm run db:seed duas vezes
  Então não há tarefas nem tags duplicadas

Cenário: CA10.5 - O erro do ORM não chega ao cliente
  Quando envio PUT /tasks/999
  Então recebo o status 404
  E o código P2025 do Prisma não aparece na resposta

Cenário: CA10.6 - Modelo e ambiente são arquivos diferentes
  Quando abro prisma/schema.prisma
  Então não existe string de conexão nele
  E a conexão vem de prisma.config.ts e do .env, lidos sem dotenv

Cenário: CA10.7 - A camada SQL saiu
  Quando abro src/database/
  Então database.ts e migration.ts não existem mais
  E não sobra nenhuma string SQL no model
```

## O que muda nesta etapa?

| Antes (etapa 7) | Agora (etapa 8) |
| --------------- | --------------- |
| `CREATE TABLE` escrito à mão | `prisma/schema.prisma` declarativo |
| Migração como script que roda uma vez | Migrações versionadas em `prisma/migrations/` |
| SQL em string no model | `findMany`, `create`, `update`, `deleteMany` |
| Tipos do banco escritos à mão (`TaskRow`) | Tipos gerados do schema |
| Só a tabela `tasks` | `Task` e `Tag`, com relação muitos-para-muitos |
| — | `prisma.config.ts` e `db:studio` |

## Relação não vem por acidente

`task.tags` só existe no resultado se a consulta pedir. Isso é uma decisão de desempenho
do Prisma: sem `include`, ele não faz o `JOIN`.

<SourceCode
  path="examples/courses/expressjs/projects/task-api-prisma/src/models/task-model.ts"
  title="src/models/task-model.ts"
  region="select"
/>

`Prisma.TaskGetPayload<{ include: typeof withTags }>` é o tipo exato daquele resultado —
com as tags dentro. Mudar o `include` muda o tipo, e o TypeScript acusa quem lia um campo
que não vem mais.

<Aside type="caution" title="`update` lança quando o id não existe">
  Diferente do `UPDATE` em SQL, que apenas afeta zero linhas, `prisma.update` lança
  `P2025`. O model usa `.catch(() => null)` para transformar isso no `undefined` que o
  controller já sabe traduzir em `404`. `deleteMany` não tem esse problema: devolve a
  contagem.
</Aside>

## Conceitos abordados

- Schema declarativo e migrações versionadas
- Prisma 7 com driver adapter (`@prisma/adapter-better-sqlite3`)
- `prisma.config.ts` separando modelo de ambiente
- Relação muitos-para-muitos e a tabela de junção implícita
- `include` explícito e o tipo gerado pelo `TaskGetPayload`
- `upsert` e `connect` em um seed idempotente
- `P2025` traduzido para `404`
