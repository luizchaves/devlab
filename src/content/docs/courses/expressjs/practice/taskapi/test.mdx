### US20 — Alterar sem quebrar o existente · RNF08

> **Como** pessoa que mantém a API,
> **quero** uma suíte que rode em segundos e fixe as decisões de segurança em asserções,
> **para** descobrir uma regressão antes de publicá-la.

```gherkin
Cenário: CA20.1 - A suíte inteira, sem porta
  Quando executo pnpm test
  Então 21 testes em 9 suítes passam
  E nenhuma porta é aberta
  E nenhum e-mail é enviado

Cenário: CA20.2 - O teste importa a aplicação
  Quando abro qualquer arquivo .test.ts de src/routes/
  Então ele importa app, e nunca server

Cenário: CA20.3 - O isolamento por dono está fixado
  Quando leio src/routes/task-router.test.ts
  Então existe um teste que consulta a tarefa de outro dono
  E ele afirma o status 404, e não 403

Cenário: CA20.4 - As regras de autenticação estão fixadas
  Quando leio src/routes/auth-router.test.ts
  Então existe um teste afirmando que a senha não sai na resposta
  E outro afirmando que senha errada e e-mail inexistente respondem o mesmo 401

Cenário: CA20.5 - Duas execuções seguidas passam
  Quando executo pnpm test duas vezes
  Então as duas passam
  E os usuários criados no before são apagados no after

Cenário: CA20.6 - Sem framework de teste
  Quando abro o package.json
  Então o script test roda node --test
  E supertest, com os seus tipos, é a única dependência nova, em devDependencies
```

### US21 — Subir a API em qualquer máquina · RNF09

> **Como** pessoa responsável pelo deploy,
> **quero** subir a API inteira com um comando,
> **para** não depender do que está instalado na máquina de destino.

```gherkin
Cenário: CA21.1 - Um comando
  Dado uma máquina com Docker e sem Node
  Quando executo JWT_SECRET=... docker compose up --build
  Então a API responde em http://localhost:3000

Cenário: CA21.2 - Migrations na subida
  Dado um volume vazio
  Quando o contêiner sobe
  Então as migrations pendentes são aplicadas antes de o servidor atender

Cenário: CA21.3 - Sem root
  Quando inspeciono o processo dentro do contêiner
  Então ele roda como o usuário app

Cenário: CA21.4 - O que não entra na imagem
  Quando inspeciono a imagem
  Então .env, node_modules, uploads e *.db não estão nela

Cenário: CA21.5 - Contêiner descartável, dados não
  Dado usuários e avatares criados
  Quando executo docker compose down e depois up
  Então o banco e os uploads continuam lá

Cenário: CA21.6 - Sem segredo, não sobe
  Quando executo docker compose up sem JWT_SECRET no ambiente
  Então o Compose recusa subir

Cenário: CA21.7 - O ciclo se fecha no /health
  Quando leio o Dockerfile
  Então o HEALTHCHECK consulta a rota /health que nasceu na etapa 1
```

## A imagem separa build de runtime

O estágio de build tem `pnpm`, o compilador e o `node_modules` completo. A imagem final
recebe só o que é preciso para rodar:

<SourceCode
  path="examples/courses/expressjs/projects/task-api-test/Dockerfile"
  title="Dockerfile"
  region="build"
/>

Copiar os manifestos **antes** do código é o que aproveita o cache: enquanto as dependências
não mudarem, a camada de instalação não é refeita. O `prisma/` vem junto porque o
`postinstall` do projeto roda `prisma generate`, que precisa do schema — e o schema muda
muito menos que `src/`, então o cache continua valendo.

<SourceCode
  path="examples/courses/expressjs/projects/task-api-test/Dockerfile"
  title="Dockerfile"
  region="runtime"
/>

<Aside type="danger" title="Não rode como root">
  O padrão da imagem `node` é o usuário `root`. Se a aplicação for comprometida, o atacante
  herda esse usuário dentro do contêiner. Um `useradd` e um `USER app` custam duas linhas.
</Aside>

<Aside type="caution" title="Usuário sem privilégio não cria diretório sozinho">
  `uploads/` e `data/` estão no `.dockerignore`, então não vêm no contexto — e o `app` não
  pode criá-los em `/app`. Sem o `mkdir` com `chown` **antes** do `USER`, o processo morre
  no arranque com `EACCES`. Vale também para o volume: montado sobre um caminho que pertence
  ao root, ele continua pertencendo ao root.
</Aside>

O `HEALTHCHECK` fecha o ciclo aberto na etapa 1: o `/health` que nasceu como a primeira rota
do guia é o que o contêiner usa para dizer se está saudável.

## O que não entra na imagem?

```txt title=".dockerignore"
node_modules
.env
*.db
*.db-journal
uploads
prisma/dev.db
.git
```

O `.env` na lista não é detalhe: sem ele, o segredo de desenvolvimento viaja dentro da
imagem e aparece em qualquer `docker history`.

## Volumes, porque contêiner é descartável

<SourceCode
  path="examples/courses/expressjs/projects/task-api-test/compose.yaml"
  title="compose.yaml"
  lang="yaml"
/>

O banco e os uploads moram em volumes: derrubar o contêiner não pode apagar os dados. O
`command` aplica as migrations antes de subir o servidor, para que um contêiner novo sobre
um volume vazio se vire sozinho — e chama o binário do `node_modules`, porque `pnpm` não
existe no estágio de runtime.

O `JWT_SECRET` usa a sintaxe `${VAR:?}`, que recusa subir sem a variável.

<Aside type="danger" title="O compose lê o `.env` do diretório sozinho">
  E é por isso que o `${VAR:?}` pode não barrar nada: se houver um `.env` ao lado do
  `compose.yaml` (e há, porque o desenvolvimento precisa dele), o compose o carrega e o
  **segredo de desenvolvimento entra em produção em silêncio**. Em produção, use
  `--env-file` apontando para outro arquivo, ou garanta que o `.env` não acompanhe o
  deploy.
</Aside>

  próximo passo natural deste projeto.
</Aside>

## Conceitos abordados

- Runner nativo (`node --test`) sem framework de teste
- `supertest` contra o `app`, sem abrir porta
- Teste de unidade para função pura, de rota para contrato
- Fixar decisões de segurança em asserção
- `before`/`after` para deixar o estado como estava
- Imagem multi-estágio e cache de camadas
- Usuário sem privilégio, `HEALTHCHECK` e `.dockerignore`
- Volumes e segredo vindo do ambiente
