Nível **Iniciante → Avançado** · Node.js · Express.js · TypeScript · Zod · Prisma

A **TaskAPI** é o projeto modelo do guia. Quando um tópico mostra um bloco de código, ele
sai daqui — de um arquivo que existe, roda e é validado pelo CI. Não é uma aplicação
para usar: é a **referência executável** das páginas de conceito.

## Análise de requisitos

### Público-alvo

A **TaskAPI** atende a dois perfis, e os dois aparecem nas histórias do backlog:

- **Estudantes do Guia de Express.js**: pessoas que chegam a um tópico de conceito, veem um
  recorte de código e precisam de um lugar onde aquele recorte exista inteiro, rode e possa ser
  alterado. Para elas, a TaskAPI é o projeto de referência.
- **Clientes HTTP da API**: quem consome a API pelo `requests.http`, por um front-end ou por outro
  serviço. Para eles, a TaskAPI é um serviço de tarefas com conta, token e isolamento por dono.

Não existe um terceiro perfil, o usuário diante de uma tela: a TaskAPI não tem front-end, e é
isso que a distingue do [InvestApp](../investapp/) e do [MonitorApp](../monitorapp/).

## Objetivo do sistema

A **TaskAPI** oferece uma API HTTP para gerir tarefas pessoais: criar, listar com filtros e
paginação, consultar, atualizar, remover e classificar por tags. Cada tarefa pertence a um
usuário autenticado, que confirma o e-mail, guarda um avatar, recebe as mudanças em tempo real
e pode medir a latência até um host a partir do servidor. Tudo isso com o mínimo de dependências
que o Node.js já não resolva, para que cada recorte exibido nos tópicos seja o menor código
possível que ainda funciona.

### Requisitos Funcionais (RF)

| Código | Requisito | Descrição |
| ------ | --------- | --------- |
| **RF01** | Gestão de Tarefas (CRUD) | O sistema deve permitir criar, listar, consultar por id, atualizar e remover tarefas com título, descrição, prioridade, prazo e estado de conclusão. |
| **RF02** | Listagem com Filtros e Paginação | A listagem deve aceitar filtros por estado, prioridade e texto, ordenação por campo e paginação com envelope `data` + `meta`. |
| **RF03** | Classificação por Tags | Cada tarefa deve poder ser associada a várias tags, e cada tag a várias tarefas, com as tags carregadas junto da tarefa. |
| **RF04** | Cadastro de Usuários | O sistema deve permitir o auto-cadastro informando nome, e-mail único e senha. |
| **RF05** | Autenticação & Sessão | O sistema deve autenticar por e-mail e senha, emitir um token JWT e expor o perfil de quem chama. |
| **RF06** | Isolamento por Dono e Papéis | Cada usuário deve acessar e manipular estritamente as próprias tarefas, e rotas administrativas devem exigir papel específico. |
| **RF07** | Verificação de E-mail | O cadastro deve disparar um e-mail com link de confirmação, e o link deve marcar o endereço como verificado. |
| **RF08** | Avatar do Usuário | O usuário autenticado deve poder enviar uma imagem de perfil (PNG, JPEG ou WebP) por `multipart/form-data`. |
| **RF09** | Eventos em Tempo Real | O usuário autenticado deve poder manter uma conexão SSE que recebe as mudanças das próprias tarefas. |
| **RF10** | Ping sob Demanda | O usuário autenticado deve poder pedir ao servidor que meça a latência até um host informado. |

### Requisitos Não-Funcionais (RNF)

| Código | Requisito | Descrição |
| ------ | --------- | --------- |
| **RNF01** | Validação Estrita de Dados | Toda entrada HTTP (`body`, `query`, `params`) deve ser validada com schemas Zod antes do handler, recusando campos não declarados e respondendo `422` com uma issue por campo. |
| **RNF02** | Criptografia & Segurança | Senhas devem ser gravadas como hash Argon2id com sal por registro, e o token deve ser assinado com HS256, ambos via `node:crypto`. |
| **RNF03** | Persistência Relacional | Os dados devem ser armazenados em SQLite, primeiro com `node:sqlite` e SQL parametrizado, depois com Prisma 7 e migrações versionadas. |
| **RNF04** | Arquitetura em Camadas & Tipagem | O código deve ser TypeScript executado nativamente pelo Node, organizado em rotas, controllers, models e middlewares, com erros tratados em um único ponto. |
| **RNF05** | Documentação da API | O contrato deve ser publicado em OpenAPI 3, gerado dos mesmos schemas que validam, e navegável no Swagger UI. |
| **RNF06** | Operação & Observabilidade | O ambiente deve ser validado no arranque; cada requisição deve gerar uma linha de log JSON com id; a API deve expor `/health`, `/ready` e `/metrics` e encerrar de forma graciosa. |
| **RNF07** | Proteção de Borda | A API deve aplicar CORS por lista de permitidos, cabeçalhos de segurança e limite de requisições por balde, sem `helmet` nem `cors`. |
| **RNF08** | Testabilidade | A aplicação deve ser importável sem abrir porta e coberta por testes de unidade e de rota com o runner nativo do Node e `supertest`. |
| **RNF09** | Portabilidade & Conteinerização | A API deve ser empacotável em imagem Docker multi-estágio, com usuário sem privilégio, e executável via Docker Compose com volumes. |
| **RNF10** | Dependências Mínimas | Nenhum pacote deve ser instalado para o que o Node já resolve: sem `bcrypt`, `jsonwebtoken`, `dotenv`, `tsx`, `helmet` ou `cors`. |

## Por que ela existe?

Um guia de referência tem um problema que um projeto passo a passo não tem: cada página
é lida sozinha. A tentação é escrever, em cada tópico, um exemplo isolado — e o resultado
é um guia onde a mesma API aparece com seis domínios diferentes, e onde o código exibido
não roda em lugar nenhum.

A TaskAPI resolve isso sem transformar o guia num tutorial: os tópicos continuam
independentes e continuam mostrando recortes de 5 a 15 linhas, mas todos os recortes vêm
da **mesma** aplicação, crescendo na mesma ordem em que o guia apresenta os assuntos.

<Aside type="note" title="Ela não é o InvestApp nem o MonitorApp">
  A TaskAPI é **só API** — sem front-end, sem Docker, sem testes E2E. O
  [InvestApp](../investapp/) e o [MonitorApp](../monitorapp/) são as aplicações
  completas, com interface, banco e infraestrutura, construídas passo a passo. A TaskAPI
  é o que as tópicos de conceito recortam; eles são o que você constrói.
</Aside>

## O domínio

Uma tarefa tem título e estado. Nada além disso, na etapa 1 — o resto do modelo aparece
quando o tópico que o justifica chega.

<Mermaid title="Crescimento do modelo de dados da TaskAPI">
{`
erDiagram
  TASK {
    int id
    string title
    boolean done
    string description "etapa 5"
    datetime dueDate "etapa 5"
    string priority "etapa 5"
  }
  TAG {
    int id
    string name
  }
  USER {
    string id
    string name
    string email
    string password
    string role
  }
  USER ||--o{ TASK : "possui (etapa 9)"
  TASK }o--o{ TAG : "recebe (etapa 8)"

O `User` só aparece na etapa 9, junto com a autenticação — a mesma ordem do InvestApp e
do MonitorApp, e a mesma ordem das seções do guia, onde `Autenticação` vem depois de
`Persistência`.

## Convenções

O que vale em toda a trilha, e que você pode assumir sem reler:

| Decisão | Escolha |
| ------- | ------- |
| Framework | Express 5, sem `express-async-errors` — o Express 5 já encaminha rejeições |
| Linguagem | JavaScript nas etapas 1 a 3, TypeScript da 4 em diante |
| Execução do TypeScript | Nativa pelo Node, sem `tsx` e sem passo de build |
| Imports internos | *Subpath imports* (`#models/…`) declarados no `package.json` |
| Variáveis de ambiente | `--env-file` nativo, sem `dotenv` |
| Autenticação | `node:crypto` para hash e para assinar o JWT, sem `bcrypt` e sem `jsonwebtoken` |
| Validação | Zod, em `body`, `query` e `params` |
| Banco | `node:sqlite` na etapa 7, Prisma 7 com driver adapter da etapa 8 em diante |

## Setup Inicial e Governança com IA

Para iniciar o desenvolvimento de forma padronizada, profissional e otimizada para assistência por IA, a estrutura base do projeto é estabelecida com quatro pilares essenciais:

1. **Documento de Requisitos do Produto (`docs/PRD.md`)**: formaliza os objetivos, escopo, regras de negócio e critérios de aceitação do sistema a partir do [Backlog do Produto](backlog/).
2. **Instruções para Agentes de IA (`AGENTS.md`)**: define as regras de stack, convenções de código, restrições arquiteturais e formato de commit (Conventional Commits em inglês com tags de tasks) que assistentes e agentes devem seguir sem exceção.
3. **Guia do Projeto (`README.md`)**: orienta como rodar a aplicação, executar testes e contribuir.
4. **Ferramentas de Qualidade, Scripts e Pre-commit Hooks**: configuração do Biome (`biome.json`) para linting e formatação, além de scripts padronizados no `package.json` (`dev`, `start`, `lint`, `format`, `check`) acionados antes de cada commit via hooks Git.

<Aside type="tip" title="Desenvolvimento orientado a specs por task">
  Antes de iniciar a implementação de qualquer tarefa (`TKXX.Y`), utilize um prompt para gerar a **spec técnica da task** sob `specs/active/spec-TKXX.Y-<nome>.md`. O diretório `specs/` organiza as tarefas em duas subpastas: `active/` (tarefas ativas em andamento) e `archived/` (tarefas concluídas e arquivadas). A spec detalha os objetivos, arquivos afetados, fases de desenvolvimento, cenários de teste Gherkin e métricas de sucesso, garantindo que o agente execute exatamente o escopo planejado. Os prompts para gerar o `PRD.md`, `AGENTS.md`, `README.md` e as specs estão disponíveis em [1. Primeiro servidor](hello/).
</Aside>
