### US09 — Não perder tarefas ao reiniciar · RNF03

> **Como** cliente HTTP,
> **quero** que as tarefas continuem cadastradas depois que o servidor reinicia,
> **para** não recadastrar tudo a cada deploy.

```gherkin
Cenário: CA09.1 - O banco nasce por script
  Quando executo npm run db:migrate
  Então a tabela tasks é criada
  E quando executo npm run db:seed
  Então as tarefas iniciais são inseridas
  E npm run db:reset refaz os dois do zero

Cenário: CA09.2 - Persistência no reinício
  Dado uma tarefa criada pela API
  Quando derrubo e subo o servidor
  Então a tarefa continua na lista

Cenário: CA09.3 - Nenhum valor entra no texto do SQL
  Quando abro src/models/task-model.ts
  Então todo valor de filtro entra por "?" em um array de parâmetros
  E não existe interpolação de valor na string do SQL

Cenário: CA09.4 - Coluna de ordenação vem de uma lista
  Quando o sort chega com um nome de coluna
  Então ele é conferido em uma lista de permitidos antes de entrar no ORDER BY

Cenário: CA09.5 - Título único em duas camadas
  Dado uma tarefa chamada "Guardar em SQLite"
  Quando envio POST /tasks com o mesmo título
  Então recebo o status 409
  E a tabela tem UNIQUE em title para o caso de duas requisições chegarem juntas

Cenário: CA09.6 - O contrato não vaza o banco
  Quando repito as requisições da etapa 6
  Então nenhuma rota nem formato de resposta mudou
  E "done" volta como booleano, mesmo gravado como 0 ou 1
```

## O que muda nesta etapa?

| Antes (etapa 6) | Agora (etapa 7) |
| --------------- | --------------- |
| Array em memória | Arquivo `db.sqlite` |
| Model síncrono | Model `async`, e os controllers com `await` |
| Filtro, ordenação e página em JavaScript | `WHERE`, `ORDER BY`, `LIMIT`/`OFFSET` |
| Regras só no schema Zod | Restrições também no `CREATE TABLE` |
| — | `db:migrate`, `db:seed` e `db:reset` |

Nenhuma rota muda, e nenhuma resposta muda de formato. É de propósito: a troca da camada
de dados não deveria vazar para o contrato da API.

## Um invólucro assíncrono

`DatabaseSync` do `node:sqlite` é **síncrono**, e o resto da aplicação é `async`.
Uniformizar isso em três métodos — `run` para escrita, `get` para uma linha, `all` para
várias — mantém o model igual ao que ele seria com qualquer outro banco:

## As restrições moram no banco

O schema Zod protege o que passa pela API. O `CREATE TABLE` protege o que entra por
qualquer caminho (seed, script, consulta manual) e é a única camada que resolve duas
requisições simultâneas tentando gravar o mesmo título:

<Aside type="note" title="O SQLite não tem booleano">
  `done` é gravado como `0` ou `1`, com um `CHECK` garantindo que não vire outra coisa. A
  conversão para `true`/`false` acontece no model, de modo que nem o controller nem a
  resposta HTTP vejam o formato do banco.
</Aside>

## Conceitos abordados

- `node:sqlite` e `DatabaseSync`, sem dependência externa
- Invólucro assíncrono sobre uma API síncrona
- Migração e seed como scripts do projeto
- Consultas parametrizadas e a defesa contra injeção
- Lista de permitidos para `ORDER BY`
- `COUNT` com os mesmos filtros da listagem
- Restrições `NOT NULL`, `UNIQUE`, `CHECK` e `DEFAULT`
