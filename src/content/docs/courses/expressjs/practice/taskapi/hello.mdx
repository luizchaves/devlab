### US01 — Criar e consultar tarefas por HTTP · RF01, RNF01

> **Como** cliente HTTP ou pessoa desenvolvedora,
> **quero** um servidor estruturado com governança de IA, scripts de qualidade e rotas básicas,
> **para** ter o ciclo requisição/resposta completo sobre uma base padronizada e confiável.

```gherkin
Cenário: CA01.1 - A rota que não depende do domínio
  Quando envio GET /health
  Então recebo o status 200
  E o corpo traz "status" igual a "ok" e o "uptime" do processo
  E nenhum dado da aplicação é consultado

Cenário: CA01.2 - Listar as tarefas
  Quando envio GET /tasks
  Então recebo o status 200
  E o corpo é a lista das tarefas iniciais

Cenário: CA01.3 - Consultar uma tarefa pelo id
  Quando envio GET /tasks/1
  Então recebo o status 200 com a tarefa
  Mas quando envio GET /tasks/99
  Então recebo o status 404 com uma mensagem

Cenário: CA01.4 - Criar uma tarefa
  Quando envio POST /tasks com o campo "title"
  Então recebo o status 201
  E o corpo traz a tarefa com um id gerado pelo servidor e "done" falso

Cenário: CA01.5 - Recusar corpo sem título
  Quando envio POST /tasks sem o campo "title"
  Então recebo o status 400
  E a mensagem diz qual campo falta
  E nada é acrescentado ao array

Cenário: CA01.6 - O menor projeto que funciona
  Quando abro o projeto
  Então o Express é a única dependência de produção do package.json
  E o código da API reside em um único arquivo em src/server.js

Cenário: CA01.7 - Governança, qualidade e automação de scripts
  Quando inspeciono a raiz do projeto
  Então existem os arquivos docs/PRD.md, AGENTS.md, README.md e biome.json
  E o diretório specs/ possui as subpastas active/ e archived/
  E o diretório .agents/skills/ possui a skill task-spec-generator
  E o package.json declara scripts para dev, start, lint, format e lint:fix
```

### TK01.1 · Criar package.json e Estrutura Inicial (Configuração, Scripts, Governança e Skill de Specs)

O `package.json` define o projeto como módulo ES nativo (`"type": "module"`), declara o Express como dependência de produção e padroniza os scripts de automação, ciclo de vida e qualidade de código:
- `dev`: executa o servidor em desenvolvimento com `--watch` nativo do Node.js 22 (`node --watch src/server.js`), reiniciando o processo automaticamente a cada alteração de arquivo sem dependências extras.
- `start`: inicia o servidor em modo de produção (`node src/server.js`).
- `lint`: executa a análise estática de código com o Biome (`biome check .`), identificando inconformidades, variáveis não utilizadas e violações de boas práticas.
- `format`: aplica formatação automática com o Biome em todo o projeto (`biome format --write .`).
- `lint:fix`: aplica formatação e correções automáticas de lint em uma única passagem (`biome check --write .`).

Junto ao `package.json`, o setup inicial estabelece os documentos de governança, ferramentas de qualidade e suporte a IA do projeto:
- `docs/PRD.md`: o Documento de Requisitos do Produto formalizado a partir do [Backlog](../backlog/).
- `AGENTS.md`: as diretrizes de arquitetura, padrões de código e Conventional Commits para assistentes de IA.
- `README.md`: o guia de execução, rotas e instruções para novos desenvolvedores.
- `biome.json` e hooks Git: configuração de linter, formatação e verificação estrita antes de cada commit.
- `.agents/skills/task-spec-generator/SKILL.md`: skill de IA que lê o `docs/PRD.md` pelo código da task (ex: `TK01.1`) e gera automaticamente a especificação técnica em `specs/active/`.

<Aside type="tip" title="Dica de IA: Gerar o AGENTS.md com governança e convenções para IA">
  O arquivo `AGENTS.md` define as regras invioláveis de arquitetura, padrões de código e convenções de commit para assistentes e agentes autônomos de IA. Utilize o prompt abaixo para gerá-lo:

  ```markdown
  Atue como Arquiteto de Software e Engenheiro de IA Sênior.
  Gere o arquivo `AGENTS.md` para a TaskAPI, definindo as diretrizes completas de governança para agentes de código:

  1. **Papel e Escopo**: API RESTful de referência em Express 5 e TypeScript nativo em 12 etapas cumulativas, sem front-end.
  2. **Regras Invioláveis de Código**:
     - Zero dependências externas no core: `node:crypto` para Argon2id/JWT, `--env-file` nativo (sem `dotenv`, `bcrypt`, `jsonwebtoken` ou `express-async-errors`).
     - Separação estrita de camadas MVC (Routes -> Controllers -> Models -> Prisma/Database).
     - Validação de fronteira obrigatória com Zod em 5 fontes (`req.valid`).
     - Tratamento centralizado de erros via `HttpError` e middleware `errorHandler`.
     - Isolamento estrito de dados por `userId` com status 404 em caso de acessos cruzados.
     - Idioma: código, tipos, specs e commits em inglês; documentação e comentários em PT-BR.
  3. **Comandos e Scripts**: tabela de comandos com `pnpm` (`dev`, `start`, `lint`, `format`, `lint:fix`, `typecheck`, `test`, `db:migrate`, `db:seed`, `db:reset`).
  4. **Mapa da Arquitetura e Diretórios**: árvore completa e explicada do projeto (`src/`, `docs/`, `specs/`, `.agents/skills/`).
  5. **Fluxo Spec-Driven Development**: ciclo de 5 passos (consulta no PRD -> geração de spec via skill em `specs/active/` -> codificação -> validação -> arquivamento em `specs/archived/`).
  6. **Padrão de Commits**: Conventional Commits em inglês com tags de tasks (`feat: [TKXX.Y] ...`).
  ```
</Aside>

<Aside type="tip" title="Dica de IA: Gerar a Spec técnica de uma task a partir do PRD via Skill">
  Para garantir máxima fidelidade aos requisitos antes de escrever código, utilize a skill `.agents/skills/task-spec-generator/SKILL.md` para consultar o `docs/PRD.md` pelo código da task, criar a branch Git dedicada e estruturar a especificação técnica em `specs/active/spec-TKXX.Y-<nome>.md`. Utilize o prompt abaixo:

  ```markdown
  Atue como Desenvolvedor Sênior especializado em Express e TypeScript e siga as diretrizes da skill `.agents/skills/task-spec-generator/SKILL.md`.
  Consulte o arquivo `docs/PRD.md` do projeto e localize a tarefa `[INFORMAR CÓDIGO DA TASK, ex: TK01.1]`.
  
  1. Crie e alterne para uma nova branch Git isolada para a tarefa (`git checkout -b feat/tkXX-Y-<nome>`).
  2. Com base na História de Usuário (US), nos Requisitos (RF/RNF) e nos Critérios de Aceitação (Gherkin) associados a esta task no PRD, elabore a especificação técnica de implementação em `specs/active/spec-TKXX.Y-<nome>.md`, contendo:
     - **Cabeçalho**: Task ID, Branch (`feat/tkXX-Y-...`), US relacionada, status e data.
     - **Objetivo e Contexto**: escopo da task e requisitos atendidos (RF/RNF).
     - **Arquivos Afetados**: tabela com arquivos criados/modificados e suas responsabilidades.
     - **Plano de Implementação por Fases**: passo a passo lógico e incremental de codificação.
     - **Critérios de Aceitação (Gherkin)**: cenários de teste específicos para validação da entrega.
     - **Métricas e Comandos de Validação**: comandos (`pnpm check`, `pnpm build`, `pnpm test`, chamadas via `requests.http`) para comprovar o funcionamento sem erros de compilação ou checagem.
  ```

  Ao concluir a implementação e a aprovação nos testes da task, utilize a skill `.agents/skills/task-pr-finalizer/SKILL.md` para arquivar a spec, commitar e abrir o Pull Request para a `main`.
</Aside>

<Aside type="tip" title="Dica de IA: Finalizar a task e abrir o Pull Request via Skill">
  Após concluir a codificação e os testes da task, utilize a skill `.agents/skills/task-pr-finalizer/SKILL.md` para arquivar a especificação técnica em `specs/archived/`, realizar o commit atômico e gerar o Pull Request rico via GitHub CLI:

  ```markdown
  Atue como Desenvolvedor Sênior e siga rigorosamente as diretrizes da skill `.agents/skills/task-pr-finalizer/SKILL.md`.
  Finalize a tarefa `[INFORMAR CÓDIGO DA TASK, ex: TK01.1]`:

  1. Execute a suíte de qualidade e build (`pnpm check`, `pnpm build`, `pnpm format`, `pnpm test`) garantindo 0 erros de build ou checagem.
  2. Atualize o status da spec em `specs/active/` para "Concluída" com a data de homologação e mova para `specs/archived/`.
  3. Realize o commit atômico no padrão Conventional Commits com a tag da task (`feat: [TK01.1] ...`).
  4. Envie a branch para o repositório remoto (`git push -u origin <branch-name>`).
  5. Crie o Pull Request rico e detalhado para a branch `main` via `gh pr create`, preenchendo todos os critérios de aceitação BDD homologados, tabela de arquivos modificados e evidências de testes e build.
