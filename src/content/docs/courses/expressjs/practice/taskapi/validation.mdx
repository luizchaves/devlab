## O schema é o contrato

`strictObject` é o que separa "validação" de "validação estrita": um `PUT` com
`{ "hacker": 1 }` é recusado com `422` em vez de ser silenciosamente descartado.

A `query` chega sempre como string — `?page=2` é `'2'`, não `2`. `z.coerce` converte antes
de validar, e o `default` garante que o controller receba números mesmo quando o cliente
não manda nada:

## Rotas

| Método | Caminho      | Sucesso | Erros                |
| ------ | ------------ | ------- | -------------------- |
| GET    | `/health`    | `200`   | —                    |
| GET    | `/tasks`     | `200`   | `422`                |
| GET    | `/tasks/:id` | `200`   | `404`, `422`         |
| POST   | `/tasks`     | `201`   | `409`, `415`, `422`  |
| PUT    | `/tasks/:id` | `200`   | `404`, `415`, `422`  |
| DELETE | `/tasks/:id` | `204`   | `404`, `422`         |

Os parâmetros aceitos por `GET /tasks`:

| Parâmetro  | Valores                                                           | Padrão        |
| ---------- | ----------------------------------------------------------------- | ------------- |
| `page`     | inteiro positivo                                                   | `1`           |
| `perPage`  | inteiro de 1 a 100                                                 | `10`          |
| `done`     | `true` ou `false`                                                  | sem filtro    |
| `priority` | `low`, `medium` ou `high`                                          | sem filtro    |
| `q`        | texto buscado no título                                            | sem filtro    |
| `sort`     | `title`, `dueDate`, `createdAt` — com `-` na frente para descendente | `-createdAt`  |

## Testando

A listagem devolve um envelope com os dados e os metadados da página. Sem nenhum
parâmetro, valem os `default` do schema:

<ApiRequest method="GET" path="/tasks?perPage=1" baseUrl="http://localhost:3000" />

<ApiResponse status={200}>
{`
  {
    "data": [
      {
        "id": 2,
        "title": "Escrever a primeira API",
        "description": null,
        "done": false,
        "priority": "medium",
        "dueDate": null,
        "createdAt": "2026-03-02T09:00:00.000Z"
      }
    ],
    "meta": { "page": 1, "perPage": 1, "total": 2, "totalPages": 2 }
  }
`}
</ApiResponse>

Um corpo com dois problemas devolve os dois de uma vez, cada um com o caminho do campo —
o cliente consegue marcar os dois inputs no formulário:

<details>

  ```http
  ### Criar com titulo curto e prioridade invalida
  POST http://localhost:3000/tasks
  Content-Type: application/json

  {
    "title": "ab",
    "priority": "urgentissima"
  }
  ```
</details>

<ApiRequest method="POST" path="/tasks" baseUrl="http://localhost:3000">
{`
  {
    "title": "ab",
    "priority": "urgentissima"
  }
`}
</ApiRequest>

<ApiResponse status={422}>
{`
  {
    "error": {
      "status": 422,
      "message": "Dados invalidos",
      "issues": [
        {
          "code": "too_small",
          "path": ["body", "title"],
          "message": "O titulo deve ter no minimo 3 caracteres"
        },
        {
          "code": "invalid_value",
          "path": ["body", "priority"],
          "message": "Invalid option: expected one of \\"low\\"|\\"medium\\"|\\"high\\""
        }
      ]
    }
  }
`}
</ApiResponse>

E um `perPage` acima do teto é recusado antes de o model ser chamado — é assim que a
validação vira também proteção contra abuso:

<ApiResponse status={422} description="perPage tem máximo de 100 no schema" />

## Conceitos abordados

- Schemas Zod para `body`, `params` e `query` na mesma validação
- `strictObject` e a recusa de campos não declarados
- `z.coerce` e valores padrão em parâmetros de query
- Middleware de fábrica e *declaration merging* para `req.valid`
- Erro `422` com `issues` por campo
- Filtro, ordenação e paginação com envelope `data` + `meta`
