## Requisitos, histórias e critérios

**Épico EP01 · Tarefas por HTTP** › **Feature FT02 · CRUD completo em camadas**

São duas histórias na mesma etapa: uma para quem consome a API, que ganha `PUT` e `DELETE`, e
outra para quem a mantém, que ganha camadas com responsabilidade única.

### US03 — Manter as tarefas de ponta a ponta · RF01

> **Como** cliente HTTP,
> **quero** também atualizar e remover tarefas,
> **para** manter a lista inteira pela API, sem reiniciar o servidor para limpá-la.

```gherkin
Cenário: CA03.1 - Atualizar uma tarefa
  Dado uma tarefa existente
  Quando envio PUT /tasks/{id} com corpo válido
  Então recebo o status 200
  E o corpo traz a tarefa atualizada

Cenário: CA03.2 - Remover uma tarefa
  Dado uma tarefa existente
  Quando envio DELETE /tasks/{id}
  Então recebo o status 204
  E a resposta não tem corpo

Cenário: CA03.3 - Tarefa inexistente
  Quando envio PUT ou DELETE em /tasks/{id} com um id que não existe
  Então recebo o status 404

Cenário: CA03.4 - Rota inexistente
  Quando envio GET /nada
  Então recebo o status 404
  E o corpo tem o mesmo formato de qualquer outro erro da API

Cenário: CA03.5 - Um envelope para todo erro
  Quando qualquer rota responde um erro
  Então o corpo traz "error" com "status" e "message"
```

### US04 — Cada responsabilidade no seu lugar · RNF04

> **Como** pessoa que mantém a API,
> **quero** o router, o controller, o model e o tratamento de erro em arquivos separados,
> **para** trocar o armazenamento na etapa 7 mexendo em um arquivo só.

```gherkin
Cenário: CA04.1 - O router só conhece caminhos
  Quando abro src/routes/task-router.js
  Então cada linha liga um método e um caminho a uma função do controller
  E nenhum corpo de handler aparece ali

Cenário: CA04.2 - O model não sabe que existe HTTP
  Quando abro src/models/task-model.js
  Então nenhuma função recebe req
  E nenhuma função devolve status

Cenário: CA04.3 - O controller lança, não responde erro
  Quando uma tarefa não é encontrada
  Então o controller lança um HttpError
  E não chama res.status para responder

Cenário: CA04.4 - O erro tem um lugar só
  Quando abro src/app.js
  Então notFound está registrado depois das rotas
  E errorHandler tem quatro parâmetros e é o último da cadeia

Cenário: CA04.5 - Erro interno não vaza detalhe
  Quando um erro com status 500 ou maior acontece
  Então a resposta traz uma mensagem genérica
  E o erro real vai para o log do servidor

Cenário: CA04.6 - O logger delega
  Quando qualquer requisição chega
  Então o terminal imprime o método e o caminho
  E o middleware chama next()
```

### Tasks da etapa

As tarefas abaixo implementam US03 e US04 e são a ordem sugerida de execução. As seções
seguintes explicam a decisão por trás de cada uma, e o código completo está ao final da página.

<Steps>

1. **TK03.1 · Criar `src/models/task-model.js`**: o array e as funções de leitura e escrita sobre ele, sem `req` nem `res`.
2. **TK03.2 · Criar `src/controllers/task-controller.js`**: a tradução de HTTP em chamadas ao model, lançando `HttpError` quando algo falta.
3. **TK03.3 · Criar `src/middlewares/error-handler.js`**: `HttpError`, `notFound` e `errorHandler`.
4. **TK03.4 · Criar `src/middlewares/logger.js`**: o middleware de aplicação que registra e delega.
5. **TK03.5 · Modificar `src/routes/task-router.js`**: `PUT` e `DELETE` acrescentados, e cada linha ligando só método, caminho e função do controller.
6. **TK03.6 · Modificar `src/app.js`**: a cadeia na ordem `logger` → `express.json()` → rotas → `notFound` → `errorHandler`.

</Steps>

## O que muda nesta etapa?

| Antes (etapa 2) | Agora (etapa 3) |
| --------------- | --------------- |
| Handlers escritos dentro do router | `src/controllers/task-controller.js` |
| Array declarado no router | `src/models/task-model.js` |
| Só `GET` e `POST` | CRUD completo, com `PUT` e `DELETE` |
| Erro respondido em cada handler | `HttpError` + `errorHandler` centralizados |
| Sem log | `src/middlewares/logger.js` |

## Quem conhece quem?

A dependência só aponta para dentro: o router conhece o controller, o controller
conhece o model, e o model não conhece ninguém. É isso que permite trocar o array por
um banco na etapa 7 mexendo em um arquivo só.

<Mermaid title="Camadas da TaskAPI na etapa 3">
{`
flowchart TD
  A["Requisição HTTP"] --> B["task-router.js<br/>caminho e método"]
  B --> C["task-controller.js<br/>lê req, escolhe status"]
  C --> D["task-model.js<br/>guarda e busca dados"]
  C -.->|"throw HttpError"| E["error-handler.js<br/>traduz erro em JSON"]
  D --> C
  C --> F["Resposta HTTP"]
  E --> F
`}
</Mermaid>

de 500 mostram a mensagem real; de 500 para cima, a mensagem é genérica e o erro vai

## Rotas

| Método | Caminho      | Sucesso | Erros   |
| ------ | ------------ | ------- | ------- |
| GET    | `/health`    | `200`   | —       |
| GET    | `/tasks`     | `200`   | —       |
| GET    | `/tasks/:id` | `200`   | `404`   |
| POST   | `/tasks`     | `201`   | `400`   |
| PUT    | `/tasks/:id` | `200`   | `404`   |
| DELETE | `/tasks/:id` | `204`   | `404`   |

## Conceitos abordados

- Separação em models, controllers, routes e middlewares
- Middleware de aplicação e a obrigação de chamar `next()`
- Erros com status HTTP (`HttpError`) e handler centralizado
- Middleware de erro com quatro parâmetros, registrado por último
- CRUD completo sobre um model em memória
