Etapa **12 de 13** · Nível **Avançado** · `node:test` · `supertest` · Vitest · Playwright

Onze etapas depois, o MonitorApp tem quatro entidades, dez rotas, uma chamada de sistema, um
agendador e um fluxo de eventos. Mexer em qualquer uma dessas peças hoje é um ato de fé.

Esta etapa troca a fé por evidência, em quatro níveis. E o critério para decidir o que testar em
cada nível não é cobertura: é **o que dói mais quando quebra**.

### US13 — Alterar sem quebrar o existente · RNF08

> **Como** pessoa desenvolvedora,
> **quero** uma suíte que exercite as regras e o contrato HTTP,
> **para** perceber uma regressão antes que ela chegue a quem usa.

```gherkin
Cenário: CA13.1 - A suíte roda sozinha
  Quando executo npm test na pasta back
  Então os testes rodam sem servidor de pé
  E sem o agendador disparando pings

Cenário: CA13.2 - O front é testado fora do navegador
  Quando executo npm test na pasta front
  Então os módulos rodam em jsdom
  E o fetch é substituído por um dublê

Cenário: CA13.3 - A suíte é repetível
  Quando executo npm test duas vezes seguidas
  Então nenhum teste falha por e-mail já cadastrado

Cenário: CA13.4 - A cobertura tem piso
  Quando executo npm run coverage abaixo do limite configurado
  Então o comando falha

Cenário: CA13.5 - O isolamento é verificado
  Dado dois usuários criados na suíte
  Então existe um teste provando que um não enxerga o host do outro

Cenário: CA13.6 - O app é importável
  Dado o arquivo src/index.ts
  Então ele exporta o app
  E só chama listen quando executado diretamente
```

## Estrutura da aplicação

Os testes ficam ao lado do código que exercitam — `ping.test.ts` mora em `lib/`, `format.test.js`
mora em `lib/` do front —, com duas exceções deliberadas: o `routes.test.ts` fica na raiz de
`src/` porque atravessa todas as camadas, e o E2E fica em `tests/`, na raiz do projeto, porque
não pertence nem ao back nem ao front.

Os quatro níveis não testam as mesmas coisas com granularidades diferentes: cada um protege algo
que o anterior não alcança. O diagrama liga cada nível ao tipo de defeito que só ele pega.

<Mermaid title="Os quatro níveis e o que cada um protege">
{`
flowchart TB
  U["Unidade · node:test<br/>ping.ts e host.schema.ts"] --> R["Rotas · supertest<br/>routes.test.ts"]
  R --> F["Front · Vitest + jsdom<br/>format.js e api.js"]
  F --> E["E2E · Playwright<br/>monitor-app.spec.js"]
  U -.- UN["regras que não passam por HTTP"]
  R -.- RN["status codes, validação e isolamento"]
  F -.- FN["a requisição que o front monta"]
  E -.- EN["as telas funcionando juntas"]
`}
</Mermaid>

A ordem também é a do custo de diagnóstico. Um teste de unidade vermelho aponta a função; um E2E
vermelho diz apenas que a jornada quebrou, e descobrir onde é trabalho manual. Daí a regra
prática: subir de nível só quando o de baixo não consegue cobrir o caso.

## Descrição das tarefas

### TK12.1 · Escrever os testes de unidade

```bash title="Terminal: dentro de back/"
npm install -D supertest @types/supertest @playwright/test
```

O teste de unidade cobre o que **não** passa por HTTP. No MonitorApp há dois lugares assim, e não
por acaso são os dois de maior risco.

O `ping.test.ts` protege a chamada de sistema. O segundo caso é o que mais importa: um endereço
com `;` embutido não pode virar comando. Se alguém trocar `execFile` por `exec` em uma
refatoração, este teste falha — e é a única barreira automática contra uma injeção de comando no
projeto.

### TK12.2 · Escrever `src/routes.test.ts` (O contrato HTTP)

O teste de rotas é o mais valioso da suíte: ele exercita router, middlewares, controller, model e
banco de uma vez, verificando exatamente o que a
[Especificação da API](../api-spec/) promete.

Para isso o `index.ts` precisou mudar. As linhas 39 a 46 passaram a chamar `listen` **somente**
quando o arquivo é executado diretamente. Importado por um teste, o `app` é usado em memória pelo
`supertest`: nenhuma porta é aberta, nenhum agendador dispara `ping` de verdade, e vários
arquivos de teste podem rodar em paralelo.

O `createValidUser` das linhas 10 a 18 resolve o critério `CA13.3`. O e-mail é `@unique` no
banco, então um valor fixo faria a segunda execução da suíte falhar com `409`. Gerar um sufixo
aleatório por execução torna os testes repetíveis sem precisar limpar o banco antes.

O `before` das linhas 33 a 49 monta o cenário: **duas** contas e um host pertencente à primeira.
Duas, e não uma, porque metade do que interessa testar nesta aplicação é o que a segunda conta
**não** consegue ver.

Os blocos seguintes cobrem cada faixa do contrato. Vale destacar quatro deles:

| Bloco | Linhas | O que prova |
| ----- | ------ | ----------- |
| `POST /api/users` | 51 a 71 | cria com `201`, nunca devolve a senha, recusa confirmação divergente |
| `POST /api/signin` | 73 a 82 | e-mail inexistente devolve o **mesmo** `401` que senha errada |
| `GET /api/hosts` | 84 a 125 | exige token, recusa token adulterado, filtra por tag e **não mostra o host da outra conta** |
| `GET /api/hosts/:id` | 149 a 165 | host de outra conta é `404`; id malformado é `400` |

O teste das linhas 115 a 124 é o que fecha o critério `CA13.5`: a conta B lista os hosts e o id
cadastrado pela conta A não está lá. É uma asserção de **ausência**, e é o tipo de garantia que
uma refatoração distraída no `Host.read` quebraria em silêncio.

### TK12.3 · Escrever os testes de front (Vitest e jsdom)

```bash title="Terminal: dentro de front/"
npm install -D vitest @vitest/coverage-v8 jsdom
```

O `format.test.js` cobre as duas funções puras do front. O caso mais instrutivo é o de
`formatLatency(0)`: zero é uma medição **válida** e precisa virar `"0 ms"`, não `"—"`. Uma
verificação escrita como `latency ? … : '—'` passaria despercebida na revisão e falharia aqui.

O `api.test.js` testa a camada que monta as requisições — sem rede. O `beforeEach` substitui o
`fetch` global por um dublê (`vi.fn`), e cada teste inspeciona **o que teria sido enviado**.

Os cinco casos correspondem, um a um, às decisões tomadas ao longo do projeto: o prefixo `/api`
da etapa 2, o `Authorization` da etapa 10, o corpo serializado, a ausência de `Content-Type` sem
corpo (a mudança da etapa 8) e a chamada pública do login. É a suíte que documenta a evolução da
camada.

### TK12.4 · Escrever o fluxo completo em Playwright

O E2E não repete o que os níveis anteriores já cobrem. Ele testa o que só existe quando tudo está
junto: as telas, a sessão no `localStorage`, o proxy do Vite e a API, em um navegador de verdade.

O teste das linhas 22 a 55 percorre a jornada inteira em uma passada — cadastro, login, cadastro
de host com tags, histórico, medição sob demanda e saída. Os seletores usam `getByRole`, que
encontra elementos pelo papel de acessibilidade e pelo rótulo visível: o teste quebra se o botão
sumir, mas não se a classe CSS mudar.

O segundo teste, nas linhas 57 a 61, é o mais curto e prova o guarda do front: abrir a página
privada sem token leva ao login.

<Aside type="tip" title="O que cada nível pega, e o que ele deixa passar">
  Um teste de unidade que valida o schema não percebe que a rota esqueceu de chamar o
  `validate`. Um teste de rota que passa não garante que o botão da tela chama a rota certa. E um
  E2E verde não diz qual das dez camadas quebrou quando ele fica vermelho. Os quatro níveis não
  são redundância — são recortes diferentes do mesmo sistema, e o custo de diagnóstico cresce do
  primeiro para o último.
</Aside>

## Conceitos abordados

- `node:test` nativo, sem framework de teste no back-end
- `supertest` exercitando o app em memória, sem abrir porta
- Export condicional do `app` para permitir importação
- Dados únicos por execução como condição de repetibilidade
- Asserção de ausência para verificar isolamento por dono
- Dublê de `fetch` para testar a requisição sem rede
- `jsdom` como ambiente de módulos de front
- `getByRole` e testes que sobrevivem a mudança de CSS
- Limite de cobertura como porta de qualidade
