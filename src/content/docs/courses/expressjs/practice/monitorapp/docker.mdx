Etapa **13 de 13** · Nível **Avançado** · Docker · Docker Compose · Nginx

A última etapa não escreve nenhuma linha de aplicação. Ela empacota o que as doze anteriores
construíram, e resolve a pergunta que ficou pendente desde a etapa 2: **em produção, quem faz o
papel do proxy do Vite?**

O MonitorApp tem duas origens, então tem duas imagens. É a diferença mais visível em relação ao
[InvestApp](../../investapp/docker/), que empacota tudo em um contêiner só porque o Express serve
o front.

> **Como** pessoa responsável pela operação,
> **quero** subir a aplicação inteira com um comando,
> **para** não depender da versão de Node instalada na máquina.

```gherkin

  Dado hosts cadastrados
```

Duas coisas atravessam a fronteira do Compose, e as duas são propositais: a porta 8080, única
publicada para fora, e o `ping` que a API dispara contra a rede. O serviço `api` não expõe porta
nenhuma — quem fala com ele é o Nginx, pela rede interna.

## Descrição das tarefas

### TK13.1 · Escrever `back/Dockerfile` (A imagem da API)

O arquivo tem dois estágios, e a razão está nas linhas 3 a 5. O manifesto é copiado **antes** do
código: assim, uma alteração em `src/` não invalida a camada de `npm ci`, e a instalação de
dependências é reaproveitada do cache. Inverter essas duas linhas transformaria cada build em uma
instalação completa.

Três linhas do segundo estágio merecem leitura:

- **Linha 12** — `apk add iputils`. A imagem `node:24-alpine` não traz o binário `ping`. Sem esta
  linha, tudo compila, o servidor sobe, e **toda medição falha em silêncio**: o `execFile` da
  etapa 8 não encontra o comando, cai no `catch` e grava `success: false`. Seria um bug
  particularmente cruel de diagnosticar, porque parece um problema de rede.
- **Linha 17** — `npx prisma generate`. O client do Prisma é específico da plataforma; o que foi
  gerado no macOS ou no Windows do desenvolvedor não serve para o Alpine Linux da imagem.
- **Linha 20** — `USER node`. Sem ela o processo roda como root dentro do contêiner, e uma falha
  na aplicação vira uma falha com privilégio total. A linha 19 prepara o diretório de dados e
  ajusta o dono antes da troca.

O `CMD` da linha 24 encadeia duas coisas: aplica as migrations pendentes no volume e só então
sobe o servidor. É `migrate deploy`, e não `migrate dev` — a variante de produção não gera
migration nova nem faz perguntas; ela apenas aplica o que já está versionado.

### TK13.2 · Escrever `front/Dockerfile` e `front/nginx.conf`

O front também usa dois estágios, mas por outro motivo. O primeiro estágio (linhas 1 a 7) roda o
build do Vite; o segundo (linhas 9 a 12) copia apenas o `dist/` para uma imagem `nginx:alpine`.

O resultado é uma imagem sem Node, sem `node_modules` e sem código-fonte: HTML, CSS e JavaScript
estáticos, servidos por um servidor web. É a consequência de o front do MonitorApp ter build
próprio desde a etapa 1.

  showLineNumbers
  mark="6-7,9-11"
/>

O `nginx.conf` é o arquivo que fecha o ciclo aberto na etapa 2. O bloco `location /api/` das
linhas 8 a 16 é o equivalente exato do `server.proxy` do `vite.config.js`: tudo que começa com
`/api` vai para o serviço `api` — endereçado pelo **nome do serviço** do Compose, que a rede
interna do Docker resolve.

Para o navegador existe uma origem só, `localhost:8080`, e nenhum CORS acontece. O middleware
`cors` do Express continua registrado, e passa a ser relevante apenas para clientes de outra
origem — um app móvel, ou outro front publicado em domínio próprio.

As três linhas 13 a 15 são específicas do MonitorApp e existem por causa da
[etapa 11](../realtime/). O padrão do Nginx é acumular a resposta em um buffer antes de
repassá-la, o que faria os eventos SSE chegarem em rajadas ou não chegarem; e o tempo limite
padrão fecharia a conexão aberta. Sem essas três linhas, o painel ao vivo simplesmente não
funcionaria em produção — mesmo com o código do servidor perfeito.

<Aside type="tip" title="Três lugares, um mesmo problema">
  O `X-Accel-Buffering: no` que a etapa 11 escreveu na resposta, o `proxy_buffering off` daqui e o
  `proxy_read_timeout 1h` atacam a mesma coisa: intermediários que tratam uma resposta longa como
  uma resposta lenta. Vale conferir os três juntos — é o tipo de detalhe que só aparece depois do
  deploy.
</Aside>

### TK13.3 · Escrever os `.dockerignore`

Os dois arquivos existem para o mesmo par de motivos: **tamanho** e **segurança**.

O `back/.dockerignore` mantém fora `node_modules` (que seria reinstalado no estágio de deps, para
a plataforma certa), `.git`, `prisma/dev.db` — o banco de desenvolvimento não pode viajar para a
imagem — e o `.env`, que traria o segredo do JWT junto.

```text title="back/.dockerignore"
node_modules
npm-debug.log
.env
.git
prisma/dev.db
playwright-report
test-results
```

O do front é mais curto: `node_modules` e o `dist/` local, que seria sobrescrito pelo build do
estágio anterior.

### TK13.4 · Escrever `compose.yaml` (Os dois serviços)

O arquivo declara os dois serviços que a arquitetura sempre teve.

O serviço `api` das linhas 4 a 13 **não expõe porta**. É uma escolha deliberada: em produção
ninguém precisa falar com a API diretamente — quem faz isso é o Nginx, pela rede interna do
Compose. Só o serviço `front` publica uma porta, a 8080 da linha 18.

As variáveis das linhas 7 a 11 são a configuração inteira da aplicação, e reúnem o que foi
introduzido ao longo do trilho: o `DATABASE_URL` da etapa 7 apontando para dentro do volume, o
`MONITOR_ENABLED` e o `MONITOR_INTERVAL` da etapa 8, e o `JWT_SECRET` da etapa 10.

O volume nomeado das linhas 12 e 13 é o que faz o banco sobreviver. Sem ele, o SQLite viveria na
camada de escrita do contêiner e um `docker compose down` levaria tudo junto.

## Executando

<Steps>

1. Suba tudo:

   ```bash title="Terminal"
   cd examples/courses/expressjs/projects/monitor-app-test
   docker compose up --build
   ```

2. Abra <code>http://localhost:8080</code> e crie uma conta. Não há seed automático: a base do
   volume começa vazia.

3. Confira que o processo não é root:

   ```bash title="Terminal"
   docker compose exec api whoami
   ```

4. Confira que o `ping` existe na imagem:

   ```bash title="Terminal"
   docker compose exec api ping -c 1 8.8.8.8
   ```

5. Prove a persistência:

   ```bash title="Terminal"
   docker compose down
   docker compose up
   ```

   Os hosts cadastrados continuam lá. Para começar do zero — e apagar o volume:

   ```bash title="Terminal"
   docker compose down -v
   ```

</Steps>

## Conceitos abordados

- Build multi-estágio e ordem de camadas para aproveitar cache
- Dependências de sistema que a aplicação assume existir (`iputils`)
- `prisma generate` na imagem, por ser específico de plataforma
- `migrate deploy` no arranque do contêiner
- Usuário não-root dentro do contêiner
- Nginx como proxy reverso no lugar do servidor de desenvolvimento
- Buffer e timeout de proxy em respostas de fluxo contínuo
- Serviço interno sem porta publicada
- Volume nomeado e o ciclo `down` / `down -v`
