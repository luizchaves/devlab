Etapa **6 de 13** · Nível **Intermediário** · `node:sqlite` · SQL

Até aqui, um `Ctrl+C` apagava o inventário. Esta etapa resolve isso com o banco relacional mais
simples possível — um arquivo SQLite — e sem instalar nenhuma dependência: o módulo `node:sqlite`
faz parte do Node desde a versão 22.

A escolha de fazer isso **sem ORM** é deliberada. Escrever o SQL à mão uma vez deixa claro o que
o Prisma vai passar a fazer na etapa 7, e por que ele vale a pena.

## Estrutura da aplicação

A pasta `src/data/` sai inteira e dá lugar a `src/database/`, com quatro arquivos que separam
três responsabilidades distintas: **conectar** (`database.ts`), **criar o esquema**
(`migration.ts`) e **popular** (`seeders.ts`, com os dados em `seeders.json`). O `load.ts` só
encadeia os dois últimos em um comando.

## O que muda nesta etapa

Esta é a primeira das duas **remoções** do trilho. A pasta `src/data/` sai inteira, porque o
array que ela exportava foi substituído pelo banco.

| Etapa 5 (`monitor-app-swagger`) | Etapa 6 (`monitor-app-db-simple`) |
| ------------------------------- | --------------------------------- |
| `src/data/hosts.ts` com o array | `src/database/` com conexão, migration e seeders |
| `hosts.push(newHost)` | `INSERT INTO hosts (…) VALUES (?, ?, ?)` |
| `hosts.findIndex(…)` | `SELECT … WHERE id = ?` |
| dados voltam ao estado inicial a cada reinício | dados vivem em `src/database/db.sqlite` |
| — | scripts `db:load`, `db:drop` e `db:reload` |

Controllers, rotas, schemas e o documento OpenAPI **não mudaram**. É a prova de que a divisão em
camadas da etapa 3 valeu a pena: a troca de armazenamento ficou contida em um arquivo.

## Descrição das tarefas

### TK06.1 · Criar `src/database/database.ts` (A conexão)

Nenhum `npm install` aqui: o `node:sqlite` já vem no Node.

O módulo expõe a classe `DatabaseSync`, e o nome não é acidente — a API dele é **síncrona**.
Todo o resto da aplicação, porém, é `async` desde a etapa 3. Em vez de espalhar essa diferença
pelo model, este arquivo a resolve em um lugar só.

O trecho destacado nas linhas 23 a 46 é esse invólucro. Ele expõe exatamente três operações, que
cobrem tudo que um CRUD precisa: `run` para escrita (linha 25), devolvendo o número de linhas
afetadas; `get` para uma linha (linha 31); e `all` para várias (linha 35). O `parseRow` da linha
12 copia cada resultado para um objeto simples, porque o que o driver devolve não é um objeto
literal comum.

O `dbFile` da linha 4 aponta para um arquivo dentro do próprio `src/database/` — e é por isso
que ele aparece no `.gitignore`. Um banco de desenvolvimento não pertence ao repositório.

### TK06.2 · Criar `migration.ts`, `seeders.ts` e `load.ts` (A preparação do banco)

A migration é o esquema, escrito em SQL. O `CREATE TABLE IF NOT EXISTS` das linhas 6 a 12
descreve a única tabela desta etapa, com os mesmos três campos que o array tinha. O `id` é
`TEXT`, e não `INTEGER PRIMARY KEY AUTOINCREMENT`, porque quem gera o identificador continua
sendo a aplicação, com `randomUUID()`.

```bash title="Terminal: os três scripts novos"
npm run db:load     # cria a tabela e semeia

```

<Aside type="caution" title="Isto ainda não é migration de verdade">
  Um `CREATE TABLE IF NOT EXISTS` resolve o primeiro dia e nada mais. Ele não sabe evoluir um
  esquema existente: acrescentar uma coluna significaria apagar o banco. A etapa 7 troca este
  arquivo por migrations versionadas do Prisma, que registram cada alteração como um passo
  aplicável em ordem.
</Aside>

### TK06.3 · Reescrever `src/models/Host.ts` (O model em SQL)

A assinatura das cinco funções é **idêntica** à da etapa 3 — mesmos parâmetros, mesmos retornos,
mesmos `throw new Error`. Só o miolo mudou.

O `mapRow` da linha 6 é a primeira novidade: o banco devolve linhas genéricas, e alguém precisa
convertê-las no tipo `Host`. Concentrar isso em uma função evita repetir a conversão em cada
consulta.

O `create` destacado nas linhas 14 a 34 mostra o padrão do arquivo. O SQL vive em um template
literal (linhas 23 a 28), legível e indentado, e os valores **não** aparecem nele: entram como
array no segundo argumento de `db.run` (linha 31). Essa separação é o que impede injeção de SQL —
o driver envia comando e dados por caminhos diferentes, e um valor como `'; DROP TABLE hosts; --`
é gravado como texto, não interpretado.

A linha 33 fecha o `create` com `return await readById(id)`: em vez de montar o objeto de
resposta na mão, o model relê o registro gravado. É mais uma ida ao banco, e é o que garante que
a resposta reflita exatamente o que ficou persistido, inclusive valores preenchidos por padrão.

O `read` das linhas 36 a 54 traz o filtro com `LIKE ?` e os curingas aplicados no **parâmetro**
(linha 46), nunca na string do SQL. E o `update` e o `remove` (linhas 74 a 106) inauguram um novo
jeito de detectar ausência: em vez de procurar um índice, eles conferem `changes !== 1` — o
número de linhas que a operação realmente afetou.

## Conceitos abordados

- `node:sqlite` sem dependência externa
- Invólucro assíncrono sobre uma API síncrona
- SQL parametrizado com `?` e a defesa contra injeção
- Migration e seeders como scripts do projeto
- `changes` como forma de detectar recurso inexistente
- Reler o registro gravado em vez de montar a resposta na mão
