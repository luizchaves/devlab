Etapa **1 de 13** · Nível **Iniciante** · HTML · Tailwind CSS · Vite · Sem JavaScript

O MonitorApp começa pela experiência visual completa. Nesta etapa existem telas, navegação,
formulários e estados estáticos, mas nenhum `fetch`, nenhum manipulador de evento e nenhum
arquivo JavaScript de aplicação. A ideia é congelar a UX antes de ligar comportamento — e já
nascer dentro do projeto Vite, que é a casa definitiva do front.

## Estrutura da aplicação

O front nasce como um protótipo navegável em HTML dentro de `front/`. Os utilitários do
Tailwind vêm do Play CDN, que os gera no navegador, e o arquivo `css/components.css` concentra
o vocabulário visual do produto. A regra da etapa continua valendo: **sem JavaScript de
aplicação**.

Repare que não existe pasta `back/` ainda. Ela nasce na etapa 2 — e o fato de o front rodar
sozinho, sem servidor de aplicação, é justamente o que caracteriza a arquitetura de duas origens
do MonitorApp.

## O que muda nesta etapa

Esta é a primeira etapa, então não existe um diff contra a etapa anterior — tudo é novo. O que
vale registrar é a fronteira que a etapa impõe: quatro páginas e uma folha de estilo entram, e
todo o comportamento fica para a etapa 2.

| Entra nesta etapa | Fica para as próximas |
| ----------------- | --------------------- |
| `index.html`, `host.html`, `signin.html` e `signup.html` | a pasta `front/js/` e qualquer tag `<script>` |
| o Play CDN do Tailwind e o `css/components.css` | `fetch`, manipuladores de evento e estado de tela |
| `vite.config.js` declarando as quatro páginas | o proxy `/api`, que chega na etapa 2 |
| dados de exemplo escritos à mão no HTML | a pasta `back/`, o servidor Express e o banco |

### TK01.2 · Carregar o Tailwind e criar `css/components.css`

Um protótipo não deveria precisar de build. É exatamente para isso que existe o **Play CDN** do
Tailwind: um `<script>` que compila as classes no próprio navegador, olhando o HTML da página e
gerando só o CSS que ela usa.

```html title="front/index.html — as duas linhas do head"
<script src="https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4"></script>
<link rel="stylesheet" href="css/components.css" />
```

A divisão entre as duas linhas é o ponto da tarefa:

| Origem | O que entrega | Exemplo |
| ------ | ------------- | ------- |
| **Play CDN** | os utilitários do Tailwind, gerados em tempo de execução | `flex`, `gap-4`, `text-slate-500`, `md:grid-cols-3` |
| **`components.css`** | o vocabulário visual **deste produto** | `.card`, `.btn-primary`, `.status-dot`, `.latency-bar` |

O Tailwind não tem — nem deveria ter — uma classe para "pastilha de estado de host". Utilitário é
o que serve a qualquer projeto; componente é o que serve a este. Separar os dois em origens
diferentes deixa a fronteira explícita.

<Aside type="caution" title="O Play CDN é para prototipar, e só">
  A própria documentação do Tailwind desaconselha o CDN em produção: ele baixa o compilador para
  o navegador e trabalha a cada carregamento de página. Aqui isso é aceitável porque a etapa é um
  protótipo — não há build, não há servidor, e trocar uma classe é recarregar a aba.

  A partir da [etapa 2](../api/) existe Vite, e o mesmo Tailwind passa a ser **compilado**: o
  `dist/` sai só com os utilitários que as páginas realmente usam, minificado e com hash. O
  `components.css` continua o mesmo arquivo — muda apenas como os utilitários chegam.
</Aside>

O `components.css` tem três blocos. As linhas 13 a 40 declaram os tokens de cor em `:root` e o
fundo do `body`; as linhas 42 a 106 são os componentes genéricos — `.card` (linha 42), `.btn` e
suas variantes (49 a 76), `.field` e `.input` (78 a 106); e da linha 108 em diante ficam as
classes que existem só porque este projeto monitora rede.

Três delas merecem leitura atenta:

| Classe | Linha | Como funciona |
| ------ | ----- | ------------- |
| `.status-dot` | 108 | Pastilha neutra. A cor vem sempre de um modificador: `.status-online` (116), `.status-offline` (120) ou `.status-unknown` (124) |
| `.tag` | 129 | Lê a cor da variável `--tag-color`, escrita no atributo `style` do elemento — é assim que a cor gravada no banco chega ao CSS |
| `.latency-bar` | 141 | Uma trilha vazia; o preenchimento é o `::after` da linha 150, cuja largura é `calc(var(--latency) * 1%)` |

Nenhuma das três caberia como utilitário: todas dependem de estado do domínio — se o host
respondeu, qual é a cor da tag, quanto foi a latência.

### TK01.3 · Criar `host.html` (Histórico de um host)

<HtmlPreview path="examples/courses/express/projects/monitor-app-static/front/host.html" height="26rem" serveFromPublic allowScripts />

Esta é a tela que justifica o produto: um host não tem "um estado", tem uma série de medições. A
página divide isso em três seções.

A faixa de métricas das linhas 39 a 52 resume a série em três números — última latência, média
das 24 horas e disponibilidade em porcentagem. O trecho destacado nas linhas 54 a 60 é o gráfico:
um `<svg class="mt-4 sparkline">` com `viewBox="0 0 300 80"` e um único `<path>` na linha 58, cujo
atributo `d` desenha a série inteira em oito pontos. Não há biblioteca de gráficos envolvida — e
na etapa 7, quando os dados vierem do banco, o JavaScript vai apenas recalcular esse mesmo `d`.

A tabela das linhas 62 a 95 é o histórico por extenso. Cada `<tr>` combina o instante, a pastilha
`.status-dot` reaproveitada do painel e a latência. A linha 85 é a mais instrutiva do arquivo: a
medição com falha mostra `status-offline` e um travessão no lugar do número, porque a medição
existe mas a latência não. Essa distinção vira `latency: null` no banco, na etapa 7.

### TK01.5 · Criar `vite.config.js` e `package.json` (O projeto do front)

O Vite trata cada HTML como um ponto de entrada. Como o MonitorApp tem quatro páginas e não uma
SPA, as quatro precisam ser declaradas em `build.rollupOptions.input` — o bloco das linhas 11 a
16. Sem isso, `npm run build` geraria apenas o `index.html` e as outras três ficariam de fora do
`dist/`.

Este arquivo vai crescer exatamente uma vez em todo o projeto: na etapa 2, quando ganhar a seção

## Executando

<Steps>

1. Entre no front desta etapa:

   ```bash title="Terminal"
   cd examples/courses/express/projects/monitor-app-static/front
   ```

2. Instale e suba o servidor de desenvolvimento:

   ```bash title="Terminal"
   npm install
   npm run dev
   ```

3. Abra <code>http://localhost:5173</code> e navegue entre `index.html`, `host.html`,
   `signin.html` e `signup.html`.

</Steps>

<Aside type="tip" title="Por que começar sem JavaScript">
  Separar primeiro a experiência visual evita misturar três problemas ao mesmo tempo: layout,
  contrato HTTP e estado de tela. A próxima etapa mantém exatamente estas páginas, troca o Play
  CDN pelo Tailwind compilado no Vite e conecta o formulário à API usando JavaScript vanilla.
</Aside>

## Conceitos abordados

- Estrutura de páginas HTML sem framework de front-end
- Play CDN do Tailwind para prototipar sem build
- A fronteira entre utilitário genérico e componente do produto
- Variáveis CSS (`--latency`, `--tag-color`) como ponte entre dado e estilo
- Gráfico em SVG puro, sem biblioteca
- Formulários preparados para etapas futuras
- Vite com múltiplos pontos de entrada
