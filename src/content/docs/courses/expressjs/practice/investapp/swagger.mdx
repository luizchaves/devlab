Etapa **5 de 13** · Nível **Intermediário** · TypeScript · Express.js · Zod · OpenAPI

A etapa anterior transformou o contrato da API em código executável. Esta etapa faz esse mesmo contrato virar documentação navegável — sem escrevê-lo uma segunda vez.

Documentação de API costuma nascer certa e envelhecer errada. O motivo é quase sempre o mesmo: ela é escrita **em outro lugar** que não o código. Alguém acrescenta um campo obrigatório na rota, esquece do arquivo YAML, e a partir dali a documentação passa a mentir — o que é pior do que não existir, porque quem a lê confia nela.

A saída é não ter duas fontes. O `investment.schema.ts` da etapa 4 já descreve, com precisão, o que cada rota aceita: `name` com no mínimo 3 caracteres, `value` positivo, `id` em UUID. Essa descrição pode ser **traduzida** para OpenAPI em vez de reescrita:

<Mermaid title="Uma fonte, dois destinos">
{`
flowchart LR
  A["investment.schema.ts<br/>(Zod)"] --> B["validate()<br/>rejeita 400 em tempo de execucao"]
  A --> C["z.toJSONSchema()<br/>documento OpenAPI"]
  C --> D["Swagger UI<br/>/api/docs"]
  C --> E["openapi.json<br/>Insomnia, Postman, geradores"]
`}
</Mermaid>

Se um campo mudar de regra, os dois lados mudam juntos — porque são o mesmo objeto.

### TK05.1 · Instalar o Swagger UI e criar `src/docs/openapi.ts`

Só a **interface** precisa de dependência. A conversão do schema é feita pelo próprio Zod: desde a versão 4 ele traz `z.toJSONSchema()`, e não é preciso instalar nenhuma biblioteca de ponte.

O `toSchema` da linha 13 é a tradução inteira. O parâmetro `{ target: 'openapi-3.0' }` importa: OpenAPI 3.0 usa um dialeto próprio de JSON Schema, e sem ele o documento sai em um formato que o Swagger UI não desenha corretamente.

O `shapeOf` da linha 18 resolve o segundo detalhe. Os schemas da etapa 4 são compostos por fonte (`z.object({ body })`, `z.object({ params })`), e o OpenAPI espera cada fonte em um lugar diferente: corpo em `requestBody`, `:id` em `parameters`, filtro em `parameters` com `in: 'query'`. A função extrai a parte certa de cada schema.

## O que a documentação herda dos schemas

Vale abrir o `/api/openapi.json` e comparar com o `investment.schema.ts`. As regras chegaram
sozinhas:

| No schema Zod (etapa 4) | No documento OpenAPI |
| ----------------------- | -------------------- |
| `z.string().min(3, …)` | `{ "type": "string", "minLength": 3 }` |
| `z.number().positive(…)` | `{ "type": "number", "minimum": 0, "exclusiveMinimum": true }` |
| `z.uuid(…)` | `{ "type": "string", "format": "uuid", "pattern": "…" }` |
| campo sem `.optional()` | entra em `required` |
| `z.string().optional()` | fica fora de `required` |

Nenhuma dessas linhas foi digitada duas vezes. Mude o mínimo de `name` para 5 na etapa 4 e
recarregue o `/api/docs`: a documentação acompanha.

<Aside type="tip" title="O que ainda é escrito à mão">
  O Zod descreve a **forma** dos dados, não a semântica da API. Os `summary`, as descrições e a
  lista de status possíveis continuam sendo texto escrito por você — e é bom que sejam: eles
  explicam a intenção, que nenhum schema consegue inferir.
</Aside>

## Testando

O melhor teste desta etapa é provocar uma divergência de propósito. Abra o
`src/schemas/investment.schema.ts`, troque o mínimo do `name` de 3 para 5, salve e recarregue a
página `/api/docs`.

Duas coisas mudam ao mesmo tempo: o `minLength` que a documentação exibe, e o `400` que a rota
passa a devolver para nomes de quatro letras. É a demonstração de que não existem duas fontes
para desalinhar.

## O documento acompanha o trilho

O `openapi.ts` não fica parado nesta etapa. Como ele lê os schemas, os campos que as etapas
seguintes acrescentam ao investimento (`interest`, `categoryId`, `broker` na etapa 7) aparecem
na documentação sozinhos, sem que ninguém edite o arquivo.

O que **não** se propaga sozinho são as rotas novas. Quando a etapa 9 fecha a API atrás de
token, o documento passa a declarar isso explicitamente:

```ts title="src/docs/openapi.ts — a partir da etapa 9"
components: {
  securitySchemes: {
    bearerAuth: { type: 'http', scheme: 'bearer', bearerFormat: 'JWT' },
  },
},
security: [{ bearerAuth: [] }],
```

Essas seis linhas fazem duas coisas: colocam o botão **Authorize** no topo da página, onde se
cola o token do `POST /api/signin`, e passam a enviar o cabeçalho `Authorization` em todo
*Try it out*. Sem elas, a documentação continuaria bonita e toda requisição de teste
responderia `401`.

<Aside type="tip" title="Um exercício que se repete a cada etapa">
  As rotas de categorias, corretoras, usuários e avatar entram nas etapas 7 a 11 e **não** estão
  no documento. Acrescentá-las é o exercício natural: cada uma é um bloco em `paths`, e o schema
  do corpo sai do `shapeOf` que já existe. Documentar a rota junto com a rota é o hábito que
  esta etapa quer instalar.
</Aside>

<Aside type="caution" title="Documentação exposta é decisão de projeto">
  Em desenvolvimento, deixar `/api/docs` aberto é o que se quer. Em produção, a decisão é
  consciente: uma API pública se beneficia da página aberta; uma API interna costuma servi-la
  atrás de autenticação, ou não servi-la.
</Aside>
