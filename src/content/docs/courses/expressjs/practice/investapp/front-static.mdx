Etapa **1 de 13** · Nível **Iniciante** · HTML · Tailwind CSS · Sem JavaScript

O InvestApp começa pela experiência visual completa. Nesta etapa existem telas, navegação,
formulários e estados estáticos, mas nenhum `fetch`, nenhum manipulador de evento e nenhum
arquivo JavaScript. A ideia é congelar a UX antes de ligar comportamento.

## O que muda nesta etapa?

Esta é a primeira etapa, então não existe um diff contra a etapa anterior — tudo é novo. O que
vale registrar é a fronteira que a etapa impõe: quatro páginas e uma folha de estilo entram, e

### TK01.1 · Criar `index.html` e Estrutura Inicial (Dashboard, Scripts, Governança e Skill de Specs)

O setup inicial do InvestApp estabelece a base do projeto com os documentos de especificação e governança (`docs/PRD.md`, `AGENTS.md`, `README.md`), a skill `.agents/skills/task-spec-generator/SKILL.md`, a configuração de formatação/linter com Biome (`biome.json`), pre-commit hooks Git e os scripts padronizados no `package.json`:
- `dev`: inicia o servidor local com recarregamento rápido.
- `build`: compila os artefatos estáticos e otimiza o bundle para produção.
- `preview`: executa uma pré-visualização local dos arquivos gerados pelo build.
- `lint`: executa a checagem estática com Biome (`biome check .`), identificando inconformidades e más práticas.
- `format`: formata automaticamente os arquivos com o Biome (`biome format --write .`).
- `lint:fix`: aplica correções estáticas e formatação em uma única etapa (`biome check --write .`).

O dashboard é montado com três blocos. O cabeçalho de navegação ocupa as linhas 11 a 27; o resumo da carteira aparece no cartão `<div class="card metric grid gap-2 p-6">` das linhas 39 a 43; e a grade de ativos repete a mesma estrutura em cada `<article class="card investment-card p-5">`, cuja primeira ocorrência está nas linhas 47 a 57. Repare como as classes se dividem nesses blocos. `card`, `investment-card`, `badge` e `status-dot` vêm do `components.css` e dizem **o que a coisa é**; tudo em volta (`mx-auto max-w-7xl px-4`, `grid gap-4 md:grid-cols-3`, `text-slate-500`) são utilitários do Tailwind escritos direto no HTML, que dizem **como ela se posiciona**. O trecho destacado nas linhas 84 a 111 é o único elemento interativo da página: o formulário de novo investimento vive dentro de um `<details class="card mt-8 p-6">`, e é o `<summary>` da linha 85 que abre e fecha o bloco, sem uma única linha de JavaScript. ### TK01.2 · Carregar o Tailwind e criar `css/components.css`

Um protótipo não deveria precisar de build. É exatamente para isso que existe o **Play CDN** do
Tailwind: um `<script>` que compila as classes no próprio navegador, olhando o HTML da página e
gerando só o CSS que ela usa.

```html title="index.html — as duas linhas do head"
<script src="https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4"></script>
<link rel="stylesheet" href="css/components.css" />
```

A divisão entre as duas linhas é o ponto da tarefa:

| Origem | O que entrega | Exemplo |
| ------ | ------------- | ------- |
| **Play CDN** | os utilitários do Tailwind, gerados em tempo de execução | `flex`, `gap-4`, `text-slate-500`, `md:grid-cols-3` |
| **`components.css`** | o vocabulário visual **deste produto** | `.card`, `.btn-primary`, `.investment-card`, `.file-drop` |

O Tailwind não tem (nem deveria ter) uma classe para "cartão de investimento". Utilitário é o
que serve a qualquer projeto; componente é o que serve a este. Separar os dois em origens
diferentes deixa a fronteira explícita.

<Aside type="caution" title="O Play CDN é para prototipar, e só">
  A própria documentação do Tailwind desaconselha o CDN em produção: ele baixa o compilador para
  o navegador e trabalha a cada carregamento de página. Aqui isso é aceitável porque a etapa é um
  protótipo — não há build, não há servidor, e trocar uma classe é recarregar a aba.

  Um projeto que vá para produção compila o Tailwind. É o que a [etapa 2](../api/) passa a fazer:
  a CLI do Tailwind lê o HTML de `public/` e escreve um `css/app.css` com apenas os utilitários
  que as telas realmente usam. O `components.css` que você escreve aqui continua exatamente o
  mesmo daquela etapa em diante — o que muda é só o caminho pelo qual os utilitários chegam.
</Aside>

O `components.css` tem três blocos. As linhas 13 a 40 declaram os tokens de cor em `:root` e o
fundo do `body`; as linhas 42 a 146 são os componentes genéricos — `.card` (linha 42), `.btn` e
suas variantes (49 a 85), o `.icon-button` dos ícones de ação (87), e `.field`, `.input` e o
`.invalid-feedback` da validação (105 a 146); e da linha 148 em diante ficam as classes
específicas do domínio: `.badge`, `.metric`, `.investment-card`, `.status-dot`, `.avatar`,
`.profile-image` e `.file-drop`.

São essas classes, e não os utilitários, que as quatro páginas reutilizam. Elas garantem
espaçamentos e cores padronizados sem depender de build step nem de pré-processador durante a
prototipagem.

Este arquivo é o mesmo nas treze etapas. O vocabulário visual do produto não muda ao longo da
trilha — o que muda é como os utilitários do Tailwind chegam até ele, e isso é assunto da
etapa 2.

<Aside type="note" title="O Vite entra só como build, e não como servidor">
  O `npm run build` é a única ferramenta do front em todo o projeto, e o que ela faz é empacotar:
  os módulos das próximas etapas viram um arquivo só, o CSS é minificado e cada arquivo ganha um
  hash no nome, o que resolve cache de navegador sem esforço.

  O que ele **não** faz é servir o front. Da etapa 2 em diante quem entrega as páginas é o
  próprio Express, na mesma origem da API — e é por isso que o InvestApp nunca precisa de CORS.
  O [MonitorApp](../../monitorapp/api/) usa o Vite do outro jeito, como servidor em outra porta,
  e paga o preço de precisar de proxy em desenvolvimento e de CORS em produção.
</Aside>

<Aside type="tip" title="Por que começar sem JavaScript">
  Separar primeiro a experiência visual evita misturar três problemas ao mesmo tempo:
  layout, contrato HTTP e estado de tela. A próxima etapa mantém esse front e conecta o
  formulário à API usando JavaScript vanilla.
</Aside>

## Conceitos abordados

- Estrutura de páginas HTML sem build
- Play CDN do Tailwind para prototipar sem build
- A fronteira entre utilitário genérico e componente do produto
- Formulários preparados para etapas futuras
- Avatar e navegação de perfil já previstos
- Evolução incremental sem framework de front-end
