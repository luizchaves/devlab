## O que muda nesta etapa

Comparando com a etapa de testes, a aplicação não ganha uma linha de regra de negócio. Entram três arquivos de empacotamento, e nada mais:

| Entra | Papel |
| ----- | ----- |
| `Dockerfile` | como a imagem é construída e o que ela executa |
| `.dockerignore` | o que **não** entra no contexto de build nem na imagem |
| `compose.yaml` | porta, variáveis de ambiente e volumes de execução |

Essa é a marca de um empacotamento bem-feito: o `src/`, o `public/` e o `prisma/` chegam intactos da etapa 12. Se conteinerizar tivesse exigido mudar a aplicação, alguma dependência do ambiente local teria vazado para o código.

## Descrição das tarefas

Abaixo estão detalhadas as tarefas de implementação desta etapa, com orientações e trechos de código.

### TK13.1 · Criar `Dockerfile` (Receita da imagem do aplicativo)

O arquivo tem trinta e uma linhas e três estágios, separados pelos `FROM` das linhas 7 e 15.

O **primeiro estágio** (linhas 1 a 5), apelidado de `deps`, existe só para instalar dependências. Ele copia apenas o `package*.json` (linha 4) antes de rodar o `npm ci` (linha 5), e essa ordem é deliberada: o Docker guarda o resultado de cada linha em cache, e como o `package.json` muda muito menos que o código, uma alteração em `src/` não refaz a instalação. O `--omit=dev` deixa `vitest`, `supertest` e Playwright de fora da imagem final.

O **segundo estágio** (linhas 7 a 13) compila o front. Ele instala as dependências **sem** o `--omit=dev`, porque o Vite é uma `devDependency`, e roda `npm run build` na linha 13. Nada deste estágio vai para a imagem final além do `dist/`.

O **terceiro estágio** (linhas 15 a 31) monta a imagem que será publicada. A linha 19 traz o `node_modules` de produção do primeiro estágio; o `COPY . .` da linha 20 traz o código; a linha 22 traz o front já compilado do estágio de build; e o `npx prisma generate` da linha 24 gera o client — ele precisa rodar **dentro** da imagem, porque o client é específico da plataforma.

As linhas 26 e 27 são a parte de segurança: criam as pastas de dados e de uploads, passam a posse para o usuário `node` e trocam o processo para ele. Sem esse `USER node`, a aplicação rodaria como `root` dentro do contêiner.

Por fim, o `CMD` da linha 31 encadeia duas coisas: `npx prisma migrate deploy` aplica as migrations pendentes no banco do volume e, só então, `npm start` sobe o servidor. É por isso que subir o contêiner pela primeira vez já entrega o banco com o schema correto.

<Aside type="note" title="Por que três estágios">
  O `--omit=dev` já reduz bastante a imagem, mas o multi-estágio garante que nada do processo
  de instalação (cache do npm, ferramentas de build nativas, o próprio Vite) vá para a imagem
  final. Só o que as linhas 19, 20 e 22 copiam explicitamente sobrevive.

  O estágio do meio existe por um motivo específico: o front precisa das `devDependencies` para
  ser compilado, e elas não podem acompanhar a imagem publicada. Separar o build da execução é o
  que permite ter as duas coisas.
</Aside>

### TK13.2 · Criar `.dockerignore` (Exclusão de arquivos no contexto de build)

O `COPY . .` da linha 11 do `Dockerfile` copia tudo que não estiver listado aqui — por isso este arquivo é de segurança, e não só de desempenho.

As linhas 1 e 2 evitam mandar dependências e logs da máquina local; a linha 3 mantém o `.env` **fora** da imagem, e a linha 5 deixa de fora o banco de desenvolvimento, com dados de teste. As linhas 8 e 9 descartam relatórios do Playwright.

O par de linhas 6 e 7 merece atenção: a primeira ignora todos os uploads já feitos localmente, e a segunda, com `!`, faz uma exceção para o `avatar.png` — a imagem padrão precisa existir na imagem Docker, mas as fotos dos usuários, não.

```txt title=".dockerignore" showLineNumbers {3,5,6-7}
node_modules
npm-debug.log
.env
.git
prisma/dev.db
public/imgs/profile/*
!public/imgs/profile/avatar.png
playwright-report
test-results
```

<Aside type="danger" title="A imagem não deve carregar o `.env`">
  Um `.env` copiado para dentro da imagem viaja com ela para qualquer registry onde ela for
  publicada — e continua lá mesmo depois de "removido" em uma camada posterior. Os valores
  entram em tempo de execução, pelo `environment` do Compose ou por `docker run -e`.
</Aside>

### TK13.3 · Criar `compose.yaml` (Orquestração do contêiner e volumes)

```bash title="Terminal: subir a aplicação com Docker Compose"
docker compose up -d --build
```

O Compose documenta, em dezessete linhas, o comando de execução completo que ninguém precisa mais lembrar.

O serviço `investapp` da linha 2 é construído a partir do próprio diretório (`build: .`, linha 3) e publica a porta 3000 na linha 5. O bloco `environment` das linhas 6 a 10 é onde entram os valores que ficaram fora da imagem: o `DATABASE_URL` da linha 8 aponta para `/app/data/dev.db` (dentro do volume, e não dentro da imagem) e o `JWT_SECRET` da linha 9 traz um `change-me-in-production` que é exatamente o que o nome diz.

### TK13.4 · Declarar os volumes persistentes (`investapp-db` e `investapp-profile-images`)

Contêiner é descartável; dado, não. Os dois volumes das linhas 11 a 13 são o que sobrevive a um `docker compose down` seguido de `up`.

O `investapp-db` guarda o arquivo SQLite em `/app/data`, e o `investapp-profile-images` guarda os avatares em `/app/public/imgs/profile` — os mesmos dois caminhos que a linha 14 do `Dockerfile` criou e entregou ao usuário `node`. A declaração das linhas 15 a 17 é o que registra esses volumes como nomeados e gerenciados pelo Docker.

Repare que o banco fica em `/app/data`, e não em `/app/prisma`. Montar um volume sobre `/app/prisma` esconderia o `schema.prisma` e a pasta `migrations/`, que são justamente o que o `prisma migrate deploy` do `CMD` precisa ler para funcionar.

## Executando

<Steps>

1. Entre na pasta da etapa final:

   ```bash title="Terminal"
   cd examples/courses/expressjs/projects/invest-app-test
   ```

2. Construa e suba com Compose:

   ```bash title="Terminal"
   docker compose up --build
   ```

3. Abra o front:

   ```txt title="URL"
   http://localhost:3000
   ```

4. Derrube sem apagar os volumes:

   ```bash title="Terminal"
   docker compose down
   ```

</Steps>

Para recomeçar o banco do zero, remova também os volumes:

```bash title="Terminal"
docker compose down --volumes
```

## O diff que importa

Compare a etapa de testes com a etapa de Docker procurando arquivos de runtime, não mudanças
em regra de negócio:

```bash title="Terminal"
git diff --no-index -- \
  examples/courses/expressjs/projects/invest-app-upload \
  examples/courses/expressjs/projects/invest-app-test || true
```

Como as etapas 12 e 12 compartilham a mesma pasta, esse comando mostra as duas de uma vez. Na
revisão, o que deve aparecer de novo são os três arquivos da tabela acima, mais os arquivos de
teste da etapa anterior. Qualquer alteração dentro de `src/` ou `public/` merece uma segunda
olhada.

Vale conferir, em particular, quatro linhas do `Dockerfile` e do `compose.yaml` — são elas que
separam uma imagem que funciona de uma que só funciona na sua máquina:

| Linha | Onde | Por quê |
| ----- | ---- | ------- |
| `RUN npm ci --omit=dev` | `Dockerfile`, linha 5 | instala pelo lockfile, sem dependências de teste |
| `RUN npx prisma generate` | `Dockerfile`, linha 12 | o client precisa ser gerado para a plataforma da imagem |
| `CMD [... migrate deploy && npm start]` | `Dockerfile`, linha 18 | aplica migrations antes de servir |
| `DATABASE_URL: file:/app/data/dev.db` | `compose.yaml`, linha 8 | aponta o banco para o volume, não para a imagem |

## Conceitos abordados

- Imagem Docker multi-estágio para aplicação Node.js
- Ordem das camadas e o cache do `npm ci`
- `.dockerignore` para reduzir contexto e manter o `.env` fora da imagem
- Execução como usuário sem privilégios com `USER node`
- Prisma Client gerado no build e `migrate deploy` na inicialização
- Compose com variáveis de ambiente e volumes nomeados
