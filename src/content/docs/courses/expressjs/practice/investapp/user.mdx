### US08 — Ter uma carteira própria · RF02, RNF02

> **Como** visitante,
> **quero** criar uma conta com nome, e-mail e senha,
> **para** ter uma carteira que seja só minha.

```gherkin
Cenário: CA08.1 - Cadastro bem-sucedido
  Quando envio POST /api/users com nome, e-mail e senha válidos
  Então recebo o status 201
  E o corpo traz id, nome e e-mail
  Mas o corpo não traz o campo password

Cenário: CA08.2 - E-mail é único
  Dado um usuário já cadastrado com "maria@email.com"
```

### TK08.2 · Criar `src/utils/password.ts` e `src/models/User.ts` (Hash da senha)

Nenhuma dependência nova: o hash é feito com `node:crypto`, importado na linha 10. O Node traz o **Argon2id** embutido, que é o algoritmo recomendado hoje para senha — mais resistente a ataque com GPU do que os anteriores, porque o custo dele é de **memória**, e não só de processador.

As constantes das linhas 14 a 23 são esse custo declarado: 64 MiB de memória, 3 passagens e 4 threads. São os números que tornam cada tentativa de quebra cara.

O `hashPassword` da linha 33 gera um sal novo a cada chamada (linha 34) e devolve tudo junto em uma string no **formato PHC**:

```txt title="O que fica gravado na coluna password"
$argon2id$v=19$m=65536,t=3,p=4$1x8S8vrkIM+oF8Y...$RdescudvJCsgt3ub...
```

Repare no que essa string carrega: o algoritmo, a versão, os três parâmetros de custo, o sal e só então o hash. Guardar os parâmetros **junto** do hash é o que permite endurecer os custos amanhã sem invalidar as senhas cadastradas hoje — o `verifyPassword` da linha 54 lê os parâmetros do próprio registro antes de refazer a conta.

A última linha da verificação usa `timingSafeEqual`, e não `===`. Uma comparação comum de strings para no primeiro byte diferente, e o tempo que ela leva vaza informação sobre quantos bytes estavam certos. A comparação em tempo constante fecha esse canal.

<Aside type="note" title="Por que não instalar `bcrypt` ou `argon2`">
  Até o Node 22, hash de senha exigia dependência nativa — `bcrypt` e `argon2` precisam ser
  compilados na instalação, o que quebra em imagens Docker enxutas e em CI. Com o Argon2id no
  `node:crypto`, essa dependência deixou de existir: menos superfície de ataque, menos build e
  o algoritmo mais recomendado hoje. Ver a implementação também ensina o que a biblioteca faria
  por você.
</Aside>

O model usa isso em uma linha. O `select` da linha 9 lista os campos públicos e **omite o `password`**, então o hash simplesmente não existe no objeto que sai do model — nenhuma rota precisa lembrar de apagá-lo. E o `hashPassword` da linha 18, dentro do `create`, garante que toda origem que crie usuário passe pelo mesmo caminho.

A exceção tem nome próprio: `readByEmailWithPassword`, na linha 41, é a única função que devolve o hash, e existe exclusivamente para o login da etapa 9.

## A migration

As duas mudanças do schema (o model novo e a chave estrangeira) viram uma migration só:
`prisma/migrations/20241012023426_create_user/migration.sql`, gerada pelo `prisma migrate dev`.
Ela cria a tabela `User`, recria `Investment` com a coluna `userId` e o índice único do e-mail.
Como toda migration, é arquivo gerado: entra no versionamento para que outra máquina chegue ao
mesmo banco, mas não se edita depois de aplicada.

As duas migrations anteriores, da etapa 7, continuam intactas ao lado dela — é isso que torna o
histórico cumulativo.

```bash title="Terminal"
npx prisma migrate dev --name add_user_model
```

<Aside type="caution" title="`userId` obrigatório em uma tabela com dados">
  Acrescentar uma coluna `NOT NULL` sem valor padrão quebra a migration se já houver
  investimentos. As saídas são: tornar o campo opcional, definir um usuário padrão na
  migration, ou resetar o banco de desenvolvimento — que é o que esta etapa faz.
</Aside>

<Aside type="danger" title="Hash não é criptografia">
  Criptografia é reversível: existe uma chave que devolve o texto original. Hash não é — e é
  justamente por isso que ele serve para senha. Um vazamento do banco entrega hashes, não
  credenciais, e nem o administrador do sistema consegue ler a senha de alguém.
</Aside>

<Aside type="caution" title="A senha sai do banco; é a rota que a remove">
  Este model não usa o `select` do Prisma, então `prisma.user.create` devolve o registro
  completo, com o hash. O `delete newUser.password` da rota é o que impede o campo de chegar
  ao cliente — e ele precisa ser repetido em **toda** rota que devolva usuário. Uma alternativa
  mais segura é declarar um `select` no próprio model, para que a senha nunca saia do banco.
</Aside>

Duas linhas a mais, e nada mais muda no model. O peso da alteração está na migration que ela
gera — e é sobre isso que o aviso do `userId` obrigatório fala.

## Conceitos abordados

- Migration que acrescenta um model e uma chave estrangeira
- Hash de senha com Argon2id do `node:crypto`, sem dependência externa
- Formato PHC: parâmetros de custo e salt viajando junto do hash
- Comparação em tempo constante com `timingSafeEqual`
- A senha removida da resposta antes de sair da rota
- Rota pública de cadastro e o restante protegido
- Formulário de cadastro consumindo a API
