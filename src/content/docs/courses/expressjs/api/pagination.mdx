`GET /tasks` funciona muito bem com vinte registros. Com duzentos mil, a mesma rota
derruba o servidor, a rede e o navegador. Este tópico trata dos parâmetros que fazem uma
coleção crescer sem quebrar.

Materiais: [slides do tópico](../../../../slides/courses/expressjs/api/pagination/) e [mapa mental](../../../../mindmaps/courses/expressjs/api/pagination/).

## Objetivo

Ao final você saberá paginar por offset e por cursor, escolher entre os dois, combinar
filtros opcionais sem uma cascata de `if`, e permitir ordenação sem abrir a porta para
consultas arbitrárias.

## Por que não devolver tudo

Uma listagem sem limite tem três custos simultâneos, e todos crescem junto com a tabela:

| Custo         | Efeito                                                          |
| ------------- | --------------------------------------------------------------- |
| Banco         | varredura completa da tabela a cada chamada                      |
| Memória       | o processo carrega o resultado inteiro antes de serializar       |
| Rede          | megabytes trafegados para exibir dez linhas na tela              |

<Aside type="danger" title="Limite padrão não é opcional">
  Uma rota de listagem sem limite padrão é uma negação de serviço esperando acontecer: basta
  a tabela crescer. Defina um padrão (20 ou 50) e um teto (100), independentemente do que o
  cliente peça.
</Aside>

## Paginação por offset

É a forma mais direta: pular `N` registros e pegar os próximos `M`.

O limite e o padrão não precisam morar no controller: no projeto modelo eles são parte do
schema que valida a query, então chegam ao model já convertidos e dentro da faixa
permitida.

O envelope separa os dados dos metadados, e é o que permite ao front-end desenhar a
paginação:

<Aside type="caution" title="Envelope muda o contrato">
  Trocar um array puro por `{ data, meta }` quebra todo cliente que fazia
  `response.json().map(...)`. Se a API já está em uso, ou se versiona
  ([REST API](../rest/)), ou se colocam os metadados em cabeçalhos — `X-Total-Count` e
  `Link` — mantendo o corpo como array.
</Aside>

## Paginação por cursor

O offset tem dois problemas que só aparecem em escala: `OFFSET 100000` ainda faz o banco
contar cem mil linhas, e um registro inserido entre duas páginas desloca todos os demais —
o usuário vê o mesmo item duas vezes ou pula um.

<Mermaid title="Offset versus cursor quando um registro é inserido entre duas páginas">
{`
flowchart TD
  subgraph OFF["Offset: SKIP 20 LIMIT 10"]
    direction TB
    O1["Página 1 lida"] --> O2["Alguém insere um registro no topo"]
    O2 --> O3["Página 2 desloca<br/>o item 20 aparece de novo"]
  end
  subgraph CUR["Cursor: WHERE id > 'último'"]
    direction TB
    C1["Página 1 lida<br/>guarda o último id"] --> C2["Alguém insere um registro no topo"]
    C2 --> C3["Página 2 continua do id guardado<br/>sem repetição"]
  end

  OFF ~~~ CUR
`}
</Mermaid>

```ts title="Paginação por cursor" showLineNumbers {2,6-8}
export async function index(req: Request, res: Response) {
  const { cursor, limit = '20' } = req.query as { cursor?: string; limit?: string };
  const take = Math.min(100, Number(limit));

  const items = await prisma.task.findMany({
    take: take + 1, // um a mais: revela se existe próxima página
    ...(cursor ? { cursor: { id: Number(cursor) }, skip: 1 } : {}),
    orderBy: { id: 'asc' },
  });

  const hasNext = items.length > take;
  const data = hasNext ? items.slice(0, take) : items;

  res.json({ data, meta: { nextCursor: hasNext ? data.at(-1)?.id : null } });
}
```

| Critério                        | Offset (`page`/`perPage`) | Cursor (`cursor`/`limit`)   |
| ------------------------------- | ------------------------- | --------------------------- |
| "Ir para a página 7"            | sim                       | não                         |
| Total de páginas                | sim                       | não (exigiria contar tudo)  |
| Desempenho em página distante   | degrada                   | constante                   |
| Estável com inserções           | não                       | sim                         |
| Uso típico                      | tabela administrativa     | *feed*, rolagem infinita    |

<Aside type="tip" title="Comece por offset">
  Offset é mais simples, permite "ir para a página N" e resolve a maioria dos casos de sala
  de aula e de painéis administrativos. Migre para cursor quando a listagem for um feed ou
  quando a tabela passar de algumas centenas de milhares de linhas.
</Aside>

## Filtros combináveis

Filtros são opcionais por natureza, e uma cascata de `if` cresce mal. Montar o objeto de
condições incrementalmente resolve:

<Tabs syncKey="filters">
  <TabItem label="Cascata de if">
    ```ts title="Difícil de estender" showLineNumbers
    let where = {};

    if (req.query.q) {
      where = { ...where, title: { contains: req.query.q } };
    }

    if (req.query.priority) {
      where = { ...where, priority: req.query.priority };
    }

    if (req.query.done) {
      where = { ...where, done: req.query.done === 'true' };
    }
    ```
  </TabItem>

  <TabItem label="Mapa de filtros">
    ```ts showLineNumbers {8}
    const FILTROS = {
      q: (valor: string) => ({ title: { contains: valor } }),
      priority: (valor: string) => ({ priority: valor }),
      done: (valor: string) => ({ done: valor === 'true' }),
    } as const;

    export function buildWhere(query: Record<string, unknown>) {
      return Object.entries(FILTROS).reduce((where, [chave, montar]) => {
        const valor = query[chave];

        return valor ? { ...where, ...montar(String(valor)) } : where;
      }, {});
    }
    ```
  </TabItem>
</Tabs>

O mapa também define o que é aceito: um parâmetro fora dele é simplesmente ignorado, e não
há como o cliente inventar uma condição.

## Ordenação com lista de permitidos

Ordenação é o parâmetro mais perigoso da consulta, porque o valor vira **nome de coluna**.
Repassá-lo direto permite ordenar por qualquer campo (inclusive `password`) e, em SQL
montado por concatenação, injetar comandos:

```ts showLineNumbers {1,7,11}
const CAMPOS_ORDENAVEIS = ['title', 'priority', 'createdAt', 'dueDate'] as const;

type CampoOrdenavel = (typeof CAMPOS_ORDENAVEIS)[number];

export function buildOrderBy(sort?: string) {
  // ?sort=-dueDate  ->  dueDate desc
  const desc = sort?.startsWith('-') ?? false;
  const campo = sort?.replace(/^-/, '') as CampoOrdenavel;

  if (!CAMPOS_ORDENAVEIS.includes(campo)) {
    return { createdAt: 'desc' as const }; // padrão previsível
  }

  return { [campo]: desc ? ('desc' as const) : ('asc' as const) };
}
```

<Aside type="danger" title="Nunca use lista de proibidos">
  Bloquear `password` e liberar o resto falha no primeiro campo sensível que alguém
  acrescentar ao schema. A lista de **permitidos** é segura por construção: campo novo só
  entra quando alguém decide colocá-lo lá.
</Aside>

O mesmo vale para a ordenação estável: dois registros com o mesmo `createdAt` podem trocar
de posição entre páginas. Acrescentar o `id` como critério de desempate resolve:

```ts title="Ordenação estável"
orderBy: [{ createdAt: 'desc' }, { id: 'asc' }]
```

## O contrato completo

Reunindo tudo, a rota de listagem aceita quatro grupos de parâmetros:

| Parâmetro    | Exemplo              | Efeito                                    |
| ------------ | -------------------- | ----------------------------------------- |
| `page`       | `?page=2`            | página, começando em 1                     |
| `perPage`    | `?perPage=50`        | tamanho da página, limitado a 100          |
| `sort`       | `?sort=-dueDate`     | campo permitido; `-` inverte a ordem       |
| filtros      | `?q=api&priority=high` | condições combináveis por `AND`          |

<ApiRequest method="GET" path="/tasks?page=1&perPage=2&sort=title&done=false" baseUrl="http://localhost:3000" />

<ApiResponse status={200}>
{`
  {
    "data": [
      {
        "id": 2,
        "title": "Escrever a primeira API",
        "done": false,
        "priority": "medium",
        "dueDate": null,
        "createdAt": "2026-03-02T09:00:00.000Z"
      }
    ],
    "meta": { "page": 1, "perPage": 2, "total": 1, "totalPages": 1 }
  }
`}
</ApiResponse>

<Aside type="note" title="O `total` custa uma consulta a mais">
  Devolver `total` exige um `COUNT(*)` com os mesmos filtros — uma segunda consulta a cada
  listagem. Em tabelas grandes, é comum omiti-lo e devolver apenas `hasNext`, ou calculá-lo
  de forma aproximada.
</Aside>

## Exercício

Na rota `GET /tasks` da [etapa 4 da TaskAPI](../../practice/taskapi/typescript/), que ainda
devolve o array inteiro e sem validação:

1. Aceite `page` e `perPage`, com padrão 20 e teto 100.
2. Responda no envelope `{ data, meta }`.
3. Aceite `?q=` filtrando por trecho do título, sem diferenciar maiúsculas.
4. Aceite `?sort=` restrito a `title` e `createdAt`, com `-` invertendo a ordem.
5. Garanta que `?page=0`, `?perPage=9999` e `?sort=constructor` não quebrem nem exponham nada.

Depois compare com a [etapa 5](../../practice/taskapi/validation/), que resolve os cinco
pontos dentro do schema Zod em vez de dentro do controller.

<details>
  <summary>Possível resposta</summary>

  ```ts showLineNumbers
  const CAMPOS_ORDENAVEIS = ['title', 'createdAt'] as const;

  export function index(req: Request, res: Response) {
    const page = Math.max(1, Number(req.query.page ?? 1) || 1);
    const perPage = Math.min(100, Math.max(1, Number(req.query.perPage ?? 20) || 20));
    const termo = String(req.query.q ?? '').toLowerCase();

    const sort = String(req.query.sort ?? '');
    const desc = sort.startsWith('-');
    const campo = sort.replace(/^-/, '');
    const ordenarPor = CAMPOS_ORDENAVEIS.includes(campo) ? campo : 'createdAt';

    const filtradas = Task.findAll()
      .filter((task) => task.title.toLowerCase().includes(termo))
      .sort((a, b) => (desc ? -1 : 1) * a[ordenarPor].localeCompare(b[ordenarPor]));

    const total = filtradas.length;
    const data = filtradas.slice((page - 1) * perPage, page * perPage);

    res.json({
      data,
      meta: { page, perPage, total, totalPages: Math.ceil(total / perPage) },
    });
  }
  ```

  O `|| 1` e o `|| 20` cobrem `?page=abc`, em que `Number()` devolve `NaN` e `Math.max` o
  propagaria.
</details>

## Desafio

Implemente a paginação por cursor na mesma rota, devolvendo `meta.nextCursor`, e escreva um
teste que comprove a diferença: inserir uma tarefa no topo entre a leitura da página 1 e da
página 2 faz o offset repetir um registro, mas não o cursor.

## Perguntas de revisão

### Paginação

1. **Por que uma listagem sem limite é um risco, e não apenas uma lentidão?**

   <details>
     <summary>Possível resposta</summary>

     Porque o custo cresce com a tabela, sem que ninguém precise atacar: uma única chamada
     pode esgotar a memória do processo. É uma negação de serviço que a própria aplicação
     habilita.
   </details>

2. **Quando o cursor é melhor que o offset?**

   <details>
     <summary>Possível resposta</summary>

     Em feeds e listas muito grandes: o desempenho não degrada em páginas distantes e a
     paginação permanece estável quando registros são inseridos. Em troca, perde-se "ir para
     a página N" e o total de páginas.
   </details>

3. **Por que devolver `total` custa caro?**

   <details>
     <summary>Possível resposta</summary>

     Porque exige um `COUNT(*)` com os mesmos filtros — uma segunda consulta a cada
     listagem, que em tabelas grandes percorre muitas linhas.
   </details>

### Filtros e ordenação

4. **Por que a ordenação precisa de lista de campos permitidos?**

   <details>
     <summary>Possível resposta</summary>

     Porque o valor vira nome de coluna. Sem a lista, o cliente ordena por qualquer campo —
     inclusive `password`, o que permite inferir dados — e, em SQL concatenado, injetar
     comandos.
   </details>

5. **Por que acrescentar `id` como critério de desempate na ordenação?**

   <details>
     <summary>Possível resposta</summary>

     Porque registros com o mesmo valor no campo ordenado não têm ordem garantida entre
     consultas: eles podem trocar de posição e aparecer duas vezes ou sumir na paginação.
   </details>
