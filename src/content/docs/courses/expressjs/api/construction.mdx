As aulas anteriores apresentaram as peças isoladas. Esta mostra a ordem em que elas se
encaixam quando se parte de um requisito em texto e se chega a uma API funcionando com um
front-end consumindo.

## Objetivo

Ao final você saberá conduzir a construção de uma API do requisito ao endpoint: identificar
recursos, definir o contrato antes de implementar, distribuir o trabalho pelas camadas e
ligar um front-end ao resultado.

## Do requisito ao recurso

Um requisito costuma vir como frase. O primeiro trabalho é extrair dele os **substantivos**
(que viram recursos) e os **verbos** (que viram operações):

> "O usuário cadastra investimentos, cada um pertencente a uma categoria e a uma corretora,
> e consegue listar, filtrar por nome, editar e excluir os seus."

| Substantivo   | Recurso        | Observação                                    |
| ------------- | -------------- | --------------------------------------------- |
| usuário       | `/users`       | dono dos demais recursos                       |
| investimento  | `/investments` | recurso principal                              |
| categoria     | `/categories`  | tabela de apoio, provavelmente só leitura      |
| corretora     | `/brokers`     | tabela de apoio                                |

| Verbo do requisito | Operação                    |
| ------------------ | --------------------------- |
| cadastra           | `POST /investments`         |
| listar             | `GET /investments`          |
| filtrar por nome   | `GET /investments?name=`    |
| editar             | `PUT /investments/:id`      |
| excluir            | `DELETE /investments/:id`   |
| "os seus"          | autenticação + posse        |

<Aside type="tip" title="“Os seus” é um requisito de autorização">
  Palavras como *seus*, *próprios*, *apenas o dono* mudam a arquitetura: elas exigem
  autenticação em toda rota e filtro por usuário no model. Identificá-las cedo evita
  reescrever o CRUD depois — é o assunto de [Autorização](../../auth/authorization/).
</Aside>

## O contrato antes do código

Definir a tabela de endpoints antes de implementar tem um efeito prático imediato: o
front-end pode começar em paralelo, e as decisões difíceis (status, formato do erro,
paginação) aparecem enquanto ainda são baratas de mudar.

| Método | Caminho             | Corpo                    | Sucesso | Erros                     |
| ------ | ------------------- | ------------------------ | ------- | ------------------------- |
| GET    | `/investments`      | —                        | `200`   | `401`                     |
| GET    | `/investments/:id`  | —                        | `200`   | `401`, `404`              |
| POST   | `/investments`      | `{ name, amount, … }`    | `201`   | `401`, `415`, `422`       |
| PUT    | `/investments/:id`  | `{ name, amount, … }`    | `200`   | `401`, `404`, `415`, `422`|
| DELETE | `/investments/:id`  | —                        | `204`   | `401`, `404`              |

<Aside type="note" title="Contrato é acordo, não burocracia">
  A tabela acima cabe em um arquivo `requests.http` executável e em um `openapi.yaml`, como
  mostra a aula de [Documentação de API](../documentation/). O que não vale é o contrato
  existir só na cabeça de quem implementou o servidor.
</Aside>

## A ordem de implementação

Com o contrato definido, a construção percorre as camadas de dentro para fora — cada etapa
testável antes da seguinte:

<Mermaid title="Ordem de construção de um recurso em uma API Express">
{`
flowchart TD
  A["1. Tipos<br/>src/types/investment.ts"] --> B["2. Model<br/>acesso aos dados"]
  B --> C["3. Controller<br/>traduz HTTP em chamadas"]
  C --> D["4. Router<br/>caminhos + middlewares"]
  D --> E["5. Registro em app.ts"]
  E --> F["6. requests.http<br/>caminho feliz e erros"]
  F --> G["7. Front-end<br/>camada de serviço + tela"]
`}
</Mermaid>

<Steps>

1. **Tipos** — declare o que entra e o que sai. É o contrato em código.

2. **Model** — implemente `create`, `read`, `readById`, `update` e `remove`. Nenhuma
   referência a `req` ou `res` aqui.

3. **Controller** — leia a requisição, chame o model, escolha o status. Lance `HttpError`
   em vez de responder erro à mão.

4. **Router** — encadeie os middlewares antes do controller: `requireJson`, `validate`,
   `authenticate`.

5. **Registro** — monte o router em `app.ts`, sempre **antes** de `notFound`.

6. **`requests.http`** — escreva o caminho feliz e um caso para cada erro do contrato.

7. **Front-end** — consuma pela camada de serviço, nunca com `fetch` espalhado pela tela.

</Steps>

## Servir o front-end junto ou separado

Há duas formas de ligar a interface à API, e a escolha muda o que precisa ser configurado:

<Tabs syncKey="frontend-hosting">
  <TabItem label="Mesma origem">
    ```ts title="src/app.ts" showLineNumbers {2,5}
    // O Express serve os arquivos estáticos e a API no mesmo host e porta.
    app.use(express.static('public'));

    app.use('/api', investmentRouter);
    ```

    O front-end chama `fetch('/api/investments')` — caminho relativo, mesma origem, sem
    CORS.
  </TabItem>

  <TabItem label="Origens separadas">
    ```ts title="src/app.ts" showLineNumbers {2}
    // O front-end roda em outro servidor (Vite, em outra porta ou domínio).
    app.use(cors({ origin: 'http://localhost:5173' }));

    app.use('/api', investmentRouter);
    ```

    O front-end chama `fetch('http://localhost:3000/api/investments')` e o navegador exige
    os cabeçalhos de [CORS](../../security/cors/).
  </TabItem>
</Tabs>

| Critério                  | Mesma origem                    | Origens separadas                    |
| ------------------------- | ------------------------------- | ------------------------------------ |
| CORS                      | não é necessário                | obrigatório                          |
| Deploy                    | um serviço                      | dois serviços independentes           |
| Ferramentas de front-end  | build precisa gerar em `public/`| servidor de desenvolvimento próprio   |
| Cookie de sessão          | simples                         | exige `credentials` e `SameSite`      |

<Aside type="tip" title="Em sala de aula, comece pela mesma origem">
  Servir o front de `public/` elimina uma variável inteira do problema. Separe as origens
  quando o front passar a ter build próprio (Vite, React) ou quando os dois forem publicados
  separadamente.
</Aside>

## A camada de serviço no front-end

Espalhar `fetch` pelas telas repete URL, cabeçalho e tratamento de erro em todo lugar. Uma
camada fina isola isso:

```js title="public/js/services/api.js" showLineNumbers {1,6,12}
const BASE_URL = '/api';

async function request(path, options = {}) {
  const response = await fetch(`${BASE_URL}${path}`, {
    ...options,
    headers: { 'Content-Type': 'application/json', ...options.headers },
  });

  if (!response.ok) {
    const { error } = await response.json().catch(() => ({ error: {} }));

    throw new Error(error.message ?? `Falha na requisição (${response.status})`);
  }

  // 204 não tem corpo: chamar .json() aqui lança.
  return response.status === 204 ? null : response.json();
}

export const api = {
  list: () => request('/investments'),
  create: (data) => request('/investments', { method: 'POST', body: JSON.stringify(data) }),
  remove: (id) => request(`/investments/${id}`, { method: 'DELETE' }),
};
```

<Aside type="caution" title="`fetch` não lança em `4xx`">
  Um `404` chega como resposta normal, com `response.ok === false`. Sem a verificação, o
  `.json()` seguinte tenta interpretar o corpo de erro como se fosse o recurso — e a tela
  mostra `undefined` em vez da mensagem.
</Aside>

## Exercício

Parta do requisito abaixo e construa a API completa:

> "O usuário cadastra hosts para monitorar. Cada host tem nome e endereço, e pode ser
> listado, editado e removido. É possível filtrar hosts pelo nome."

1. Extraia recursos e operações e escreva a tabela de contrato com status de sucesso e erro.
2. Implemente na ordem tipos → model → controller → router → registro.
3. Escreva o `requests.http` cobrindo o contrato inteiro, erros incluídos.
4. Sirva um `public/index.html` que liste os hosts usando uma camada `services/api.js`.

<details>
  <summary>Possível resposta</summary>

  | Método | Caminho      | Corpo               | Sucesso | Erros              |
  | ------ | ------------ | ------------------- | ------- | ------------------ |
  | GET    | `/hosts`     | —                   | `200`   | —                  |
  | GET    | `/hosts?name=` | —                 | `200`   | —                  |
  | GET    | `/hosts/:id` | —                   | `200`   | `404`              |
  | POST   | `/hosts`     | `{ name, address }` | `201`   | `415`, `422`, `409`|
  | PUT    | `/hosts/:id` | `{ name, address }` | `200`   | `404`, `415`, `422`|
  | DELETE | `/hosts/:id` | —                   | `204`   | `404`              |

  O `409` cobre o endereço já monitorado — decisão de contrato que precisa ser tomada antes
  de implementar, não depois.
</details>

## Desafio

Implemente o mesmo recurso nas duas topologias: front servido por `express.static` e front
em um servidor Vite separado. Documente o que precisou mudar em cada lado — e o que aconteceu
no navegador antes de configurar o CORS.

## Perguntas de revisão

### Modelagem

1. **Como um requisito em texto vira uma lista de endpoints?**

   <details>
     <summary>Possível resposta</summary>

     Os substantivos viram recursos (caminhos) e os verbos viram operações (métodos HTTP).
     Palavras como "os seus" viram requisitos de autenticação e autorização.
   </details>

2. **Por que definir o contrato antes de implementar?**

   <details>
     <summary>Possível resposta</summary>

     Porque o front-end pode trabalhar em paralelo e porque as decisões de status, formato
     de erro e paginação ficam explícitas enquanto ainda são baratas de mudar.
   </details>

### Integração

3. **Por que implementar na ordem model → controller → router?**

   <details>
     <summary>Possível resposta</summary>

     Porque cada camada só depende da anterior: o model é testável sem servidor, o
     controller é testável com o model pronto, e o router só amarra o que já funciona.
   </details>

4. **Por que concentrar o `fetch` em uma camada de serviço no front-end?**

   <details>
     <summary>Possível resposta</summary>

     Porque URL base, cabeçalhos, token e tratamento de erro passam a existir em um lugar
     só. Mudar o prefixo da API ou acrescentar o cabeçalho de autenticação vira uma edição
     em um arquivo.
   </details>

5. **Por que `fetch` não lança em resposta `404`?**

   <details>
     <summary>Possível resposta</summary>

     Porque a requisição HTTP foi bem-sucedida — o servidor respondeu. `fetch` só rejeita em
     falha de rede. O status precisa ser verificado com `response.ok`.
   </details>
