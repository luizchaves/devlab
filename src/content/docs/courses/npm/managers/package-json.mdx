Este tópico apresenta o **`package.json`**, o arquivo de manifesto declarativo que define a identidade, as dependências, as configurações de ambiente e os scripts de automação de qualquer projeto no ecossistema JavaScript.

Presente em praticamente todas as aplicações modernas (sejam elas desenvolvidas em Node.js, TypeScript, React, Vue ou executadas no navegador com bundlers), o `package.json` funciona como a certidão de nascimento e o contrato central do projeto. É por meio dele que ferramentas de build, gerenciadores de pacotes (`npm`, `pnpm`, `Yarn`) e esteiras de integração contínua (CI/CD) compreendem como instalar, compilar e executar a aplicação.

## Objetivo

Compreender a estrutura, a semântica e os campos do manifesto `package.json`, dominando as regras de versionamento semântico (*SemVer*), a configuração de módulos e a automação de tarefas por scripts. Ao final do tópico, o leitor deve ser capaz de:

- Explicar o papel do `package.json` como manifesto central de projetos JavaScript e TypeScript.
- Identificar e configurar campos de metadados essenciais (`name`, `version`, `type`, `main`, `exports`, `license` e `private`).
- Diferenciar os tipos de dependências do projeto (`dependencies`, `devDependencies`, `peerDependencies` e `optionalDependencies`).
- Aplicar as regras e os operadores de versionamento semântico (*SemVer*) como `^`, `~` e faixas de versão.
- Criar e encadear *scripts* de automação com argumentos dinâmicos (`--`) e ganchos de ciclo de vida (`pre*` e `post*`).
- Configurar restrições de ambiente e gerenciadores oficiais através dos campos `engines` e `packageManager`.

## O que é o package.json?

O `package.json` é um arquivo em formato JSON posicionado na raiz de um projeto. Ele transforma uma pasta comum de arquivos em um pacote reconhecível pelo Node.js e pelos gerenciadores de dependências.

Ao criar um projeto com o comando `npm init -y`, o gerenciador gera uma estrutura mínima com os campos básicos de identificação:

```json title="package.json inicial"
{
  "name": "meu-projeto",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "type": "commonjs"
}
```

Qualquer ferramenta que interaja com o projeto lê esse arquivo para determinar quais módulos carregar, quais comandos executar e como empacotar os arquivos resultantes.

## Anatomia e Categorias de Campos

Os campos de um manifesto podem ser agrupados em cinco categorias funcionais: metadados, pontos de entrada, dependências, automação e restrições de ambiente.

A tabela a seguir resume os campos mais importantes de cada categoria:

| Campo | Categoria | Finalidade | Exemplo |
| :--- | :--- | :--- | :--- |
| `name` | Metadados | Nome único do pacote (suporta escopos com `@org/`). | `"@empresa/minha-api"` |
| `version` | Metadados | Versão atual do projeto seguindo SemVer. | `"1.2.0"` |
| `private` | Metadados | Impede a publicação acidental do projeto no registro npm. | `true` |
| `license` | Metadados | Licença de uso e distribuição em formato SPDX. | `"MIT"` ou `"UNLICENSED"` |
| `type` | Módulos | Define o sistema padrão de módulos (`"module"` ou `"commonjs"`). | `"module"` |
| `main` | Entradas | Ponto de entrada padrão para importação no Node.js clássico. | `"./dist/index.js"` |
| `exports` | Entradas | Mapeamento moderno de múltiplos caminhos e condições de importação. | `{"./utils": "./src/utils.js"}` |
| `scripts` | Automação | Comandos de terminal executáveis com `npm run`. | `{"dev": "vite", "build": "vite build"}` |
| `dependencies` | Dependências | Pacotes necessários para a execução em produção. | `{"express": "^5.0.0"}` |
| `devDependencies` | Dependências | Pacotes usados apenas no desenvolvimento, testes e compilação. | `{"vitest": "^3.0.0"}` |
| `engines` | Ambiente | Faixa de versões exigidas do Node.js ou npm. | `{"node": ">=20.0.0"}` |
| `packageManager` | Ambiente | Declara o gerenciador oficial e versão com Corepack. | `"pnpm@10.5.0"` |

<Aside type="caution" title="Dica de IA: Proteção contra publicação acidental">
Projetos de aplicações web, APIs privadas e trabalhos acadêmicos devem conter obrigatoriamente o campo `"private": true` no `package.json`. Isso impede que comandos acidentais como `npm publish` enviem o código-fonte proprietário para o registro público global.

**Prompt:** *"Adicione 'private: true' e revise todos os metadados deste package.json para garantir que nenhuma credencial ou arquivo privado possa ser publicado por engano."*
</Aside>

## Sistema de Módulos: ESM vs CommonJS

O campo `"type"` define como o runtime do Node.js interpreta arquivos `.js` dentro do projeto:

- **`"type": "module"`**: Habilita o padrão oficial **ECMAScript Modules (ESM)**. O código passa a usar `import` e `export` nativamente, e recursos modernos como *top-level await* ficam disponíveis.
- **`"type": "commonjs"`** (padrão quando omitido): Mantém o sistema legado do Node.js com `require()` e `module.exports`.

O trecho abaixo exemplifica a configuração recomendada para projetos modernos com suporte a ESM:

```json title="package.json (Módulos ESM e Ponto de Entrada)"
{
  "name": "meu-app",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "main": "src/index.js",
  "exports": {
    ".": "./src/index.js",
    "./services": "./src/services/index.js"
  }
}
```

O campo `exports` é a convenção moderna que substitui e expande o antigo `main`. Ele permite expor submódulos públicos específicos e bloquear o acesso direto a pastas internas privadas da biblioteca.

## Tipologias de Dependências

O `package.json` separa as dependências em blocos distintos conforme o momento em que são necessárias.

O diagrama a seguir sintetiza a árvore de decisões para classificar um pacote no manifesto:

<Mermaid title="Critérios de classificação de dependências">
{`
flowchart TD
  A["Novo pacote a instalar"] --> B{"O código roda no navegador<br/>ou servidor em produção?"}
  B -- "Sim" --> C["dependencies<br/>(ex: axios, zod, express)"]
  B -- "Não" --> D{"É usado apenas para<br/>build, testes ou lint?"}
  D -- "Sim" --> E["devDependencies<br/>(ex: vitest, biome, vite)"]
  D -- "Não" --> F{"É um plugin que exige<br/>uma biblioteca hospedeira?"}
  F -- "Sim" --> G["peerDependencies<br/>(ex: react, tailwindcss)"]
  F -- "Não" --> H["optionalDependencies<br/>(binários por SO / arquitetura)"]
`}
</Mermaid>

A distinção entre `dependencies` e `devDependencies` é fundamental para servidores e contêineres Docker: em ambientes de produção, o comando `npm install --omit=dev` ignora linters e testes, reduzindo o consumo de memória e a superfície de segurança da imagem final.

## Versionamento Semântico (SemVer)

O formato das versões no `package.json` segue a especificação **Semantic Versioning (SemVer)**, composta por três dígitos numéricos: `MAJOR.MINOR.PATCH` (por exemplo, `2.4.1`):

- **MAJOR (Maior)**: Alterações que quebram a compatibilidade com versões anteriores (*breaking changes*). Exige adaptação manual no código.
- **MINOR (Menor)**: Novas funcionalidades adicionadas mantendo 100% de retrocompatibilidade.
- **PATCH (Correção)**: Correções de bugs e pequenos ajustes que não alteram a assinatura das funções existentes.

A tabela a seguir demonstra o significado de cada operador de faixa no `package.json`:

| Notação | Exemplo | Faixa permitida na instalação | Comportamento prático |
| :--- | :--- | :--- | :--- |
| **Circunflexo (`^`)** | `"^2.4.1"` | `>=2.4.1 <3.0.0` | Aceita correções e novas funcionalidades; trava a versão maior. |
| **Til (`~`)** | `"~2.4.1"` | `>=2.4.1 <2.5.0` | Aceita apenas correções de bug (*patch*); trava menor e maior. |
| **Versão Exata** | `"2.4.1"` | `2.4.1` | Instala estritamente a versão declarada, sem atualizações automáticas. |
| **Faixa Livre (`*`)** | `"*"` | Qualquer versão | Perigoso: aceita quebras de compatibilidade sem aviso. |
| **Intervalo Comparativo** | `">=18.0.0 <22.0.0"` | Faixa customizada | Comum no campo `engines` para travar versões do runtime. |

<Aside type="note" title="SemVer em versões 0.x.x">
Em versões iniciais de desenvolvimento (`0.y.z`), a especificação SemVer considera que qualquer incremento pode quebrar a API. Portanto, no `^0.3.2`, o npm aceita atualizações apenas até `0.3.x`, travando qualquer mudança no dígito `0.4.0`.
</Aside>

## Automação com Scripts e Ciclo de Vida

O bloco `"scripts"` permite definir atalhos de terminal para compilação, testes, formatação e execução do projeto.

O trecho a seguir demonstra a declaração de scripts de trabalho diário:

```json title="package.json (Scripts de desenvolvimento e qualidade)"
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "lint": "biome check .",
    "lint:fix": "biome check --write .",
    "test": "vitest run",
    "prebuild": "npm run lint && npm run test"
  }
}
```

As principais regras de execução e ciclo de vida de scripts incluem:

1. **Scripts padrão vs customizados**: Os scripts `start`, `test`, `restart` e `stop` podem ser executados diretamente com `npm test` ou `npm start`. Qualquer outro script personalizado exige a palavra `run` (por exemplo: `npm run dev` ou `npm run build`).
2. **Ganchos de ciclo de vida (`pre*` e `post*`)**: O npm executa automaticamente scripts prefixados por `pre` antes e `post` depois do comando principal. No exemplo acima, ao rodar `npm run build`, o script `prebuild` roda primeiro para validar linter e testes.
3. **Passagem de parâmetros (`--`)**: Para repassar opções de terminal diretamente para o binário executado pelo script, utilize o separador `--`:
   ```bash title="Terminal"
   npm run dev -- --port 8080 --host
   ```
4. **Execução sequencial vs concorrente**:
   - `npm run lint && npm run test`: Executa o segundo comando apenas se o primeiro terminar com sucesso (`exit code 0`).
   - `npm run dev & npm run mock`: No Linux e macOS, o operador `&` dispara o processo em segundo plano (em monorepos ou tarefas concorrentes, prefira ferramentas dedicadas como `concurrently` ou `pnpm --parallel`).

## Resumo e Boas Práticas

A tabela a seguir sintetiza as diretrizes recomendadas para manter manifestos saudáveis e manuteníveis:

| Prática recomendada | Motivo técnico |
| :--- | :--- |
| **Declarar `"private": true` em aplicações** | Evita vazamento acidental de código em registros públicos. |
| **Utilizar `"type": "module"`** | Adota o padrão moderno ECMAScript Modules (ESM) em todo o projeto. |
| **Separar dependências estritamente** | Deixa o ambiente de produção mais enxuto e seguro com `npm install --omit=dev`. |
| **Fixar motores no campo `engines`** | Documenta e garante que toda a equipe use a mesma versão mínima do Node.js. |
| **Criar scripts com nomes semânticos** | Padroniza comandos (`dev`, `build`, `test`, `lint`) facilitando a integração em CI/CD. |

## Executando

Veja como inspecionar e manipular o manifesto diretamente pelo terminal:

### Visualizando Informações do Manifesto

```bash title="Terminal"
npm pkg get name version scripts
```

```txt title="Output" frame="terminal"
{
  "name": "meu-projeto",
  "version": "1.0.0",
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  }
}
```

### Alterando Campos via Linha de Comando

O comando `npm pkg set` permite adicionar ou editar propriedades sem abrir o editor de texto:

```bash title="Terminal"
npm pkg set private=true type="module" engines.node=">=22.0.0"
```

```txt title="Output" frame="terminal"
Updated package.json:
- private: true
- type: "module"
- engines.node: ">=22.0.0"
```

## Desafio

Crie um manifesto para uma biblioteca reutilizável que exporta duas entradas distintas (`.` e `./math`) utilizando o campo moderno `exports`, garantindo compatibilidade com TypeScript e bloqueando a importação direta de arquivos internos privados.

<details>
  <summary>Possível resposta</summary>

  ```json title="package.json"
  {
    "name": "@meu-escopo/minha-lib",
    "version": "1.0.0",
    "type": "module",
    "license": "MIT",
    "exports": {
      ".": {
        "types": "./dist/index.d.ts",
        "default": "./dist/index.js"
      },
      "./math": {
        "types": "./dist/math.d.ts",
        "default": "./dist/math.js"
      }
    },
    "files": [
      "dist"
    ]
  }
  ```

  Ao configurar o objeto `exports` dessa forma, consumidores da biblioteca só conseguem importar `import { algo } from '@meu-escopo/minha-lib'` ou `import { somar } from '@meu-escopo/minha-lib/math'`. Qualquer tentativa de acessar arquivos privados como `@meu-escopo/minha-lib/dist/interno.js` será rejeitada pelo Node.js.
</details>

## Perguntas de revisão

Responda às questões para validar seu entendimento:

1. **Qual é a consequência de omitir o campo `"private": true` em uma aplicação comercial?**
   <details>
     <summary>Possível resposta</summary>
     O projeto fica vulnerável a ser publicado publicamente no registro global do npm caso alguém execute `npm publish` por engano.
   </details>

2. **Qual é a diferença de comportamento entre `"^1.5.0"` e `"~1.5.0"` no SemVer?**
   <details>
     <summary>Possível resposta</summary>
     O circunflexo `^1.5.0` aceita novas funcionalidades e correções até a versão menor (`<2.0.0`), enquanto o til `~1.5.0` aceita apenas correções de bug (*patch*) dentro da mesma versão menor (`<1.6.0`).
   </details>

3. **Por que o campo `"type": "module"` é necessário para utilizar `import`/`export` em arquivos `.js`?**
   <details>
     <summary>Possível resposta</summary>
     Porque o comportamento padrão do Node.js para a extensão `.js` é CommonJS (`require`). Declarar `"type": "module"` informa ao interpretador que todos os arquivos `.js` daquele diretório devem ser tratados como ECMAScript Modules (ESM).
   </details>

4. **Como funciona o gancho de ciclo de vida `pretest` no npm?**
   <details>
     <summary>Possível resposta</summary>
     Sempre que o comando `npm test` é acionado, o npm busca e executa o script `pretest` automaticamente antes de iniciar o `test`. Se o `pretest` falhar, a execução é interrompida.
   </details>
