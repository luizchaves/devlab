Etapa **1 de 11** · Nível **Iniciante** · HTML · Tailwind CSS · Vite · Sem BaaS conectado

Esta etapa constrói a superfície do InvestFlow antes de persistir dados. As páginas definem os campos, os estados visuais e a navegação que as sprints seguintes vão conectar ao Supabase. Os números da carteira, a autenticação e os indicadores administrativos são exemplos estáticos.

<Aside type="note" title="Tópicos conceituais associados">
  Se os formulários, links e scripts desta etapa parecerem "só tela", volte aos guias de [HTML semântico](../../../../html/elements/semantic-structure/), [Vite](../../../build/vite/) e [npm](../../../). O conceito central é prototipar contratos: cada `name`, `id`, página e estado vazio antecipa uma regra que depois será ligada a Auth, PostgreSQL e Storage, sem fingir que dado estático já é dado persistido.
</Aside>

## Objetivo

Construir um protótipo navegável que descreva a experiência do InvestFlow antes da infraestrutura. Ao final da etapa, o leitor deve ser capaz de:

- Diferenciar dado demonstrativo de dado persistido.
- Identificar as telas e os contratos visuais que a trilha vai implementar.
- Executar e revisar a interface estática com Vite e Biome.

## O que muda nesta etapa?

Como é a primeira etapa, tudo entra pela primeira vez. A fronteira mais importante é negativa: o protótipo não tem SDK, credencial, banco ou comportamento de domínio. Isso mantém a UX revisável sem criar a falsa impressão de que um formulário já cadastrou uma conta.

| Entra | Fica para a Sprint 2 ou posterior |
| ----- | --------------------------------- |
| HTML semântico, Tailwind instalado e CSS local compilado. | `@supabase/supabase-js`, sessão e chamadas remotas. |
| Links e formulários navegáveis. | Cadastro, login e redirecionamento por sessão real. |
| Valores de exemplo em tabelas, cards e páginas internas. | Dados de `assets`, `transactions`, `quotes_history`, `dividends_history`, `exchange_rates`, `brokers` e `profiles`. |
| Scripts Vite e qualidade. | Migrations, Edge Functions, bucket e policies. |

<Aside type="tip" title="Dica de IA: Gerar o AGENTS.md com governança e convenções para IA">
  O arquivo `AGENTS.md` define as regras operacionais, os padrões arquiteturais e o fluxo de trabalho para assistentes e agentes autônomos de IA. Utilize o prompt abaixo para gerá-lo:

  ```markdown
  Atue como Arquiteto de Sistemas BaaS e Engenheiro de IA Sênior.
  Gere o arquivo `AGENTS.md` para o InvestFlow, definindo as diretrizes completas de governança para agentes de código:

  1. **Papel e Escopo**: plataforma de gestão patrimonial com front-end em HTML5, Tailwind CSS e JavaScript modular, e back-end fornecido pelo Supabase.
  2. **Regras Invioláveis de Arquitetura**:
     - BaaS e serverless: banco, identidade, arquivos e funções residem no Supabase; proibido criar servidor Express ou API intermediária.
     - Row Level Security em 100% das tabelas de domínio (`enable row level security`), com policies comparando `auth.uid()` a `user_id` em `using` e `with check`.
     - Visão administrativa agregada, protegida por `profiles.role = 'admin'` conferido no banco, nunca só no front.
     - Cotações e qualquer segredo (chave de serviço, token de provedor) exclusivamente em Edge Functions; no navegador só `VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY`.

  3. **Comandos e Scripts**: tabela com `npm run dev`, `build:css`, `build`, `preview`, `lint`, `format`, `lint:fix` e os comandos da CLI do Supabase (`supabase start`, `db push`, `functions serve`).
  4. **Mapa da Arquitetura e Diretórios**: árvore explicada com `src/lib`, `src/services`, `src/guards`, `src/pages`, `supabase/migrations` e `supabase/functions`.
  5. **Fluxo Spec-Driven Development**: ciclo de 5 passos (consulta no PRD → branch `feat/tkXX-Y-...` → spec via skill em `specs/active/` → implementação e validação → PR via skill e arquivamento em `specs/archived/`).
  6. **Padrão de Commits**: Conventional Commits em inglês com tag de task (`feat: [TK03-5] add rls policies for assets`).
  ```
</Aside>

### TK01-6 · Criar `admin.html` com métricas agregadas

O painel administrativo tem três cartões e uma linha de status dos serviços, e nenhuma tabela.
