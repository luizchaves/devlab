Nível **Intermediário** · HTML · Tailwind CSS · JavaScript modular · Supabase · PostgreSQL · RLS · Deno

O **InvestFlow** é uma plataforma de gestão patrimonial para investidores individuais. Ela começa como um protótipo navegável e evolui, em onze sprints, para uma aplicação BaaS: o Supabase fornece identidade, banco de dados, arquivos privados e funções de servidor, sem introduzir uma API Express intermediária.

<ProjectLinks path="examples/courses/npm/projects/investflow-static" devcontainer="investflow-static" />

## Objetivo do sistema

O **InvestFlow** oferece uma plataforma web de gestão patrimonial em que o navegador fala diretamente com o Supabase: a conta vive no Supabase Auth, a carteira em PostgreSQL com Row Level Security, os comprovantes em um bucket privado e as cotações são atualizadas por uma Edge Function. O objetivo didático é mostrar que "sem back-end próprio" não significa "sem regras no servidor": cada regra que o InvestApp escreveu em um middleware Express aparece aqui como policy, constraint, trigger ou função no banco.

## Leitores e limites

O **InvestFlow** foi projetado para atender a três perfis, e a distinção entre os dois últimos é o que molda a segurança do sistema:

- **Estudantes do Guia de Pacotes**: pessoas que já construíram uma API própria no InvestApp ou no MonitorApp e querem ver o mesmo domínio entregue **sem** servidor intermediário, com identidade, banco, arquivos e funções fornecidos por um BaaS.
- **Investidores individuais**: quem precisa registrar e entender a própria carteira (ativos, transações, comprovantes e rentabilidade), e só a própria.
- **Administração da plataforma**: quem precisa enxergar saúde e volume do serviço (contas, AUM, execução de cotações) sem receber a lista de posições de ninguém.

A tabela resume o que cada perfil de uso pode ver, e é ela que origina os requisitos não funcionais:

| Perfil | Necessidade principal | Limite de acesso |
| ------ | --------------------- | ---------------- |
| Investidor | Registrar ativos, transações, comprovantes e rentabilidade. | Somente os próprios dados e arquivos. |
| Administrador | Acompanhar contas, AUM e execução de serviços. | Métricas agregadas, sem posições individuais. |

Os requisitos completos ficam no [backlog do produto](backlog/), com 11 épicos, 32 histórias de usuário, 111 critérios de aceitação e 94 tasks. Esta visão geral mantém apenas o resumo do domínio, da arquitetura e da trilha de leitura.

## Arquitetura do sistema

O InvestFlow é uma aplicação estática que usa o Supabase como back-end gerenciado. Isso muda o desenho em relação ao InvestApp: não existe uma API Express própria entre o navegador e o banco. O front-end publica HTML, CSS e JavaScript, carrega a chave anônima do projeto e chama diretamente os serviços públicos do Supabase.

A chave anônima identifica o projeto, mas não autoriza acesso irrestrito. Depois do login, o Supabase Auth entrega uma sessão com JWT; esse token acompanha as chamadas ao PostgreSQL e ao Storage. No banco, as policies de Row Level Security leem `auth.uid()` e decidem se aquela linha pertence ao usuário atual. No Storage, as policies seguem a mesma ideia, mas aplicadas aos caminhos dos arquivos privados.

O diagrama abaixo separa três caminhos. O primeiro é o caminho cotidiano do investidor, do navegador para Auth, banco e Storage. O segundo é o caminho operacional das cotações, que passa por uma Edge Function porque precisa de segredos e escrita privilegiada. O terceiro é a leitura administrativa, limitada a views e funções agregadas para não expor posições individuais.

{`

  Admin --> Db
`}
</Mermaid>

Na leitura de carteira, o navegador consulta tabelas como `assets`, `transactions` e `quotes_history` com a chave anônima e o JWT do usuário. A segurança não depende de o JavaScript lembrar de filtrar por `user_id`: mesmo que uma tela errasse a consulta, a policy RLS continuaria bloqueando linhas de outro investidor.

No upload de comprovantes, o navegador também fala com uma API pública, mas os arquivos ficam em um bucket privado. A tabela guarda apenas `receipt_path`; quando o usuário precisa ver o documento, a aplicação pede uma URL assinada de curta duração. Esse detalhe evita transformar um comprovante em link permanente, copiável e difícil de revogar.

Já as cotações ficam fora do navegador por dois motivos. Primeiro, o token do provedor e a chave `service_role` não podem entrar no bundle público. Segundo, atualizar preços exige uma operação idempotente e auditável: a Edge Function chama o provedor, grava o preço no PostgreSQL e registra falhas operacionais sem depender de uma aba aberta pelo usuário.

O painel administrativo fecha a arquitetura com uma fronteira diferente. Ele pode ler métricas como AUM, quantidade de contas e status de execução, mas não deve consultar a carteira completa de ninguém. Por isso o diagrama aponta para uma view administrativa agregada, não para acesso livre às tabelas de domínio.

<Aside type="caution" title="Dica de IA: A chave anônima não substitui RLS">
  A chave pública do projeto pode aparecer no navegador. A segurança vem de policies que usam a identidade presente no JWT, não de esconder essa chave. A `service_role`, por outro lado, ignora RLS e nunca pode entrar em HTML, JavaScript publicado ou variáveis expostas pelo build.

  **Prompt:** *"Revise estas policies RLS para assets e transactions; mostre um cenário em que um usuário A tenta ler ou inserir um registro do usuário B e explique qual cláusula bloqueia cada tentativa."*
</Aside>

## Stack tecnológica da aplicação

O projeto evolui acrescentando um serviço do Supabase por sprint, e nunca um servidor próprio:

| Camada | Tecnologias e bibliotecas |
| ------ | ------------------------- |
| **Front-end** | HTML5 semântico, Tailwind CSS (Play CDN no protótipo, compilado pela CLI da Sprint 2 em diante), JavaScript vanilla em módulos ES e Vite como servidor e build |
| **Identidade** | Supabase Auth (e-mail e senha, JWT, sessão renovada pelo SDK) e `@supabase/supabase-js` |
| **Persistência** | PostgreSQL gerenciado pelo Supabase, migrations SQL versionadas em `supabase/migrations/`, Row Level Security em toda tabela de domínio |
| **Arquivos** | Supabase Storage com bucket privado, policies em `storage.objects` e URLs assinadas |
| **Código de servidor** | Edge Functions em Deno/TypeScript, únicas portadoras da chave de serviço e do token do provedor de cotações |
| **Agendamento** | `pg_cron` e `pg_net` dentro do próprio PostgreSQL |
| **Qualidade** | Biome (lint e formatação), specs por task em `specs/`, template de PR |

## Trilha incremental de desenvolvimento

As sprints seguem uma dependência deliberada: não há policy RLS útil sem identidade, nem analytics honesto antes de transações e cotações. A sequência abaixo é também a ordem sugerida de leitura das páginas.

<Steps>

1. **Frontend estático**: telas, vocabulário visual, navegação e documentação de governança.
2. **Autenticação BaaS**: Supabase Auth, sessão, perfil, guardas de páginas privadas e as três camadas de teste.
3. **Banco de dados e RLS**: migrations, ativos, corretoras, transações, histórico, isolamento no PostgreSQL e a tela de cada investimento.
4. **Cotações com Edge Functions**: atualização idempotente, falhas parciais e operação agendada.
5. **Armazenamento de comprovantes**: bucket privado, paths por usuário e URLs assinadas.
6. **Analytics e painel admin**: matriz de retorno, AUM agregado e autorização administrativa.
7. **Origem e evolução**: treemap por corretora, categoria e emissor, e a linha de aportes versus valor atual por ativo e carteira.
8. **Lançamentos e cotação manual**: editar e excluir lançamentos, renda fixa pelo saldo, cotação por ativo com fallback manual, filtro e ordenação com estado na URL.
9. **Proventos e movimentações**: histórico de proventos por ativo, direito pela data ex, retorno total e o extrato de aportes e resgates.
10. **Dólar e cripto**: moeda por ativo, tabela de câmbio, cripto cotada em dólar e o calendário de mercado.
11. **Perfil e experiência**: avatar, barra de navegação comum, tema, ocultação de valores e o build publicado.

</Steps>

As Sprints 1 a 7 têm um projeto executável cada; as Sprints 8 a 11 evoluem o mesmo `investflow-origins`, que é o projeto final. A separação entre elas é feita pelos critérios de aceitação numerados por sprint e pelos testes que os citam.

## Resumo comparativo das sprints

Como no InvestApp e no MonitorApp, cada uma das sete primeiras sprints é uma pasta em `examples/courses/npm/projects/`, cópia da anterior mais o delta. As quatro últimas acrescentam camadas ao mesmo `investflow-origins`. A lista abaixo resume o projeto, o serviço principal e a novidade de cada etapa sem forçar uma tabela larga.

1. **Frontend estático** (`investflow-static`): telas em HTML e Tailwind CSS, ainda sem Supabase. Estado: versionada.
2. **Autenticação BaaS** (`investflow-auth`): Supabase Auth, `profiles`, grants, trigger, sessão e guardas de página. Estado: versionada e testada, com 15 Vitest e 4 Playwright.
3. **Banco de dados e RLS** (`investflow-database`): PostgreSQL, migrations, RLS, `assets`, `brokers`, `transactions`, `quotes_history` e tela do investimento. Estado: versionada e testada, com 36 Vitest e 8 Playwright.
4. **Cotações com Edge Functions** (`investflow-edge-quotes`): `update-quotes`, `pg_cron`, idempotência e chave de serviço fora do navegador. Estado: versionada e testada, com 48 Vitest e 9 Playwright.
5. **Armazenamento de comprovantes** (`investflow-storage`): bucket privado, policies em `storage.objects`, path por dono e URL assinada. Estado: versionada e testada, com 63 Vitest e 11 Playwright.
6. **Analytics e painel admin** (`investflow-analytics`): views, funções, `security_invoker`, `security definer`, matriz de rentabilidade e métricas agregadas. Estado: versionada e testada, com 79 Vitest e 14 Playwright.
7. **Origem e evolução** (`investflow-origins`): treemap por corretora, categoria e emissor, além da linha de aportes versus valor. Estado: versionada e testada.
8. **Lançamentos e cotação manual** (`investflow-origins`): escrita do dono em `quotes_history`, lançamentos editáveis, renda fixa por saldo e filtros na URL. Estado: versionada e testada.
9. **Proventos e movimentações** (`investflow-origins`): `dividends_history`, RLS pelo dono do ativo, retorno total e extrato de aportes e resgates. Estado: versionada e testada.
10. **Dólar e cripto** (`investflow-origins`): `exchange_rates`, câmbio por data, carteira consolidada em reais, cripto via `BRL=X` e calendário de mercado. Estado: versionada e testada.
11. **Perfil e experiência** (`investflow-origins`): avatar público, atualização controlada de perfil, barra comum, tema, ocultação de valores e deploy. Estado: versionada e testada, com 216 Vitest e 33 Playwright acumulados.

## Evolução incremental do projeto

<Aside type="tip" title="O trilho é cumulativo por construção">
  Cada pasta de sprint nasce como cópia da anterior mais o delta daquela sprint. Nada que foi
  introduzido desaparece depois: as telas da Sprint 1 não são reescritas, recebem módulos; as
  policies da Sprint 3 não são refeitas na 5, o Storage ganha as suas no mesmo desenho. As duas
  únicas substituições são explicadas na própria página: o `action="./dashboard.html"` dos
  formulários dá lugar ao SDK na Sprint 2, e o Tailwind pelo Play CDN dá lugar ao compilado.
</Aside>

Cada página de sprint mostra a árvore de arquivos, os trechos reais via `<SourceCode>`, os testes e o comando de execução daquela etapa. O índice fica apenas com a regra geral: as pastas são cumulativas até a Sprint 7, e as Sprints 8 a 11 evoluem o mesmo projeto final.

## Execução local

Cada página de sprint aponta para uma pasta em `examples/courses/npm/projects/`. A Sprint 1 só precisa do Vite; da Sprint 2 em diante, a stack local do Supabase (Docker e a CLI) substitui um projeto na nuvem:

```bash title="Terminal"
cd examples/courses/npm/projects/investflow-auth
pnpm install
pnpm db:start
pnpm db:reset
pnpm dev
```

<Aside type="caution" title="Stack local ou projeto na nuvem">
  Os testes das sprints rodam contra `supabase start`. Para usar um projeto em
  [supabase.com](https://supabase.com/), copie apenas a URL e a chave anônima para o `.env`
  (`VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY`) e aplique as migrations com `supabase db push`.
  A chave de serviço e o token do provedor de cotações entram só nos segredos das Edge Functions.
</Aside>
