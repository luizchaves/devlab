O backlog do **InvestFlow** transforma a ideia de uma plataforma financeira em trabalho
executável. Ele conecta requisitos de produto a telas, tabelas, policies RLS, buckets,
Edge Functions, métricas administrativas e validações manuais.

## Como ler este backlog?

Use esta página como mapa de execução da trilha. Cada requisito diz o que o produto precisa fazer,
cada épico agrupa uma capacidade, cada história explica a necessidade do usuário e cada task aponta
uma entrega técnica pequena o suficiente para revisão, provada por um teste com o id do critério.

```txt title="Fluxo de planejamento"
Requisito (RF/RNF) -> Épico -> Feature -> História de usuário -> Critério de aceite -> Sprint -> Task -> Teste
```

## Objetivo

Compreender o escopo funcional e técnico do InvestFlow, decompondo a aplicação em sprints e
tasks cumulativas que mantêm rastreabilidade entre produto, documentação e implementação.

Ao final do tópico, o leitor deve ser capaz de:

- Relacionar cada épico do produto a uma etapa da trilha InvestFlow.
- Identificar quais tasks constroem interface, autenticação, banco, storage, analytics, operação, proventos, câmbio e experiência.
- Explicar por que RLS, Edge Functions e Storage precisam aparecer no backlog, não só no código.
- Planejar uma sprint usando critérios de aceite e validações objetivas.
- Revisar se uma task está pequena, testável e conectada a uma história de usuário.

## Requisitos

Os requisitos são a origem de cada história: uma história sem requisito é uma feature que ninguém
pediu, e um requisito sem história é uma promessa sem entrega. Os requisitos funcionais (RF) dizem
o que o sistema faz; os não funcionais (RNF) dizem as regras que valem em qualquer tela. A coluna
da direita aponta as histórias que os realizam.

### Requisitos não funcionais (RNF)

Cada RNF vale em toda tela; a coluna de histórias aponta onde ele é provado por teste.

| Código | Regra | Consequência prática | Histórias |
| ------ | ----- | -------------------- | --------- |
| RNF01 | RLS em toda tabela de domínio. | Um filtro esquecido no front não vaza carteira. | US04, US06, US21, US29 |
| RNF02 | Chaves privadas fora do navegador. | A `service_role` fica apenas em Edge Functions e nos testes. | US07, US27 |
| RNF03 | Dados monetários com precisão decimal. | Saldo e preço em `numeric`, nunca em ponto flutuante binário. | US05, US25 |
| RNF04 | Arquivos privados em bucket privado. | Comprovante lido por policy e URL assinada curta; avatar público por escolha. | US08, US29 |
| RNF05 | Administração agregada e autorizada. | O painel não consulta posições de investidores. | US10 |
| RNF06 | Front publicável só com variáveis públicas. | O bundle leva `VITE_*` e cabeçalhos de segurança; nada de chave de serviço. | US32 |

## Rastreabilidade

A tabela liga cada **história de usuário (US)** aos **critérios de aceitação (CA)** escritos em
Gherkin na página da sprint e às **tasks (TK)** do `docs/SPRINTS.md`. O critério é numerado pela
sprint (`CA03.4` é o quarto critério da Sprint 3), e a task também (`TK03-4` é a quarta task da
Sprint 3); os dois números não coincidem, porque uma sprint entrega mais de uma história. Cada
critério tem pelo menos um teste automatizado com o mesmo id no nome (`it('CA09.3: …')`), e é
essa ligação, e não a descrição da task, que diz se a entrega está pronta.

## Histórias de usuário

### US01 · Simular crescimento patrimonial · RF01

Entregue pela [Sprint 1 (Frontend estático)](../front-static/).

> **Como** investidor iniciante,
> **quero** simular aportes e prazo de investimento,
> **para** entender o efeito dos juros compostos antes de criar uma conta.

##### Critérios de Aceitação

- **CA01.1** — `pnpm dev` abre a landing com o simulador e os links de navegação, sem nenhum projeto Supabase.
- **CA01.2** — O simulador traz valor inicial, aporte mensal e prazo, com `id` estáveis e valores apresentados como exemplo, não como recomendação.

## Planejamento de sprints

As sprints abaixo organizam todas as tasks necessárias para evoluir o protótipo estático até uma
aplicação BaaS completa. A validação indicada em cada task é o mínimo esperado antes de mover a
entrega para pronta. As Sprints 1 a 7 têm um projeto executável cada (`investflow-static` a
`investflow-origins`); as Sprints 8 a 11 evoluem o mesmo `investflow-origins`, que é o projeto
final da trilha.

## Perguntas de revisão

### Backlog e execução

1. **Por que uma task precisa apontar uma validação objetiva?**

   <details>
     <summary>Possível resposta</summary>

     Porque a validação define como a equipe reconhece que a entrega funciona. Sem isso, a revisão
     depende de interpretação e a task pode parecer pronta mesmo sem cumprir a história.
   </details>

2. **Qual é a diferença entre a Sprint 1 e as sprints BaaS seguintes?**

   <details>
     <summary>Possível resposta</summary>

     A Sprint 1 cria o contrato visual estático. As sprints seguintes conectam esse contrato a
     autenticação, banco, RLS, funções, Storage e dados reais.
   </details>

3. **Por que as Sprints 8 a 11 não ganharam um projeto executável cada?**

   <details>
     <summary>Possível resposta</summary>

     Porque elas não trocam a arquitetura: acrescentam tabelas, regras e telas ao mesmo projeto.
     Copiar o projeto quatro vezes multiplicaria código idêntico sem ensinar nada novo; a
     rastreabilidade por CA e o nome dos testes fazem o papel de separar o que cada sprint entregou.
   </details>

### Segurança e privacidade

4. **Por que RLS aparece como task explícita, e não como detalhe de implementação?**

   <details>
     <summary>Possível resposta</summary>

     Porque isolamento por investidor é requisito central do produto. Se as policies não forem
     criadas e testadas, o sistema não atende à promessa de privacidade financeira.
   </details>

5. **Por que o painel admin deve usar métricas agregadas?**

   <details>
     <summary>Possível resposta</summary>

     Porque administração operacional não exige acesso irrestrito a posições individuais. Métricas
     agregadas reduzem exposição de dados sensíveis e mantêm coerência com a arquitetura segura.
   </details>
