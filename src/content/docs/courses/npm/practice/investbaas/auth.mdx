Etapa **2 de 6** · Nível **Intermediário** · Supabase Auth · JWT · Sessão · Perfil

A Sprint 1 desenhou as telas de entrada; esta etapa torna a identidade real. O Supabase Auth cria a conta, entrega uma sessão e assina o JWT. O front-end usa a chave anônima do projeto, mas as decisões de autorização ficam para o banco na próxima sprint.

<Aside type="note" title="Tópicos conceituais associados">
  Esta etapa combina [pacotes npm](../../../) com os conceitos de [autenticação](../../../../expressjs/auth/authentication/) e [autorização](../../../../expressjs/auth/authorization/).
</Aside>

## Objetivo

Integrar identidade e sessão ao protótipo sem expor privilégios do ambiente BaaS. Ao final da etapa, o leitor deve ser capaz de:

- Explicar o papel de `auth.users`, profile, JWT e sessão.
- Implementar cadastro, entrada, saída e guarda de páginas privadas.
- Separar a chave anônima pública de segredos que nunca pertencem ao navegador.

### US03 · Criar conta e entrar · RF02

> **Como** investidor,
> **quero** criar uma conta e entrar com e-mail e senha,
> **para** ter uma identidade estável antes de registrar minha carteira.

```gherkin
Cenário: CA02.1 - Cadastro válido
  Quando envio nome, e-mail e senha válidos pelo formulário
  Então o Supabase Auth cria o usuário
  E um profile é criado com o mesmo identificador

Cenário: CA02.2 - Login válido e inválido
  Quando entro com credenciais válidas
  Então recebo uma sessão com access token
  Mas quando uso credenciais inválidas
  Então a interface informa a falha sem revelar qual campo está cadastrado

Cenário: CA02.3 - Recuperação de sessão
  Dado que já entrei no sistema
  Quando recarrego dashboard.html
  Então a sessão é recuperada pelo SDK
  E a tela não redireciona para signin.html
```

### US04 · Proteger telas privadas · RF02, RNF01

> **Como** investidor,
> **quero** ser direcionado ao login ao abrir uma tela privada sem sessão,
> **para** não confundir uma interface disponível com acesso autorizado.

```gherkin
Cenário: CA02.4 - Guarda de página
  Dado que não existe sessão ativa
  Quando abro dashboard.html, analytics.html ou admin.html
  Então sou redirecionado para signin.html

Cenário: CA02.5 - Logout
  Dado que tenho uma sessão ativa
  Quando escolho sair
  Então o SDK encerra a sessão
  E uma nova abertura de página privada exige login
```

### Tasks da etapa

As tasks mantêm a chave de projeto em um único módulo e separam evento de formulário de regra de sessão. Essa organização permite substituir o HTML estático sem espalhar configuração sensível.

## O que muda nesta etapa?

A Sprint 1 desenhou `signin.html` e `signup.html` com `action="./dashboard.html"`: o formulário "entra" navegando para a carteira, sem conferir nada. Esta etapa troca essa navegação por uma sessão real e passa a exigir a sessão em toda página privada.

| Antes (Sprint 1) | Agora (Sprint 2) |
| ---------------- | ---------------- |
| `<form action="./dashboard.html">` | `form.onsubmit` chamando `signInWithPassword()` |
| Cadastro sem efeito | `signUp()` cria a conta em `auth.users` e um `profile` |
| Qualquer página abre direto do disco | `requireSession()` redireciona para `signin.html` sem sessão |
| Nenhum módulo JavaScript | `src/lib/supabase-client.js`, `src/services/auth.js` e `src/guards/require-session.js` |
| Nenhuma dependência | `@supabase/supabase-js` no `package.json` |
| Nenhuma variável de ambiente | `VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY` |

<Aside type="note" title="O código desta etapa é o alvo, não o repositório">
  Os trechos abaixo mostram o que cada task escreve quando a sprint for executada sobre o
  `investbaas-static`. Eles não vêm de arquivos de `examples/`, e por isso não têm caminho de
  arquivo no título. A [Sprint 1](../front-static/) é a única com código versionado.
</Aside>

## Descrição das tarefas

Abaixo estão detalhadas as tarefas de implementação desta etapa, com orientações e os trechos de código que cada uma produz.

### TK02-1 · Criar o cliente Supabase (URL e chave anônima)

O SDK é instalado como dependência do Vite. Nada de `<script src>` de CDN: o módulo entra no `package.json` e é resolvido pelo build, o que permite trocar a versão em um lugar só.

```bash title="Terminal"
pnpm add @supabase/supabase-js
```

O cliente é criado uma vez e importado por todo mundo. As duas variáveis vêm de `import.meta.env`, e o prefixo `VITE_` é o que autoriza o Vite a embuti-las no bundle: é a marca de "público". Uma variável sem o prefixo nunca chega ao navegador, e é assim que um `SUPABASE_SERVICE_ROLE_KEY` colocado por engano no `.env` continua fora do HTML publicado.

```js title="Cliente único do Supabase (alvo de src/lib/supabase-client.js)"
import { createClient } from '@supabase/supabase-js';

const url = import.meta.env.VITE_SUPABASE_URL;
const anonKey = import.meta.env.VITE_SUPABASE_ANON_KEY;

if (!url || !anonKey) {
  throw new Error('Defina VITE_SUPABASE_URL e VITE_SUPABASE_ANON_KEY no .env');
}

// A chave anonima identifica o projeto; quem limita o acesso e o RLS da Sprint 3.
export const supabase = createClient(url, anonKey);
```

O `.env.example` documenta as duas variáveis e nada mais. Ele é versionado; o `.env` real fica no `.gitignore`, como já acontece nas trilhas do InvestApp e do MonitorApp.

```ini title=".env.example (alvo)"
VITE_SUPABASE_URL=https://<projeto>.supabase.co
VITE_SUPABASE_ANON_KEY=<chave anonima do projeto>
```

### TK02-2 · Implementar o cadastro (`signUp`)

O `signUp` recebe e-mail, senha e, em `options.data`, os metadados que o Supabase grava em `raw_user_meta_data`. É de lá que a trigger da TK02-6 vai copiar o nome para `profiles`. O serviço devolve `{ data, error }` em vez de lançar: a decisão de como mostrar o erro fica com a tela.

```js title="Serviço de conta (alvo de src/services/auth.js)"
import { supabase } from '../lib/supabase-client.js';

export async function signUp({ fullName, email, password }) {
  return supabase.auth.signUp({
    email,
    password,
    options: { data: { full_name: fullName } },
  });
}
```

Em `signup.html` o `action` sai e entra um módulo. Os campos já tinham `id` desde a Sprint 1, então o script só lê e envia. Com a confirmação de e-mail ligada no projeto Supabase, o cadastro não devolve sessão: a tela avisa para conferir a caixa de entrada e leva para o login.

```js title="Envio do formulário de cadastro (alvo de src/pages/signup.js)"
import { signUp } from '../services/auth.js';

const form = document.querySelector('form');

form.addEventListener('submit', async (event) => {
  event.preventDefault();

  const { error } = await signUp({
    fullName: form.elements.fullName.value,
    email: form.elements.email.value,
    password: form.elements.password.value,
  });

  if (error) {
    return showError(form, error.message);
  }

  window.location.href = './signin.html?registered=1';
});
```

### TK02-3 · Implementar o login (`signInWithPassword`)

O login segue o mesmo desenho. A diferença está no erro: e-mail inexistente e senha errada voltam como o **mesmo** `AuthApiError` (`Invalid login credentials`), e a tela repete essa indistinção. Traduzir para "e-mail não encontrado" entregaria a lista de contas a quem tentasse de fora.

```js title="Login e a mensagem única (alvo de src/pages/signin.js)"
import { signIn } from '../services/auth.js';

form.addEventListener('submit', async (event) => {
  event.preventDefault();

  const { error } = await signIn({
    email: form.elements.email.value,
    password: form.elements.password.value,
  });

  if (error) {
    // A mesma frase para e-mail inexistente e senha errada.
    return showError(form, 'E-mail ou senha invalidos');
  }

  window.location.href = './dashboard.html';
});
```

A sessão devolvida pelo `signInWithPassword` é guardada pelo SDK no `localStorage`, sob a chave `sb-<projeto>-auth-token`, e renovada sozinha antes de expirar. O front não toca no JWT: ele pede ao SDK, e o SDK anexa o `Authorization: Bearer` em cada chamada ao banco e ao Storage.

### TK02-4 · Criar a guarda de sessão (`requireSession`)

`dashboard.html`, `analytics.html` e `admin.html` importam a guarda antes de qualquer outro módulo. Sem sessão, a página redireciona e o resto do script nem executa. A guarda é uma cortesia de interface, e a página deixa isso claro: quem impede uma consulta de outra conta é o RLS da Sprint 3, não este `if`.

```js title="Guarda das paginas privadas (alvo de src/guards/require-session.js)"
import { supabase } from '../lib/supabase-client.js';

export async function requireSession() {
  const { data } = await supabase.auth.getSession();

  if (!data.session) {
    window.location.replace('./signin.html');
    // A promessa nunca resolve: o resto da pagina nao roda sem sessao.
    return new Promise(() => {});
  }

  return data.session;
}
```

```html title="Uso da guarda no topo de uma pagina privada"
<script type="module">
  import { requireSession } from './src/guards/require-session.js';

  const session = await requireSession();
  document.querySelector('#user-email').textContent = session.user.email;
</script>
```

### TK02-5 · Implementar sessão, logout e e-mail do usuário

O botão "Sair" chama `signOut()`, que apaga a sessão do `localStorage` e revoga o *refresh token* no servidor. O `onAuthStateChange` cobre a outra ponta: se a sessão acabar em outra aba, ou o token for revogado, a página privada volta ao login sem esperar um clique.

```js title="Logout e reacao a mudanca de sessao (alvo de src/services/auth.js)"
export function signOut() {
  return supabase.auth.signOut();
}

export function onSessionEnd(callback) {
  return supabase.auth.onAuthStateChange((event) => {
    if (event === 'SIGNED_OUT') callback();
  });
}
```

### TK02-6 · Criar `profiles` vinculada a `auth.users`

`auth.users` pertence ao Supabase e não recebe colunas de domínio. Nome de exibição e papel (`investor` ou `admin`) moram em `public.profiles`, com o **mesmo** `id`. A trigger copia o `full_name` dos metadados do cadastro, então a tela não precisa de uma segunda chamada para criar o perfil, e o RLS já nasce ligado: cada pessoa lê e edita apenas a própria linha.

```sql title="Migration de profiles (alvo de supabase/migrations/0001_profiles.sql)"
create table public.profiles (
  id uuid primary key references auth.users (id) on delete cascade,
  full_name text not null,
  role text not null default 'investor' check (role in ('investor', 'admin')),
  created_at timestamptz not null default now()
);

alter table public.profiles enable row level security;

create policy "profiles: dono le" on public.profiles
  for select using (auth.uid() = id);

create policy "profiles: dono edita" on public.profiles
  for update using (auth.uid() = id) with check (auth.uid() = id);

create function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  insert into public.profiles (id, full_name)
  values (new.id, coalesce(new.raw_user_meta_data ->> 'full_name', new.email));
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

`security definer` é o que permite à trigger inserir em `profiles` mesmo sem policy de `insert`: ela roda com os privilégios de quem a criou, não com os do usuário que acabou de se cadastrar. O `set search_path` fecha a brecha clássica dessa opção, que é um objeto homônimo em outro schema desviando a função.

## Fluxo de autenticação

Autenticação identifica a pessoa; autorização decide o que ela pode consultar. Nesta etapa o JWT prepara a segunda parte, mas RLS é a camada que efetivamente limita linhas de banco na Sprint 3.

<Mermaid title="Cadastro, sessão e acesso a páginas privadas">
{`
sequenceDiagram
  actor Investor as Investidor
  participant UI as Front-end
  participant Auth as Supabase Auth
  participant Profile as profiles
  Investor->>UI: Envia cadastro ou login
  UI->>Auth: signUp ou signInWithPassword
  Auth-->>UI: user + session (JWT)
  Auth->>Profile: trigger cria profile no cadastro
  Investor->>UI: Abre dashboard
  UI->>Auth: getSession()
  Auth-->>UI: sessão ativa ou nula
  UI-->>Investor: página privada ou redirecionamento
`}
</Mermaid>

## Limites e decisões da etapa

A tabela separa o que pertence à sessão do que ainda depende da modelagem de carteira. Isso evita usar o estado da interface como substituto de regras de banco.

| Entra na Sprint 2 | Fica para a Sprint 3 |
| ----------------- | -------------------- |
| Usuário, sessão, JWT e profile. | `assets`, `transactions` e `quotes_history`. |
| Guarda de navegação no navegador. | Policies RLS nas tabelas de domínio. |
| Chave anônima pública. | `service_role` limitada ao ambiente de Edge Function. |
| Logout e recuperação de sessão. | Listagem real da carteira. |

<Aside type="caution" title="Dica de IA: Confirme o tipo da chave antes de publicar">
  Um assistente pode sugerir `SUPABASE_SERVICE_ROLE_KEY` no cliente para resolver um erro de permissão. Isso remove a proteção de RLS para qualquer pessoa que abra as ferramentas do navegador.

  **Prompt:** *"Examine estas variáveis usadas pelo front-end do InvestBaaS; classifique cada uma como pública ou secreta e recuse qualquer solução que coloque service_role, senha de banco ou token de provedor no bundle."*
</Aside>

## Testando

Sem uma API própria, os testes desta etapa acontecem em dois lugares: no navegador, pelas telas, e no painel do Supabase, pelas tabelas. Cada item abaixo prova um critério da seção de requisitos.

| Verificação | Como fazer | Critério |
| ----------- | ---------- | -------- |
| Cadastro cria conta e perfil | Cadastre `ana@example.com`; em **Authentication › Users** o usuário aparece, e em **Table Editor › profiles** existe uma linha com o mesmo `id` e o nome informado | CA02.1 |
| Login válido e inválido | Entre com a senha certa e chegue ao `dashboard.html`; repita com senha errada e com um e-mail que não existe: a mensagem é a mesma nas duas falhas | CA02.2 |
| Recuperação de sessão | Com a sessão aberta, recarregue `dashboard.html`: a página fica, e o e-mail aparece no cabeçalho | CA02.3 |
| Guarda de página | Em uma janela anônima, abra `dashboard.html`, `analytics.html` e `admin.html`: as três redirecionam para `signin.html` | CA02.4 |
| Logout | Clique em **Sair** e volte a `dashboard.html`: o redirecionamento acontece de novo | CA02.5 |
| Só valores públicos no bundle | Rode `pnpm build` e procure a chave de serviço no resultado: `grep -r service_role dist/` não encontra nada | RNF02 |

O `localStorage` mostra o que o SDK guarda. Depois do login, a chave `sb-<projeto>-auth-token` contém `access_token`, `refresh_token` e `expires_at`; é esse objeto que `getSession()` lê na recarga da página.
