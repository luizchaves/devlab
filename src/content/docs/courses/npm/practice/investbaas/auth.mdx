Etapa **2 de 7** · Nível **Intermediário** · Supabase Auth · JWT · Sessão · Perfil

A Sprint 1 desenhou as telas de entrada; esta etapa torna a identidade real. O Supabase Auth cria a conta, entrega uma sessão e assina o JWT. O front-end usa a chave anônima do projeto, mas as decisões de autorização ficam para o banco na próxima sprint.

<Aside type="note" title="Tópicos conceituais associados">
  Esta etapa combina [pacotes npm](../../../) com os conceitos de [autenticação](../../../../expressjs/auth/authentication/) e [autorização](../../../../expressjs/auth/authorization/).
</Aside>

## Objetivo

Integrar identidade e sessão ao protótipo sem expor privilégios do ambiente BaaS. Ao final da etapa, o leitor deve ser capaz de:

- Explicar o papel de `auth.users`, profile, JWT e sessão.
- Implementar cadastro, entrada, saída e guarda de páginas privadas.
- Separar a chave anônima pública de segredos que nunca pertencem ao navegador.

### US03 · Criar conta e entrar · RF02

> **Como** investidor,
> **quero** criar uma conta e entrar com e-mail e senha,
> **para** ter uma identidade estável antes de registrar minha carteira.

```gherkin
Cenário: CA02.1 - Cadastro válido
  Quando envio nome, e-mail e senha válidos pelo formulário
  Então o Supabase Auth cria o usuário
  E um profile é criado com o mesmo identificador

Cenário: CA02.2 - Login válido e inválido
  Quando entro com credenciais válidas
  Então recebo uma sessão com access token
  Mas quando uso credenciais inválidas
  Então a interface informa a falha sem revelar qual campo está cadastrado

Cenário: CA02.3 - Recuperação de sessão
  Dado que já entrei no sistema
  Quando recarrego dashboard.html
  Então a sessão é recuperada pelo SDK
  E a tela não redireciona para signin.html
```

### US04 · Proteger telas privadas · RF02, RNF01

> **Como** investidor,
> **quero** ser direcionado ao login ao abrir uma tela privada sem sessão,
> **para** não confundir uma interface disponível com acesso autorizado.

```gherkin
Cenário: CA02.4 - Guarda de página
  Dado que não existe sessão ativa
  Quando abro dashboard.html, analytics.html ou admin.html
  Então sou redirecionado para signin.html

Cenário: CA02.5 - Logout
  Dado que tenho uma sessão ativa
  Quando escolho sair
  Então o SDK encerra a sessão
  E uma nova abertura de página privada exige login
```

## O que muda nesta etapa?

A Sprint 1 desenhou `signin.html` e `signup.html` com `action="./dashboard.html"`: o formulário "entra" navegando para a carteira, sem conferir nada. Esta etapa troca essa navegação por uma sessão real e passa a exigir a sessão em toda página privada.

| Antes (Sprint 1) | Agora (Sprint 2) |
| ---------------- | ---------------- |
| `<form action="./dashboard.html">` | `form.onsubmit` chamando `signInWithPassword()` |
| Cadastro sem efeito | `signUp()` cria a conta em `auth.users` e um `profile` |
| Qualquer página abre direto do disco | `requireSession()` redireciona para `signin.html` sem sessão |
| Nenhum módulo JavaScript | `src/lib/supabase-client.js`, `src/services/auth.js` e `src/guards/require-session.js` |
| Nenhuma dependência | `@supabase/supabase-js` no `package.json` |
| Nenhuma variável de ambiente | `VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY` |

<Aside type="note" title="Um projeto por sprint">
  Como nas trilhas do Express.js, cada sprint é uma pasta em `examples/`: `investbaas-auth` é a
  cópia de `investbaas-static` mais o delta desta página. Comparar as duas com
  `git diff --no-index` mostra exatamente o que a sprint acrescentou.
</Aside>

### TK02-6 · Criar `profiles` vinculada a `auth.users`

`auth.users` pertence ao Supabase e não recebe colunas de domínio. Nome de exibição e papel (`investor` ou `admin`) moram em `public.profiles`, com o **mesmo** `id`. A migration é aplicada por `supabase db reset` na stack local e por `supabase db push` na nuvem.

<SourceCode

A segurança da tabela tem **duas camadas**, e as duas são explícitas nesta versão do Supabase: uma tabela nova não concede `select` nem `update` a ninguém. O `grant` decide quais operações e quais **colunas** cada papel alcança; a policy RLS decide quais **linhas**. O grant por coluna é o detalhe que importa: sem ele, a policy de `update` da própria linha deixaria qualquer conta escrever `role = 'admin'` em si mesma pelo SDK.

## Fluxo de autenticação

Autenticação identifica a pessoa; autorização decide o que ela pode consultar. Nesta etapa o JWT prepara a segunda parte, mas RLS é a camada que efetivamente limita linhas de banco na Sprint 3.

<Mermaid title="Cadastro, sessão e acesso a páginas privadas">
{`
sequenceDiagram
  actor Investor as Investidor
  participant UI as Front-end
  participant Auth as Supabase Auth
  participant Profile as profiles
  Investor->>UI: Envia cadastro ou login
  UI->>Auth: signUp ou signInWithPassword
  Auth-->>UI: user + session (JWT)
  Auth->>Profile: trigger cria profile no cadastro
  Investor->>UI: Abre dashboard
  UI->>Auth: getSession()
  Auth-->>UI: sessão ativa ou nula
  UI-->>Investor: página privada ou redirecionamento
`}

## Limites e decisões da etapa

A tabela separa o que pertence à sessão do que ainda depende da modelagem de carteira. Isso evita usar o estado da interface como substituto de regras de banco.

| Entra na Sprint 2 | Fica para a Sprint 3 |
| ----------------- | -------------------- |
| Usuário, sessão, JWT e profile. | `assets`, `transactions` e `quotes_history`. |
| Guarda de navegação no navegador. | Policies RLS nas tabelas de domínio. |
| Chave anônima pública. | `service_role` limitada ao ambiente de Edge Function. |
| Logout e recuperação de sessão. | Listagem real da carteira. |

<Aside type="caution" title="Dica de IA: Confirme o tipo da chave antes de publicar">
  Um assistente pode sugerir `SUPABASE_SERVICE_ROLE_KEY` no cliente para resolver um erro de permissão. Isso remove a proteção de RLS para qualquer pessoa que abra as ferramentas do navegador.

  **Prompt:** *"Examine estas variáveis usadas pelo front-end do InvestBaaS; classifique cada uma como pública ou secreta e recuse qualquer solução que coloque service_role, senha de banco ou token de provedor no bundle."*
</Aside>

## Executando

A stack local do Supabase roda em Docker e substitui um projeto na nuvem para tudo que esta sprint precisa.

<Steps>

1. Entre no projeto e instale as dependências:

   ```bash title="Terminal"
   cd examples/courses/npm/projects/investbaas-auth
   pnpm install
   ```

2. Suba a stack local e copie os valores para o `.env` (o `.env.example` diz quais):

   ```bash title="Terminal"

   supabase status -o env
   ```

3. Aplique a migration de `profiles`:

   ```bash title="Terminal"
   pnpm db:reset
   ```

4. Suba o Vite e abra `http://localhost:5173/signup.html`:

   ```bash title="Terminal"
   pnpm dev
   ```

5. Rode as suítes (o Playwright pede `pnpm exec playwright install chromium` na primeira vez):

   ```bash title="Terminal"
   pnpm test
   pnpm test:e2e
   ```

</Steps>

O Studio local fica em `http://127.0.0.1:54323`: em **Authentication › Users** aparecem as contas criadas, e em **Table Editor › profiles** as linhas que a trigger gerou.
