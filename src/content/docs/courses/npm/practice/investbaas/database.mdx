Etapa **3 de 7** · Nível **Avançado** · PostgreSQL · Migrations · RLS · Dados financeiros

Com uma identidade estável, o InvestBaaS pode registrar a carteira. Esta etapa modela fatos que precisam sobreviver ao tempo, como compra, venda e preço diário. Ela também transfere a regra "cada pessoa vê apenas o que é seu" da interface para o PostgreSQL.

## Objetivo

Modelar a carteira como dados relacionais auditáveis e protegidos no ponto de persistência. Ao final da etapa, o leitor deve ser capaz de:

- Distinguir ativo, transação e cotação como fatos com responsabilidades diferentes.
- Planejar migrations com integridade referencial e precisão decimal.
- Derivar policies RLS de leitura e escrita a partir de `auth.uid()`.

## Modelo de dados

O ativo descreve o instrumento que está na carteira; a transação registra um evento imutável da história; a cotação registra um preço observado. Essa separação permite recalcular qualquer métrica sem sobrescrever a origem do dado.

<Mermaid title="Relações e donos das tabelas de domínio">
{`
erDiagram
  PROFILE ||--o{ ASSET : owns
  ASSET ||--o{ TRANSACTION : has
  ASSET ||--o{ QUOTE_HISTORY : has
  PROFILE ||--o{ TRANSACTION : owns
  PROFILE { uuid id PK string role }
  ASSET { uuid id PK uuid user_id FK string ticker string category numeric current_price }
  TRANSACTION { uuid id PK uuid user_id FK uuid asset_id FK string type numeric quantity numeric price date transaction_date }
  QUOTE_HISTORY { uuid id PK uuid asset_id FK numeric price date quote_date }
`}
</Mermaid>

Para valores de dinheiro, use `numeric`, não `real` ou `double precision`. Quantidade também pode precisar de casas decimais, especialmente para frações de criptoativos e fundos.

## O que muda nesta etapa?

A carteira deixa de ser cinco linhas escritas no HTML e passa a vir de tabelas que só devolvem o que pertence a quem chama. A mudança de fora é pequena (a tabela parece a mesma); a de dentro é a maior da trilha.

| Antes (Sprint 2) | Agora (Sprint 3) |
| ---------------- | ---------------- |
| Cinco posições escritas em `dashboard.html` | Linhas geradas a partir de `assets` e `transactions` |
| Só a tabela `profiles` | `+ assets`, `transactions` e `quotes_history` |
| Botão **+ Novo Ativo** sem efeito | Formulário que insere pelo SDK e recarrega a lista |

## Descrição das tarefas

Abaixo estão detalhadas as tarefas de implementação desta etapa, com orientações e os trechos de código que cada uma produz.

### TK03-1 · Criar a migration de `assets`

O ativo é o instrumento que está na carteira: um ticker, um nome, uma categoria e o preço mais recente. As cinco categorias são as mesmas que a Sprint 1 desenhou como *badges*, e o `check` é o que impede um sexto valor de entrar por qualquer caminho, inclusive pelo SQL Editor. `numeric(14, 4)` guarda quatro casas para o preço, porque um FII pode ser negociado a `R$ 9,8750`; `real` e `double precision` não representam esse valor com exatidão.

```sql title="Migration de assets (alvo de supabase/migrations/0002_assets.sql)"
create table public.assets (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles (id) on delete cascade,
  ticker text not null,
  name text not null,
  category text not null
    check (category in ('renda_fixa', 'acoes', 'fiis', 'fundos', 'cripto')),
  current_price numeric(14, 4),
  created_at timestamptz not null default now(),
  unique (user_id, ticker)
);
```

O `unique (user_id, ticker)` segue a regra que a TaskAPI e o InvestApp já usam para o título: único **por dono**, não no sistema inteiro. Duas contas podem ter `PETR4`; a mesma conta, não.

### TK03-2 · Criar a migration de `transactions`

A transação é um fato: aconteceu uma compra ou uma venda, de tanta quantidade, a tanto, em tal dia. Ela nunca é editada para "corrigir" a posição; um erro vira outra transação. É essa imutabilidade que torna a carteira auditável e permite recalcular qualquer métrica a partir da origem.

```sql title="Migration de transactions (alvo de supabase/migrations/0003_transactions.sql)"
create table public.transactions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles (id) on delete cascade,
  asset_id uuid not null references public.assets (id) on delete cascade,
  type text not null check (type in ('buy', 'sell')),
  quantity numeric(18, 8) not null check (quantity > 0),
  price numeric(14, 4) not null check (price >= 0),
  transaction_date date not null default current_date,
  receipt_path text,
  created_at timestamptz not null default now()
);
```

`user_id` aparece de novo, mesmo já existindo em `assets`. É redundância de propósito: a policy RLS da TK03-5 compara `auth.uid()` com uma coluna da **própria** tabela, sem `join`, o que a torna mais simples de ler e mais barata de executar. `receipt_path` fica vazio até a Sprint 5.

### TK03-3 · Criar a migration de `quotes_history`

Uma linha por ativo e por dia. A chave `unique (asset_id, quote_date)` é o que torna a atualização da Sprint 4 idempotente: rodar a função duas vezes no mesmo dia faz `upsert`, e não duplica.

```sql title="Migration de quotes_history (alvo de supabase/migrations/0004_quotes_history.sql)"
create table public.quotes_history (
  id uuid primary key default gen_random_uuid(),
  asset_id uuid not null references public.assets (id) on delete cascade,
  price numeric(14, 4) not null check (price >= 0),
  quote_date date not null,
  created_at timestamptz not null default now(),
  unique (asset_id, quote_date)
);
```

### TK03-4 · Habilitar RLS nas quatro tabelas

Uma tabela recém-criada no Supabase é **legível pela chave anônima** até que o RLS seja ligado. Por isso a migration de policies começa ligando o RLS antes de escrever a primeira regra: com RLS ligado e nenhuma policy, a tabela fica fechada para todo mundo, que é o estado seguro para partir.

```sql title="Ligar o RLS (inicio de supabase/migrations/0005_rls_policies.sql)"
alter table public.assets enable row level security;
alter table public.transactions enable row level security;
alter table public.quotes_history enable row level security;
-- profiles ja foi ligada na Sprint 2.
```

### TK03-5 · Criar as policies por `auth.uid()`

Quatro operações, quatro regras, e a distinção que a seção de decisões de segurança explica: `using` filtra as linhas que já existem, `with check` julga a linha que está tentando entrar. Sem o `with check` no `insert`, um cliente poderia gravar um ativo com o `user_id` de outra conta.

```sql title="Policies de assets (alvo de supabase/migrations/0005_rls_policies.sql)"
create policy "assets: dono le" on public.assets
  for select using (auth.uid() = user_id);

create policy "assets: dono insere" on public.assets
  for insert with check (auth.uid() = user_id);

create policy "assets: dono edita" on public.assets
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);

create policy "assets: dono remove" on public.assets
  for delete using (auth.uid() = user_id);
```

`transactions` repete as quatro, trocando a tabela. `quotes_history` não tem `user_id`: a leitura passa por uma subconsulta no ativo, e a escrita fica **sem policy**, porque só a Edge Function da Sprint 4 grava ali, com a chave de serviço, que ignora RLS.

```sql title="Policy de leitura de quotes_history"
create policy "quotes: dono do ativo le" on public.quotes_history
  for select using (
    exists (
      select 1 from public.assets a
      where a.id = quotes_history.asset_id and a.user_id = auth.uid()
    )
  );
```

### TK03-6 · Ligar a carteira ao banco

O serviço encapsula a consulta. `select('*, transactions(*)')` traz as transações aninhadas em uma chamada só, no estilo do `include` do Prisma; o `order` garante uma tabela estável entre recargas. Repare no que **não** está aqui: nenhum `.eq('user_id', …)`. O filtro por dono é do RLS, e escrevê-lo no cliente só daria a falsa impressão de que a segurança mora nele.

```js title="Servico de ativos (alvo de src/services/assets.js)"
import { supabase } from '../lib/supabase-client.js';

export async function listAssets() {
  return supabase
    .from('assets')
    .select('id, ticker, name, category, current_price, transactions(type, quantity, price)')
    .order('ticker');
}

export async function createAsset({ ticker, name, category }) {
  const { data: { user } } = await supabase.auth.getUser();

  return supabase
    .from('assets')
    .insert({ user_id: user.id, ticker: ticker.toUpperCase(), name, category })
    .select()
    .single();
}
```

O `user_id` vai no `insert` porque a policy `with check` exige que ele seja o do token. Enviar o de outra pessoa não "funciona": o banco responde `42501`, *new row violates row-level security policy*.

### TK03-7 · Criar os formulários de ativo e transação

O botão **+ Novo Ativo** da Sprint 1 passa a abrir um `<dialog>` com o formulário. O módulo da página lê os campos, chama o serviço e, em caso de sucesso, recarrega a lista. O erro do banco chega com `code` e `message`; o `23505` é a violação do `unique (user_id, ticker)`, e a tela o traduz para uma frase.

```js title="Cadastro de ativo pela tela (alvo de src/pages/dashboard.js)"
assetForm.addEventListener('submit', async (event) => {
  event.preventDefault();

  const { error } = await createAsset({
    ticker: assetForm.elements.ticker.value,
    name: assetForm.elements.name.value,
    category: assetForm.elements.category.value,
  });

  if (error?.code === '23505') return showError(assetForm, 'Voce ja tem esse ticker');
  if (error) return showError(assetForm, error.message);

  assetDialog.close();
  await renderPortfolio();
});
```

A transação segue o mesmo desenho, com `asset_id` vindo da linha da tabela em que o botão **Comprar** ou **Vender** foi clicado.

### TK03-8 · Calcular os indicadores da carteira

Custo, quantidade e patrimônio nascem das transações, e é por isso que este módulo é uma função pura: recebe o ativo com as transações aninhadas e devolve números. Sem `fetch`, sem DOM, ele é o candidato natural para o primeiro teste de unidade do projeto.

```js title="Indicadores de uma posicao (alvo de src/lib/portfolio.js)"
export function summarize(asset) {
  let quantity = 0;
  let cost = 0;

  for (const t of asset.transactions) {
    if (t.type === 'buy') {
      quantity += Number(t.quantity);
      cost += Number(t.quantity) * Number(t.price);
    } else {
      // Venda baixa o custo pelo preco medio, nao pelo preco de venda.
      cost -= Number(t.quantity) * (cost / quantity);
      quantity -= Number(t.quantity);
    }
  }

  const value = quantity * Number(asset.current_price ?? 0);

  return {
    quantity,
    cost,
    value,
    averagePrice: quantity ? cost / quantity : 0,
    returnPct: cost ? (value - cost) / cost : 0,
  };
}
```

A conversão com `Number()` é obrigatória: o PostgREST devolve `numeric` como **string**, justamente para não perder precisão no caminho. Somar sem converter concatena texto.

### TK03-9 · Criar os índices

Toda consulta desta etapa filtra por `user_id` (o RLS faz isso em cada linha) e ordena ou agrupa por ativo e data. Sem índice, o PostgreSQL varre a tabela inteira para aplicar a policy, e o custo cresce com o número de contas, não com o tamanho da carteira de quem consulta.

```sql title="Indices (fim de supabase/migrations/0005_rls_policies.sql)"
create index assets_user_id_idx on public.assets (user_id);
create index transactions_user_id_idx on public.transactions (user_id);
create index transactions_asset_date_idx on public.transactions (asset_id, transaction_date);
create index quotes_history_asset_date_idx on public.quotes_history (asset_id, quote_date desc);
```


## Decisões de segurança

RLS não é apenas uma `SELECT` com filtro. Cada operação precisa de uma regra: `USING` controla linhas existentes que podem ser vistas, alteradas ou removidas; `WITH CHECK` controla a linha nova ou alterada que tenta entrar na tabela.

| Operação | Regra mínima para `assets` | Motivo |
| -------- | -------------------------- | ------ |
| `SELECT` | `auth.uid() = user_id` em `USING`. | Não listar carteiras de terceiros. |
| `INSERT` | `auth.uid() = user_id` em `WITH CHECK`. | Não gravar um ativo em nome de outra conta. |
| `UPDATE` | A condição em `USING` e `WITH CHECK`. | Não editar nem trocar o dono do registro. |
| `DELETE` | `auth.uid() = user_id` em `USING`. | Não remover ativos de terceiros. |

<Aside type="caution" title="Dica de IA: Uma policy de leitura não protege escrita">
  É frequente gerar apenas `FOR SELECT` e concluir que RLS está pronto. Sem policies explícitas de inserção e alteração, a aplicação falha ou abre espaço para um `user_id` forjado, conforme a policy criada.

  **Prompt:** *"Para assets e transactions do InvestBaaS, derive as quatro policies RLS e inclua um teste negativo para INSERT e UPDATE que tenta trocar user_id para outra conta."*
</Aside>

## Testando

O melhor lugar para provar RLS é o **SQL Editor** do Supabase, porque ele permite executar uma consulta *como* um usuário específico. Crie duas contas pela tela (`ana@example.com` e `bruno@example.com`), cadastre um ativo em cada uma e rode os cenários abaixo.

```sql title="SQL Editor: consultar como a Ana"
-- O JWT simulado faz auth.uid() devolver o id da Ana.
select set_config('request.jwt.claims',
  json_build_object('sub', (select id from auth.users where email = 'ana@example.com'), 'role', 'authenticated')::text,
  true);
set local role authenticated;

select ticker, user_id from public.assets;
-- Esperado: so os ativos da Ana (CA03.4)
```

```sql title="SQL Editor: tentar gravar em nome do Bruno"
insert into public.transactions (user_id, asset_id, type, quantity, price)
values ((select id from auth.users where email = 'bruno@example.com'),
        (select id from public.assets limit 1), 'buy', 10, 30.5);
-- Esperado: ERROR 42501 new row violates row-level security policy (CA03.5)
```

Pela tela, os critérios restantes se provam em sequência: cadastre `PETR4` na conta da Ana e tente cadastrar de novo (a mensagem "Voce ja tem esse ticker" cobre o `unique`); registre uma compra de 100 a `R$ 30,00` e outra de 100 a `R$ 34,00`, e confira preço médio `R$ 32,00` e custo `R$ 6.400,00` na tabela (CA03.3). Por fim, abra a carteira do Bruno: o `PETR4` da Ana não aparece, e a resposta da API não traz sequer o `id` dele.
