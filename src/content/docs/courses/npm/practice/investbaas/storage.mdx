Etapa **5 de 6** · Nível **Avançado** · Supabase Storage · Policies · URLs assinadas

Uma nota de corretagem é tão sensível quanto os dados da transação que ela comprova. Esta etapa adiciona arquivos privados à carteira, usando paths previsíveis, policies em `storage.objects` e URLs temporárias, sem transformar o bucket em uma pasta pública.

<Aside type="note" title="Tópicos conceituais associados">
  A etapa estende a defesa em profundidade de [autorização](../../../../expressjs/auth/authorization/): RLS também governa objetos de Storage, não apenas tabelas do schema público.
</Aside>

## Objetivo

Adicionar comprovantes privados à carteira sem transformá-los em arquivos publicamente acessíveis. Ao final da etapa, o leitor deve ser capaz de:

- Organizar paths de objetos a partir da identidade autenticada.
- Diferenciar path persistido de URL assinada temporária.
- Testar upload e leitura cruzada usando duas contas distintas.

## Fluxo de arquivo privado

O front pode validar ergonomia, mas o Storage valida autorização. A tabela mantém só a referência estável; a URL assinada é descartável e nasce novamente a cada leitura autorizada.

## O que muda nesta etapa?

A coluna `receipt_path` existe desde a Sprint 3 e ficou vazia até aqui. Esta etapa a preenche com um objeto do Storage, guardado em um bucket que nunca devolve arquivo a quem não é dono.

| Antes (Sprint 4) | Agora (Sprint 5) |
| ---------------- | ---------------- |
| `receipt_path` sempre nulo | Path do objeto no bucket `receipts`, gravado junto da transação |
| Nenhum bucket | `receipts`, privado, com policies em `storage.objects` |
| Formulário de transação só com números | `<input type="file">` aceitando PDF, PNG e JPG até 5 MB |
| Nenhuma leitura de arquivo | Botão **Ver comprovante** gerando uma URL assinada de 60 segundos |
| Admin sem visão de arquivos | Contagem agregada de uploads e falhas, sem listar objetos |

## Descrição das tarefas

Abaixo estão detalhadas as tarefas de implementação desta etapa, com orientações e os trechos de código que cada uma produz.

### TK05-1 · Criar o bucket privado `receipts`

O bucket é criado por migration, e não pelo painel, para que o ambiente seja reproduzível. `public = false` é a linha que importa: em um bucket público, qualquer pessoa com a URL lê o objeto para sempre; em um privado, só quem passa por uma policy, e só pelo tempo de uma URL assinada.

```sql title="Bucket privado (inicio de supabase/migrations/0008_storage_receipts.sql)"
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values (
  'receipts',
  'receipts',
  false,
  5 * 1024 * 1024,
  array['application/pdf', 'image/png', 'image/jpeg']
);
```

O limite de tamanho e a lista de tipos ficam no próprio bucket. Eles valem para qualquer cliente, inclusive um `curl` que pule a validação do navegador.

### TK05-2 · Criar as policies em `storage.objects`

O Storage guarda cada objeto como uma linha de `storage.objects`, e o RLS vale ali como em qualquer tabela. A regra é uma só, repetida por operação: o primeiro segmento do *path* tem que ser o `auth.uid()` de quem chama. `storage.foldername(name)` devolve os segmentos do caminho como array, e `[1]` é a pasta de primeiro nível.

```sql title="Policies do bucket (continuacao de 0008_storage_receipts.sql)"
create policy "receipts: dono envia" on storage.objects
  for insert to authenticated
  with check (bucket_id = 'receipts' and (storage.foldername(name))[1] = auth.uid()::text);

create policy "receipts: dono le" on storage.objects
  for select to authenticated
  using (bucket_id = 'receipts' and (storage.foldername(name))[1] = auth.uid()::text);

create policy "receipts: dono remove" on storage.objects
  for delete to authenticated
  using (bucket_id = 'receipts' and (storage.foldername(name))[1] = auth.uid()::text);
```

Não há policy de `update`: um comprovante não é editado, é substituído por outro upload.

### TK05-3 · Validar o upload no navegador

A validação do cliente existe para a pessoa, não para a segurança: ela responde antes de subir 5 MB pela rede. É uma função pura, sem DOM, e por isso o tipo e o limite ficam declarados uma vez e testáveis.

```js title="Validacao de arquivo (alvo de src/lib/file-validation.js)"
export const ALLOWED_TYPES = ['application/pdf', 'image/png', 'image/jpeg'];
export const MAX_SIZE = 5 * 1024 * 1024;

export function validateReceipt(file) {
  if (!ALLOWED_TYPES.includes(file.type)) return 'Envie um PDF, PNG ou JPG';
  if (file.size > MAX_SIZE) return 'O arquivo pode ter no maximo 5 MB';
  return null;
}
```

`file.type` é o MIME que o **navegador** declara a partir da extensão. Um `virus.exe` renomeado para `nota.pdf` passa aqui; é o bucket, com `allowed_mime_types`, e a policy que fecham o caminho. A página repete a lição da etapa de upload das outras trilhas: validação no cliente é ergonomia, validação no servidor é segurança.

### TK05-4 · Enviar o arquivo e vincular à transação

O *path* é decidido pelo código, nunca pelo nome do arquivo: `<user_id>/<transaction_id>/<uuid>.<ext>`. O primeiro segmento é o que a policy confere; o segundo permite encontrar os comprovantes de uma transação; o terceiro evita colisão e esconde o nome original. Depois do upload, a transação recebe o *path* (e só o *path*).

```js title="Upload e vinculo (alvo de src/services/receipts.js)"
import { supabase } from '../lib/supabase-client.js';

export async function uploadReceipt({ userId, transactionId, file }) {
  const ext = file.name.split('.').pop().toLowerCase();
  const path = `${userId}/${transactionId}/${crypto.randomUUID()}.${ext}`;

  const { error: uploadError } = await supabase.storage
    .from('receipts')
    .upload(path, file, { contentType: file.type });

  if (uploadError) return { error: uploadError };

  return supabase
    .from('transactions')
    .update({ receipt_path: path })
    .eq('id', transactionId);
}
```

Gravar a URL assinada no banco seria guardar uma credencial que expira: em um minuto a coluna estaria apontando para um link morto. O *path* é estável; a URL nasce a cada leitura.

### TK05-5 · Gerar a URL assinada de curta duração

`createSignedUrl` só funciona para quem passa pela policy de `select`: pedir a URL de um *path* de outra conta responde erro, não link. Sessenta segundos bastam para abrir o documento em uma aba; quem precisar de novo pede de novo.

```js title="URL temporaria (continuacao de src/services/receipts.js)"
export async function receiptUrl(path) {
  const { data, error } = await supabase.storage
    .from('receipts')
    .createSignedUrl(path, 60);

  return error ? { error } : { url: data.signedUrl };
}
```

### TK05-6 · Exibir o comprovante na tela

Na tabela de transações, a linha que tem `receipt_path` ganha o botão **Ver comprovante**. O clique pede a URL e abre uma aba; a URL não é escrita no HTML, e um `Ctrl+C` no botão não copia nada reutilizável.

```js title="Acao Ver comprovante (trecho de src/pages/dashboard.js)"
table.addEventListener('click', async (event) => {
  const button = event.target.closest('[data-receipt]');
  if (!button) return;

  const { url, error } = await receiptUrl(button.dataset.receipt);
  if (error) return showToast('Comprovante indisponivel');

  window.open(url, '_blank', 'noopener');
});
```

### TK05-7 · Medir a operação para o admin

O admin da Sprint 6 mostra quantos comprovantes existem e quantos uploads falharam, sem listar um arquivo sequer. A contagem vem de uma função `security definer` que lê `storage.objects` agregado; a função é chamável só por quem tem `role = 'admin'` em `profiles`, checagem feita dentro dela.

```sql title="Contagem agregada (alvo de supabase/migrations/0009_admin_receipts_stats.sql)"
create function public.admin_receipts_stats()
returns table (total bigint, last_upload timestamptz)
language sql security definer set search_path = public, storage as $$
  select count(*), max(created_at)
  from storage.objects
  where bucket_id = 'receipts'
    and exists (select 1 from public.profiles where id = auth.uid() and role = 'admin');
$$;
```

Sem o `exists`, qualquer conta poderia chamar a função e ler o total. Com ele, um investidor recebe zero linhas, e não um erro que confirme a existência da função.

## Regras de segurança

| Regra | Implementação | O que evita |
| ----- | ------------- | ----------- |
| Bucket privado | `public = false`. | URL permanente conhecida por terceiros. |
| Prefixo por dono | `receipts/<auth.uid()>/...`. | Colisão e leitura entre contas. |
| Path persistido | Coluna `receipt_path`. | Salvar credencial temporária no banco. |
| URL curta | Criada somente para leitura autorizada. | Compartilhamento prolongado de documento. |
| Validação dupla | Front para UX, policy para segurança. | Confiar no navegador como fronteira. |

<Aside type="caution" title="Dica de IA: Não valide só pela extensão">
  Renomear um arquivo não muda seu conteúdo. A interface pode conferir extensão e MIME informado, mas o sistema deve limitar o tipo aceito e registrar falhas sem pressupor que o navegador é confiável.

  **Prompt:** *"Projete a validação de comprovantes do InvestBaaS com tipos permitidos, limite de tamanho, mensagens para o usuário e casos de teste que incluem uma extensão PDF com MIME incompatível."*
</Aside>

## Testando

Os cenários desta etapa exigem **duas contas**: um upload que funciona para a Ana não prova nada sobre o Bruno. Com os dois logados em navegadores diferentes, o roteiro é o seguinte.

| Verificação | Como fazer | Critério |
| ----------- | ---------- | -------- |
| Bucket privado | Em **Storage › receipts**, o cadeado indica *private*; a URL pública de um objeto (`/storage/v1/object/public/receipts/...`) responde `400` | RNF04 |
| Upload válido | Como Ana, anexe um PDF de até 5 MB a uma transação: o objeto aparece em `receipts/<id da Ana>/<id da transacao>/` e `receipt_path` é preenchido | CA05.1 |
| Tipo e tamanho | Tente um `.exe` e um PDF de 8 MB: o navegador recusa antes de enviar, e um `curl` direto recebe erro do bucket | CA05.2 |
| Leitura própria | Como Ana, clique em **Ver comprovante**: a aba abre, e a URL contém `token=` e expira em 60 segundos | CA05.3 |
| Leitura cruzada | Como Bruno, chame `createSignedUrl` com o *path* da Ana no console do navegador: a resposta é `Object not found`, sem confirmar que o arquivo existe | CA05.4 |
| URL não persistida | No **Table Editor**, `receipt_path` guarda `<uuid>/<uuid>/<uuid>.pdf`, e não uma URL | CA05.5 |

```js title="Console do navegador, logado como Bruno"
const { data, error } = await supabase.storage
  .from('receipts')
  .createSignedUrl('<id da Ana>/<id da transacao>/<uuid>.pdf', 60);
// error.message === 'Object not found'
```

## Executando

Crie o bucket privado e as policies antes de conectar o formulário. Valide com duas contas reais de teste, pois um upload bem-sucedido de uma conta não prova que o isolamento funciona.

<Steps>

1. **Aplique as migrations de Storage**: confirme no painel que `receipts` não é público.
2. **Teste upload e URL assinada**: envie um arquivo permitido e abra-o como o proprietário.
3. **Teste o caso negativo**: tente ler o path da primeira conta com a segunda e confirme a recusa.

</Steps>

## Conceitos abordados

- Bucket privado com limite de tamanho e lista de tipos no próprio bucket
- RLS em `storage.objects` e o primeiro segmento do *path* como dono
- Validação no cliente para ergonomia, no servidor para segurança
- *Path* estável no banco, URL assinada descartável na leitura
- Contagem agregada por função `security definer` restrita a `admin`
