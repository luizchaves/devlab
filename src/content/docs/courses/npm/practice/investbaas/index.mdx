Nível **Intermediário** · HTML · Tailwind CSS · JavaScript modular · Supabase · PostgreSQL · RLS · Deno

O **InvestBaaS** é uma plataforma de gestão patrimonial para investidores individuais. Ela começa como um protótipo navegável e evolui, sprint a sprint, para uma aplicação BaaS: o Supabase fornece identidade, banco de dados, arquivos privados e funções de servidor, sem introduzir uma API Express intermediária.

## Análise de requisitos

### Público-alvo

O **InvestBaaS** foi projetado para atender a três perfis, e a distinção entre os dois últimos é o que molda a segurança do sistema:

- **Estudantes do Guia de Pacotes**: pessoas que já construíram uma API própria no InvestApp ou no MonitorApp e querem ver o mesmo domínio entregue **sem** servidor intermediário, com identidade, banco, arquivos e funções fornecidos por um BaaS.
- **Investidores individuais**: quem precisa registrar e entender a própria carteira (ativos, transações, comprovantes e rentabilidade), e só a própria.
- **Administração da plataforma**: quem precisa enxergar saúde e volume do serviço (contas, AUM, execução de cotações) sem receber a lista de posições de ninguém.

A tabela resume o que cada perfil de uso pode ver, e é ela que origina os requisitos não funcionais:

| Perfil | Necessidade principal | Limite de acesso |
| ------ | --------------------- | ---------------- |
| Investidor | Registrar ativos, transações, comprovantes e rentabilidade. | Somente os próprios dados e arquivos. |
| Administrador | Acompanhar contas, AUM e execução de serviços. | Métricas agregadas, sem posições individuais. |

## Objetivo do sistema

O **InvestBaaS** oferece uma plataforma web de gestão patrimonial em que o navegador fala diretamente com o Supabase: a conta vive no Supabase Auth, a carteira em PostgreSQL com Row Level Security, os comprovantes em um bucket privado e as cotações são atualizadas por uma Edge Function. O objetivo didático é mostrar que "sem back-end próprio" não significa "sem regras no servidor": cada regra que o InvestApp escreveu em um middleware Express aparece aqui como policy, constraint, trigger ou função no banco.

### Requisitos Funcionais (RF)

Os códigos da tabela são retomados no [backlog](backlog/) e nas seis etapas da trilha.

| Código | Requisito funcional | Resultado esperado |
| ------ | ------------------- | ------------------ |
| RF01 | Simulação | Calcular projeção de aportes e juros compostos na landing page. |
| RF02 | Conta e sessão | Criar conta, entrar, recuperar a sessão e sair. |
| RF03 | Carteira | Manter ativos e transações de compra e venda. |
| RF04 | Comprovantes | Anexar e consultar documentos privados de transações. |
| RF05 | Cotações | Atualizar preço atual e histórico de ativos elegíveis. |
| RF06 | Analytics | Mostrar rentabilidade mensal, anual e distribuição por classe. |
| RF07 | Operação | Exibir indicadores agregados e status dos serviços para administradores. |

### Requisitos Não-Funcionais (RNF)

Os requisitos não funcionais protegem o domínio financeiro. Eles definem onde a aplicação pode confiar na regra de acesso e onde segredos podem existir.

| Código | Regra arquitetural | Consequência prática |
| ------ | ------------------ | -------------------- |
| RNF01 | RLS em toda tabela de domínio. | Um filtro esquecido no front não vaza carteira. |
| RNF02 | Chaves privadas fora do navegador. | A `service_role` fica apenas em Edge Functions. |
| RNF03 | Dados monetários com precisão decimal. | Valores não usam ponto flutuante binário para saldo. |
| RNF04 | Arquivos em bucket privado. | A leitura acontece por policy e URL assinada curta. |
| RNF05 | Administração agregada e autorizada. | O painel não consulta posições de investidores. |

## Stack tecnológica da aplicação

O projeto evolui acrescentando um serviço do Supabase por sprint, e nunca um servidor próprio:

| Camada | Tecnologias e bibliotecas |
| ------ | ------------------------- |
| **Front-end** | HTML5 semântico, Tailwind CSS (Play CDN no protótipo, compilado pela CLI da Sprint 2 em diante), JavaScript vanilla em módulos ES e Vite como servidor e build |
| **Identidade** | Supabase Auth (e-mail e senha, JWT, sessão renovada pelo SDK) e `@supabase/supabase-js` |
| **Persistência** | PostgreSQL gerenciado pelo Supabase, migrations SQL versionadas em `supabase/migrations/`, Row Level Security em toda tabela de domínio |
| **Arquivos** | Supabase Storage com bucket privado, policies em `storage.objects` e URLs assinadas |
| **Código de servidor** | Edge Functions em Deno/TypeScript, únicas portadoras da chave de serviço e do token do provedor de cotações |
| **Agendamento** | `pg_cron` e `pg_net` dentro do próprio PostgreSQL |
| **Qualidade** | Biome (lint e formatação), specs por task em `specs/`, template de PR |

## Arquitetura do sistema

O navegador fala diretamente com as APIs públicas do Supabase usando a chave anônima. A chave identifica o projeto, mas não concede acesso irrestrito: o JWT do usuário e as policies RLS delimitam cada consulta. A função de cotação é a única camada com privilégio de serviço.

<Mermaid title="Caminho dos dados no InvestBaaS">
{`
flowchart TB
  Browser["Navegador\nHTML + Tailwind + JavaScript"]
  Auth["Supabase Auth\nconta e JWT"]
  Db[("PostgreSQL\nprofiles · assets · transactions\nquotes_history + RLS")]
  Storage["Storage privado\nreceipts/<user_id>/..."]
  Edge["Edge Function\nupdate-quotes"]
  Market["Provedor de cotações"]
  Admin["View administrativa\nmétricas agregadas"]
  Browser --> Auth
  Browser -->|"JWT + anon key"| Db
  Browser -->|"JWT + anon key"| Storage
  Browser -->|"invocação autenticada"| Edge
  Edge -->|"service role no ambiente"| Db
  Edge --> Market
  Admin --> Db
`}
</Mermaid>

<Aside type="caution" title="A chave anônima não substitui RLS">
  A chave pública do projeto pode aparecer no navegador. A segurança vem de policies que usam a identidade presente no JWT, não de esconder essa chave. A `service_role`, por outro lado, ignora RLS e nunca pode entrar em HTML, JavaScript publicado ou variáveis expostas pelo build.

  **Prompt:** *"Revise estas policies RLS para assets e transactions; mostre um cenário em que um usuário A tenta ler ou inserir um registro do usuário B e explique qual cláusula bloqueia cada tentativa."*
</Aside>

## Modelo de domínio

As entidades são introduzidas em camadas. O protótipo já mostra a linguagem do domínio; o banco entra na Sprint 3, e as leituras agregadas aparecem somente quando já há dados confiáveis.

<Mermaid title="Entidades da versão BaaS planejada">
{`
erDiagram
  PROFILE ||--o{ ASSET : possui
  ASSET ||--o{ TRANSACTION : recebe
  ASSET ||--o{ QUOTE_HISTORY : registra
  TRANSACTION }o--|| RECEIPT : referencia
  PROFILE { uuid id PK string full_name string role }
  ASSET { uuid id PK uuid user_id FK string ticker string category numeric current_price }
  TRANSACTION { uuid id PK uuid asset_id FK uuid user_id FK string type numeric quantity numeric price string receipt_path }
  QUOTE_HISTORY { uuid id PK uuid asset_id FK numeric price date quote_date }
  RECEIPT { string path PK }
`}
</Mermaid>

`receipt_path` é uma referência para um objeto do Storage, não uma URL pública. A URL é criada sob demanda, expira em pouco tempo e não deve ser persistida na tabela.

### Dicionário de dados do domínio

O dicionário formaliza a estrutura, os tipos e as regras de cada tabela que as sprints 2, 3 e 4 criam. Todo valor monetário é `numeric`, e toda tabela tem RLS ligado.

#### 1. Tabela `profiles` (Investidor)

Espelha `auth.users` com os dados de domínio da conta. É criada por trigger no cadastro (Sprint 2) e carrega o papel que o painel administrativo confere (Sprint 6).

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `uuid` | **PK**, **FK** (`auth.users.id`) | O mesmo identificador da conta no Supabase Auth. |
| `full_name` | `text` | Obrigatório | Nome de exibição, copiado dos metadados do cadastro. |
| `role` | `text` | `check` em `investor`, `admin`; padrão `investor` | Papel da conta. Promovido só pelo SQL Editor, nunca pelo SDK. |
| `created_at` | `timestamptz` | Padrão `now()` | Instante do cadastro. |

#### 2. Tabela `assets` (Ativo)

O instrumento que está na carteira: o que é, de que categoria e a que preço está.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `uuid` | **PK** | Identificador gerado pelo banco. |
| `user_id` | `uuid` | **FK** (`profiles.id`), `not null` | Dono do ativo; a coluna que toda policy compara com `auth.uid()`. |
| `ticker` | `text` | Obrigatório, único por dono | Código do ativo (`PETR4`, `HGLG11`) ou nome curto para renda fixa. |
| `name` | `text` | Obrigatório | Nome de exibição. |
| `category` | `text` | `check` em `renda_fixa`, `acoes`, `fiis`, `fundos`, `cripto` | As cinco categorias que o protótipo desenha como *badges*. |
| `current_price` | `numeric(14, 4)` | Opcional | Última cotação; preenchida pela Edge Function para `acoes` e `fiis`, manual nas demais. |

#### 3. Tabela `transactions` (Transação)

Um fato imutável: uma compra ou venda, de tanta quantidade, a tanto, em tal dia. A posição é sempre derivada daqui.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `uuid` | **PK** | Identificador gerado pelo banco. |
| `user_id` | `uuid` | **FK** (`profiles.id`), `not null` | Dono, repetido para que a policy não precise de `join`. |
| `asset_id` | `uuid` | **FK** (`assets.id`), `not null` | O ativo negociado. |
| `type` | `text` | `check` em `buy`, `sell` | Compra ou venda. |
| `quantity` | `numeric(18, 8)` | `> 0` | Quantidade, com casas para frações de cripto e fundos. |
| `price` | `numeric(14, 4)` | `>= 0` | Preço unitário na data. |
| `transaction_date` | `date` | Padrão `current_date` | Data do negócio. |
| `receipt_path` | `text` | Opcional | *Path* do comprovante no bucket `receipts` (Sprint 5), nunca uma URL. |

#### 4. Tabela `quotes_history` (Cotação diária)

Uma observação de preço por ativo e por dia. Escrita apenas pela Edge Function, com a chave de serviço.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `uuid` | **PK** | Identificador gerado pelo banco. |
| `asset_id` | `uuid` | **FK** (`assets.id`), `not null` | O ativo cotado. |
| `price` | `numeric(14, 4)` | `>= 0` | Preço observado. |
| `quote_date` | `date` | Único junto com `asset_id` | A data; a chave única é o que torna a atualização idempotente. |

#### 5. Tabela `quote_runs` (Execução de cotações)

Resumo operacional de cada execução da função `update-quotes`, lido apenas por `admin`.

| Campo | Tipo de dado | Chave / Restrição | Descrição e Regras de Negócio |
| ----- | ------------ | ----------------- | ----------------------------- |
| `id` | `uuid` | **PK** | Identificador gerado pelo banco. |
| `ran_at` | `timestamptz` | Padrão `now()` | Instante da execução. |
| `requested` / `updated` | `integer` | Obrigatórios | Tickers pedidos e atualizados. |
| `failed` | `jsonb` | Padrão `[]` | Lista de `{ ticker, reason }` das falhas. |

## Trilha incremental de desenvolvimento

As sprints seguem uma dependência deliberada: não há policy RLS útil sem identidade, nem analytics honesto antes de transações e cotações. A sequência abaixo é também a ordem sugerida de leitura das páginas.

<Steps>

1. **Frontend estático**: telas, vocabulário visual, navegação e documentação de governança.
2. **Autenticação BaaS**: Supabase Auth, sessão, perfil, guardas de páginas privadas e as três camadas de teste.
3. **Banco de dados e RLS**: migrations, ativos, transações, histórico e isolamento no PostgreSQL.
4. **Cotações com Edge Functions**: atualização idempotente, falhas parciais e operação agendada.
5. **Armazenamento de comprovantes**: bucket privado, paths por usuário e URLs assinadas.
6. **Analytics e painel admin**: matrizes de retorno, AUM agregado e autorização administrativa.

</Steps>

## Evolução incremental do projeto

<Aside type="tip" title="O trilho é cumulativo por construção">
  Cada pasta de sprint nasce como cópia da anterior mais o delta daquela sprint. Nada que foi
  introduzido desaparece depois: as telas da Sprint 1 não são reescritas, recebem módulos; as
  policies da Sprint 3 não são refeitas na 5, o Storage ganha as suas no mesmo desenho. As duas
  únicas substituições são explicadas na própria página: o `action="./dashboard.html"` dos
  formulários dá lugar ao SDK na Sprint 2, e o Tailwind pelo Play CDN dá lugar ao compilado.
</Aside>

Comparar duas pastas com `git diff --no-index` mostra, de forma isolada, exatamente o que aquela sprint alterou:

```bash title="Terminal"
git diff --no-index -- \
  examples/courses/npm/projects/investbaas-static \
  examples/courses/npm/projects/investbaas-auth || true
```

A partir da Sprint 2, toda task chega com pelo menos um teste na camada que a prova: **unidade** (Vitest e jsdom, com o SDK mockado) para serviços e funções puras, **integração** (Vitest e o SDK real contra a stack local do Supabase) para migrations, policies e funções, e **E2E** (Playwright) para o fluxo de tela. É a mesma exigência da etapa 12 das outras trilhas, aplicada desde a segunda sprint.

### Execução do projeto local

Cada página de sprint aponta para uma pasta em `examples/courses/npm/projects/`. A Sprint 1 só precisa do Vite; da Sprint 2 em diante, a stack local do Supabase (Docker e a CLI) substitui um projeto na nuvem:

```bash title="Terminal"
cd examples/courses/npm/projects/investbaas-auth
pnpm install
pnpm db:start
pnpm db:reset
pnpm dev
```

<Aside type="caution" title="Stack local ou projeto na nuvem">
  Os testes das sprints rodam contra `supabase start`. Para usar um projeto em
  [supabase.com](https://supabase.com/), copie apenas a URL e a chave anônima para o `.env`
  (`VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY`) e aplique as migrations com `supabase db push`.
  A chave de serviço e o token do provedor de cotações entram só nos segredos das Edge Functions.
</Aside>
