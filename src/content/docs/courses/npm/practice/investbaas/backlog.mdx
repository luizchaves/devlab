O backlog do **InvestBaaS** transforma a ideia de uma plataforma financeira em trabalho
executável. Ele conecta requisitos de produto a telas, tabelas, policies RLS, buckets,
Edge Functions, métricas administrativas e validações manuais.

## Como ler este backlog?

Use esta página como mapa de execução da trilha. Cada épico descreve uma capacidade do produto,
cada história explica a necessidade do usuário e cada task aponta uma entrega técnica pequena o
suficiente para revisão.

```txt title="Fluxo de planejamento"
Épico -> História de usuário -> Critérios de aceite -> Sprint -> Task -> Validação
```

## Objetivo

Compreender o escopo funcional e técnico do InvestBaaS, decompondo a aplicação em sprints e
tasks cumulativas que mantêm rastreabilidade entre produto, documentação e implementação.

Ao final do tópico, o leitor deve ser capaz de:

- Relacionar cada épico do produto a uma etapa da trilha InvestBaaS.
- Identificar quais tasks constroem interface, autenticação, banco, storage, analytics e operação.
- Explicar por que RLS, Edge Functions e Storage precisam aparecer no backlog, não só no código.
- Planejar uma sprint usando critérios de aceite e validações objetivas.
- Revisar se uma task está pequena, testável e conectada a uma história de usuário.

## Mapa dos épicos

Os épicos avançam do protótipo para a aplicação BaaS completa. A ordem é cumulativa: a interface
estática cria o contrato visual, a autenticação cria identidade, o banco aplica isolamento, as
funções atualizam dados e as telas analíticas consolidam a leitura financeira.

## Histórias de usuário

As histórias abaixo dão contexto às tasks. Uma task sem história vira implementação solta; uma
história sem task vira intenção sem entrega. A versão executável dos critérios, em Gherkin, fica
na página da sprint correspondente.

### US01 · Simular crescimento patrimonial · RF01

Como investidor iniciante, quero simular aportes e prazo de investimento, para entender o efeito
dos juros compostos antes de criar uma conta.

Critérios de aceite:

- A landing page deve exibir aporte inicial, aporte mensal e prazo.
- O resultado deve separar patrimônio estimado, total investido e rendimento.
- O simulador deve funcionar sem autenticação.

### US02 · Navegar pelo protótipo completo · RF02, RF03, RF06, RF07

Como avaliador do produto, quero navegar por landing, carteira, analytics, admin e telas de
sessão, para validar a experiência antes da integração com Supabase.

Critérios de aceite:

- Todas as páginas HTML devem ter links relativos funcionando.
- O dashboard deve mostrar KPIs e posições categorizadas.
- Analytics e admin devem antecipar as leituras financeiras sem expor dados individuais no painel global.

### US03 · Criar conta e entrar · RF02

Como investidor, quero criar conta e entrar com e-mail e senha, para acessar minha carteira
privada.

Critérios de aceite:

- O cadastro deve usar Supabase Auth.
- O login deve criar sessão recuperável no recarregamento.
- O logout deve encerrar a sessão e retornar à landing page.

### US04 · Proteger telas privadas · RF02, RNF01

Como investidor autenticado, quero que usuários anônimos não acessem minha carteira, para manter
dados financeiros protegidos.

Critérios de aceite:

- Páginas privadas devem executar guarda de sessão.
- Usuários sem sessão devem ser redirecionados para `signin.html`.
- O front-end não deve expor segredos de servidor.

### US05 · Gerenciar posições e transações · RF03, RF04

Como investidor, quero registrar ativos e transações, para acompanhar quantidade, preço médio,
valor atual e rentabilidade.

Critérios de aceite:

- Ativos devem guardar ticker, nome, categoria, quantidade, preço médio e preço atual.
- Transações devem guardar tipo, quantidade, preço, data e comprovante opcional.
- Cada registro deve pertencer ao usuário autenticado.

### US06 · Isolar dados por investidor · RNF01

Como usuário cadastrado, quero acessar apenas meus próprios registros, para garantir privacidade
financeira mesmo que uma consulta do cliente esteja incompleta.

Critérios de aceite:

- Todas as tabelas de domínio devem ter RLS habilitado.
- Policies devem comparar `auth.uid()` com `user_id`.
- Usuários comuns não devem ler, alterar ou apagar linhas de terceiros.

### US07 · Atualizar cotações · RF05

Como investidor, quero atualizar cotações de ativos negociados, para visualizar patrimônio e
rentabilidade com preços recentes.

Critérios de aceite:

- A rotina deve consultar tickers elegíveis.
- Falhas por ticker não devem interromper toda a atualização.
- Cada atualização deve registrar preço atual e histórico.

### US08 · Anexar comprovantes · RF04, RNF05

Como investidor, quero anexar notas de corretagem e comprovantes às transações, para manter a
carteira auditável.

Critérios de aceite:

- O bucket deve ser privado.
- Arquivos devem ficar em pastas iniciadas pelo `user_id`.
- URLs assinadas devem expirar em tempo curto.

### US09 · Consultar rentabilidade histórica · RF06

Como investidor avançado, quero visualizar rendimento mensal e anual, para auditar o desempenho
da carteira.

Critérios de aceite:

- A matriz deve ter meses nas colunas e anos nas linhas.
- Cada célula deve exibir percentual e valor nominal quando houver dado.
- O acumulado anual deve respeitar composição dos meses.

### US10 · Acompanhar operação global · RF07

Como administrador, quero visualizar contas ativas, AUM e saúde das rotinas, para acompanhar a
operação sem acessar posições individuais.

Critérios de aceite:

- A visão administrativa deve exigir perfil `admin`.
- Métricas devem ser agregadas.
- Falhas de cotações, Storage e jobs devem aparecer como status operacional.

## Planejamento de sprints

As sprints abaixo organizam todas as tasks necessárias para evoluir o protótipo estático até uma
aplicação BaaS completa. A validação indicada em cada task é o mínimo esperado antes de mover a
entrega para pronta.

### Sprint 1 · Frontend estático e governança

A primeira sprint cria a aplicação navegável e registra a forma de trabalho. Ela já existe no
projeto `investbaas-static` e serve como base visual para as próximas integrações.

| Task | História | Entrega | Validação |
| ---- | -------- | ------- | --------- |
| **TK01-1** | US02 | Criar projeto Vite, `package.json`, Biome, README e `AGENTS.md`. | `pnpm install`, `pnpm dev`, `pnpm lint`. |
| **TK01-2** | US01 | Construir `index.html` com landing page e simulador visual. | Abrir landing e conferir inputs, CTAs e responsividade. |
| **TK01-3** | US03 | Criar `signin.html` e `signup.html` com formulários de sessão. | Navegar entre cadastro, login e landing por links relativos. |
| **TK01-4** | US05 | Criar `dashboard.html` com KPIs, tabela de ativos e ações principais. | Conferir categorias, valores, botões e leitura em mobile. |
| **TK01-5** | US09 | Criar `analytics.html` com matriz de rentabilidade e distribuição. | Conferir anos, meses, valores positivos, negativos e células vazias. |
| **TK01-6** | US10 | Criar `admin.html` com métricas agregadas e status operacional. | Verificar que não há posições individuais na tela admin. |
| **TK01-7** | US02 | Criar specs arquivadas, skills locais, template de PR e documentação de sprint. | Conferir `docs/SPRINTS.md`, `specs/archived/` e `.github/pull_request_template.md`. |

### Sprint 2 · Supabase Auth e sessão

A segunda sprint substitui telas estáticas por autenticação real. A chave anônima pode aparecer
no cliente, mas nenhuma chave privilegiada entra no HTML ou no JavaScript público.

| Task | História | Entrega | Validação |
| ---- | -------- | ------- | --------- |
| **TK02-1** | US03 | Criar arquivo de configuração do cliente Supabase com `SUPABASE_URL` e `SUPABASE_ANON_KEY`. | Conferir que apenas valores públicos aparecem no front-end. |
| **TK02-2** | US03 | Implementar `signUp()` com e-mail, senha e metadados de nome completo. | Criar usuário de teste no projeto Supabase. |
| **TK02-3** | US03 | Implementar `signInWithPassword()` e mensagens de erro para credenciais inválidas. | Testar login válido e inválido. |
| **TK02-4** | US04 | Criar `requireAuth()` para proteger `dashboard.html`, `analytics.html` e páginas privadas. | Abrir página privada sem sessão e verificar redirecionamento. |
| **TK02-5** | US03, US04 | Implementar logout, recuperação de sessão com `getSession()` e exibição do e-mail do usuário. | Recarregar página autenticada e confirmar permanência da sessão. |
| **TK02-6** | US03 | Criar tabela ou trigger de `profiles` vinculada a `auth.users`. | Confirmar criação de perfil para novo usuário. |

### Sprint 3 · PostgreSQL, carteira e RLS

A terceira sprint cria a persistência real. O ponto central é que a segurança precisa morar no
banco, não apenas no código do cliente.

| Task | História | Entrega | Validação |
| ---- | -------- | ------- | --------- |
| **TK03-1** | US05 | Criar migration SQL para `assets` com tipos, categorias, constraints e `user_id`. | Inserir ativo válido e recusar categoria inválida. |
| **TK03-2** | US05 | Criar migration SQL para `transactions` com compra, venda, preço, data e `receipt_url`. | Inserir transação vinculada a ativo existente. |
| **TK03-3** | US07, US09 | Criar `quotes_history` para histórico de preços por ativo e data. | Inserir cotação e consultar por ativo. |
| **TK03-4** | US06 | Habilitar RLS em `profiles`, `assets`, `transactions` e `quotes_history`. | Consultar tabelas como usuário autenticado e anônimo. |
| **TK03-5** | US06 | Criar policies de leitura, inserção, atualização e exclusão por `auth.uid()`. | Tentar acessar dados de outro usuário e confirmar bloqueio. |
| **TK03-6** | US05 | Ligar `dashboard.html` ao Supabase para listar ativos reais. | Criar ativo no banco e visualizar na tabela. |
| **TK03-7** | US05 | Implementar criação de ativo e transação pelo front-end. | Cadastrar compra e conferir atualização da carteira. |
| **TK03-8** | US05, US09 | Calcular patrimônio, custo, lucro e rentabilidade a partir dos registros. | Comparar cálculo exibido com dados de teste conhecidos. |
| **TK03-9** | US06 | Criar índices para `user_id`, `asset_id`, `ticker` e datas de consulta. | Executar consultas comuns e revisar plano ou tempo de resposta. |

### Sprint 4 · Cotações com Edge Functions

A quarta sprint introduz código privilegiado em Deno. Ela evita colocar segredo de provedor ou
`service role key` no navegador.

| Task | História | Entrega | Validação |
| ---- | -------- | ------- | --------- |
| **TK04-1** | US07 | Criar estrutura da Edge Function `update-quotes`. | Executar função localmente com Supabase CLI. |
| **TK04-2** | US07 | Consultar tickers elegíveis em `assets` usando chave de serviço no ambiente da função. | Confirmar que o cliente não recebe a `service role key`. |
| **TK04-3** | US07 | Integrar provedor de cotações ou adaptador simulado com contrato estável. | Testar resposta com lista de tickers conhecidos. |
| **TK04-4** | US07 | Atualizar `assets.current_price` e inserir linhas em `quotes_history`. | Conferir antes e depois no SQL Editor. |
| **TK04-5** | US07 | Registrar falhas por ticker sem abortar toda a atualização. | Simular ticker inválido e verificar resumo parcial. |
| **TK04-6** | US07 | Adicionar botão "Atualizar Cotações" no dashboard chamando a função. | Clicar no botão e observar atualização dos valores. |
| **TK04-7** | US07, US10 | Criar status operacional da última execução para o painel admin. | Conferir data, sucesso, falhas e total atualizado. |
| **TK04-8** | US07 | Documentar agendamento diário da função no Supabase. | Conferir configuração de cron ou instrução operacional. |

### Sprint 5 · Supabase Storage e comprovantes

A quinta sprint adiciona arquivos privados. O ponto didático é que Storage também precisa de
política de acesso, não apenas de upload.

| Task | História | Entrega | Validação |
| ---- | -------- | ------- | --------- |
| **TK05-1** | US08 | Criar bucket privado `receipts`. | Confirmar que o bucket não é público. |
| **TK05-2** | US08 | Criar policies em `storage.objects` para pasta `auth.uid()`. | Tentar ler arquivo de outro usuário e confirmar bloqueio. |
| **TK05-3** | US08 | Implementar upload de PDF, PNG e JPG com limite de tamanho. | Enviar arquivo válido, arquivo grande e extensão inválida. |
| **TK05-4** | US08 | Salvar caminho do comprovante em `transactions.receipt_url` ou campo equivalente. | Conferir vínculo entre transação e arquivo. |
| **TK05-5** | US08 | Implementar geração de URL assinada com expiração curta. | Abrir URL válida e verificar expiração depois do prazo. |
| **TK05-6** | US08 | Exibir comprovante na tela de detalhes ou histórico da transação. | Abrir comprovante de uma transação própria. |
| **TK05-7** | US08, US10 | Expor contagem agregada de uploads e falhas no painel admin. | Confirmar métrica agregada sem listar arquivos individuais. |

### Sprint 6 · Analytics, admin e operação

A sexta sprint fecha a trilha transformando dados operacionais em leitura financeira. Ela também
separa visão do investidor e visão administrativa.

| Task | História | Entrega | Validação |
| ---- | -------- | ------- | --------- |

| **TK06-4** | US09 | Criar distribuição por classe de ativo e evolução patrimonial. | Conferir soma por categoria contra tabela de ativos. |
| **TK06-5** | US10 | Criar função ou view administrativa para contas ativas e AUM agregado. | Confirmar que a consulta não retorna posições individuais. |
| **TK06-6** | US10 | Proteger painel admin por `role = 'admin'`. | Testar acesso com usuário comum e administrador. |
| **TK06-7** | US10 | Exibir status de Auth, banco, cotações, Storage e jobs no admin. | Simular falha operacional e conferir indicador visual. |
| **TK06-8** | US09, US10 | Revisar responsividade de analytics e admin com dados reais. | Testar mobile e desktop com tabelas largas. |
| **TK06-9** | US09, US10 | Documentar limites conhecidos, riscos e próximos passos técnicos. | Atualizar página de próximos passos e checklist de publicação. |

Depois que uma task entra nessa tabela, ela precisa ser pequena o bastante para virar spec,
branch, pull request e validação. O lembrete abaixo resume o critério prático para não deixar o
backlog escorregar de volta para uma lista de desejos.

<Aside type="tip" title="Do backlog ao código">
  A task pronta para implementação deve citar história, arquivos, contrato de dados e validação.
  Se qualquer um desses quatro itens estiver ausente, ainda é planejamento, não trabalho executável.
</Aside>

## Desafio

## Perguntas de revisão

### Backlog e execução

1. **Por que uma task precisa apontar uma validação objetiva?**

   <details>
     <summary>Possível resposta</summary>

     Porque a validação define como a equipe reconhece que a entrega funciona. Sem isso, a revisão
     depende de interpretação e a task pode parecer pronta mesmo sem cumprir a história.
   </details>

2. **Qual é a diferença entre a Sprint 1 e as sprints BaaS seguintes?**

   <details>
     <summary>Possível resposta</summary>

     A Sprint 1 cria o contrato visual estático. As sprints seguintes conectam esse contrato a
     autenticação, banco, RLS, funções, Storage e dados reais.
   </details>

### Segurança e privacidade

3. **Por que RLS aparece como task explícita, e não como detalhe de implementação?**

   <details>
     <summary>Possível resposta</summary>

     Porque isolamento por investidor é requisito central do produto. Se as policies não forem
     criadas e testadas, o sistema não atende à promessa de privacidade financeira.
   </details>

4. **Por que o painel admin deve usar métricas agregadas?**

   <details>
     <summary>Possível resposta</summary>

     Porque administração operacional não exige acesso irrestrito a posições individuais. Métricas
     agregadas reduzem exposição de dados sensíveis e mantêm coerência com a arquitetura segura.
   </details>
