Este tópico apresenta um mapa de decisão para escolher pacotes npm em aplicações web. A proposta não é listar tudo que existe no registro, mas separar as famílias mais úteis para projetos didáticos e profissionais: ferramentas de build, clientes HTTP, validação, testes, gráficos, autenticação, banco de dados, BaaS e utilidades de domínio.

## Objetivo

Compreender como avaliar pacotes npm por função, risco e encaixe no projeto, diferenciando biblioteca local, ferramenta de desenvolvimento, API nativa e serviço remoto. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar pacotes instalados, Web APIs nativas, APIs do Node.js e serviços externos.
- Escolher uma família de pacote a partir da necessidade real da aplicação.
- Reconhecer pacotes já cobertos pelo guia e candidatos relevantes para páginas futuras.
- Avaliar custo de manutenção, segurança, tamanho de bundle e acoplamento antes de instalar.
- Planejar uma integração sem transformar o `package.json` em uma coleção de dependências sem dono.

## Modelo Mental de Escolha

Toda instalação precisa responder a duas perguntas: qual problema o pacote resolve e em que momento ele roda. Um pacote pode existir apenas no desenvolvimento, entrar no bundle do navegador, executar no servidor ou representar um serviço remoto com credenciais e dados próprios.

O fluxo abaixo ajuda a decidir antes de rodar `npm install`:

<Mermaid title="Fluxo de decisão antes de instalar um pacote npm">
{`
flowchart TD
  A["Tenho uma necessidade"] --> B{"Existe API nativa?"}
  B -->|"Sim"| C["Use Web API<br/>ou Node.js API"]
  B -->|"Não"| D{"É ferramenta<br/>de projeto?"}
  D -->|"Sim"| E["devDependency<br/>Vite, Vitest, ESLint"]
  D -->|"Não"| F{"Vai para o<br/>código final?"}
  F -->|"Sim"| G["dependency<br/>Axios, Zod, D3, ECharts"]
  F -->|"Não"| H["script ou npx<br/>uso pontual"]
  G --> I{"Depende de<br/>serviço externo?"}
  I -->|"Sim"| J["SDK + contrato remoto<br/>Supabase, Firebase"]
  I -->|"Não"| K["Biblioteca local<br/>utilitário ou UI"]
`}
</Mermaid>

O ponto decisivo está na fronteira entre biblioteca e serviço. `chart.js` roda no navegador e depende dos dados que a aplicação entrega; `firebase` e `@supabase/supabase-js` conectam o front-end a uma plataforma externa, com autenticação, regras de acesso, banco e configuração fora do repositório.

<Aside type="caution" title="Dica de IA: Peça a justificativa antes do comando">
  Assistentes costumam sugerir pacotes por popularidade sem verificar se uma API nativa já resolve o problema. Em front-end, isso aparece quando `fetch()`, `URLSearchParams`, `Intl`, `crypto.randomUUID()` ou `structuredClone()` seriam suficientes.

  **Prompt:** *"Antes de sugerir `npm install`, compare uma solução com API nativa e uma solução com pacote externo para este caso; inclua tamanho, suporte nos ambientes alvo, manutenção e um exemplo mínimo das duas opções."*
</Aside>

## Pacotes Já Cobertos no Guia

O recorte atual do guia prioriza pacotes que aparecem cedo em aplicações web: criar projeto, configurar ferramentas de desenvolvimento, simular API, consumir HTTP, validar dados, desenhar gráficos e usar BaaS. A tabela liga cada necessidade à página correspondente.

| Necessidade | Página do guia | Papel no projeto | Alternativa nativa ou conceitual |
| --- | --- | --- | --- |
| Testar, lintar, formatar e checar tipos | [Pacotes de Desenvolvimento](../../dev/dev-dependencies/) | Ferramentas locais para terminal e CI. | Scripts manuais e revisão humana, com menos repetibilidade. |
| Criar e empacotar front-end | [Vite](../../build/vite/) | Ferramenta de desenvolvimento e build. | Servir arquivos estáticos manualmente, com menos ergonomia. |
| Simular uma API REST | [JSON Server](../../mock/json-server/) | Servidor local de prototipagem. | API real em Express, Fastify ou outro back-end. |
| Consumir HTTP com interceptores | [Axios](../../http/axios/) | Cliente HTTP instalado na aplicação. | `fetch()` do navegador e do Node.js moderno. |
| Validar dados externos | [Zod](../../validation/zod/) | Schema runtime com tipos derivados. | Validação manual pequena ou contrato já validado no servidor. |
| Exibir gráficos em Canvas | [Chart.js](../../ui/chartjs/) | Biblioteca de visualização no front-end. | Canvas API, SVG manual ou tabelas HTML. |
| Criar visualização SVG sob medida | [D3.js](../../ui/d3/) | Biblioteca de escalas, eixos, seleções e data join. | SVG manual, Canvas API ou biblioteca declarativa. |
| Montar dashboard declarativo | [Apache ECharts](../../ui/echarts/) | Biblioteca de gráficos com séries, tooltip e legenda prontos. | Chart.js para gráficos simples ou D3 para desenho sob medida. |
| Renderizar mapas interativos | [Leaflet](../../ui/leaflet/) | Biblioteca de mapas 2D com tiles e camadas. | Imagem estática, iframe de provedor ou MapLibre GL. |
| Usar PostgreSQL e Auth gerenciado | [Supabase](../../../cloud/supabase/) | Serviço BaaS com SDK JavaScript. | API própria com banco PostgreSQL. |
| Usar NoSQL em tempo real e Auth | [Firebase](../../../cloud/firebase/) | Plataforma BaaS com SDK JavaScript. | API própria ou outro BaaS. |

Quando uma página do guia usa pacote e serviço ao mesmo tempo, leia a visão geral antes do tutorial específico. Em BaaS, por exemplo, a instalação do SDK é só a ponta local de um contrato que também envolve painel, chaves, regras de segurança e dados hospedados.

## Famílias Relevantes Para Expansão

Nem todo pacote relevante precisa virar página imediatamente. Um bom candidato a tópico é aquele que ensina uma decisão recorrente, aparece em mais de um projeto ou introduz um contrato novo que o aluno precisa auditar.

A tabela abaixo separa famílias que costumam merecer cobertura quando o guia avançar:

| Família | Exemplos de pacotes | Quando estudar | Risco didático principal |
| --- | --- | --- | --- |
| **Validação de dados** | [Zod](../../validation/zod/), Valibot, Yup | Quando payloads externos entram na aplicação. | Confundir tipo TypeScript com validação em tempo de execução. |
| **Testes** | [Vitest](../../dev/dev-dependencies/), Playwright, Testing Library | Quando o projeto precisa provar comportamento. | Escrever testes que só repetem a implementação. |
| **Formatação e lint** | Biome, [ESLint e Prettier](../../dev/dev-dependencies/) | Quando a equipe precisa padronizar código e CI. | Tratar ferramenta como gosto pessoal, não como contrato coletivo. |
| **Estado e cache de servidor** | TanStack Query, SWR | Quando telas consomem APIs com loading, erro e revalidação. | Duplicar estado remoto em variáveis locais sem regra clara. |
| **Datas e tempo** | date-fns, Day.js, Luxon | Quando há fuso horário, duração, calendário ou formatação. | Misturar data absoluta, data civil e texto formatado. |
| **ORM e banco** | Prisma, Drizzle | Quando o back-end precisa mapear entidades para tabelas. | Esconder SQL antes de entender modelo relacional. |
| **Autenticação no servidor** | Passport, Better Auth, jose | Quando o projeto assina sessões ou tokens próprios. | Copiar fluxo de login sem entender ameaça e armazenamento. |
| **UI e componentes** | Bootstrap, Tailwind, shadcn/ui | Quando a produtividade visual importa mais que CSS artesanal. | Pular fundamentos de layout, acessibilidade e semântica. |
| **Visualização de dados** | [Chart.js](../../ui/chartjs/), [D3.js](../../ui/d3/), [Apache ECharts](../../ui/echarts/) | Quando dados precisam virar gráfico, eixo, escala ou dashboard. | Escolher biblioteca por fama sem saber o nível de controle necessário. |
| **Mapas e geodados** | [Leaflet](../../ui/leaflet/), MapLibre GL | Quando a interface precisa de mapa interativo. | Usar mapa como imagem decorativa sem modelar coordenadas. |

Essas famílias também ajudam a decidir novas páginas do guia. Agora que Zod, D3, ECharts, Leaflet e pacotes de desenvolvimento têm páginas próprias, bons próximos candidatos seriam Playwright para testes de navegador, TanStack Query para estado remoto e date-fns ou Day.js para datas. Cada um tem objetivo próprio e não cabe como nota solta em uma página de Axios ou Supabase.

## Matriz de Decisão

Antes de adicionar dependência, compare a necessidade com a superfície que ela cria. A escolha fica mais clara quando a pergunta muda de “qual pacote usar?” para “qual contrato estou assumindo?”.

| Pergunta | Sinal de pacote local | Sinal de API nativa | Sinal de serviço externo |
| --- | --- | --- | --- |
| Onde roda? | No navegador ou no Node.js do projeto. | No ambiente sem instalação. | Fora do projeto, em uma plataforma hospedada. |
| Como atualiza? | Via `package.json` e *lockfile*. | Via navegador, Node.js ou runtime. | Via SDK, painel e API do provedor. |
| Que falha aparece? | Quebra de versão, bundle pesado, bug de biblioteca. | Incompatibilidade entre ambientes ou navegadores. | Quota, credencial, regra de acesso, indisponibilidade. |
| Como testar? | Testes unitários ou integração local. | Testes no ambiente alvo. | Testes com ambiente isolado, chaves e dados de teste. |
| Como remover? | Trocar imports e comandos. | Reescrever código para alternativa. | Migrar dados, regras, autenticação e chamadas de API. |

Use essa matriz principalmente em revisões de projeto. Dependências pequenas podem ser simples de instalar e difíceis de remover quando espalham tipos, componentes, hooks ou objetos de configuração por toda a base.

## Roteiro Para Avaliar um Novo Pacote

Quando um pacote parecer necessário, siga uma avaliação curta antes de incorporá-lo. O processo abaixo cabe em uma revisão de pull request e evita dependências que entram por impulso.

<Steps>
1. **Defina a necessidade**: Escreva a frase “precisamos deste pacote para…” sem citar o nome do pacote. Se a frase não sair clara, a instalação está cedo demais.
2. **Compare com a plataforma**: Verifique se Web APIs, APIs do Node.js ou código próprio pequeno resolvem o mesmo problema com menor acoplamento.
3. **Leia o contrato**: Confira documentação, tipo de módulo (ESM/CommonJS), suporte aos ambientes alvo, modelo de configuração e exemplos oficiais.
4. **Avalie manutenção e segurança**: Consulte frequência de publicação, issues abertas, licença, tamanho aproximado e alertas de vulnerabilidade.
5. **Isole a integração**: Crie uma camada pequena, como `services/api.js`, `lib/validation.ts` ou `charts/createLineChart.js`, para não espalhar detalhes do pacote.
6. **Teste o comportamento**: Cubra pelo menos um caso feliz e um caso de erro, principalmente quando o pacote lida com rede, autenticação, datas ou entrada do usuário.
</Steps>

## Exercício

Escolha uma aplicação que você já construiu ou está construindo e faça uma auditoria de dependências. O objetivo é justificar o papel de cada pacote, não remover tudo.

1. Liste os pacotes em `dependencies` e `devDependencies`.
2. Classifique cada pacote como biblioteca local, ferramenta de desenvolvimento, SDK de serviço ou utilitário de domínio.
3. Marque quais pacotes têm alternativa nativa conhecida.
4. Escolha uma dependência crítica e descreva como a aplicação falharia se ela mudasse de versão maior.
5. Proponha uma camada de isolamento para uma dependência que hoje aparece espalhada em muitos arquivos.

Uma resposta aceitável deve mostrar a decisão, o risco e a ação prática para pelo menos três pacotes:

<details>
  <summary>Possível resposta</summary>

  Em uma aplicação com `axios`, `echarts`, `vitest` e `vite`, `vite` e `vitest` ficam em `devDependencies` porque são ferramentas de desenvolvimento, build e teste. `axios` fica em `dependencies` porque participa do código executado pela aplicação e pode ser isolado em `services/http.js`. `echarts` também fica em `dependencies`, mas deve aparecer por meio de um módulo como `charts/createRevenueChart.js`, evitando que componentes de tela conheçam toda a configuração da biblioteca.
</details>

## Perguntas de revisão

As perguntas abaixo ajudam a conferir se a decisão por um pacote está conectada ao problema real do projeto.

### Classificação de dependências

1. **Qual é a diferença entre um pacote local e um serviço externo consumido por SDK?**

<details>
  <summary>Possível resposta</summary>

  Um pacote local é código instalado no projeto e versionado pelo `package.json`. Um serviço externo depende de infraestrutura fora do repositório, como banco, autenticação, regras de segurança, chaves de API e disponibilidade do provedor.
</details>

2. **Por que `vite` costuma ser `devDependency`, enquanto `axios` costuma ser `dependency`?**

<details>
  <summary>Possível resposta</summary>

  O Vite é usado para desenvolver e gerar o build, mas não é importado pela aplicação final no navegador. O Axios é importado pelo código da aplicação e participa da execução em produção.
</details>

3. **Quando uma API nativa deve ser preferida a um pacote npm?**

<details>
  <summary>Possível resposta</summary>

  Quando ela atende aos ambientes alvo, tem contrato estável e evita acoplamento extra. `fetch()`, `URL`, `URLSearchParams`, `Intl` e `crypto.randomUUID()` são exemplos comuns antes de instalar bibliotecas para tarefas equivalentes.
</details>

### Risco e manutenção

4. **Por que tamanho de bundle não é o único critério para escolher pacote?**

<details>
  <summary>Possível resposta</summary>

  Tamanho importa, mas manutenção, segurança, licença, compatibilidade, qualidade da documentação e facilidade de remoção também afetam o custo real da dependência.
</details>

5. **O que torna uma dependência difícil de remover?**

<details>
  <summary>Possível resposta</summary>

  Ela fica difícil de remover quando seus tipos, funções, componentes ou objetos de configuração aparecem espalhados em muitas camadas. Criar um módulo de integração reduz esse acoplamento.
</details>

6. **Por que um SDK de BaaS exige mais cuidado que uma biblioteca utilitária?**

<details>
  <summary>Possível resposta</summary>

  Porque o SDK representa um contrato com serviço remoto, regras de acesso, credenciais, modelo de dados e disponibilidade. Remover o SDK pode exigir migração de dados e reescrita de autenticação.
</details>
