Este tópico apresenta um panorama estruturado das principais bibliotecas e frameworks de interface de usuário (UI) do ecossistema JavaScript e TypeScript: **React**, **Vue.js**, **Angular**, **Svelte** e **SolidJS**.

Embora todos resolvam o desafio fundamental de sincronizar o estado da aplicação com a árvore de elementos do DOM no navegador, cada ferramenta adota uma filosofia arquitetural distinta: desde abstrações baseadas em Virtual DOM até modelos de reatividade fina com Signals ou compilação cirúrgica antecipada.

## Objetivo

Compreender as diferenças arquiteturais, os paradigmas de reatividade e os modelos de componentes dos principais frameworks de UI do mercado, aplicando critérios objetivos de escolha técnica. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar a abordagem de biblioteca focada em visão (React) de frameworks completos e opinados (Angular, Vue).
- Explicar o funcionamento do Virtual DOM e compará-lo com a reatividade fina (*fine-grained reactivity*) baseada em Signals.
- Descrever o modelo de compilação sem runtime pesado introduzido pelo Svelte.
- Identificar as convenções de escrita de componentes (JSX/TSX, Single-File Components `.vue` e templates HTML com diretivas).
- Avaliar ecossistema, curva de aprendizado, desempenho e manutenibilidade para selecionar o framework adequado a cada projeto.

## O Panorama dos Frameworks de UI

A evolução do desenvolvimento front-end moderno substituiu a manipulação manual do DOM (com jQuery ou `document.querySelector`) por modelos declarativos e reativos, nos quais o desenvolvedor descreve a interface como uma função do estado atual.

A tabela a seguir compara os cinco principais frameworks e bibliotecas do ecossistema:

| Framework / Lib | Filosofia central | Modelo de Reatividade | Sintaxe de Componentes | Tamanho de Runtime |
| :--- | :--- | :--- | :--- | :--- |
| **React** | Biblioteca minimalista e flexível. | Virtual DOM com reconciliação (Fiber). | JSX / TSX | Médio (~40 KB) |
| **Vue.js** | Framework progressivo e amigável. | Proxies reativos e Signals internos. | Single-File Components (`.vue`) | Leve (~33 KB) |
| **Angular** | Plataforma enterprise completa e opinada. | Signals nativos e RxJS (Zone.js opcional). | Classes TypeScript + Templates HTML | Robusto (~80+ KB) |
| **Svelte** | Compilador que elimina o Virtual DOM. | Reatividade em tempo de compilação (Runas). | Arquivos `.svelte` | Ultra-leve (~2 KB) |
| **SolidJS** | Desempenho máximo com JSX declarativo. | Signals e reatividade fina sem Virtual DOM. | JSX / TSX | Ultra-leve (~7 KB) |

Cada solução equilibra flexibilidade e convenção de forma diferente.

## Fundamentos: Virtual DOM vs Signals vs Compilação

O aspecto técnico mais determinante na arquitetura de um framework de UI é a estratégia utilizada para detectar alterações de dados e atualizar o DOM real do navegador.

### 1. Virtual DOM (React)
O framework mantém uma representação leve da interface em memória. Quando o estado muda, uma nova árvore virtual é construída e comparada com a anterior (*diffing*), aplicando apenas as diferenças no DOM real.

### 2. Signals e Reatividade Granular (Solid, Vue, Angular)
O estado é encapsulado em contêineres reativos (*signals* / *proxies*). Os nós do DOM que dependem diretamente daquele valor subscrevem-se a ele; quando o dado muda, apenas o nó específico do DOM é atualizado cirurgicamente, sem re-executar todo o componente.

### 3. Compilação Antecipada (Svelte)
O código é transformado durante o build em comandos JavaScript imperativos (`p.textContent = count`). O framework não carrega uma máquina de reconciliação em runtime no navegador.

## Anatomia de Componentes: Comparação Prática

Para ilustrar a sintaxe de cada framework, veja a implementação de um botão de contagem simples com estado reativo:

### React (JSX com Hooks)

```tsx title="src/Counter.tsx (React)"
import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((c) => c + 1)} className="btn">
      Cliques: {count}
    </button>
  );
}
```

### Vue.js (Single-File Component com Composition API)

```vue title="src/Counter.vue (Vue.js)"
<script setup>
import { ref } from 'vue';

const count = ref(0);
</script>

<template>
  <button @click="count++" class="btn">
    Cliques: {{ count }}
  </button>
</template>
```

### Angular (Componente Standalone com Signals)

```ts title="src/counter.component.ts (Angular)"
import { Component, signal } from '@angular/core';

@Component({
  selector: 'app-counter',
  standalone: true,
  template: `
    <button (click)="increment()" class="btn">
      Cliques: {{ count() }}
    </button>
  `,
})
export class CounterComponent {
  count = signal(0);

  increment() {
    this.count.update((v) => v + 1);
  }
}
```

### Svelte (Svelte 5 com Runas)

```svelte title="src/Counter.svelte (Svelte)"
<script>
  let count = $state(0);
</script>

<button onclick={() => count++} class="btn">
  Cliques: {count}
</button>
```

## Como Escolher o Framework Ideal?

A decisão por um framework deve considerar a escala da equipe, o perfil da aplicação e a longevidade técnica esperada.

A tabela a seguir sintetiza as recomendações para os cenários mais comuns:

| Cenário de Projeto | Framework Recomendado | Justificativa Técnica |
| :--- | :--- | :--- |
| **Maior mercado de trabalho e ecossistema** | **React** | Enorme volume de bibliotecas de terceiros, documentação farta e vagas profissionais. |
| **Equipes multidisciplinares e transição suave** | **Vue.js** | Separação intuitiva de template/script/style e excelente documentação oficial. |
| **Grandes corporações e padrões rígidos** | **Angular** | Estrutura unificada com roteamento, injeção de dependências e HTTP client integrados de fábrica. |
| **Dashboards embarcados e foco em performance** | **Svelte / SolidJS** | Menor consumo de memória e bundles ultra-leves sem sobrecarga de Virtual DOM. |

<Aside type="caution" title="Dica de IA: Isole as regras de negócio dos componentes">
Assistentes de código costumam acoplar chamadas de API, regras de validação e cálculos matemáticos complexos diretamente dentro do estado local dos componentes. Mantenha essas regras em funções TypeScript puras em `services/` ou `domain/`.

**Prompt:** *"Refatore o componente abaixo separando a lógica de negócio e as chamadas assíncronas em um serviço independente testável, mantendo o componente de UI apenas com a responsabilidade de apresentação."*
</Aside>

## Exercício

Analise as afirmativas abaixo e classifique cada uma como Verdadeira ou Falsa, justificando as falsas:

1. O React atualiza o DOM real através de comparação (*diffing*) de árvores no Virtual DOM.
2. O Svelte inclui uma máquina virtual pesada de reconciliação de Virtual DOM no bundle final do navegador.
3. No Vue 3 (Composition API), a função `ref()` cria um contêiner reativo baseado em JavaScript Proxies.
4. O Angular exige a instalação de pacotes externos de terceiros para obter roteamento básico e formulários reativos.

<details>
  <summary>Possível resposta</summary>

  1. **Verdadeira**: O React utiliza o Virtual DOM e o algoritmo Fiber para reconciliar e atualizar apenas os nós alterados.
  2. **Falsa**: O Svelte é um compilador que transforma os componentes em código imperativo cirúrgico sem incluir um runtime de Virtual DOM no bundle.
  3. **Verdadeira**: `ref()` e `reactive()` utilizam Proxies nativos para interceptar leituras e escritas de propriedades.
  4. **Falsa**: O Angular é uma plataforma completa que fornece `@angular/router`, `@angular/forms` e `@angular/common/http` como módulos oficiais de primeira classe.
</details>

## Desafio

Explique o conceito de *Fine-grained Reactivity* (Reatividade de Granularidade Fina) presente no SolidJS e nos novos Signals do Angular/Vue, contrastando com o modelo de re-renderização por componente do React.

<details>
  <summary>Possível resposta</summary>

  No modelo do React, quando o estado de um componente é atualizado via `useState`, a função inteira do componente é re-executada, gerando um novo nó na árvore virtual e disparando o processo de diffing com todos os nós filhos.

  Na reatividade de granularidade fina (*fine-grained reactivity*), a função do componente é executada apenas **uma vez** durante a montagem. Os Signals criam conexões diretas entre o dado e o nó específico do DOM real que o renderiza. Quando o valor do Signal muda, apenas a instrução de atualização do nó vinculado é disparada, sem re-executar o componente ou inspecionar elementos vizinhos.
</details>

## Perguntas de revisão

Responda às questões para consolidar o aprendizado:

1. **Qual é a principal diferença entre uma biblioteca como o React e um framework completo como o Angular?**
   <details>
     <summary>Possível resposta</summary>
     O React foca essencialmente na camada de visualização e delega roteamento, validação e clientes HTTP a pacotes externos escolhidos pelo desenvolvedor. O Angular fornece uma plataforma integrada e opinada com todas essas ferramentas padronizadas.
   </details>

2. **Como a abordagem do Svelte impacta o tamanho final do arquivo JavaScript entregue ao usuário?**
   <details>
     <summary>Possível resposta</summary>
     Como o Svelte compila o código em instruções nativas e não envia uma biblioteca de Virtual DOM para o navegador, o tamanho do bundle inicial é significativamente menor, acelerando o tempo de carregamento e o First Contentful Paint (FCP).
   </details>

3. **O que são Single-File Components (SFCs) no Vue.js?**
   <details>
     <summary>Possível resposta</summary>
     São arquivos com extensão `.vue` que encapsulam a lógica (`<script>`), a estrutura visual (`<template>`) e os estilos com escopo local (`<style scoped>`) de um componente em um único documento coeso.
   </details>

4. **Por que o isolamento de lógica em serviços agnósticos de framework é uma boa prática de arquitetura?**
   <details>
     <summary>Possível resposta</summary>
     Porque permite que regras de negócio e integrações de API sejam testadas sem a necessidade de renderizar componentes em navegadores ou mocks complexos, além de facilitar migrações futuras de framework com baixo impacto no domínio.
   </details>
