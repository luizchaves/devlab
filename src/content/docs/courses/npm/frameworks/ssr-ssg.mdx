Este tópico apresenta as estratégias modernas de renderização e os principais **meta-frameworks full-stack** do ecossistema JavaScript e TypeScript: **Next.js**, **Nuxt**, **Astro**, **Remix** (React Router) e **SvelteKit**.

A criação de Single-Page Applications (SPAs) clássicas no modelo puramente executado no cliente (*Client-Side Rendering*) revelou limitações importantes em SEO, tempo até o primeiro conteúdo visível (FCP) e peso de JavaScript enviado a dispositivos móveis. Os meta-frameworks resolvem essas limitações movendo a geração de HTML para o servidor ou para o momento do build.

## Objetivo

Compreender os diferentes modelos de renderização da web moderna e a proposta de valor dos meta-frameworks full-stack, escolhendo a estratégia adequada para cada tipo de produto digital. Ao final do tópico, o leitor deve ser capaz de:

- Diferenciar com precisão as estratégias CSR (*Client-Side Rendering*), SSR (*Server-Side Rendering*), SSG (*Static Site Generation*) e ISR (*Incremental Static Regeneration*).
- Explicar o processo de hidratação (*hydration*) e os custos de enviar JavaScript excessivo ao cliente.
- Descrever a **Arquitetura de Ilhas** (*Islands Architecture*) popularizada pelo Astro.
- Identificar as características de meta-frameworks consagrados (Next.js para React, Nuxt para Vue, Astro para sites orientados a conteúdo).
- Avaliar métricas de Core Web Vitals (LCP, INP, CLS) para justificar a escolha de renderização no servidor ou geração estática.

## Estratégias de Renderização: CSR vs SSR vs SSG vs Ilhas

A tabela abaixo compara o momento em que o HTML é gerado, o impacto em SEO e o consumo de infraestrutura:

| Estratégia | Onde e quando o HTML nasce | Vantagens | Desvantagens | Cenário típico |
| :--- | :--- | :--- | :--- | :--- |
| **CSR (Client-Side Rendering)** | No navegador do usuário, após baixar e rodar o bundle `.js`. | Transições instantâneas entre rotas após o carregamento inicial. | SEO frágil, tela em branco inicial em conexões lentas. | Painéis administrativos internos (Dashboards autenticados). |
| **SSR (Server-Side Rendering)** | No servidor Node.js/Edge, a cada requisição HTTP do usuário. | HTML completo no primeiro byte (ótimo SEO e FCP), dados sempre frescos. | Maior custo de servidor e latência inicial (TTFB). | Feeds sociais personalizados, e-commerces com estoque dinâmico. |
| **SSG (Static Site Generation)** | No servidor de build (`npm run build`), antes do deploy. | Hospedagem barata em CDN global, TTFB mínimo e segurança máxima. | Requer novo build para atualizar conteúdos estáticos. | Documentações técnicas, blogs, portais institucionais e DevLab. |
| **ISR (Incremental Static Regeneration)** | No build inicial, com revalidação assíncrona sob demanda no servidor. | Velocidade de CDN estático com atualização periódica sem rebuild total. | Exige infraestrutura compatível (Vercel ou servidores Node.js). | Portais de notícias e grandes catálogos de produtos. |
| **Arquitetura de Ilhas (Islands)** | HTML estático gerado no build; apenas componentes isolados baixam JS. | *Zero JavaScript* por padrão; hidratação parcial pontual. | Não é voltada para SPAs ricas com estado global contínuo. | Portais de conteúdo, marketing sites e e-commerces editoriais. |

## O Processo de Hidratação (*Hydration*)

No SSR tradicional, o servidor entrega um documento HTML completo e visualmente pronto. No entanto, os botões e formulários ainda não respondem a cliques até que o arquivo JavaScript da aplicação seja baixado, parseado e executado pelo navegador.

O processo pelo qual o framework associa ouvintes de evento (*event listeners*) e estado reativo à árvore HTML já existente é chamado de **Hidratação** (*Hydration*).

### O Custo da Hidratação Total
Em frameworks clássicos, a página inteira precisa ser hidratada de uma só vez (*all-or-nothing hydration*), consumindo tempo de CPU em dispositivos móveis modestos e prejudicando a métrica **INP (Interaction to Next Paint)**.

### A Solução: Arquitetura de Ilhas
O **Astro** introduziu o conceito de hidratação parcial (*Partial Hydration*). Todo o cabeçalho, texto, rodapé e artigos são entregues como HTML puro sem um único byte de JavaScript. Apenas os componentes que necessitam de interatividade (como um carrinho de compras ou um carrossel de fotos) são hidratados explicitamente:

```astro title="src/pages/index.astro (Exemplo no Astro)"
---
import HeaderEstilo from '../components/Header.astro';
import CarrinhoInterativo from '../components/Carrinho.jsx';
import Rodape from '../components/Footer.astro';
---

<!-- HTML puro estático sem JS -->
<HeaderEstilo />

<main>
  <h1>Loja Virtual</h1>
  <p>Conteúdo estático de alta performance.</p>

  <!-- Ilha interativa hidratada apenas quando visível na tela -->
  <CarrinhoInterativo client:visible />
</main>

<Rodape />
```

## Panorama dos Meta-frameworks Modernos

Os meta-frameworks adicionam roteamento baseado em arquivos (*file-system routing*), renderização híbrida, rotas de API (*endpoints*) e otimização de imagens sobre as bibliotecas de base:

A tabela a seguir apresenta os líderes de cada ecossistema:

| Meta-framework | Biblioteca Base | Paradigma de Roteamento | Ponto Forte |
| :--- | :--- | :--- | :--- |
| **Next.js** | React | `app/` (App Router com Server Components). | Padrão da indústria corporativa para React, Server Actions e Edge compute. |
| **Nuxt** | Vue.js | `pages/` (baseado no Vue Router e Nitro). | Auto-imports de componentes, excelente experiência de desenvolvimento (DX). |
| **Astro** | Agnóstico (Astro, React, Vue, Svelte) | `src/pages/` (Arquitetura de Ilhas). | Desempenho imbatível para sites de conteúdo, blogs e documentações. |
| **Remix / React Router** | React | Rotas aninhadas com `loader` e `action`. | Foco estrito em Web Standards (Formulários HTTP nativos e mutations sem cascata). |
| **SvelteKit** | Svelte | `src/routes/` com arquivos `+page.svelte`. | Roteamento rápido, adaptadores para múltiplos hosts (Node, Cloudflare, Vercel). |

## React Server Components (RSC) vs Client Components

No Next.js moderno (App Router), os componentes React são divididos em dois mundos:

1. **Server Components (Padrão)**: Executam **exclusivamente no servidor**. Eles podem acessar bancos de dados diretamente, ler arquivos do sistema operacional e manter chaves de API secretas sem enviar nenhum código fonte para o cliente.
2. **Client Components (`'use client'`)*: Componentes tradicionais que utilizam hooks de estado (`useState`, `useEffect`) ou ouvem eventos do usuário (`onClick`, `onChange`).

```tsx title="app/usuarios/page.tsx (Server Component no Next.js)"
import prisma from '@/lib/prisma';
import BotaoSeguir from './BotaoSeguir'; // Client Component

// Este código executa direto no servidor sem enviar Prisma para o navegador
export default async function UsuariosPage() {
  const usuarios = await prisma.user.findMany();

  return (
    <main className="p-8">
      <h1 className="text-2xl font-bold">Lista de Usuários</h1>
      <ul className="space-y-4">
        {usuarios.map((user) => (
          <li key={user.id} className="flex justify-between border-b py-2">
            <span>{user.name} ({user.email})</span>
            <BotaoSeguir userId={user.id} />
          </li>
        ))}
      </ul>
    </main>
  );
}
```

<Aside type="caution" title="Dica de IA: Não use 'use client' no topo de todas as páginas">
Assistentes desatualizados tendem a adicionar a diretiva `'use client'` em todas as páginas para contornar erros de hooks, transformando o Next.js em uma SPA tradicional pesada. Mova a diretiva apenas para os pequenos botões e formulários que realmente precisam de interatividade.

**Prompt:** *"Analise a árvore de componentes desta rota do Next.js e isole as interações do usuário em componentes-folha com `'use client'`, mantendo o componente pai como Server Component assíncrono."*
</Aside>

## Exercício

Classifique qual estratégia de renderização (CSR, SSR, SSG ou Arquitetura de Ilhas) é a mais adequada para cada um dos cenários abaixo, justificando a resposta:

1. Um blog de artigos de tecnologia que publica 3 novos textos por semana.
2. O painel interno de faturamento de uma empresa acessível apenas via login administrativo.
3. A página de produto de um grande e-commerce com promoções relâmpago e estoque que varia por segundo.
4. Um portal de documentação técnica com centenas de páginas e busca local rápida.

<details>
  <summary>Possível resposta</summary>

  1. **SSG (ou Ilhas com Astro)**: O conteúdo não muda a cada segundo; gerar HTML estático no build garante velocidade máxima em CDN e custo de hospedagem quase nulo.
  2. **CSR (Client-Side Rendering)**: O painel não requer indexação por mecanismos de busca (SEO) e o estado da aplicação é interativo e protegido por sessão do usuário.
  3. **SSR (Server-Side Rendering)**: É fundamental entregar o preço e a disponibilidade exatos no primeiro HTML para evitar exibir produtos esgotados, mantendo boa indexação no Google.
  4. **SSG (Static Site Generation)**: Como o próprio DevLab, a documentação é estável entre releases e se beneficia de HTML estático ultra-rápido com busca indexada no cliente.
</details>

## Desafio

Explique a diferença entre **hidratação progressiva/parcial** e **hidratação total clássica**, detalhando como diretivas de cliente no Astro (como `client:idle` e `client:media`) colaboram para a pontuação de Core Web Vitals no Google PageSpeed.

<details>
  <summary>Possível resposta</summary>

  Na hidratação total clássica, o navegador é obrigado a baixar e executar todo o código JavaScript de todos os componentes da página logo no carregamento inicial, bloqueando a thread principal e atrasando a capacidade de resposta (INP / TBT).

  Com a hidratação parcial e controlada por diretivas do Astro:
  - `client:load`: Hidrata o componente prioritário imediatamente ao carregar.
  - `client:idle`: Aguarda a página terminar de carregar e a thread principal ficar ociosa (`requestIdleCallback`) antes de rodar o JS do componente.
  - `client:visible`: Baixa e hidrata o JavaScript do componente apenas quando o usuário rolar a página e o elemento entrar na janela de visualização (`IntersectionObserver`).
  - `client:media="(max-width: 768px)"`: Hidrata apenas se a consulta de mídia CSS for atendida (ex: um menu móvel que não precisa de JS no desktop).

  Essa estratégia reduz o volume de JavaScript inicial a quase zero, garantindo pontuações máximas em métricas de performance.
</details>

## Perguntas de revisão

Responda às questões para validar a fixação dos conceitos:

1. **Por que o SSG oferece custos de hospedagem menores e maior resiliência em picos de tráfego comparado ao SSR?**
   <details>
     <summary>Possível resposta</summary>
     Porque os arquivos HTML são gerados previamente e distribuídos por redes globais de entrega de conteúdo (CDNs). Nenhuma requisição de usuário exige execução de código Node.js no servidor ou consultas em tempo real ao banco de dados durante a navegação.
   </details>

2. **Qual é o papel dos React Server Components (RSC) introduzidos no Next.js App Router?**
   <details>
     <summary>Possível resposta</summary>
     Permitir que componentes React executem exclusivamente no servidor, eliminando o envio de seu código JavaScript para o cliente e possibilitando acesso direto e seguro a bancos de dados e segredos de ambiente.
   </details>

3. **O que é Time to First Byte (TTFB) e como ele é afetado pelo SSR em comparação com o SSG?**
   <details>
     <summary>Possível resposta</summary>
     TTFB é o tempo decorrido entre a requisição do navegador e o primeiro byte de resposta retornado pelo servidor. No SSG, o TTFB é quase instantâneo porque o arquivo estático já está pronto no CDN. No SSR, o TTFB é maior porque o servidor precisa processar código e consultar dados antes de responder.
   </details>

4. **Como o Remix aborda o envio de formulários e mutações de dados?**
   <details>
     <summary>Possível resposta</summary>
     Ele resgata o modelo clássico da web baseado em elementos `<form>` nativos e requisições HTTP `POST`, processando as mutações em funções `action` no servidor e revalidando automaticamente os `loaders` das rotas sem a necessidade de gerenciar estados complexos de loading manualmente.
   </details>
