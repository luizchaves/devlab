Este tópico apresenta pacotes consagrados que costumam entrar em `devDependencies`: ferramentas de teste, lint, formatação e tipagem. Eles não resolvem uma regra de negócio da aplicação, mas sustentam o desenvolvimento, a revisão e o CI.

## Objetivo

Compreender o papel de pacotes de desenvolvimento em projetos npm, diferenciando ferramentas que rodam no terminal de bibliotecas importadas pela aplicação final. Ao final do tópico, o leitor deve ser capaz de:

- Explicar por que Vitest, ESLint, Prettier e TypeScript costumam ficar em `devDependencies`.
- Instalar ferramentas de desenvolvimento com a flag `-D`.
- Diferenciar dependência de execução, ferramenta de build e ferramenta de qualidade.
- Planejar scripts para teste, lint, formatação e checagem de tipos.
- Avaliar quando uma ferramenta deve entrar no projeto inteiro ou em um exemplo isolado.

## Modelo Mental

Uma dependência de desenvolvimento participa do processo de construir, testar ou revisar o projeto. Ela pode ser indispensável para a equipe, mas não precisa ser entregue ao usuário como parte do código final.

O diagrama abaixo separa o fluxo de desenvolvimento do fluxo de execução:

<Mermaid title="Diferença entre dependencies e devDependencies">
{`
flowchart TD
  A["package.json"] --> B["dependencies<br/>código usado em runtime"]
  A --> C["devDependencies<br/>ferramentas de projeto"]
  B --> D["Aplicação final<br/>bundle ou servidor"]
  C --> E["Terminal e CI<br/>test, lint, build, typecheck"]
  E --> F["Artefato validado<br/>dist ou deploy"]
`}
</Mermaid>

Essa separação não torna `devDependencies` menos importantes. Um projeto pode depender de Vitest e ESLint para aceitar mudanças com segurança, mesmo que essas ferramentas não sejam importadas pelo navegador em produção.

<Aside type="tip" title="Dependência de desenvolvimento também é contrato">
  Colocar um pacote em `devDependencies` não significa que ele seja descartável. A versão de TypeScript, a configuração do ESLint e o executor de testes influenciam como o código é escrito, revisado e aceito no CI.
</Aside>

## Pacotes Consagrados

Os pacotes abaixo aparecem com frequência em projetos JavaScript e TypeScript. A coluna “papel” indica por que cada um costuma ser instalado como dependência de desenvolvimento.

| Pacote | Papel | Script comum | Por que é `devDependency`? |
| --- | --- | --- | --- |
| **Vitest** | Testes unitários e de integração. | `test` | Roda no terminal e no CI para verificar comportamento. |
| **ESLint** | Análise estática e regras de qualidade. | `lint` | Inspeciona o código-fonte, mas não entra no runtime da aplicação. |
| **Prettier** | Formatação automática de código. | `format` | Padroniza arquivos durante edição ou CI. |
| **TypeScript** | Tipagem estática e compilação. | `typecheck` ou `build` | Checa tipos e pode gerar JavaScript antes da execução final. |

Essas ferramentas podem coexistir. Um projeto TypeScript comum usa TypeScript para tipos, ESLint para regras semânticas, Prettier para formatação e Vitest para comportamento.

## Instalando Como Dev

A flag `-D` registra o pacote em `devDependencies`. Use-a quando o pacote é chamado por script, CLI, build ou CI, mas não é importado como parte da aplicação final.

<PackageManagerTabs package="vitest eslint prettier typescript" dev />

Depois da instalação, os scripts tornam a ferramenta previsível para toda a equipe. O nome do script vira a interface pública do projeto.

```json title="Exemplo de scripts"
{
  "scripts": {
    "test": "vitest run",
    "lint": "eslint .",
    "format": "prettier . --write",
    "typecheck": "tsc --noEmit"
  }
}
```

O comando abaixo mostra como a equipe executa as verificações sem decorar o binário de cada pacote:

<PackageManagerTabs run="test" />

## Decidindo Onde o Pacote Entra

A mesma ferramenta pode ter papéis diferentes dependendo do projeto. O critério é observar quem importa, quem executa e em qual ambiente a ferramenta precisa existir.

| Pergunta | Sinal de `dependencies` | Sinal de `devDependencies` |
| --- | --- | --- |
| O código importa o pacote durante a execução? | Sim, como `import axios from 'axios'`. | Não, apenas CLI ou configuração. |
| O usuário final precisa desse código? | Sim, no bundle ou no servidor. | Não, só equipe e CI. |
| O pacote roda por script? | Pode acontecer em servidor. | Normalmente sim, como `test`, `lint` ou `build`. |
| Remover do deploy quebra a aplicação? | Sim. | Não deveria, desde que o build já tenha sido gerado. |

Em aplicações hospedadas, a distinção também afeta instalação em produção. Ambientes que instalam apenas dependências de produção esperam que o build já tenha sido feito antes.

<Aside type="caution" title="Dica de IA: Confira onde o pacote é importado">
  Assistentes podem sugerir `npm install -D` por hábito, especialmente para pacotes conhecidos de front-end. Antes de aceitar, procure se o pacote aparece em `import` de código executado pelo navegador ou servidor.

  **Prompt:** *"Classifique estes pacotes entre `dependencies` e `devDependencies`; justifique cada decisão apontando se ele é importado em runtime, executado por script ou usado apenas no CI."*
</Aside>

## Executando

Use este roteiro para experimentar a classificação em qualquer projeto npm:

<Steps>
1. Abra o `package.json` de um projeto.
2. Liste tudo que aparece em `dependencies` e `devDependencies`.
3. Procure cada pacote nos imports do código-fonte.
4. Procure cada pacote nos scripts e arquivos de configuração.
5. Reclassifique mentalmente os pacotes que parecem estar na seção errada e anote a justificativa.
</Steps>

## Exercício

Classifique os pacotes de um projeto Vite simples. O objetivo é decidir pela função, não pela fama do pacote.

1. Coloque `vite`, `typescript`, `eslint` e `vitest` em `devDependencies`.
2. Coloque `axios`, `zod`, `chart.js` ou `echarts` em `dependencies` quando forem importados pelo código da aplicação.
3. Escreva um script para cada ferramenta de desenvolvimento.
4. Explique o que quebra se `devDependencies` não forem instaladas antes do build.

Uma resposta aceitável separa execução final de ferramentas de projeto:

<details>
  <summary>Possível resposta</summary>

  `vite`, `typescript`, `eslint` e `vitest` entram em `devDependencies` porque rodam no terminal ou no CI. `axios`, `zod` e `echarts` entram em `dependencies` quando o código da aplicação importa esses pacotes em runtime. Sem `devDependencies`, o ambiente pode não conseguir testar, checar tipos ou gerar `dist/`.
</details>

## Desafio

Monte uma política de dependências para uma equipe. O objetivo é transformar a classificação em regra de revisão.

1. Defina quando usar `dependencies`.
2. Defina quando usar `devDependencies`.
3. Liste três scripts obrigatórios para o CI.
4. Explique como revisar uma mudança no `package-lock.json`.
5. Indique quando pedir justificativa para uma nova dependência.

Use a resposta abaixo como referência de política:

<details>
  <summary>Possível resposta</summary>

  A política pode exigir que todo pacote novo explique seu papel, sua alternativa nativa e onde será usado. Dependências importadas em runtime ficam em `dependencies`; CLIs de teste, lint, formatação e tipagem ficam em `devDependencies`. O CI roda `npm ci`, `npm run lint`, `npm run test` e `npm run build`.
</details>

## Perguntas de revisão

As perguntas abaixo verificam se você consegue classificar ferramentas pelo ambiente onde elas rodam.

### Classificação

1. **Por que Vitest costuma ser `devDependency`?**

<details>
  <summary>Possível resposta</summary>

  Porque ele executa testes durante desenvolvimento ou CI, mas não é importado pelo código entregue ao usuário final.
</details>

2. **Por que Axios normalmente é `dependency`, não `devDependency`?**

<details>
  <summary>Possível resposta</summary>

  Porque a aplicação importa Axios para fazer chamadas HTTP em runtime. Se ele faltar no ambiente final, o código que usa o cliente HTTP quebra.
</details>

3. **A seção `devDependencies` é menos importante que `dependencies`?**

<details>
  <summary>Possível resposta</summary>

  Não. Ela não entra no runtime final, mas define ferramentas de build, teste, lint, formatação e tipagem que sustentam a qualidade do projeto.
</details>

### Revisão de projeto

4. **O que investigar quando um pacote novo aparece em `package-lock.json`?**

<details>
  <summary>Possível resposta</summary>

  É preciso verificar quem o trouxe, se é dependência direta ou transitiva, se a seção está correta, se há vulnerabilidades e se a mudança faz sentido para o objetivo do projeto.
</details>

5. **Por que scripts são preferíveis a comandos decorados pela equipe?**

<details>
  <summary>Possível resposta</summary>

  Porque scripts documentam a interface do projeto. A equipe executa `npm run test` ou `npm run lint` sem precisar saber qual binário, flag ou configuração cada ferramenta usa por baixo.
</details>
