Este tópico propõe um projeto prático para consolidar o Guia de React. A ideia é criar um produto
pequeno, autoral e completo o suficiente para exercitar componentes, estado, efeitos, APIs,
roteamento e decisões de arquitetura.

## Objetivo

Construir uma aplicação React de ponta a ponta, aplicando os conceitos estudados no guia e
registrando decisões técnicas de forma clara. Ao final do tópico, o leitor deve ser capaz de:

- Definir escopo e domínio de uma aplicação React.
- Escolher Vite ou Next.js com justificativa.
- Implementar componentes, props, estado local e formulários.
- Integrar uma API externa com carregamento, erro e cancelamento.
- Adicionar rotas, detalhe de item e estado compartilhado.
- Planejar uma evolução com Context API, Redux Toolkit ou biblioteca de dados.

## Proposta de Produto

Escolha um domínio que você entenda. O produto precisa ter uma lista, um detalhe, um formulário,
um filtro, uma integração externa e algum estado compartilhado.

| Ideia | API externa possível | Estado compartilhado |
| ----- | -------------------- | -------------------- |
| Painel de estudos | API pública de livros ou artigos | tema, usuário, filtros salvos |
| Rastreador de hábitos | API de calendário ou clima | preferências e metas |
| Carteira de investimentos fictícia | API de cotações de demonstração | moeda, categoria selecionada |
| Catálogo de filmes | OMDb, TMDB ou API similar | favoritos e filtros |

O domínio pode mudar, mas os requisitos técnicos devem permanecer. Isso evita um projeto bonito
que não pratica os conceitos centrais do guia.

## Requisitos Técnicos

Implemente os itens abaixo em etapas pequenas. Cada entrega deve deixar a aplicação rodando.

<Steps>

1. Crie o projeto com Vite ou Next.js e registre a justificativa da escolha no `README.md`.
2. Monte a primeira tela com componentes pequenos e nomes de domínio claros.
3. Passe dados por props e renderize listas com `key` estável.
4. Adicione formulário controlado com validação mínima e mensagens acessíveis.
5. Busque dados de uma API externa com `fetch`, estados de carregamento e erro.
6. Adicione rotas para lista, detalhe e configurações.
7. Inclua Context API para tema, usuário fictício ou preferências globais.
8. Escreva uma reflexão comparando manter Context API ou migrar para Redux Toolkit.
9. Finalize com uma página de próximos passos e dívidas técnicas conhecidas.

</Steps>

## Arquitetura Recomendada

Uma aplicação Vite pode começar com a estrutura abaixo. Ela separa componentes reutilizáveis,
páginas, serviços de API, hooks próprios e contexto.

```txt title="Estrutura com Vite"
src
├── components
│   ├── AppShell.jsx
│   └── LoadingState.jsx
├── contexts
│   └── PreferencesContext.jsx
├── hooks
│   └── useRemoteItems.js
├── pages
│   ├── DashboardPage.jsx
│   ├── DetailsPage.jsx
│   └── SettingsPage.jsx
├── services
│   └── api.js
└── App.jsx
```

Em Next.js, a estrutura muda porque rotas e layouts são convenção de pastas. Essa escolha é boa
quando a navegação e a renderização por página são parte central do produto.

```txt title="Estrutura com Next.js"
src/app
├── layout.jsx
├── page.jsx
├── items
│   └── [id]
│       └── page.jsx
└── settings
    └── page.jsx
```

<Aside type="tip" title="Dica de IA: Gere o backlog antes dos componentes">
  Para o projeto final, evite pedir “crie a aplicação inteira”. Primeiro gere escopo,
  requisitos, rotas, estados de erro e critérios de aceite. Depois implemente uma etapa por vez.

  **Prompt:** *"Crie um backlog para um projeto React de painel de estudos com lista, detalhe, formulário, API externa, rotas e Context API; divida em etapas pequenas, cada uma com critério de aceite testável."*
</Aside>

## Exemplo de Serviço de API

Centralize chamadas HTTP em uma camada simples. Isso evita espalhar `fetch` por todos os
componentes e facilita trocar a API depois.

```js title="Camada de API"
export async function getJson(url, signal) {
  const response = await fetch(url, { signal });

  if (!response.ok) {
    throw new Error(`Falha HTTP: ${response.status}`);
  }

  return response.json();
}
```

Um hook próprio pode usar essa função e devolver os estados que a tela precisa renderizar.

```jsx title="Hook de dados remotos"
function useRemoteItems(url) {
  const [state, setState] = useState({ status: 'loading', data: [], error: null });

  useEffect(() => {
    const controller = new AbortController();

    getJson(url, controller.signal)
      .then((data) => setState({ status: 'success', data, error: null }))
      .catch((error) => {
        if (error.name !== 'AbortError') {
          setState({ status: 'error', data: [], error: error.message });
        }
      });

    return () => controller.abort();
  }, [url]);

  return state;
}
```

## Reflexão de Soluções

Antes de finalizar, escreva uma pequena decisão arquitetural. Ela deve responder por que você
ficou em Context API ou por que migraria para Redux Toolkit.

| Decisão | Mantém simples | Migra quando |
| ------- | -------------- | ------------ |
| Context API | poucos estados globais, pouca lógica, equipe pequena | providers demais ou re-renderizações difíceis |
| Redux Toolkit | fluxos complexos, debug por ação, equipe maior | app simples vira boilerplate |
| TanStack Query ou SWR | dados remotos dominam o projeto | cache manual começa a duplicar lógica |
